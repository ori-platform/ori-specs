# Runtime Posture Contract v1

> Status: maturity `draft`; compatibility `amendable`; adoption: none
> recorded; proof: end-to-end `none`, HIL `none`, production `none`. Record:
> [status/runtime-posture/v1.json](../status/runtime-posture/v1.json).

A runtime device's standing is read by people through several surfaces, and
each surface that re-derives it becomes a second author of a statement it has
no standing to make. This contract defines **one record of a runtime's
posture, authored and signed by the runtime, which every other component
forwards and none edits.** Its one rule above every other: **the record is a
report, and nothing in it grants, widens or restores authority anywhere.**

This version is a first cut. Its record names the runtime's device, its
installed release, its deployment profile and the commissioned binding in
force, and orders itself by a durable identity that no clock decides. It
defines how a gateway verifies, orders and carries the record, how the gateway
learns the runtime's key, and what a reader of the carried record may and may
not conclude.

## What this contract is not

- **It grants no authority.** No member of the record authorises, enables,
  approves or restores anything on any consumer, and a consumer's acceptance
  or refusal of a record changes nothing on the device. Tier D never reads it,
  and no Tier C admission consults it.
- **It states no physical authority.** The record has no member saying whether
  the runtime may actuate, and no zone member. A surface MUST NOT render the
  absence of such a member as a value, neither as "none" nor as "full". The
  commissioned binding's hash says which binding is in force, not what it
  permits; [commissioned-safety-binding/v2.md](../commissioned-safety-binding/v2.md)
  and the runtime's own health say that.
- **It is not liveness.** A `current` record says the runtime signed this
  record recently, under the bounds in [Posture state](#posture-state). It does
  not say the runtime is acting, and a gateway's heartbeat freshness is a
  separate fact under [gateway-api/v2.md](../gateway-api/v2.md).
- **A carrier's view is the carrier's assertion.** A gateway's `state`,
  `reason` and `received_at_ms` for a record are statements the gateway makes,
  outside the runtime's signature. Only the record's bytes are the runtime's,
  and only a reader holding the runtime's key from a source independent of the
  carrier can verify them; see [Carriage](#carriage).

## Identities

The contract uses four identities. Each names a different thing, and none is
read as another.

| Identity | What it names | Where it comes from |
| --- | --- | --- |
| `device_id` | The runtime device, as its provisioning names it | `device.id` of the provisioning document the runtime holds accepted, under [runtime-config/v2.md](../runtime-config/v2.md) |
| The runtime's **posture key** | The Ed25519 key that signs the record | The runtime's evidence device key, the key [evidence/v2.md](../evidence/v2.md) signs chain rows with |
| `key_identity` | One posture key, as this contract compares it in a record | `sha256:` followed by the 64 lowercase hex characters of SHA-256 over the key's RFC 8410 SubjectPublicKeyInfo DER: the 12-byte prefix `302a300506032b6570032100` followed by the raw 32-byte key |
| The **recognised key** | One holder of a posture key | The 32 key bytes with bit 255 cleared, as [ed25519-key-admission/v1.md](../ed25519-key-admission/v1.md) *Recognising a key* defines it |

`key_identity` is not the evidence key's `key_id` in any evidence contract, not
an `anchor_epoch_id` or `key_epoch_id` of
[device-provisioning/v1.md](../device-provisioning/v1.md), not a certificate's
identity, and not a device identity. A key and its negation have different
`key_identity` values and one recognised key. A posture **epoch** is one
recognised key: a new posture key is a new epoch, and nothing else is.

## The record

The record is one JSON object with exactly these members:

| Member | Value |
| --- | --- |
| `v` | The integer `1`. |
| `device_id` | The runtime's `device_id`, matching `^[A-Za-z0-9._-]{1,128}$`. |
| `release` | The SemVer `runtime_version` of the verified release bundle the running code was installed from, under [runtime-release-bundle/v1.md](../runtime-release-bundle/v1.md), matching `^(0\|[1-9][0-9]*)\.(0\|[1-9][0-9]*)\.(0\|[1-9][0-9]*)(-rc\.[1-9][0-9]*)?$` and at most 64 characters; or `null` when the running code was not installed from a verified bundle. It is never a version the code reports about itself. |
| `deployment_profile` | `development`, `staging` or `production`: the `device.deployment_profile` of the provisioning document the runtime holds accepted. |
| `commissioned_binding` | The canonical hash of the commissioned binding in force, the value the next binding's `supersedes` would name under commissioned-safety-binding/v2.md: `sha256:` followed by 64 lowercase hex characters. `null` when no binding is in force. |
| `key_identity` | The `key_identity` of the posture key that signs this record. |
| `boot_generation` | The runtime's boot generation (below). |
| `posture_seq` | The record's sequence within its boot (below). |
| `issued_at_ms` | The record's signing time in Unix milliseconds, from the runtime's signing clock (below). |
| `signature` | The Ed25519 signature, canonical padded RFC 4648 Base64 of its 64 bytes. |

**Integers.** `v`, `boot_generation`, `posture_seq` and `issued_at_ms` are each
written as a JSON integer token: the digit `0`, or a digit `1` to `9` followed
by digits, with no sign, fraction, exponent or leading zero. Each is at least
`1` and at most 2^53 − 1 (9007199254740991). `1.0`, `1e0`, `-1`, `01`, `true`
and `"1"` are not integers here.

**Strings.** Every string member is ASCII and matches its pattern above. No
string in the record needs a JSON escape, so every canonical form in the
estate, gateway-mqtt-canonical-json/v1, Profile 2 of
[signing/v2.md](../signing/v2.md) and the canonical form of evidence/v2.md,
writes the same bytes for it.

**Canonical bytes.** The record's canonical bytes are the
[gateway-mqtt-canonical-json/v1.md](../gateway-mqtt-canonical-json/v1.md)
canonical form of the object: members sorted by name, no insignificant
whitespace, and every number token kept exactly as written, as that
contract's verifier keeps it. Canonical bytes never respell a number, so a
record whose integer is written `1e0` or `1.0` has canonical bytes and is
`malformed`, not `not_canonical`. **A record is published as exactly its canonical bytes,** with
nothing before or after them. Bytes that parse to a record but are not its
canonical bytes are not a record; a receiver refuses them as `not_canonical`
under [Receiving](#receiving). One record therefore has exactly one encoding,
and its digest names it.

**Signature.** The signing input is the ASCII bytes `ori.runtime_posture.v1`,
one NUL byte, then the canonical bytes of the record without its `signature`
member. The posture key signs it with Ed25519. A verifier applies
ed25519-key-admission/v1.md to the key and verifies under
[ed25519-verification/v1.md](../ed25519-verification/v1.md); any failure is
`signature_invalid`.

**Why the evidence device key may sign it.** The rule this relies on: **every
other input the evidence device key signs either begins with `{` and contains
no NUL byte, or begins with an ASCII prefix other than
`ori.runtime_posture.v1` followed by a NUL byte.** A posture signing input
begins with the byte `o` and contains a NUL, so it is none of those inputs,
and none of them is a posture signing input; a signature made for one use
verifies for no other. The uses known when this version was written are the
chain rows of evidence/v2 and evidence/v3, signed over canonical JSON with no
prefix, and the prefixed inputs `ori.evidence.rotation.v2`,
`ori.evidence_anchor_registration.v1`, `ori.evidence_checkpoint.v1` and
`ori.evidence_delivery_envelope.v1` of the evidence and evidence-exchange
contracts. A runtime MUST NOT sign under this key any input that breaks the
rule.

## Publication

The runtime publishes the record on `ori/{device_id}/runtime/posture`, under
[gateway-api/v2.md](../gateway-api/v2.md), as an MQTT message at QoS 1 with the
retain flag set.

- **When.** At start, once its boot generation is claimed and its posture key
  is loaded; whenever any member other than `posture_seq`, `issued_at_ms` and
  `signature` would change; and at least once every 60 seconds while it runs.
  The republish interval is a fifth of check 10's 300000 ms bound, so a
  retained record a gateway receives on subscribing is within that bound by a
  margin that absorbs delivery and clock offset.
- **Coalescing.** A runtime publishes at most 2 records in any 10 seconds and at
  most 5 in any minute, both judged over sliding windows. A change that would
  exceed either waits, and only the latest content is published when the wait
  ends. Against gateway-api/v2's volume bound, a bucket that holds 5 records
  and gains one every 10 seconds, this leaves at least one record of room
  for the broker's redelivery of the retained record at a subscribe.
- **Every publication is a new record.** Each one carries `posture_seq` one
  greater than the previous record of the same boot, and a new `issued_at_ms`,
  and is signed afresh. A runtime never publishes bytes it has published
  before, apart from the MQTT client's own retransmission of an unacknowledged
  QoS 1 message.
- **Boot generation.** `boot_generation` is a durable, strictly increasing
  counter, claimed and committed to durable storage before the first record
  under it is signed, never reused within an epoch, never deleted and never
  lowered. The first is `1`. It is claimed at least once per run and may be
  claimed again within one, as when the store is reopened; every record under
  a higher generation orders above every record under a lower one. On
  ori-runtime it is the evidence ledger's boot counter.
- **Posture sequence.** `posture_seq` is `1` for the first record under a
  boot generation and counts the publications under it. It is held in memory:
  a new generation starts higher, so a lower `posture_seq` under it orders
  correctly.
- **Signing clock.** `issued_at_ms` comes from a signing clock with these
  properties: it never issues one value twice, across its signers and across
  restarts on the same store; it is strictly increasing, within a run and
  across restarts; it is durable, so a restart never issues a value at or below
  one already issued; and no value it issues is more than 30000 ms ahead of the
  runtime's wall clock when issued. A runtime without such a clock publishes no
  record. On ori-runtime it is the clock that gives `signed_at_ms` to the
  gateway-api/v2 envelopes the runtime signs, under
  [Senders](../gateway-api/v2.md#senders). Domain separation comes from the
  signing input, not the clock.
- **No record without its inputs.** While the posture key is not loaded in a
  run, or the signing clock or the boot generation cannot be claimed because
  the runtime's store is unavailable, the runtime publishes no record. It never
  publishes an unsigned record or one with a stale member. The device then
  reads `stale` at every receiver that held a record, and `unknown` at one that
  held none: a runtime store fault stops posture publication, visibly and
  failing closed.

The record's members are read from the run: `device_id`,
`deployment_profile` and `commissioned_binding` from the provisioning document
and binding the runtime holds accepted, `release` from its installation. A
document or binding accepted while the runtime runs changes the record, and
the runtime publishes the changed record as soon as coalescing allows.

## Receiving

A gateway that serves `device_id` under `gateway.device_ids` subscribes to its
posture topic, per device or under a wildcard, and judges each message in this
order. The first check that fails is the answer. A message's **receipt** is one
reading of the gateway's wall clock and one of its monotonic clock, taken when
the message is taken off the broker connection, before it is queued; check 10,
a held record's age and `received_at_ms` all use that one reading.

1. [Payload Size](../gateway-api/v2.md#payload-size): `payload_too_large`, then
   [Payload Volume](../gateway-api/v2.md#payload-volume), whose drops are
   counted and not judged further.
2. [Payload Member Rule](../gateway-api/v2.md#payload-member-rule): its seven
   reasons.
3. The bytes are not the canonical bytes of the object they parse to:
   `not_canonical`.
4. The object is not a record: a member missing, unknown or of the wrong type,
   a value outside its form, `v` not `1`: `malformed`.
5. The topic's device is not in `gateway.device_ids`: `unknown_device`. A
   gateway that subscribes per device never receives one.
6. The record's `device_id` differs from the topic's device: `device_mismatch`.
7. No posture key is pinned for the device under gateway-config/v2:
   `no_pinned_key`.
8. The record's `key_identity` is not the pinned key's: `key_mismatch`.
9. The signature fails under the pinned key: `signature_invalid`.
10. `issued_at_ms` is more than 300000 ms before the gateway's wall clock at
    receipt: `stale_timestamp`; more than 300000 ms after it:
    `future_timestamp`. This **skew bound** is 300000 ms whatever skew the
    gateway configures for envelopes under gateway-api/v2.
11. Ordering, against the **held record** for the device and the pinned key's
    recognised key (below):
    - **`accepted`**: there is no held record, or the record's
      (`boot_generation`, `posture_seq`) is strictly greater, compared as a
      pair, first by `boot_generation`. The record becomes the held record.
      Except that a strictly greater pair whose `issued_at_ms` is more than
      300000 ms, the **regression bound**, below the held record's is
      **`conflict`**: one signing clock never goes back, so both cannot be
      genuine.
    - **`replayed`**: an equal pair with identical bytes. Nothing changes.
    - **`conflict`**: an equal pair with different bytes.
    - **`lower_tuple`**: a smaller pair.

    A record that is `conflict` or `lower_tuple` leaves the held record as it
    was: only an `accepted` record replaces it. A greater pair's
    `issued_at_ms` is compared with the held record's `issued_at_ms`, never
    with the wall clock at the held record's receipt.

    While the gateway cannot read its held state, a record that passes checks
    1 to 10 is **`store_unavailable`** instead, and changes nothing.

Checks 1 to 10 change no state, and a record refused at them is counted and
otherwise ignored. Check 11 changes state only as [Posture state](#posture-state)
says. No refusal and no verdict is ever an instruction to the device, and none
is answered on any topic.

**Held state.** For each pair of a configured device and a recognised key, the
gateway holds at most one held record, its bytes, its pair, its
`issued_at_ms` and the wall clock at its receipt, and at most one sticky
reason. A sticky reason belongs to that pair, never to the device alone: a
device read under another key reads that key's state. A device removed from
`gateway.device_ids` keeps its state, which a later configuration that serves
it again resumes. It keeps this durably in its state directory under
[gateway-config/v2.md](../gateway-config/v2.md), and keeps it for every
recognised key it has held a record under, not only the pinned one. A change of
pin selects which recognised key's state is read. It never resets a state: a
key pinned again after another resumes from what it held, so an old record
under it is still `lower_tuple`. A key and its negation share one state. The
state grows only with keys pinned, which are configuration changes.

A new held record, a sticky reason set or cleared, and the pair they belong to
are written in one atomic step, durable before the gateway acts on them: staged
to a new file, synced, renamed over the old one, and the directory synced. A
store the gateway cannot read, or whose contents do not parse, makes every
configured device with a pinned key `unknown` with reason `store_unavailable`,
and nothing is accepted into it.

**The store fails closed, for one of two causes.**

- **Unreadable.** A store the gateway cannot read, at start or later, holds no
  state the gateway knows. It is unavailable until a read of it succeeds; the
  gateway retries the read off the receive path, and the state the read finds
  is then the state in force. A held record that the gateway received earlier
  in the same run, recognised by its exact bytes, keeps the monotonic reading
  of its receipt.
- **Unwritten.** A write that fails, or one still outstanding 1000 ms after it
  began on the gateway's monotonic clock, leaves the gateway's state in memory
  known but not durable. The message whose write it was keeps its verdict and
  its change in memory, so a `conflict` or `lower_tuple` is not lost. The store
  is then unavailable until a write of the state in memory completes: the
  outstanding write completing late, which wrote that state, or a fresh write
  of it. The gateway retries that write no sooner than 1000 ms after the
  previous attempt began, never once per message, with at most one write
  outstanding. It never reads the store while it is unwritten.

While the store is unavailable for either cause, every configured device with a
pinned key reads `unknown` with reason `store_unavailable`, a record that passes
checks 1 to 10 is `store_unavailable` and changes nothing, and the gateway reports
`degraded` in its heartbeat status and its site health. At most one read or
write of the store is outstanding at a time, and none starts while another is.
A record that arrives for a device while a write for that device is outstanding
waits for that write; if the write is still outstanding at its 1000 ms bound,
the record is `store_unavailable`. A message that changes nothing durable, as a
sticky reason set again to the reason already held does, writes nothing and so
cannot fail a write. A receiver needs no in-order or synchronous handling across
devices: ordering is by pair, and the compare and the store for one device are
one atomic step.

**Counting.** A gateway counts each refusal and each `lower_tuple` and
`conflict` by reason, and counts `replayed` apart from them, since a retained
message is redelivered at every subscribe. A count carries no device
identifier and no part of the record. A gateway logs the counts, and reports
them in its health once its health names a field for them.

## Posture state

A gateway reports one posture state for each configured device, read from the
state its pinned key's recognised key selects:

- **`unknown`**, with a `reason`:
  - `no_pinned_key`: no posture key is pinned for the device;
  - `store_unavailable`: the gateway cannot read its held state;
  - `no_record`: no record is held under the pinned key;
  - `lower_tuple_seen`: a record passed checks 1 to 10 and was `lower_tuple`;
  - `conflict`: a record passed checks 1 to 10 and was `conflict`.

  `lower_tuple_seen` and `conflict` are **sticky**: each is held durably with
  its device and recognised key, survives a gateway restart and every change of
  pin, and clears only when a record is `accepted` under that same recognised
  key. A key pinned for the first time has no sticky reason. A record that is `replayed`, or
  refused at checks 1 to 10, clears nothing. A later sticky reason replaces an
  earlier one.

  The reasons are listed in precedence order, and the first that holds is
  the reason: a device with no pinned key is `no_pinned_key` whatever the
  store's condition, and an unreadable store hides whether a record or a
  sticky reason is held.
- **`current`**: a record is held, no sticky reason is held, and its age is at
  most 900000 ms.
- **`stale`**: a record is held, no sticky reason is held, and its age is more
  than 900000 ms or cannot be computed.

**Age.** A held record's age is its age at receipt, the gateway's wall clock at
receipt minus `issued_at_ms`, taken as `0` when negative, plus the time elapsed
since receipt: the greater of the elapsed time on the gateway's monotonic clock
and on its wall clock. Taking the greater keeps a record from staying `current`
across a suspend or pause the monotonic clock did not count, and lets a forward
step of the wall clock stale it early, which fails safe. Check 10 bounds the first term
at 300000 ms. A later step of the gateway's wall clock never freshens a held
record. A gateway's monotonic clock does not carry
across its restarts, so after a restart the age of a record received before it
cannot be computed: the record reads `stale` until a fresh one is accepted. The
retained copy the broker redelivers on subscribing is `replayed` while it
passes check 10, and `stale_timestamp` once it is older.

## Key pinning and discovery

The gateway learns each runtime's posture key from its own configuration, under
`posture.runtime_keys` in gateway-config/v2.md, and from nowhere else. It never
learns or replaces a key from the posture topic, any other MQTT topic, a
product, or a record.

**First installation is the installer's to authenticate.** Whoever installs a
pin reads the key at the runtime device itself, through the
`runtime_device_key` operation of [operator-socket/v3.md](../operator-socket/v3.md),
and installs it in the gateway's configuration. That operation is public-key
discovery, not enrolment: it proves which key the runtime holds, and neither
which device the installer intended nor which site it is at. The pin is as
trustworthy as that commissioning act and the gateway's configuration file.

**Rotation is a new pin.** A runtime whose posture key changes, as when its
sealed key cannot be unsealed and a new one is made, signs under a new
recognised key, which is a new epoch. Its records are `key_mismatch` until the
new key is pinned. There is no overlap and no staged rotation in this version:
from the new key's first use until the new pin, the device's state is what the
old pin's state reads, which goes `stale`.

## Carriage

A gateway carries each configured device's posture in its site health
projection and on its LAN API, under gateway-api/v2.md and
[lan-app-api/v1.md](../lan-app-api/v1.md). It carries, for each device:

- `state` and, when `unknown`, `reason`, as above;
- when the state is `current` or `stale`, `record_b64`, the canonical padded
  RFC 4648 Base64 of the held record's exact bytes, and `received_at_ms`, the
  gateway's wall clock at its receipt;
- `last_refusal` and `last_refusal_at_ms`, the reason of the most recent message
  for that device refused at checks 3 to 10 since the gateway started, and the
  gateway's wall clock at its receipt, when there is one. An accepted record
  does not clear it. It names the reason only, never the message, and it makes
  a device whose records all arrive `key_mismatch`, as after its posture key
  changes, distinguishable from one that has gone silent, unless a party
  publishing on the topic overwrites it. `state`, `reason`,
  `received_at_ms`, `last_refusal` and `last_refusal_at_ms` are all the
  gateway's assertions.

A gateway never re-serialises, summarises, re-signs, merges or edits a record,
never carries a record under `unknown`, and never carries one record for two
devices.

**No surface presents more than the record says.** A surface that carries or
shows a posture, the gateway's site health and LAN API and anything that reads
them among them, MUST NOT present a record as verified unless it verified it
under an independently obtained key, and MUST NOT present `current`, a
`commissioned_binding`, a `deployment_profile` of `production` or any other
member as protection, actuation availability or authority. A `current` record
says what the runtime last signed, and nothing about what it may do.

**What a reader may conclude.** `state`, `reason` and `received_at_ms` are the
gateway's assertions. `record_b64` decodes to the runtime's signed bytes, but a
reader can verify them only under a posture key it obtained independently of
the gateway: a key the gateway supplies, or one learned from the same LAN API,
authenticates nothing the gateway could not have forged. A reader that holds an
independent key verifies the bytes under [The record](#the-record) and may judge
their currency itself, from `issued_at_ms` against its own clock with this
contract's bounds; it then has the same limits as a gateway. A reader without
one relies on the gateway for both authenticity and currency.

## Limits and later versions

- **No physical authority or zone fields.** A later version may add them once
  their vocabulary is reconciled with runtime-health/v4's `safety_zones[]`,
  commissioned-safety-binding/v2 and the command-result posture of
  firmware-command-result/v1.
- **No consumer key distribution.** This version defines how a gateway learns a
  posture key and no way for any reader beyond it to learn one independently,
  so no such reader can verify a record without trusting the gateway.
- **Delayed delivery.** A party that can delay messages on a device's posture
  topic, but not forge them, can hold back records and release them later.
  Check 10 refuses any record whose `issued_at_ms` is more than 300000 ms
  behind the gateway's clock when it arrives, and a held record stops being
  `current` once its age passes 900000 ms. A delayed record therefore reads
  `current` for at most 900000 ms past its `issued_at_ms` as the gateway's
  clock reads it. Measured from when the record was truly signed, the bound
  grows by however far the runtime's signing clock ran ahead of true time.
  The signing clock runs at most 30000 ms ahead of the runtime's wall clock,
  as [Publication](#publication) requires, so a runtime whose wall clock is right holds the
  bound to about 930000 ms. A runtime clock that runs further ahead, whose
  records check 10 would refuse as `future_timestamp` on time, lets a party
  that delays them by about as much bring them inside the bound: the error of
  the runtime's clock extends the bound by as much, and so does the error of
  the gateway's own clock. A record
  released in time stays the held record until a later one arrives; a party
  that withholds every later record keeps the device at that record, `stale`
  after the bound. It can never make the device show a record the runtime did
  not sign.
- **A publisher can blank a device.** A party that can publish on a device's
  posture topic can resend a validly signed lower record from within the skew
  bound, setting `unknown(lower_tuple_seen)`, or publish enough of anything to
  drain the device's volume bound, so that the runtime's genuine records are
  dropped, and can replace the broker's retained copy, and can overwrite the
  device's `last_refusal`. While it keeps doing so it holds the device at
  `unknown` or `stale` indefinitely. It can never make
  the device show a posture the runtime did not sign. Broker access control
  bounds who can publish there.
- **Honest traffic can spend the volume bound.** A backlog queued for the gateway
  while it was disconnected, the retained redelivery at each subscribe and the
  MQTT client's QoS 1 retransmissions all spend the device's bound with the
  runtime's records, and together can exceed it, so a genuine record is
  dropped; the next arrives within 60 seconds. Volume drops leave no
  `last_refusal`.
- **An honest reordering can blank a device briefly.** A gateway whose broker
  session queues messages while it is disconnected can, on reconnecting,
  receive queued records and the retained record out of order, and read a
  validly signed lower one: the device reads `unknown(lower_tuple_seen)` until
  the runtime's next record, at most 60 seconds later. Nothing false is shown.
- **The store is one point of loss.** Deleting the gateway's posture store,
  restoring an older copy, or configuring a different state directory resets
  every watermark and sticky reason it held, so a validly signed record from
  within the skew bound that the store had superseded is accepted once, and a
  restore it had detected is forgotten. One corrupt store makes every pinned
  device `unknown(store_unavailable)`. The only recovery is an operator
  removing the store while the gateway is stopped, at that same cost; check 10
  bounds what it readmits to records signed in the last 300000 ms.
- **No posture without evidence and a signing clock.** The posture key is the
  evidence device key, so a runtime that runs with evidence disabled, or whose
  evidence key did not load, publishes no record; so does a runtime without the
  signing clock [Publication](#publication) requires, which on ori-runtime
  exists only while gateway authentication is enabled. A gateway then reads the
  device `stale` where it held a record and `unknown(no_record)` otherwise,
  with no further reason it can see. The readback answers `key_unavailable`
  when the key is not loaded, but answers with the key when only the clock is
  missing, so an installer can pin a key under which no record will come.
- **An evidence key rotation is a new epoch.** A rotation of the evidence device
  key under `ori.evidence.rotation.v2` changes the posture key, so its records
  are `key_mismatch` until the new key is pinned, and the device's
  `last_refusal` shows it.
- **The record is readable on the broker.** It is signed, not encrypted, so any
  party that can subscribe to the topic reads the runtime's release, profile
  and binding hash.
- **A restored store may go undetected.** A backup restore or replacement of the
  runtime's store under the same posture key lowers its boot generation and
  its signing clock: its records are `lower_tuple`, and the device reads
  `unknown(lower_tuple_seen)` until a new key is pinned or its pair passes the
  held one. A restore that reproduces the held record's exact bytes at the held
  pair, as deterministic Ed25519 can, is `replayed`, and its next record is
  `accepted`: that restore is not detected. A `conflict` shows that two records
  under one key cannot both be genuine; it is not guaranteed evidence of any
  restore. The installer's automatic rollback keeps the same store, so it
  lowers neither counter.
- **A runtime clock that is wrong refuses.** A runtime whose wall clock is more
  than 300000 ms from the gateway's, such as a device without a battery-backed
  clock before it reaches its time source, has every record refused at check
  10, so the device reads `stale` where a record was held, and `unknown`
  where none was. This is the same limit as gateway-api/v2's envelope skew.
- **No staged rotation.** See [Key pinning and discovery](#key-pinning-and-discovery).
  A later version may add a staged rotation with a possession proof under the
  old key, a bounded overlap, a confirmation and a retirement, or
  certificate-based key distribution, without changing the record or its
  signature.

## Representable and enforced

The record, its publication, the receiver's checks and state, the pin and the
carriage are representable here and exercised by the corpus below. No
production consumer enforces any of it. The runtime is the enforcing repository
for the record and its publication (ori-runtime#782), and the gateway for
receiving, the pin and carriage (ori-gateway#118).

## Vectors

These rules have no corpus case and are exercised by no vector: a record
waiting on an outstanding write for its device, the pacing of write retries,
Payload Volume drops on the posture topic, and the posture store's file rules
in gateway-config/v2.

[vectors/posture-v1.json](vectors/posture-v1.json) holds signed records as
exact bytes under a published test key, each with the verdict a receiver gives
it at checks 3 to 10, and receiver sequences, each a list of events with the
verdict and the posture state after each. It is reproduced byte for byte by
`scripts/generate-runtime-posture-vectors-v1`, and
`scripts/check-runtime-posture-vectors-v1`, which shares no code with it, holds
the corpus to this text.
