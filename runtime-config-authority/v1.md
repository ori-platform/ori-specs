# Runtime Configuration Authority Contract v1

> Status: Design target, pre-ratification. No shipped consumer claims
> conformance. Amendable in place under the
> [pre-ratification exception](../VERSIONING.md#pre-ratification-exception).

[runtime-config/v1.md](../runtime-config/v1.md) describes one configuration
document, and [runtime-config-signing/v1.md](../runtime-config-signing/v1.md)
describes one key that signs it. That is the shape a provisioning backend
generates today.

It is the wrong shape, and the reason is not tidiness. A single signed document
means a single authority, and the runtime's configuration surface spans four
that must not be the same party.

## What A Signature Does Not Prove

A valid signature proves **who wrote a document**. It does not prove they were
entitled to write what is in it.

With one document and one key, those collapse. The provisioning backend signs
everything, so anything it puts in the file is, by construction, authorised —
including a value that decides when a physical cutoff fires. Nothing in the
verification path can object, because the signature is genuinely valid.

Splitting by authority is what re-separates them. A provisioning document
carrying a safety multiplier is **perfectly signed and still refused**, because
the schema its signer may write does not contain that field.

**Implementers must not conflate the two.** A system that treats a valid
signature as sufficient authorisation has reimplemented the defect this
contract exists to remove, and it will pass every signature test while doing
so.

## The Four Authorities

| Class | Signer | Carries |
| --- | --- | --- |
| `device_site` | Provisioning authority | Identity, location, timezone, gateway relationship, selected skills with versions and package digests, and a hardware **inventory** |
| `entitlement` | Commercial policy authority | Paid capabilities, caps, lease and expiry |
| `commissioning` | Commissioning authority | The physical arrangement, per [commissioned-safety-binding/v1.md](../commissioned-safety-binding/v1.md) |
| — | The release | Safety profiles: Tier D conditions, evaluators, multipliers and bounds |

Safety profiles appear only to state what they are not. They are shipped and
signed with the runtime, they are **not a configuration document**, and they
never arrive from a backend. A deployment that can supply one has removed the
release from the safety decision.

Entitlement is already separate through
[device-policy/v1.md](../device-policy/v1.md). This contract reconciles that
path rather than introducing a third shape: the entitlement payload **is** the
device policy payload, and its fields are defined there.

## Document Shape

Every configuration document is an envelope wrapping one payload.

```json
{
  "config": {
    "v": 1,
    "class": "device_site",
    "device_id": "energy-monitor-ikeja-01",
    "generation": 7,
    "issued_at_ms": 1800000000000,
    "signing_key": "ed25519:<base64-32-byte-public-key>",
    "payload": { }
  },
  "signature": "ed25519:<base64>"
}
```

### The envelope is shared, and that is deliberate

| Field | Type | Meaning |
| --- | --- | --- |
| `v` | integer | Exactly `1` |
| `class` | string | `device_site`, `entitlement` or `commissioning` |
| `device_id` | string | The device this document addresses |
| `generation` | integer | Strictly increasing per `(device_id, class)` |
| `issued_at_ms` | integer | Audit only; never a freshness proof |
| `signing_key` | string | The raw key that signed this document, inside the signed body |
| `payload` | object | The authority-owned content, closed per class |

**These fields appear in all three classes on purpose**, and the disjointness
rule below does not apply to them. Every document has to say which device it
addresses, which class it is, and how fresh it is, or none of the routing,
freshness or authority checks can run. Requiring them to differ per class would
be a rule against saying the same necessary thing the same way.

Canonical bytes and encodings follow
[commissioned-safety-binding/v1.md](../commissioned-safety-binding/v1.md#the-closed-grammar):
canonical JSON, strict UTF-8, `signing_key` and `signature` as canonical base64
of exactly 32 and 64 bytes.

### Payload paths are what must not overlap

| Class | Top-level payload paths |
| --- | --- |
| `device_site` | `device`, `sensors`, `actuators_present`, `skills`, `gateway`, `database`, `logging`, `telemetry_export`, `health_socket`, `actions` |
| `entitlement` | `tier`, `capabilities`, `caps`, `lease` |
| `commissioning` | `zones`, `inventory_generation` |

`device.rated_capacity_amps` does not appear in any of them. It moves out of
`device_site` and into a commissioned zone, where the party who certified the
electrical work owns it.

## Inventory Is Not Association

This is the boundary the whole split turns on, and it is one line inside what
looks like one subject.

Provisioning may declare that a current sensor and a relay **exist** on this
device, with their addresses and buses. That is procurement information, and
the backend legitimately holds it.

Provisioning may **not** declare that this sensor observes the circuit that
relay controls, nor what that circuit is rated for. That determines whether and
when a cutoff fires. It belongs to the party who certified the electrical work,
and it arrives in the commissioning document.

Put plainly: *a current clamp at 0x48 exists* is inventory. *That clamp watches
the main distribution circuit, which is rated 10 A* is association, and it is
the difference between a cutoff that protects the right load and one that opens
the wrong breaker.

Keeping the boundary here is what stops a provisioning document moving a trip
point through a field that reads like a measurement.

## Closed Schemas

**Every document schema is closed. An unrecognised field is a refusal, never
passthrough.**

The split's value is that a field in the wrong file becomes a mechanical
refusal rather than a judgement call, and that only holds if nothing can ride
along unread. A permissive parser turns the boundary into advice.

### Three refusals, not one

A refused path gets one of three verdicts, because they need three different
actions:

| Verdict | Meaning | What an operator does |
| --- | --- | --- |
| `malformed` | Belongs to nobody | Fix a typo or a version mismatch |
| `foreign_field` | Belongs to **another authority** | Move it to that document |
| `forbidden_content` | Belongs to **no configuration authority** — release-owned | Remove it; there is nowhere it may go |

`safety_profiles`, `action_tiers` and `capability_grants` are release-owned.
Reporting one of them as a foreign field would suggest relocating it to some
other document, and no such document exists.

### `foreign_field` is a distinct verdict

When a refused field is recognisable as **another authority's**, the consumer
MUST report `foreign_field` and name the document it belongs in, rather than
the generic `unknown_field`.

The two failures need different actions. An unknown field is a typo or a
version mismatch. A foreign field is a backend writing outside its authority —
possibly a bug, possibly an attempt — and telling an operator "unknown field
`rated_capacity_amps`" sends them looking for a spelling mistake instead of at
a boundary violation.

## Forbidden Content, Testable By Construction

A blocklist of field names fails open: it catches the names someone thought of
and admits the next one.

So the rule is structural. **The top-level payload paths of the three classes
are pairwise disjoint**, and a conforming implementation ships a test asserting
that every pairwise intersection is empty.

The rule is about **payload paths, not every key in the document**. The
envelope is shared by construction — `device_id`, `class`, `generation` and the
rest have to appear in all three, and a document that could not say which
device it addresses would break routing rather than protect anything. What must
not overlap is the content each authority owns.

The release-owned safety-profile parameter names appear in no payload.

On top of that, no configuration document may carry:

- an action-tier declaration,
- a Tier D condition or any of its parameters,
- a safety-profile parameter override,
- a safety multiplier,
- a capability grant or a grant signature.

**This prohibits safety authority, not numbers.** Ordinary Tier A through C
tuning values remain permitted where a skill's schema and its capability grant
allow them: an alerting threshold, a cooldown, a reporting interval. The line
is whether a value is an input to a condition the runtime evaluates
autonomously without an operator, which is Tier D alone.

`device.rated_capacity_amps` is the field that makes this concrete. It reads as
inventory, it is currently in the provisioning document, and multiplying it by
a release-owned constant is exactly how a trip point is computed. It moves to
the commissioning document. Its presence in a device-site document is
`foreign_field`.

## Verification

### Order

1. **Parse** each document against its closed schema. A shape violation is
   `malformed`; a payload path belonging to another authority is
   `foreign_field`.
2. **Bind** each document to this device. A document addressed elsewhere is
   `wrong_device`.
3. **Select** by key material, **across every configured anchor rather than
   the one for this class**. The document's `signing_key` is matched against
   the whole anchor set; matching none is `unknown_signer`. No signature is
   attempted against a key the document did not name, and `signer_id`-style
   labels are never an input.
4. **Verify** the signature against that one selected key. Failure is
   `bad_signature`.
5. **Authorise**: the anchor that matched has an assigned class. If it is not
   this document's `class`, the verdict is `wrong_authority`.
6. **Freshness** per that document's own rule.
7. **Cross-document** consistency, below.

The **legacy latch is checked immediately after parsing**, before device
binding and before any signature work. A latched device refuses a legacy
document on sight; carrying it as far as the authority stage would refuse it
for the wrong reason — a legacy document is signed by the provisioning key and
would be reported as that signer writing outside its class, when the actual
fault is that the format is no longer accepted here at all.

**Selecting across all anchors is what makes step 5 reachable.** Selecting only
the anchor for the declared class would send a `device_site` document signed by
the commissioning key straight to `bad_signature` — reporting a boundary
violation as a broken signature, and sending an operator to look at key custody
when the fault is that a signer wrote outside its authority. Both failures
would be indistinguishable, and `wrong_authority` would be dead text.

Steps 4 and 5 stay separate and ordered for the reason in the binding contract:
an authority verdict issued over an unverified document is forgeable, because a
public key is not a secret.

### Mandatory, Optional, And Partial Failure

| Class | Missing | Fails verification |
| --- | --- | --- |
| `device_site` | Refuse to start | Refuse to start |
| `entitlement` | Start with no paid capability | Reject the document; **retain the last accepted policy**, which remains bounded by its own expiry |
| `commissioning` | Start; no actuating profile activates | Reject the document; retain the last accepted binding |

**A partially verified set must never produce a half-applied device.** Each
document applies whole or not at all, and a document that fails leaves the
previously accepted one of its class in force — not a merge of the two.

Entitlement retention is the same rule as
[device-policy/v1.md](../device-policy/v1.md#rejection-behavior) and this
contract does not change it. Retention does not accept the rejected document;
it keeps the last one that verified, and **revocation is carried by expiry
rather than by a failed fetch**. A retained policy still runs out. Discarding
on verification failure would instead disable paid capability for a customer
whose network dropped, and would give anyone able to corrupt a response the
power to switch features off.

### Cross-Document Staleness

Applying documents independently is what creates the seam this work exists to
close: a **new hardware inventory beside an old commissioning binding**, where
every signature is valid and the association is silently wrong.

A commissioning payload therefore carries `inventory_generation`: the
`device_site` generation whose inventory it was commissioned against.

- A commissioning document whose `inventory_generation` is **greater than** the
  accepted `device_site` generation is `ahead_of_inventory` and is not applied.
- A commissioning document whose `inventory_generation` is **less than** the
  accepted `device_site` generation is **stale**, and the runtime MUST NOT
  activate any actuating profile for its zones. It reports that state rather
  than reporting healthy.

So advancing the inventory does not silently re-point a binding at hardware it
was never commissioned against. It withdraws actuation until the binding is
re-issued against the new generation, which is the outcome a re-wired site
should produce.

A `device_site` document is not held back by a stale binding: observation,
reasoning and alerting continue. Only actuation waits.

## Migration

A device provisioned under the single-document format MUST upgrade **without an
identity change**. Regenerating a device identity at a configuration migration
would orphan its evidence chain, its anchors and its history, which is a far
larger event than the change that caused it. This ties to identity continuity
in `ori-runtime` #329.

### The latch is one-way and durable

**Once a device has accepted a split-format set, it MUST refuse legacy
single-document configuration permanently.** The latch is persisted, survives
restart and reinstall, and there is no configuration flag that clears it.

Without it, migration is an authority downgrade waiting to happen. A legacy
document is signed by the provisioning key and legitimately carries
`device.rated_capacity_amps` — so an older, perfectly valid document, replayed
after the split, reintroduces a relocated safety parameter under the very
authority this contract removed it from. Nothing about that document is
malformed; it is simply from before the boundary existed.

A runtime MAY accept a legacy document while it has never seen a split set. It
MUST NOT accept a legacy document and a split set at the same time: two sources
describing one device, with no rule for which wins, is precisely the ambiguity
the split removes.

### Legacy mode cannot activate a commissioned profile

While a device is in legacy mode it has no commissioning document, and
therefore no commissioned mapping. It MUST NOT activate any safety profile that
requires commissioned facts, whatever a legacy document declares. Legacy
support is a path to migrate an observing device, not a way to keep actuating
on provisioning-signed wiring claims.

## Relationship To The Existing Contracts

[runtime-config/v1.md](../runtime-config/v1.md) remains the accurate
description of the single-document format that runtimes implement today, and is
not withdrawn while devices run it. Its `device.rated_capacity_amps` field is
the one this contract relocates.

[runtime-config-signing/v1.md](../runtime-config-signing/v1.md) describes the
single signer and the `config_signature` envelope. Its envelope shape carries
over per document; what changes is that there is more than one, with more than
one anchor.

Both are superseded for new deployments once a consumer claims conformance
here, and not before.

## Error Semantics

| Verdict | Decided at | Cause |
| --- | --- | --- |
| `malformed` | parses | Shape, grammar, or a path belonging to nobody |
| `foreign_field` | parses | A payload path belonging to **another authority** |
| `forbidden_content` | parses | A path belonging to **no configuration authority** because it is release-owned |
| `legacy_after_latch` | legacy_latch | A legacy document offered to a device that has accepted the split |
| `wrong_device` | device_binding | Document addressed to a different device |
| `unknown_signer` | key_selection | Named key matches no configured anchor of any class |
| `anchor_collision` | key_selection | Two classes are configured with the same key material |
| `bad_signature` | signature | Signature does not verify against the selected key |
| `wrong_authority` | authority | Verified signer holds a different class's authority |
| `stale` | freshness | Document is not newer than the accepted one of its class |
| `ahead_of_inventory` | cross_document | Binding names an inventory generation the device has not accepted |
| `stale_association` | cross_document | Binding was commissioned against a superseded inventory |

`anchor_collision` matters as much here as in the binding contract. If the
provisioning and commissioning anchors are the same key material, the split is
decorative — one party can write both documents — and no document can reveal
that. It is refused at configuration load, before any document is read.

## Required Test Vectors

| Vector | Establishes |
| --- | --- |
| A valid document of each class | The shapes are producible |
| `rated_capacity_amps` in a device-site document | `foreign_field`, not `malformed` |
| A safety multiplier in any configuration document | Forbidden content is refused |
| A device-site document signed by the commissioning authority | `wrong_authority`, after a valid signature |
| Provisioning and commissioning anchors identical | `anchor_collision` at load |
| An entitlement document failing verification | No fall back to the last accepted copy |
| A commissioning document absent | Starts, actuating profiles inactive |
| A device-site document absent | Refuses to start |
| One document of a set failing | The others' previously accepted versions stay in force, unmerged |
| A legacy single document | Accepted, with the relocation reported |
| A legacy document and a split set together | Refused |
| Schema key sets pairwise | Intersection empty |

## Anchors

Four authorities means four anchors, and where they come from decides whether
the split is real.

### An anchor must not arrive inside a document it verifies

Today `device_policy.public_key_b64` — the key that verifies entitlement — is a
field **inside the configuration file**, which is signed by the provisioning
authority. So provisioning chooses the key that checks entitlement, and can
substitute its own and sign its own entitlements. The separation is nominal.

**Every anchor is supplied out of band**, through the environment or an
installation record, and never through a document any of them signs. The
existing `trust_anchor_env` pattern in
[runtime-config-signing/v1.md](../runtime-config-signing/v1.md#runtime-signature-policy)
is the right shape; it needs one variable per class rather than one overall.

| Class | Anchor source |
| --- | --- |
| `device_site` | Provisioning trust anchor, environment-supplied |
| `entitlement` | Commercial policy anchor, environment-supplied — **relocated out of the config file** |
| `commissioning` | Installation record, per the binding contract |

### The entitlement authority

`device-policy/v1.md` names a key and no party. The **commercial policy
authority** is the signer of entitlement, distinct from provisioning and from
commissioning, and its anchor is configured as above. This is the reconciliation
that contract's key field was missing: the same payload, verified against an
anchor the provisioning authority cannot replace.

### Rotation and collision

Each class carries a current anchor and an optional previous one. The previous
verifies and does not sign: a new document must be signed by the current
generation, so a compromised key stops authoring the moment the anchor moves.
This is the posture in
[commissioned-safety-binding/v1.md](../commissioned-safety-binding/v1.md#key-selection-generations-and-rotation),
applied per class.

**If any two configured anchors are the same key material, across any pair of
classes or generations, the runtime refuses at configuration load** with
`anchor_collision`. One party able to sign two classes is the collapse this
contract exists to prevent, and no document can reveal it — only the anchor set
can.

## Golden Vectors

The authoritative corpus is
[config-authority-vectors-v1.json](config-authority-vectors-v1.json), held here
beside this document. Its SHA-256 is
`c5effd24961d8358761662d09e0cd3abdab29abd4535c56d9a179f582d92fdbd`.

It carries 3 accept cases -- one per class -- and 14 reject cases, at least one per verdict,
including the ones this contract exists for: a relocated safety parameter in a
provisioning payload, a document signed by another class's authority, an anchor
collision, a stale commissioning generation, and a legacy document offered
after the latch.

Every case records exact canonical bytes, digest and signature, so a producer's
bytes are checkable without running a verifier and a verifier's verdicts
without running a producer. Reject cases carry `reason` and `stage`, and a
conforming verifier must be refused at that stage having passed every earlier
one — refusing for the right reason at the wrong stage is not evidence the
named check exists.

Canonical bytes follow the same rules as the binding contract, so the same
implementations serve both.

## Open Questions

- **Skill config authorship.** Selected skills and their tuning values sit in
  the `device_site` payload, which makes the provisioning authority the author
  of Tier A–C behaviour. That is probably correct — it is the same party that
  chooses which skills run at all — and it is recorded rather than argued.
- **What a device does when its inventory advances and no re-issued binding
  arrives.** The rule here withdraws actuation, which is safe and could strand
  a site indefinitely. Whether that warrants an operator-visible deadline, and
  what expires when it passes, is not settled.
