# LAN Application API v1

> Status: maturity `draft`; compatibility `amendable`; adoption: none
> recorded; proof: end-to-end `none`, HIL `none`, production `none`. Record:
> [status/lan-app-api/v1.json](../status/lan-app-api/v1.json).

This proposed contract defines the customer application's site-LAN connection
to a gateway. It is not an implemented service or an approval mechanism. The
gateway serves site data and relays replies; only the runtime admits a Tier C
approval under [tier-c-approval/v1](../tier-c-approval/v1.md). No application,
product role, pairing grant, gateway session or gateway acknowledgement grants
physical authority. Tier D never depends on this interface.

## Roles and identity

The closed product site-role vocabulary is `owner`, `manager` and `viewer`.
All three may read the site health, posture, readings, events and alerts
allowed below. Only an `owner` may manage site membership through the product
backend. A `manager` has no membership-management privilege. This vocabulary
is site-scoped: a role at one site conveys nothing at another.

Product roles govern ordinary site reads only. A product `owner` or `manager`
is not thereby a Tier C approver; a product `viewer` with a separately
enrolled LAN key is not thereby excluded from Tier C. The runtime's local
[Tier C approver registry v1](../tier-c-approvers/v1.md) alone maps an enrolled
application key to an active credential. The gateway asks the runtime on
**every** proposal read which proposals in that read's bounded scope the
exact presented key may see. It does not cache that answer or infer it from a
product role.
The runtime repeats the key, epoch, cutoff and proposal checks at durable
reply admission. A product role may narrow ordinary product access but
cannot add or remove runtime approval eligibility.

The product backend identifies a customer by a tenant-scoped, stable
`customer_id`. Phone numbers, display names and commercial entitlement are
not approval identities. The gateway never derives a role from a phone
number or lets the application assert one.

## Authorities and signed documents

Two Ed25519 signing purposes are distinct from each other and from
provisioning, commissioning, evidence and commercial-policy keys:

| Purpose | Issuer | Consumer |
| --- | --- | --- |
| `ori.lan.pairing-grant.v1` | Product backend | Gateway |
| `ori.lan.time-assertion.v1` | Product backend time service | Gateway |

An issuer MUST NOT reuse one private key across those purposes. Consumers
select an explicitly installed anchor for the named purpose, never a key
supplied by the document being verified. The exact wire bytes of each
document are the Profile 2 canonical JSON bytes of
[signing/v2](../signing/v2.md), prefixed with the UTF-8 purpose string and
one NUL byte. The `signature` field is excluded from those bytes and is the
RFC 4648 padded Base64 of the Ed25519 signature. Unknown, duplicate, missing
or wrong-type members are refused before signature verification. The grant
and time documents carry `v: 1`; another version is refused, not
interpreted as v1.

### Pairing grant

The authenticated product backend issues one grant to a customer session with
an explicit role at exactly one site. Its signed object has exactly:
`v`, `grant_id`, `tenant_id`, `site_id`, `gateway_id`, `device_id`,
`customer_id`, `role`, `app_spki_sha256`, `gateway_spki_sha256`,
`code_sha256`, `issued_at_ms`, `not_before_ms`, `expires_at_ms`,
`signing_key_id` and `signature`. Identifiers are nonempty opaque strings,
SPKI digests are `sha256:` plus 64 lowercase hex digits, and times are
positive integer Unix milliseconds. The validity interval MUST be no longer
than ten minutes. The gateway requires its own gateway and site identities,
its configured runtime device and TLS SPKI digest to match the grant. A grant
is never a configuration anchor or an entitlement.

The backend separately shows the customer a uniformly random 12-character
code from the uppercase Crockford Base32 alphabet, excluding ambiguous
characters. It does not embed the code in the grant. `code_sha256` is SHA-256
over ASCII `ori.lan.code.v1`, one NUL byte, UTF-8 `grant_id`, one NUL
byte, then ASCII `code`, encoded as
`sha256:<64 lowercase hex>`. The gateway compares the digest in constant
time. This code is a human check, not proof of presence or authority; a
photograph or copied code can be relayed. A deployment that requires physical
presence needs an independently recorded local-control challenge.

The backend MUST refuse issuance unless the customer still holds the named
site role. The application presents a public key generated on its device;
the backend binds that key's SPKI digest. The gateway verifies possession in
the client TLS handshake as described below. A role or site change invalidates
future grants at the backend and is delivered as a revocation to the gateway
at its next synchronization. An already issued grant can remain usable while
offline until its expiry if the gateway has trusted time; that exposure is
bounded and must be shown to the operator.

The backend issues no approver list. Its pairing grant, role, customer ID and
revocation of a product session never amend the runtime registry or the
frozen `tier-c-approval/v1` authority snapshot or `policy_digest`. Runtime
credential enrolment and removal follow
[tier-c-approvers/v1](../tier-c-approvers/v1.md); a gateway or
product document cannot add a credential. A relayed reply is not itself a
`tier_c_approval` record. Resource-scoped Tier B and host-state authority
remain pending [#212](https://github.com/ori-platform/ori-specs/issues/212).

## Gateway authentication and transport

The gateway exposes HTTPS with TLS 1.3 only. Plain HTTP, TLS downgrade and
certificate-warning bypass have no fallback. The gateway presents an
Ed25519 certificate whose SPKI SHA-256 matches `gateway_spki_sha256` in the
backend-signed grant. The application verifies this pin **before sending the
grant, code or customer data**. The grant arrives over the backend's ordinary
authenticated HTTPS channel. Gateway certificate rotation requires a newly
issued grant with the new pin.

The application presents a self-signed Ed25519 client certificate. For
product pairing its SPKI SHA-256 must match the grant's `app_spki_sha256`;
for a local proposal session its SPKI must match the key that signs the
challenge response. The gateway requests the certificate during
TLS and verifies proof of possession in the handshake. It admits an
untrusted issuer only for the pair, proposal-challenge and proposal-session
endpoints. Pairing binds the certificate SPKI to the signed grant; local
session creation binds it to the signed challenge response. Subsequent
requests require a live session bound to that SPKI. A bearer session ID alone
never authenticates a request.
Gateways MUST limit handshake and pairing attempts before expensive work.

The application may discover a gateway by a typed address or DNS-SD service
`_ori-lan._tcp`. Discovery supplies only an address and port; it conveys no
identity, role or trust. A discovered hostname or certificate chain never
overrides the signed SPKI pin.
An app using local proposal-session renewal must retain a gateway SPKI pin
learned from a valid pairing grant or receive it through a separately
authenticated local enrolment channel. It refuses a new or changed gateway
key without such a channel. The exact local pin handoff for a first locally
seeded key is not yet defined; offline renewal cannot be claimed implemented
until that handoff exists.

## Trusted time and pairing admission

New pairing requires trusted gateway time. The v1 qualified source is a
backend-signed `time-assertion/v1` response to a fresh, uniformly random
128-bit gateway-generated nonce. Its signed members are exactly `v`, `site_id`,
`gateway_id`, `nonce`, `utc_ms`, `signing_key_id` and `signature`.
The dedicated time anchor, gateway/site binding and nonce must verify. The
nonce is single-use and valid for at most ten seconds on the gateway's
monotonic clock; the gateway captures the monotonic time at receipt and sets
its trusted wall-time estimate from `utc_ms` plus elapsed monotonic time.
Reachable but unauthenticated NTP, DNS or a browser clock is never qualified.

The time estimate remains qualified for at most five minutes of monotonic age.
After restart, it is unqualified until a new challenge is answered. At
pairing, the gateway refuses without qualified time and otherwise requires
`not_before_ms - 30_000 <= now <= expires_at_ms + 30_000`. Skew never
changes the signed interval's ten-minute maximum; the 30-second tolerance
is an additional admission bound. The gateway records which
assertion qualified the decision. V1 provides no offline new-pairing or local
console override; an existing session may continue for its monotonic
lifetime while disconnected.

Admission order is fixed: gateway certificate pin at the client; grant
signature and binding, client-key proof; qualified clock and validity; code;
durable single redemption; session issuance. The gateway durably counts
wrong codes by `grant_id`. After five wrong attempts it durably burns the
grant and reports the burn when connected. Comparing a correct code after
burn, replaying a redeemed grant, or failing the durable write refuses
pairing. Code comparison is constant-time. No session is returned before
the redemption commit.

## Session and HTTP surface

A `POST /lan/v1/pair` request contains exactly `grant_b64` (RFC 4648
padded Base64 of the exact signed grant JSON bytes) and `code` (the
human-entered code). It is made under TLS with the bound client
certificate, and no customer session is required. A successful response
contains exactly `session_id` (a random 256-bit value shown once) and
`expires_in_ms` (integer `1800000`).
The gateway stores only its digest, session kind (`product` or `proposal`),
site, client SPKI digest, issue monotonic instant and a 30-minute monotonic
deadline; a product session additionally stores its customer and role. Every
request uses the same client certificate and `Authorization: Bearer`
session ID. Restart destroys all sessions. Product-session revocation and
device suspension destroy affected sessions; backend revocation is applied at
the next sync. Runtime registry revocation makes the key ineligible for
disclosure and reply admission immediately, but the gateway need not learn
that revocation to invalidate a transport session: the session alone confers
no approval authority.
An ordinary product-read session expires at its monotonic deadline and cannot
be refreshed offline from a backend grant. An enrolled `lan_ed25519` key may
instead open a local proposal session. `GET /lan/v1/proposal-challenge`
under the presented TLS client certificate returns an object with exactly
`v: 1`, `site_id`, `device_id`, `challenge` (canonical padded Base64 of 16
fresh random bytes) and `expires_in_ms: 30000`. The gateway durably stores
the challenge bound to that certificate's SPKI, site and device. It is valid
for 30 seconds on the gateway's monotonic clock and never reused.
The application signs ASCII
`ori.lan.proposal-session.v1`, one NUL byte, then Profile 2 canonical JSON
with exactly `v: 1`, `site_id`, `device_id`, `challenge` and
`app_spki_sha256` (the digest of that certificate's exact DER SPKI).
`POST /lan/v1/proposal-session` carries exactly `proof` (that signed object)
and `signature` (its canonical padded Base64 Ed25519 signature) under the
client's TLS certificate. The gateway verifies certificate possession, the
signature, site/device binding and an unconsumed challenge before issuing a 30-minute
session bound to the key. Its success response has exactly `session_id` and
`expires_in_ms: 1800000`, as for pairing. It consumes the challenge durably, including on a
failed presentation; if storage is unavailable it refuses. This session is a
transport credential only: it grants no proposal disclosure or approval.
It can be renewed while the site is offline by repeating this local challenge.
Restart destroys it. The gateway does not require a product grant or backend
contact for this endpoint. Runtime disclosure and admission remain mandatory.

All responses containing customer or site data carry
`Cache-Control: no-store`. Page size is at most 100, and cursors are opaque,
site-bound and authenticated by the gateway; an invalid cursor is refused.
The closed surface is:

| Method and path | Result |
| --- | --- |
| `POST /lan/v1/pair` | Redeem grant and code; no customer session required. |
| `GET /lan/v1/proposal-challenge` | Issue a one-use local key challenge under client TLS; no session required. |
| `POST /lan/v1/proposal-session` | Prove possession of a candidate key for a local transport session; no product grant required. |
| `GET /lan/v1/site/health` | Site health, no secrets or contact details. |
| `GET /lan/v1/posture` | Exact runtime-signed posture bytes, one record per runtime device; no reserialization once runtime-posture/v1 is defined. |
| `GET /lan/v1/readings?cursor=` | Bounded readings since cursor. |
| `GET /lan/v1/events?cursor=` | Bounded events since cursor. |
| `GET /lan/v1/alerts?cursor=` | Alerts and delivery status without contact numbers. |
| `GET /lan/v1/proposals` | Open proposals only after a fresh runtime disclosure decision for the presented key and each returned proposal. |
| `PUT /lan/v1/preferences` | Bounded preference update with a client nonce; never widens device policy. |
| `POST /lan/v1/proposals/{proposal_id}/replies` | Reply with `yes` or `no` and a client nonce; relay only. |

`GET /lan/v1/proposals` returns exactly an object with `v` (integer 1),
`site_id`, `device_id` and `proposals`. `proposals` is an array of at most
100 objects, sorted by `proposal_id`. Each object has exactly `proposal_id`,
`created_at_ms`, `expires_at_ms`, `summary`, `authority_snapshot_digest` and
`identity_epoch`. The times and summary are the corresponding values in the
runtime-authenticated `lan_proposal` projection; the summary is at most 256
UTF-8 bytes and is display text, not signed by the application. The digest
is `sha256:` plus 64 lowercase hex characters over the exact Profile 2
canonical bytes of the proposal's authority snapshot in
[tier-c-approval/v1](../tier-c-approval/v1.md). `identity_epoch` is the
canonical padded Base64 epoch returned by the runtime's fresh disclosure
decision for that proposal. For example:

```json
{
  "v": 1,
  "site_id": "site-a",
  "device_id": "edge-01",
  "proposals": [{
    "proposal_id": "AB12CD34",
    "created_at_ms": 1787000000000,
    "expires_at_ms": 1787000030000,
    "summary": "Open protected circuit",
    "authority_snapshot_digest": "sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "identity_epoch": "AAECAwQFBgcICQoLDA0ODw=="
  }]
}
```

The gateway returns only proposals in the runtime's allowed subset and never
replaces a missing or invalid digest or epoch with a locally inferred value.
An empty candidate set yields exactly the same outer object with an empty
array and no runtime query. If more than 100 candidate projections are open,
the gateway refuses the read as `runtime_disclosure_unavailable` without a
proposal count or partial page; v1 has no proposal cursor. The application
shows the site, device, summary, expiry and reply choice before signing, and
binds the exact returned digest and epoch in its signed reply. The gateway's
summary is not authenticated end to end; this limitation is tracked in
[gaps/open.md](../gaps/open.md).

Before releasing any proposal metadata, including a count, title, or whether
an identifier exists, the gateway sends the exact key SPKI digest and sorted
candidate proposal IDs to the runtime in one bounded request/response in
[gateway-api/v2](../gateway-api/v2.md#lan-tier-c-reply-relay). It returns
metadata only for IDs in the runtime's allowed subset. The runtime
checks an active `lan_ed25519` credential in its own site and identity epoch,
the proposal's enrolment cutoff, current open state, and registry availability.
For an allowed proposal the gateway includes the runtime's returned
`identity_epoch` with the proposal metadata so the app can bind its signed
reply to that epoch. It never supplies a gateway-inferred epoch.
An absent, malformed, mismatched or timed-out response discloses nothing;
the gateway never uses a cached eligibility decision. A later revocation or
proposal closure is checked again at reply admission.

The gateway refuses unknown fields on writes, unknown methods, cross-site
identifiers and requests without the required session. It never exposes
secrets, tokens, broker URLs, filesystem paths, contact numbers or
subordinate identifiers beyond the role's site. A read is idempotent. The
gateway durably deduplicates writes by
`(site_id, app_spki_sha256, session_id, client_nonce)` for at least 24 hours;
the same nonce with different bytes is refused. For a proposal reply,
`proposal_id` and nonce are also bound; a retry returns the stored relay
outcome, never a second runtime message, after the client proves possession
of the same key and presents the still-live session. This lookup precedes a
new relay or any runtime eligibility check; a key revoked after the first
queue may receive only its already stored `queued` result, never a new relay.
A preference write that the
in-force device policy disallows is refused, not silently widened.
Only a product session may use ordinary site reads or write preferences.
Either session kind may request proposals and relay a reply, but only a fresh
runtime disclosure answer permits the former and only durable runtime
admission can accept the latter. A product session whose key is not enrolled
sees no proposals and cannot approve, regardless of role.

The reply body carries exactly `v` (integer 1), `site_id`, `device_id`,
`identity_epoch`, `proposal_id`, `authority_snapshot_digest`, `reply` (`yes` or `no`), `client_nonce`
(a canonical padded Base64 16-byte random value), and `app_signature`.
The application signs ASCII `ori.lan.reply.v1`, one NUL byte, then Profile 2
canonical JSON of those members except `app_signature`, with the private key
that authenticated its client certificate. `app_signature` is canonical
padded RFC 4648 Base64 Ed25519. The gateway checks the signed site and device
against its configured identity and the authenticated transport session. It
forwards the exact reply and client certificate's DER SPKI bytes under the named
[gateway-api/v2 relay amendment](../gateway-api/v2.md#lan-tier-c-reply-relay).
Its HTTP success means the relay was durably queued, **not approved**.
A successful HTTP response has exactly `status` (`queued`), `proposal_id`
and `client_nonce` echoed from the request. It never returns `approved`,
`accepted` or an authority record; the runtime's decision is separate.
The runtime verifies the SPKI and `app_signature` using
`ed25519-key-admission/v1` and `ed25519-verification/v1`, maps that exact key
to an active local credential, checks the signed site, device and epoch,
then requires the signed snapshot digest to equal the open proposal's
recorded digest and repeats the proposal cutoff and registry checks in the durable
admission transaction before following `tier-c-approval/v1`. A gateway HMAC
authenticates the courier, never the human. Product role, customer ID,
pairing grant and session never substitute for that enrolled key.
Runtime acceptance or refusal is reported separately. A `no` is a refusal,
not an approval; timeout, undelivered and listener-ended outcomes retain the
existing runtime decision-log meanings and do not acquire
`tier_c_approval` evidence authority. Their signed-evidence vocabulary is
still tracked by [#205](https://github.com/ori-platform/ori-specs/issues/205);
this API MUST NOT invent a second one.

## Refusals and proof

The closed pairing refusal reasons, in admission order, are
`signature_invalid`, `binding_mismatch`, `wrong_application_key`,
`no_trusted_time`, `not_yet_valid`, `expired`, `code_attempts_exhausted`,
`code_mismatch`, `already_redeemed` and `revoked`. Session and write
refusals are `unauthenticated`, `session_expired`, `role_not_permitted`,
`runtime_disclosure_unavailable`, `credential_unavailable`,
`proposal_mismatch`, `binding_mismatch`, `nonce_reused`,
`policy_refused` and `relay_unavailable`. A refusal is recorded without
logging the grant, code, session ID or customer phone. A malformed input is
`malformed` before any semantic check; an unavailable durable store is
`storage_unavailable` and never succeeds optimistically.

For a local proposal session, the gateway applies these checks in order.
It consumes a presented challenge on a failed presentation when durable
storage is available, as described above:

| Order | Check ID | Refusal |
| --- | --- | --- |
| 1 | `session_shape` | `malformed` |
| 2 | `session_key_proof` | `unauthenticated` |
| 3 | `session_binding` | `binding_mismatch` |
| 4 | `session_challenge_live` | `session_expired` |
| 5 | `session_challenge_unused` | `nonce_reused` |
| 6 | `session_store` | `storage_unavailable` |

For a proposal reply, the gateway HTTP layer authenticates the client key
and session and applies these checks in order. An exact retry requires the
same session, key, nonce, proposal ID and request bytes; it returns the stored
relay outcome without publishing another runtime message. An altered retry
is refused even when the application signature is valid. A registry
revocation cannot change a stored HTTP relay result:

| Order | Check ID | Refusal or result |
| --- | --- | --- |
| 1 | `http_shape` | `malformed` |
| 2 | `http_session` | `session_expired` |
| 3 | `http_key_proof` | `unauthenticated` |
| 4 | `http_binding` | `proposal_mismatch` |
| 5 | `http_exact_retry` | `stored_relay` |
| 6 | `http_nonce_conflict` | `nonce_reused` |
| 7 | `http_outbox` | `relay_unavailable` |

`stored_relay` and successful `queued` are results, not refusal reasons.
The gateway never returns a registry eligibility decision. At runtime, after
the MQTT envelope has passed `gateway-api/v2` verification, a newly relayed
reply follows the independent pre-admission checks below, in the same durable
transaction as Tier C admission. A duplicate signed application reply already
processed for the same open proposal and nonce returns its recorded result
without repeating approval or actuation. The table gives refusal precedence
for a new reply; a `yes` that passes it only reaches the separate frozen
`tier-c-approval/v1` admission, and a `no` records refusal:

| Order | Check ID | Refusal |
| --- | --- | --- |
| 1 | `runtime_shape` | `malformed` |
| 2 | `runtime_app_signature` | `unauthenticated` |
| 3 | `runtime_active_key` | `credential_unavailable` |
| 4 | `runtime_site_device` | `proposal_mismatch` |
| 5 | `runtime_epoch` | `credential_unavailable` |
| 6 | `runtime_proposal_id` | `proposal_mismatch` |
| 7 | `runtime_snapshot_digest` | `proposal_mismatch` |
| 8 | `runtime_cutoff` | `credential_unavailable` |

The runtime compares the application-signed digest to the open proposal's
recorded authority snapshot digest at step 7. It does not trust a digest
provided only by the gateway. The gateway's `queued` response never implies
that any runtime step passed.

Required conformance vectors include pairing accept and refusal reasons;
replayed redemption; different client key; no trusted time; five wrong codes
and burn; local session challenge replay, expiry and restart; key revocation,
epoch replacement and proposal cutoff; nonce retry and altered retry;
byte-identical posture; disclosure timeout, missing and mismatched runtime
responses; a gateway that marks a reply admitted (reject); and a runtime
that admits a reply without an active enrolled key (reject). The current
corpus covers only a subset; missing transport and consumer vectors block a
conformance claim.

[vectors/admission.json](vectors/admission.json) contains deterministic
Ed25519 fixtures for the grant, time assertion, local session proof and app
reply, plus pairing, session, reply, modeled disclosure and relay-status cases. Run
`python3 scripts/generate-lan-app-api-vectors --check` and
`python3 scripts/check-lan-app-api-vectors --mutations`. The generator
and checker share no code. Their result proves only that these particular
proposed bytes and refusal decisions are representable and reproducible.
Both use Python's `cryptography` implementation for Ed25519, so they are not
independent cryptographic implementations. A second implementation remains
required for cross-implementation signature conformance.
TLS handshake, HTTP parsing, MQTT delivery, durable attempts and nonce
storage, gateway/runtime consumers, exact posture bytes, restart behavior
and HIL remain unverified. No implementation or HIL proof is recorded.
