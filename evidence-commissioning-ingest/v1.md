# Evidence Commissioning Ingest v1

> Status: Design target, pre-ratification. No implementation exists. This
> contract defines the authority-side write path for signed commissioning
> authorisations. It does not identify an implementation, endpoint host,
> deployment location, credential custodian, or administrative surface.

[evidence-exchange/v1.md](../evidence-exchange/v1.md) fixes that a
commissioning authorisation never crosses onto the device, the gateway, or
the fleet manager; the device holds only the `commissioning_digest`, delivered
by the local bridge command in [cli-commands/v1.md](../cli-commands/v1.md).
It places the authorisation's own delivery with the `commissioning_authority`
registry as an organisational concern. This contract is that path: an
authenticated, purpose-bound write into the evidence authority, separate from
the courier's `evidence_ingest` credential in
[evidence-transport/v1.md](../evidence-transport/v1.md) and from the read
path in [evidence-audit/v1.md](../evidence-audit/v1.md). The three do not
restate one another.

## Boundary

```text
commissioning tool -- HTTPS/this contract --> authority
runtime ------------- MQTT/gateway-api --> gateway -- HTTPS/evidence-transport --> authority
```

The caller is a commissioning tool operated on behalf of a commissioning
actor, outside every runtime, site network and gateway. It presents the
authorisation the commissioning authority signed; it does not sign. Nothing at
an evidenced site holds this credential, reaches this endpoint, or learns that
it exists, and the site's health surface reports the outcome only as the
generic registration status in
[runtime-health/v2.md](../runtime-health/v2.md).

The path carries exactly two artifacts, both signed by a commissioning key the
registry already holds: the authorisation defined in `evidence-exchange/v1`,
and the revocation defined below. It never carries a registration, an envelope,
a checkpoint, a receipt or a confirmation, and an authority MUST refuse those
types here as malformed before any verifier is reached, as the courier path
refuses an authorisation.

## Endpoint

| Property | Value |
| --- | --- |
| Method | `POST` |
| Path | `/v1/evidence/commissioning/artifacts` |
| Request content type | `application/octet-stream` |
| Response content type | `application/json` |
| Transport | HTTPS with server-certificate verification |

The request body is exactly one complete canonical wire artifact. The caller
MUST send the bytes the commissioning authority signed and MUST NOT decode and
re-encode them; the authority reconstructs no missing bytes.

`X-Ori-Commissioning-Artifact-Type` MUST be one of:

- `commissioning_authorization`
- `commissioning_revocation`

The header names the verifier. The authority MUST NOT infer the type by trial
verification, and naming a type does not make the body valid under it.

## Client authentication

Every request is authenticated with a dedicated symmetric secret whose sole
purpose is `commissioning_ingest`. It MUST have at least 256 bits of entropy
and MUST be distinct in resolved bytes from every `evidence_ingest`,
`evidence_audit`, fleet, runtime-gateway envelope, custody and
authority-signing secret. Registry construction MUST refuse a secret that
resolves to the same bytes as one held for another purpose, a duplicate
derived identifier, and a configured identifier. The identifier is derived,
never configured:

```text
key_id = "hkdf-sha256:" || lowercase_hex(HKDF-SHA256(
  ikm = secret UTF-8,
  salt = "ori.commissioning_ingest_key_id.v1",
  info = "commissioning_ingest",
  length = 16
))
```

Each credential record binds:

- `purpose`, exactly `commissioning_ingest`;
- a stable opaque `client_id` and key generation;
- a non-empty set of permitted commissioning `key_id`s — the
  `commissioning_authority` registry entries this caller may submit artifacts
  signed under;
- `not_before_ms` and `expires_at_ms`.

A valid credential grants transport admission for artifacts signed under its
permitted keys. It grants no signing authority, no read, and no device
enumeration: the credential names keys, never devices, because which devices
a commissioning actor may license is decided by who signs, not by who
delivers.

Required headers:

| Header | Rule |
| --- | --- |
| `X-Ori-Commissioning-Client` | Stable opaque client identifier; 1–128 printable ASCII characters. |
| `X-Ori-Commissioning-Key-Id` | Derived identifier above, compared byte-exactly. |
| `X-Ori-Commissioning-Sent-At-Ms` | Positive D-011 integer. |
| `X-Ori-Commissioning-Nonce` | Exactly 32 lowercase hexadecimal characters from 16 random bytes. |
| `X-Ori-Commissioning-Artifact-Type` | Closed vocabulary above. |
| `X-Ori-Commissioning-Artifact-Digest` | `sha256:` plus 64 lowercase hex over the exact body bytes. |
| `Authorization` | `Ori-Commissioning-HMAC hmac-sha256:<64 lowercase hex>`. |

The HMAC input is:

```text
"ori.commissioning_ingest_request.v1" || NUL || canonical({
  "artifact_digest": X-Ori-Commissioning-Artifact-Digest,
  "artifact_type": X-Ori-Commissioning-Artifact-Type,
  "client_id": X-Ori-Commissioning-Client,
  "key_id": X-Ori-Commissioning-Key-Id,
  "method": "POST",
  "nonce": X-Ori-Commissioning-Nonce,
  "path": "/v1/evidence/commissioning/artifacts",
  "sent_at_ms": integer(X-Ori-Commissioning-Sent-At-Ms)
})
```

`canonical` has the same UTF-8 JSON rules as `evidence-transport/v1`. The
signature is HMAC-SHA256 under the selected secret.

Because the authorisation's `commissioning_digest` is, by
`evidence-exchange/v1`, the digest over the complete signed object, the
`X-Ori-Commissioning-Artifact-Digest` of an authorisation submission is the
commissioning reference itself. The caller learns nothing from the response
it did not already hold.

Authentication and resolution order is normative:

1. Enforce request-line, header, and body-size limits.
2. Validate header shapes and recompute the body digest.
3. Resolve `(commissioning_ingest, key_id)` without trial verification.
4. Verify the HMAC in constant time.
5. Enforce clock skew and atomically reserve `(client_id, key_id, nonce)`.
6. Parse the body as the named type; refuse any other shape as malformed.
7. Check that the credential permits the artifact's `key_id`.
8. Only then invoke the artifact verifier.

The default maximum clock skew is 300,000 ms. A nonce is retained for at least
twice that window. Reusing a nonce is a transport replay and reaches no
verifier. A retry uses a fresh timestamp, nonce and HMAC while keeping the
artifact bytes and digest unchanged.

## Resolution on receipt

**Authorisation.** The verifier is the one `evidence-exchange/v1` defines for
`commissioning_authorization`, selected by `(commissioning_authority,
key_id)`. Each refusal is distinct because the remedies differ:

| Condition | HTTP | `reason` |
| --- | ---: | --- |
| Body is not exactly one well-formed authorisation, or the named type does not match the body | 400 | `malformed` |
| `key_id` is held for no `commissioning_authority` key | 422 | `unknown_commissioning_key` |
| `key_id` is held, but under another purpose | 422 | `wrong_purpose` |
| The signature verifies under the device key the authorisation licenses, or under any key that is not a commissioning key | 422 | `self_authorised` |
| The signature does not verify under the named commissioning key | 422 | `bad_signature` |
| An authorisation with this digest is held and revoked | 409 | `revoked` |
| A revocation's `key_id` is neither the issuing key nor a revocation key the registry designates for it | 422 | `revocation_not_permitted` |
| A revocation names a digest the authority does not hold | 422 | `unknown_authorisation` |

A verified authorisation is retained idempotently by `commissioning_digest`,
transactionally with its provenance below. Byte-identical resubmission under
a fresh transport nonce returns `accepted` with the same outcome and no second
retention. An authority MAY hold more than one authorisation for a device and
epoch, per `evidence-exchange/v1`; re-issuance is a fresh artifact with its
own digest and its own reference, and the reference delivered to the device
must be the one for the authorisation that is held.

**Promotion.** On retention the authority resolves any registration retained
pending under this digest, exactly as the resolution table in
`evidence-exchange/v1` and the `receiver-state/commissioning-resolution.json`
corpus require: verify, register, promote, write provenance and create the
epoch confirmation in **one transaction**, or none of them. The confirmation
is returned to the device through the courier's next delivery per
`evidence-transport/v1`; it is never returned here. A registration that
arrives later applies under the now-held authorisation on its own path.

**Revocation.** A revocation is a separately signed artifact:

| Field | Type | Notes |
| --- | --- | --- |
| `v` | `int` | `1`. |
| `commissioning_digest` | `string` | The digest of the authorisation being revoked. |
| `key_id` | `string` | A held `commissioning_authority` key that is permitted to revoke this authorisation — see *Who may revoke* below. |
| `actor` | `string` | Who requested revocation. |
| `reason` | `string` | Free text. |
| `revoked_at_ms` | `int` | Commissioning-side clock. |
| `signature` | `string` | `ed25519:` over the domain `ori.evidence_commissioning_revocation.v1` and a NUL byte, then the canonical object without `signature`. |

**Who may revoke.** Holding a commissioning key does not license revoking
what another commissioning key signed: without a stated relation, any
credential permitted for an unrelated key could revoke a known digest and
keep a pending registration from ever confirming. The relation is
registry-backed and explicit. A revocation is permitted when its `key_id` is

- the key that signed the authorisation being revoked, or
- a key the `commissioning_authority` registry designates as a
  **revocation key** for that signing key, in the signing key's own entry
  (`revocation_key_ids`), so that a lost or retired issuing key remains
  revocable by a party the registry named in advance.

The registry entry is the sole source of that designation; nothing in the
revocation artifact, the credential, or the request can confer it. Any other
held key — including one otherwise valid for issuing authorisations — is
refused `422 revocation_not_permitted`, after its signature has verified, so
the refusal is distinguishable from a forgery. Designation is checked
against the registry as held at the time of the revocation, not as it was
when the authorisation was issued.

A verified and permitted revocation marks the named authorisation revoked,
transactionally.
From that commit a registration resolving to it is refused
`commissioning_digest_mismatch` on the courier path, and resubmitting the
authorisation here is refused `409 revoked`. Revocation does not withdraw an
epoch confirmation already issued: an epoch that was confirmed stays
confirmed, and retiring it is the epoch lifecycle in `evidence-exchange/v1`,
not this path. A byte-identical revocation resubmitted is `accepted` idempotently.

## Response

```json
{
  "v": 1,
  "artifact_digest": "sha256:...",
  "outcome": "accepted",
  "reason": "",
  "retriable": false,
  "registration": "awaiting_registration"
}
```

`registration` is `applied` when retaining this authorisation promoted a
registration in the same transaction, `awaiting_registration` when none was
held, and `not_applicable` for a revocation. It says whether a device is now
confirmed; it does not carry the confirmation, the device's key, or anything
that names the authority.

| HTTP | `outcome` | Meaning | Caller action |
| ---: | --- | --- | --- |
| 200 | `accepted` | Durably and idempotently retained, promotion committed if any. | Deliver `artifact_digest` to the device as its commissioning reference. |
| 400 | `refused` | Request or body permanently malformed. | Do not retry the same bytes. |
| 401 | `refused` | Missing, unknown, stale, replayed, or invalid transport authentication. | Retry only with a fresh authenticated request or repaired credentials. |
| 403 | `refused` | Credential not permitted for the artifact's `key_id`; `reason` is `key_not_permitted`. | Record; a different credential or key is required. |
| 409 | `refused` | Conflicts with retained state (`revoked`). | Issue a fresh authorisation. |
| 422 | `refused` | Artifact authenticator or semantic check failed; `reason` from the table above. | Identical retry cannot repair bytes. |
| 429 | `pending` | Explicit rate limit. | Retry after `Retry-After`. |
| 503 | `pending` | Authority temporarily cannot commit durably. | Retain and back off. |

Unauthenticated responses MUST omit `artifact_digest` and `registration`;
otherwise the endpoint becomes a membership oracle for commissioning
references. Authenticated refusals include the submitted digest.

## Audit

The authority records, transactionally with every decision, accepted or
refused:

- artifact type and digest, and the exact bytes of an accepted artifact;
- the authenticated `client_id` and ingest key generation;
- the commissioning `key_id` named by the artifact, and for an authorisation
  its `device_id`, `pubkey_hex` and `anchor_epoch_id`;
- the outcome and `reason`;
- the authority clock at decision and the independently released service
  version, as evidence provenance;
- for a promotion, the registration's digest and the confirmation issued.

A refused submission creates no device-history state and no evidence gap. The
record is readable through the audit path in `evidence-audit/v1`, under that
path's own credential, and by no other means.

## Disclosure boundary

Nothing at an evidenced site learns of this path. The runtime, the gateway,
the fleet manager, the bridge command, configuration documents and every
health surface carry no endpoint, credential, client identifier, or mention
of this contract; the device sees only the reference and the generic
registration status. Responses, headers, logs, metrics and error text MUST
NOT disclose implementation identity, host, deployment location, credential
material, signing-key custody, or the existence of other credentials.

Who may commission a site, and how the commissioning key is issued, held and
rotated, stays with the `commissioning_authority` registry and
[commissioned-safety-binding/v1.md](../commissioned-safety-binding/v1.md).
This contract decides only how a signed statement reaches the authority that
must hold it.

## Limits and failure behaviour

- The service MUST bound header count and size, request body size,
  concurrent requests, per-client rate, and stored replay nonces.
- Backpressure is an explicit `429` or `503`; `accepted` is returned only
  after durable commit.
- A partially written transaction is absent after restart. A committed
  response survives restart and is returned idempotently.
- Loss of this path leaves registrations retained pending and devices at
  `pending_confirmation`, never confirmed and never receipted by inference.

## Vectors

[`vectors/ingest-auth.json`](vectors/ingest-auth.json) fixes the key
derivation, canonical authentication metadata, exact HMAC preimage and
signature for an authorisation submission whose body is the valid
`commissioning_authorization` artifact from `evidence-exchange/vectors`, and
for a revocation of it signed under the published commissioning seed. Its
`commissioning_registry` designates a published recovery key for that seed
and holds a second, unrelated commissioning key; revocations signed by all
three are carried, and only the issuing key and the designated recovery key
are accepted. It carries negative cases for body substitution, a
wrong-purpose secret, nonce replay, a credential not permitted for the key,
and — reusing the exchange's own rejection artifacts — an unknown
commissioning key and a self-authorised device, plus revocation by an
unrelated held key, revocation of an unheld digest and resubmission after
revocation.
`scripts/check-evidence-commissioning-ingest-vectors` recomputes every
derivation and signature and refuses a corpus that has lost a case.
