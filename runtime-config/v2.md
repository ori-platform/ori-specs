# Runtime Config Surface v2

> Status: Design target, pre-ratification. No shipped consumer claims
> conformance. Amendable in place under the
> [pre-ratification exception](../VERSIONING.md#pre-ratification-exception).
>
> Supersedes [v1.md](v1.md) for deployments that adopt the configuration
> authority split. v1 remains the accurate description of what runtimes
> implement today.

[v1.md](v1.md) documents the configuration surface section by section. It does
not say what happens to a key it does not document, and no implementation
refuses one.

That is the gap this version closes, and it is not cosmetic.
The configuration authority split (ori-specs#75) separates
configuration by signing authority so that a field written by the wrong party
becomes a mechanical refusal. **That guarantee is only as deep as the schema.**
Disjoint top-level section names stop a provisioning backend adding a
top-level `zones`; they do nothing about a safety parameter appearing three
levels down inside `actions`, where nothing is looking.

## The Closure Rule

**Every object in this document is closed at every depth. A key that is not
declared for its node is `unknown_key`, and the document is refused.**

Not ignored, not passed through, not logged and dropped. A configuration key
that a runtime silently discards reads, to whoever wrote it, as a setting that
took effect — and the settings people write into a config file by hand are
disproportionately the ones they believe are protecting them.

Closure is **recursive**. It applies to `gateway.auth` exactly as it applies to
`gateway`, and to `actions.sms.incoming_webhook.signature` exactly as it
applies to `actions`.

### Node kinds

Every node is exactly one of these, and this document names which for each:

| Kind | Meaning |
| --- | --- |
| **closed object** | Exactly the declared keys. Unknown key is a refusal. |
| **declared map** | Keys are operator-chosen; **every value is a named closed object**. The openness is in the keys, never in the shape. |
| **list of `T`** | Ordered; every element conforms to `T`. |
| scalar | `string`, `int`, `float`, `bool`, with the stated constraint. |

### The two open points, named

A recursive schema that pretends a configuration surface has no open points is
lying about one of them. This surface has exactly two, and both are open in
their **keys** rather than in their shape:

**`actions.coap.commands`** is a declared map. An operator names commands; each
value is a closed `CoapCommand`.

**`skills[].config`** is delegated, not open. Its shape is the skill's own
`config` schema from
[skills-package/v2.md](../skills-package/v2.md), and the runtime closes it
against that manifest. A skill with no declared `config` schema accepts no
config keys at all. Delegation is what keeps a skill's tuning surface out of
this document without making it unbounded — the reserved-name and admission
rules there continue to apply.

**Neither may carry safety authority.** The forbidden-content rule
in ori-specs#75 reaches into both.

## Error Semantics

| Verdict | Cause |
| --- | --- |
| `unknown_key` | A key not declared for its node, at any depth |
| `wrong_type` | A declared key whose value is the wrong type |
| `out_of_range` | A declared key whose value violates its constraint |
| `missing_required` | A key required by its node, or by another key's presence |
| `relocated_key` | A key this version moved to another authority's artifact |

`relocated_key` is separate from `unknown_key` because the two need different
actions. `rated_capacity_amps` is not a typo and not an unrecognised setting —
it is a real field that now belongs somewhere else, and saying so is the
difference between an operator moving it and an operator deleting it.

## Migration From v1

A v1 document is not a v2 document. Adopting v2 means:

1. Every key not declared above is removed or relocated. A backend that emitted
   undocumented keys learns which on the first refusal, because a v2 runtime
   names them rather than dropping them.
2. `device.rated_capacity_amps` moves to a commissioned zone. Until a binding
   carries it, the device observes and does not actuate.
3. `skills[].config` is validated against each skill's manifest schema rather
   than accepted wholesale.

Identity is preserved: `device.id` is unchanged by migration, and a device does
not become a new device because its configuration format did.

## Golden Vectors

The authoritative corpus is
[config-surface-vectors-v2.json](config-surface-vectors-v2.json), held here
beside this document. Its SHA-256 is
`1c071ff642a85e11933e9edc6916b8ed11cfe801e196fe372abf977ba32dced9`.

It carries 1 accept case and 15 reject cases, at least one per verdict, each
naming the **exact path** of the offending key so a validator's report is
checkable and not merely its verdict.

### The schema travels with the cases

The corpus carries the node table as **machine-readable data** under `nodes`,
not only example documents. A 492-line contract that every implementer
hand-transcribes is one they will transcribe differently, and the differences
would surface as a device rejecting a configuration another device accepts. A
conforming validator consumes `nodes` rather than re-deriving it.

`relocated` and `skill_manifests` travel the same way, so the relocation rule
and the delegation target are data rather than prose an implementer must
interpret.

### What the corpus measures

Every node is reachable from the root — a declared node nothing references is
decoration, and the corpus check refuses one.

The gap this version closes is quantified rather than asserted. Validating the
same corpus with closure applied **only at the root**, which is what v1
effectively specifies, accepts **14 of the 15** documents v2 refuses:

| Closure | Documents refused |
| --- | --- |
| Root only, as v1 | 1 of 15 |
| Recursive, as v2 | 15 of 15 |

The one v1 catches is an unknown key at the top level. Everything else — a
weakened webhook signature setting four levels down, a relocated safety
parameter, a wrong type, an out-of-range bound, an absent required key — passes
a one-level check.

## Open Questions

- **`address` is `string | int`.** `0x48` is idiomatic in YAML and arrives as
  an integer; a string form is common in generated documents. Accepting both is
  honest about practice and weaker than a closed schema should be. Narrowing it
  needs a survey of what backends actually emit.
- **Whether v2 should carry `sensors` at all.** It is inventory, and the
  authority split says inventory is provisioning's. It is listed here because
  that is where it lives today, not because the boundary has been re-argued.
