# Runtime Config Surface v2

> Status: Design target, pre-ratification. No shipped consumer claims
> conformance. Amendable in place under the
> [pre-ratification exception](../VERSIONING.md#pre-ratification-exception).
> `runtime-config/v1` remains the implemented baseline.

This version closes the provisioning document. Every key at every depth is
declared with a type and its bounds; an undeclared key is refused by full
path; types are checked and never coerced; and every key that carried
safety or trust authority in v1 is gone, each refused with a verdict naming
the authority it belongs to.

The declaration is the file [vectors/schema.json](vectors/schema.json). It is
normative: a consumer vendors it byte-for-byte and validates against it. The
tables in this document are generated from it and gated against drift, so the
prose cannot say one thing while the schema says another.

## Why v1 Is Not Closed, And Why That Matters

`runtime-config/v1` documents sections. The loader behind it ignores an
unknown top-level section, and beneath the top level refuses nothing: `_parse_gateway` copies the mapping it is given and validates
the keys it knows, so a key it does not know rides along silently. The shipped
example sets `actions.relay.active_high`, and nothing in the runtime reads it —
an operator setting it to `false` on an active-low board gets an inverted
relay and no error.

An open surface is a safety problem before it is a tidiness problem, because a
signed document is trusted whole. A provisioning signer that can write any key
can write `device.rated_capacity_amps`, and a release-owned multiplier turns
that number into a Tier D trip point. The signature proves the backend wrote
it; nothing proves the backend was entitled to.

Closing the surface is what makes the split by signing authority mechanical:
a field in the wrong document becomes a refusal a schema decides, rather than
a convention a reviewer has to notice.

## Scope

This contract defines **one document**: the provisioning document, signed by
the provisioning authority under
[runtime-config-signing/v1.md](../runtime-config-signing/v1.md). It carries
device and site identity, the hardware inventory, selected skills, and every
host and channel setting the runtime reads.

It does not define the entitlement document
([device-policy/v1.md](../device-policy/v1.md)), the commissioned safety
binding ([commissioned-safety-binding/v1.md](../commissioned-safety-binding/v1.md)),
or the release-owned safety profiles
([safety-profile/v1.md](../safety-profile/v1.md)). How those artifacts are
selected, anchored, and reconciled with this one — including what a consumer
does when the binding's `inventory_generation` disagrees with
`device.inventory_generation` — belongs to
[runtime-config-orchestration/v1.md](../runtime-config-orchestration/v1.md).
This document is the provisioning half of that split and nothing more.

## The Method

The declaration was not transcribed from `runtime-config/v1.md`. An earlier
attempt at that produced a schema which refused 34 shipped features, because
the loader accepts far more than the document describes. Instead the surface
was **extracted**: the 177 paths `ori/config.py` parses at `ori-runtime`
`fe5eb9a`, recorded in [inventory/](inventory/README.md), plus the 70 leaves
the shipped example sets that consumers outside the loader read. Every
descriptor's type and bounds were taken from the validation code or the
consumer that reads the value, and are cited in the appendix by the
constraint they enforce.

**Where v2 is stricter than the loader, it says so.** Most bounds are the
loader's own. These are not, and a producer must know they bind under v2
even though a v1 runtime accepts the value: `reasoning.escalation_threshold`
in `[0, 1]`; `reasoning.energy_aware_reasoning.throttle_threshold_percent` and
`critical_threshold_percent` in `[0, 100]`; `reasoning.causal_memory.min_confidence_to_store`
in `[0, 1]` and `rejection_expiry_days ≥ 0`; `logging.max_bytes ≥ 1` and
`backup_count ≥ 0`; `actions.sms.incoming_webhook.port` in `[1, 65535]`;
`actions.sms.gsm` timeouts and `actions.coap.timeout_s` strictly positive
where the consumer today clamps a smaller value to a floor; and
`skills[].config.approval_timeout_seconds ≥ 1` where the runtime today clamps
to one. Each is the bound the consumer's own behaviour implies; none changes
what a valid document does.

The declaration was then run against every shipped example —
`ori.yaml.example`, `ori.linux.yaml.example`, and the three phone examples —
after the migration rules below. All five validate with no residual undeclared
path. That run is reproducible with
`scripts/check-runtime-config-vectors --runtime-examples <ori-runtime checkout>`.

## Grammar

This contract adopts [schema-descriptor/v1](../schema-descriptor/v1.md)
unchanged, and adds five descriptor properties and one schema-level table.

| Extension | Meaning |
| --- | --- |
| `description` | Prose carried into refusals and the appendix. Never load-bearing. |
| `pattern` | On `type: string`: a regular expression the whole value must match. It must compile at schema load, and a `default` is checked against it there. |
| `exclusive_minimum` | A strict lower bound, subject to the same load-time rules as `minimum`; the two are mutually exclusive on one descriptor. |
| `entries` | On `type: object`, in place of `properties`: every key is operator-chosen, and every value validates against this descriptor. An object declares exactly one of `properties` or `entries`. |
| `delegate` | On `type: object` beside `properties`: keys beyond those declared are validated by the named contract. Whether a consumer that does not implement that contract passes them through or refuses them is fixed per contract below. |
| `retired` | Schema-level. Paths this version removed, each with the verdict a consumer returns, the authority the key belongs to, and where it now lives. |

**Delegation is explicit about what happens when the delegate is absent.**

| Delegate | Where | A consumer without it |
| --- | --- | --- |
| `sensor-configuration/v1` | `sensors[]` and `sensors[].calibration` | Passes protocol keys through. Every runtime that accepts a v2 document already implements that contract; the sensor entry's canonical envelope is typed here regardless |
| `skills-package/v3` | `skills[].config` | **Refuses** any key other than `approval_timeout_seconds`, naming the contract. v3 is a design target with no implementation, and absence is not permission |

`entries` exists for exactly one path, `actions.coap.commands`, whose keys are
command names an operator chooses. Everything else is closed by name.

### Types are checked, never coerced

The v1 loader accepts `enabled: "true"`, `failure_threshold: "5"`, and
`gpio_pin: "26"`, converting each. v2 refuses all three. A producer emits the
declared type, and a document that relied on coercion is a document that was
never checked.

Two fields are strings where a reader might expect integers:
`health_socket.mode` and `firmware_mqtt_provisioning.socket_mode`. They carry a
**quoted** octal string, `"0o660"`, because YAML 1.1 parsers read an unquoted
`0o660` as a string and YAML 1.2 parsers read it as the integer 432. A document
that means one thing in both parsers has to quote it, and the schema refuses
the integer form so the ambiguity cannot arrive by another route.

### Environment placeholders

A document is validated **as signed**, before `${VAR}` expansion, because the
signature covers the literal placeholder and expansion is the last thing a
consumer does with a verified document. A placeholder is therefore a string,
and may appear only in a field declared `string`. `port: ${PORT}` is refused
as a string where an integer is declared, which is what it is.

### The document marker

A v2 document carries `schema: ori.runtime-config.v2` at the top level,
required and fixed. A document without it is a **legacy document** — a
single-document configuration from before this version — and is not
malformed: the consumer applies the migration rules and the one-way latch
described under Migration. A document with any other marker is malformed.

## What Moved, And Where

Some keys carried authority that a provisioning signer must not hold, some
carried settings that were never a site's to make, and two named a setting
that must not exist. Every one is in the retired table at the end of this
document, refused by full path with a verdict naming where the content
belongs.

| Verdict | Meaning | What an operator does |
| --- | --- | --- |
| `malformed` | Belongs to nobody: an undeclared key, a wrong type, a bound violation | Fix the document |
| `foreign_field` | Belongs to **another authority**; validly signed and still refused | Move it to that authority's document |
| `forbidden_content` | Belongs to **no configuration authority**: an anchor, or release-owned | Remove it; it is delivered another way |

A `foreign_field` or `forbidden_content` refusal is an **authority failure,
not a signature failure**. The document may verify perfectly. Reporting either
as `bad_signature` sends an operator to key custody instead of to the boundary.

**`device.rated_capacity_amps` → the commissioned zone.** It reads as
inventory and is not: multiplied by a release-owned constant it is a trip
point, so it is signed by the party that certified the electrical work, as
`zone.rated_capacity` under the binding contract. `foreign_field`.

**`actions.relay.active_high` → the commissioned actuator identity.** Driver
polarity maps a GPIO level to a coil state and is proven at commissioning.
Nothing in the runtime ever read this key. `foreign_field`.

**No artifact of the set selects an anchor — by key or by name.** An anchor
inside a provisioning-signed document is the provisioning signer's choice,
and the separation it was meant to verify is then decorative. Naming the
*variable* the anchor is read from is the same choice by indirection: a
signer that can write `public_key_env: EVIL_KEY` has chosen the anchor as
surely as one that wrote the key. So anchor locations are **fixed by this
contract**, owned by the release and the installer, and a document may not
name them at all:

| Anchor | Fixed location |
| --- | --- |
| provisioning, current | `ORI_CONFIG_TRUST_ANCHOR_PUBLIC_KEY_B64` |
| provisioning, previous (verify-only) | `ORI_CONFIG_TRUST_ANCHOR_PREVIOUS_PUBLIC_KEY_B64` |
| entitlement | `ORI_DEVICE_POLICY_PUBLIC_KEY_B64` |
| Tier C offline approval tokens | `ORI_OFFLINE_TOKEN_PUBLIC_KEY_B64` |

`device_policy.public_key_b64` and `actions.offline_tokens.public_key_b64`
carried the keys themselves; `security.config_signature.trust_anchor_env`
carried the provisioning anchor's location, which the v1 loader read from the
document *before* verifying it; and any `*_env` selector for the other two is
the indirection above. All are `forbidden_content`. The host-level
`ORI_CONFIG_TRUST_ANCHOR_ENV` override remains a host setting, outside every
document, for deployments that must relocate the variable.

**`evidence.authority_keys_path` and `evidence.checkpoint_interval_s` → the
release.** The loader already refuses both with the reason: a site operator is
the party evidence exists to constrain. `forbidden_content`.

**`gateway.tls.insecure_skip_verify` and `gateway.tls.insecure` → nowhere.**
`malformed`; a private CA is configured through `gateway.tls.ca_certfile`.

## What Was Added

**`device.inventory_generation`**, required, an integer of at least one. It
names the hardware inventory this document declares, allocated by the
provisioning authority, monotonic per device, and **never reused for
different contents**. The commissioned binding names the generation it was
proven against, and that equality is the invariant the orchestration contract
enforces; this document supplies one side of it and guarantees the two
allocation rules.

**`skills[].digest`**, optional, `sha256:<64 lowercase hex>` of the selected
package. Selection by digest confers no authority; a consumer that verifies
packages MUST refuse a package whose digest differs when one is declared.
Representable here; enforcement lands with package verification in
`ori-runtime`.

**`skills[].config` is closed to `approval_timeout_seconds`.** That is the
only key the runtime reads from this object: `ori.yaml`'s skill configuration
never reaches the skill loader, and the shipped examples' `energy_cost_naira`,
`owner_name`, `tariff_per_kwh` and the rest are settings nothing consumes.
Under `skills-package/v3` a package declares a signed `config_schema` and a
consumer validates these keys against it; until a runtime implements v3, they
are refused, naming the contract, rather than carried as though they took
effect.

## Migration

A consumer accepting v2 MUST also load a legacy document, once, under these
rules, and MUST NOT change `device.id` in doing so — identity continuity is
the property the installer already protects.

1. Recognise a legacy document by the absent marker, and load it under v1's
   rules. The steps below then derive the v2 document from it.
2. Add `schema: ori.runtime-config.v2`, and `device.inventory_generation: 1`:
   a legacy document is the first declared inventory.
3. Drop every path in the retired table and report each one, with its
   destination, on the operator-visible surface. A value that carried a Tier D
   parameter is recorded as relocated, not lost; an anchor value is provisioned
   into its fixed environment variable by the installer.
4. Drop every `skills[].config` key other than `approval_timeout_seconds`,
   reporting each one.
5. Rewrite an integer `health_socket.mode` or
   `firmware_mqtt_provisioning.socket_mode` as its quoted octal string.

`scripts/check-runtime-config-vectors --runtime-examples` implements exactly
these steps, so the prose and the mechanism cannot drift.

**The latch is one-way.** Once a device has accepted a v2 document it MUST
refuse a legacy document permanently — persisted, surviving restart and
reinstall, with no flag that clears it. A legacy document is provisioning-signed
and legitimately carried `device.rated_capacity_amps`, so replaying an old
valid one after the split would reintroduce a safety parameter under the
authority the split removed it from.

## Signing

The envelope and its canonical payload are those of
[runtime-config-signing/v1.md](../runtime-config-signing/v1.md); the `schema`
marker is signed like any other top-level key. v2 adds one field inside the
block, `config_signature.signing_key`: the raw Ed25519 public key that signed
the document, `ed25519:` plus the canonical base64 of exactly 32 bytes. It sits
inside the signed bytes, so it cannot be altered without breaking the
signature, and it is what lets a consumer select an anchor by comparing key
material across every configured anchor and then decide authority over a
verified document — the rule [runtime-config-orchestration/v1.md](../runtime-config-orchestration/v1.md)
fixes. `signer_id` remains an audit label and is never an authority input.

The `config_signature` block is declared here so that the envelope is closed
too: a key beside the signature is outside the signed bytes, and ignoring it
would let an intermediary attach content a careless consumer might read.

## Consumer Obligations

- Vendor [vectors/schema.json](vectors/schema.json) byte-for-byte, pin its
  digest, and validate every provisioning document against it at load, before
  environment expansion and after signature verification.
- Refuse an undeclared key at any depth by full path; refuse a retired path
  with the verdict and destination the table gives; never pass a key through
  to a consumer that the schema did not declare, except under a delegation
  whose absent-consumer rule says so.
- Read every anchor from its fixed location, and never from a value or a
  variable name carried in any document.
- Refuse a `skills[].config` key other than `approval_timeout_seconds` until
  `skills-package/v3` is implemented, naming the contract.
- Load legacy documents once under the migration rules and then latch.
- Report refusals by verdict, so that an authority failure is never shown as
  a signature failure.

## Producer Obligations

A provisioning backend generating v2 documents MUST emit declared types, MUST
NOT emit any retired path, MUST allocate `device.inventory_generation`
monotonically per device and never reuse a generation for different contents,
and MUST NOT emit any key the schema does not declare — a generator that
passes unknown fields through has reproduced the v1 defect on the producing
side. `ori-cloud` #19 owns
that implementation.

### Golden Vectors

[vectors/schema.json](vectors/schema.json) is the declaration.
[vectors/schema-load.json](vectors/schema-load.json) carries descriptor
fragments that must load or be refused at schema load — one per load-time
rule of the descriptor core and of the extensions — so that a consumer proves
it refuses a bad declaration before any document exists.
[vectors/documents.json](vectors/documents.json) carries the document cases:
accepted documents including the minimal one and the migrated shipped example,
one legacy document, and one refusal per verdict, per retired path, per
extension, and per document-level requirement class of the core. Each refused
case carries exactly one defect and names the full path the refusal must
contain, and the checker enforces both.

## Open Questions

- **Sensor and skill delegation are asymmetric.** Sensor protocol keys pass
  through because every v2-capable runtime implements
  `sensor-configuration/v1`; skill configuration is refused because nothing
  implements `skills-package/v3`. When v3 ships, the `skills[].config`
  delegation flips to pass-through in the schema and this asymmetry ends.
- **Host-local settings under the provisioning signature.** `database.path`,
  `logging`, `health_socket` and the socket paths are signed by the
  provisioning authority because they were in v1's single document. Whether a
  host-local document with its own signer is warranted is an orchestration
  question, not answered here.
- **Cross-field rules are prose.** The conditional requirements are enforced
  by the consumer and stated in a table; the descriptor core has no grammar
  for them. A future core revision could carry them mechanically.
