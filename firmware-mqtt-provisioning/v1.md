# Firmware MQTT Transport-Identity Provisioning Contract v1

> Status: Contract target. No implementation is claimed until the
> implementing repositories cite this contract from a tagged release.

This contract defines authenticated management of a firmware device's MQTT
transport identity: generating a certificate signing request (CSR), installing
the public certificate bundle, revoking transport access, and reading public
lifecycle status.

It does **not** grant Layer 1 evidence authority or physical-action authority.
MQTT authentication is transport defence in depth. Layer 1 envelope signatures,
the approved device anchor, runtime command signatures, command freshness, and
manifest-scoped action authority remain mandatory.

## Scope And Trust Model

Three private keys remain separate:

| Key | Purpose | Custody |
| --- | --- | --- |
| Device Layer 1 Ed25519 key | Signs manifests, telemetry, faults, and responses defined here | Generated and retained on-device |
| Provisioning-authority Ed25519 key | Authorizes Layer 1 approval and the requests defined here | Held by the controlled off-device provisioner; only its public key is flashed |
| MQTT P-256 transport key | Authenticates the device to the MQTT broker through its client certificate | Generated and retained on-device |

The provisioning-authority key is the same trust root used by the signed
approval in [firmware-commands/v1.md](../firmware-commands/v1.md). This contract
does not introduce another fleet authority.

A transport adapter is untrusted routing. USB attachment, physical presence,
an MQTT topic, a TLS session, or possession of a serial port MUST NOT authorize
an operation. Every request is authorized by its signed payload.

The adapter MUST process these operations outside the Local Interlock path. It
MUST NOT block, allocate, parse certificates, or perform network I/O on the
Local Interlock path.

## Prerequisite Layer 1 Approval

`create_csr` and `install` require a currently approved, unrevoked Layer 1
anchor for the named `device_id`. A factory-fresh flow therefore proceeds in
this order:

1. export only the device's public Layer 1 identity and signed manifest;
2. register and promote the same `anchor_epoch_id` in the runtime and evidence
   store under [device-provisioning/v1.md](../device-provisioning/v1.md);
3. deliver and verify the existing provisioning-authority-signed Layer 1
   approval;
4. only then issue a request from this contract.

Public identity export and delivery of the existing signed approval may use a
physically attached bootstrap channel. The channel still grants no authority:
the approval signature and exact device/manifest binding do.

Withdrawal must remain possible after Layer 1 revocation. A PA-signed `revoke`
or read-only `status` request MAY therefore bind the identity's retained
formerly active anchor while the identity is revoked. That exception can only
withdraw MQTT authority or report public state; it cannot create a key, install
a candidate, clear either revocation, or restore Layer 1 acceptance.

### Anchor-epoch transitions

An MQTT transport identity is bound to exactly one approved
`anchor_epoch_id`. Any change of device key, posture, or `capability_hash`
creates a different anchor epoch and immediately makes the prior transport
identity ineligible for production MQTT startup.

Re-issuance is required after **every** anchor-epoch change, including a
same-key manifest change. This strict coupling is intentional: the stored
transport record must never claim an approval epoch different from the one the
device currently operates under.

The provisioning adapter MUST remain reachable independently of production
MQTT so the device can recover from that fail-closed transition. Implementations
MUST NOT keep using the old certificate merely because its X.509 validity
interval has not expired.

## Actor And Reason

Every mutating request carries:

- `actor`: the provisioning authority's stable identifier for the
  authenticated operator;
- `reason`: the audit reason for the operation.

The provisioning-authority signature attests both values. Firmware verifies
that signature; it does not authenticate `actor` through a second credential.
The off-device provisioner MUST authenticate the operator before signing and
MUST record the richer audit context it used.

`actor` is a fleet identifier, non-empty and at most 64 ASCII bytes.
`reason` is non-empty, at most 128 UTF-8 bytes, and MUST contain no control
characters, double quote, or backslash. These bounds keep the device parser
fixed and remove alternative JSON escaping forms.

## Provisioning Freshness

`provision_seq` is a strictly increasing positive integer per `device_id`.

- It is distinct from telemetry `(boot_id, seq)` and command `cmd_seq`.
- It is within `1 .. 2^53 - 1` and has canonical decimal encoding: no sign and
  no leading zeros.
- Its high-water mark persists across reboot, Layer 1 re-approval, device-key
  rotation, command-key rotation, MQTT certificate replacement, MQTT transport
  revocation, and Layer 1 revocation/reinstatement.
- A transport revocation MUST NOT erase or reset it.
- Gaps are valid. A repeated or lower value is `replayed`.
- Malformed, wrong-device, bad-signature, wrong-epoch, and replayed requests do
  not consume it.

Once grammar, device binding, provisioning-authority signature, current
approved epoch, and freshness pass, `create_csr` and `install` consume
`provision_seq` **before** changing key or certificate state. A crash may lose
the requested operation, but it cannot leave the request replayable; the
provisioner retries with a higher sequence.

`revoke` is deliberately ordered differently:

1. write the fail-closed revocation tombstone;
2. persist the `provision_seq` high-water mark;
3. erase active, candidate, and pending MQTT records.

If step 1 succeeds and a later step fails, transport remains revoked. Replaying
the same signed revoke is an idempotent recovery attempt, not a path to restore
transport. After the high-water mark is durable, the same request is
`replayed`, while the tombstone remains effective.

## Signature And Canonical Grammar

All signatures use `ed25519:<standard-base64-64-byte-signature>`.

Requests have one outer form:

```json
{"request":<request-object>,"signature":"ed25519:<base64-64-byte-signature>"}
```

The provisioning authority signs the exact canonical UTF-8 bytes of
`request-object`, excluding the outer wrapper and `signature`.

Rules shared by every request and response:

- object fields appear in the exact lexicographic order shown;
- there is no whitespace outside string values;
- duplicate, reordered, missing, unknown, or extra fields are `malformed`;
- `v` is the integer `1`;
- identifiers use `[A-Za-z0-9._-]`;
- base64 is standard padded base64 with canonical padding;
- a decoded PEM value is the exact UTF-8 PEM byte sequence, including line
  endings and final newline where present;
- private-key bytes are forbidden in every request and response.

### `create_csr`

```json
{"actor":"operator-17","anchor_epoch_id":"sha256:<64-lowercase-hex>","device_id":"ori-fw-7c9f2b3a","kind":"create_csr","provision_seq":41,"reason":"initial-mqtt-enrollment","v":1}
```

Acceptance generates a new P-256 transport key using device entropy, replaces
only the pending CSR key, and returns the signed CSR response below. It never
replaces an active or candidate certificate record.

### `install`

```json
{"actor":"operator-17","anchor_epoch_id":"sha256:<64-lowercase-hex>","broker_ca_pem_b64":"<standard-base64-of-PEM-bytes>","broker_uri":"mqtts://broker.example:8883","client_cert_pem_b64":"<standard-base64-of-PEM-bytes>","device_id":"ori-fw-7c9f2b3a","kind":"install","provision_seq":42,"reason":"initial-mqtt-enrollment","time_server":"time.example","v":1}
```

Bounds:

- decoded broker CA PEM: `1 .. 4095` bytes plus the receiver's terminating NUL;
- decoded client certificate PEM: `1 .. 4095` bytes plus terminating NUL;
- `broker_uri`: `mqtts://` plus a DNS host and optional numeric port, at most
  255 bytes; credentials, paths, queries, and fragments are forbidden;
- `time_server`: DNS host only, at most 255 bytes.

The private key is not an install field. Acceptance requires a pending key from
`create_csr`, an exact device and epoch match, valid X.509 and CA parsing, a
single client-certificate common name equal to `device_id`, and a public key
matching the pending private key.

Installation stages a candidate. It does not make that candidate active. Only
a completed TLS handshake and successful MQTT CONNACK may promote it. Until
promotion, the previously confirmed active record remains the fallback. A
failed candidate is durably marked rejected before fallback so reboot cannot
silently retry it.

If transport is revoked, a newly authorized install may stage a recovery
candidate. The revocation tombstone is cleared only after that candidate is
broker-confirmed and promoted.

### `revoke`

```json
{"actor":"operator-17","anchor_epoch_id":"sha256:<64-lowercase-hex>","device_id":"ori-fw-7c9f2b3a","kind":"revoke","provision_seq":43,"reason":"certificate-compromise","v":1}
```

Revocation withdraws MQTT transport only. It preserves the Layer 1 device key,
approved anchor, command key and high-water mark, telemetry counters, signed
evidence buffer, and `provision_seq`.

### `status`

Status is a lower-privilege read, but it still requires a
provisioning-authority signature so an attached transport cannot turn the
device into an unauthenticated inventory oracle.

```json
{"actor":"operator-17","anchor_epoch_id":"sha256:<64-lowercase-hex>","device_id":"ori-fw-7c9f2b3a","kind":"status","request_id":"inventory-20260723-01","v":1}
```

`status` carries no `reason`, changes no trust, consumes no `provision_seq`, and
performs no persistent write. `request_id` is a non-empty fleet identifier of
at most 64 bytes used only to correlate the signed response. Replaying a status
request may repeat the same public response and cannot change state.

## Device-Signed Responses

Responses are signed by the device's Layer 1 Ed25519 key over the exact
canonical response object. The issuer MUST verify that signature against the
eligible anchor before issuing a certificate or trusting status: the active
approved anchor for CSR/installation, or the retained formerly active anchor
for post-revocation status/withdrawal.

### CSR response

```json
{"response":{"anchor_epoch_id":"sha256:<64-lowercase-hex>","csr_pem_b64":"<standard-base64-of-PEM-bytes>","device_id":"ori-fw-7c9f2b3a","kind":"csr","provision_seq":41,"v":1},"signature":"ed25519:<base64-64-byte-signature>"}
```

The CSR's own P-256 signature proves possession of the pending transport key.
The Layer 1 wrapper proves which approved device and request produced it.

### Status response

```json
{"response":{"active_anchor_epoch_id":"sha256:<64-lowercase-hex>","active_certificate_sha256":"sha256:<64-lowercase-hex>","candidate_anchor_epoch_id":null,"candidate_certificate_sha256":null,"device_id":"ori-fw-7c9f2b3a","kind":"status","pending_csr":false,"request_id":"inventory-20260723-01","revoked":false,"v":1},"signature":"ed25519:<base64-64-byte-signature>"}
```

Each anchor or certificate field is either the exact string or `null`.
Certificate hashes cover the exact decoded PEM bytes. Status MUST NOT expose a
private key, pending-key bytes, NVS record bytes, Wi-Fi secret, command key, or
raw Layer 1 seed.

### Mutation result

After a request passes grammar, device binding, and signature verification, the
device may return:

```json
{"result":{"anchor_epoch_id":"sha256:<64-lowercase-hex>","device_id":"ori-fw-7c9f2b3a","kind":"install","provision_seq":42,"v":1,"verdict":"accepted"},"signature":"ed25519:<base64-64-byte-signature>"}
```

`kind` is the request kind and `verdict` is one of the normative verdicts
below. A result is diagnostic evidence, not authority to assume the candidate
is active; only later signed status plus broker-side observation proves
promotion.

An implementation MUST NOT reflect untrusted request fields in a signed result
before grammar, device binding, and provisioning-authority signature pass.
Early failures may be returned as local adapter errors.

## Transport Binding

This contract does not prescribe USB framing or MQTT topic names. Adapter
contracts may do so without changing the signed objects above.

Every adapter MUST enforce:

- mutating requests and status requests are never retained;
- responses are never retained;
- MQTT delivery, when used, is QoS 1 and device-scoped with no wildcard
  subscription;
- the existing retained `ori/fw/<device_id>/provision` approval topic MUST NOT
  carry these requests;
- message fragmentation and maximum size are handled before verification;
- dropped input is observable;
- serial/USB attachment and TLS authentication remain routing/defence in depth,
  not substitutes for the provisioning-authority signature.

## Normative Verdicts

| Condition | Verdict | Consumes `provision_seq`? |
| --- | --- | --- |
| Fixed grammar or bounds violated | `malformed` | No |
| `device_id` names another device | `wrong_device` | No |
| Provisioning-authority signature fails | `bad_signature` | No |
| No eligible Layer 1 anchor exists for the requested operation | `anchor_not_approved` | No |
| `anchor_epoch_id` differs from the active approved epoch, or from the retained formerly active epoch permitted for `revoke`/`status` | `anchor_epoch_mismatch` | No |
| `provision_seq` is not above the persisted mark | `replayed` | No |
| `actor` or `reason` is absent/invalid for a mutation | `audit_required` | No |
| `kind` is not supported under v1 | `unsupported_operation` | No |
| PEM/base64/URI/time-server/X.509 material is invalid | `invalid_material` | Yes for `install` |
| No pending transport key exists for install | `no_pending_key` | Yes |
| Client certificate key does not match the pending key or CN differs | `key_certificate_mismatch` | Yes |
| Required storage write fails | `storage_failure` | See operation ordering |
| Operation is accepted into its defined state | `accepted` | Yes for mutations |

Malformed, unauthenticated, wrong-device, wrong-epoch, and replayed requests
MUST change nothing. A valid `install` that fails public-material validation is
spent so a payload rejected today cannot become valid after unrelated local
state changes.

## Runtime And Issuer Obligations

The runtime/provisioner MUST:

- authenticate the operator before signing;
- derive `anchor_epoch_id` from the same anchor held by the runtime and evidence
  store: active for issuance/install, or the retained formerly active anchor
  for post-revocation withdrawal/status;
- allocate one durable, strictly increasing `provision_seq` per device;
- record actor, reason, exact request digest, result, certificate fingerprint,
  and broker identity for mutations in append-only audit; status records actor
  and `request_id` but has no mutation reason;
- verify the Layer 1 signature and eligible epoch on CSR/status/results;
- issue a client certificate only for the public key proven by the CSR;
- never receive, request, reconstruct, or escrow the MQTT private key;
- never treat certificate issuance or MQTT connection as command authority.

The evidence store may record signed provisioning results as evidence. It is
not the certificate issuer and does not own transport-key policy.

## Firmware Obligations

Firmware MUST:

- verify fixed grammar before signature verification;
- verify the provisioning-authority signature before mutating state;
- bind issuance/install to its own `device_id` and active approved epoch, and
  bind post-revocation withdrawal/status to the retained formerly active epoch;
- apply the operation-specific crash ordering above;
- keep all key generation and certificate processing outside the Local
  Interlock path;
- use bounded static storage and declared input limits;
- wipe temporary private-key and decoded credential buffers;
- preserve already-signed buffered evidence across install, renewal, failure,
  and revocation;
- fail production MQTT closed on missing, revoked, malformed, or epoch-mismatched
  transport identity.

## Required Implementation Artifacts

Before an implementation may claim this contract:

- shared golden vectors for every request and device-signed response grammar;
- cross-language tests that the runtime signer and firmware verifier produce
  and accept byte-identical canonical bytes;
- replay and persistence tests proving `provision_seq` is independent from and
  preserved alongside other counters;
- failure-injection tests for every storage boundary, including tombstone-first
  revocation and candidate-rejection-before-fallback;
- tests for wrong device, wrong epoch, bad signature, malformed base64,
  invalid certificate, key/CN mismatch, private-key-field refusal, and
  unsupported operation;
- HIL evidence for initial issuance, live broker identity/ACL, failed renewal,
  successful promotion, restart persistence, revocation, expiry refusal, and
  preservation of buffered signed evidence.

The initial syntax, signature, and canonical negative-verdict corpus is
[vectors-v1.json](vectors-v1.json). Each negative is a
provisioning-authority-signed `create_csr` that changes exactly one field of
the accepted `create_csr` baseline (`provision_seq` 41): `wrong_device`
changes only `device_id`, `anchor_epoch_mismatch` changes only
`anchor_epoch_id`, and `replayed` changes only `provision_seq` to `1`. The
`replayed` case is evaluated against a device whose persisted high-water mark
is already 41, so a `provision_seq` of `1` is not above it; `wrong_device` and
`anchor_epoch_mismatch` are rejected before the freshness check regardless of
sequence. A signer and a firmware verifier reject these byte-identical inputs
with the same verdict. Its SHA-256 is
`1e6ee11c2df3633965650a2cab2380f31879fe6dd4babe62a813784395bc89a0`.
The disclosed test seeds are fixtures only and MUST NOT be used outside
deterministic tests. Implementing repositories must mirror the corpus
byte-for-byte and pin this digest; generating expectations from an
implementation under test is not conformance evidence.
