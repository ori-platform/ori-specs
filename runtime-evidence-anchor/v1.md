# Runtime evidence anchor v1

Status: Design target, pre-ratification. The derivation is implemented in
`ori-runtime` (`ori/security/evidence_anchor.py`) against the vectors here,
and independently in `ori-verity` (`src/anchor.rs`), which does not yet
consume these vectors.

A runtime signs its evidence with a key of its own, and every delivery envelope
it seals names that key and the epoch authorising it. This contract defines how
those two identifiers are derived.

Both are **derived, never configured**. They identify the key that signs
immutable evidence: a value an operator can set is a value that will be set
wrongly on some device, permanently, because a sealed envelope cannot be
rewritten.

## Relationship to device-provisioning/v1

[`device-provisioning/v1.md`](../device-provisioning/v1.md) defines
`anchor_epoch_id` for a **firmware** anchor. The construction here follows the
same shape and the same reasoning — an epoch names an exact trust proposition,
and changes when that proposition changes — but the inputs differ, because a
runtime has no firmware capability manifest and its key custody is materially
different from a sealed-flash device's.

The two are not interchangeable. A verifier MUST NOT compare a runtime epoch to
a firmware epoch, or assume one derivation produces the other.

## Canonical encoding

Both derivations canonicalise with the rule in
[`evidence-exchange/v1.md`](../evidence-exchange/v1.md): keys sorted by Unicode
scalar value, `","` and `":"` separators with no whitespace, RFC 8259 escaping
emitting `<`, `>`, `&`, `U+2028` and `U+2029` literally, and numbers within the
D-011 agreement zone.

## `key_id`

Names the evidence key generation, and is the `(evidence_device, key_id)`
selector a verifier uses.

`public_key_b64` is the RFC 4648 standard Base64 encoding, with padding, of the
32 raw public key bytes. Where a carrier holds the key as hex — anchor
registration carries `pubkey_hex` — the conversion is specified in
[`evidence-exchange/v1.md`](../evidence-exchange/v1.md) and MUST be applied
before deriving, never after.

```text
key_id = "sha256:" || lowercase_hex(SHA-256(canonical({
             "device_id":      <runtime device identity>,
             "public_key_b64": <base64 of the 32-byte Ed25519 public key>,
             "v":              1
         })))
```

For a fixed device identity it changes only when the key changes. `device_id` is
also an input, so two devices never share a `key_id` even if they somehow held
the same key material. A rotation therefore produces a new `key_id` while the
previous one stays resolvable, which is what lets an outgoing key remain
`verify_only` while its successor is `active`.

## `anchor_epoch_id`

Names the whole trust proposition: this device, holding this key, under this
custody posture, with these evidence capabilities.

```text
anchor_epoch_id = "sha256:" || lowercase_hex(SHA-256(canonical({
                      "capability_hash": <evidence capability hash, below>,
                      "device_id":       <runtime device identity>,
                      "posture":         <custody posture, below>,
                      "public_key_b64":  <base64 of the 32-byte Ed25519 public key>,
                      "v":               1
                  })))
```

It changes when the key, the posture, or the evidence capability profile
changes. Consumers MUST compare epochs by this identifier, never by arrival
order, row id, or timestamp.

## Evidence capability profile

The capability input is a small, release-owned document describing only
trust-relevant properties.

It is deliberately **not** a hash of the runtime's configuration, skills, or
general capabilities. Those change for reasons unrelated to trust, and hashing
them would mint a new epoch — invalidating cross-store agreement — every time an
operator edited something that has no bearing on whether the evidence can be
believed.

```text
capability_hash = "sha256:" || lowercase_hex(SHA-256(canonical({
                      "artifact_purposes":       [<sorted key purposes the runtime verifies>],
                      "chain_protocol":          "ori.evidence.v2",
                      "firmware_freshness_verified": <bool>,
                      "signing_alg":             "ed25519",
                      "v":                       1
                  })))
```

| Field | Meaning |
| --- | --- |
| `chain_protocol` | Schema version of the chain this runtime emits. |
| `signing_alg` | Algorithm the device key signs with. |
| `firmware_freshness_verified` | Whether Layer 1 freshness is **atomically verified**, not merely signed. A runtime that records supplied coordinates without validating them against confirmed registration and epoch state MUST report `false`. |
| `artifact_purposes` | Key purposes this runtime can verify. MUST be sorted, MUST contain no duplicates, and MUST be drawn from the closed purpose vocabulary in [`evidence-exchange/v1.md`](../evidence-exchange/v1.md). An unsorted, duplicated, or unknown entry would produce a distinct epoch without a distinct capability, so a producer MUST refuse to derive from one and an authority MUST reject it. |

`firmware_freshness_verified` is in the epoch on purpose. A runtime that gains
atomic freshness verification is a materially different trust proposition, and
an authority should see that as a new epoch rather than as the same device
quietly becoming more trustworthy.

## Custody posture

| Value | Meaning |
| --- | --- |
| `software_wrapped` | An Ed25519 private key encrypted at rest on a general-purpose operating system, under an installation secret held outside the key file. The key is exportable by anyone with the secret and sufficient host access. |
| `sealed_flash` | As defined in `device-provisioning/v1.md`. Not applicable to a runtime. |
| `hardware_key` | As defined in `device-provisioning/v1.md`. Requires hardware-backed non-exportability. |

A runtime storing its key as an encrypted file MUST report `software_wrapped`.

Filesystem or block-device encryption strengthens the deployment posture and
does **not** promote the value. The claim is about key custody — whether the
private key can be extracted by a party with host access — and an encrypted
mount that is mounted does not change that answer. Promoting it would overclaim
non-exportability inside an artifact a third party may rely on.

## Vectors

[`vectors/runtime-anchor.json`](vectors/runtime-anchor.json).

An implementation passes when it reproduces `key_id`, `capability_hash` and
`anchor_epoch_id` for each case. The cases include changes to the key, the
posture and each capability field, so an implementation that ignores an input
fails rather than silently agreeing on the default case.

Verity MUST reproduce these derivations before the exchange is called end-to-end
conformant: an authority that cannot recompute the epoch a device claims cannot
check that the device is the one it registered.

The exchange vectors in
[`evidence-exchange/vectors/`](../evidence-exchange/vectors/) are generated from
these derivations, so the two contracts agree by construction rather than by
inspection. `receiver-state/anchor-quarantine.json` covers the quarantine
invariant, which is not reachable through a conforming wire artifact.

Recomputation is possible because anchor registration carries the complete
`capability_profile`, per `evidence-exchange/v1.md`. That is what makes the
derivation a check rather than a declaration -- an epoch a device merely asserts,
with the inputs withheld, would be exactly the circular trust this contract
exists to remove.
