# Gateway API v2

> Status: maturity `draft`; compatibility `amendable`; adoption: producer
> (runtime) `implemented-unreleased`, `unassessed`, gateway
> `implemented-unreleased`, `unassessed`; proof: end-to-end `none`, HIL
> `none`, production `none`. Record:
> [status/gateway-api/v2.json](../status/gateway-api/v2.json).


This contract defines the MQTT boundary between `ori-runtime` and `ori-gateway`.
It covers four message families:

- Tier 3 reasoning request/response, used when runtime escalates reasoning to a LAN gateway.
- Runtime data export request/response, used by the gateway to generate reports and sync bounded runtime-owned data.
- Outbound evidence carriage, used by a runtime to hand end-to-end signed artifacts to its durable courier.
- Inbound evidence delivery, used by the gateway to carry authority artifacts back to the runtime that produced the evidence.

Cloud reasoning, when used, is a gateway backend. The runtime never sends
provider-specific cloud requests and never depends on cloud provider SDKs for
this contract.

The gateway must not read runtime SQLite files directly. Runtime owns data semantics;
gateway owns product/reporting behavior.

## Transport

- Protocol: MQTT
- Broker: `gateway.broker_url`
- Pattern: request/response with correlation by `request_id`
- Runtime export responses are read-only, device-scoped, bounded, and paginated.
- HTTP export endpoints are not part of the runtime/gateway boundary.

Gateway serves only configured runtime devices (`gateway.device_ids`). Reasoning
may use the `ori/+/reasoning/request` filter internally, but runtime heartbeat
and Tier C enrichment handlers subscribe per configured device. For runtime data
exports, the gateway publishes a request to the target device's export request
topic and subscribes to `ori/+/export/response/+` or the specific response topic
for the request.

The device owns the `ori/{device_id}/...` namespace. The gateway owns only its
site-level health topic. Production broker ACLs must enforce the same boundary.

## LAN Tier C Reply Relay

This amendable v2 message family carries a runtime-owned proposal projection
to the gateway and a customer application's reply back to the runtime.
[lan-app-api/v1](../lan-app-api/v1.md) defines pairing, the application
session and the per-read runtime disclosure check. This carriage does not admit an approval.
The existing runtime [tier-c-approval/v1](../tier-c-approval/v1.md) admission
remains the only path to an approved physical Tier C action. All four LAN topics use
QoS 1, are not retained, and bind `device_id` to their topic segment.
They always require the current runtime-gateway HMAC secret and a valid `auth`
envelope, even if a deployment disables optional reasoning authentication.
If the secret or its freshness/replay state is unavailable, LAN disclosure and
reply relay refuse closed. The signer and signing-input correlation are:

| Direction | `message_type` | `request_id` in HMAC input | Signed by |
| --- | --- | --- | --- |
| Runtime → gateway proposal | `lan_proposal` | `proposal_id` | Runtime |
| Gateway → runtime reply | `lan_customer_reply` | `proposal_id` | Gateway |
| Gateway → runtime disclosure request | `lan_disclosure_request` | `request_id` | Gateway |
| Runtime → gateway disclosure response | `lan_disclosure_response` | `request_id` | Runtime |

All use the existing [Heartbeat Auth Envelope](#heartbeat-auth-envelope)
canonical signing input over the complete payload with `auth` removed, with
the topic's `device_id`, this table's message type and correlation value.
Verification, topic binding, freshness and replay checks precede reading
authority-bearing fields or changing state. A previous secret may verify
within the existing rotation window but never signs new LAN messages.
Each LAN envelope's replay key is the standard `message_type`, `device_id`,
`request_id`, `signed_at_ms`, `signature` tuple in
[Envelope Freshness and Replay](#envelope-freshness-and-replay); the table above
defines the correlation value used as `request_id` for each family.
The JSON blocks below show member shape; placeholder signatures and digests
are not conformance vectors.

A proposal publication on `ori/{device_id}/lan/proposal` has
`message_type: lan_proposal` in the normal authenticated envelope:

```json
{
  "v": 1,
  "message_type": "lan_proposal",
  "device_id": "edge-01",
  "site_id": "site-a",
  "proposal_id": "AB12CD34",
  "operation": "upsert",
  "created_at_ms": 1787000000000,
  "expires_at_ms": 1787000030000,
  "summary": "Open protected circuit",
  "authority_snapshot_digest": "sha256:...",
  "auth": {
    "scheme": "hmac-sha256",
    "signed_at_ms": 1787000000000,
    "signature": "hmac-sha256:..."
  }
}
```

The closed `operation` vocabulary is `upsert` and `close`. An `upsert`
names a proposal already committed durably by the runtime; a `close`
removes it from the gateway view. The gateway cannot create or extend a
proposal. The runtime limits `summary` to 256 UTF-8 bytes. The gateway
discards an expired or mismatched projection, or one whose summary exceeds
256 UTF-8 bytes; it never truncates a summary or infers an approval from it.
The summary is display text and contains no secret, phone, credential or
subordinate identifier. `authority_snapshot_digest`
is over the exact Profile 2 canonical snapshot bound by tier-c-approval/v1;
it is not
authority supplied by the gateway.
For LAN-exposed proposals, the runtime durably remembers each used
`proposal_id` for the full identity epoch, including across restart and
closure. It must redraw a colliding ID before committing a new proposal;
it never reuses one in that epoch. A failure to retain this nonreuse state
refuses new LAN proposal publication. This prevents a previously signed
reply from naming a later proposal under the same epoch, even when the
authority snapshot bytes are identical.

A reply publication on `ori/{device_id}/lan/reply` has
`message_type: lan_customer_reply` in the normal authenticated envelope:

```json
{
  "v": 1,
  "message_type": "lan_customer_reply",
  "device_id": "edge-01",
  "site_id": "site-a",
  "identity_epoch": "<canonical padded Base64 of runtime epoch>",
  "proposal_id": "AB12CD34",
  "authority_snapshot_digest": "sha256:<64 lowercase hex>",
  "reply": "yes",
  "client_nonce": "<canonical padded Base64 of 16 random bytes>",
  "app_spki_b64": "<RFC 4648 padded Base64 of client certificate SPKI DER>",
  "app_signature": "<RFC 4648 padded Base64 Ed25519 signature>",
  "auth": {
    "scheme": "hmac-sha256",
    "signed_at_ms": 1787000001000,
    "signature": "hmac-sha256:..."
  }
}
```

`reply` is exactly `yes` or `no`. The gateway commits the HTTP write
nonce and a durable outbox entry before returning `queued` to the
application. A QoS PUBACK alone is not runtime admission. If the gateway
cannot commit, it returns `relay_unavailable`, never `queued`. Retries
republish the same logical reply in a newly signed HMAC envelope while
preserving the original application signature and nonce.

The HMAC binds the topic's device, site, proposal, snapshot digest, application proof and
all other payload fields by the existing envelope construction
(`request_id` is `proposal_id`). The runtime applies the Payload Member
Rule and verifies this envelope, then verifies the application signature
against the forwarded SPKI and maps that key to an active credential in its
own registry. It checks the current identity epoch, proposal cutoff and
requires the application-signed `authority_snapshot_digest` to equal the open
proposal's recorded snapshot digest **inside durable admission**.
A valid HMAC, backend grant or product role cannot substitute for an active
runtime credential. A duplicate `(proposal_id, app_spki_b64, client_nonce)` is idempotent;
same nonce with different reply bytes is refused. A `no` is recorded as
refusal and never enters approval admission. An expired, closed or
snapshot-mismatched proposal is refused under tier-c-approval/v1 and
cannot be reopened by this carriage.

The gateway may show a relay state separately from the runtime's later
decision, but MUST NOT display `approved` based on `queued`, PUBACK or
its own role check. Non-approval decisions retain the runtime decision-log
vocabulary. Their signed evidence representation is pending
[#205](https://github.com/ori-platform/ori-specs/issues/205); this
message family does not define a second evidence authority kind.

Before disclosing any proposal metadata, the gateway sends one check per
HTTP proposal read for the presented TLS client key and its bounded scope.
The scope is the sorted unique array of at most 100 currently projected
`proposal_id` values, each matching `^[A-Z0-9]{8}$`. An empty array yields
an empty HTTP result without a runtime request or proposal count. A request on
`ori/{device_id}/lan/disclosure/request` has exactly `v` (integer 1),
`message_type` (`lan_disclosure_request`), `device_id`, `site_id`,
`proposal_ids`, `app_spki_sha256`, `request_id` and `auth`. The gateway mints a
fresh `request_id` of 1 to 128 ASCII characters from `[A-Za-z0-9._-]`.
The digest is lowercase `sha256:` plus 64 hex characters over the exact
RFC 8410 Ed25519 DER SPKI presented in the authenticated TLS handshake.
To look up a `lan_ed25519` credential in
[tier-c-approvers/v1](../tier-c-approvers/v1.md), the runtime removes only
the literal `sha256:` prefix and compares the remaining 64 lowercase hex
characters to its stored SPKI digest; it never hashes the text of the digest
or accepts a differently encoded key.
The gateway HMAC authenticates the request and binds all these members.
For example, the request shape is:

```json
{
  "v": 1,
  "message_type": "lan_disclosure_request",
  "device_id": "edge-01",
  "site_id": "site-a",
  "proposal_ids": ["AB12CD34"],
  "app_spki_sha256": "sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "request_id": "disclosure-1",
  "auth": {
    "scheme": "hmac-sha256",
    "signed_at_ms": 1787000001000,
    "signature": "hmac-sha256:..."
  }
}
```

The runtime answers on `ori/{device_id}/lan/disclosure/response/{request_id}`
with exactly `v` (integer 1), `message_type`
(`lan_disclosure_response`), `device_id`, `site_id`, `proposal_ids`,
`app_spki_sha256`, `request_id`, `allowed_proposal_ids`, `identity_epoch` and `auth`.
The result array is a sorted unique subset of the requested IDs. The runtime
includes an ID only when its registry is readable, that exact key maps to an
active LAN credential for the signed site and current epoch, the credential's
enrolment sequence is within that proposal's cutoff, and that proposal is
still open. `identity_epoch` is the runtime's current canonical padded
Base64 epoch only when the allowed array is nonempty; otherwise it is JSON
`null`. With an unreadable registry the runtime returns an empty array and
`null`. The response is bound by the runtime HMAC. The gateway accepts only
the first verified response matching every echoed field, a subset result,
the response topic and its pending request. It drops and logs an unverified
response, including a malformed, oversized, stale or unauthenticated one,
and keeps the request waiting. A forged message on the response topic cannot
complete the exchange. Duplicates and unrequested responses are discarded.
The gateway's 2-second monotonic bound begins when it publishes the request;
no received message, verified or not, extends that bound. If no matching
verified response arrives within the bound, the gateway ends the request and
discloses nothing. The runtime verifies a disclosure request before reading
its registry or publishing any response, including a deny. It drops and logs
a request whose envelope is unverified for any reason, including a
verification fault, freshness or replay refusal. The request's `device_id`
must equal the topic's device segment independently of signature verification,
and the signature must verify under the expected `device_id` and `request_id`
independently of the topic check. Neither check may depend on the other
having run. Neither an allowed ID nor a projection is an
eligibility cache. Every proposal read repeats the exchange, and a later
reply undergoes a separate durable runtime admission check. Both sides bound
the in-flight request count and rate under Payload Volume; an over-limit
request denies disclosure without queuing it. A timeout vector and matched,
denied and mismatched-response cases are required before adoption.
For example, the response shape is:

```json
{
  "v": 1,
  "message_type": "lan_disclosure_response",
  "device_id": "edge-01",
  "site_id": "site-a",
  "proposal_ids": ["AB12CD34"],
  "app_spki_sha256": "sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "request_id": "disclosure-1",
  "allowed_proposal_ids": ["AB12CD34"],
  "identity_epoch": "AAECAwQFBgcICQoLDA0ODw==",
  "auth": {
    "scheme": "hmac-sha256",
    "signed_at_ms": 1787000001100,
    "signature": "hmac-sha256:..."
  }
}
```

## Payload Size

Every payload this contract carries between a runtime and a gateway has a
maximum length in bytes, set by its topic. A payload's length is the length of
the MQTT application message exactly as delivered, before it is decrypted,
decoded or read. Size is the first check, because it bounds the cost of every
check after it.

| Topic | Direction | Maximum (bytes) | Derived from |
| --- | --- | --- | --- |
| `ori/gateway/health` | Gateway -> Runtime | 16384 | Fixed members and the optional `webhook_bridge` block, a few hundred bytes, with room for members this version adds. |
| `ori/{device_id}/runtime/heartbeat` | Runtime -> Gateway | 65536 | Fixed members, the closed `degradation_reasons` tokens, and `active_triggers`, which a runtime fills only as far as fits (below). |
| `ori/{device_id}/reasoning/request` | Runtime -> Gateway | 262144 | The prompt, which a skill renders, and at most ten history points. |
| `ori/{device_id}/reasoning/response` | Gateway -> Runtime | 262144 | The reasoning text and the fixed members. |
| `ori/{device_id}/tier_c/enrichment/request` | Runtime -> Gateway | 262144 | The operator message and the bounded history window. |
| `ori/{device_id}/tier_c/enrichment/response` | Gateway -> Runtime | 262144 | The advisory text members. |
| `ori/{device_id}/export/request` | Gateway -> Runtime | 16384 | Fixed members and the export's `params`. |
| `ori/{device_id}/export/response/{request_id}` | Runtime -> Gateway | 4194304 | One page of export items, encrypted and Base64-encoded where the export is sensitive. |
| `ori/{device_id}/evidence/outbound` | Runtime -> Gateway | 1572864 | An artifact of at most 1048576 bytes (evidence-transport/v2), 1398104 bytes in Base64, and the envelope. |
| `ori/{device_id}/evidence/outbound/ack` | Gateway -> Runtime | 16384 | Fixed members. |
| `ori/{device_id}/evidence/inbound` | Gateway -> Runtime | 1114112 | An authority artifact of at most 1048576 canonical bytes, which the gateway publishes in canonical form so the artifact occupies exactly those bytes, and `device_id`, `artifact_type` and `auth`. The artifacts carry strings no contract bounds, such as an epoch confirmation's `actor`, so the bound is this hop's, below. |
| `ori/{device_id}/evidence/inbound/ack` | Runtime -> Gateway | 16384 | Fixed members. |
| `ori/{device_id}/lan/proposal` | Runtime -> Gateway | 16384 | One bounded proposal summary and fixed envelope members. |
| `ori/{device_id}/lan/reply` | Gateway -> Runtime | 16384 | One Ed25519 SPKI, signed reply and fixed envelope members. |
| `ori/{device_id}/lan/disclosure/request` | Gateway -> Runtime | 16384 | One key digest, at most 100 proposal IDs and a correlation ID. |
| `ori/{device_id}/lan/disclosure/response/{request_id}` | Runtime -> Gateway | 16384 | A subset of at most 100 proposal IDs and correlation fields. |

Every row counts its routing members at their bounds. A runtime refuses at
load a `device.id` outside the pattern
[runtime-config/v2](../runtime-config/v2.md) declares for it,
`^[A-Za-z0-9._-]{1,128}$`, so a `device_id` on this hop is at most 128 ASCII
characters, 128 bytes in every encoding. A gateway configuration may still
name an identity outside it, as gateway-config/v2's compatibility rule allows,
but no conforming runtime answers to one, so these maxima hold wherever a
conforming runtime is on the other end. A `request_id` is 1 to 128 characters
from the same set. The runtime mints one of that form for reasoning and
enrichment, the gateway mints one for an export request, and a runtime refuses
an export request whose `request_id` is outside it, unanswered, as it refuses
an oversized payload. A `proposal_id` is the eight characters
[evidence/v3](../evidence/v3.md) fixes.

A receiver compares a payload's length with its topic's maximum before it
parses, decodes, decrypts or verifies anything. A payload longer than the
maximum is refused as `payload_too_large`. It is not answered, since none of
its members can be relied on, and it changes no state. The refusal is recorded
with the topic family and the payload's size class, the least power of two not
below its length, and never with its contents or a device identifier. A topic
family is a row of the table above, named by its topic with the
`{device_id}` and `{request_id}` segments left as written. A
payload at most the maximum goes on to the
[Payload Member Rule](#payload-member-rule).

Where an implementation offers a setting for a topic's maximum, a deployment
may configure a lower maximum, never a higher one, and never below 4096
bytes. The evidence topics, `ori/{device_id}/evidence/outbound` and
`ori/{device_id}/evidence/inbound`, are never lowered: a courier cannot shrink
a conforming artifact, and an inbound artifact refused for size would be
redelivered without end. A configured value above the table or below that floor is refused when
the configuration is loaded. A producer sizes and pages against the maximum in
force for the topic it publishes, its own configured value where one is set,
so a deployment that lowers a receiver's maximum lowers the producer's to
match; a receiver that applies a lower maximum than its producer refuses
conforming payloads above it.

A producer never publishes a payload longer than its topic's maximum. When
content would not fit:

- **A reasoning or enrichment request** is not published. The runtime treats
  the escalation or the enrichment as unavailable at once, without waiting out
  its timeout.
- **A reasoning or enrichment response** is replaced by the family's error
  response, with `error` `response_too_large`, so the runtime does not wait
  for an answer that will not come.
- **An export page** holds as many items as keep the payload, after encryption,
  encoding and `auth`, within the maximum, and at least one;
  `next_page_token` continues from the first item not returned. An item that
  does not fit in a page by itself ends the export with an error response whose
  `error` is `item_exceeds_payload_maximum`, and the gateway does not request
  that page again.
- **A required reply** fits within 4096 bytes, the floor, so no permitted
  configuration refuses one: a reasoning, enrichment or export error
  response, encrypted where the export is sensitive; an acknowledgement; a
  runtime node heartbeat with no `active_triggers`; and the gateway heartbeat.
  An error response carries an `error` of at most 128 Unicode scalar values
  and no other free-form content: its routing, correlation, authentication and
  protocol members keep the values their family requires, and every other
  free-form string, such as `text`, `model` or the enrichment's optional
  strings, is empty or, where its family lets it, omitted. A heartbeat's `action_event_type` is at most 64 ASCII
  characters.
- **A runtime node heartbeat** lists in `active_triggers` at most 64 names, in
  the order the runtime holds them, and only those that keep the payload within
  its maximum; it never omits another member to make room. A consumer reads the
  number of names as a lower bound on the triggers active, never as their count.
- **An outbound evidence carriage** never exceeds its maximum for a conforming
  artifact, and an artifact larger than evidence-transport/v2 admits is refused
  there.
- **An inbound evidence message** is published as the canonical JSON of the
  whole payload, `auth` included, under the canonicalisation of
  [Artifact Bytes](#artifact-bytes), so the artifact occupies exactly its
  canonical bytes. This bounds size only: a receiver neither checks it nor
  relies on it, and Artifact Bytes is unchanged.
- **An inbound authority artifact** whose canonical bytes exceed 1048576 cannot
  be carried on this hop, as an outbound artifact of that size cannot. The
  gateway's staging admits no artifact it could not carry, so a response
  carrying one is a response carrying an authority artifact the gateway cannot
  durably stage, which evidence-transport/v2 already decides: an unrecognised
  outcome for that attempt, the queue entry retained and backed off, the
  artifacts already staged staying staged, and delivery reported degraded. No
  such artifact is ever published to the runtime. An authority that keeps
  returning one holds that entry at the head of that device's lane, as any
  unrecognised response does, and evidence-transport/v2 keeps the device's
  other lane and every other device moving.

A broker's own message size limit SHOULD be at most the largest maximum above,
so an oversized message is dropped before it reaches either side.

### Size vectors

[vectors/payload-size-v2.json](vectors/payload-size-v2.json) holds this
section's cases. Its SHA-256 is
`c3359f38734501206b26735a25e117a26bb53bd74b6e9cfb526363ace72246ef`.

Each case names a topic, a configured maximum or `null`, a construction, a
length, the SHA-256 of the bytes the construction gives at that length, and a
verdict: `admitted`, when the length is within the maximum in force and the
Payload Member Rule decides what follows; `payload_too_large`; or
`configuration_refused`, when the configured maximum is above the table or
below the floor. The
constructions are:

- `json_object`: the bytes `{"pad":"`, then `a` repeated to make up the
  length, then `"}`;
- `invalid_utf8`: the byte `0xFF` repeated.

For every topic in the table the corpus holds a `json_object` payload at the
maximum, one byte over it, and four times it; an `invalid_utf8` payload one
byte over the maximum, refused for its size before anything else; a
configured maximum half the table's, with payloads at it and one byte over;
a configured maximum one byte above the table's, refused; and one a byte
below the floor, refused. For the evidence topics, which are never lowered,
the configured half is refused as well.

Its `paging` cases give an export page's fixed bytes (the envelope, `auth`, and
encryption and encoding overhead), each item's bytes, and the maximum, and the
pages the export rule above produces: each page's item count and the index its
`next_page_token` continues from, ending in `item_exceeds_payload_maximum`
where an item does not fit in a page by itself.

Its `envelopes` cases build the evidence payloads at their bounds: a
`device_id` of 128 characters, the longest `artifact_type` and
`reason` each topic's vocabulary holds, `signed_at_ms` and the acknowledgement
time at 9007199254740991, a 64-digit signature, and, on the evidence topics,
an artifact at 1048576 bytes. Each case names its encoding: `canonical`, the
canonical JSON of the whole payload, or `escaped`, sorted keys with no
whitespace and every character outside ASCII written as a `\u` escape. Each
gives the length and SHA-256 of the bytes and the verdict under the table. The
inbound evidence message is given both ways, admitted in canonical form and
refused when escaped, which is why its producer rule fixes the form.

Its `replies` cases build every required reply at its bounds, escaped, against
a configured maximum at the floor: `device_id` and `request_id` at 128
characters, an `error` of 128 copies of U+1F600, every integer at
9007199254740991, the longest `export_type`, and, for the runtime node
heartbeat, `status` `critical`, every `degradation_reasons` token and an
`evidence` block with a 64-character `action_event_type`. The encrypted export
error carries its plaintext as AES-GCM ciphertext with a 16-byte tag and a
12-byte nonce, both Base64; the gateway heartbeat holds the longest `status`
and `provider` and the widest number in every numeric member. Each is admitted
at the floor, and so is each acknowledgement the `envelopes` cases build.

`scripts/generate-gateway-payload-size-vectors-v2` reproduces the file byte for
byte. `scripts/check-gateway-payload-size-vectors-v2` shares no code with it:
it reads the table, the verdicts and the constructions from this section, the
`device_id` bound from runtime-config/v2's schema, and the vocabularies from
this contract, builds every payload itself and compares its digest, and
confirms each verdict and the coverage above.

## Payload Volume

Authentication proves which side sent a message, not that the sender is
working correctly. Neither side lets the other's message volume exhaust it.

For each topic it receives, a receiver bounds the rate at which it processes
messages and the durable state any message may add. Beyond either bound it
drops the message without reading past the size check, keeps no state for it,
and counts the drop. A message that answers nothing the receiver holds adds
no state: a response with no pending request, an acknowledgement for nothing
sent, an export request beyond the rate the runtime serves. The values are each
implementation's, chosen for its host, and a peer can never raise them: no
payload, envelope or configuration the other side controls changes a bound.

Size and volume refusals are reported in each side's own health. A gateway
reports them in its operational posture, below. A runtime reports them under
[runtime-health/v4.md](../runtime-health/v4.md) once that contract names the
field; until it does, a runtime records each refusal in its own log, by topic
family, and reports nothing else about them.

## Payload Member Rule

Every payload this contract carries between a runtime and a gateway, on every
topic and in either direction, is admitted under this rule, once
[Payload Size](#payload-size) has admitted its length, before any member of
it is read: before an envelope is verified, before a signing input is rebuilt,
and before the payload is routed. Where a payload carries an encrypted member,
the plaintext it decrypts to is a JSON text in its own right, and is admitted
under the same rule before any member of it is read. A string that encodes
bytes, such as `artifact_b64`, is a string to this rule; the bytes it decodes
to are governed by the contract that defines them.

Two readers that resolve one byte sequence differently give one signature two
meanings. A reader that keeps the last of two same-named members and a reader
that keeps the first see different payloads under one valid signature, and a
decoder that matches member names without regard to case reads `STATUS` as
`status` where an exact reader ignores it. The rule leaves each payload one
reading.

A receiver refuses a payload when any row below applies. The member rows,
`duplicate_member` and `case_variant_member`, apply to every object at every
depth, including objects inside arrays. When several rows
apply, the earliest row in the table names the reason, wherever in the payload
each violation sits, so every receiver names the same reason whatever order its
parser meets them in.

| Reason | Refused when |
| --- | --- |
| `invalid_unicode` | The payload is not valid UTF-8, or a name or value holds a lone or misordered surrogate escape. |
| `malformed_json` | The payload does not begin, after optional JSON whitespace (RFC 8259), with one complete JSON value: it is empty, ends early, or breaks the RFC 8259 grammar before that value ends. `NaN`, `Infinity` and `-Infinity` are not JSON values. |
| `nesting_too_deep` | An object or array sits deeper than 32, the top-level value at depth 1. |
| `trailing_data` | Anything other than JSON whitespace (RFC 8259) follows that value. |
| `duplicate_member` | Two members of one object have identical names, compared after unescaping, code point by code point, with no normalisation. |
| `case_variant_member` | Two names in one object, or a name and a member the contract defining that object names for it, differ but are equal under the closed fold. |
| `not_an_object` | That value is not an object: every payload this contract carries is one. |

The terms in the table mean exactly this:

- **Valid UTF-8** is RFC 3629 UTF-8: no overlong form, no encoded surrogate,
  nothing above U+10FFFF. The whole payload is judged, bytes after the first
  value included.
- **JSON whitespace (RFC 8259)** is four characters: space, horizontal tab,
  line feed and carriage return, and nothing else a language library may call
  whitespace. A byte order mark is not JSON whitespace, so a payload that
  begins with one does not begin with a JSON value.
- **A surrogate escape** is a `\u` escape naming a code unit from D800 to DFFF,
  in either case of hex digit. An escape from D800 to DBFF is lone unless the
  next six characters of the same string are an escape from DC00 to DFFF, and
  an escape from DC00 to DFFF is lone unless it completes such a pair. A
  completed pair is one scalar value. An escape cut short names no code unit
  and breaks the grammar. Every name and value is judged from the
  start of the payload to the end of its first value, or to the point where it
  breaks the grammar if that comes first, so a string that ends, or a payload
  that stops, after an unpaired escape holds a lone one.
- **Depth** counts objects and arrays only. The top-level value is at depth 1,
  and an object or array inside another is one deeper than its container. A
  scalar adds no depth, so thirty-two nested arrays around a number are
  admitted. Depth is judged within the first value; whatever follows it is
  trailing data, however deep. A grammar break anywhere in the first value
  outranks its depth, so a receiver scans the first value to its end past the
  bound. It counts depth rather than recursing: a stack of one entry per open
  container, bounded by the payload's size, is enough.
- **The first value** ends where the RFC 8259 grammar ends it, so a top-level
  `01` is the value `0` followed by trailing data, while `[01]` breaks the
  grammar inside the array. A number takes every character that can continue
  it: a `.` after its integer part begins a fraction and an `e` or `E` after its
  integer or fraction part begins an exponent, and one begun and not completed
  breaks the grammar. So `1.`, `1e` and `1e+` are `malformed_json` at any
  depth, while `1.5.` and `1e5.` are a number followed by trailing data. The
  member rules, `duplicate_member` and
  `case_variant_member`, judge the first value only.
- **Unescaping** turns every escape into the scalar value it names, a completed
  surrogate pair into one, so `"st\u0061tus"` and `"status"` are one name.
- **The closed fold** maps each code point of a name on its own: each ASCII
  capital letter to its small letter, U+017F LATIN SMALL LETTER LONG S to `s`,
  U+212A KELVIN SIGN to `k`, and every other code point to itself. Two names
  are equal under it when their mapped sequences are identical. Unicode simple
  case folding is not used, because it changes with the Unicode version each
  toolchain ships, and a Go and a Python receiver would then fold some names
  differently. Every member name this contract defines is ASCII, and U+017F
  and U+212A are exactly the non-ASCII code points that Go's `encoding/json`
  struct decoder matches to an ASCII name on go1.26.1 (Unicode 15.0.0), as
  ori-gateway's sweep over every scalar value shows. `ß`, `ẞ`, `ς`, `σ`, `Σ`,
  `İ` and `ı` therefore compare exactly.
- **A member the contract defining that object names for it** is, for every
  object of a payload, any key of any JSON example, or the backticked name in
  the first column of a row of a table whose first header cell is `Field`,
  which holds one such name per row, in the sections the
  table below gives the payload's topic, and any key of the JSON example under
  [Envelope Members](#envelope-members). A name written anywhere else, in
  backticks or in words, is not one, and no member of the payload is read to
  choose the set. A section the table names is its own body only; "with its
  subsections" adds every section beneath it, and "X, under Y" names the
  section X whose direct parent is Y. The set is decidable rather than
  complete: members are read by exact name, so a variant of a member it leaves
  out is an unknown member and is never read as that member.

| Topic | Sections that give the members |
| --- | --- |
| `ori/{device_id}/reasoning/request` | Tier 3 Reasoning Request Payload |
| `ori/{device_id}/reasoning/response` | Tier 3 Reasoning Response Payload |
| `ori/gateway/health` | Heartbeat Payload |
| `ori/{device_id}/runtime/heartbeat` | Runtime Node Heartbeat Payload, with its subsections |
| `ori/{device_id}/export/request` | Runtime Export Request Payload, with its subsections; Supported Export Types, with its subsections |
| `ori/{device_id}/export/response/{request_id}` | Runtime Export Response Payload; Supported Export Types, with its subsections |
| `ori/{device_id}/tier_c/enrichment/request` | Tier C Enrichment Request Payload |
| `ori/{device_id}/tier_c/enrichment/response` | Tier C Enrichment Response Payload |
| `ori/{device_id}/evidence/outbound` | Outbound Evidence Carriage |
| `ori/{device_id}/evidence/outbound/ack` | Outbound acknowledgement |
| `ori/{device_id}/evidence/inbound` | Envelope, under Inbound Evidence Delivery |
| `ori/{device_id}/evidence/inbound/ack` | Durability and Retirement, under Inbound Evidence Delivery |
| `ori/{device_id}/lan/proposal` | LAN Tier C Reply Relay |
| `ori/{device_id}/lan/reply` | LAN Tier C Reply Relay |
| `ori/{device_id}/lan/disclosure/request` | LAN Tier C Reply Relay |
| `ori/{device_id}/lan/disclosure/response/{request_id}` | LAN Tier C Reply Relay |

Nothing else changes. A member whose name passes the rule and that a section
does not define stays tolerated wherever that section tolerates unknown
members, so additive compatibility holds. A receiver reads an admitted
payload's members by exact name only: a decoder that matches names in any
other way, such as by a case-insensitive option, does not conform even on a
payload this rule admits. The rule judges a number by the RFC
8259 grammar alone: its range and spelling stay with the section that reads it
and with `gateway-mqtt-canonical-json/v1`, and D-011 numeric admission is
unchanged, so `1e400` is a JSON value here.

A refused payload reaches no verifier, changes no state, and is recorded with
its reason. It is not answered: no member of it can be relied on, its
correlation identifier and device included, so a reply would name what the
payload may not have said. The seven reasons name that record and add nothing to
any reply vocabulary a section defines; an error envelope or acknowledgement a
section defines answers only a payload this rule admits. A producer MUST NOT
emit a payload this rule refuses. A gateway that carries an object it did not
author, as it carries an inbound `artifact` from the evidence authority,
applies the rule when it receives the object to the payload it would forward
carrying the object exactly as it received it, on that payload's topic, and
does not queue an object whose payload the rule refuses: it could not then
forward the object unchanged without emitting a payload this rule refuses.
Judging the object alone would not do, since the payload around it adds a
level of depth and the members its topic defines. Such an object is one the
gateway cannot durably stage, which evidence-transport/v2 already decides, as
it decides an artifact larger than this hop admits under
[Payload Size](#payload-size): the attempt is an unrecognised outcome, the
queue entry is retained and backed off, artifacts already staged stay staged,
delivery is reported degraded, and the object is never published to the
runtime. The gateway decides an object's routing before this rule, so a
malformed or misrouted object stays the unrecognised outcome it already was.

[`vectors/payload-members-v2.json`](vectors/payload-members-v2.json) carries
the payloads as exact bytes, each with the reason a receiver MUST name or the
admission it MUST give. Each case names the topic whose sections give its
defined members, or none, and the corpus lists every topic's defined members so
an implementation can compare its own with them.

## Envelope Freshness and Replay

These rules hold for every envelope this contract authenticates with the
runtime–gateway HMAC, in both directions: the gateway heartbeat, the runtime
node heartbeat, the reasoning, export and Tier C enrichment requests and
responses, the inbound evidence envelope and its acknowledgement, the
outbound acknowledgement, and all four LAN families (`lan_proposal`,
`lan_customer_reply`, `lan_disclosure_request`, `lan_disclosure_response`).
Every receiver applies them, the runtime and the
gateway alike, once the envelope's signature and its topic-device check hold
and before any side effect, a correlated error response included.

This section alone states what replay protection achieves. Every other
section names an envelope's key and refers here, and whatever this contract
says replay protection stops, it stops outside the cases
[Limits and later versions](#limits-and-later-versions) names.

The terms:

- **The receiver's clock** is the clock it reads, in milliseconds, when it
  verifies an envelope.
- **The skew** is the receiver's maximum clock skew, never negative; for the
  runtime, `gateway.auth.max_clock_skew_ms`.
- **An envelope's key** is its `message_type`, `device_id`, `request_id`,
  `signed_at_ms` and `signature`. The gateway heartbeat, whose `device_id` and
  `request_id` are empty, may leave those two out. A receiver holds a key with
  the envelope's signing time and the time it was received.
- **The replay floor** is a signing time in milliseconds, kept by the receiver
  for its current secret generation.

### Order of checks

An envelope signed at `signed_at_ms` and verified at clock `t`, under skew `S`
and floor `F`, is accepted only if every check holds, in this order. It is
refused for the first that fails:

| Order | Check | Reason |
| --- | --- | --- |
| 1 | `signed_at_ms` ≥ `t` − `S` | `stale_timestamp` |
| 2 | `signed_at_ms` ≤ `t` + `S` | `future_timestamp` |
| 3 | `signed_at_ms` ≥ `F` | `before_replay_floor` |
| 4 | its key is not held | `replay_detected` |

Every bound is inclusive. An accepted envelope's key is held from then on. A
family that records the key only once the envelope answers something
authenticates first and records later. It then makes checks 3 and 4 again when
it records, in one atomic step with recording, so a key dropped and a floor
raised in between are both seen. The key's receipt time is the time it was
authenticated. A recorded key is never un-recorded: a receiver that recorded it
and then did not act on the envelope still holds it, and the sender's next
attempt is newly signed, as [Senders](#senders) requires.

The reasons name a transport-authentication refusal in the receiver's logs and
counts. None is an evidence-artifact rejection, and none is proof that an
attack occurred: `before_replay_floor` most often means a restart or a clock
step.

### Retention

A held key may be dropped only once both hold:

- `t` > `signed_at_ms` + `S`, so the envelope is stale;
- `t` ≥ its receipt time plus `gateway.auth.replay_ttl_ms`, where the receiver
  has that setting.

`replay_ttl_ms` is a lower bound on retention from receipt and nothing more. A
shorter value cannot drop a key while its envelope still passes check 1, and a
longer one only keeps keys whose envelopes are already refused as stale. The
latest a key can be needed is `S` past its signing time, which is never more
than 2 × `S` past its receipt.

### The floor

- **A dropped key raises the floor.** Dropping a key raises `F` to at least its
  `signed_at_ms` + 1, in the same atomic step, so no verification sees the key
  gone and the floor not yet raised. A receiver whose memory is full may drop
  the held key with the smallest signing time, any one of several that share it,
  before its retention ends, by the same step, instead of refusing the new
  envelope.
- **The stored floor never falls,** except under [Recovery](#recovery).
- **At every start,** `F` becomes the greater of the floor the receiver stored,
  if any, and its clock at that start. A receiver that stores its floor stores
  its held keys with it, and keeps both across a restart; one that stores
  neither starts each run with no stored floor and no held keys, so from its
  clock. A restart discards every authentication not yet recorded.
- **Only a floor raised by a dropped key is stored,** never a clock reading. A
  stored floor is one past a time an accepted envelope was signed at, so a
  receiver whose clock ran fast at one start does not carry that error past its
  next start.

The start rule covers keys dropped while no floor was kept, for envelopes
signed before that start: after a fresh install, the first start after
upgrading from a release that kept none, a rollback to such a release and the
upgrade after it, and every restart of a receiver that stores no floor.
Because it takes the greater of the two values, a floor stored before a
rollback can never lower the floor at the next start. A start floor is not
stored, so it covers its own run only; see
[Limits and later versions](#limits-and-later-versions).

A raised skew is covered the same way. Every key dropped under the narrower
skew raised the floor past its envelope, so the wider skew readmits none of
them. A clock stepped back, live or across a start, is covered for every key
whose drop raised the stored floor, because the stored floor does not follow
the clock down.

### What the floor costs

- **Envelopes in flight across a start** are refused as `before_replay_floor`
  when they were signed before it. The sender's next attempt is newly signed.
- **A sender whose clock runs behind the receiver's** by `d`, which the skew
  admits up to `S`, signs below a start floor for up to `d` after the start.
  Its fresh attempts are refused until then, so a start can cost up to `d` of
  that sender's traffic and not just one retry. For gateway heartbeats that
  means `gateway_reachable` may be false for up to `d`, and Tier 3 escalation
  falls back as [Gateway Availability Check](#gateway-availability-check)
  describes. Tier D and every local deterministic path are unaffected.
- **A clock stepped back** below the floor refuses fresh envelopes until the
  clock passes it again.
- **An eviction** raises the floor past the evicted envelope, which may have
  been signed up to `S` ahead of the clock. Senders whose clocks run behind
  that envelope's signing time are then refused until their clocks pass it,
  across a restart too when the floor is stored. A gateway's floor covers
  every runtime it serves, so one runtime that fills its memory can raise the
  floor for all of them.

Whenever a receiver refuses an envelope as `before_replay_floor` while `F` >
`t` − `S`, it logs a warning naming `F` and `t`. It also shows the condition
in its own health, which it can do without hearing from the other party,
once its health names a field for it: a gateway in its operational posture,
and a runtime under [runtime-health/v4.md](../runtime-health/v4.md). Until
then its log is the only record.

### Recovery

A floor ahead of the clock is cleared in one of two ways:

- **Wait** until the clock passes it.
- **Rotate the secret.** The receiver may drop its stored floor and every held
  key, and discard every authentication not yet recorded, which leaves `F` at
  its clock, only in one atomic step with switching to a new secret generation,
  under new key material, in which no earlier secret verifies, including any
  configured previous secret. No verification under the retired generation
  commits after the switch. Nothing signed before it verifies after it, so the
  reset readmits nothing. A receiver cannot tell new key material from a retired
  secret brought back, so an operator MUST NOT bring back a secret retired by a
  rotation that reset the floor, in any later configuration, as the current
  secret or the previous one: doing so readmits envelopes signed under it that
  were dropped at the reset.

An ordinary rotation, with the earlier secret kept as the previous one, keeps
the floor and every held key. No other path lowers the stored floor, and no
command clears it.

### Senders

Every sender signs a fresh envelope for every message it publishes, including
every retry and every redelivery. A fresh envelope is one whose bytes the
sender has never published: re-signing unchanged content at an unchanged
`signed_at_ms` gives identical bytes, so reading the clock again is not
enough when it has not moved. A sender that may sign the same content twice
in one millisecond, or across a restart with its clock unchanged or set back,
takes `signed_at_ms` from a signing clock that never repeats a value: one
millisecond past the previous when the clock has not moved, and durable
across a restart, as
[Outbound acknowledgement](#outbound-acknowledgement) requires of the
gateway's acknowledgements. It never republishes envelope bytes it has already
published. A
refusal for any reason above is answered, if at all, by a newly signed
attempt. The content keeps its own identity across attempts, such as an
artifact's digest, and the receiver's deduplication of content is unchanged.
[Durability and Retirement](#durability-and-retirement) states the same rule
for inbound evidence and why a byte-identical retransmission cannot work.

### Limits and later versions

- **A future-dated envelope can outlive lost history.** Suppose an envelope was
  accepted before a start, signed by a sender whose clock ran ahead of the
  receiver's so that it was signed at or after that start, and the receiver kept
  no copy of its key. It can then be replayed after the start until it goes
  stale, at most `S` past its signing time. A start floor of the start time plus
  `S` would close this, at the cost of refusing every envelope for up to `S`
  after each start. This version accepts the gap.
- **A clock stepped back across a later start reopens what only a start floor
  covered.** A start floor is a clock reading and is not stored. For a
  receiver that stores nothing, a clock stepped back across a restart readmits
  every envelope of earlier runs that its new skew window reaches. For a
  storing receiver, it readmits envelopes whose keys were dropped by a
  release that kept no floor, or during a rollback to one. Storing the start
  clock would close this, at the cost of carrying a clock that ran fast at one
  start into every later run until real time passes it. This version accepts
  the gap; a receiver that stores its floor and keeps them through upgrades
  leaves it only for keys dropped before it first stored a floor.
- **A gateway's message signing clock can repeat a signing time across a
  restart.** This is an exception to [Senders](#senders). The clock from which
  the gateway signs every envelope under the runtime–gateway HMAC outside the
  evidence path is to keep its mark in `gateway.state_directory`, under
  [`gateway-config/v2.md`](../gateway-config/v2.md#gatewaystate_directory).
  A restart can repeat a value that
  clock issued without persisting it, one issued during an episode whose mark
  landed late or never, or one covered by a mark that was later
  lowered, as
  [that document's limits](../gateway-config/v2.md#limits-and-later-versions-state-directory)
  state.
  A receiver that evicted the keys of values no persisted mark now covers has
  raised its floor past them, so fresh envelopes the gateway signs below that
  floor and within the skew are refused as `before_replay_floor`, whatever
  their content, until its signing time passes the floor. An envelope repeated byte for byte is
  refused, outside the
  cases this section's other limits name, and the gateway's next attempt is
  newly signed. This version accepts these exceptions for that clock only. The
  clocks the gateway signs evidence-path envelopes from are held to Senders
  and [Outbound acknowledgement](#outbound-acknowledgement) unchanged.
- **No complete protection across lost state.** The floor gives no complete
  replay protection across the loss of a stored floor, the restore of an older
  state store, or a clock and state restored together. A floor restored from
  an older copy is lower than the one lost, and the start rule covers only
  envelopes signed before the start.
- **Freshness depends on clocks.** A later version may bind each exchange to
  an authenticated receiver epoch or challenge, so that telling sessions apart
  no longer depends on synchronised clocks.

### Replay vectors

[vectors/replay-v2.json](vectors/replay-v2.json) holds this section's cases.
Each case is a receiver context and a run of events in order. Every envelope in
it is one whose signature and topic-device check hold. The context gives the
skew, `replay_ttl_ms` or `null`, whether the receiver stores its floor and keys,
the floor it has stored, its clock at its last start, and the keys it holds,
each with its signing and receipt times. The events are:

- `receive`: the receiver verifies an envelope and, when it is accepted,
  holds its key.
- `authenticate` and `commit`: a family that records only once the envelope
  answers something.
- `prune`: the receiver drops every key whose retention has ended.
- `evict`: a full receiver drops its held key with the smallest signing time.
- `restart`: the receiver starts again, with a new skew where the case gives
  one.
- `rotate`: a rotation that keeps the previous secret, or one that keeps none.

Each event gives its reason, or none when accepted, and the floor and held
keys after it.

The cases cover:

- an envelope signed exactly at the floor, and one millisecond below it;
- both skew bounds and one millisecond beyond each;
- a replay at the last millisecond its envelope passes check 1, under a
  `replay_ttl_ms` shorter than the skew, and under a longer one;
- a key recorded at commit, kept for `replay_ttl_ms` from its authentication;
- senders whose clocks run ahead of and behind the receiver's, across a start;
- the clock stepped forward and back, live and across a start, and stepped
  back across a later start, by a receiver that stores nothing and by a
  storing receiver after an upgrade;
- the skew raised and lowered across a restart;
- a restart that stores its floor and keys, one that stores neither, the
  first start after an upgrade from a release that kept no floor, and a
  rollback and upgrade;
- a key dropped between `authenticate` and `commit`;
- a full receiver evicting a key, and an evicted key signed ahead of the
  clock raising the stored floor above a sender behind it, across a restart;
- a rotation that keeps the previous secret and one that keeps none;
- precedence where two checks fail together: stale and below the floor,
  future and below the floor, and below the floor and held. Checks 1 and 2
  cannot fail together.

`scripts/generate-gateway-replay-vectors-v2` reproduces the file byte for
byte. `scripts/check-gateway-replay-vectors-v2` shares no code with it: it
reads the order of checks from this section, replays every case under the
rules above, and confirms that each event's reason, floor and held keys are
the ones declared.

{

  "device_id": "string",
  "sensor_type": "string",
  "trigger_name": "string",
  "prompt": "string",
  "context": {
    "value": 0.0,
    "unit": "string",

    "producer_time": "reported|not_reported|unknown",
    "history": [
      {
        "value": 0.0,
        "timestamp": 0,

      }
    ]
  },
  "action_tier_hint": "A|B|C|D",

`producer_time` on the reading and on each history point says what its

## Tier 3 Reasoning Response Payload

```json
{
  "request_id": "uuid4-string",
  "device_id": "string",
  "text": "string",
  "model": "string",
  "tokens_used": 0,
  "latency_ms": 0,
  "confidence": 0.0,
  "action_tier": "A|B|C|D",
  "proposed_action": "string or null",
  "error": "string or omitted"
}
```

`request_id` must match a pending runtime request, and `device_id` is the
request's device: the response body names the device its topic and envelope
are bound to, so a consumer verifies all three against one value. On provider timeout or failure,
the gateway still publishes an error response with the original `request_id` and
an `error` string so the runtime does not wait for an unanswered request.

`action_tier` must be one of `A`, `B`, `C`, or `D`. The runtime rejects invalid
response tiers. For matched triggers, the runtime remains trigger-authoritative:
the gateway cannot grant more physical authority than the trigger declared in
skill YAML. Unmatched gateway reasoning must not create autonomous physical
action authority; Tier C remains approval-gated and Tier D remains rule-only.

### Reasoning Auth Envelope

Both directions carry the runtime-gateway HMAC envelope whenever
`gateway.auth.enabled: true`, on the same terms as the export and enrichment
envelopes, and a gateway MUST NOT invoke a provider for an unauthenticated
request or publish an unauthenticated response while authentication is
enabled.

| Direction | `message_type` | `device_id` | `request_id` | Signed by |
| --- | --- | --- | --- | --- |
| Request, runtime → gateway | `reasoning_request` | the request's `device_id` | the request's `request_id` | runtime, current shared secret |
| Response, gateway → runtime | `reasoning_response` | the request's `device_id` | the request's `request_id` | gateway, current shared secret |

The signing input is the one defined under *Heartbeat Auth Envelope*, over the
complete payload with `auth` removed. Verification precedes every side effect,
including the correlated error response; the topic-device check and the
signature check each hold alone; freshness and replay follow
[Envelope Freshness and Replay](#envelope-freshness-and-replay); the previous secret verifies and never signs. A verified
response confers no authority the trigger did not declare.

Both payloads are admitted under the [Payload Member Rule](#payload-member-rule) before the envelope is verified.

**Floating-point fields in gateway-signed payloads.** The runtime verifies a
signed payload by re-serialising it, and Go and CPython spell a non-zero
magnitude below `1e-4` differently. A gateway therefore MUST emit `confidence`
rounded to four decimal places, so every emitted value is exactly `0` or at
least `0.0001` and both serialisers agree; `uptime_s` in the heartbeat is
rounded to milliseconds on the same principle. Runtime-signed payloads are
unaffected, because the gateway reproduces the wire literal rather than
re-serialising.

bridge posture. It deliberately excludes URLs, env var names, CIDR values,
tokens, HMAC secrets, and provider-specific headers.

The `auth` object is present when `gateway.auth.enabled: true` and omitted (`auth` field absent) when `false`. Runtimes with auth enabled reject heartbeats that omit or fail the `auth` block. Runtimes with auth disabled accept unsigned heartbeats (see `gateway.auth` in `runtime-config/v1.md`).

### Heartbeat Auth Envelope

When `gateway.auth.enabled: true`, the gateway signs each heartbeat payload using HMAC-SHA256 over a canonical string:

```text
message_type\ndevice_id\nrequest_id\nsigned_at_ms\ncanonical_json
```

Where:

| Field            | Value                                      | Notes                                                    |
| ---------------- | ------------------------------------------ | -------------------------------------------------------- |
| `message_type`   | `"gateway.heartbeat"`                      | Fixed string.                                            |
| `device_id`      | `""`                                       | Empty string — heartbeat is site-scoped, not per-device. |
| `request_id`     | `""`                                       | Empty string — no request correlation.                   |
| `signed_at_ms`   | string of the `signed_at_ms` integer       | Should equal `timestamp_ms`.                             |
| `canonical_json` | JSON with keys sorted, no extra whitespace | Must reproduce the full heartbeat payload exactly.       |

The shared secret is the same secret used for reasoning and export envelopes, named by `gateway.auth.shared_secret_env`. `device_id` is intentionally empty: a LAN-broadcast heartbeat is site-scoped via the shared secret, not per-device. This is a distinct trust model from reasoning and export envelopes, which bind to `device_id` for per-device isolation.

The heartbeat's key is `message_type`, `signed_at_ms` and `signature`. Freshness and replay follow [Envelope Freshness and Replay](#envelope-freshness-and-replay).

The heartbeat is admitted under the [Payload Member Rule](#payload-member-rule) before its envelope is verified.

## Runtime Node Heartbeat Payload

Published by each runtime to `ori/{device_id}/runtime/heartbeat` when runtime
`gateway.enabled` and `gateway.node_heartbeat.enabled` are true. The gateway
subscribes per configured `gateway.device_ids` and stamps `gateway_seen_ms` when
it ingests the heartbeat.

```json
{
  "device_id": "site-a-edge-01",
  "status": "healthy|degraded|critical",
  "last_seen_ms": 1717000000000,
  "gateway_seen_ms": 0,
  "active_triggers": ["trigger_name"],
  "evidence": {
    "chain_head_hash": "64-char lowercase sha256 hex or empty",
    "attestation_gap_count": 0,
    "available": true,
    "action_event_type": "SAFETY_ACTION_EXECUTED"
  },
  "auth": {
    "scheme": "hmac-sha256",
    "signed_at_ms": 1717000000000,
    "signature": "hmac-sha256:<hex-digest>"
  }
}
```

`status` is `healthy`, `degraded` or `critical`. The `starting` value belongs
to the site-scoped gateway heartbeat above; runtime-node publishers and
gateway consumers do not emit or accept it on this topic.

The runtime derives `status` from its local health snapshot under
[runtime-health/v4.md](../runtime-health/v4.md#heartbeat-mapping): local `ok`
is `healthy`, `degraded` is `degraded`, and `critical` is `critical`. A local
status that is absent, unknown or malformed, or inconsistent with the
snapshot's own `critical` or `degradation_reasons`, as that contract's triple
check decides, is the fallback heartbeat: `status: "critical"`,
`degradation_reasons: ["health_snapshot_invalid"]`, `active_triggers: []`, no
`evidence` block, and nothing else taken from that snapshot. It never maps to
`healthy`. A stateful projector that has seen evidence from the node reads the
missing block as evidence unavailable, which is consistent with a critical
node. runtime-health/v4 *Heartbeat Mapping* gives the source of every field.

**Migration.** The runtime node heartbeat family is defined, as it stood, in
[gateway-api/v1.md](v1.md), which is frozen and which the gateway claims.
The `critical` status, the tokens above and steps 1, 9 and 11 exist only
here. A gateway implements and claims this version's heartbeat rules before
any runtime emits a runtime-health/v4 heartbeat; until then the runtime
emits only what v1 accepts. The site projection, in the gateway's site
health and its `GET /health`, and every consumer of that projection gain
`critical`.

A gateway keeps `critical` through every projection of the node: the site
view shows a `critical` node as `critical`, and any aggregate across nodes
takes the most severe, `critical` over `degraded` over `healthy`. Accepting
the value is not enough; a projection that folds `critical` into `degraded`
or `healthy` loses the one signal the value exists to carry.

### `degradation_reasons`

Optional and additive. Names the runtime subsystems that are degraded, so a
consumer can tell *why* a node reports `degraded` rather than only *that* it
does.

It is deliberately **not** `active_triggers`. An active trigger is a physical or
automation trigger; a degraded subsystem is neither. Overloading that field
would inflate the trigger count and leave a receiver unable to distinguish
"three rules are firing" from "one background loop died". The two also differ in
disclosure: trigger names are site-authored and arbitrary, which is why gateways
expose only their count, whereas the tokens below are contract-owned and
non-sensitive by construction and may therefore be projected.

The vocabulary is closed. Each token but the umbrella and
`health_snapshot_invalid` names one condition of the runtime health snapshot;
[runtime-health/v4.md](../runtime-health/v4.md#conditions) gives its predicate
and its severity, and this table owns the token. `health_snapshot_invalid` is
defined by that contract's heartbeat mapping.

| Token | Severity | Meaning |
| --- | --- | --- |
| `action_log_records_lost` | `degraded` | An action record was lost before the store took it, and no authenticated operator has acknowledged the loss. |
| `alert_delivery_overdue` | `degraded` | A queued alert other than a Tier D notification is at or past its stated age bound, its delivery unconfirmed. |
| `action_log_records_stalled` | `degraded` | A record has waited past the release-owned stall bound: the store is not answering. |
| `commissioning_problem` | `degraded` | The commissioned binding has a problem, such as declared actuating hardware with no binding in force. |
| `community_skills_refused` | `degraded` | Community skills the device was configured with were refused. |
| `config_unsigned_value_source` | `degraded` | A file outside the configuration signature supplied values the runtime is running on. |
| `decision_record_lost` | `critical` | An operator's decision whose record the store never took, and no authenticated operator has acknowledged the loss. |
| `evidence_application_storage_fault` | `degraded` | Since the runtime last started, its store failed while deciding or applying a verified inbound evidence artifact, or while recording a refusal, and no inbound artifact has been applied since; never while evidence is `disabled` or `starting`. |
| `evidence_contributor_link_unresolved` | `degraded` | A contributor record names a holder whose record of the act was lost. |
| `evidence_courier_answer_unrecognised` | `degraded` | The delivery ledger holds a courier answer outside its closed set. |
| `evidence_posture_problem` | `degraded` | Evidence trust is not established on the device. |
| `firmware_liveness_degraded` | none | Umbrella: one or more of the five `firmware_liveness_*` conditions below holds. Emitted beside them; it decides no severity by itself. |
| `firmware_liveness_device_expired` | `critical` | A supervised device's last liveness publication is at least the expiry window old. |
| `firmware_liveness_over_capacity` | `degraded` | More devices are supervised than the scheduler supports. |
| `firmware_liveness_stopped` | `critical` | The liveness loop ended after starting, not by orderly shutdown. |
| `firmware_liveness_tick_failures` | `degraded` | Liveness ticks are failing while supervision is still inside its window. |
| `firmware_liveness_tick_stale` | `critical` | No liveness tick has succeeded within the expiry window. |
| `safety_zone_activation_refused` | `degraded` | An eligible zone's profile was refused at activation, so the zone is not protected. |
| `safety_zone_active_unprotected` | `degraded` | A zone the device has undertaken to protect reports `unprotected`, or its sensor is not reporting. |
| `safety_zone_trip_unresolved` | `critical` | A commanded protective trip whose command was refused or failed, whose observed effect mismatched, or whose effect was not verified within its deadline. |
| `sensor_stale` | `degraded` | A connected sensor has gone without a reading beyond its silence bound. |
| `sensor_measurement_degraded` | `degraded` | A sensor answers and its windows are refused as not a measurement. |
| `sensor_unconnected` | `degraded` | A configured sensor is not connected. |
| `health_snapshot_invalid` | `critical` | The runtime's local health snapshot was malformed, so its health is unknown. Published by the heartbeat alone, never carried in a snapshot, and always the only token. |
| `subsystem_starting` | `degraded` | A subsystem whose state decides severity is still initialising. |
| `subsystem_state_unknown` | `degraded` | A subsystem that decides only degraded conditions could not be read. |
| `subsystem_state_unknown_critical` | `critical` | A subsystem that can raise a critical condition could not be read: critical visibility is unavailable. It does not say a trip failed or any physical fault occurred. |
| `tier_c_records_degraded` | `degraded` | Tier C outcome records are uncertain, unappended, or at their ceiling. |
| `skill_optional_hooks_unavailable` | `degraded` | A loaded skill runs without hooks it declared optional. |
| `skill_required_hooks_unavailable` | `critical` | A skill whose hooks are required was refused because they are unavailable. |
| `tier_c_recovery_failed` | `degraded` | Tier C recovery at start did not complete. |
| `tier_d_alert_delivery_unconfirmed` | `critical` | A Tier D notification is unresolved at or past its attempt or age threshold: its delivery is unconfirmed. |

`firmware_liveness_degraded` means "one or more" of the liveness conditions:
they differ in blast radius, and a consumer that reads only the umbrella learns
that liveness is at risk without being told it is total. It never
decides `status`; the precise tokens beside it do. Per-device identity,
supervised and expiring counts and capacity stay in the runtime's local health
interface.

A token confers nothing. Reasons explain health; they never grant actuation
authority and never gate Tier D.

A conforming healthy heartbeat, with the optional blocks omitted for brevity:

```json
{
  "device_id": "site-a-edge-01",
  "status": "healthy",
  "last_seen_ms": 1717000000000,
  "gateway_seen_ms": 0,
  "active_triggers": []
}
```

A conforming degraded heartbeat, from a runtime whose liveness ticks are
failing inside the expiry window:

```json
{
  "device_id": "site-a-edge-01",
  "status": "degraded",
  "last_seen_ms": 1717000000000,
  "gateway_seen_ms": 0,
  "active_triggers": [],
  "degradation_reasons": ["firmware_liveness_degraded", "firmware_liveness_tick_failures"]
}
```

A conforming critical heartbeat, from a runtime that lost an operator's
decision record while a sensor is unconnected; the degraded condition beside
it does not lower the status:

```json
{
  "device_id": "site-a-edge-01",
  "status": "critical",
  "last_seen_ms": 1717000000000,
  "gateway_seen_ms": 0,
  "active_triggers": [],
  "degradation_reasons": ["decision_record_lost", "sensor_unconnected"]
}
```

The healthy examples deliberately omit `degradation_reasons`: the field is
absent whenever there is nothing to report, which is the ordinary case, and a
`status` alternation placeholder cannot carry it without contradicting the
implication rule below.

**Presence and shape.** The field is absent when no named degradation exists. If
present it carries at least one token; an empty array is **malformed**, because
two encodings of one state is a difference implementations resolve
inconsistently. Tokens are unique, in byte order, and number at most
**32** — an exact bound rather than "bounded", so conformance is checkable
without judgement. The vocabulary holds 32 tokens. A conforming heartbeat names
either `health_snapshot_invalid` alone, or a combination of the other 31. Not
all 31 can hold at once, because a block that names
`subsystem_state_unknown_critical` cannot also name its own conditions, but
the bound admits all 31 together. A conforming runtime never emits
`firmware_liveness_degraded` alone, because its local triple check refuses
that snapshot (runtime-health/v4 step T4), though a receiver accepts it. The
bound of 32 admits every such combination and leaves room for one addition
without a change to the bound; step 9 refuses `health_snapshot_invalid`
beside any other token.

**Validation order is normative.** It applies after authentication and generic
JSON syntax parsing, but **before typed decoding or normalisation** — otherwise
a typed decoder would already have rejected the array-type and element-type
checks, or collapsed absent into present-empty, before this validator ever ran.

| Step | Check | Verdict on failure |
| --- | --- | --- |
| 1 | `status` is the string `"healthy"`, `"degraded"` or `"critical"`; never `"starting"` on this topic | `runtime_status_invalid` |
| 2 | presence of `degradation_reasons` — absent is valid and terminates validation | — |
| 3 | value is an array | `degradation_reasons_not_array` |
| 4 | length is `1 .. 32` | `degradation_reasons_length_invalid` |
| 5 | every element is a string | `degradation_reason_not_string` |
| 6 | elements are unique | `degradation_reasons_not_unique` |
| 7 | elements are in byte order of their UTF-8 encoding | `degradation_reasons_not_ordered` |
| 8 | every token is in the closed vocabulary | `degradation_reason_unknown` |
| 9 | `health_snapshot_invalid`, when present, is the only token and `status` is `"critical"` | `degradation_reason_not_alone` |
| 10 | non-empty reasons require `status` to be `"degraded"` or `"critical"` | `degradation_reasons_status_mismatch` |
| 11 | `status` is at least the most severe token's severity, `critical` over `degraded`, `firmware_liveness_degraded` counting for nothing | `degradation_reasons_severity_understated` |

Step 11 refuses a heartbeat that names a critical condition under
`degraded`. A `status` above its tokens' severity is accepted, and so is an
older runtime's `degraded` heartbeat naming only `firmware_liveness_degraded`.

Step 1 comes first because no reason can be judged against a status that is
not one; a heartbeat whose `status` is invalid is refused whatever its
reasons.

A receiver MUST classify a refusal as the verdict of the **first** failing step.
Uniqueness and ordering are separate steps deliberately: they are different
defects, and sharing one verdict would make a conformance failure ambiguous
about which rule an implementation is missing.

**These verdicts are internal classification tokens, not a wire response.** The
runtime node heartbeat is a one-way MQTT publication with no rejection envelope,
so a receiver is not required to reply to anything. The tokens exist so that a
refusal is nameable in logs, metrics and conformance tests — which is what makes
"refused for the right reason" checkable at all.

The order is load-bearing rather than stylistic: the vocabulary holds fewer
tokens than the bound, so any list longer than the vocabulary necessarily also
contains duplicates or unknown tokens. Without fixed precedence an over-length
list could be refused by the uniqueness, ordering or vocabulary check while no
length guard exists at all, and a conformance test asserting only "refused"
would pass against that implementation.

**Consumers MUST preserve field presence** long enough to distinguish absent
from present-empty, and MUST NOT normalise both to the same empty collection
before validation. In Go the `nil` versus zero-length slice distinction carries
it, and an ordinary copy or normalisation step destroys it silently.

**Authentication.** When gateway heartbeat authentication is enabled,
`degradation_reasons` participates in the canonical authenticated payload below.
It is never excluded from the signing input or treated as unsigned metadata.
When authentication is disabled it takes the same unauthenticated transport
posture as every other heartbeat field — it is not separately protected and does
not become trustworthy on an unauthenticated link.

Ordering failures therefore surface at two different layers, and both must be
implemented:

| Case | Outcome |
| --- | --- |
| An already-signed list is reordered in transit | **Authentication fails.** The canonical bytes changed. |
| A freshly signed list is out of byte order | **Authentication passes**, then the ordering check refuses it as `degradation_reasons_not_ordered`. |

An implementation that tests only the first leaves semantic ordering unenforced
for any publisher that signs a malformed list correctly.

**Rolling upgrades.** `status: "degraded"` or `status: "critical"` with the
field absent MUST remain accepted: an older runtime that cannot name its reason
is still reporting a true degradation, and refusing it would turn an upgrade
window into an outage.

**Vocabulary additions are order-dependent.** Because unrecognised tokens are
refused, adding one requires ratification here, then gateway acceptance and
projection, and only then runtime emission. The same holds for the `critical`
status: a gateway accepts and projects it before any runtime emits it. A
runtime emitting ahead of its gateways would make a conforming older gateway
reject the entire heartbeat,
turning an additive contract change into fleet-wide loss of health reporting.
"Additive" describes the contract, not the deployment.

**Not carried here.** Per-device failure identity, supervised and expiring
device counts, worst-case publish latency and supported capacity are not in
the heartbeat. The heartbeat is a site-scoped broadcast, authenticated by a
secret every node on the site shares, so anything in it reaches every
subscriber on the broker: counts would reveal deployment topology there, and
subordinate device identifiers are a disclosure this contract does not make.
The `health` export below is different: the gateway requests it from one
device, and the response is bound to that device's `device_id`,
authenticated when gateway authentication is enabled, and published on that
device's export topic, which per-device broker ACLs restrict, rather than
broadcast to the site. It carries counts for that reason. It is plaintext
operational posture, never encrypted, so it still carries no subordinate
identity, path or free text. Broker URLs, exception text, filesystem
paths and secrets are never carried. The runtime node's own `device_id` is
unaffected — it identifies the node reporting the degradation.

`evidence` is optional and additive. It is present when the runtime has
`evidence.enabled: true` (see `evidence/v1.md`) and omitted otherwise.
Stateless consumers ignore it when absent. Stateful site-health projectors
must not: once a device has reported evidence, a heartbeat that omits the
block is treated as evidence-unavailable and degrades the node (see
`evidence/v1.md`). Field semantics:

| Field                   | Type     | Notes                                                                                                     |
| ----------------------- | -------- | --------------------------------------------------------------------------------------------------------- |
| `chain_head_hash`       | `string` | Current evidence chain head: empty string (no events yet or chain unavailable) or 64 lowercase hex chars. |
| `attestation_gap_count` | `int`    | Count of Tier C/D action rows with attestation status `pending` or `failed`. Must be `>= 0`.              |
| `available`             | `bool`   | Whether evidence signing is currently available on the device.                                            |
| `action_event_type`     | `string` | Chain event type the device emits for new Tier C/D attestations; `''` while signing is unavailable. Lets a mixed-fleet vocabulary rollout be confirmed per device (see `evidence/v1.md`). |

The heartbeat evidence block is a liveness/integrity signal, not an evidence
archive: the persisted chain on the device remains the evidence object. The
gateway rejects heartbeats whose evidence block fails the bounds above, and
enriches accepted signals with tamper observations (truncation and head
regression) defined in `evidence/v1.md`.

`auth` is present when runtime `gateway.auth.enabled: true` and omitted when
false. Gateway deployments with auth enabled reject unsigned, stale, replayed, or
device-mismatched runtime heartbeats. Runtime heartbeats are infrastructure
liveness signals, not sensor events, and must use `retain=false`.

A runtime heartbeat is admitted under the [Payload Member Rule](#payload-member-rule) before its envelope is verified.

The HMAC signing input uses the regular device-bound gateway envelope:

```text
runtime.heartbeat
device_id
request_id
signed_at_ms
canonical_json
```

`request_id` is an empty string for runtime heartbeats because the heartbeat is
not a request/response exchange.

`canonical_json` covers the whole payload except `auth`, so additive fields such
as `degradation_reasons` are signed without amending the envelope. That is the
mechanism behind the two ordering cases above: reordering an already-signed list
changes the canonical bytes and fails authentication, while a publisher that
signs a list out of byte order produces valid bytes that only the ordering check
can refuse, as `degradation_reasons_not_ordered`.

| Parameter        | Target                                                                                                                                                                                                        |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| response timeout | 10s default                                                                                                                                                                                                   |
| retry            | 1 retry                                                                                                                                                                                                       |

## Gateway Availability Check

The runtime's `gateway_reachable` capability posture flag is set **exclusively** by received heartbeats. Internet availability (`internet_available`) is a separate posture field and has no effect on Tier 3 escalation decisions. A site with no internet but a working LAN gateway will correctly escalate to Tier 3.

Behavior:

- Runtime subscribes to `ori/gateway/health` via `MqttGatewayHeartbeatSubscriber`.
- Gateway publishes a heartbeat on this topic at `heartbeat_interval_s` (default 30s).
- `gateway_reachable` flips to `false` when no heartbeat has been received within `reasoning.capability_posture.gateway_heartbeat_ttl_seconds` (default 30s).
- Detection window for gateway loss: up to `heartbeat_interval_s + gateway_heartbeat_ttl_seconds` seconds after the gateway stops publishing. During this window the elevator may attempt Tier 3 escalation, burn `gateway.reasoning.timeout_ms` per attempt, then fall back to `local_slm`. This is expected offline-first behavior — Tier D and safety paths are unaffected.
- The gateway's heartbeat interval and crash-recovery behavior therefore directly determine Tier 3 availability. If the gateway heartbeat publisher stalls, `gateway_reachable` expires and Tier 3 escalation stops until heartbeats resume.

## Producer Time

`timestamp` on a sensor reading is meant to be the producer's account of when
the world was measured, and some producers give none. A device that pushes a value
without a time, or a signed firmware envelope, whose `emitted_at_ms` is
advisory under [firmware-telemetry/v2.md](../firmware-telemetry/v2.md), leaves
the runtime only its own clock, and the runtime still sends a time in
`timestamp`, because every consumer requires the member. `producer_time` says
what that time is. It is carried on every `sensor_history` row and on the
reading and every history point of a Tier 3 reasoning request, and it
describes the value actually sent in `timestamp`, including one the runtime
put there because the reading had none.

| `producer_time` | `timestamp` is |
| --- | --- |
| `reported` | the measurement's time: a time the producer reported in a member its protocol declares to be the measurement time, or the runtime's clock at a read it requested itself, which dates that read. |
| `not_reported` | the value's arrival: the runtime's own clock when the value reached it. Nothing reported when the world was measured. |
| `unknown` | a time the runtime does not state to be either of the above: one whose basis it cannot state, or one that is not a reading's time. |

**The runtime decides it at ingest and stores it with the reading,** from a
closed table of its producer paths, keyed by the path a reading arrives by and
the member, if any, the runtime takes `timestamp` from. This contract does not
enumerate the table; the runtime owns it.

- A value the runtime obtains by a request it makes at the time of the read,
  by a bus read, a serial or Modbus exchange, a network request it issues or a
  host counter, is `reported`, and `timestamp` is the runtime's clock at the
  read. That dates the read, not the instrument's own sampling: an
  instrument, or a device in front of it, that caches its value can answer
  with one it took earlier, as firmware-telemetry/v2 says of a bridged
  channel.
- A value pushed to the runtime is `not_reported`, including one the runtime
  holds from a subscription and reads later, and one it reads from a broker's
  retained message or from a cache that pushed values fill, which are not
  reads of the instrument, unless the runtime takes `timestamp` from a member
  the producer's protocol declares to be the time of measurement, which makes
  it `reported`. Each value in a cache keeps the time and basis it entered
  with: a value the runtime obtained by its own request keeps that request's
  time and basis when it is later served from the cache.
- Under `not_reported`, `timestamp` is the value's arrival: the runtime's own
  clock when the value reached it. A time an intermediary or a transport gave,
  such as a LoRaWAN network server's `received_at` or a Zigbee coordinator's
  `last_seen`, is neither a measurement nor the value's arrival, and a time the protocol
  calls advisory is not a measurement. A runtime never sends such a time in
  `timestamp` for a reading it ingests once it records the basis; it may
  carry it in another member.
- A reading stored before the runtime recorded the basis is `unknown`, unless
  a member the runtime itself wrote at ingest, never one copied from the
  payload, identifies the path it arrived by. Every row compacted before the
  runtime recorded the basis is `unknown`. Such a reading keeps the
  `timestamp` it was stored with, including an intermediary's or an advisory
  time an earlier release took into it: the runtime does not rewrite, omit or
  refuse it, and cannot reconstruct the arrival it lost, so `unknown` is the
  whole of what it says.

The runtime never infers the basis at export from a reading's value, from a
member copied from its payload, or by comparing `timestamp` with
`received_at_ms`: a measured reading can carry the same value as its receipt.
In this contract a value's *arrival* is when it reached the runtime, and its
*receipt*, `received_at_ms`, is when the runtime stored it: a second reading
of the runtime's clock that need not equal the arrival, since a value waits
between reaching the runtime and being stored, and a value held from a
subscription can be stored more than once.

**What a consumer does with each.**

- `reported`: `timestamp` is the producer's account, under the rules of
  [`sensor_history`](#sensor_history) and `runtime-telemetry/v2`.
- `not_reported`: `timestamp` carries no measurement time. A consumer never
  presents it as when the value was measured, or under any name that says
  so; it may present it as when the value reached the runtime. The
  measurement happened at or before the arrival, by an amount nothing here
  bounds, so a consumer that filters or aggregates by `timestamp` places such
  a record by its arrival, and reports it as having reached the runtime in a
  period, never as measured in it.
- `unknown`: `timestamp` is of unstated basis. A consumer may filter and aggregate
  by it as before, and presents it as a time of unstated basis, never as when
  the value was measured.

A record with no `producer_time`, from a runtime that predates the member,
is read as `unknown`, and so is a value outside the three or of another JSON
type. Reading an absent marker as `reported` would assert a measurement for
every firmware reading exported before the marker existed.

**No record carries an age.** firmware-telemetry/v2 lets the runtime that
signed a reading's liveness nonce bound the reading's age, anchored to the
instant it computed the bound. No member of this contract carries that bound,
and an unanchored age MUST NOT appear in any member.

**Rollout.** A runtime may emit `producer_time` before its gateways read it.
A gateway that ignores unknown members goes on reading every `timestamp` as a
measurement, as it does today. One thing changes for it: a bucket holding
readings of more than one basis arrives as one row per basis with the same
`start_ms` and `end_ms`, which such a gateway passes on unmarked, and the
extra rows count toward the rows a request returns, so a request that fitted a
gateway's own limit before can exceed it. That happens only for a bucket
whose readings were recorded under more than one basis: readings of one
sensor that arrived by more than one path or member, or a bucket that spans
the runtime's adoption of the member.

### Request Fields

| Field         |        Required | Notes                                                                                    |
| ------------- | --------------: | ---------------------------------------------------------------------------------------- |
| `request_id`  |             yes | Correlates request and response. Must be non-empty.                                      |
| `export_type` |             yes | One of `health`, `sensor_history`, `action_log`, `reasoning_log`, `tier_c_decision_log`. |
| `device_id`   |             yes | Must match the target runtime device ID.                                                 |
| `since_ms`    | export-specific | Unix milliseconds lower bound. Required for `sensor_history`.                            |
| `until_ms`    | export-specific | Unix milliseconds upper bound. Required for `sensor_history`.                            |
| `limit`       |              no | Runtime caps page size. Clients should use `<= 1000`.                                    |
| `page_token`  |              no | Empty string for first page. Subsequent value comes from response `next_page_token`.     |
| `params`      |              no | Export-specific object. Defaults to `{}`.                                                |

`until_ms` must be greater than or equal to `since_ms` when both are present.
Invalid or mismatched requests return an error response envelope instead of
raising transport-level failures. That applies only to a request
[Payload Size](#payload-size) and the [Payload Member Rule](#payload-member-rule)
admit and [Payload Volume](#payload-volume) does not drop. A request refused
under either rule, or dropped under Payload Volume, is not answered: its
`request_id` and `device_id` cannot be relied on, or answering it would cost
what the bound exists to refuse. Nor is a request answered whose envelope is
not verified while `gateway.auth.enabled` is true, under
[Export Auth Envelope](#export-auth-envelope).

## Runtime Export Response Payload

Published by runtime to `ori/{device_id}/export/response/{request_id}`.

```json
{
  "request_id": "uuid4-string",
  "export_type": "sensor_history",
  "device_id": "site-a-edge-01",
  "items": [],
  "next_page_token": "",
  "complete": true,
  "error": null
}
```

Every response, including validation failures, includes the envelope fields above.
When `error` is non-null, `items` is empty and `complete` is true.

When `gateway.auth.enabled: true`, export responses carry an `auth` block signed
with `message_type=export_response`. When runtime `gateway.encryption.enabled`
is `true`, sensitive export responses (`sensor_history`, `action_log`,
`reasoning_log`, and `tier_c_decision_log`) are AES-GCM encrypted before HMAC
signing. Health exports remain plaintext operational posture.

Export requests and responses are admitted under the [Payload Member Rule](#payload-member-rule) before an envelope
is verified, and a decrypted response plaintext again before any member of it
is read.

### Export Auth Envelope

Both directions carry the runtime-gateway HMAC envelope whenever
`gateway.auth.enabled: true`.

**Scope.** Verifying requests and verifying responses, and every rule below
that turns on whether an envelope is verified, apply while
`gateway.auth.enabled` is true. With authentication disabled, as a development
convenience, requests and responses travel unsigned: a runtime answers a
mismatched or invalid request with an error response as
[Request Fields](#request-fields) states, and a gateway delivers the response
it correlates to a pending request. The bound on a gateway's wait applies in
both modes.

| Direction | `message_type` | `device_id` | `request_id` | Signed by |
| --- | --- | --- | --- | --- |
| Request, gateway → runtime | `export_request` | the request's `device_id` | the request's `request_id` | gateway, current shared secret |
| Response, runtime → gateway | `export_response` | the request's `device_id` | the request's `request_id` | runtime, current shared secret |

The signing input is the one defined under *Heartbeat Auth Envelope*, over the
complete payload with `auth` removed. An encrypted response is signed over its
encrypted form, as above.

**Verification precedes every side effect.** A runtime verifies the request
envelope before it reads its store, builds a page or publishes anything, a
signed error response included. A request whose envelope is not verified, for
any reason, freshness and replay included and a fault in verification itself,
is dropped and logged, and is not answered. A signed answer to it would let
anything that can reach the broker:

- put a runtime-signed error on a genuine exchange's response topic, by
  reusing that exchange's `request_id` with a bad signature;
- read the runtime's clock and the state of its replay cache from the
  refusal reason;
- make the runtime compute a signature and publish once for every message it
  sends.

**Two checks that must each hold alone.** The request's `device_id` MUST equal
the topic's device segment, checked independently of signature verification,
and the signature MUST verify under the expected `device_id` and `request_id`.
Neither check may depend on the other having run. With authentication enabled,
a request that fails either check is one whose envelope is not verified, and
is not answered; the error response for a mismatched request applies only with
authentication disabled. A gateway verifies a response under the `device_id`
and `request_id` of the request waiting for it, so a response signed for
another device or another request is not verified.

**Freshness and replay** follow
[Envelope Freshness and Replay](#envelope-freshness-and-replay).

**Rotation.** `gateway.auth.previous_shared_secret_env` verifies and never
signs; each side signs under its current secret.

**The gateway's side.**

- With authentication enabled, a gateway verifies a response before it
  delivers anything to the request waiting for it. A response that is not verified is dropped and logged, and
  the request keeps waiting, so a broker client cannot end an exchange by
  publishing on its response topic.
- A gateway bounds its wait for every export request, in both modes. The
  bound runs from publishing the request, and no message the gateway receives,
  verified or not, extends it. When no verified response arrives within the
  bound, it ends that request as failed, logs it, and releases what it held
  for it. A later attempt is a new request, newly signed. A gateway also
  bounds the number of pages one export requests, so no export as a whole
  waits without a bound. No caller waits on an export request without a
  bound. The bound is the gateway's to set; this version requires one and
  fixes no value.
- With no answer to an unverified request, the gateway's log of that timeout
  is the only local sign of a clock outside the skew or a mismatched secret,
  and it cannot tell either apart from a lost network or a stopped runtime.

**Implementation tests.** Neither side adopts these rules without tests that
drive its real entry point:

- a runtime answers no request whose envelope is not verified, whether
  unsigned, stale, future-dated, replayed, signed under another secret or
  device, or failing by a fault in verification, and answers an invalid
  request with authentication disabled;
- a gateway that receives a forged response leaves the genuine exchange
  pending, and a later verified response completes it;
- a gateway waiting on a silent runtime ends the request at its bound,
  releases its pending state and logs it, in both modes, and so does one whose
  subscription or publication stalls, or that receives forged responses
  repeatedly while it waits: the caller's whole operation stays bounded.

These are behaviour, not bytes, so no corpus here holds them.

**Adoption order.** A gateway bounds its wait and drops unverified responses
before a runtime stops answering unverified requests. Against a gateway that
waits without a bound, an unanswered request blocks its caller indefinitely,
and the mismatch that caused it is reported nowhere.

## Supported Export Types

### `health`

Returns a single remote health projection in `items[0]`, as
[runtime-health/v4.md](../runtime-health/v4.md#remote-health-projection)
defines it. It is not the local snapshot: it is an allowlist of approved
members, so a member added to the snapshot later stays local until that
contract approves it. It carries the node's `device_id`, `status`,
`critical`, `degradation_reasons`, every block's `state`, counts and stable
reason codes. It never carries paths, exception text, sender identities or
subordinate device identities. Remote device-level diagnosis needs a
separately authorised, encrypted detailed export, which this contract does
not define.

The projection no longer carries `remote_command_lockout.senders`, which the
runtime-health/v3 snapshot this export returned did. The gateway's runtime
client, which reads sender risk from it, migrates to the projection's sender
counts.

Request notes:

- `since_ms`, `until_ms`, and `params` are ignored.

### `sensor_history`

Returns bounded sensor history for one sensor.

Request `params`:

| Field       | Required | Notes                                                                                                                          |
| ----------- | -------: | ------------------------------------------------------------------------------------------------------------------------------ |
| `sensor_id` |      yes | Runtime sensor ID to export.                                                                                                   |
| `bucket_ms` |       no | Aggregation bucket width in milliseconds. `3600000` means hourly buckets. `0` or omitted returns runtime-selected source rows. |

Response item shape for unbucketed rows:

```json
{
  "sensor_id": "current-main",
  "sensor_type": "current_clamp",
  "timestamp": 1717000000000,
  "value": 4.2,
  "unit": "ampere",
  "quality": 0.99,
  "sample_count": 1,
  "tier": "raw|5min|hourly|daily",
  "received_at_ms": 1717000000480,
  "producer_time": "reported"
}
```

Response item shape for bucketed rows:

```json
{
  "sensor_id": "current-main",
  "sensor_type": "current_clamp",
  "timestamp": 1717000000000,
  "start_ms": 1717000000000,
  "end_ms": 1717003600000,
  "value": 4.2,
  "avg_value": 4.2,
  "min_value": 3.8,
  "max_value": 4.8,
  "unit": "ampere",
  "quality": null,
  "sample_count": 12,
  "bucket_ms": 3600000,
  "tier": "bucketed",
  "received_at_ms": 1717003599900,
  "producer_time": "reported"
}
```

Bucket averages are weighted by `sample_count` so compacted runtime rows remain
statistically meaningful when re-aggregated for weekly reports.

A reading from a firmware device, which reports no measurement time, as an
unbucketed row:

```json
{
  "sensor_id": "panel-feed-ch0",
  "sensor_type": "current",
  "timestamp": 1717000000480,
  "value": 8.21,
  "unit": "ampere",
  "quality": 1.0,
  "sample_count": 1,
  "tier": "raw",
  "received_at_ms": 1717000000483,
  "producer_time": "not_reported"
}
```

**A row aggregates one basis.** A bucketed or compacted row aggregates only
readings of one `producer_time`, and carries it. A bucket holding readings of
more than one is exported as one row for each, in the order `reported`,
`not_reported`, `unknown`, after ordering by `start_ms`. Each row is computed
over the rows it aggregates alone: `sample_count` is their sum, `value` and
`avg_value` their mean weighted by `sample_count`, `min_value` and `max_value`
the least and greatest of their `value`, and `received_at_ms` the greatest of
their receipts. A bucketed row's `timestamp` is its `start_ms`,
`end_ms` is `start_ms` plus `bucket_ms`, `tier` is `bucketed` and `quality` is
`null`. A row falls in the bucket whose `start_ms` is its `timestamp` rounded
down to a multiple of `bucket_ms`. A raw `not_reported` reading is therefore
bucketed by when it reached the runtime, and a compacted row by the start of
its own bucket. The runtime records
the basis when it compacts from the moment it implements `producer_time`, so
only a row compacted before then is `unknown` for that reason.

An unbucketed row whose `tier` is `raw` and whose `producer_time` is
`not_reported` carries `received_at_ms`: a reading that reached the runtime
was stored by it. A history point in the reasoning request obeys the same
rule. Over compacted rows, which keep only their mean, `min_value` and
`max_value` are the least and greatest of those means, not of the readings
they summarise.

Where `producer_time` is `reported`, `timestamp` is the producer's account of
when the world was measured, kept as reported; under
[Producer Time](#producer-time), it is otherwise the value's arrival or of
unstated basis. `received_at_ms` is the runtime's own clock when it stored the
reading, its receipt; on a compacted or bucketed row it is the greatest
receipt among the rows aggregated. The two travel together on every row, and on every history
point in the reasoning request, because of the producer-time rules in
`runtime-telemetry/v2`. The receipt is for an age and for a mark: a consumer
that emits `timestamp` with neither the receipt nor an age beside it marks a
value that exceeds its receipt rather than changing it, and a consumer that
filters a window by when the world was measured filters on `timestamp`.
`timestamp` keeps its name: renaming it would break every consumer for a
distinction the receipt beside it already makes.

The export does not answer which reading is current. That is the runtime's
own answer, decided on the order the runtime stored its readings in, which a
wall clock cannot stand in for because the runtime's clock can step backwards
and a later reading then carries the smaller arrival and the smaller receipt;
the export carries no such order, and a
consumer must not derive "latest" from `received_at_ms` or from `timestamp`.
A bounded page of the export is cut by `timestamp` inside the caller's window,
so the first page is the earliest rows in that window by `timestamp`, which
for a `not_reported` row is its arrival.

A runtime from before the receipt sends no `received_at_ms`. A consumer reads
a value that is absent, or is not an integer from 1 to 9007199254740991
written without a fraction or an exponent, as no receipt, never as an
instant, and never fills it from `timestamp`.

### `action_log`

Returns bounded action-log rows for the runtime device.

Optional request `params`:

| Field  | Required | Notes                                  |
| ------ | -------: | -------------------------------------- |
| `tier` |       no | Optional `A`, `B`, `C`, or `D` filter. |

Response items include action name, tier, execution status, approval status,
action taken, operator response, proposal ID, safe-default usage, device ID,
sensor ID, sensor type, trigger name, timestamp, `attestation_status`,
`attestation_seq`, `input_attestation_grade`, and `input_posture`. The
`input_attestation_grade`/`input_posture` pair follows the evidence contract:
`attested` requires `sealed_flash` or `hardware_key`, `attested_dev` requires
`development`, and `unattested` uses an empty posture.

Each item also carries `record_kind`, `record_key` and `contributed_to`, under
the members `executed` and `action_taken` already name:

```json
{
  "action_name": "trip_relay",
  "tier": "D",
  "executed": false,
  "action_taken": "coalesced",
  "timestamp": 1717000000950,
  "record_kind": "contributor",
  "record_key": "5c0f8e2d9b6a4f17a3e1c2d4b5f60718",
  "contributed_to": "0b7d4c1e2f3a49d58e6c7b8a9f0e1d2c"
}
```

with the item's other members omitted here for brevity.

**What a row records.** A request can act, or join an act another request
already holds: the runtime then records the joining request as a
*contributor* of that act, not as an act of its own.

| `record_kind` | The row records | `contributed_to` |
| --- | --- | --- |
| `dispatch` | a request the runtime dispatched as its own act | `null` |
| `contributor` | a request that joined the act another row holds, instead of acting | that row's `record_key` |
| `contributor_legacy` | a request that joined another act, recorded by a release that predates contributor records | `null`: that release recorded no holder |

`record_key` is the row's own key, a non-empty string, and `null`, never the
empty string, on a row the runtime assigned no key. The runtime
assigns each key to one row, but a store can hold keys duplicated before keys
were constrained, and the runtime exports them as they are.
`contributed_to` is never the row's own `record_key`.

**Export row checks.** A runtime emits only rows that pass every check below.
A consumer that finds a row failing one classifies the row by the first that
fails. It reads a failing reading's `timestamp` as of unstated basis, and
counts a failing `action_log` row as no act and resolves nothing from it. *Readings* are `sensor_history` rows and the reading and history
points of a Tier 3 reasoning request. Each check applies only to its family,
and the checks of a family are made in this order.

| Step | Family | Check | Verdict on failure |
| --- | --- | --- | --- |
| 1 | readings | `producer_time`, when present, is `reported`, `not_reported` or `unknown` | `producer_time_invalid` |
| 2 | readings | a history point, or an unbucketed row whose `tier` is `raw`, whose `producer_time` is `not_reported` carries `received_at_ms`, an integer from 1 to 9007199254740991 written without a fraction or an exponent | `receipt_missing` |
| 3 | `action_log` | `record_kind`, when present, is `dispatch`, `contributor` or `contributor_legacy` | `record_kind_invalid` |
| 4 | `action_log` | `record_key` is `null` or a non-empty string | `record_key_invalid` |
| 5 | `action_log` | `contributed_to` is a non-empty string on a `contributor` row, other than the row's own `record_key`, and `null` on a `dispatch` or `contributor_legacy` row | `contributed_to_invalid` |
| 6 | `action_log` | a `contributor` or `contributor_legacy` row has `action_taken` `coalesced`, and a `dispatch` row does not | `action_taken_mismatch` |
| 7 | `action_log` | a `contributor` row has `executed` `false` | `contributor_executed` |

A member whose value is `null` is present. A runtime that implements these
members emits all of them on every row. A reading with no `producer_time`, and an `action_log` row with no
`record_kind`, are from a runtime that predates them: step 1 passes the first
and step 2 does not apply to it, and steps 3 to 7 pass the second. An
`action_log` row that carries `record_kind` and omits `record_key` fails step
4, and one that omits `contributed_to` fails step 5. A reading whose
`producer_time` is `not_reported` and that omits `received_at_ms` fails step
2. A `contributor_legacy` row may carry `executed` `true`: that is what the
earlier release recorded, and step 7 does not apply to it.

**What a consumer counts.** A row is an act when, and only when, its
`record_kind` is `dispatch`, whether or not it executed: `executed` says which.
A `contributor` or `contributor_legacy` row is never counted as an
act or an execution, whatever its `executed`. A row from a runtime that sends
no `record_kind` is read as `contributor_legacy` when its `action_taken` is
`coalesced` and as `dispatch` otherwise, which is the test the runtime applies
to its own earlier rows.

**Resolving a contributor.** `contributed_to` names the `record_key` of the row
that holds the act. That row can be on another page, outside the requested
window or `tier` filter, or lost. A consumer resolves it across a complete
traversal of the pages. The holder is a `dispatch` row: a key the consumer does
not find, one that names a row of another kind, and one that more than one row
of the traversal carries are unresolved, which is not an error in the export
and not an act. Resolution is therefore a fact about a traversal, not about
the store: a holder or a duplicate outside a traversal's window or `tier`
filter cannot be seen, so two traversals with different filters can resolve
one contributor differently.

**Page order.** Rows are ordered by `timestamp` descending, and rows with
equal `timestamp` by the order the runtime stored them, latest first, so that
no two rows share a position. `next_page_token` names a position in that
order, never a count of rows to skip: the next page begins with the first row
stored when it is requested whose position is after the last row returned,
whether or not that row is still stored. A traversal therefore returns every row that is
stored throughout it exactly once, in that order, whatever is stored or
removed while it runs; a row stored or removed during the traversal may be
returned or not. The token is opaque to the gateway, which sends back only a
value the runtime gave it, with the export type, window and `params` it was
given under. The runtime answers a token it did not issue, including an
offset from a runtime that paged by count, or one sent with other filters,
with an error envelope whose `error` is exactly `page_token_invalid`, a value
it gives no other failure; every token it refuses, whatever the reason,
carries that one value. An empty token begins a traversal and is never
refused this way. Each page's position follows the last, so a runtime never
issues one token twice since a traversal last began, and a gateway fails the
export on a token it has already seen since then. A gateway that receives
`page_token_invalid` begins the traversal again once,
with an empty token, and discards the rows it had collected and the tokens it
had seen, since a runtime can issue the same token for the same position
again; a second `page_token_invalid` in one traversal, or any other error,
fails the export, and a failed export yields no rows. The gateway enforces
this. Across an upgrade either side may predate the rule: a gateway that
predates it fails the export on `page_token_invalid` as on any error, and a
runtime that predates it refuses a position token with an error of its own,
on which a gateway that implements the rule fails the export too. Either
costs the one traversal the upgrade interrupts.

**Rollout.** A runtime may emit `record_kind`, `record_key` and
`contributed_to`, and page by position, before its gateways read them: a
gateway that ignores unknown members and returns the token it was given keeps
working, and goes on counting contributor rows as acts until it reads
`record_kind`.

[`vectors/export-rows-v2.json`](vectors/export-rows-v2.json) carries example
readings and `action_log` rows with their verdicts under the checks above and
how a consumer reads each, bucketing across the three bases, page traversals
while rows are stored and removed, and contributor resolution across pages.

## Runtime Export Invariants

- Runtime export requests are read-only. They must never mutate state, change
  policy, trigger actions, or affect Tier C/Tier D paths.
- Runtime owns data semantics. Gateway must not infer runtime SQLite table names
  or read runtime database files directly.
- Export responses must be bounded and paginated.
- Requests must be scoped to the target `device_id`.
- Runtime must return error envelopes for malformed requests rather than leaving
  request/response calls unanswered. Two kinds of request are exceptions and
  are not answered: one Payload Size or the Payload Member Rule refuses, or
  Payload Volume drops, and one whose envelope is not verified while
  `gateway.auth.enabled` is true, under [Export Auth Envelope](#export-auth-envelope).
- A gateway bounds its wait for every export request, and with authentication
  enabled never acts on a response it has not verified, under [Export Auth Envelope](#export-auth-envelope).
- Cloud/provider SDKs do not belong in runtime export or runtime reasoning
  implementations. Gateway/product layers own reporting and cloud reasoning
  providers.

### Enrichment Auth Envelope

Enrichment sits beside an actuation decision: the response is what shapes the
operator's understanding of a Tier C proposal they are about to approve, and the
request carries free text that reaches a model-backed provider at the operator's
cost. Both directions therefore carry the runtime-gateway HMAC envelope whenever
`gateway.auth.enabled: true`, on the same terms as export envelopes, and a
gateway MUST NOT accept an unauthenticated request or publish an
unauthenticated response while authentication is enabled.

| Direction | `message_type` | `device_id` | `request_id` | Signed by |
| --- | --- | --- | --- | --- |
| Request, runtime → gateway | `tier_c_enrichment_request` | the request's `device_id` | the request's `request_id` | runtime, current shared secret |
| Response, gateway → runtime | `tier_c_enrichment_response` | the request's `device_id` | the request's `request_id` | gateway, current shared secret |

The signing input is the one defined under *Heartbeat Auth Envelope*:
`message_type\ndevice_id\nrequest_id\nsigned_at_ms\ncanonical_json`, over the
complete payload with `auth` removed, so the message type, the device, the
proposal's correlation and every field of the payload are bound together. The
`auth` block is the same object as for heartbeats: `scheme`, `signed_at_ms`,
`signature`.

Both payloads are admitted under the [Payload Member Rule](#payload-member-rule) before the envelope is verified.

**Verification precedes every side effect.** A gateway verifies the request
envelope before it invokes the provider, allocates model resources, or
publishes anything — including the correlated error response it would
otherwise publish for a valid-but-rejected request. An unauthenticated request
is dropped and audited; answering it would let any broker client make the
gateway spend provider calls and publish on a device's response topic.

**Two checks that must each hold alone.** The request's `device_id` MUST equal
the topic's device segment, checked independently of signature verification,
and the signature MUST verify under the expected `device_id` and `request_id`.
Neither check may depend on the other having run: a valid signature over a
payload naming another device, or a matching device with a forged signature,
are both refused.

**Freshness and replay** follow
[Envelope Freshness and Replay](#envelope-freshness-and-replay), under a key of
`message_type`, `device_id`, `request_id`, `signed_at_ms` and `signature`.

**Rotation.** `gateway.auth.previous_shared_secret_env` verifies requests and
never signs responses; a response is always signed under the current secret.

**Non-authority survives authentication.** A verified response is still
advisory. It cannot alter tier, action, safe default, approval state or
proposal identity, and a runtime consumer, when built, verifies the response
under `tier_c_enrichment_response` with its own `device_id` and the pending
`request_id`, rejects a `proposal_id` that does not match the proposal in
flight, and leaves the proposal intact and approval-gated when enrichment is
absent, failed or rejected. Broker ACLs remain defence in depth, never the
authentication.

**The unsigned path exists only with authentication disabled.** With
`gateway.auth.enabled: false` the gateway handles enrichment unsigned, as a
development convenience, and publishes unsigned responses. The runtime's
staging and production posture already refuse gateway integration without
authentication for every broker, loopback included, so no hardened deployment
reaches that path.

## Site Health HTTP Projection

> Status: Implemented in `ori-gateway` (`internal/site`, `cmd/ori-gateway/app.go`).

The gateway may expose a local diagnostic HTTP endpoint for site-level health.
This is not a runtime MQTT topic and is not pulled directly by ori-cloud by
default. Future cloud sync should push the same safe projection from the gateway
to ori-cloud rather than requiring ori-cloud to reach into a LAN/loopback address.

- Default listen address: `127.0.0.1:8765`
- Endpoint: `GET /health`
- Default state: disabled
- Response body: JSON `SiteHealth` projection

The projection includes expected runtime device IDs, heartbeat freshness, stale
state, active trigger counts, gateway operational posture, and runtime security
posture fetched via the runtime health export surface. It must not expose
secrets, tokens, MQTT URLs, filesystem paths, phone numbers, provider CIDRs,
raw active trigger names, or remote-command lockout risk maps. Nor does it

Per-node runtime posture may include:

- broker hardening posture (`broker_hardening`)
- state-store encryption posture (`encryption`)
- alert outbox posture (`alert_outbox`)

Per-node evidence state (`evidence`) may also be projected: the last observed
chain head, attestation gap count, availability, and the gateway-side sticky
integrity flags `truncation_suspected` and `head_regressed`. An evidence
integrity problem (truncation, regression, or signing unavailable — including
an omitted evidence block from a node that previously reported evidence)
degrades the node and therefore the site. Gap count alone is informational.
See `evidence/v1.md` for the detection semantics.

When the durable evidence courier is enabled, gateway operational posture MUST
include `evidence_delivery` with its pending count and the booleans `degraded`

## Outbound Evidence Carriage

> Status: Implemented on main, pre-ratification. Runtime production is
> `ori-runtime` (`ori/gateway/evidence_outbound.py`) and gateway
> consumption is `ori-gateway` (`internal/evidence/runtime_ingress.go`);
> the carriage, acknowledgement and custody round-trip has been exercised on a
> loopback broker between the two, not in a deployment.

This is the LAN handoff from a runtime to its durable gateway courier. It does
not define the gateway-to-authority hop; that is `evidence-transport/v2`.

| Property | Value |
| --- | --- |
| Topic | `ori/{device_id}/evidence/outbound` |
| Direction | Runtime -> Gateway |
| QoS | 1 |
| Retained | No |

The payload is:

```json
{
  "device_id": "site-a-edge-01",
  "artifact_type": "delivery_envelope",
  "artifact_b64": "eyJhbmNob3JfZXBvY2hfaWQiOiIuLi4ifQ=="
}
```

`artifact_b64` is RFC 4648 standard Base64 with padding over the complete
canonical wire bytes fixed by `evidence-exchange/v1`. It is byte-literal rather
than a nested object because gateway custody digests the exact signed envelope,
and the authority requires the gateway to forward those same bytes. A receiver
MUST decode once and MUST NOT re-serialise the artifact.

The closed outbound vocabulary is `anchor_registration`, `delivery_envelope`,
and `checkpoint`. Type is named, never inferred by trial verification. The
commissioning authorisation is not carried: the device never holds it, per
`evidence-exchange/v1`, and a gateway MUST refuse a payload naming that type
rather than queue it. `device_id` MUST equal the topic segment
and the decoded artifact's `device_id` before the gateway spends durable queue
capacity.

The carriage payload deliberately has no runtime-gateway HMAC envelope. Every
artifact is already authenticated end to end, so a carriage HMAC would add no
artifact authenticity and could not constrain a gateway that holds that key.
The checkpoint's evidence authenticator remains the device signature; a gateway
secret never substitutes for it. Production transport security relies on
mutually authenticated broker access, per-device publish ACLs, and TLS for
non-loopback brokers. Omitting the HMAC is not permission to use anonymous or
shared MQTT clients.

The carriage payload is admitted under the [Payload Member Rule](#payload-member-rule) before any member of it is
read, and a carriage it refuses gets no acknowledgement.

### Outbound acknowledgement

MQTT PUBACK is not proof the gateway durably stored the bytes. After an atomic
queue commit or an explicit refusal, the gateway publishes:

| Property | Value |
| --- | --- |
| Topic | `ori/{device_id}/evidence/outbound/ack` |
| Direction | Gateway -> Runtime |
| QoS | 1 |
| Retained | No |

```json
{
  "device_id": "site-a-edge-01",
  "artifact_type": "checkpoint",
  "artifact_digest": "sha256:...",
  "outcome": "queued",
  "reason": "",
  "acknowledged_at_ms": 1787000001000,
  "auth": {
    "scheme": "hmac-sha256",
    "signed_at_ms": 1787000001000,
    "signature": "hmac-sha256:..."
  }
}
```

`artifact_digest` is SHA-256 over the decoded exact artifact bytes.
`outcome` is `queued` or `refused`. `reason` is empty for `queued`; the closed
transport refusal vocabulary is `malformed`, `binding_mismatch`, and
`queue_full`. `queue_full` is retriable and MUST NOT be flattened into a drop.

The acknowledgement uses the normal runtime-gateway envelope secret with
`message_type` `evidence_outbound_ack`, empty `request_id`, the target
`device_id`, and the usual canonical payload without `auth`. It is an
authenticated transport decision, not an evidence artifact and not an
authority receipt.

It is admitted under the [Payload Member Rule](#payload-member-rule) before its envelope is verified.

**Two timestamps, two meanings.** `acknowledged_at_ms` is the queue decision
time and repeats: re-admitting the same bytes recovers the same entry and the
same decision. `auth.signed_at_ms` is the gateway's signing time and MUST be
strictly increasing across the acknowledgements one gateway issues — one
millisecond past the previous when the clock has not moved, and durable
across a gateway restart so an unchanged or regressed clock cannot reissue an
earlier value — so two acknowledgements are never byte-identical. A runtime's replay defence keys on
the signature, and a re-acknowledgement that repeated the first would be
refused as a replay rather than applied.

For `delivery_envelope`, a `queued` acknowledgement does not advance runtime
custody state. The gateway also sends the separately authenticated
`custody_acknowledgement` through the inbound route below, and only that artifact
can mark custody. For the other outbound types, `queued` permits the runtime to
retire its handoff copy because the gateway's durable queue now owns retry.

If an acknowledgement is lost, the runtime republishes the same carriage. The
gateway's queue is idempotent by `(artifact_type, artifact_digest)` and returns a
newly signed acknowledgement. A full queue never produces `queued` and never
produces custody.

Persistent MQTT sessions are required on the gateway subscriber. The runtime
retains each artifact until the corresponding authenticated acknowledgement (or
custody artifact for delivery envelopes) is applied; PUBACK alone retires
nothing.

[`vectors/outbound-evidence.json`](vectors/outbound-evidence.json) fixes one
checkpoint carriage, its exact decoded bytes and digest, and the authenticated
queue acknowledgement.

## Inbound Evidence Delivery

> Status: Implemented on main, pre-ratification. Runtime-side routing and
> ingest are `ori-runtime` (`ori/gateway/evidence_inbound.py`) and
> gateway-side publishing is `ori-gateway` (`internal/evidence/return_publisher.go`);
> custody acknowledgements travel through the same durable return queue and are
> retired by the runtime's acknowledgement.

`evidence-exchange/v1` defines seven evidence artifacts, their authenticators and
their exact bytes. It does not define how they travel; that is this contract's
concern. Three of those artifacts move gateway to runtime, and this section
defines their carriage only.

The division is strict. `evidence-exchange/v1` owns what an artifact means and
which bytes are authenticated. `gateway-api` owns the topic, the envelope, the
authentication binding and the routing. Neither may restate the other: a
transport that re-specified artifact fields would become a second source of
truth for bytes that are already fixed.

### Topic and Delivery

| Property  | Value                              |
| --------- | ---------------------------------- |
| Topic     | `ori/{device_id}/evidence/inbound` |
| Direction | Gateway -> Runtime                 |
| QoS       | 1                                  |
| Retained  | No                                 |

QoS 1 rather than 0. A dropped authority artifact is not recoverable by asking
again: the runtime does not know one was sent, and the gateway is a courier
rather than an authority, so it cannot reissue one. Retained messages are
refused because an artifact is a statement about a moment, and a broker
replaying the last one to a reconnecting runtime would present a stale custody
claim as a current one.

Device-scoped, matching the rest of the `ori/{device_id}/...` namespace. The
envelope binds `device_id`, so a shared topic would carry artifacts every
subscriber but one must refuse, and a refusal that is routine stops being a
signal. Production broker ACLs must enforce the same boundary.

### Durability and Retirement

QoS 1 is not sufficient on its own, and a PUBACK is not a retirement signal.

**Sessions MUST be persistent.** The runtime subscribes with a stable client
identifier and a session that survives disconnection — `clean_session: false`
under MQTT 3.1.1, or a non-zero session expiry under MQTT 5. Under a clean
session the broker discards subscriptions on disconnect, so every artifact
published while a runtime is restarting is dropped with nothing recording that
it existed. Brokers bound the retained queue, so a persistent session narrows
the window rather than closing it; it is not the retirement signal.

**Retirement is by acknowledgement, never by PUBACK.** A PUBACK says the broker
accepted the packet. It says nothing about whether the runtime verified the
artifact, applied it, or was even running. A gateway that retired a delivery
receipt on PUBACK could lose it permanently, and a lost receipt is the failure
this whole exchange exists to prevent: the runtime's delivery state would stall
with no record of what was carried.

The runtime therefore publishes an ingest acknowledgement, and the gateway
retires an artifact from its durable queue only on receiving one.

| Property  | Value                                  |
| --------- | -------------------------------------- |
| Topic     | `ori/{device_id}/evidence/inbound/ack`  |
| Direction | Runtime -> Gateway                     |
| QoS       | 1                                      |
| Retained  | No                                     |

```json
{
  "device_id": "site-a-edge-01",
  "artifact_type": "custody_acknowledgement",
  "artifact_digest": "sha256:5f2c...",
  "outcome": "applied",
  "reason": "",
  "acknowledged_at_ms": 1787000001000,
  "auth": { "scheme": "hmac-sha256", "signed_at_ms": 1787000001000, "signature": "hmac-sha256:..." }
}
```

| Field                | Notes                                                                                        |
| -------------------- | -------------------------------------------------------------------------------------------- |
| `artifact_digest`    | SHA-256 over the artifact's canonical bytes, `sha256:` prefixed. Identity without a new field. |
| `outcome`            | `applied` or `refused`.                                                                       |
| `reason`             | `""` when applied; otherwise a reason from the [evidence-exchange/v3](../evidence-exchange/v3.md#receiver-rejection-vocabulary) receiver rejection vocabulary. |
| `acknowledged_at_ms` | When the receiver decided.                                                                     |

Identity is the digest rather than a correlation identifier. The artifacts
already carry their own identity in the bytes the authority signed, and
inventing a transport identifier would create a second name for the same thing
that the two sides could disagree about.

The acknowledgement is signed with the same envelope binding as the inbound
message, under `message_type` `evidence_inbound_ack`.

It is admitted under the [Payload Member Rule](#payload-member-rule) before its envelope is verified.

**An acknowledgement is not an assertion that the artifact was true.** It says
this receiver reached a decision, so the courier need not carry those bytes
again.

`outcome: refused` retires the artifact only when the refusal is a property of
the artifact's own bytes. A refusal that depends on receiver state MUST NOT
retire it, because that state can change without the bytes changing — a release
ships an authority key or adds a version, an operator resolves a retirement, a
later envelope is sealed. There is one exception: a refusal decided against an
immutable, verified record the receiver already holds retires, because that
record never reverts and the same bytes are refused the same way on every
delivery. Two refusals are of that kind, `superseded` and
`restatement_conflict`, as
[gateway-evidence-carriage/v1.md](../gateway-evidence-carriage/v1.md) also
states. This section carries no evidence disposition, so `superseded` never
arises on it, and `restatement_conflict` is the only one of the two it carries.
Every other refusal that depends on receiver state still does not retire. The classification follows from that rule rather than from a list to be
memorised:

| Rejection reason        | Retire? | Determined by                                             |
| ----------------------- | ------- | --------------------------------------------------------- |
| `malformed`             | yes     | The bytes. They are not a well-formed artifact and will not become one. |
| `bad_authenticator`     | yes     | The bytes and the named key. The authenticator does not verify, and resending cannot change that. |
| `binding_mismatch`      | yes     | The bytes. The artifact is about another device, another key, or an artifact this runtime never sealed, or a receipt's range digest does not match the chain rows sealed for its range. |
| `non_contiguous_range`  | yes     | The bytes. The claimed range is not a closed interval.     |
| `unrecognised_version`  | **no**  | Receiver capability. A later release may interpret that version. |
| `wrong_purpose`         | **no**  | Receiver state. The purpose a `key_id` is held under is registry state, not something readable from the artifact. |
| `unknown_key`           | **no**  | Receiver state. A later release may ship the authority key. |
| `retired_key`           | **no**  | Receiver state, resolved by operator action.               |
| `unknown_sequence`      | **no**  | Receiver state. The envelope may not be sealed yet.        |
| `restatement_conflict`  | yes     | The bytes against a final record the runtime holds, verified and immutable, which never reverts. |

For a non-retiring refusal the gateway MUST keep the artifact and MUST NOT
retry it on a fixed short interval; the condition changes on a release or an
operator action, not on elapsed time. Queue bounds still apply, and a gateway
dropping an artifact under pressure MUST record that it did.

The gateway retries a retained artifact when it observes a relevant runtime
state-change signal, including a newly handed-off outbound artifact, or after an
operator restarts the courier following repair. This event-driven retry is not
permission to poll a receiver-state refusal on the ordinary delivery interval.

**An undecided store-fault attempt produces no acknowledgement.** When the
runtime cannot decide or apply a verified artifact because its store failed, it
rolls back and records no decision, as
[evidence-exchange/v3.md](../evidence-exchange/v3.md#store-faults) requires.
Once the rollback completes it releases the broker message, with the MQTT
PUBACK, and publishes no ingest acknowledgement. The courier keeps the
artifact, as it keeps any artifact it holds no acknowledgement for, and
redelivers it in a newly signed envelope. Withholding the PUBACK would bring
back only the identical envelope, which replay protection refuses without an
acknowledgement. Replay protection is unchanged. No rejection reason stands for a store fault: a retiring reason
would retire valid evidence, and a non-retiring one would hold the artifact
until a release or an operator acted. A decided refusal whose record could not
be written is not undecided: it is acknowledged as that refusal, and retires as
that reason's row in the retirement table says.

**A new rejection reason is supported by the gateway first.** A gateway accepts
and retires on a reason before any runtime it serves sends it; a gateway that
does not recognise a reason cannot retire the artifact, and holds it at the
head of that device's lane as a non-retiring refusal. A runtime that adopts
[evidence-exchange/v3.md](../evidence-exchange/v3.md) answers a conflicting
restatement `restatement_conflict` whatever its courier, and never weakens that
refusal into `applied` or into another reason for an older courier, so it is
deployed only beside a gateway that accepts and retires on
`restatement_conflict`.

**Every delivery attempt MUST carry a newly signed envelope.** The artifact
bytes do not change between attempts; the envelope around them does, with a
fresh `signed_at_ms` and the signature that follows from it.

Retransmitting the byte-identical envelope does not work and MUST NOT be
attempted. Envelope replay protection is keyed on the message type, the signing
timestamp and the signature, so a byte-identical retransmission is
indistinguishable from a captured envelope replayed by an attacker. The
receiver refuses it, and because it is a transport refusal it produces no
acknowledgement — so a courier that retried by resending the same bytes would
be refused forever while waiting for an acknowledgement that can never come.
The queue would deadlock on its own retry.

This is why redelivery is the courier's to construct rather than the broker's
to repeat, and it is the reason the acknowledgement is bound to the artifact
digest rather than to anything in the envelope: the artifact keeps its identity
across attempts while every envelope carrying it is distinct.

Receivers MUST NOT relax replay protection to accommodate redelivery. The
protection is what stops a captured custody acknowledgement being replayed to
misreport a stalled queue, and a receiver cannot tell an honest retransmission
from a hostile one.

**A transport refusal produces no acknowledgement.** A message that fails
envelope authentication, or that carries no artifact this contract routes, is
not a statement about an artifact and has no digest to name. Answering one with
a signed acknowledgement would also hand anything that can reach the broker a
signing oracle. Such messages are simply dropped, and the courier redelivers.

### Envelope

```json
{
  "device_id": "site-a-edge-01",
  "artifact_type": "custody_acknowledgement",
  "artifact": {
    "v": 1,
    "device_id": "site-a-edge-01",
    "local_seq": 12,
    "envelope_digest": "sha256:a079...",
    "custody_at_ms": 1787000000900,
    "key_id": "hkdf-sha256:d6aff3c0837ca1a07a5124e30d9612ac",
    "mac": "hmac-sha256:b8bb..."
  },
  "auth": {
    "scheme": "hmac-sha256",
    "signed_at_ms": 1787000000950,
    "signature": "hmac-sha256:..."
  }
}
```

| Field           | Required | Notes                                                                         |
| --------------- | -------: | ----------------------------------------------------------------------------- |
| `device_id`     |      yes | The runtime that produced the evidence. Must match the topic segment.          |
| `artifact_type` |      yes | One of the three names below. Not inferred from the artifact's shape.          |
| `artifact`      |      yes | The `evidence-exchange/v1` artifact, unaltered. This contract fixes no field.  |
| `auth`          | see below | Transport envelope authentication, as for reasoning and export.               |

No `request_id`. Inbound evidence is not a response to anything the runtime
asked for, and correlating it with a request the runtime never made would
invent state on both sides.

### Artifact Type Vocabulary

| `artifact_type`           | `evidence-exchange/v1` artifact | Authenticated under                    |
| ------------------------- | ------------------------------- | -------------------------------------- |
| `custody_acknowledgement` | Custody acknowledgement         | The dedicated custody secret (HMAC)     |
| `delivery_receipt`        | Delivery receipt                | An authority key, purpose `evidence_authority_receipt` |
| `epoch_confirmation`      | Epoch confirmation              | An authority key, purpose `evidence_authority_epoch`   |

The sender names the artifact and the receiver MUST NOT infer the type from the
object's shape. The three have disjoint field sets, so trying each verifier
until one succeeds would work — and it decides what an artifact is from whether
it passed, which is the same reasoning `evidence-exchange/v1` forbids when
selecting a key. An `artifact_type` outside this table MUST be refused without
reaching any verifier.

A receiver MUST refuse an artifact whose type it does not route, rather than
routing it as the nearest match. New types are added here and in
`evidence-exchange`, never by a receiver's leniency.

### Artifact Bytes

The artifact travels as a JSON object, not as an opaque string, and the
obligation is on **values** rather than on bytes.

The gateway MUST forward every field of `artifact` with its value unchanged: it
MUST NOT add, drop, rename, or alter any field, at any depth, and MUST NOT
re-sign or re-MAC anything inside it. Key order and whitespace are explicitly
**not** part of that obligation. A JSON object does not carry them, so a
receiver cannot observe them and a courier cannot preserve them; requiring it
would be an unverifiable rule that implementations would satisfy only by
accident.

The receiver reconstructs the authenticated bytes from the decoded object under
the canonicalisation `evidence-exchange/v1` fixes, which is the same derivation
its published vectors pair with each artifact. Canonicalisation is what makes
key order irrelevant: two encodings carrying the same values reduce to the same
authenticated bytes.

This works only because `evidence-exchange/v1` bounds integers to the D-011
agreement zone and fixes string and Unicode handling, so every value survives a
JSON decode and re-encode unchanged. A future artifact carrying a value outside
that zone could not travel this way, and would need an encoding that preserves
bytes literally.

The gateway holds no evidence-authority key and signs nothing on the evidence
path. The custody acknowledgement it produces is an artifact of its own, not a
modification of one it carries.

### Envelope Auth Envelope

When `gateway.auth.enabled: true`, the gateway signs the payload with the
per-device binding used for reasoning and export, over the canonical string:

```text
message_type\ndevice_id\nrequest_id\nsigned_at_ms\ncanonical_json
```

| Field            | Value                                          |
| ---------------- | ---------------------------------------------- |
| `message_type`   | `"evidence_inbound"`                           |
| `device_id`      | The target device ID                           |
| `request_id`     | `""` — inbound evidence is not correlated       |
| `signed_at_ms`   | String of the `signed_at_ms` integer            |
| `canonical_json` | The payload without `auth`, canonicalised       |

`message_type` is distinct from every other family in this contract so an
envelope authenticating one exchange cannot be verified as another. The
secret is the runtime-gateway envelope secret named by
`gateway.auth.shared_secret_env` — **not** the custody secret, which
authenticates the custody artifact itself and is named by
`gateway.custody.secret_env`.

Freshness and replay follow
[Envelope Freshness and Replay](#envelope-freshness-and-replay).

The message, `artifact` included, is admitted under the [Payload Member Rule](#payload-member-rule) before its
envelope is verified, and a message it refuses is a transport refusal and gets
no acknowledgement.

### Invariants

- **Envelope authentication precedes reading the artifact.** A receiver MUST
  verify the envelope, when authentication is enabled, before dispatching to any
  artifact verifier. Reaching a verifier is what spends the receiver's ingest
  path.
- **The envelope is not the proof.** Each artifact carries its own
  authenticator under key material this transport never sees. A verified
  envelope proves the site gateway sent the message and nothing about whether
  the artifact is true. Arrival grants no authority: only a verified receipt
  advances delivery state, and only a verified epoch confirmation activates an
  epoch.
- **Transport refusals are distinct from artifact rejections.** A receiver MUST
  NOT report a transport failure using `evidence-exchange/v3`'s closed receiver
  rejection vocabulary. `bad_authenticator` means an artifact's own MAC or
  signature did not verify — the shape a forgery takes — and reusing it for an
  unsigned or stale envelope would present ordinary clock skew as a forgery.
- **Rejections are surfaced.** A refused artifact and one that never arrived
  leave identical receiver state, so a receiver MUST record or report each
  refusal with its reason rather than dropping it silently.
- **Delivery is not application.** Publishing to this topic does not entitle
  the gateway to consider an artifact applied, and neither does a PUBACK. The
  runtime's custody, delivery and epoch state changes only on verification, and
  the gateway retires an artifact only on an ingest acknowledgement.
- **An acknowledgement carries no authority.** It reports that a receiver
  decided, not that the artifact was true, and a receiver MUST NOT treat one it
  receives as evidence of anything.

> Status: Implemented in `ori-gateway` under `internal/contracts/testdata`.

Gateway contract fixtures are byte-stable golden JSON files. Tests unmarshal and
marshal request, response, error response, gateway heartbeat, runtime heartbeat,
and enrichment fixtures back to the exact same canonical bytes. Equivalent public
fixtures must be mirrored or referenced from `ori-sdk` when SDK contract coverage
is updated.
