# Evidence Transport v1

> Status: Design target. This contract defines the independently deployed
> evidence-authority ingest reached by a site gateway. It does not identify an
> implementation, endpoint, deployment location, credential custodian, or
> administrative surface.

`evidence-exchange/v1` owns artifact meaning and authenticated bytes.
`gateway-api/v1` owns carriage between a runtime and its LAN gateway. This
contract owns the separate gateway-to-authority hop. The three contracts do not
restate one another.

## Boundary

```text
runtime -- MQTT/gateway-api --> gateway -- HTTPS/evidence-transport --> authority
```

The second hop MUST NOT use the fleet-management client, credentials, storage,
acknowledgement, retry state, health state, or endpoint. A fleet outage does not
disable evidence delivery, and an evidence outage does not disable fleet
management.

The gateway is a blind courier. It does not hold an `evidence_device`,
`commissioning_authority`, `evidence_authority_receipt`, or
`evidence_authority_epoch` key. It authenticates as a transport client only.

## Endpoint

| Property | Value |
| --- | --- |
| Method | `POST` |
| Path | `/v1/evidence/artifacts` |
| Request content type | `application/octet-stream` |
| Response content type | `application/json` |
| Transport | HTTPS with server-certificate verification |

The request body is exactly one complete wire artifact from
`evidence-exchange/v1`. A gateway MUST send the bytes it durably queued and MUST
NOT decode and re-encode them. The authority reconstructs no missing bytes.

`X-Ori-Evidence-Artifact-Type` MUST be one of:

- `anchor_registration`
- `delivery_envelope`
- `checkpoint`

The header names the verifier. The authority MUST NOT infer an artifact type by
trial verification. Naming a type does not make the body valid under that type.

`commissioning_authorization` is not in this vocabulary. The authorisation is
an authority object the device never holds; it reaches the authority through
the organisational commissioning path defined in
[evidence-exchange/v1.md](../evidence-exchange/v1.md), and a courier
submission naming that type is refused as malformed (`400`) before any
verifier is invoked.

## Client authentication

Every request is authenticated with a dedicated symmetric secret whose sole
purpose is `evidence_ingest`. It is distinct from fleet, runtime-gateway
envelope, custody, and authority-signing keys. A valid ingest credential grants
transport admission for its allowlisted devices; it grants no signing or read
authority.

The secret MUST have at least 256 bits of entropy. Its identifier is derived,
never configured:

```text
key_id = "hkdf-sha256:" || lowercase_hex(HKDF-SHA256(
  ikm = secret UTF-8,
  salt = "ori.evidence_ingest_key_id.v1",
  info = "evidence_ingest",
  length = 16
))
```

A service MUST refuse two held secrets deriving the same identifier and MUST
NOT accept a configured identifier alongside a secret.

Required headers:

| Header | Rule |
| --- | --- |
| `X-Ori-Evidence-Client` | Stable opaque client identifier; 1–128 printable ASCII characters. |
| `X-Ori-Evidence-Key-Id` | Derived identifier above, compared byte-exactly. |
| `X-Ori-Evidence-Sent-At-Ms` | Positive D-011 integer. |
| `X-Ori-Evidence-Nonce` | Exactly 32 lowercase hexadecimal characters from 16 random bytes. |
| `X-Ori-Evidence-Artifact-Type` | Closed vocabulary above. |
| `X-Ori-Evidence-Artifact-Digest` | `sha256:` plus 64 lowercase hex over the exact body bytes. |
| `Authorization` | `Ori-Evidence-HMAC hmac-sha256:<64 lowercase hex>`. |

The HMAC input is:

```text
"ori.evidence_ingest_request.v1" || NUL || canonical({
  "artifact_digest": X-Ori-Evidence-Artifact-Digest,
  "artifact_type": X-Ori-Evidence-Artifact-Type,
  "client_id": X-Ori-Evidence-Client,
  "key_id": X-Ori-Evidence-Key-Id,
  "method": "POST",
  "nonce": X-Ori-Evidence-Nonce,
  "path": "/v1/evidence/artifacts",
  "sent_at_ms": integer(X-Ori-Evidence-Sent-At-Ms)
})
```

`canonical` is UTF-8 JSON with keys sorted lexicographically, no insignificant
whitespace, strings encoded without ASCII escaping except where JSON requires,
and integers restricted to the D-011 agreement zone. The signature is
HMAC-SHA256 under the selected ingest secret.

Authentication order is normative:

1. Enforce request-line, header, and body-size limits.
2. Validate header shapes and recompute the body digest.
3. Resolve `(evidence_ingest, key_id)` without trial verification.
4. Verify the HMAC in constant time.
5. Enforce clock skew and atomically reserve `(client_id, key_id, nonce)`.
6. Check that the authenticated client is authorised for the artifact's
   `device_id`.
7. Only then invoke an artifact verifier.

The default maximum clock skew is 300,000 ms. A nonce is retained for at least
twice that window. Reusing a nonce is a transport replay and reaches no artifact
verifier. A client retry uses a fresh timestamp, nonce, and HMAC while keeping
the artifact bytes and digest unchanged.

## Device authorisation and enumeration resistance

Each ingest credential maps to an explicit set of device identities. The
service MUST apply this check after transport authentication and before any
device-specific semantic response. An unknown device and a known device outside
the caller's set produce the same status, body, log code, and timing class. No
read or enumeration endpoint is granted by an ingest credential.

## Response

An authenticated request receives a neutral response:

```json
{
  "v": 1,
  "artifact_digest": "sha256:...",
  "outcome": "accepted",
  "reason": "",
  "retriable": false,
  "authority_artifacts": [
    {
      "artifact_type": "delivery_receipt",
      "artifact_b64": "..."
    }
  ]
}
```

`authority_artifacts` contains zero or more complete canonical wire artifacts,
standard Base64 with padding. Its closed vocabulary is `delivery_receipt` and
`epoch_confirmation`. The gateway MUST decode and durably stage the exact bytes
before retiring its outbound entry.

| HTTP | `outcome` | Meaning | Gateway action |
| ---: | --- | --- | --- |
| 200 | `accepted` | Artifact durably and idempotently applied. | Stage returned artifacts, then retire. |
| 400 | `refused` | Request or artifact bytes are permanently malformed. | Record permanent refusal; do not short-loop. |
| 401 | `refused` | Missing, unknown, stale, replayed, or invalid transport authentication. | Retry only after constructing a fresh authenticated request or repairing credentials. |
| 403 | `refused` | Authenticated client is not authorised for the named device. | Record security refusal; do not enumerate. |
| 409 | `refused` | Valid artifact conflicts with retained authority state. | Quarantine; operator/authority resolution required. |
| 422 | `refused` | Artifact authenticator or semantic contract check failed. | Record the `evidence-exchange/v1` reason; identical retry cannot repair bytes. |
| 429 | `pending` | Explicit rate limit. | Retain and retry after `Retry-After`. |
| 503 | `pending` | Authority temporarily cannot commit durably. | Retain and back off. |

Unauthenticated responses MUST omit `artifact_digest` and
`authority_artifacts`; otherwise the service becomes an artifact-membership
oracle. Authenticated refusals include the submitted digest so the courier can
bind the decision to its queue entry.

For a delivery envelope, `accepted` MUST include a delivery receipt whose
`device_id` matches and whose closed range covers the envelope's `local_seq`.
For an anchor registration applied under a held commissioning authorisation,
`accepted` MUST include the resulting epoch confirmation; for one retained
pending, `accepted` carries none. A response lacking a required artifact is
malformed and MUST NOT retire the request.

Idempotency is by `(artifact_type, artifact_digest)`. Repeating byte-identical
input under a fresh transport nonce returns the same semantic outcome and the
same authority-artifact bytes. In particular, receipt and confirmation
timestamps are the original committed timestamps, not retry time. The one
outcome that legitimately changes is a registration retained pending: once its
authorisation arrives and promotion commits, a byte-identical retry returns
`accepted` with the confirmation that now exists, because the outcome is
decided by the retained pair and not by the request. The confirmation's bytes
are then stable across every later retry.

## Registration resolution

An anchor registration and the commissioning authorisation it names arrive by
different paths — the registration through this transport, the authorisation
through the commissioning path — and may arrive in either order. The authority
durably retains whichever arrives first, keyed by `commissioning_digest`, and
applies neither until both are present and mutually bound as
`evidence-exchange/v1` requires.

A registration received before its authorisation returns `accepted` with no
epoch confirmation: accepted means durably retained, not activated. Arrival of
the matching authorisation, or of the registration when the authorisation is
already held, performs verify, register, promote, provenance write, and
confirmation creation in one transaction. A confirmation MUST NOT exist if
promotion did not commit. A registration that names a digest other than the
authorisation held for its device and epoch, or whose resolved authorisation
names a different device, key or epoch, is refused `422` with reason
`commissioning_digest_mismatch`; a corrected registration under the right reference
is a fresh artifact and is not a retry of the refused bytes.

## Persistence and provenance

The service records, transactionally with each accepted artifact:

- artifact type and digest;
- exact artifact bytes;
- authenticated client identifier and ingest key generation;
- first accepted timestamp from the authority clock;
- independently released service version;
- stable response bytes.

The service version is evidence provenance, not an HTTP banner. Responses,
headers, logs, metrics, and error text MUST NOT disclose implementation identity,
host, endpoint, deployment location, credential material, signing-key custody,
database path, or administrative surface.

## Key custody and deployment

Receipt and epoch keys are purpose-separated and externally provisioned. A
production service MUST refuse software-only authority keys and MUST use a key
provider whose custody survives loss of the service host and is inaccessible
from site and commercial-plane operators. Test/development software keys MUST
emit an explicit warning and MUST NOT be accepted under production posture.

The service is independently versioned and deployed outside every runtime/site
network and outside the commercial control plane. Operators at an evidenced site
have no endpoint, credential, transfer step, or administrative role.

## Limits and failure behaviour

- The service MUST bound header count/size, request body size, concurrent
  requests, per-client rate, and stored replay nonces.
- Backpressure is an explicit `429` or `503`; accepted is returned only after
  durable commit.
- A partially written transaction is absent after restart. A committed response
  survives restart and is returned idempotently.
- Artifact rejection and security refusal are audit events. Unauthenticated or
  malformed submissions never create evidence gaps or device-history state.
- Failure to reach the service leaves gateway evidence pending. Nothing infers
  receipt, confirmation, or healthy evidence delivery from network success.

## Vectors

[`vectors/ingest-auth.json`](vectors/ingest-auth.json) fixes the key derivation,
canonical authentication metadata, exact HMAC preimage and signature. It also
contains negative cases for body substitution, wrong purpose, replay, and a
device-side `commissioning_authorization` submission, which is refused as
malformed before any verifier is invoked.
