# Evidence Transport v2

> Status: maturity `draft`; compatibility `amendable`; adoption: none
> recorded; proof: end-to-end `none`, HIL `none`, production `none`. Record:
> [status/evidence-transport/v2.json](../status/evidence-transport/v2.json).
>
> This contract defines the independently deployed evidence-authority ingest
> reached by a site gateway. It does not identify an implementation, endpoint,
> deployment location, credential custodian, or administrative surface.


`evidence-exchange/v2` owns artifact meaning and authenticated bytes.
`gateway-evidence-carriage/v1` owns evidence carriage between a runtime and its
LAN gateway. This
contract owns the separate gateway-to-authority hop. The three contracts do not
restate one another.

## Boundary

```text
runtime -- MQTT/gateway-evidence-carriage --> gateway -- HTTPS/evidence-transport --> authority
```

The second hop MUST NOT use the fleet-management client, credentials, storage,
acknowledgement, retry state, health state, or endpoint. A fleet outage does not
disable evidence delivery, and an evidence outage does not disable fleet
management.

The gateway is a blind courier. It does not hold an `evidence_device`,
`commissioning_authority`, `evidence_authority_receipt`,
`evidence_authority_epoch`, or `evidence_authority_disposition` key. It
authenticates as a transport client only.

## Endpoint

| Property | Value |
| --- | --- |
| Method | `POST` |
| Path | `/v1/evidence/artifacts` |
| Request content type | `application/octet-stream` |
| Response content type | `application/json` |
| Transport | HTTPS with server-certificate verification |

The request body is exactly one complete wire artifact from
`evidence-exchange/v2`. A gateway MUST send the bytes it durably queued and MUST
NOT decode and re-encode them. The authority reconstructs no missing bytes.

`X-Ori-Evidence-Artifact-Type` MUST be one of:

- `anchor_registration`
- `delivery_envelope`
- `checkpoint`

The header names the verifier. The authority MUST NOT infer an artifact type by
trial verification. Naming a type does not make the body valid under that type.

`commissioning_authorization` is not in this vocabulary. The authorisation is
an authority object the device never holds; it reaches the authority through
[evidence-commissioning-ingest/v1.md](../evidence-commissioning-ingest/v1.md),
and a courier
submission naming that type, or any type outside the vocabulary, is refused
`400 malformed` before any verifier is invoked.

## Client authentication

Every request is authenticated with a dedicated symmetric secret whose sole
purpose is `evidence_ingest`. It is distinct from fleet, runtime-gateway
envelope, custody, and authority-signing keys. A valid ingest credential grants
transport admission for its allowlisted devices; it grants no signing or read
authority.

The secret MUST have at least 256 bits of entropy. Its identifier is derived,
never configured:

```text
key_id = "hkdf-sha256:" || lowercase_hex(HKDF-SHA256(
  ikm = secret UTF-8,
  salt = "ori.evidence_ingest_key_id.v1",
  info = "evidence_ingest",
  length = 16
))
```

A service MUST refuse two held secrets deriving the same identifier and MUST
NOT accept a configured identifier alongside a secret.

**Carriage capability.** The authority's credential registry records, for each
ingest credential, whether the gateway holding it is registered as conforming
to `gateway-evidence-carriage/v1`. The authority emits new response members and
statuses only for ingest credentials registered as conforming to
`gateway-evidence-carriage/v1`. A missing capability means legacy behaviour.
The capability covers the complete response generation: `refused_retained`,
the `retention` and `stop` members, evidence dispositions, `507`,
`409 pending_registration_conflict`, `429 pending_registration_limit`, and the
return artifacts accompanying a refusal or a pending acceptance. It is registry
state the authority holds, set when the credential is registered or changed
there, and never a request header or anything a gateway asserts on a request.

Both are required: capability-gated response shapes, and a gateway upgrade
before the new refusal and stop policy is activated for that credential. The
authority activates that policy for a credential only once its credential
registry records the gateway holding it as conforming. A legacy credential
continues to receive legacy behaviour, not legacy-shaped versions of the new
terminal semantics. The table below is the capability gate on response
shapes, and never licenses activating the new policy for a legacy credential.
Where one of its decisions exists for a request under a credential without the
capability, the authority commits and audits it exactly as for a conforming
credential, and changes only what the response carries:

| Decision | Response to a conforming credential | Response to a legacy credential |
| --- | --- | --- |
| terminal refusal retained | `refused_retained` with `retention` | `refused` at the same status and reason, with no `retention` |
| epoch- or identity-scoped disposition issued | the disposition in `authority_artifacts`, with `stop` | no disposition and no `stop` |
| artifact-scoped disposition issued | the disposition in `authority_artifacts` | no disposition |
| registration retained pending | `200 accepted` with its `retained_pending` disposition | `200 accepted` with no authority artifact |
| terminal refusal beyond an identity's allowance under an identity-scoped disposition | `507 retention_capacity_exhausted` | `503 unavailable` |
| terminal refusal beyond the pre-disposition allowance | `503 retention_capacity_unavailable` | `503 unavailable` |
| pending registration conflict | `409 pending_registration_conflict` | `503 unavailable` |
| pending registration limit | `429 pending_registration_limit` with `Retry-After` | `503 unavailable` |
| return set on `refused` or `refused_retained` | carried | not carried |
| return set on `accepted` | carried | its epoch confirmations only |

A legacy response carries no member, status, reason or artifact type the table
withholds. Deploying every gateway before the authority is the recommended
order, and is not the correctness boundary: the credential's registered
capability is. A gateway re-registered as conforming receives, on its next
request for a device, every return-set artifact the authority holds for that
device, and a retransmission of bytes decided earlier returns the decision
recomputed for the capability the credential then has.
[`vectors/carriage-capability-v2.json`](vectors/carriage-capability-v2.json) fixes
mixed-capability cases, and `scripts/check-evidence-transport-capability-vectors`
holds them to this table.

**Rollout qualification.** During a mixed rollout, while epochs whose signed
capability profile does not declare `checkpoint_fifo_handoff_v1` still
deliver, the authority does not activate the new refusal policy for such a
non-FIFO legacy epoch, whatever the capability of the credential that carries
it. A valid envelope refused as a fork at an already-accepted `local_seq` may
remain identity-scoped under such an epoch.

Required headers:

| Header | Rule |
| --- | --- |
| `X-Ori-Evidence-Client` | Stable opaque client identifier; 1–128 printable ASCII characters. |
| `X-Ori-Evidence-Key-Id` | Derived identifier above, compared byte-exactly. |
| `X-Ori-Evidence-Sent-At-Ms` | Positive D-011 integer. |
| `X-Ori-Evidence-Nonce` | Exactly 32 lowercase hexadecimal characters from 16 random bytes. |
| `X-Ori-Evidence-Artifact-Type` | 1–64 characters from `a`–`z` and `_`; membership in the closed vocabulary above is checked after authentication. |
| `X-Ori-Evidence-Artifact-Digest` | `sha256:` plus 64 lowercase hex over the exact body bytes. |
| `Authorization` | `Ori-Evidence-HMAC hmac-sha256:<64 lowercase hex>`. |

The HMAC input is:

```text
"ori.evidence_ingest_request.v1" || NUL || canonical({
  "artifact_digest": X-Ori-Evidence-Artifact-Digest,
  "artifact_type": X-Ori-Evidence-Artifact-Type,
  "client_id": X-Ori-Evidence-Client,
  "key_id": X-Ori-Evidence-Key-Id,
  "method": "POST",
  "nonce": X-Ori-Evidence-Nonce,
  "path": "/v1/evidence/artifacts",
  "sent_at_ms": integer(X-Ori-Evidence-Sent-At-Ms)
})
```

`canonical` is UTF-8 JSON with keys sorted lexicographically, no insignificant
whitespace, strings encoded without ASCII escaping except where JSON requires,
and integers restricted to the D-011 agreement zone. The signature is
HMAC-SHA256 under the selected ingest secret.

Authentication order is normative:

1. Enforce request-line, header, and body-size limits.
2. Validate header shapes and recompute the body digest.
3. Resolve `(evidence_ingest, key_id)` without trial verification.
4. Verify the HMAC in constant time.
5. Enforce clock skew and atomically reserve `(client_id, key_id, nonce)`.
   A well-formed `X-Ori-Evidence-Artifact-Type` outside the closed vocabulary
   is then refused `400 malformed`, with the submitted digest.
6. Check that the authenticated client is authorised for the artifact's
   `device_id`.
7. Only then invoke an artifact verifier.

The default maximum clock skew is 300,000 ms. A nonce is retained for at least
twice that window. Reusing a nonce is a transport replay and reaches no artifact
verifier. A client retry uses a fresh timestamp, nonce, and HMAC while keeping
the artifact bytes and digest unchanged.

## Device authorisation and enumeration resistance

Each ingest credential maps to an explicit set of device identities. The
service MUST apply this check after transport authentication and before any
device-specific semantic response. An unknown device and a known device outside
the caller's set produce the same status, body, log code, and timing class. No
read or enumeration endpoint is granted by an ingest credential.

## Response

An authenticated request receives a neutral response:

```json
{
  "v": 1,
  "artifact_digest": "sha256:...",
  "outcome": "accepted",
  "reason": "",
  "retriable": false,
  "authority_artifacts": [
    {
      "artifact_type": "delivery_receipt",
      "artifact_b64": "..."
    }
  ]
}
```

`authority_artifacts` contains zero or more complete canonical wire artifacts,
standard Base64 with padding. Its closed vocabulary is `delivery_receipt`,
`epoch_confirmation`, and `evidence_disposition`. The gateway MUST decode and
durably stage the exact bytes of every authority artifact in a response before
acting on the response.

| HTTP | `outcome` | Meaning |
| ---: | --- | --- |
| 200 | `accepted` | Artifact durably and idempotently applied. |
| 400 | `refused` or `refused_retained` | Request or artifact bytes are permanently malformed. |
| 401 | `refused` | Missing, malformed, unknown, stale, replayed, or invalid transport authentication. |
| 403 | `refused` | Authenticated client is not authorised for the named device. |
| 409 | `refused` or `refused_retained` | Valid artifact conflicts with retained authority state. |
| 422 | `refused` or `refused_retained` | The artifact fails an authenticator or semantic check, or the authority cannot yet accept it. |
| 429 | `pending` | Explicit rate limit. |
| 503 | `pending` | Authority temporarily cannot commit durably. |
| 507 | `refused` | The identity is already under an identity-scoped disposition, and the authority cannot retain this terminal refusal within its allowance; no custody is accepted. |

What the gateway does with each is the refusal policy below.

### Retained refusals

`refused_retained` answers an authenticated terminal refusal whose exact bytes
the authority has retained. Before it answers, the authority commits the exact
request body, the retention record below, and the audit record it already
writes, in one transaction; no response is sent before that commit, and if the
commit fails the authority answers `503 unavailable`. The authority answers
every terminal refusal it decides after device authorisation `refused_retained`,
except where *Retention bounds* below refuses it without retention; a terminal
refusal decided before device authorisation is an ordinary `refused`. A legacy
credential receives an ordinary `refused` in place of `refused_retained`, per
*Carriage capability*, and the bytes are retained all the same. `refused_retained` is
admitted only at a reason whose policy row archives; at any other reason, and
at any other status, the response is an unrecognised outcome.

A `refused_retained` response carries `retention`, and no other response
carries it:

```json
{
  "v": 1,
  "artifact_digest": "sha256:...",
  "outcome": "refused_retained",
  "reason": "conflict",
  "retriable": false,
  "authority_artifacts": [],
  "retention": {
    "v": 1,
    "artifact_digest": "sha256:...",
    "artifact_type": "checkpoint",
    "device_id": "site-a-edge-01",
    "anchor_epoch_id": "sha256:...",
    "refusal_status": 409,
    "reason": "conflict",
    "decided_at_ms": 1787000003000,
    "key_id": "hkdf-sha256:...",
    "mac": "hmac-sha256:..."
  }
}
```

| Field | Rule |
| --- | --- |
| `v` | `1`. |
| `artifact_digest` | The submitted digest. |
| `artifact_type` | The submitted `X-Ori-Evidence-Artifact-Type`. |
| `device_id` | The artifact's routing-projection `device_id`. |
| `anchor_epoch_id` | The epoch the refused bytes name, or `""` when the authority could parse none. |
| `refusal_status` | The HTTP status of this response. |
| `reason` | The `reason` of this response. |
| `decided_at_ms` | Authority clock when the refusal was first retained. |
| `key_id` | The request's `X-Ori-Evidence-Key-Id`. |
| `mac` | `hmac-sha256:` plus 64 lowercase hex. |

`mac` is HMAC-SHA256, under the ingest secret named by `key_id`, over
`"ori.evidence_ingest_retention.v1" || NUL || canonical(retention without mac)`.
The retention is authenticated under the transport relationship the request
used and is bound to that purpose by its domain. It is not an artifact and is
never forwarded to the runtime. It asserts custody of forensic bytes, never
acceptance, receipt, contiguous coverage, or confirmation. The authority
recomputes the retention for each request it answers: every field but `key_id`
and `mac` is fixed when the refusal is first retained, and `key_id` and `mac`
are those of the request being answered.

The gateway verifies a retention before acting on it: it carries exactly the
fields in the table above and no other, `v` is `1`, and `anchor_epoch_id` is
`""` or `sha256:` followed by 64 lowercase hexadecimal characters; `mac`
verifies under the secret the request was signed with; `artifact_digest` equals the response's and
the queued entry's digest; `artifact_type` equals the request's header;
`device_id` equals the queued artifact's routing-projection `device_id`;
`refusal_status` equals the HTTP status; and `reason` equals the response's
`reason`. A `refused_retained` whose `retention` is absent or fails any of these
is an unrecognised outcome. Only a verified `refused_retained` lets the gateway
release its byte copy. An ordinary `refused` transfers no custody, and an
unauthenticated or malformed transport response makes no retention claim.

Retention is idempotent by `(artifact_type, artifact_digest)`. A retransmission
of the identical bytes, including after the response was lost before the
gateway received it, returns, for a credential whose carriage capability has
not changed, the same decision, the same `decided_at_ms`, and
the same authority artifacts, without retaining another copy; its response
bytes differ from the first only in the retention's `key_id` and `mac`. A retained refusal
is custody of forensic bytes: it contributes to no receipt and to no contiguous
frontier, later accepted ranges never erase it, and an envelope fork it records
stays a retained security finding.

### Retention bounds

The authority holds retained refusals within a hard per-identity ordinary
allowance, a per-identity registration-repair reservation, and a hard global
bound. It reserves, per identity, the space for that identity's first
identity-scoped refusal, and, within the global bound, the space needed to
commit and deliver dispositions; no identity's retention consumes another
identity's allowance or any reservation. Each bound carries an early-warning
threshold below its limit, audited when crossed. Bounds and counts are durable
and survive restart, and an identical retransmission of a retained refusal
never counts twice.

Every terminally refused anchor registration, whether refused during courier
ingest, commissioning resolution, or cancellation, consumes the
registration-repair reservation rather than the ordinary evidence-refusal
allowance. That reservation MUST be partitioned per identity so one identity
cannot consume another identity's repair capacity.

Before an identity-scoped disposition has been durably issued, inability to
retain a terminal refusal within the applicable ordinary allowance is answered
`503 retention_capacity_unavailable`; the authority accepts no custody, retains
no partial state, and audits `retention_capacity_unavailable`. Capacity exhaustion alone MUST NOT
issue or imply an identity disposition. A legacy credential receives
`503 unavailable` in place of `503 retention_capacity_unavailable`, per
*Carriage capability*.

`507 retention_capacity_exhausted` is permitted only for an identity already
subject to a durably issued identity-scoped disposition. It confines a stopped
identity and is never used to classify an otherwise repairable identity. Once
that disposition has been issued, the identity's reservation for its first
identity-scoped refusal is spent, and a terminal refusal beyond the applicable
allowance is refused `507`, which explicitly accepts no custody. The identity's
allowance is decided before the global capacity. A terminal refusal the global
unreserved capacity cannot hold is answered `503 unavailable`, accepts no
custody, and is audited as authority-wide degraded capacity. No bound is ever
met by evicting earlier evidence.

### Refusal policy

This section is normative for the gateway-to-authority HTTP hop only.
`gateway-evidence-carriage/v1` refusal and retirement semantics do not govern
this hop.

Evidence attests the authority basis of an action after the action; it never
supplies it. So no delivery outcome may discard evidence, and no delivery state
may delay or gate a runtime action. Every rule below keeps the exact queued
bytes until the authority has retained them, and every one of them concerns
only when those bytes are next offered or where they are kept.

| HTTP | Closed reason(s) | Gateway action |
| ---: | --- | --- |
| 400 | `malformed` | Archive once retained; otherwise hold. |
| 401 | `malformed`, `unknown_key`, `bad_authenticator`, `stale`, `replay` | Retain; retry on the next handoff, never on a timer. |
| 403 | `not_authorized` | Retain; retry on the next handoff, never on a timer. |
| 409 | `conflict` | Archive once retained; otherwise hold. |
| 409 | `pending_registration_conflict` | Retain; back off. |
| 422 | `bad_authenticator`, `binding_mismatch`, `commissioning_digest_mismatch` | Archive once retained; otherwise hold. |
| 422 | `unrecognised_version`, `unknown_key` | Retain; retry on the next handoff, never on a timer. |
| 429 | `rate_limited`, `pending_registration_limit` | Retain; retry no earlier than `Retry-After`. |
| 503 | `unavailable`, `retention_capacity_unavailable` | Retain; back off. |
| 507 | `retention_capacity_exhausted` | Hold. |

A refusal is terminal or non-terminal by this closed classification, and by
nothing else:

| Status | Reason | Class |
| --- | --- | --- |
| `400` | `malformed` | terminal |
| `401` | `malformed`, `unknown_key`, `bad_authenticator`, `stale`, `replay` | non-terminal |
| `403` | `not_authorized` | non-terminal |
| `409` | `conflict` | terminal |
| `409` | `pending_registration_conflict` | non-terminal |
| `422` | `bad_authenticator`, `binding_mismatch`, `commissioning_digest_mismatch` | terminal |
| `422` | `unrecognised_version`, `unknown_key` | non-terminal |
| `429` | `rate_limited`, `pending_registration_limit` | non-terminal |
| `503` | `unavailable`, `retention_capacity_unavailable` | non-terminal |
| `507` | `retention_capacity_exhausted` | non-terminal |

A terminal refusal is exactly one whose policy row archives. Non-terminal
refusals stay active in their lane and retry as their rows say. A reason a
status does not admit is classified by neither table; the fail-closed rule below
decides it, and it never archives.

The reasons mean, on this hop:

- `malformed` at `400`: request framing or authenticated artifact bytes fail
  the applicable artifact grammar or canonical form. At `401`: the
  courier-built transport request could not be admitted before authentication,
  because a required authentication header is absent, duplicated, not UTF-8,
  unparsable, or wrong-shaped, or `X-Ori-Evidence-Artifact-Digest` does not
  equal the digest recomputed over the submitted body. A `401 malformed`
  carries no artifact digest and says nothing about the artifact bytes: the
  courier keeps its exact queued bytes and rebuilds every transport header,
  including digest, timestamp, nonce, and HMAC, on the next handoff. Repeated
  `401 malformed` is a visible delivery-availability fault, never evidence of
  invalid artifact bytes and never a reason to discard, rewrite, or immediately
  resend them.
- `unknown_key`: at `401`, the ingest `key_id` is not one the authority holds.
  At `422`, the artifact names a key or epoch the authority does not yet hold
  active; the same bytes are accepted once it is.
- `bad_authenticator`: at `401`, the transport HMAC does not verify. At `422`,
  the artifact's own end-to-end authenticator does not verify under the key it
  names.
- `stale`, `replay`: the transport timestamp is outside the permitted skew, or
  the nonce was already used.
- `not_authorized`: the authenticated client is not authorised for the
  artifact's `device_id`.
- `binding_mismatch`: the artifact's signed bindings contradict one another,
  or it names a key other than the anchor the authority holds for its device and
  epoch. The held anchor does not change, so the same bytes are never accepted.
- `commissioning_digest_mismatch`: an anchor registration's named authorisation
  is recorded revoked or cancelled, or is held and its `device_id`,
  `pubkey_hex`, or `anchor_epoch_id` disagrees with the registration. The
  refusal is final for those exact canonical registration bytes, whatever later
  arrives or is revoked; a corrected registration is a fresh artifact, not a
  retry of the refused bytes. A registration naming an authorisation the
  authority does not hold is accepted pending, not refused.
- `unrecognised_version`: the artifact's declared `v` is not one the authority
  supports. An artifact is a JSON object and MUST contain `v` as a positive
  integer; an absent, zero, negative, fractional, Boolean, string, or otherwise
  non-integer `v` is `400 malformed`. A positive unsupported `v` is
  `422 unrecognised_version`, decided before that version's grammar is
  applied, so an artifact of an unsupported version is never refused
  `malformed` for fields that version introduces; the same bytes may be
  accepted after the authority is upgraded.
- `conflict`: a valid artifact conflicts with retained authority state, such as
  a chain rewind, a checkpoint rollback, or an envelope fork. It is not a report
  of the authority's own storage failure, which is `503 unavailable`.
- `pending_registration_conflict`: an anchor registration names a commissioning
  digest under which the authority retains a different registration pending.
  The refused bytes are not retained by the authority, and the refusal lasts
  only while that registration is pending: once it applies or reaches a
  terminal refusal, the same bytes resolve afresh, per `evidence-exchange/v2`.
- `retention_capacity_unavailable`: `503 retention_capacity_unavailable` means
  the authority cannot retain this terminal refusal within the applicable
  pre-disposition allowance. It accepts no custody and commits no partial
  state. The gateway retains the exact bytes, backs off, and reports
  `authority_retention_capacity_unavailable`. Elapsed time does not itself
  resolve the condition. Exit requires authority-operator action that restores
  or increases durable retention capacity; evidence MUST NOT be evicted to
  create that capacity.
- `rate_limited`, `unavailable`: backpressure. A `429` MUST carry
  `Retry-After`.
- `pending_registration_limit`: the authority already retains its per-device
  bound of pending registrations, per `evidence-exchange/v2`. Its `Retry-After`
  is a minimum retry interval, not a claim that elapsed time repairs the
  condition; the same bytes are accepted once a retained registration resolves.
- `retention_capacity_exhausted`: the identity is already subject to an
  identity-scoped disposition, and the authority cannot retain this terminal
  refusal within the identity's allowance, per *Retention bounds*; it accepts
  no custody. The gateway holds that device's lane with its bytes; no other lane
  or device waits on it. Elapsed time does not repair it; identity replacement,
  per `evidence-exchange/v2`, starts a new lane.

**Courier opacity and version routing.** The courier MUST NOT reject, hold,
retire, or classify an artifact because of its declared `v`. It preserves the
exact bytes and reads only the carriage artifact type and the routing
projection guaranteed by `evidence-exchange/v2`; it does not define
artifact-field meaning. The courier may refuse at admission an artifact whose
routing projection is missing or unparseable. The authority alone decides
artifact-version support.

A **handoff** is a relevant state-change signal: a newly admitted outbound
artifact for the same device; an authenticated admission refused `queue_full`
for a configured device; a `200` retiring an anchor registration for that
device; or courier process start. A `queue_full` handoff admits no bytes,
transfers no custody, and changes no queue ordering; it only makes an existing
eligible head entry for that device runnable once. An **authenticated
admission** is an outbound carriage the gateway receives on a configured
device's own outbound topic under the broker posture the gateway asserts —
per-device authenticated broker principals and per-device publish ACLs — whose
topic, carriage and artifact `device_id` agree, per
`gateway-evidence-carriage/v1`. MQTT 3.1.1 does not expose the publishing
principal to a subscriber, so the gateway cannot observe it; the asserted
posture is what makes the topic stand for the principal. A carriage on any
other topic, or whose `device_id` values disagree, is no admission and signals
nothing. A timer is
never a handoff. A handoff never brings a back-off or a `Retry-After` wait
forward, and a restart restores such a wait rather than ending it.

An **archive** moves a refused artifact, atomically, out of its lane's active
delivery order into the device's durable incident archive, and releases the
gateway's byte copy, before the lane advances. It happens only on a verified
`refused_retained`, and the archive keeps the incident metadata
`gateway-evidence-carriage/v1` projects, never the bytes, which the authority now holds. If the archive cannot
commit, the entry stays at the head of its lane with its bytes and the courier
reports store failure; each process that starts without that archive sends it
once more, and the identical retry returns the same retained decision. An
archived artifact is never re-sent by the courier, is not `state: held`, and
counts toward neither `pending` nor `blocked`.

A **hold** retains the refused artifact, with its bytes, at the head of its
lane's delivery order and sends it no further. A terminal refusal answered with
an ordinary `refused` is held, never archived. Release is not defined by this
revision, and no release may rewrite the held bytes; a corrected artifact is a
new artifact. A hold becomes durable when the gateway persists it. A courier
that stops, or whose hold write fails, between the refusal and the durable hold
sends the artifact once more from each process that starts without that hold,
and holds it when it is refused again.

**Delivery order is per device and lane.** Each device has two lanes: its
anchor registrations, and every other artifact it delivers. Order, retry state,
and holds are kept, persisted, and restored per `device_id` and lane. A hold or
back-off in one lane MUST NOT delay delivery in the other lane or for another
device, so a registration waiting on commissioning never stalls evidence under
an epoch already confirmed. Queue capacity is reserved per device, so one
device cannot exhaust another's. Every device share reserves one
`anchor_registration` slot and the maximum encoded registration-record bytes
exclusively for registration, so an evidence lane waiting on an unconfirmed
epoch can never refuse the registration that would confirm it. Evidence-lane
admission must preserve that reserve. Configuration requires each share to hold
that reserve plus one maximum encoded evidence record: at least two items and
the exact combined encoded-byte bound. The incident archive is outside
active-delivery capacity. A hold and a back-off are persisted beside
their queue record and restored before delivery; a handoff wait has no
persisted timer, because a newly admitted artifact for that device, or a
process start, is itself the handoff. Back-off base and bound are courier
configuration, not wire constants: configuration MUST require
`bound >= base >= delivery_interval`, every back-off wait is at least the
delivery interval, and a `Retry-After` is an additional floor.

The gateway durably admits checkpoints for one device in runtime handoff order
and MUST NOT reorder them within the evidence lane. A repeated checkpoint is
idempotent and retains its original queue position.

**Stopped scopes.** When the gateway learns through the authenticated transport
response that an epoch or identity is stopped, it durably stops the
corresponding queued scope after staging the authority artifact for the
runtime. Stopping retains every queued byte and its order, performs no archive,
and changes no custody the runtime already holds. An admission covered by a
stop enters stopped custody only within the applicable bounds. After the
stopped bytes and their return obligation are durable, the gateway publishes
`queued`. For a `delivery_envelope`, it also durably stages and subsequently
delivers the custody acknowledgement; that acknowledgement is what permits the
runtime to release its local copy. Beyond an applicable bound, the gateway
accepts no custody and publishes neither acknowledgement. The custody
acknowledgement is staged durably before `queued` is published, so `queued`
never leads the runtime to expect proof of custody that is not yet durable. An
entry already in gateway custody when a later verified stop arrives moves to
stopped custody even beyond a bound, because custody cannot be revoked
retrospectively. The bounds are those of `gateway-config/v2`. The
gateway does not originate, widen or clear
the stop. It learns of a stop only from a verified `stop` projection:

```json
"stop": {
  "v": 1,
  "device_id": "site-a-edge-01",
  "scope": "identity",
  "anchor_epoch_id": "sha256:...",
  "artifact_digest": "sha256:...",
  "disposition_digest": "sha256:...",
  "decided_at_ms": 1787000003000,
  "key_id": "hkdf-sha256:...",
  "mac": "hmac-sha256:..."
}
```

| Field | Rule |
| --- | --- |
| `v` | `1`. |
| `device_id` | The request's routing-projection `device_id`. |
| `scope` | `epoch` or `identity`, the scope of the disposition it accompanies. |
| `anchor_epoch_id` | The disposition's epoch; for `identity` scope, the epoch of its triggering artifact. |
| `artifact_digest` | The response's `artifact_digest`: the submitted artifact this response answers. |
| `disposition_digest` | `sha256:` over the wire bytes of an `evidence_disposition` in the same response's `authority_artifacts`. |
| `decided_at_ms` | The disposition's `decided_at_ms`. |
| `key_id` | The request's `X-Ori-Evidence-Key-Id`. |
| `mac` | `hmac-sha256:` plus 64 lowercase hex. |

`mac` is HMAC-SHA256, under the ingest secret named by `key_id`, over
`"ori.evidence_ingest_stop.v1" || NUL || canonical(stop without mac)`, recomputed
for each request as a retention is. The authority attaches `stop` to every
response whose `authority_artifacts` carry an `epoch`- or `identity`-scoped
disposition, and to no other response. The gateway acts on it only when it
carries exactly these fields, `mac` verifies under the secret the request was
signed with, `device_id` is the request's, and `disposition_digest` names an
artifact the same response carries; it never reads the disposition's fields to
decide the stop. `artifact_digest` must also equal the response's, so a
projection replayed from another response binds nothing. The MAC is compared in
constant time. The ingest secret it is computed under is one gateway's own and
is never shared between gateways; that is a deployment obligation no party can
detect, since a shared secret produces valid MACs at every gateway holding it.
Anything else is an unrecognised outcome and stops nothing.

A verified stop projection is an authenticated operational instruction on the
gateway-authority transport relationship. It is sufficient only to place
gateway-custodied bytes into stopped custody. It is not an evidence artifact,
does not prove the authority's decision to the runtime or an auditor, is never
forwarded as one, and cannot change runtime health or action authority. Only
the separately signed evidence disposition can do that at the runtime.

An
`identity` stop covers every queued entry for that device, in both lanes; an
`epoch` stop covers the queued entries whose routing-projection
`anchor_epoch_id` is that epoch. A stopped entry is never sent, archived, or
retired, survives restart in order, and is reported as stopped custody in `gateway-evidence-carriage/v1`. An artifact covered by a verified epoch or identity stop
leaves active delivery ordering and active-delivery capacity only after it is
durably moved to stopped local custody or stopped gateway custody. Its bytes,
digest, original order and stop scope remain durable. A stopped registration
does not occupy the active anchor-registration reservation; that reservation
remains available to an unstopped epoch. The move is between durable states,
never a deletion: an interrupted move leaves the artifact in exactly one of
them, and stopped custody counts toward the stopped-custody bounds of
`gateway-config/v2`, never toward active-delivery capacity. The durable stop
record covers later admissions in its scope: an artifact admitted after a
verified stop covers it enters stopped custody directly and never becomes
sendable, within those bounds, and `gateway-evidence-carriage/v1` refuses it
custody beyond them. Because a stop is applied by
`anchor_epoch_id`, the gateway refuses `malformed` at admission an outbound
anchor registration, delivery envelope or checkpoint whose `anchor_epoch_id` is
missing or outside its routing-projection domain.

A refusal on a handoff row is not evidence that the artifact bytes are
irreparable: at `403` and `422` it is a decision about receiver-held keys,
activation, version support, or authorisation, and at `401` it concerns the
transport request, which is rebuilt. The gateway keeps its exact queued bytes and
constructs a fresh transport request on the next handoff.

A server MUST emit only a reason its status admits. For a status in the table with any other reason, including an empty `reason`, the gateway records `unrecognised`,
retains the queue entry, and fails closed: `400` and `422` hold; `401` and `403`
wait for the next handoff; `409` and `507` hold; `429` and `503` back off, a
`429` waiting no less than any parseable `Retry-After`. The response `retriable`
flag never changes this classification.

Anything else is an **unrecognised** transport outcome: a status outside the
table; a response whose media type, body, required field, digest binding,
outcome, retention, or retry metadata is invalid or absent, including a
`429 rate_limited` or `429 pending_registration_limit` without a positive integer `Retry-After`, a `403`, `409`, `422`, or `507` refusal without its digest, and an unauthenticated response carrying one; a response
carrying an authority artifact the gateway cannot durably stage, or one whose
routing-projection `device_id` is not the request's; and
any `2xx` that is not a clean acceptance, including a `200` that carries a
reason. A reason a table status does not admit is not an unrecognised outcome;
the fail-closed rule above decides it. The gateway retains the exact bytes, records `unrecognised`, reports
delivery degraded, and retries with bounded exponential back-off. It MUST NOT
retire, archive, hold, or immediately resend the entry. Only a `200` meeting
every acceptance requirement below retires an entry, and only a verified
`refused_retained` archives one.

**Size.** An artifact larger than 1,048,576 bytes is outside this hop. A gateway
MUST refuse it at admission, as `malformed`, before acknowledging custody, rather
than queueing bytes that no authority will accept.

The policy is exercised by
[`vectors/refusal-policy-v2.json`](vectors/refusal-policy-v2.json), which
`scripts/check-evidence-transport-refusal-policy-vectors` holds to this section.

An authenticated artifact or security refusal that the authority is required to
audit MUST be durably recorded before it is returned; if that record cannot
commit, the authority answers `503 unavailable`. An unauthenticated malformed
transport submission creates no device-history or gap state.

Unauthenticated responses MUST omit `artifact_digest`, `authority_artifacts`,
`retention`, and `stop`; otherwise the service becomes an artifact-membership oracle.
Authenticated refusals include the submitted digest so the courier can bind the
decision to its queue entry.

For a delivery envelope, `accepted` MUST include a delivery receipt whose
`device_id` matches and whose closed range covers the envelope's `local_seq`.
For an anchor registration applied under a held commissioning authorisation,
`accepted` MUST include the resulting epoch confirmation; for one retained
pending, `accepted` to a conforming credential MUST include the
`retained_pending` disposition bound to it, and `accepted` to a legacy
credential carries none, per *Carriage capability*. A pending `accepted` is a successful delivery and retires the courier's
entry; it is not a confirmation, and the runtime acts on the disposition as
`evidence-exchange/v2` requires. The courier tells the two apart from the
response's declared authority-artifact types; when forwarding, it reads only
the stable routing projection, not semantic artifact fields. A response lacking
a required artifact is malformed and MUST NOT retire the request.

**Return set.** The authority keeps, per device, a durable return set: every
epoch confirmation or evidence disposition it committed for that device outside
the response to the request that decided it — an epoch confirmation promoted on
the commissioning path for a registration answered `retained_pending`, and a
terminal disposition for a registration refused or cancelled there. It carries
the device's whole return set, in `authority_artifacts`, on every authenticated
response for that device whose `outcome` is `accepted`, `refused`, or
`refused_retained` and that passed device authorisation, to a conforming
credential, and to a legacy credential only as *Carriage capability* permits. A return-set entry
holds at most one artifact per registration digest and is kept for the life of
the identity. The courier treats every disposition alike, whatever its scope or
value: it stages the exact bytes and forwards them to the runtime on the inbound
route of `gateway-evidence-carriage/v1`, and its own queue actions follow only from the HTTP
outcome, a verified retention, and a verified `stop` projection. An
`artifact`-scoped disposition therefore retires nothing the retention has not,
and no disposition stops, holds, or widens delivery at the gateway except
through a verified `stop` projection.

**Staging is idempotent by digest.** The gateway keeps, per device and for the
life of the identity, the digest of every authority artifact it has staged,
including those its return queue has since retired on the runtime's
acknowledgement. An artifact whose digest it already holds is neither staged
nor forwarded again, and its repetition on later responses, as the return set
repeats, is not a staging failure. A response carrying an artifact it cannot
durably stage is an unrecognised outcome for that attempt only: the queue entry
is retained and backed off, the artifacts already staged stay staged, and the
next attempt stages what remains.

Idempotency is by `(artifact_type, artifact_digest)`. Repeating byte-identical
input under a fresh transport nonce returns the same semantic outcome and the
same authority-artifact bytes, except in these cases, where the outcome may
change because the receiver's retained state or capacity changed:

- a registration retained pending returns `accepted` with its epoch
  confirmation once the authorisation arrives and promotion commits;
- a `422` receiver-state refusal (`unknown_key`, `unrecognised_version`) returns
  `accepted` once the key or epoch is active, or the version is supported;
- a `401` or `403` refusal changes once credentials or authorisation are
  repaired;
- a `429` or `503` outcome changes once capacity returns;
- a `507` would change only if the authority's retention capacity for that
  identity changed; the courier holds the entry and never re-sends it, because
  this revision defines no release of a hold, so no retry observes that change;
- a retained pending registration whose named authorisation later arrives but
  disagrees, or whose commissioning digest is cancelled, changes from `accepted`
  with its `retained_pending` disposition to `422 commissioning_digest_mismatch`
  answered `refused_retained`;
- a `409 pending_registration_conflict` changes, once the registration retained
  pending under its commissioning digest has applied or reached a terminal
  refusal, to whatever *Resolution at the authority* in `evidence-exchange/v2`
  then gives these bytes;
- the return set carried on any response grows as the authority commits to it.

Receipt, confirmation, disposition, and retention timestamps are the original
committed timestamps, not retry time. Once accepted or retained, returned
authority-artifact bytes remain stable across every later retry, including
after the commissioning authorisation a registration named is revoked.

## Registration resolution

An anchor registration and the commissioning authorisation it names arrive by
different paths — the registration through this transport, the authorisation
through the commissioning path — and may arrive in either order. The authority
durably retains whichever arrives first, keyed by `commissioning_digest`, and
resolves the registration exactly as *Resolution at the authority* in
`evidence-exchange/v2` decides; this section restates none of its outcomes and
adds only how they are carried on this hop.

A registration retained pending returns `accepted` with its `retained_pending`
disposition and no epoch confirmation: accepted means durably retained, not
activated. Arrival of the matching
authorisation, or of the registration when the authorisation is already held,
performs verify, register, promote, provenance write, and confirmation creation
in one transaction. A confirmation MUST NOT exist if promotion did not commit.
A refusal `commissioning_digest_mismatch` is terminal: retained, answered
`refused_retained`, and archived; a corrected registration under the right
reference is a fresh artifact and is not a retry of the refused bytes. A
`409 pending_registration_conflict` is retained and backed off in the device's
registration lane.

**Registration reservation.** A deployment claiming production evidence
security MUST establish each of these; its gateway posture check MUST assert
the first three, the commissioning ceremony MUST enforce the fourth, and the
evidence authority and the courier MUST implement the fifth:

- every evidence device publishes through its own authenticated broker
  principal, with no anonymous, shared, or wildcard publisher;
- that principal can publish only to its own device's outbound evidence topic,
  shown by a cross-device publish attempt that the broker refuses;
- a carriage whose topic, carriage, and artifact `device_id` disagree creates no
  queue entry and no custody;
- the evidence authority durably holds an authorisation, received through the
  commissioning path, before its reference is installed at the device; and
- a registration refused `409 pending_registration_conflict` is audited by the
  authority and reported by the courier, is never confirmed, and delays no lane
  but its own.

A deployment that has not established them makes no production claim for
evidence registration.

## Persistence and provenance

The service records, transactionally with each accepted artifact and with each
retained refusal:

- artifact type and digest;
- exact artifact bytes;
- authenticated client identifier and ingest key generation;
- first accepted or retained timestamp from the authority clock;
- for a retained refusal, its status, reason, and any disposition issued;
- independently released service version;
- stable response bytes, from which a retained refusal's response differs on a
  later request only in the retention's `key_id` and `mac`.

Every retained refusal stays individually retrievable by digest, and the
authority's durable audit record enumerates every retained digest per device.
No revision of `evidence-audit/v1` yet defines a query for them, so this is a
retention obligation, not a read surface.

The service version is evidence provenance, not an HTTP banner. Responses,
headers, logs, metrics, and error text MUST NOT disclose implementation identity,
host, endpoint, deployment location, credential material, signing-key custody,
database path, or administrative surface.

## Key custody and deployment

Receipt, epoch, and disposition keys are purpose-separated and externally
provisioned. A production service MUST refuse software-only authority keys and
MUST use a key provider whose custody survives loss of the service host and is
inaccessible from site and commercial-plane operators. Test/development
software keys MUST emit an explicit warning and MUST NOT be accepted under
production posture.

The service is independently versioned and deployed outside every runtime/site
network and outside the commercial control plane. Operators at an evidenced site
have no endpoint, credential, transfer step, or administrative role.

## Limits and failure behaviour

- The service MUST bound header count/size, request body size, concurrent
  requests, per-client rate, and stored replay nonces.
- Backpressure is an explicit `429` or `503`; accepted is returned only after
  durable commit, and `refused_retained` only after the retention commit.
- A partially written transaction is absent after restart. A committed response
  survives restart and is returned idempotently.
- Artifact rejection and security refusal are audit events. Unauthenticated or
  malformed submissions never create evidence gaps or device-history state.
- Failure to reach the service leaves gateway evidence pending. Nothing infers
  receipt, confirmation, retention, or healthy evidence delivery from network
  success.
- A tracked limitation of this revision: a `200 accepted` for a checkpoint, or
  for an anchor registration, carries nothing the gateway can verify, since it
  holds no authority key, so the gateway releases its copy on the
  TLS-authenticated response alone. A
  TLS-authenticated `200 accepted` is authority trust, not signed retention
  proof, and MUST NOT be described as cryptographic custody evidence.

## Vectors

device-side `commissioning_authorization` submission, and an artifact type
outside the vocabulary; the last two are refused `400 malformed` before any
verifier is invoked.

[`vectors/refusal-policy-v2.json`](vectors/refusal-policy-v2.json) fixes the gateway

a status does not admit, and the unrecognised-outcome rule, including every
retention that fails to verify or bind, as single responses
and as step-by-step courier sequences, including per-device and per-lane
scope, an archive that cannot commit, and the
per-process bound on a hold that is not yet durable.
`scripts/check-evidence-transport-refusal-policy-vectors` derives the policy
from this contract's text; `--mutations` proves it refuses both a corrupted
corpus and a weakened contract.

[`vectors/retention-v2.json`](vectors/retention-v2.json) fixes the authority side:

per-identity registration-repair reservation and the global bound with their
reservations at the exact boundary and across restart, `503` with

`scripts/check-evidence-transport-retention-vectors` derives those rules from

[`vectors/handoff-order-v2.json`](vectors/handoff-order-v2.json) fixes checkpoint

widened and misbound projections that stop nothing, and which queued entries an
`identity` or `epoch` stop covers, retained in order and never archived, a

`scripts/check-evidence-handoff-vectors` holds the corpus to this contract and
