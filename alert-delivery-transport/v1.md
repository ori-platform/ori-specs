# Alert Delivery Transport Contract v1

> Status: maturity `draft`; compatibility `amendable`; adoption: none
> recorded; proof: end-to-end `none`, HIL `none`, production `none`. Record:
> [status/alert-delivery-transport/v1.json](../status/alert-delivery-transport/v1.json).

[alert-delivery/v1.md](../alert-delivery/v1.md) has a gateway take custody of
each runtime-signed alert-delivery record and carry it to the report receiver.
This contract defines **that last hop**: the endpoint, the gateway's credential,
the receiver's responses, and the rule that decides when the gateway may retire
a record. Its one rule above every other: **a gateway retires a record only on
a response that says the receiver holds it, bound to that record's digest.**

## Boundary

```text
runtime -- MQTT/alert-delivery/v1 --> gateway -- HTTPS/this contract --> receiver
```

The hop uses none of the evidence hop's client, credentials, storage, queue,
retry state, health state or endpoint
([evidence-transport/v1.md](../evidence-transport/v1.md)), and none of the fleet
or weekly-reporting ones (gateway-api/v2.md *Gateway Weekly Reporting*). An
outage of any of them does not stop this hop, and an outage of this hop stops
none of them.

The gateway is a blind courier here as on the LAN: it holds no runtime key and
verifies no record. The receiver verifies every record under
alert-delivery/v1.md *Verifying*.

## Endpoint

| Property | Value |
| --- | --- |
| Method | `POST` |
| Path | `/v1/runtime/alert-delivery-records` |
| Request content type | `application/octet-stream` |
| Response content type | `application/json` |
| Transport | HTTPS with server-certificate verification |
| Body | Exactly one record's exact bytes, at most 4096 bytes |

A gateway sends the bytes it holds in custody, and never decodes and
re-encodes them. One request carries one record.

## Client authentication

Every request is authenticated with a dedicated symmetric secret whose sole
purpose is `alert_delivery_forward`. It is distinct from every other secret the
gateway holds: the evidence-ingest secret, the runtime–gateway envelope secret,
and every fleet and reporting credential. It grants transport admission for the
devices its gateway may forward for, and no signing, read or enrolment
authority.

The secret has at least 256 bits of entropy. Its identifier is derived, never
configured:

```text
key_id = "hkdf-sha256:" || lowercase_hex(HKDF-SHA256(
  ikm = secret UTF-8,
  salt = "ori.alert_delivery_forward_key_id.v1",
  info = "alert_delivery_forward",
  length = 16
))
```

A receiver refuses to hold two secrets that derive the same identifier.

Required headers:

| Header | Rule |
| --- | --- |
| `X-Ori-Alert-Client` | The gateway's stable opaque client identifier; 1 to 128 printable ASCII characters. |
| `X-Ori-Alert-Key-Id` | The derived identifier above, compared byte for byte. |
| `X-Ori-Alert-Sent-At-Ms` | A positive integer, the gateway's wall clock at sending. |
| `X-Ori-Alert-Nonce` | Exactly 32 lowercase hexadecimal characters from 16 random bytes. |
| `X-Ori-Alert-Record-Digest` | `sha256:` and 64 lowercase hexadecimal characters, over the exact body bytes. |
| `Authorization` | `Ori-Alert-HMAC hmac-sha256:` and 64 lowercase hexadecimal characters. |

The HMAC input is the ASCII bytes `ori.alert_delivery_forward_request.v1`, one
NUL byte, then the canonical bytes, under
[gateway-mqtt-canonical-json/v1.md](../gateway-mqtt-canonical-json/v1.md), of:

```json
{
  "client_id": "<X-Ori-Alert-Client>",
  "key_id": "<X-Ori-Alert-Key-Id>",
  "method": "POST",
  "nonce": "<X-Ori-Alert-Nonce>",
  "path": "/v1/runtime/alert-delivery-records",
  "record_digest": "<X-Ori-Alert-Record-Digest>",
  "sent_at_ms": 0
}
```

`sent_at_ms` is the integer the header carries. The signature is HMAC-SHA256
under the selected secret.

**Order.** A receiver judges each request in this order, and the first failure
is the answer:

1. Request-line, header and body-size limits.
2. Header forms, and the body digest recomputed and compared with
   `X-Ori-Alert-Record-Digest`.
3. The secret selected by `key_id`, never by trial verification.
4. The HMAC, compared in constant time.
5. `sent_at_ms` within 300000 ms of the receiver's clock, and
   `(client_id, key_id, nonce)` reserved atomically. A nonce is kept for at
   least twice that window, and a reused one is a transport replay.
6. The authenticated client is permitted to forward for the record's
   `device_id`.
7. Only then, alert-delivery/v1.md *Verifying*, from its check 2.

A retry carries the same body and digest, under a fresh `sent_at_ms`, nonce and
HMAC.

**Enumeration resistance.** An unknown device and a known device outside the
client's set get the same status, body, log code and timing class. The
credential grants no read or enumeration endpoint.

## Response

An authenticated request gets:

```json
{
  "outcome": "stored",
  "reason": "",
  "record_digest": "sha256:...",
  "v": 1
}
```

| HTTP | `outcome` | Meaning | Gateway action |
| ---: | --- | --- | --- |
| 200 | `stored` | The receiver verified the record and holds it durably, including a record it holds as `conflict` beside another. | Retire. |
| 200 | `duplicate` | The receiver already holds these exact bytes durably. | Retire. |
| 200 | `superseded` | A verified tally whose count is below the one held: `lower_count`. The receiver holds the greater, and has counted this one. | Retire. |
| 202 | `retry_later` | A reason the receiver's state may cure: `key_not_enrolled`, `not_owned`. | Keep, and retry with long back-off. |
| 400 | `refused` | The request or the bytes are malformed. | Reject (below). |
| 401 | `refused` | Transport authentication failed: missing, unknown, stale, replayed or invalid. | Keep; repair the credential and back off. Never retire. |
| 403 | `refused` | The authenticated client may not forward for this device. | Keep; report it in site health. Never retire. |
| 422 | `refused` | The record fails verification for a reason no later state cures: `signature_invalid`, `transition_refused`, `class_refused`, `detail_refused`. | Reject (below). |
| 429, 503 | `retry_later` | Rate limit, or the receiver cannot commit durably. | Keep; retry after `Retry-After` or with back-off. |

**Bound to the digest.** An authenticated response names the request's
`record_digest`, and a gateway acts on it only when it is that digest. A
response that names another digest, does not parse, names an outcome or an HTTP
status this table does not pair, or never arrives retires nothing, and the
gateway keeps the record and retries. Unauthenticated responses omit
`record_digest`, so the receiver is no membership oracle.

**Rejection is audited, never silent.** A gateway rejects a record only on a
400 or 422 response bound to its digest. It moves the record from custody to a
bounded rejected store, with the response and the time, keeps it there for at
least 30 days, reports the count by reason in its site health, and only then
may delete it. A 401 or a 403 never rejects a record: credential and permission
faults are repaired, and the records they hold back wait.

`stored` and `duplicate` are idempotent: the same bytes under a fresh request
get the same outcome, and never a different one.

## Bounds

- **Receiver.** It bounds header count and size, body size, concurrent
  requests, per-client rate and held nonces, and answers backpressure with an
  explicit 429 or 503. It returns `stored` only after a durable commit; a
  commit lost to a restart is absent, and a committed one is answered again
  idempotently.
- **Gateway.** It keeps a custody share per device, so one device cannot exhaust
  another's, and sends at most 4 requests at a time. Its back-off doubles from 1
  s to at most 300 s, and to at most 3600 s for `retry_later` with a reason. It
  reports its backlog, its oldest record's age and every rejection in its site
  health.
- **Nothing infers delivery.** A network success, a TLS handshake, or an HTTP
  status the table does not pair with a matching digest never means the
  receiver holds a record.

## Representable and enforced

Nothing here is enforced by any production consumer. The gateway is the
enforcing repository for sending, response validation, retry and custody
retirement; the product's report receiver for the endpoint, its credential
scopes, durable idempotency and the response vocabulary.

## Configuration

A gateway's forwarding keys are gateway-config/v2.md `alert_delivery`
`endpoint_env`, `client_id_env` and `secret_env`, under that section's load
rules. The request path is appended to the receiver's base URL that
`endpoint_env` names.

## Vectors

[vectors/alert-delivery-transport-v1.json](vectors/alert-delivery-transport-v1.json)
holds:

- **`key_ids`**: test secrets, each the SHA-256 of the ASCII label
  `ori alert-delivery-transport/v1 <name> test secret` written as 64 lowercase
  hexadecimal characters, with the `key_id` this contract derives from it.
  They are test secrets only.
- **`requests`**: requests as exact header sets and bodies, each with its HMAC
  input and authorisation header and the receiver's verdict at checks 1 to 6 of
  *Order*: accepted, or refused with its HTTP status. One case for each check,
  refused for it alone, among them a reused nonce, a body digest that does not
  match, a skew one past the bound and one at it, and an unknown and an
  unauthorised device answered alike.
- **`responses`**: a response, with its HTTP status and the digest of the
  request it answers, and the gateway's action: `retire`, `keep` or `reject`.
  One case for each row of the table, and for each way a response retires
  nothing: another digest, a body that does not parse, an outcome and a status
  the table does not pair, and an unauthenticated response.
- **`config`**: gateway-config/v2 `alert_delivery` cases for load rules 6 to 8,
  and for rule 1 on the forwarding keys, and accepted cases.

It is reproduced byte for byte by
`scripts/generate-alert-delivery-transport-vectors-v1`.
`scripts/check-alert-delivery-transport-vectors-v1`, which shares no code with
it, holds the corpus to this text, and with `--mutations` shows that each of
its checks fails on a corpus or text altered to break that check.

These rules have no corpus case: the receiver's durable commit and idempotent
replies across a restart, nonce retention, rate limits, the gateway's back-off,
concurrency and per-device share, the rejected store's retention, and the
site-health reports.
