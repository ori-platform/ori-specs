# Device Policy Contract v1

> Status: Implemented baseline in `ori-runtime`
> Source of truth: `ori/policy/device_policy.py`, `ori/policy/remote_fetch.py`, `ori/runtime.py`

This contract defines remote DevicePolicy payload semantics and runtime verification requirements.

## Remote Fetch Preconditions

Runtime enforces:

- `device_policy.url` must start with `https://`
- request includes bearer auth token (`device_policy.auth_token`)
- public key is configured (`device_policy.public_key_b64`)
- timeout and clock skew config sanity

## Policy Payload Fields

| Field | Type | Required |
|---|---|---|
| `tier` | `string` | Yes |
| `relay_b_enabled` | `bool` | Yes |
| `relay_c_enabled` | `bool` | Yes |
| `cloud_llm_enabled` | `bool` | Yes |
| `valid_until` | `int` (unix seconds) | Yes |
| `policy_version` | `int` | Yes |
| `issued_at` | `int` (unix seconds) | Yes |
| `signature` | `string` | Yes |
| `timestamp` | `int` (unix seconds) | Yes |
| `entitlement_status` | `string` | No |
| `grace_until` | `int | null` (unix seconds) | No |
| `alert_sms_monthly_cap` | `int | null` | No |
| `alert_whatsapp_monthly_cap` | `int | null` | No |

Optional fields are additive for v1 compatibility. Older runtimes ignore them.
Newer runtimes use them to enforce commercial messaging policy locally while
preserving the action-tier safety invariants below.

## Verification Rules

Runtime rejects payloads unless all checks pass:

- payload is valid JSON object
- required fields are present and typed
- Ed25519 signature verification succeeds
- payload timestamp is within allowed skew window
- `policy_version` is not lower than current in-memory policy version

## Rejection Behavior

On verification failure:

- payload is rejected
- current in-memory policy is retained
- warning + audit trail are emitted

Runtime must not fail open by applying unverified payloads.

## Tier Semantics

`DevicePolicy.permits_action(action_tier)` semantics:

- Tier `A`: always permitted
- Tier `D`: always permitted (safety bypass invariant)
- Tier `B`: controlled by policy + runtime relay gates
- Tier `C`: controlled by policy + runtime relay gates

Tier D bypass is mandatory safety behavior and not a billing control.

## External Alert Cap Semantics

`alert_sms_monthly_cap` and `alert_whatsapp_monthly_cap` control paid external
message transport, not local reasoning authority.

- absent or `null`: unlimited for backward compatibility
- `-1`: unlimited by explicit policy
- `0`: no non-emergency delivery for the channel in the current month
- `> 0`: runtime may deliver non-emergency messages until the channel's
  monthly count reaches the cap
- `< -1`: invalid; producers must not emit it and consumers must reject the
  policy rather than interpreting it as unlimited

Tier D emergency notification must bypass these caps. Safety messages are not a
commercial feature. Tier A local reasoning, logging, and on-device audit remain
available even when SMS/WhatsApp transport is capped.
