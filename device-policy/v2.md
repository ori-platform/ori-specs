# Device Policy Contract v2

> Status: maturity `draft`; compatibility `frozen` by shipment (runtime
> `ee242ed`, 2026-07-24; release v2.1.0), baseline audit `complete`; adoption:
> consumer (runtime) `shipped` in v2.1.0, `unassessed`; proof: end-to-end
> `none`, HIL `none`, production `none`. Record:
> [status/device-policy/v2.json](../status/device-policy/v2.json).

This contract defines remote DevicePolicy payload semantics and runtime verification requirements.

## Remote Fetch Preconditions

Runtime enforces:

- `device_policy.url` must start with `https://`
- request includes bearer auth token (`device_policy.auth_token`)
- public key is configured (`device_policy.public_key_b64`)
- timeout and clock skew config sanity

## Policy Payload Fields

| Field | Type | Required |
|---|---|---|
| `tier` | `string` | Yes |
| `relay_b_enabled` | `bool` | Yes |
| `relay_c_enabled` | `bool` | Yes |
| `cloud_llm_enabled` | `bool` | Yes |
| `valid_until` | `int` (unix seconds) | Yes |
| `policy_version` | `int` | Yes |
| `issued_at` | `int` (unix seconds) | Yes |
| `signature` | `string` | Yes |
| `timestamp` | `int` (unix seconds) | Yes |
| `entitlement_status` | `string` | No |
| `grace_until` | `int | null` (unix seconds) | No |
| `alert_sms_monthly_cap` | `int | null` | No |
| `alert_whatsapp_monthly_cap` | `int | null` | No |
| `alerts` | `object` | No |

Optional fields are additive for v1 compatibility. Older runtimes ignore them.
Newer runtimes use them to enforce commercial messaging policy locally while
preserving the action-tier safety invariants below.

## Verification Rules

Runtime rejects payloads unless all checks pass:

- payload is valid JSON object
- required fields are present and typed
- Ed25519 signature verification succeeds
- payload timestamp is within allowed skew window
- `policy_version` is not lower than current in-memory policy version

## Rejection Behavior

On verification failure:

- payload is rejected
- current in-memory policy is retained
- warning + audit trail are emitted

Runtime must not fail open by applying unverified payloads.

## Tier Semantics

`DevicePolicy.permits_action(action_tier)` semantics:

- Tier `A`: always permitted
- Tier `D`: always permitted (safety bypass invariant)
- Tier `B`: controlled by policy + runtime relay gates
- Tier `C`: controlled by policy + runtime relay gates

Tier D bypass is mandatory safety behavior and not a billing control.

## External Alert Cap Semantics

`alert_sms_monthly_cap` and `alert_whatsapp_monthly_cap` control paid external
message transport, not local reasoning authority.

- absent or `null`: unlimited for backward compatibility
- `-1`: unlimited by explicit policy
- `0`: no non-emergency delivery for the channel in the current month
- `> 0`: runtime may deliver non-emergency messages until the channel's
  monthly count reaches the cap
- `< -1`: invalid; producers must not emit it and consumers must reject the
  policy rather than interpreting it as unlimited

Tier D emergency notification must bypass these caps. Safety messages are not a
commercial feature. Tier A local reasoning, logging, and on-device audit remain
available even when SMS/WhatsApp transport is capped.

## Alert Class Preferences

`alerts` carries a customer's choice to switch off optional notices, one member
per alert class. It decides whether the runtime sends an optional external
notice. It never decides a physical action, the record of one, or a safety
notice, and it never gates, delays or suppresses an approved Tier C action or
any Tier D execution.

Each class below is defined by what its notice would tell the customer. A
definition is not a claim that any installed runtime detects that condition.

| Class | Customer meaning |
|---|---|
| `generator_running_too_long` | The generator has kept running long after grid power returned |
| `unusual_consumption_spike` | Consumption is well above the site's usual level |
| `battery_underperforming` | The battery delivers less than expected for the charge it received |
| `grid_power_restored` | Grid power has returned after an outage |

A consumer reads `alerts` from a verified payload only, and applies these
rules:

- **Only an explicit `false` withholds a notice.** A known class whose value is
  the JSON boolean `false`, in a policy whose `valid_until` has not passed,
  withholds that class's optional notice.
- **Everything else leaves the notice on.** An absent `alerts`, an `alerts`
  that is not an object, an absent class, and a value that is not a JSON
  boolean all mean enabled. So does an expired policy.
- **No `alerts` member rejects the policy.** A consumer ignores a class name
  it does not know, and a member a producer must not emit. Neither invalidates
  the policy, and neither withholds anything.
- **Safety notices are never a class.** No Tier D notice and no
  `protection_degraded` notice is withheld by `alerts`, and a producer does not
  emit either as a member. A consumer does not consult `alerts` for a Tier D
  act or its notification, and the rule holds when a producer emits one anyway.
- **A class names a first-party trigger.** A notice belongs to a class only
  when the runtime binds the first-party skill and trigger that raised it to
  that class. A community skill's trigger never belongs to a class, whatever
  its name. Which trigger each class binds to, and what it detects, are the
  runtime's, not this contract's. A class the installed runtime binds to no
  trigger withholds nothing, because nothing raises it.

`alerts` is signed with the rest of the payload, as every member but
`signature` is. A consumer that does not implement it ignores it, so a producer
cannot tell from the policy whether a consumer honours a `false`, or which
classes the consumer binds. This version defines no report of either; until
one exists, a product cannot show a class as effective on the strength of the
policy alone.
