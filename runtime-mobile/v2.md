# Android Runtime Payload Publication v2

> Status: Design Target
>
> Intended consumers: `ori-runtime` release automation, and any Android
> application that packages a runtime payload obtained from a release.

`runtime-mobile/v1` defines the payload boundary and what release tooling must
refuse about a payload it is handed. This contract defines how a payload is
**published** and what a consumer must establish before packaging one it did
not build.

**v1 consumers are unaffected.** Nothing here is required of an application
that builds the payload from the runtime source tree, or that is handed one
directly. This version is a new obligation for a new capability — obtaining a
payload from a signed release — and a v1 consumer that never does so conforms
to v1 unchanged. It is a separate version rather than an addition to v1 because
v1 is an implemented baseline: adding mandatory verification to it would assert
a conformance no consumer has.

## Target identity

A target names an ABI and the Android API floor the payload was built against:

```text
android-arm64-v8a-api21
android-armeabi-v7a-api21
android-x86_64-api21
```

The API component is part of the identity because it changes the bytes and is
invisible in a file name. A payload built against a higher floor than a device
provides will not load, and the name it is published under is the only place the
floor appears in what a consumer compares. The artifact does record it, in the
`.note.android.ident` note the NDK writes, which is what lets a producer check
the target it is signing against the build that happened; a consumer is not
required to read ELF notes, and none of the ordered checks below does.

The set is additive. A consumer refuses a target it does not know rather than
guessing, and publishing a target absent from this list is the producer's error.

## Two versions, which are not the same version

`runtime_version` is the **runtime release version** the payload was built
from, such as `2.5.0`. It is not the version of the application packaging it,
which is independent and unrelated.

A consumer selects a runtime release version deliberately and requires the
envelope to name it. It MUST NOT compare `runtime_version` against its own
application version, and MUST NOT accept whichever payload it happens to hold.

## Published assets

Each target publishes atomically under an immutable version tag:

```text
ori-runtime-<runtime_version>-<target>.so
ori-runtime-<runtime_version>-<target>.so.signature.json
ori-runtime-<runtime_version>-<target>.so.sha256
```

The published name binds runtime version and target, and a consumer derives
it rather than trusting it. Given a selected `runtime_version` and the slot's
`target`, the expected name is exactly:

```text
ori-runtime-<runtime_version>-<target>.so
```

A consumer MUST require both the envelope's `artifact` and the basename of the
file it downloaded to equal that derived name. Comparing them to each other is
not enough: two names that agree can still both be the wrong release.

`artifact` is attacker-influenced until the signature has been checked, and a
verifier that uses it to build a path before then is constructing a filesystem
operation out of unverified input. It is therefore a plain filename of printable
ASCII — no path separator, no `.` or `..` component, no control character — and
a consumer
MUST NOT join it to a directory before the name has been derived and matched.

The name the payload is staged under, `libori_runtime_exec.so`, carries no
identity at all, which is why identity is established before the rename.

A release publishes every target it claims or none. A partial set leaves a
consumer unable to tell which ABIs were withheld deliberately.

## Signature envelope

```json
{
  "artifact": "ori-runtime-2.5.0-android-arm64-v8a-api21.so",
  "artifact_sha256": "sha256:8f2c…",
  "artifact_size": 2199440,
  "key_id": "ori-android-payload-2026-01",
  "runtime_version": "2.5.0",
  "schema": "ori.android_runtime_payload_signature.v1",
  "signature": "ed25519:…",
  "stripped": true,
  "target": "android-arm64-v8a-api21"
}
```

The envelope is strict JSON and carries exactly these nine fields. Duplicate
keys, unknown fields, and missing fields are each a refusal. A parser that
accepts a duplicate key silently chooses one of two documents, so a document
containing one is not a document this contract defines.

An envelope longer than 64 KiB is refused unread, and so is a key registry. No
field is an array or an object, so a document with either inside it is
malformed. What is required of a deeply nested document is that the verifier
*refuse* it: an array nested thirty thousand deep fits well inside the size
bound and exhausts a recursive parser's stack, and a verifier that crashes has
not refused. Refusing without recursing and recursing under a bound that turns
into a refusal both satisfy this; an unhandled stack exhaustion does not.

| Field | Form |
| --- | --- |
| `artifact` | the derived published name; 1–255 characters, each printable ASCII from `!` (U+0021) to `~` (U+007E) other than `/`, `\` and `"`, and neither `.` nor `..` |
| `artifact_sha256` | `sha256:` followed by 64 lowercase hex characters |
| `artifact_size` | integer from 1 to 9007199254740991 (2⁵³ − 1), written as decimal digits with no sign, fraction or exponent; equal to the byte length at step 7 |
| `key_id` | 1–64 characters from `[A-Za-z0-9._-]` |
| `runtime_version` | the release version, matching the published name: `MAJOR.MINOR.PATCH` with an optional `-` pre-release suffix of `[0-9A-Za-z.-]`, no `+` build metadata, and no leading `v` |
| `schema` | exactly `ori.android_runtime_payload_signature.v1` |
| `signature` | `ed25519:` followed by standard padded Base64 of 64 raw bytes, in its one canonical spelling |
| `stripped` | boolean |
| `target` | a string of the target grammar `android-<abi>-api<N>`, `<abi>` from `[a-z0-9_-]` and `<N>` a decimal integer with no leading zero; whether it names a v2 target is decided at step 3, not here |

**The signature has one spelling.** Standard Base64 of 64 bytes ends with two
padding characters, and its last data character carries two bits of the
signature and four bits that must be zero. A strict decoder accepts a spelling
with any of those four set and yields the same 64 bytes, so the signature would
still verify; it is refused anyway, because a verifier that accepts two spellings
of one signature is accepting two documents. A consumer confirms that the value
re-encodes to exactly itself.

**A target's form and its membership are different refusals.** A `target` that
is not a string of the target grammar is a malformed envelope. A well-formed
target this contract does not list is `unsupported_target`, refused at step 3
after the signature has been checked, so that refusal is always about a
genuine envelope naming a target the consumer does not know.

The signed bytes are the domain separator followed by the canonical encoding of
every field except `signature`:

```text
ori.android_runtime_payload_signature.v1\0
```

Canonical encoding is UTF-8 JSON with keys sorted by Unicode code point, no
insignificant whitespace, no non-finite numbers, and no escaping of characters
that need none. The separator is the literal schema string followed by one zero
byte.

The field forms keep that encoding the same in every language. Every string a
well-formed envelope can carry is printable ASCII without `"` or `\`, and every
number is a decimal integer JSON represents exactly, so the canonical bytes
contain no escape sequence and no byte above 0x7F. An encoder that escapes
non-ASCII, or one that does not, produces the same bytes for every envelope that
reaches step 2.

### What the domain separator does, and what it does not

It prevents cross-protocol signature reuse: a signature made under the
release-bundle domain cannot verify a payload, and the reverse cannot verify a
bundle. That is necessary because the same release key may sign both — the
authority asserted, that this is an Ori Runtime release, is the same for a
Linux archive and an Android payload, so key material separates nothing.

It is not sufficient on its own, and no single check here is. The strict schema,
the purpose-bound pinned key, the expected target, the expected runtime
version, the digest and size, and the ABI check are each separately
load-bearing; each catches a failure the others do not. A verifier that treats a
valid signature as evidence of artifact class, of correct ABI, or of the
intended release is wrong in three different ways.

## Key registry

The registry is strict JSON shipped with or embedded into the reviewed
consumer, never loaded from a payload, an environment variable, or a document
under verification:

```json
{
  "keys": [
    {
      "key_id": "ori-android-payload-2026-01",
      "public_key_b64": "aDlW3MqinQM8y96szEqNske2ytKkxbmMDl87CuLbAQ8=",
      "purpose": "android_runtime_payload",
      "status": "active"
    }
  ],
  "schema": "ori.android_runtime_payload_keys.v1"
}
```

The registry and every entry reject duplicate and unknown fields, and each
field is refused unless it has its form: `schema` exactly
`ori.android_runtime_payload_keys.v1`; `keys` a non-empty array of entries;
`key_id` of the envelope's `key_id` form and unique within the registry;
`public_key_b64` standard padded Base64 of 32 raw bytes, in its one canonical
spelling, that decode to a valid Ed25519 public key; `purpose` exactly
`android_runtime_payload`; and `status` one of the strings `active`,
`verify_only` and `revoked`. A registry that fails any of these is refused whole
rather than loaded without the entry, because a registry is reviewed as one
document.

**Both `active` and `verify_only` keys verify existing payloads; only `active`
keys sign new ones; `revoked` keys fail closed.** A registry that admitted only
active keys would make every historical payload unverifiable the moment a key
was rotated, which is the opposite of what rotation is for.

A signature envelope names a key. It cannot supply key bytes and cannot change
a registry status.

**A registry never holds a published key.** The conformance corpus publishes the
private seeds it signs with, by construction, and lists their public keys under
`known_test_public_keys_b64`. A consumer registry containing any of them would
accept a payload anyone with a clone of this repository can sign, so a consumer
refuses those keys at registry load, and a release that finds one in the registry
it ships fails.

Purpose is checked at registry load and again at verification, and each check
refuses on its own. A registry load that admitted a `runtime_release_bundle`
entry must still not produce a verifiable payload, so the corpus carries such an
entry deliberately and requires verification to refuse it.

### The same public key under two purposes

The release key that signs Linux bundles may also sign Android payloads. Where
it does, its public key appears in two registries under two purposes, with a
`key_id` distinct in each, and purpose is checked at registry load and again at
verification.

This is deliberate, and it means purpose is an authorisation statement rather
than a property of the key material. A verifier MUST NOT infer purpose from the
key bytes, and MUST NOT accept a `runtime_release_bundle` entry for a payload
even when the public key matches. Rotation is per purpose: demoting a key to
`verify_only` in one registry says nothing about the other.

## What a consumer establishes before packaging

A consumer knows which ABI slot it is filling and which runtime release version
it intends to package. For each payload it establishes, in order, refusing on
the first failure:

1. **envelope** — the envelope parses as strict JSON with exactly the defined
   fields, each in its defined form: `schema` this contract's, and `artifact` a
   plain filename among them;
2. **signature** — the signature verifies under the domain separator against
   a registry key whose `key_id` is the envelope's, whose `purpose` is
   `android_runtime_payload` and whose `status` is `active` or `verify_only`;
3. **identity** — `runtime_version` is the release version the consumer
   selected, `target` is a v2 target, and `target` names the ABI slot being
   filled;
4. **artifact name** — `artifact` equals the name derived from that version and
   target;
5. **presence** — the payload file exists;
6. **basename** — the basename of the downloaded file equals that same derived
   name;
7. **integrity** — `artifact_sha256` and `artifact_size` each match the file
   exactly;
8. **abi** — the ELF header agrees with the target's ABI — `EI_CLASS`,
   `EI_DATA`, `e_machine`;
9. **content** — no shell interpreter line and no placeholder marker is present.

The bold names are the stage names the conformance corpus records against each
refusal, and the order is normative: a case refused at one stage must not be
refusable at any earlier one.

Step 7 compares the size and the digest separately. For bytes that were altered
the two fail together, so a verifier comparing only the digest looks correct;
the size check is what refuses an envelope whose digest is right and whose own
size claim is false.

Steps 3, 4 and 6 establish *which release asset this is*, and are not implied by
the signature. A signature proves that a producer signed these bytes under this
envelope; it does not prove the consumer fetched the asset it meant to, nor
that the file on disk is the one the envelope describes. Deriving the name from
the selected version and slot, then requiring both the claim and the file to
match it, is what closes that.

Steps 3 and 8 both bear on the ABI and neither replaces the other. Step 3 is
the identity control: it is the only one that catches a correctly built,
validly signed payload exported into the wrong slot, because every other
property of that file is genuine. Step 8 is independent of the signing path, so
it holds when a verifier is misconfigured, when a key is wrong, and before any
signed release exists.

The ABI is decided from the ELF header, never from a textual description.
Descriptions nest: an `aarch64` binary is described "ARM aarch64", so a
substring test for the 32-bit "ARM" accepts it, and the wrong payload reaches
the `armeabi-v7a` slot. It packages cleanly and fails only on a 32-bit handset.

**Absence is a failure, not a default.** A consumer MUST NOT substitute a
placeholder, a checked-in stub, or a previously staged file for a missing
payload. A build that silently supplies a stub produces an application that
installs, starts and does nothing.

## Producer obligations

- Build and sign in separate boundaries. The toolchain that compiles a payload
  MUST NOT hold signing credentials, and the job that signs MUST receive
  artifacts it did not build.
- Verify each artifact against its declared target before signing, by ELF
  header.
- Measure what the envelope records, never assert it from build configuration.
  `stripped` is true exactly when the artifact has no `.symtab` section and no
  section whose name begins `.debug`. The target's API level equals the one
  recorded in the artifact's `.note.android.ident` note, and an artifact without
  that note is not signed. A flag and the build that honoured it can disagree,
  and only the bytes say which happened.
- Publish the complete target set for a release, or none of it.
- Pin the build environment. The API floor, the ABI and the strip state are
  properties of how the artifact was produced, and a published digest that
  cannot be reproduced describes nothing.

## Rejection cases

| Condition | Reason |
| --- | --- |
| envelope is longer than 64 KiB, is not strict JSON, has duplicate, unknown or missing fields, or nests where no field does | `invalid_signature_envelope` |
| `schema` is not this contract's | `invalid_signature_envelope` |
| a field is present but malformed | `invalid_signature_envelope` |
| `artifact` is not a plain filename | `invalid_signature_envelope` |
| signature does not verify, including one made under another protocol's domain separator | `invalid_signature` |
| `key_id` is not in the registry | `untrusted_release_key` |
| key purpose is not `android_runtime_payload` | `untrusted_release_key` |
| key status is `revoked` | `untrusted_release_key` |
| digest or size mismatch | `artifact_integrity_mismatch` |
| `runtime_version` is not the selected release version | `artifact_integrity_mismatch` |
| `artifact` is not the name derived from the version and target | `artifact_integrity_mismatch` |
| the downloaded basename is not that derived name | `artifact_integrity_mismatch` |
| `target` is not a v2 target | `unsupported_target` |
| `target` does not match the slot being filled | `unsupported_target` |
| ELF class, byte order or machine disagrees with the target | `unsupported_target` |
| shell interpreter line or placeholder marker present | `invalid_artifact` |
| payload absent | `invalid_artifact` |

## Conformance vectors

This contract is not implementable from prose alone. A vector corpus must
accompany it, consumed by both the producing signer and every consuming
verifier, covering at minimum: one accepted payload per target; a duplicate
key; an unknown field; a missing field; each field malformed in turn; a
signature made under the release-bundle domain; a `runtime_release_bundle` key
entry carrying the same public key; a `revoked` key; a `verify_only` key
verifying an existing payload; a digest mismatch; a size mismatch; a wrong
`runtime_version`; an `artifact` that disagrees with the derived name; a
downloaded basename that disagrees with it; an `artifact` carrying a path
separator or a `..` component; each ABI substituted into each other slot,
including the width-only cases; and a payload absent.

That corpus is `runtime-mobile/payload-vectors-v2.json`. Each case is a
complete consumer input — the envelope as raw text, so a repeated key and
non-strict JSON are representable, the artifact bytes, the basename it was
downloaded under, the selected runtime version and the slot — with the stage
and reason the ordered checks reach. It covers every item above, and in
addition: the non-canonical spelling of a valid signature, a digest that is
right with a size that is wrong, a well-formed target the contract does not
list, a mislabelled payload whose envelope, name, digest and slot all agree
while its ELF header describes another ABI, a big-endian header, each content
refusal, and the inputs that crash a parser rather than failing a rule: an
oversized envelope, deep nesting, an integer too long to convert, and a lone
surrogate escape. Where two checks could both refuse one input, a case holds
both faults so that the order is observable: an absent payload fetched under the
wrong name, a wrong-ABI payload carrying a shell line, and a slot that is itself
not a v2 target. The ELF images carry a correct identification header and
deterministic filler; they are not programs and must never be packaged.

Separately, `registry_cases` holds registry documents and whether a consumer
loads or refuses each, including a registry holding a published test key.

`scripts/check-runtime-mobile-payload-vectors` reads it with no code shared with
`scripts/generate-runtime-mobile-payload-vectors`, and requires every stage to
stop at least one case and every refusal after step 2 to carry a signature that
verifies. `scripts/check-runtime-mobile-payload-vectors-mutations` proves the
checker fires on a neutered refusal, an impure one, a stage left without a case,
a published seed that no longer derives its key, and a registry holding a
published key marked loadable.

The corpus has one reader, and that reader is not a consumer. **This contract
remains a design target, and no implementation may claim conformance until a
producing signer and a consuming verifier are each driven by the corpus.**
