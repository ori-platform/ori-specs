# Skill Hook Isolation v1

> Status: **Design Target.** No part of this contract is implemented.
> Community hook execution is disabled in `ori-runtime` v2.4.0 and stays
> disabled until this contract is implemented and reviewed.
>
> Source of truth for current behaviour: `ori/skills/loader.py`,
> `ori/skills/os_sandbox.py`, `ori/skills/sandbox.py` in `ori-runtime`.
>
> Related: [skills-package/v1.md](../skills-package/v1.md) defines package
> *shape*; this contract defines how packaged hook code may *execute*.

## Why this contract exists

`hooks.py` is arbitrary Python supplied by a third party. Until v2.4.0 the
runtime executed it in its own interpreter behind a filtered `builtins` mapping
and a `sys.meta_path` import finder, and described that as a sandbox. It was not
one, for two independent reasons:

1. The restricted namespace was built by copying `builtins` and removing a short
   denylist, leaving `object`, `type`, `getattr` and `__build_class__` in place.
   Ordinary attribute traversal from any surviving object reached the full
   interpreter.
2. The import finder implemented only `find_module`, a protocol removed in
   Python 3.12. On Ubuntu 24.04 — a supported deployment target — it was ignored
   by the import system. It failed open, silently, for as long as it existed.

It was removed rather than repaired. A boundary that can be walked around is
worse than no boundary, because the configuration around it gets written as
though the protection is real: `os_sandbox.enabled: false` and an unsupported
Landlock host both degraded to the in-process loader, so the platforms with the
weakest isolation were the ones running untrusted code in-process.

This contract defines what has to be true before community hook code may run
again. It is deliberately specified before implementation, because the previous
design's defects were design defects, not coding mistakes.

## Threat model

Assume the hook author is hostile and the package is correctly signed. A
signature proves who wrote the code; it does not make the code safe. In
particular the contract must hold against an author who:

- attempts to read runtime credentials, gateway secrets, or the evidence device
  key
- attempts to reach the network, the filesystem outside its allowance, or other
  processes
- attempts to influence the Action Tier Framework — to raise its own authority,
  suppress a Tier D condition, or fabricate a sensor reading
- attempts to exhaust CPU, memory, descriptors, or the event loop that Tier D
  safety processing shares
- supplies hook bytes that differ from the bytes that were signed

Out of scope: a hostile *runtime* operator, physical device access, and
compromise of the Hub signing key. Those are addressed by
[signing/v1.md](../signing/v1.md) and deployment posture.

## Execution model

| Property | Requirement |
|---|---|
| Interpreter | Community hooks MUST NOT execute in the runtime interpreter. No fallback path may exist. |
| Process | A separate worker process per skill. |
| Availability | If the platform cannot provide the isolation below, the hook MUST be refused. Degrading to a weaker mechanism is forbidden. |
| Lifetime | Worker lifetime is bounded. A worker that exceeds its wall-clock budget is terminated by process group, not by signalling the direct child alone. |
| Failure | Worker failure is reported to the runtime as a typed error. It never propagates as a runtime exception and never blocks the event loop. |

### Ambiguity — worker reuse

Whether one worker serves many invocations of the same skill, or a worker is
created per invocation, is **undecided**. Reuse lowers latency but allows state
to persist between invocations, which widens what one hostile invocation can
leave behind for the next. A decision must state the isolation guarantee between
invocations either way.

## Artifact integrity

The signature defined in [signing/v1.md](../signing/v1.md) covers the
canonicalised `skill.yaml` manifest. It does not cover `hooks.py`. A valid
signed manifest can therefore be paired with different hook bytes after
verification, and the runner reloads `hooks.py` by path on each invocation.

| Requirement | Detail |
|---|---|
| Manifest binding | An installation receipt MUST bind every executable file in the package by cryptographic digest, not the manifest alone. |
| Coverage | `skill.yaml`, `hooks.py`, and any other file the package can cause to be executed or imported. |
| Verification point | Digests MUST be verified against the sealed bytes immediately before execution, not only at install time. |
| Storage | Sealed bytes MUST live where the service identity cannot rewrite them. |
| Re-check | Identity MUST be re-checked on each worker start, so a file replaced between invocations is detected. |

## Environment and filesystem visibility

| Requirement | Detail |
|---|---|
| Environment | The worker receives a minimal constructed environment. It MUST NOT inherit the runtime's environment. |
| Secrets | `GATEWAY_SHARED_SECRET`, `ORI_EVIDENCE_DEVICE_SECRET`, provider API keys and webhook secrets MUST NOT be present in the worker environment under any configuration. |
| Filesystem | Read access is an explicit allowlist. Broad grants such as all of `/etc` are forbidden — system installations keep the runtime environment file at `/etc/ori/runtime.env`. |
| Temporary files | A private temporary directory per worker. The shared system temporary directory MUST NOT be visible. |
| Network | No network access. |
| Writable paths | None, except the private temporary directory and hook state mediated by RPC. |

## Resource and process limits

| Limit | Requirement |
|---|---|
| CPU time | Bounded. |
| Address space | Bounded. |
| Process count | Bounded. |
| File size | Bounded. |
| File descriptors | Bounded. |
| Child processes | Creating a child process or `exec` MUST be denied. |
| Termination | Timeout termination MUST kill the process group. |
| Accounting | Limits are enforced by the operating system, not by cooperation from the hook. |

## IPC

| Requirement | Detail |
|---|---|
| Framing | Bounded framed messages. Message and frame size are capped. |
| Malformed input | A malformed or oversized frame terminates the worker; it does not raise inside the runtime. |
| Direction | The worker MUST NOT be able to initiate arbitrary runtime calls — only the capabilities below. |
| Call budget | Each invocation has a bounded number of RPC calls. Exhaustion terminates the invocation. |

## Capabilities and quotas

Hooks reach runtime data through mediated capabilities, never directly.

| Capability | Requirement |
|---|---|
| History | Restricted to the sensors the skill declares in `sensors_required`. A hook MUST NOT read history for sensors it did not declare. |
| Query volume | Bounded per invocation. |
| State | Key and value sizes bounded; total per-skill state bounded. |
| Namespacing | State is namespaced by authenticated package identity, not by manifest `name` or directory name, so two skills cannot collide. |
| Authority fields | Hooks MUST NOT be able to set or influence `action_tier`, `bypass_llm`, or the reserved sensor-reading names (`value`, `sensor_id`, `sensor_type`, `unit`, `quality`). The runtime re-applies trigger-declared authority after every extension point. |

> The authority-field rule is already enforced in `ori-runtime` v2.4.0 and is
> restated here because it must survive the move to an isolated worker.

## Required-hook semantics

A skill whose triggers depend on hook-derived values behaves differently when
its hooks are absent. Loading it without them activates a skill whose conditions
no longer mean what the author wrote — potentially including its safety
conditions.

| Requirement | Detail |
|---|---|
| Declaration | A package MUST be able to declare that its hooks are required. |
| Required + unavailable | The whole skill is refused. It MUST NOT load with hooks silently absent. |
| Health | A required-hook failure raises a critical runtime health condition, visible in the health snapshot. |
| Optional + unavailable | The skill may load; the health snapshot records the degraded state. |

### Ambiguity — default

Whether `hooks_required` defaults to true or false is **undecided**. Defaulting
to true is fail-closed but breaks packages that treat hooks as enrichment;
defaulting to false preserves them but makes the unsafe case the quiet one.

## Signer identity, revocation and rollback

| Requirement | Detail |
|---|---|
| Identity | Package identity is bound to the signer, not to the manifest `name` field. |
| Uniqueness | Two packages MUST NOT be able to present the same identity. |
| Revocation | The runtime MUST be able to refuse a previously valid signer or package. |
| Expiry | Signatures carry an expiry the runtime enforces. |
| Anti-rollback | A package version that has been superseded MUST NOT install over its successor. An older, legitimately signed, vulnerable package is a replay. |

### Ambiguity — offline revocation

How revocation reaches an offline-first device is **undecided**. A device may be
without connectivity for weeks by design, so a purely online revocation list
does not fit the deployment model. Options include signed revocation bundles
distributed with releases, gateway-mediated distribution, or short signature
expiry with periodic re-issue. Each trades freshness against availability, and
the choice must state which failure mode is preferred when revocation data is
stale.

## Transactional reload

| Requirement | Detail |
|---|---|
| Plan first | The complete registration plan is validated before any existing handler is removed. |
| Commit or roll back | A failure during registration restores the previous handler graph. |
| Never partial | A reload MUST NOT leave a partially replaced handler graph, which can be missing Tier D coverage while appearing healthy. |
| Budget | Subscription accounting reflects active handlers, so repeated reloads do not exhaust a budget. |

> `ori-runtime` v2.4.0 implements plan-validation before mutation, and
> subscription accounting that reflects active handlers. Full rollback on
> mid-registration failure is not implemented; the runtime logs at CRITICAL and
> re-raises. That remainder is a design target.

## Authoring budgets

The runtime enforces workload limits so that an accepted package cannot exhaust
the event loop that Tier D safety processing shares. Registration produces one
EventBus handler per trigger × distinct declared sensor type, and each handler
schedules a reasoning task.

These values are **published here as the authoring target**. They are enforced
in `ori-runtime` v2.4.0.

| Budget | Value |
|---|---|
| Triggers per skill | 64 |
| Declared sensors per skill | 32 |
| Trigger × sensor subscriptions per skill | 256 |
| Declared actions (`actions.available`) | 64 |
| Default actions per trigger | 16 |
| Total default-action references per skill | 256 |
| Prompts per skill | 64 |
| Config entries per skill | 256 |
| Skills per load | 64 |
| Cumulative subscriptions across a load | 1024 |

Manifest admission limits, also enforced in v2.4.0:

| Limit | Value |
|---|---|
| `skill.yaml` size | 1 MiB |
| YAML aliases and merge keys (`<<:`) | Rejected |
| Nesting depth | 32 |
| Total YAML nodes | 20000 |
| Entries in one collection | 1000 |
| `name` / `author` / `version` | Strings; 64 / 128 / 32 characters; no control, format, separator or surrogate characters |

Duplicate action names within one default-action list are rejected, because each
entry is dispatched separately.

### Notes on the values

Handler count is a proxy for cost, not a measure of it. Actual load also depends
on sensor event frequency, reasoning duration, cooldowns and concurrent tasks, so
a package with few handlers on a fast sensor can cost more than a larger quiet
one. These values were not derived from the current packaged inventory, and
headroom against that inventory is not a reason to raise them. Raising a value
requires event-loop benchmarking on the supported deployment targets.

## Relationship to current runtime behaviour

What `ori-runtime` v2.4.0 does today, for implementers reading this against a
shipped runtime:

| Behaviour | State |
|---|---|
| Community hook execution | Disabled unconditionally, including where seccomp/Landlock is available |
| In-process restricted loader | Removed; the entry point raises |
| `os_sandbox.enabled`, `os_sandbox.require_for_community` | No longer decide whether untrusted hook code runs |
| Non-first-party skill carrying `hooks.py` | Refused entirely |
| First-party packaged hooks | Imported directly into the runtime interpreter |
| `OSSandboxHookRunner` | Present, unreferenced by the loader; a starting point for this contract |

## Open questions for implementers

1. Worker reuse and the isolation guarantee between invocations.
2. `hooks_required` default.
3. Offline revocation distribution and staleness policy.
4. Whether the isolation mechanism is required to be identical across Linux
   targets, or whether a documented per-platform matrix is acceptable given that
   refusal — not degradation — is the fallback.
5. Whether artifact receipts are produced by the Hub, the SDK build path, or the
   installer, and which of those the runtime is required to trust.
