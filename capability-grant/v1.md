# Capability Grant Contract v1

> Status: Design target, pre-ratification. No shipped consumer claims
> conformance. Amendable in place under the
> [pre-ratification exception](../VERSIONING.md#pre-ratification-exception).
>
> Related: [skills-package/v3.md](../skills-package/v3.md) for the package a
> grant travels in, [signing/v1.md](../signing/v1.md) for signature encoding
> and the author and Hub signatures a grant is distinct from,
> [safety-profile/v1.md](../safety-profile/v1.md) for the Tier D authority
> this contract deliberately cannot confer, and
> [runtime-release-bundle/v1.md](../runtime-release-bundle/v1.md) for the key
> registry model the grant anchor follows. Issuance, key custody, rotation and
> revocation are the issuance contract's (ori-platform/ori-specs#73); this
> contract defines what a grant says and how a consumer verifies one.

A skill's permitted authority ceiling is implicit today: it is whatever
survives the action registry floor, the dispatcher's escalation cap, and the
loader's provenance checks. An author has no machine-verifiable statement of
what they were granted, and discovers their limits by being rejected at load.
A **capability grant** is a signed statement, issued by a capability authority
whose public key is anchored in the runtime release, that names the ceiling —
which triggers, which actions, and up to which tier — for one exact payload of
one skill.

A grant is a **ceiling, never a floor**. It permits nothing the runtime
forbids, lowers no runtime-owned minimum tier, and exempts nothing from any
other refusal. Effective authority is the intersection of the grant with every
runtime-owned constraint; removing the grant from that intersection can only
shrink it.

## The grant object

A grant is one strict JSON object.

| Field | Type | Meaning |
|---|---|---|
| `schema` | `string` | Exactly `ori.capability_grant.v1`. |
| `skill_name` | `string` | Must equal the package manifest's `name`, byte for byte. |
| `skill_version` | `string` | Must equal the manifest's `version`, byte for byte. |
| `payload_sha256` | `string` | `sha256:<64-lowercase-hex>` over the payload tree digest domain below. |
| `permitted_triggers` | `array[string]` | Trigger names the package may declare. May be empty. |
| `permitted_actions` | `array[string]` | Action names the package may declare in `actions.available`. May be empty. |
| `max_tier` | `string` | Exactly `A`, `B`, or `C`. Never `D`. |
| `authority_key_id` | `string` | Names the verifying key in the release's capability authority registry. |
| `signature` | `string` | `ed25519:<standard-base64>` per [signing/v1.md](../signing/v1.md), detached from the signed bytes by exclusion. |

Every field is required. Unknown fields, duplicate keys, non-string entries in
either list, and duplicate entries within a list are refused. The lists are
matched against manifest declarations by exact byte equality.

**`max_tier` is capped at C, normatively.** Tier D removes the operator from
the loop: it fires immediately, before any reasoning, and cannot be
overridden. That authority is a property of the reviewed runtime release — its
conditions are typed, release-shipped records under
[safety-profile/v1.md](../safety-profile/v1.md) — and is not issuable by any
third party. A grant whose `max_tier` is `D`, or any value outside the three
permitted letters, is refused as malformed before its signature is examined: a
correctly signed claim of an unissuable authority is not a signature problem.

## Canonical bytes and the signed message

The signed object is the grant with the `signature` field removed,
canonicalised exactly as [signing/v1.md](../signing/v1.md) Profile 2
canonicalises a manifest: keys sorted lexicographically at every level,
compact `,` and `:` separators, UTF-8, unescaped Unicode, JSON scalars only,
non-finite numbers refused, duplicate keys refused at parse.

The Ed25519 message is:

```text
ori.capability_grant.v1\n<canonical unsigned grant bytes>
```

The domain separation string is exactly `ori.capability_grant.v1` followed by
one `\n` (0x0A). It is fixed for this contract version and is not read from
the document. The `schema` field inside the signed bytes states the same fact
as data; the prefix states it as the verifier's intent, so a capability
authority signature can never verify as any other object family even if field
names collide.

## The payload tree digest domain

`payload_sha256` binds the grant to the exact package content it was issued
for — the manifest, the executable `hooks.py`, and every other file the
package carries — while excluding the grant itself, which cannot be inside its
own digest.

The digest is SHA-256 over the concatenation, for each included file in
ascending order of raw UTF-8 path bytes, of:

```text
<path-utf8> 0x00 <decimal-content-length> 0x00 <file-bytes>
```

- **Included files:** every regular file in the package, except exactly
  `grant.json` at the package root.
- **Paths** are relative to the package root, use `/` as the separator, and
  are the exact bytes used for ordering.
- **Directory entries contribute no bytes** to the digest.
- Every entry reaching this computation has already passed archive admission
  (verification step 1), so the digest itself is pure arithmetic: path
  safety, duplicate detection, entry kinds, and the presence of the grant are
  decided there, for every entry kind, before anything is hashed or parsed.
- `<decimal-content-length>` is the file's content length in bytes, in ASCII
  decimal with no leading zeros (`0` for an empty file).

Two implementations that disagree about these bytes disagree about what was
signed, which is why the boundary admits no discretion: nothing is normalised,
nothing is decompressed, no metadata (mode, mtime, owner) participates, and
exclusion is by exact name, not by pattern.

## Placement

The grant travels **inside the package**, as `grant.json` at the package
root, beside `skill.yaml`. A consumer MUST NOT accept a grant from anywhere
else. Device configuration is explicitly forbidden as a carrier: a grant
delivered through `ori.yaml`, a provisioning document, or any other
deployment-controlled channel would arrive through the same party that
selected the skill, which restores exactly the channel this contract exists to
cut. A grant found in such a channel is refused outright — not ignored — so
the misconfiguration is surfaced rather than silently unused.

The grant's placement interacts with the package's other signatures without
circularity:

- The **author's manifest signature** ([signing/v1.md](../signing/v1.md)
  Profile 2) covers the canonicalised `skill.yaml` only. `grant.json` is a
  separate file; embedding it changes no signed manifest byte.
- The **payload tree digest** excludes `grant.json`, so issuing a grant does
  not alter the bytes it binds.
- The **Hub artifact signature** (Profile 1) covers the final artifact bytes,
  grant included, and is applied after the grant is embedded.

The full signing order — author, digest, grant, finalisation — is specified by
the issuance contract.

## Verification

Verification is **fully offline**. The trust anchor is a capability authority
key registry shipped in the runtime release, following the pinned-registry
model of [runtime-release-bundle/v1.md](../runtime-release-bundle/v1.md):
strict JSON, `key_id` unique, statuses `active`, `verify_only`, and `revoked`.
Both `active` and `verify_only` keys verify existing grants; `revoked` keys
fail closed; only `active` keys sign new grants. A grant names a key by
`authority_key_id`; it cannot add key bytes or change registry status. There
is no issuer the device contacts, no lease, no expiry, and no online
revocation check — a grant that required a reachable issuer would put skill
authority behind network availability. Withdrawal of a mistakenly issued grant
is by denial list inside a signed release, specified by the issuance contract.

A consumer verifies in this order, refusing at the first failure:

1. **Archive admission.** Verification enumerates the authenticated
   archive's entries, never an extracted filesystem tree — extraction
   collapses duplicates and resolves links, erasing exactly the evidence
   this stage refuses on. Every entry's path, **whatever its kind**, must be
   non-empty, valid UTF-8, free of `0x00`, free of `\` (0x5C — the byte a
   Windows consumer would reinterpret as a separator, turning `..\escape`,
   a drive-qualified path, or a UNC path back into traversal), not begin
   with `/`, contain no `.` or `..` segment, and contain no empty segment,
   so `a//b` and trailing-slash aliases cannot collapse into other paths
   during extraction. A directory is ignored by the digest and is still
   validated here, because ignored-by-the-digest is not ignored-by-safety.
   Extraction must preserve this validated logical-path interpretation: the
   only separator is `/`, and a consumer must not reinterpret any other
   byte — a backslash, a drive letter, anything platform-specific — as path
   structure on its platform. A
   path that is a byte-for-byte duplicate of another, across all entry
   kinds, refuses. An entry that is neither a regular file nor a directory —
   symlink, device node, FIFO, socket, anything else — refuses, whatever its
   name. The archive must contain **exactly one** regular root `grant.json`
   — none, more than one, or a non-regular one refuses, per the placement
   rule — and exactly one regular root `skill.yaml`, which is the manifest
   every later binding reads. The grant the remaining stages verify is the
   exact bytes of that root `grant.json`; no other source is consulted.
2. **Parse strictly.** Valid JSON, no duplicate keys, exactly the fields
   above, each of the declared type.
3. **`schema`** is exactly `ori.capability_grant.v1`.
4. **Field validity.** `max_tier` is one of `A`, `B`, `C`; `payload_sha256`
   matches `sha256:<64-lowercase-hex>`; list entries are unique strings;
   identity fields satisfy the manifest's own identity-field rules.
5. **Key resolution.** `authority_key_id` names a registry key whose status is
   `active` or `verify_only`. An unknown or `revoked` key id refuses.
6. **Signature.** The `ed25519:` value verifies over the domain-separated
   message under the resolved key, with every encoding rule of
   [signing/v1.md](../signing/v1.md) enforced.
7. **Payload binding.** The recomputed payload tree digest equals
   `payload_sha256`.
8. **Identity binding.** `skill_name` and `skill_version` equal the `name`
   and `version` parsed from the archive's root `skill.yaml` — the
   authenticated manifest, never a sidecar.
9. **Package admission.** Every trigger and action the **archive's own
   manifest** declares is held against the grant: every declared trigger
   name is in
   `permitted_triggers`; every action name in `actions.available` is in
   `permitted_actions`; no declared trigger or action tier exceeds
   `max_tier`. Any excess refuses the package, naming the excess declaration.

Steps 1–4 need no key material, so an unsafe archive or a malformed grant —
including one claiming Tier D — is refused without consulting the registry,
and its refusal reason names the entry or field, not the signature. Steps 7–9
run only over a grant whose signature already verified, so their refusal
reasons ("digest mismatch", "identity mismatch", "unpermitted declaration")
are statements about a genuine grant applied to a package it does not admit,
which is operationally different from a forged grant and must be reported
distinctly. A grant that verifies is not a package that loads:
`grant_verified` is the outcome of steps 1–8, `package_admitted` the outcome
of all nine, and a consumer that reports the first as the second has skipped
the ceiling this contract exists to state.

## What a verified grant means

For a package whose grant verified:

- Package admission (step 9) refuses the **package at load** on any excess
  declaration. Fail closed; nothing is silently narrowed, because a package
  that loads with fewer capabilities than its manifest declares is exactly the
  invented-setting defect [skills-package/v3.md](../skills-package/v3.md)
  exists to close.
- The grant composes with every runtime-owned constraint: the action registry
  floor still binds, a skill may still raise but never lower an action's tier,
  and no grant field exempts a package from signature verification, hook
  policy, or admission limits.
- The grant confers nothing at Tier D, and nothing about the release-owned
  safety registry's evaluation changes with any grant present or absent.

Selection of a package by exact digest — which is what a provisioning backend
does — confers nothing: it chooses which authorised package runs, never what a
package is authorised to do. The author's signature proves authorship of
the signed manifest declarations — it does not bind `hooks.py` or the rest of
the tree; the grant's payload digest binds the complete payload, and its
signature proves what that payload was permitted. Neither implies the other.

How a consumer treats a package that carries **no grant** is an admission
policy, not a verification outcome, and is decided by the issuance contract
together with its migration consequences. Until that contract decides
otherwise, the conservative posture holds: a package without a grant has no
authority above Tier A.

## Vectors

`grant-vectors-v1.json` is the normative corpus, checked in CI by
`scripts/check-capability-grant-vectors`, which shares no code with whatever
authored the corpus. Each case carries only the enumerated archive tree —
entries with raw path bytes and an entry kind, so paths a filesystem cannot
hold and kinds a dict cannot express are representable — plus the canonical
unsigned bytes and signed message where a grant exists and parses, and the
expected outcome with its refusal stage. The grant is read from the tree's
root `grant.json` bytes and the manifest from its root `skill.yaml` bytes:
there is no sidecar to verify instead of the archive. Vector manifests are
written as JSON — a JSON document is a valid YAML manifest — so the checker
parses the authenticated bytes with no YAML dependency; a consumer parses
YAML per [skills-package/v3.md](../skills-package/v3.md). The corpus
covers at minimum: an admitted grant; a wrong payload digest; a wrong skill
name; a wrong skill version; a tampered ceiling (signed at one tier,
presented at another); an unknown key id; a grant claiming Tier D; an unknown
field; a duplicate JSON key; a malformed signature encoding; grant identity
fields that break the manifest's syntax and length rules; the three
package-admission refusals (unpermitted trigger, unpermitted action, tier
above ceiling); and the archive-admission refusals (a missing root
`grant.json`, a missing root `skill.yaml`, traversal, absolute, empty and
NUL-bearing paths, backslash-bearing paths in their Windows traversal,
drive-qualified and UNC shapes, empty segments and trailing-slash aliases,
invalid UTF-8, duplicate paths including a directory duplicating a file,
unsafe paths on directory entries, a non-regular entry) plus
positive proof that a root `grant.json` entry is excluded, a nested
`grant.json` is not, directory entries are ignored, and ordering is by raw
path bytes regardless of enumeration order. A reject case must be refused
**for its declared reason**: a corpus whose Tier D case is refused for its
signature reports coverage that does not exist.

## Downstream impact

- **ori-runtime** implements the verifier and the load-time ceiling
  enforcement, ships the capability authority registry in the release, and
  refuses grants arriving through configuration channels.
- **ori-skills-hub** carries `grant.json` through upload, storage and
  distribution untouched, and is forbidden from signing grants — the Hub
  artifact signature attests distribution, never authority.
- **ori-sdk-python** surfaces the granted ceiling to authors at build time so
  a package that exceeds its grant fails at authoring, not at a device.
