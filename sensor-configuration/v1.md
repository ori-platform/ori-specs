# Sensor Configuration Contract v1

> Status: Design target, pre-ratification. No shipped consumer claims
> conformance. Amendable in place under the
> [pre-ratification exception](../VERSIONING.md#pre-ratification-exception).

`runtime-config/v1.md` specifies every section of `ori.yaml` except one.
`sensors` is absent, and that absence is not an oversight in the document — it
reflects that the sensor surface has no single shape to write down.

This contract gives it one.

## Why This Cannot Be A Closed Object

The runtime keeps five sensor keys and routes **every other key** into
`metadata`, which is then merged into the dictionary handed to
`adapter.connect()`. So the accepted sensor surface is not one schema. It is
**whatever each adapter reads**, and that has never been written down anywhere.

Extracted mechanically from the runtime rather than from its documentation:
**15 protocols, 15 adapters, 31 operator-written keys.** Sixteen of those keys
appear under more than one protocol.

A single closed `Sensor` object cannot represent that. An attempt to write one
rejected `port`, `baud_rate`, and every CoAP and Modbus field, because those
keys exist only in adapters.

Nor can the answer be a table of fifteen protocols in this document. **If adding
an adapter requires editing a contract in another repository, adapters will be
added without editing it**, and the schema becomes wrong quietly — which is
worse than having none, because it looks authoritative.

So this contract specifies a **grammar and an enforcement rule**, and requires
each adapter to declare its own accepted keys in machine-readable form beside
its code. The contract owns what a declaration means and what happens to a key
nobody declared. The adapter owns its field list.

## Two Boundaries, Not One

A sensor's configuration crosses two boundaries with different rules, and
collapsing them is a defect in its own right — it either refuses fields an
operator must be able to write, or admits ones that displace the runtime.

### Boundary 1 — the sensor entry

What an operator writes in `sensors[]`. It has exactly two parts.

**Canonical fields.** These are the envelope every protocol schema sits inside,
so they are specified here rather than declared per adapter:

| Field | Type | Required | Default | Constraint |
| --- | --- | --- | --- | --- |
| `id` | string | Yes | — | Non-empty after trimming; unique across `sensors[]` |
| `type` | string | Yes | — | Non-empty after trimming |
| `protocol` | string | Yes | — | Must name a defined protocol |
| `poll_interval_ms` | integer | No | `1000` | 100–60000 inclusive |
| `calibration` | object | No | `{}` | Validated against the `(protocol, type)` schema |

This table is a [`schema-descriptor/v1`](../schema-descriptor/v1.md)
declaration like any other, owned by this contract rather than by an adapter.
Its types are therefore checked and never coerced by that core's rule:
`poll_interval_ms: "1500"` is a string where an integer is declared, and
`id: 123` is a number where a string is. Both are refused.

**`id` MUST be unique.** The runtime keys per-sensor state by it, so duplicates
do not produce two sensors — they produce one, silently, with readings from both
arriving under a single identity.

Some of this is stricter than the loader that exists today, deliberately: an
empty `id` is currently accepted, duplicates are currently accepted, and typed
fields are currently coerced. Those are the defects this envelope closes.

**Protocol configuration**: every other key in the entry. Each MUST appear in
the declared schema for that `protocol`, and **a key no schema declares MUST be
refused at configuration load**.

Forwarding it is the behaviour this replaces. A key the runtime accepts and
discards reads, to whoever wrote it, as a setting that took effect: the shipped
example set `baud_rate` on a serial sensor while the adapter read `baudrate`,
and it appeared to work only because the two values coincided.

**Reserved names.** Protocol configuration MUST NOT contain `sensor_id`,
`sensor_type`, or `circuit_breaker`. These are the names the runtime uses at the
second boundary, and a sensor entry carrying one would displace what the runtime
supplies there.

Refusal, not precedence. An operator who wrote `circuit_breaker` on a sensor
meant something by it, and silently preferring the runtime's value is the same
defect one level down. The refusal MUST name the offending keys and say where
the setting belongs.

Note that `poll_interval_ms` and `calibration` are **canonical fields, not
reserved names**. An operator writes them; the runtime carries them across. Only
the three names above are reserved, because only those three are introduced by
the runtime rather than translated from something the operator wrote.

### Boundary 2 — the adapter connection

What the adapter receives from `connect()`. The runtime assembles it from three
sources, in this order:

1. **Protocol configuration**, as validated at boundary 1.
2. **Runtime-supplied values**, applied over it:

   | Key at the adapter | Derived from |
   | --- | --- |
   | `sensor_id` | the entry's `id` |
   | `sensor_type` | the entry's `type` |
   | `poll_interval_ms` | the entry's `poll_interval_ms` |
   | `calibration` | the entry's `calibration` |
   | `circuit_breaker` | `hal.circuit_breaker` |

3. **Protocol defaults**, applied only where the key is still absent.

**The runtime's values MUST be applied after the protocol configuration, never
before**, and that ordering MUST NOT depend on the reserved-name refusal having
run. A check that holds only because an earlier check held is not a boundary;
both are required, and each must fail closed alone.

This is not hypothetical. Before it was closed, a sensor entry could set
`circuit_breaker` and disable hardware recovery for its own adapter while the
global setting still read as configured, or present to its adapter as a type it
was not declared as.

### Protocol defaults

A field MAY inherit from another config section when the sensor does not set it.
This is declared, not implied by runtime behaviour, with two descriptor
properties:

| Property | Meaning |
| --- | --- |
| `fallback_from` | Config path supplying the value when the sensor omits the key |
| `must_be_subset_of` | Config path whose value bounds a sensor-supplied one |

```yaml
allowed_hosts:
  type: array
  items: {type: string}
  fallback_from: actions.coap.allowed_hosts
  must_be_subset_of: actions.coap.allowed_hosts
timeout_s:
  type: number
  fallback_from: actions.coap.timeout_s
  minimum: 0
```

These are checked in two phases, because the referenced value does not exist
until a configuration is loaded. Saying "checked at schema load" would describe
a malformed `actions.coap.allowed_hosts` as validated at a point where nothing
can look at it.

**At schema load**, with no configuration in hand:

- The path MUST be well-formed and MUST name a section **outside** `sensors[]`.
  A fallback a sensor could write is not a bound.
- `must_be_subset_of` MUST appear only on a field declared `type: array`.

**At configuration load**, once the referenced section exists:

- The path MUST resolve. A fallback naming a field the configuration does not
  contain is refused, not treated as absent.
- The resolved value MUST validate against the field's own descriptor. An
  `actions.coap.timeout_s` that the sensor's `timeout_s` descriptor would reject
  is refused there, rather than reaching an adapter because it arrived by
  inheritance instead of being written on the sensor.
- For `must_be_subset_of`, the resolved value MUST be an array, and a
  sensor-supplied value MUST be a subset of it.
- The fallback applies **only** where the sensor did not set the key. The
  operator's value wins.

**`must_be_subset_of` is how a security boundary is declared.** A sensor
narrowing its own CoAP host allowlist is legitimate and useful; widening it is
not, and refusing the widening is what makes the fallback safe to offer at all.
Without this property the mechanism would let a sensor entry escape a limit set
in a section it cannot otherwise reach.

A field with `must_be_subset_of` and no `fallback_from` is valid: bounded, but
with no default.

## Adapter Schema Declarations

### The protocol definition

Today the runtime resolves a protocol by a factory chain that **returns an
adapter instance**, and maintains the set of supported protocols as a second,
hand-written list beside it. Neither can answer "what does this protocol
accept?" without constructing an adapter, and the two lists can drift apart
silently.

This contract requires a single **protocol definition** per protocol, from which
both are derived:

| Element | Requirement |
| --- | --- |
| `protocol` | The string an operator writes in `sensors[].protocol` |
| adapter | The module and class implementing it, named but **not instantiated** |

**The definition identifies the module. The module owns the schemas.** A
definition MUST NOT carry its own copy of a schema: two declarations of the same
thing drift, and the one a validator reads stops being the one an adapter obeys.

Each adapter module exposes **two required module-level schema mappings**:

| Name | Contents |
| --- | --- |
| `CONFIG_SCHEMA` | The declaration governing that protocol's configuration |
| `CALIBRATION_SCHEMAS` | Declarations keyed by sensor `type`, possibly empty |

Both are authoritative: not a docstring, not a README table, not this contract.

This says nothing about the rest of the module. Adapters legitimately carry
implementation constants and lookup tables of their own — sensor-type maps, gain
tables, register addresses — and this contract governs only the two names above.

**Both MUST be present.** An empty `CALIBRATION_SCHEMAS` states that the
protocol calibrates nothing; an absent one states nothing at all, and cannot be
distinguished from an adapter whose author did not consider the question.

**Resolving a schema MUST NOT instantiate an adapter.** Configuration is
validated before any hardware is touched, so a resolution path that constructs
adapters cannot run at the point the answer is needed. Importing the module is
permitted — adapters already guard their hardware imports — but construction is
not.

**The set of supported protocols MUST derive from these definitions**, not be
maintained beside them. Two lists that must agree by hand are a defect waiting
for the edit that updates one.

**A definition whose module is missing either mapping MUST be refused at
configuration load**, naming the protocol, the module, and which mapping is
absent. Not warned, not defaulted to an open schema: an adapter registered
without a declaration is one whose accepted surface is unknown, which is the
state this contract exists to end.

A conforming implementation MUST have a check, run in CI, asserting that every
defined protocol resolves to **both** mappings without instantiating an adapter.
Without it the rule holds only while someone remembers, and the failure is
silent — a new adapter would simply accept anything.

### Shape

```yaml
port:
  type: string
  required: true
baud_rate:
  type: integer
  default: 9600
  minimum: 1
baudrate:
  type: integer
  deprecated: true
  supersedes: baud_rate
parity:
  type: string
  default: "N"
  enum: ["N", "E", "O"]
```

### Field descriptor grammar

The primitive layer is [`schema-descriptor/v1`](../schema-descriptor/v1.md):
types, bounds, enumerations, defaults, recursive closure, and the rule that
values are checked rather than coerced. This contract **adopts that core** and
does not restate it — two copies of a type system drift, and the drift is
invisible until two implementations disagree about whether `7.0` satisfies
`integer`.

What this contract adds to it:

| Property | Meaning |
| --- | --- |
| `deprecated` | The key is accepted and warned about. Requires `supersedes`. |
| `supersedes` | The canonical key this one is an alias for, named by a dotted path from the schema root. Required when `deprecated`. |
| `required_unless` | Required unless a named sibling holds a given value. |
| `fallback_from` | Config path supplying the value when the sensor omits the key. |
| `must_be_subset_of` | Config path whose value bounds a sensor-supplied one. |

`exactly_one_of` and `at_least_one_of` are schema-level rather than field-level,
and are specified below.

The last two properties are why this contract adopts the core rather than being
merged with the package-configuration one. Inheriting a value from another
section of the device configuration document is right here, where the schema
ships with the release and the document is the operator's. It would be wrong in
a signed package manifest, where a schema inheriting from an unsigned document
would invert the trust model the signature exists to establish.

### Conditional requirements, expressed mechanically

Prose conditions are not implementable. A declaration expresses them with:

| Property | Meaning |
| --- | --- |
| `required_unless: {key: value}` | Field-level. Required unless that sibling key equals that value. |
| `exactly_one_of: [[a], [b, c]]` | Schema-level. Exactly one group must be fully present. |
| `at_least_one_of: [[a], [b]]` | Schema-level. At least one group must be fully present. |

**`exactly_one_of` refuses stray members of the groups not selected.** Naming a
group is choosing it, and a key belonging to a rejected alternative is not
merely unused — it states an intent the runtime will not honour. A sensor
declaring both a `host` and a `serial` is not configured twice; it is
configured ambiguously, and that must be refused rather than resolved by
precedence. Keys outside every group are unaffected and validated normally.

**A `default` declared on a member of a group that was not selected MUST NOT be
applied.** Applying it would materialise a key belonging to a rejected
alternative — the same thing the constraint refuses when an operator writes it,
arriving instead by the runtime's own hand. A sensor reachable by `serial` does
not acquire a `port` because the network alternative declares one.

`at_least_one_of` does not refuse extra groups, because it is the mechanism for
"any of these will do".

#### What a condition reads

**`required_unless` evaluates the sibling's resolved value**, after that
sibling's `default` and any applicable `fallback_from` have been applied — not
the value as written, and not its absence.

Reading the raw document instead makes a complete document fail. Given a `mode`
that defaults to `"auto"` and a `path` required unless `mode` is `"auto"`, an
entry that omits both is complete: `mode` resolves to `"auto"`, so `path` is not
required. A condition reading the raw entry sees nothing where `mode` should be
and refuses.

So resolution happens in two passes over each mapping. First every field that
can be settled without knowing whether a dependent field is required — values
written by the operator, defaults, and inherited values. Then requirements,
against those settled values.

**Dependencies are evaluated within the object that declares them.** A
`required_unless` inside a nested object names a sibling in *that* mapping, and
resolution order is per scope. A nested condition cannot name a field in its
parent or in a sibling object; scopes do not see each other.

#### Cycles are refused when the schema loads

Because a condition reads a resolved value, two conditions that depend on each
other have no defined evaluation order: each would need the other settled first.

**A cycle among `required_unless` dependencies MUST be refused when the schema
loads, and the refusal MUST name the cycle.** Direct — `a` unless `b`, `b`
unless `a` — and indirect, `a` → `b` → `c` → `a`, at any length.

Resolving one by declaration order would be worse than refusing it. Declaration
order is invisible in the file that carries it, and two people reading the same
schema would disagree about which field is required. Refusing at load, naming
the fields that form the cycle, tells the author exactly which declarations to
change.

A schema whose conditions form no cycle has exactly one evaluation order, so
implementations that agree on this rule agree on which documents are valid.

A real case from the current adapters:

```yaml
# usb_serial: a path, unless the adapter is asked to find one
device_path:
  type: string
  required_unless: {auto_detect_device_path: true}
```

**No adapter shipping today needs `exactly_one_of` or `at_least_one_of`.** They
are specified because a declaration that needs one has no other way to say it,
and a grammar that admits the condition only after an adapter arrives to need it
would be edited under deadline. An illustration, not drawn from any adapter:

```yaml
# a reader reachable by network or by local socket, never by both
exactly_one_of:
  - [host, port]
  - [socket_path]
```

An earlier revision offered `growatt` and `solarman_modbus` here as "reachable
by network or by serial, not both". That is wrong, and wrong in the direction
that matters: both adapters construct `PySolarmanV5(host, serial, port)` and
refuse each field independently, because `serial` is the logger dongle's serial
number carried over TCP beside the host, not an alternative transport. An
implementer declaring those two protocols from that example would have written a
schema refusing every working configuration, since a document supplying both
fields satisfies neither group.

It is recorded rather than quietly deleted because the sentence that made it
harmful was "real cases from the current adapters" — the phrase an implementer
trusts instead of reading the adapter. An example claimed as extracted has to be
extracted.

### References are validated when the schema loads

A conditional that names a field which does not exist is unenforceable, and it
fails silently: the condition simply never fires. These are checked when the
schema is loaded, not when a document exercises them.

- Every member of an `exactly_one_of` or `at_least_one_of` group MUST name a
  field declared in the same schema.
- `required_unless.key` MUST name a field declared in the same schema.
- A group MUST be non-empty. An empty group is either always satisfied or never
  satisfiable, and neither is what anyone meant.
- Within one constraint, a field MUST NOT appear in more than one group, and no
  two groups may be identical. Both make the constraint ambiguous: the first
  makes "exactly one group" undecidable, the second makes it meaningless.
- `required_unless` dependencies MUST NOT form a cycle, direct or indirect. See
  [Cycles are refused when the schema loads](#cycles-are-refused-when-the-schema-loads);
  it is listed here because it is a load-time reference check like the others.

### Deprecation

A key being renamed MUST be declared `deprecated` with `supersedes` naming its
replacement, for at least one configuration generation rather than removed, and
the runtime MUST warn naming the replacement.

**Supplying both a key and its deprecated alias MUST be refused, even when the
values agree.** Agreement today is not agreement after the next edit, and a
precedence rule is invisible in the file that carries it.

**An alias's value MUST be resolved into its target's position**, before the
target's own descriptor is applied. Accepting an alias and then discarding what
it carried is worse than refusing it: the operator is told their key was
accepted, the target falls back to its declared default, and the adapter runs on
a value nobody wrote. That is the defect this contract exists to close,
occurring inside the mechanism meant to close it.

So a schema declaring `baud_rate` with a default of `9600` and `baudrate` as its
alias, given `baudrate: 19200`, MUST resolve to `baud_rate: 19200` — not to the
default, and not with the alias still present beside it. Defaults, bounds and
conditional requirements all see the canonical spelling.

**The target is the sole owner of value semantics.** A deprecated alias MUST
declare only `type`, `deprecated`, `supersedes` and `description`, and MUST be
refused at schema load if it carries any other property — a `default`, a bound,
an `enum`, `properties`, `items`, `required`, `required_unless`,
`fallback_from`, or `must_be_subset_of`.

Without that rule the two descriptors compete and nothing says which wins. An
alias carrying its own `default` is the sharpest case: the value moves to the
target, so the alias's default applies to a position no longer holding anything,
and an implementation could apply it, ignore it, or apply it after the target's —
three readings of one declaration. The same ambiguity runs through bounds, which
would let the alias admit what its target refuses, and through `fallback_from`
and `required_unless`, which would make a key that is being removed the thing
another field's requirement is evaluated against.

`type` is the exception because it is not competing semantics: the alias must
already declare the same type as its target, and stating it keeps a declaration
readable on its own.

An alias of an `array` or `object` target is therefore **exempt from the core's
requirement that those types declare their contents**. Without the exemption the
rule would make such an alias unconstructible — `items` and `properties` are
required by `schema-descriptor/v1` and forbidden here — and an alias holds
nothing after resolution, so there are no contents of its own for it to close
over. The target's declaration is what every value is checked against.

A deprecated key MUST NOT itself be `required`, and its `supersedes` MUST name a
field declared in the same schema.

#### Aliasing across a nested boundary

A rename that moves a setting into a nested object is the same migration as a
rename within one, and a grammar that cannot express it does not prevent the
move — it leaves the resulting precedence undeclared. This is not hypothetical:
the MQTT adapter family accepts a broker credential as `mqtt_username` on the
sensor entry, as `username` on the sensor entry, and as `username` inside a
nested `mqtt` object, resolved by a precedence chain written in the adapter and
stated nowhere an operator can read.

`supersedes` MAY therefore name a **dotted path**, resolved from the root of the
schema that declares it:

```yaml
mqtt:
  type: object
  properties:
    username: {type: string}

mqtt_username:
  type: string
  deprecated: true
  supersedes: mqtt.username
```

At schema load:

- Every segment but the last MUST name a field declared at that level, and each
  MUST be `type: object` carrying `properties`. A path MUST NOT descend through
  `items`: an array element has no stable identity for an alias to name.
- The final segment MUST name a field declared in that object.
- The target MUST NOT itself be `deprecated`. An alias of an alias has no single
  canonical spelling, which is the whole of what this property establishes.
- The alias MUST declare the same `type` as its target. Two descriptors for one
  setting are two things to edit, and the one an operator's value is checked
  against would stop being the one the adapter obeys.
- A single-segment path is the same-scope case and is unchanged by this.

At configuration load:

- The alias and its target MUST NOT both be present, and presence is judged on
  the document as written. A default or an inherited value at the target is not
  the operator having written it, so it does not make a supplied alias a
  conflict.
- Where only the alias is present, its value is resolved into the target's
  position as above, creating the intermediate objects the path names. An
  implementation that instead read both positions at the point of use would
  reintroduce the precedence rule this removes.
- The refusal and the deprecation warning MUST both name the full canonical
  path, not the leaf. `username` does not tell an operator which of three
  places to write it.

## Calibration

`calibration` is a canonical sensor field and is **not** part of the protocol
schema. It describes what a reading means, not how the reading is fetched.

It MUST NOT be flattened into the same namespace as protocol configuration.
Flattening is what let a documented `sensitivity` sit unread beside an adapter's
own default.

### Selected by protocol and type

A calibration schema is selected by the pair **(`protocol`, `type`)**, not by
`type` alone. The same measurement over different transports needs different
calibration, or none: a current reading taken through an ADS1115 needs the
clamp's sensitivity, the supply frequency, a gain, a data rate and a window
bound, while the same quantity read from a Modbus meter that reports amperes
needs nothing at all.

The adapter module therefore exposes **`CALIBRATION_SCHEMAS`**, a mapping from
sensor `type` to a declaration in the same grammar as `CONFIG_SCHEMA`. The
mapping may be empty; that is a statement, not an omission.

As with `CONFIG_SCHEMA`, the protocol definition identifies the module and does
not carry a copy.

### Refusals

| Situation | Result |
| --- | --- |
| Sensor supplies a non-empty `calibration`, and the pair has no schema | **Refused**, naming the protocol and type |
| Sensor supplies keys the selected schema does not declare | **Refused**, naming the full path |
| Selected schema has required fields the sensor omits | **Refused**, naming what is missing |
| Pair has no schema and the sensor supplies no calibration | Accepted |

A calibration block nobody declared is the unknown-key defect in the one place
where the consequence is a wrong measurement rather than a missing feature. A
sensitivity that does not reach the adapter does not fail loudly; it produces
readings that look plausible and are wrong by a constant factor.

## Unknown Keys

**An undeclared key MUST be refused, at configuration load, naming the key and
the protocol whose schema does not contain it.**

Not warned, not forwarded, not dropped. The whole class of defect this contract
addresses is a key that an operator wrote, the runtime accepted, and nothing
consumed — indistinguishable, from the operator's side, from one that worked.

A refusal MUST say what to do instead. A refusal that does not invites a
workaround.

### The reverse direction

An adapter MUST NOT read a key that no schema declares and no runtime-supplied
namespace provides. Such a read always resolves to the adapter's own default,
whatever the operator writes.

This has occurred, and is the mirror of the unknown-key case. Three adapters
once read `poll_interval_ms` while the runtime withheld it from metadata and did
not supply it, so each polled at its own default and the operator's value
governed only the runtime's own schedule. Two of them genuinely needed it and now
receive it; the third used the value nowhere and the read was removed rather than
fed, which is the correct answer to a read nothing consumes.

A conforming implementation SHOULD check this mechanically. Note the limit of
the obvious check: static extraction finds literal reads inside an adapter and
does not see a setting resolved through a shared helper, so an adapter that
resolves keys indirectly MUST pass presence and values explicitly rather than
handing the configuration object to a helper.

## What This Contract Does Not Decide

**Per-sensor circuit-breaker tuning.** `circuit_breaker` is runtime-supplied
here, so a sensor cannot vary it. The need is real — a flaky radio sensor and a
local I²C sensor have very different failure characteristics — but the bound is
not obvious. Opening a breaker blocks reads, so on a sensor feeding a
safety-critical condition an over-eager breaker removes the input the protection
path depends on. Neither tripping sooner nor later is unambiguously safe without
knowing what the sensor feeds.

A future revision MAY add a bounded per-sensor block. It MUST state the bound in
terms of what the sensor feeds, and the global setting MUST remain a limit the
sensor cannot escape in the unsafe direction.

**Which sensor types exist.** `type` is validated by the adapter that consumes
it. This contract governs configuration shape, not the sensor vocabulary.

## Vectors

A corpus accompanies this contract in [`vectors/`](vectors/), split by what a
failure would blame. It must exercise both the documents an operator writes and
the schemas an adapter declares, because a defect in either produces the same
outcome — a setting that does not do what it appears to.

**Schema loading**, refused before any document is validated:

- a protocol definition whose module is missing `CONFIG_SCHEMA`, and one missing
  `CALIBRATION_SCHEMAS`; an empty `CALIBRATION_SCHEMAS` accepted
- `type: object` without `properties`; `type: array` without `items`
- a `default` its own descriptor would reject
- a conditional group naming an undeclared field, an empty group, a field in
  two groups of one constraint, and two identical groups
- `required_unless` naming an undeclared field
- `deprecated` without `supersedes`, and `supersedes` naming a key absent from
  the schema
- `supersedes` naming a path whose intermediate segment is not a declared
  object, one descending through `items`, one whose target is itself
  `deprecated`, and an alias whose `type` differs from its target's
- a deprecated alias carrying a `default`, a bound, an `enum`, `properties`,
  `required_unless`, `fallback_from` or `must_be_subset_of`, each refused
- `fallback_from` or `must_be_subset_of` naming a path inside `sensors[]`
- `must_be_subset_of` on a non-array field

and at configuration load:

- `fallback_from` naming a field the configuration does not contain
- an inherited value the field's own descriptor would reject
- `must_be_subset_of` resolving to a non-array

**Sensor documents**:

- one accepted sensor per protocol, with declared defaults applied. This one
  cannot live in the shared corpus: the schemas are owned by the adapter
  modules, so a copy here would be the second declaration this contract
  forbids. It is a conformance check each implementation runs against its own
  definitions, and a conforming implementation MUST have one.
- an undeclared key, refused, naming the key and the protocol
- an undeclared key nested inside a declared object, refused by full path
- a reserved name — `sensor_id`, `sensor_type`, `circuit_breaker` — written as
  protocol configuration, refused
- a canonical field — `poll_interval_ms`, `calibration` — accepted, since these
  are not reserved
- a duplicate `id`, an empty `id`, and `poll_interval_ms` out of range, refused
- `poll_interval_ms: "1500"` and `id: 123`, refused rather than coerced
- a missing requirement under each of `required`, `required_unless`,
  `exactly_one_of` and `at_least_one_of`
- a `required_unless` satisfied by the sibling's **default**, accepted
- a `required_unless` satisfied by the sibling's **fallback**, accepted
- a `required_unless` still unsatisfied once the default is applied, refused
- a `required_unless` in a nested object resolving against its own scope rather
  than the parent's
- a **direct** conditional cycle, refused at schema load, naming the cycle
- an **indirect** conditional cycle across three or more fields, refused at
  schema load, naming the cycle
- a stray member of an unselected `exactly_one_of` group, refused, and a
  `default` on such a member not applied
- a deprecated alias accepted with a warning; the alias and its replacement
  together, refused
- an alias superseding a nested field, accepted and resolved into the target's
  position; the same alias written alongside that nested field, refused naming
  the full path; the alias written where the target only has a default,
  accepted
- a protocol default applied where the sensor is silent, and not applied where
  it is not
- a sensor-level allowlist narrowing accepted, and a widening refused
- an out-of-bounds value, a wrong type, and `7.0` where an integer is declared

**Calibration**:

- a `(protocol, type)` pair with no schema and a non-empty `calibration`,
  refused
- the same pair with no calibration, accepted
- a calibration key the selected schema does not declare, refused
- a required calibration field omitted, refused

Producer and verifier MUST NOT share code. A corpus checked only by the tool
that wrote it certifies that tool's defects.
