# Offline Tier C Token Contract v2

> Status: maturity `draft`; compatibility `amendable`; adoption: none
> recorded; proof: end-to-end `none`, HIL `none`, production `none`. Record:
> [status/offline-tokens/v2.json](../status/offline-tokens/v2.json).
>
> [offline-tokens/v1.md](v1.md) remains the format the runtime verifies today.


`offline-tokens/v1` remains the implemented legacy format. A runtime
conforming to this revision MUST NOT accept a v1 token as approval for any
Tier C action. This includes host-state Tier C actions that remain on the
existing approval workflow. Because offline-tokens/v2 requires a commissioned
zone, a host-state Tier C action has no offline-token approval path until a
resource-scoped approval contract defines one. `offline-tokens/v2` binds one
open proposal, device, exact action, target and commissioned zone and permits
no wildcard Tier C scope.

A v1 token approves any request for its `action_scope`, or for every action
when that scope is `*`, on its device, and names no proposal. That is the
breaking change: a v2 token approves one proposal and nothing else.

The Tier C binding below applies to Tier C actions capable of changing physical
state, which [tier-c-approval/v1.md](../tier-c-approval/v1.md#scope) governs.
Host-state Tier C actions and Tier B actions requiring approval remain on the
existing approval workflow outside this contract and outside
`tier-c-approval/v1`; no v1 token approves a host-state Tier C action there,
as above.

## Token Encoding

As v1: a base64url-encoded JSON payload (preferred), or the raw JSON payload
string.

A payload with no `token_version` claim is a v1 token. A payload whose
`token_version` is the integer `2` is a v2 token. Any other `token_version`
value is malformed and approves nothing.

`token_version` MUST have JSON integer type and value `2`; Boolean values are
not integers for this purpose. A number written with a fraction or an
exponent, such as `2.0`, is not a JSON integer, and a string such as `"2"` is
not a number. A verifier decides integer type from the JSON number token, not
from a decoded numeric value, so `2.0`, `2e0` and `2E0` are malformed even
where a decoder maps them to the same value as `2`. In Python, with a
decoder that keeps a number written with a fraction or an exponent as a
non-integer, the rule is `type(v) is int and v == 2`.

The payload is a JSON object whose member names are unique. A payload naming
any member twice, at any depth, is malformed and approves nothing, whichever
occurrence a decoder would keep.

## Signature

A v2 token signature is Ed25519 over
`"ori.offline_token.v2" || NUL || canonical(payload_without_signature)`. A v1
verifier, which verifies the unprefixed v1 preimage, therefore MUST reject a v2
signature. Implementations MUST select the signature domain from the exact
token version before verification and MUST NOT use trial verification or fall
back between versions.

`"ori.offline_token.v2"` is those 20 ASCII bytes, without quotes, and NUL is
one zero byte. `canonical(payload_without_signature)` is the Profile 2
canonical form of [signing/v2.md](../signing/v2.md) applied to the payload
without `signature`: Python `json.dumps(sort_keys=True, separators=(",", ":"),
ensure_ascii=False, allow_nan=False)` semantics, in which only `"`, `\` and
U+0000–U+001F are escaped and integers are written in decimal without exponent.
It is the v1 preimage: the payload object without its `signature` member,
serialized as JSON with object keys sorted by code point, no whitespace between
tokens, non-ASCII characters written as UTF-8 rather than escaped, and encoded
as UTF-8. `token_version` is inside that preimage, so removing or changing it
invalidates the signature.
`signature` is `ed25519:` followed by the padded standard base64 of the
64-byte signature, as in v1.

Domain separation needs no separate key: the prefix, not the key, keeps a v1
verifier from accepting a v2 token. It holds only for tokens signed in the v2
domain, so an issuer MUST sign a v2 token over the v2 preimage and never over
the unprefixed one.

## Required Claims

| Claim | Type | Required | Notes |
| --- | --- | --- | --- |
| `token_version` | `int` | Yes | `2` |
| `token_id` | `string` | Yes | Unique token ID; the key a durable approval consumes |
| `device_id` | `string` | Yes | Must match the runtime device and the proposal's device |
| `proposal_id` | `string` | Yes | The open Tier C proposal this token approves |
| `action_scope` | `string` | Yes | The exact action the proposal commands; never `*` |
| `target` | `string` | Yes | The proposal's target |
| `zone_id` | `string` | Yes | The commissioned zone the proposal commands |
| `issued_at` | `int` (unix seconds) | Yes | Issued time |
| `expires_at` | `int` (unix seconds) | Yes | Expiry time |
| `nonce` | `string` | Yes | Signed randomness, as v1; consumption is keyed by `token_id`, not by `nonce` |
| `signature` | `string` | Yes | Ed25519 signature field, as v1 |

## Tier C Binding

An offline token used for Tier C MUST name `proposal_id`, `device_id`, the
exact action, its target and commissioned zone. A wildcard action scope does
not authorize Tier C.

For Tier C a token therefore carries `proposal_id`, an exact `action_scope`,
`target`, and `zone_id`, each of which must equal the open proposal's, in
addition to the claims above; a token missing any of them, or naming another
proposal, action, target or zone, approves nothing. The admission it then
reaches is admission in [tier-c-approval/v1.md](../tier-c-approval/v1.md).

The token's expiry limits token validity only. It cannot create, extend or
revive proposal authority; the proposal's monotonic deadline governs admission.

Claiming the token's `token_id` and committing the Tier C approval are one
transaction. If either operation fails, neither commits. A token MUST NOT be
consumed by a reply that did not become a durable approval. A `token_id`
already claimed approves nothing.

## Verification Rules

Runtime verifies, in addition to the v1 rules for decoding,
`issued_at`/`expires_at` skew and replay:

- the exact `token_version` selects the signature domain before any signature
  is verified: a payload without it is v1, which is never Tier C approval, and
  any value other than the integer `2` is malformed and is not verified
- the signature verifies over the v2 preimage under the configured offline
  token public key, and over no other preimage
- `token_version` is `2`; a v1 token is refused as Tier C approval
- `device_id`, `proposal_id`, `action_scope`, `target` and `zone_id` each equal
  the open proposal's
- `action_scope` is not `*`
- the payload names no member twice
- the `token_id` claim commits in the same transaction as the approval

## Vectors

[vectors/tier-c-binding-v2.json](vectors/tier-c-binding-v2.json) fixes the binding
rules, including a v1 token parsed as v1 and refused, and a v1 token refused
for a host-state Tier C action, and
`scripts/check-tier-c-approval-vectors` replays it through the admission model
of [tier-c-approval/v1.md](../tier-c-approval/v1.md).

[vectors/signing-domain-v2.json](vectors/signing-domain-v2.json) fixes the signature
domain with real Ed25519 signatures under a published test key, never a
production key: a valid v2 token fails v1 verification, a valid v1 token fails
v2 verification, removing or changing `token_version` invalidates the
signature, a missing version and the values `"2"`, `true`, `3`, `2.0`, `2e0`
and `2E0` refuse under v2, a v2 token signed over the unprefixed preimage
refuses under v2, and a valid v2 token whose claim carries `<`, `&` and U+2028
verifies under v2 over their unescaped UTF-8 bytes, and a payload naming
`token_version` twice refuses under v2 although a last-occurrence decoder would
read a valid token. The `2e0` and `2E0` cases
carry the valid v2 signature over `"token_version":2`, so only a verifier that
decides from the number token refuses them for their version. The
same checker verifies every signature and derives every verdict from this
section.
