# Firmware Command Result Contract v1

> Status: maturity `draft`; compatibility `amendable`; adoption: none
> recorded; proof: end-to-end `none`, HIL `none`, production `none`. Record:
> [status/firmware-command-result/v1.json](../status/firmware-command-result/v1.json).

A runtime that publishes a firmware command has proved that it signed and sent
it, and nothing further. [firmware-commands/v2.md](../firmware-commands/v2.md)
defines the command and the device's verdicts, and reports a refusal only as a
`command_rejected` fault that names neither the command nor its sequence. This
contract defines what a device signs about each command it verifies, how a
runtime joins that report to the command it issued, and what the runtime may
conclude from it. Its one rule above every other: **published is not
executed, and accepted is not executed either.**

It is a minimum slice. It names the events, correlates them, and fixes what
each one proves. It does not admit firmware-backed actuators into an in-force
safety zone, and it gives no event the power to reconcile a Tier C dispatch.

## What this contract is not

- **It is not physical evidence.** The strongest event a device signs here is
  that its driver write returned success. That is a fact about the
  microcontroller's output, not about the coil, the contacts or the circuit.
  An outcome observed on the circuit is
  [`terminal_outcome_observed`](#runtime-lifecycle), recorded by the runtime
  from an observer it names, and no device in this version produces one.
- **It grants no authority.** A result never authorizes, approves, retries or
  suppresses anything. It never establishes or extends runtime supervision or
  liveness, and a device cannot hold a backstop suppressed by publishing
  results.
- **It does not change the command.** The command object, its signature, its
  verdicts and its sequence rules are
  [firmware-commands/v2.md](../firmware-commands/v2.md)'s, unchanged.
- **It does not replace the fault.** A device that declares this contract keeps
  signing every `command_rejected` fault
  [firmware-telemetry/v2.md](../firmware-telemetry/v2.md#signed-fault-events)
  requires, unchanged.

## The result object

A command result is the fifth Layer 1 evidence family on the telemetry topic,
discriminated by its top-level `command_result` key, under
[firmware-telemetry/v2.md](../firmware-telemetry/v2.md#layer-1-evidence-families).
It is signed by the device key over its canonical bytes, exactly as the other
four families are, with no signing domain.

```json
{"command_result":{"alg":"ed25519","boot_id":41,"capability_hash":"sha256:<64-lowercase-hex>","cmd_seq":1047,"command_digest":"sha256:<64-lowercase-hex>","device_id":"ori-fw-7c9f2b3a","device_uptime_ms":925310,"kind":"driver_reported","outcome":"ok","posture":"sealed_flash","seq":130486,"v":1},"signature":"ed25519:<base64-64-byte-signature>"}
```

| Field | Type | Notes |
| --- | --- | --- |
| `v` | `int` | `1`. |
| `alg`, `device_id`, `boot_id`, `seq`, `capability_hash`, `posture`, `device_uptime_ms` | | The Layer 1 identity and freshness fields, with [firmware-telemetry/v1.md](../firmware-telemetry/v1.md)'s semantics and drawn from the device's one `(boot_id, seq)` stream. `capability_hash` is the manifest hash in force when the result is signed. |
| `cmd_seq` | `int` | The `cmd_seq` of the command the result answers, as the command carried it. |
| `command_digest` | `string` | `sha256:` and 64 lowercase hex digits: SHA-256 of the command's [signing preimage](../firmware-commands/v2.md#signing-domains), the domain `ori.firmware_command.v2`, one NUL byte, and the command object's bytes exactly as received. |
| `kind` | `string` | One of the [kinds](#kinds) below. |
| `outcome` | `string` | Closed per kind, as the table below gives. Empty where the kind takes none. |

Every member is required, and the object's members are exactly these. A
receiver refuses a command result with any other member, a missing one, a
`kind` outside the table, or an `outcome` the table does not allow for its
`kind`, even when its signature verifies.

`command_digest` is taken over the preimage the device verified, never over a
re-encoding of the command, so it costs the device one SHA-256 over bytes it
already holds. Including the domain binds the digest to the command's purpose:
the same object bytes under the liveness domain have another digest.

### Kinds

| `kind` | `outcome` | Signed when | It proves | It does not prove |
| --- | --- | --- | --- | --- |
| `accepted` | `""` | The command passed every check of [firmware-commands/v2.md](../firmware-commands/v2.md#rate-limited-refusal), the rate policy included, and the device decided to act on it. | The device verified this command and decided to act on it. | That anything was driven, or anything happened. |
| `refused` | `capability_mismatch`, `unknown_action`, `rate_limited` or `storage_failure` | The command's signature verified, its `cmd_seq` was above the mark, and a later check refused it. | The device refused this command, under that verdict. Nothing was actuated. | Anything about a later command. |
| `duplicate` | The stored disposition, under [Duplicate and conflict](#duplicate-and-conflict) | The command repeats the last fresh command exactly. | The device recognised a repeat and did not act on it again. | That the first delivery executed. |
| `conflict` | `""` | The command reuses the last fresh `cmd_seq`, under the same `capability_hash`, with different bytes. | Two different commands were signed for one sequence. Nothing was actuated. | Which of the two the runtime meant. |
| `attempted` | `""` | The device recorded the operation in its rate policy and began the driver write. | The device began driving the output for this command. | That the write succeeded. |
| `driver_reported` | `ok` or `error` | The driver write returned, or the device found no driver for the command's channel and wrote nothing (`error`). | The driver write for this command returned success, or failed. | The state of the coil, the contacts or the circuit. |

**Signed when names what is attested, not the moment.** A device signs the
results for one command in the order of this table, so their `seq` order
shows the sequence. It MAY sign `accepted` and `attempted` after its driver
write returns, so that no signature and no buffer append stands between the
decision and the write of a protective `relay_open`. It MAY omit both when it
signs `driver_reported`. A consumer MUST NOT require `accepted` or
`attempted` before `driver_reported`. A command whose channel has no driver
mapping passed every check of firmware-commands/v2 and began no write: the
device signs `driver_reported` with `error`, and no `attempted`.

`feedback_observed` is reserved for an observation of the circuit by an input
the device's manifest commissions for that channel. No kind in this version
carries it, a device MUST NOT sign it, and a receiver refuses it as an unknown
kind.

**No result for an unauthenticated message.** A device signs a command result
only for a command whose signature verified. A message refused as `malformed`,
`wrong_device` or `bad_signature` gets no result. Its fields are the sender's
to choose, and a device that signed a reply to each such message would sign
bytes for anyone who can publish to its command topic, and fill its evidence
ring for them. Those refusals are reported by the `command_rejected` fault
alone, as today.

**No result for a replay, and one duplicate at most.** Anyone who captured
one valid command holds bytes whose signature verifies. A device that signed a
result for every replay of it would sign and buffer without bound for them,
evicting the oldest evidence first. So a command refused as `replayed` gets no
result, only its `command_rejected` fault, and a device signs at most one
`duplicate` result for a `cmd_seq` in a boot; later repeats get none. A
runtime never reissues a command under
[firmware-commands/v2.md](../firmware-commands/v2.md#unresolved-commands), so a
duplicate reaches a device only by redelivery, and one answer is enough.

### Duplicate and conflict

A device judges a repeat only against **the last fresh command**: the command
whose `cmd_seq` set its high-water mark. It holds that command's `cmd_seq`,
its `command_digest`, the device's accepted `capability_hash` when it recorded
that command's freshness, and its
stored disposition, in one durable record that is written atomically with the
mark. A record written in two parts can tear on power loss into a mark that
disagrees with its digest, which would report a conflict as a duplicate or the
reverse.

For a command whose signature verified:

| `cmd_seq` against the mark | Stored `capability_hash` | `command_digest` | Result |
| --- | --- | --- | --- |
| Below it | any | any | No result: a `command_rejected` fault, `replayed`, only |
| Equal to it | Differs from the device's current one | any | No result: a `command_rejected` fault, `replayed`, only |
| Equal to it | Equals the current one | Equals the stored one | `duplicate`, with the stored disposition, once a boot |
| Equal to it | Equals the current one | Differs | `conflict` |
| Above it | | | Freshness passes; the command is judged as a new command |

A command at the mark is judged by this table whatever `capability_hash` it
carries itself. One whose own hash differs from the device's, under a stored
record of the current hash, has a different digest, so it is a `conflict`,
never `capability_mismatch`: the runtime signed two objects for one sequence.
A command whose freshness write failed (`storage_failure`) stored nothing, so a
resend of it meets no record: its `cmd_seq` is still above the mark, and it is
judged as a new command.

- **A repeat never actuates again.** Neither a `duplicate` nor a `conflict`
  drives any output.
- **A duplicate answers with what the device recorded, never with "executed".**
  The device persists the mark after the signature and before the capability
  checks, so the last fresh command may be one it went on to refuse. A
  duplicate's `outcome` is the last disposition the device made durable for
  that command, one of:
  - `pending`: freshness was recorded and no later disposition was made
    durable. Whether the driver was asked is unknown. A device that crashed
    between its driver write and recording the write's result reports
    `pending` for a command it did drive, so `pending` is in doubt, as
    `timed_out` is, and a consumer MUST NOT read it as "not acted on";
  - `capability_mismatch`, `unknown_action` or `rate_limited`: the device
    refused the command under that verdict, and nothing was actuated;
  - `driver_ok` or `driver_error`: the driver write for the command returned
    success, or failed. `driver_ok` is not a physical state.

  A device records at most two dispositions for a command: `pending` with the
  mark, and the final one once it is known. It never records "accepted", and
  never one better than what happened. No disposition means "executed". If it
  could not record a refusal's disposition, the record stays `pending`, and a
  later duplicate of that refused command answers `pending`: in doubt, though
  nothing was actuated, and a consumer cannot tell which.
- **The signed result never waits on the stored record.** A device signs
  `driver_reported` from its driver write's actual return, whether or not it
  then made that disposition durable. When it could not, the record stays
  `pending`, a later duplicate answers `pending`, and the device reports the
  failed write as a `storage_degraded` fault. It never reports `refused` with
  `storage_failure` for a command it drove: that verdict means the freshness
  write failed and nothing was actuated, as
  [firmware-commands/v2.md](../firmware-commands/v2.md#error-semantics)
  defines it.
- **A judgment never crosses an approval epoch.** Re-approval changes what a
  device is authorized to do, so a stored judgment made under another
  `capability_hash` never answers for a command under the current one. The
  mark itself stays device-global, as
  [firmware-commands/v2.md](../firmware-commands/v2.md#error-semantics) has it.
- **Older sequences stay replays.** A device tells a duplicate from a conflict
  only at the last fresh `cmd_seq`. Anything below the mark is `replayed`,
  whatever its bytes, and gets no result.
- **A conflict is a security event.** Two different commands signed for one
  sequence mean a runtime defect or a compromised runtime key. A runtime MUST
  record a conflict it receives as a security event, and MUST NOT resolve it
  by choosing either command.

## Publication and durability

A command result is signed when it is produced, like every Layer 1 family,
and buffered and published as signed bytes through the device's offline
evidence buffer, in `seq` order, under
[firmware-telemetry/v2.md](../firmware-telemetry/v2.md#layer-1-evidence-families).
Every kind is buffered. None is sent ahead of the buffer, because a result
that overtook buffered records with lower `seq` would move a receiver's mark
past them, and every one of them would then be refused as a replay.

- Its freshness fields say when the device signed the report, which follows
  the driver's return for `driver_reported`. They never say when the driver
  acted, or when the command arrived.
- `cmd_seq`, `command_digest` and `kind` say what it answers.
- A buffer that is full loses its oldest records, whatever their family. A
  lost result is a gap in `seq` the receiver can see, and nothing in this
  contract ranks one kind above another for survival.
- A result delivered twice by the broker is the same `(device_id, boot_id,
  seq)` and is refused the second time as a replay, as every family is.

## Correlation

A runtime records, for every command it signs, the device, the `cmd_seq` and
the `command_digest` of the preimage it signed, durably and before it
publishes. A record made after publishing could be lost to a crash in between,
leaving a command the device may run with nothing to join its results to. It
joins a verified command result to that record by all three, and by nothing
else:

- A result whose `(device_id, cmd_seq)` names no command the runtime holds a
  record of attaches to no command. That includes a result buffered through a
  long outage, or arriving after a restart, once the runtime no longer holds
  the record. The runtime records it as an uncorrelated result: evidence only,
  never a refusal, a reconciliation or "executed", and never applied to any
  command. Late truth therefore always has a place.
- A result whose `(device_id, cmd_seq)` names a command the runtime recorded,
  but whose `command_digest` differs, says that the device verified, under the
  runtime's key and at a sequence the runtime used, bytes the runtime did not
  sign for it. That is the runtime-side image of `conflict`: a runtime defect
  or a compromised key. The runtime MUST record it as a security event, and
  MUST NOT apply it to any command.
- The stream `seq` is never a correlation key. It orders the device's
  evidence; it says nothing about which command a result answers.

## Runtime lifecycle

A runtime records a command's lifecycle as events it never rewrites, each
carrying the command's `(device_id, cmd_seq, command_digest)`:

| Event | Recorded when |
| --- | --- |
| `signed` | The runtime signed the command and recorded it, before publishing. |
| `issued` | The broker accepted the publication. |
| `publish_unconfirmed` | Acceptance was not confirmed: a timeout, a refused return code, a cancellation. The command may still have reached the broker and the device. It is in doubt, never "not sent", and results still attach to it. A runtime records at most one of `issued` and `publish_unconfirmed` for a command, and never records `issued` after `publish_unconfirmed`, even if an acknowledgement later arrives. |
| `device_accepted`, `device_refused(verdict)`, `device_duplicate(disposition)`, `device_conflict`, `actuation_attempted`, `driver_reported(ok \| error)` | A verified command result of the matching kind attaches to the command. |
| `terminal_outcome_observed(observer, outcome)` | An observer the runtime names (a commissioned sensor, or a person through an attestation that stays human evidence) reports the circuit's state after the command. No device produces this event in this version. |
| `timed_out` | The command's result deadline, measured from `signed`, passed with no final result attached: no `driver_reported`, `device_refused` or `device_conflict`, and no `device_duplicate` with a final disposition. `device_accepted`, `actuation_attempted` and `device_duplicate(pending)` are not final. |

Derived from the events, and never one of them: **`outcome_uncertain`** holds
for every signed command that has no `terminal_outcome_observed`. Events and
posture compose: a command can be `driver_reported(ok)` and `outcome_uncertain`
at once, and an accepted command whose report never arrived is both
`timed_out` and `outcome_uncertain`.

- **Absence is never a refusal.** No result, a `seq` gap, a `timed_out` and an
  `outcome_uncertain` are each "in doubt". A runtime MUST NOT record any of
  them as a refusal, a failure or a success.
- **Late truth appends.** A result that attaches after `timed_out` is recorded
  as a new event. The `timed_out` event stays, because it was true when
  recorded, and no earlier event is rewritten or removed.
- **Executed means observed and attributed.** A runtime concludes that a
  firmware command executed only when a `terminal_outcome_observed` that
  matches the command has attached, and so has positive device evidence that
  the device acted on that command: `driver_reported(ok)`, or a
  `device_duplicate` whose disposition is `driver_ok`. A matching observation
  without that evidence shows the circuit in the commanded state, not that this
  command put it there: an interlock or a person may have, or the device may
  never have received the command. The runtime records it as the commanded
  state observed and not attributed, which is neither executed nor uncertain,
  whatever the absence is: a refusal, a conflict, a duplicate answering a
  refusal, or no driver result at all.
- **No boolean is set short of that.** events/v1 `executed`, events/v2
  `approved_action_outcome` and the boolean `executed` in the payload of an
  evidence/v3 `SAFETY_ACTION_EXECUTED` event have no value that means "in
  doubt". Until successor versions of those contracts define one, a firmware
  command's outcome is recorded in this lifecycle, and such a boolean may be
  set true only from the conclusion above, never from anything short of it.
- **The deadline is the release's, under a ceiling.** Each runtime release
  documents its result deadline: the time after `signed` at which, with no
  final result attached, it records `timed_out`. That deadline MUST be no
  more than 300,000 ms. A device reconnecting with a full evidence buffer
  publishes its results only after the backlog, which the reference firmware
  drains in roughly 75 to 130 s by arithmetic from its loop and buffer, not by
  measurement. A release whose measured drain exceeds its deadline raises the
  deadline, within the ceiling, and never drops results to meet it. A result
  later than the deadline is in doubt until it attaches, and then appends.

### Tier D

[safety-profile/v1.md](../safety-profile/v1.md) ends a latched trip's
`open_protected_circuit` attempts when the driver accepts one. For a
`firmware_channel` zone, **driver acceptance is `driver_reported(ok)`, or a
`device_duplicate` whose stored disposition is `driver_ok`, and nothing
earlier.** The second is the device re-signing the same fact for the same
command, and after a buffer loss it can be the only copy.

- `device_accepted` and `actuation_attempted` are lifecycle events only. A
  device that accepted a command and then failed at its driver would, if
  acceptance ended the attempts, leave the hazard with no further attempt.
- `driver_reported(error)`, `device_refused`, `device_conflict`, a
  `device_duplicate` with any other disposition, `timed_out`,
  `publish_unconfirmed`, a `seq` gap and no result each leave the attempts
  going, on the safety registry's bounded backoff.
- A `driver_reported(ok)` that attaches late ends further attempts from then
  on, and changes nothing already done.
- `terminal_outcome_observed` does not end the attempts, even when it matches.
  safety-profile/v1's stop conditions are driver acceptance, a successful local
  reset and shutdown, and an observation is none of them. Letting whatever can
  record an observation stop the one authority with no human in the loop would
  be a new way to switch protection off. The attempts that continue are
  physical no-ops. Whether an observed open circuit may end them is a question
  for a successor of safety-profile/v1, not for this contract.
- **An observed failure is critical.** A `terminal_outcome_observed` that
  differs from the command, on a command issued for a Tier D trip, is the one
  case where the runtime knows the protection failed while the hazard may
  stand. The runtime MUST raise it as a critical operator and audit event, and
  the pair reads unprotected. It does not restart attempts that ended at
  driver acceptance; whether it should belongs to the same safety-profile/v1
  successor question.
- `driver_reported(ok)` ends attempts; it does not end `outcome_uncertain`.
  A runtime that has stopped attempting still presents the outcome as
  uncertain until an observer reports the circuit.
- **Commanded, not observed.** A consumer MUST NOT present
  `driver_reported(ok)` as the physical outcome, in health, operator notices
  or evidence. A pair whose trip ended at `driver_reported(ok)` with no
  `terminal_outcome_observed` never reads as protected, and a notice of it
  says the circuit was commanded open, not that it opened.
- Re-issuing is physically idempotent because only the same protective outcome
  is ever re-issued: each attempt is a `relay_open`, which no rate policy
  refuses or delays, under
  [firmware-commands/v2.md](../firmware-commands/v2.md#rate-limited-refusal).

This does not make a `firmware_channel` zone eligible for an in-force safety
zone. [runtime-health/v3.md](../runtime-health/v3.md) requires a later
specification for that, and this contract is not it.

### Tier C

A command result is evidence only. It MUST NOT reconcile a
[tier-c-approval/v1.md](../tier-c-approval/v1.md) dispatch, under either of
that contract's forms. Form b's commissioned feedback is an observation
independent of the actuator, and a device reporting on its own command is not
independent. A dispatch stays `dispatch_outcome_unknown` or
`dispatch_not_proven` until that contract's own reconciliation resolves it.

## Declaration

A device declares that it signs command results in one optional member of its
signed capability manifest, defined by
[firmware-telemetry/v2.md](../firmware-telemetry/v2.md#command-results):

```json
"command_results": "firmware-command-result/v1"
```

- A runtime expects command results only from a device whose accepted manifest
  carries it. From any other device, the absence of a result means only that
  none is reported: every command stays `outcome_uncertain`, and a Tier D zone
  on that device keeps attempting as safety-profile/v1 requires.
- Declaring it changes the device's `capability_hash`, which is a capability
  transition: the provisioning approval for the earlier hash no longer covers
  the device, and it needs approval for the new one.

### Adoption order

The runtime adopts first. A firmware release that declares `command_results`
MUST be deployed only to devices served by a runtime release that accepts the
member, and both release checklists carry that ordering.

Nothing in this version lets a device learn whether its runtime accepts the
member, so the ordering is a release rule, and the runtime's refusal of an
unknown manifest member is its backstop. Its cost, stated plainly: a device
that declares early is refused at provisioning, or, after an upgrade in place,
its telemetry under the new `capability_hash` is refused against its old
anchor, and its commands and supervision stop. That fails towards the device's
local protection and loses evidence, Tier D inputs included, until the runtime
accepts the member and the device is approved again. It is never a silent
actuation.

## Limits and later versions

- **Driver success is not physical state.** No board in this version has an
  input that observes the circuit, so no device signs anything stronger than
  `driver_reported`. `feedback_observed` waits for a commissioned feedback
  input and a later version.
- **Results queue behind a backlog.** Results are published in `seq` order
  behind every buffered record, so after a reconnect a result can arrive
  minutes after the driver acted. While they queue, a Tier D zone keeps
  re-issuing the protective outcome on the safety registry's backoff, each
  attempt a physical no-op, and each adds a command and its results to the
  device's buffer: about one command per backoff step. A release sizes its
  buffer and its deadline knowing both.
- **Repeated opens delay the next close.** A device's rate policy counts every
  `relay_open`, never refusing or delaying it, so a run of re-issued opens
  restarts the interval before the next permitted `relay_close`, and that close
  can be refused as `rate_limited` for longer. That fails safe.
- **Results are as readable as readings.** They share the telemetry topic, so
  any client that can read a device's telemetry can read its command results.
  They carry no secret: a sequence, a digest and a disposition.
- **An observation ends nothing in Tier D.** A matching observation does not
  end a trip's attempts, and a differing one does not restart them. Both wait
  for a successor of safety-profile/v1, which would decide them together.
- **An unconfirmed publication can arrive late, as a replay.** A command
  whose publication was unconfirmed can reach the device after a later
  command. The later one set the mark, so the earlier is `replayed`, signs no
  result, and its fault names no `cmd_seq`. The runtime sees
  `publish_unconfirmed` and then `timed_out` for it, which is in doubt and not a
  device gone silent. A Tier D zone is unaffected: the later command carries
  the attempt.
- **Only the last fresh command is remembered.** A repeat of any older command
  is `replayed`, and the device cannot say whether it was a duplicate.
- **Unauthenticated refusals stay uncorrelated.** A `malformed`,
  `wrong_device` or `bad_signature` command is reported only by its
  uncorrelated fault.
- **The adoption order is a release rule.** A positive signal from the runtime
  that it accepts the member would need a new version of the provisioning
  approval, which approves a manifest declaring it, checked against what the
  device already declares, so that no received message ever changes what a
  device declares.

## Representable and enforced

This contract and its corpus make the result representable. No runtime parses,
stores or correlates a command result yet, and no device signs one: the
runtime's firmware command path records the `cmd_seq` and nothing else, and the
runtime's actuator interface returns a boolean that cannot carry "in doubt".
Enforcement belongs to the runtime, which records the digest, correlates, and
types the actuator result (ori-platform/ori-runtime#482), and to the reference
device firmware.

## Golden vectors

The corpus for this contract is
[command-result-vectors-v1.json](command-result-vectors-v1.json), held here
beside this document. Its SHA-256 is
`d2fabd3f5d762134053a339e25782525f0d409b581fb2ee4a513d8cfaf6e7a60`.
Implementing repositories copy it byte for byte, pin that digest, and never
generate its expectations from their own behaviour. It signs with the
disclosed test-only seeds of
[firmware-telemetry/v2.md](../firmware-telemetry/v2.md#golden-vectors)'s fault
corpus, for the device key, and of
[firmware-commands/v2.md](../firmware-commands/v2.md#command-vectors)'s command
corpus, for the runtime command key. They MUST NOT be used outside
deterministic tests.

It holds four groups:

- **`results`**: signed telemetry-topic payloads, each judged on its own
  against the corpus's `verifier_context`. A receiver accepts every case
  marked `accept` and refuses every other case with its declared reason. Every
  refusal's signature verifies, so a receiver that refuses it has refused it
  for that reason and not at the signature. The reasons are closed:
  - `member_set`: the object has a member this contract does not define, or
    lacks one it requires;
  - `unsupported_version`: `v` is not the integer `1`;
  - `unknown_kind`: `kind` is not one of the six kinds, `feedback_observed`
    included;
  - `outcome_not_allowed`: `outcome` is not one its `kind` allows;
  - `digest_form`: `command_digest` is not `sha256:` and 64 lowercase hex
    digits;
  - `family_keys`: the payload carries more than one family key beside
    `signature`.
- **`digests`**: commands signed by the runtime test key, each with the
  `command_digest` this contract defines for it.
- **`judgments`**: a device's stored record and mark, its current
  `capability_hash`, and a verified command's `cmd_seq`, `command_digest` and
  `capability_hash`, with the result the [Duplicate and conflict](#duplicate-and-conflict)
  table gives: a kind and outcome, `none` where the table gives no result, or
  `new` when freshness passes.
- **`lifecycle`**: what happened to a command, in order: `signed`, `issued`,
  `publish_unconfirmed`, each device result as it attached
  (`device_duplicate_` followed by its disposition), `deadline_passed`, and
  `terminal_outcome_observed_matches` or `_differs`, whether the observed state
  is the one commanded. Each is a command issued for a Tier D trip. With it,
  what the runtime may conclude: whether it records `timed_out`, whether the
  trip's attempts for the command have ended, whether `outcome_uncertain`
  holds, whether it may record the command as executed, and whether it raises
  the critical event of an observed failure.

`scripts/generate-firmware-command-result-vectors-v1` reproduces the file byte
for byte. `scripts/check-firmware-command-result-vectors-v1` shares no code
with it: it reads the kinds, outcomes, reasons and the duplicate table from
this document, recomputes every canonical byte, digest and signature with its
own arithmetic, and confirms that each case is judged as declared, each
refusal for its declared reason alone.
