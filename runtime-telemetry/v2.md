# Runtime Telemetry v2

> Status: Design target, pre-ratification. No shipped conforming consumer.
> Supersedes: `runtime-telemetry/v1.md`, which is retained and accurate for
> consumers that have not migrated.
> Primary consumer: product provisioning backends during phone and lightweight
> deployments.

This contract defines the direct HTTP telemetry boundary from `ori-runtime` to a
product backend. It exists for phone and lightweight deployments where running a
LAN `ori-gateway` is unnecessary or unavailable.

This is not the runtime/gateway MQTT boundary. Gateway exports remain defined in
`gateway-api/v1.md`.

## Why v2 Exists

Under v1 a producer and a receiver can both conform while readings are signed,
sent, answered `200`, stored as nothing, and recorded by the device as
delivered. v1 permits it because two of its sentences disagree: one lets a
receiver reject a whole batch on `sequence`, the other says event IDs are the
idempotency keys. `sequence` has no stated lifetime, a retried batch has no
stated identity, and the success response is undefined, so neither party is
obliged to notice.

v2 resolves it in the direction v1 already pointed, and the resolution is
breaking for a receiver that keys on `sequence` and for a producer that ignores
the response body. Those are shipped behaviours, so this is a new version
rather than an amendment in place.

**The request body shape does not change, and neither does its
`schema_version`.** A `sensor.reading` batch is byte-identical under v1 and v2,
including `"schema_version": "runtime.telemetry.v1"`, and the golden fixture
below is the one v1 carries. The payload's `schema_version` identifies the body
shape; this document's version identifies the behaviour around it. Re-stamping
an unchanged body would force every producer and every byte fixture to change
for no semantic reason, and the cross-language byte agreement is the expensive
part to re-prove.

**A receiver therefore cannot tell a v1 producer from a v2 one, and does not
need to.** v2 receiver behaviour is strictly safer for a v1 producer: per-event
idempotency never discards more than batch rejection did, and a defined
response body only adds members a v1 producer ignores. The migration is
receiver-first — **a receiver adopts v2 before or with its producers**, and the
reverse order is worse than not migrating at all. A v2 producer re-sends a
retained batch under its original `sequence`; a v1 receiver keying on `sequence`
then rejects every attempt rather than the first, so a batch that v1 would
eventually have delivered under a fresh sequence is never delivered. Retry
identity is safe only once the receiver has stopped treating `sequence` as a
key.

## Authority Boundary

Runtime telemetry export is observational only.

- It mirrors real runtime `sensor.reading` events, and sensor liveness, to a
  product backend.
- Backend availability must never affect Tier B, Tier C, or Tier D action
  authority.
- The backend must not use either route to mutate runtime configuration,
  thresholds, relay state, DevicePolicy, update intent, or actuator settings.
- Tier D remains deterministic and local.
- Nothing a receiver derives from either route may become an input to an action,
  a threshold, or a policy on the device.

## Routes

| Route | Body schema | Carries |
|---|---|---|
| `POST <endpoint>` | `runtime.telemetry.v1` | a batch of `sensor.reading` events |
| `POST <endpoint>/sensor-status` | `runtime.sensor_status.v1` | a full snapshot of declared sensor liveness |

The status route is the configured `telemetry_export.endpoint` with
`/sensor-status` appended. There is no second configuration key: a deployment
that can reach one route can reach the other, and a separate endpoint would let
the two diverge to different receivers holding one device's state.

Both routes use the same transport, headers, key, canonicalisation and signing
rules. They differ in their bodies, their responses, and their retention rules,
because one carries history and the other carries state.

Sensor status is a separate route rather than a new `event_type` in the reading
batch. A new `event_type` is breaking for a receiver that admits only
`sensor.reading` and answers anything else `422`, and that answer rejects the
readings travelling in the same batch — so a report that a meter has stopped
would cost the readings of every meter that has not. A separate route cannot do
that to a reading under any receiver behaviour, including a receiver that has
not implemented it.

## Transport

| Field | Value |
|---|---|
| Protocol | HTTPS POST |
| Content type | `application/json` |
| Runtime config | `telemetry_export` |
| Default state | Disabled |
| Loopback exception | `http://localhost` or `http://127.0.0.1` allowed for local development |

Production and public endpoints must use HTTPS.

## Request Headers

| Header | Required | Notes |
|---|---:|---|
| `Authorization` | Yes | `Bearer <device_api_key>` |
| `Content-Type` | Yes | `application/json` |
| `X-Ori-Device-Id` | Yes | Must match payload `device_id`. |
| `X-Ori-Timestamp-Ms` | Yes | Unix milliseconds UTC when the request was signed. |
| `X-Ori-Signature` | Yes | `v1=<hex hmac sha256>` |

The device API key is read from the runtime environment variable named by
`telemetry_export.api_key_env`. The secret must not be committed to `ori.yaml`.

The signature prefix stays `v1=`: the signing construction is unchanged, and a
new prefix would invalidate every fixture and every verifier for a rule that
did not move.

## Signature

The runtime signs:

```text
timestamp_ms + "." + canonical_json_body
```

Using HMAC-SHA256 with the device API key as the secret. The same rule applies
to both routes.

The JSON body must be canonicalized before signing:

- encode as UTF-8 and emit non-ASCII characters directly rather than as
  `\uXXXX` escapes;
- sort object keys lexicographically at every nesting level;
- preserve array order;
- emit no whitespace outside string values;
- escape JSON strings according to RFC 8259;
- reject `NaN`, `Infinity`, and `-Infinity`;
- require integers to satisfy `|n| <= 9007199254740991` (`2^53 - 1`);
- require non-integer numbers to be finite and either exactly zero or have
  magnitude in `[1e-4, 1e16)`;
- serialize non-integer numbers as the shortest round-trip decimal in fixed
  notation with a mandatory fractional part, preserving `-0.0`; and
- never emit exponent notation in canonical bytes.

These are the same proven Python/Rust numeric agreement rules used by
`firmware-telemetry/v1.md`. Producers must reject values outside the agreement
zone rather than sign implementation-dependent bytes.

The backend must, on both routes:

- verify the bearer token/device API key;
- verify `X-Ori-Device-Id` matches payload `device_id`;
- verify timestamp skew within backend policy;
- verify the HMAC signature before accepting the body.

## Idempotency

**The idempotency key is `(device_id, event_id)`, and it is per event.**

A receiver must store every event in a batch that it does not already hold, and
must ignore only those it already holds. A batch must not be rejected, in whole
or in part, because it carries an event the receiver already holds.

v1's licence to "reject replayed or duplicate batches using `device_id`,
`sequence`, and/or event IDs" is withdrawn. Batch-level rejection is what turns
one known event into the loss of every new reading beside it, and a receiver
that rejects on `sequence` alone discards readings it has never seen.

**Replay defence does not rest on `sequence`.** It rests on the HMAC signature,
the timestamp skew bound, and per-event idempotency. A replayed batch inside
the skew window is verified, read, and stores nothing new — which is the
property that matters, obtained from a key that cannot silently reset.

## `sequence`

**`sequence` is an ordering and diagnostic hint. A receiver must not use it to
discard, reject, or deduplicate anything.**

A producer must emit `sequence` as a positive integer that increases by one for
each batch it attempts, starting at 1 in each producer process. **It is not
unique across restarts, and a producer is not required to persist it.** A
replay key that silently resets to 1 on every restart is the defect this
version exists to remove; making `sequence` durable would instead require
producer-side persistence that this contract keeps out of scope, on a payload
that runs on a phone and has none.

A receiver may use `sequence` to detect gaps within a single run of batches it
has observed. It must not derive loss from a `sequence` that decreases or
repeats, because a restart and a retry both produce exactly that.

## Retry Identity

A retained batch is re-sent **as the same batch**: the same events, in the same
order, under the same `sequence`, with a fresh `sent_at_ms`, a fresh
`X-Ori-Timestamp-Ms`, and a signature recomputed over the resulting bytes.

- A retained batch must not be merged with events enqueued since.
- A retained batch must not be re-batched, split, or re-ordered.
- Retained batches are re-sent in the order they were first attempted, ahead of
  any newer batch, so `sequence` arrives monotonically within a run even when
  attempts fail.

Per-event idempotency already prevents a merged retry from costing new
readings. A stable retry identity is required for a different reason: without
it neither a receiver nor an operator can tell a retry from a new batch, and the
`sequence` diagnostics above have nothing to mean.

## Response To A Reading Batch

A receiver must answer a verified batch with `200` and a JSON body:

```json
{
  "status": "accepted",
  "accepted_events": 2,
  "duplicate_events": 1,
  "rejected_events": []
}
```

Every member is required **of a receiver**; the producer tolerances below are
separate and describe reading a receiver that does not yet conform.

| Member | Receiver must send | Meaning |
|---|---:|---|
| `status` | Yes | `accepted`, `duplicate`, or `partial`. |
| `accepted_events` | Yes | Events newly stored by this request. |
| `duplicate_events` | Yes | Events the receiver already held. |
| `rejected_events` | Yes | One entry per event the receiver declined, each with `event_id` and a `reason` string. |

- `accepted` — every event in the batch is now held, and at least one was newly
  stored.
- `duplicate` — every event in the batch was already held. Nothing was stored,
  and nothing was lost.
- `partial` — at least one event was declined.

`accepted_events + duplicate_events + length(rejected_events)` must equal the
number of events in the batch. This invariant is what makes "stored nothing"
distinguishable from "stored everything"; without it a `200` carries no
information a producer can act on.

A producer must:

- read the body of every `2xx`;
- treat the batch as delivered when no event is reported as rejected;
- treat a rejected event as **permanently** refused: count it, log it, and
  discard it. The receiver's answer will not change on a second attempt, the
  rest of the batch is already stored, and retrying is a loop with no exit;
- count rejected events under a counter distinct from its queue-overflow and
  terminal-refusal counters, and report that counter, so events a receiver
  declined are never reported as sent;
- treat `duplicate` as delivered, and not as loss;
- treat a `2xx` whose body it cannot parse, or whose three count members are all
  present and violate the invariant above, as a transport failure: retain the
  batch and retry under the rules above. That retry is bounded by
  `max_queue_size` and by nothing else, so a receiver answering unreadably costs
  queue capacity until it stops.

A producer reading a body that omits `rejected_events` reads it as no events
rejected, and one that omits `duplicate_events` as an unknown number already
held. **Such a body is not conformant** — both members are required above. The
tolerance exists so that a v2 producer posting to a receiver part-way through
its own migration neither retries forever nor reports phantom loss; it is not a
licence for a receiver to omit them. A body that omits `status` or
`accepted_events` is a transport failure, because neither absence has a safe
reading.

A producer must not POST an empty batch. The invariant above has no meaning over
zero events, and a `200` for nothing sent is indistinguishable from a `200` for
everything discarded.

## Retry And Backpressure

Producer behaviour on the reading route:

- queue writes are non-blocking;
- queue size is bounded by `max_queue_size`;
- overflow drops new telemetry and increments a producer drop counter;
- failed batches are retained in memory when queue capacity permits;
- durable historical backfill is outside this contract. It removes the loss that
  a producer and a receiver cause between them, not the loss from a device that
  was switched off.

**A transport failure must never end a producer.** A producer must not
terminate its process, abandon its export loop, or discard a retained batch
because a POST failed — a connection failure, a timeout, a `5xx`, or any status
this contract does not record as terminal.

**Only a recorded terminal refusal stops export**, and it stops export alone:
the producer process continues, sensing continues, and action authority is
untouched.

A terminal refusal on either route suspends both, because it is a statement
about the credential rather than about the body — a device suspended for
readings is not entitled to report its sensors instead.

A terminal refusal is `403` with the exact `detail` the receiver's published
refusal contract records for it, over a JSON media type, with no authentication
challenge. `401` is re-issuable, `415` and `422` describe the
request rather than the credential, and this contract records no terminal case
for `404` or `410`; every one of those is retried, so a serialisation fault
stays visible instead of silencing export. The enumeration of refusal statuses
and details belongs to the receiver, and a producer vendors it and pins it by
digest rather than restating it here.

## Sensor Status

A producer whose sensor stops answering posts no readings, and a receiver cannot
tell a silent meter from a quiet one or from a dead network. This route makes
the producer's own observation of its sensors expressible.

### Body

```json
{
  "schema_version": "runtime.sensor_status.v1",
  "device_id": "phone-gateway-ikeja-01",
  "sent_at_ms": 1719000000000,
  "sensors": [
    {
      "sensor_id": "phone-main-power",
      "sensor_type": "usb_power",
      "state": "failing",
      "reason": "no_response",
      "last_success_ms": 1718999400000,
      "consecutive_failures": 120
    }
  ]
}
```

`sensors` is a **full snapshot of every sensor the producer has declared**, not
a report of the ones that changed. A snapshot needs no reconciliation and a
receiver never has to remember which sensors it has heard about.

| Member | Required | Meaning |
|---|---:|---|
| `sensor_id` | Yes | The declared sensor identifier, as the runtime configuration names it. |
| `sensor_type` | Yes | The declared sensor type. |
| `state` | Yes | One of the closed set below. |
| `reason` | Yes | One of the closed set below; `none` when `state` is `reading`. |
| `last_success_ms` | Only when known | Present for `reading` and `failing`, absent for `never_read`. |
| `consecutive_failures` | Yes | Failed read attempts since the last success, or since the producer started if there has been none. |

A receiver ignores a member it does not recognise, per the estate's
compatibility rule, so a later version may add one without breaking it.

### `state`

A closed set of three, each decidable from the producer's own read attempts:

| `state` | Means |
|---|---|
| `reading` | The most recent read attempt succeeded. |
| `failing` | The most recent read attempt failed, and an earlier one succeeded. |
| `never_read` | No read attempt has succeeded in this producer's lifetime. |

`last_success_ms` is present for `reading` and `failing` and **absent** for
`never_read`. It is never `null`: two spellings of one fact is two code paths in
every receiver.

**The producer reports observations, not severity.** There is no threshold and
no "degraded" state, because any such state needs a window the producer would
have to be told, and a configured window on this path is a deployment-supplied
number deciding what counts as a fault. A receiver derives "the meter has
stopped" from `failing` and `last_success_ms`, and that derivation is the
receiver's.

### `reason`

`none` when `state` is `reading`. Otherwise one of a closed set, each a fact
about the read attempt rather than a diagnosis of the sensor:

| `reason` | Means |
|---|---|
| `no_response` | The sensor did not answer within the producer's read timeout. |
| `malformed_response` | An answer arrived that did not parse as this sensor's protocol. |
| `integrity_failed` | An answer parsed but failed its own checksum or CRC. |
| `interface_absent` | The producer could not reach the interface: no such device, or it disappeared. |
| `interface_denied` | The interface exists and the producer was refused access to it. |
| `not_configured` | The sensor is declared and the producer has no usable configuration for it. |
| `not_attempted` | No read has been attempted yet in this producer's lifetime. |

`interface_absent` and `interface_denied` are separate because an operator acts
differently on each: one is a cable, the other is a permission.

`not_attempted` is the startup state, paired with `never_read` and
`consecutive_failures: 0`. It exists because every other reason describes a read
that happened, and a producer that has declared a sensor and not yet polled it
has no such read to describe — without it a producer would have to claim a
failure it has not observed.

**There is no free-text detail.** An operator-facing string here is unbounded
producer input that a receiver stores and renders, and it is the obvious place
for a path or a credential to leak. The producer's own log is where detail
belongs; the closed `reason` is what a receiver may act on.

### Retention And Cadence

Sensor status is **state, not history**.

- A producer holds **at most one pending snapshot** per device. A newer snapshot
  replaces a pending one outright.
- A producer sends a snapshot when any sensor's `state` or `reason` changes, and
  otherwise no more often than the reading flush interval.
- **Any non-`2xx` answer discards the pending snapshot.** It is not retained and
  not retried. A receiver that has not implemented this route answers `404`, and
  that must cost a producer nothing and grow nothing. The one answer that costs
  more is a terminal refusal, which suspends export on both routes under the
  rule above — it is a statement about the credential, not about this snapshot.
- A state-change edge lost to a failed POST is re-reported by the next snapshot,
  and the receiver's view converges. That is the trade this route makes
  deliberately: a snapshot that is always current is worth more here than an
  edge that is never lost.

There is no `sequence` on this route. A receiver keeps the snapshot with the
greatest `sent_at_ms` it has seen for a device and ignores an older one, which
is how an out-of-order delivery resolves.

### Response

```json
{
  "status": "accepted",
  "accepted_sensors": 3,
  "rejected_sensors": []
}
```

`status` is `accepted` when every entry was accepted and `partial` when at
least one was rejected. There is no `duplicate`: a snapshot is state, and
re-sending the same state is not a duplicate of anything.

A receiver must reject an unknown `state` or `reason` **for that sensor entry
alone**, with an entry in `rejected_sensors` carrying `sensor_id` and `reason`,
and must accept the rest of the snapshot. A producer counts and logs rejected
entries and does not retry them; the next snapshot supersedes them.

### What A Receiver May And May Not Derive

A receiver may use this route to display sensor liveness, to alert an owner that
a meter has stopped being read, and to distinguish that from a device that has
gone quiet.

- **Absence of a snapshot is not evidence of health.** A producer that is
  switched off, unreachable, or has not implemented this route sends nothing. A
  receiver's device liveness must still rest on its own last-seen time.
- **A snapshot is not evidence a reading was stored.** It reports what the
  producer observed of its sensor, not what the receiver holds.
- Nothing here may become an input to an action, a threshold, or a policy on the
  device. The authority boundary above is unchanged.

## What This Contract Does Not Yet Enforce

Both fixtures are byte authorities for a request body. **Nothing here is a
corpus, and the rules this version exists for are the response and idempotency
rules, which no fixture exercises.** A receiver can reproduce both digests and
still reject a batch on `sequence`; a producer can reproduce both and still
treat a `duplicate` body as loss.

What is needed, and is not in this version, is a vector corpus over
`(receiver state, batch) → (status, counts, stored set)` with accept and reject
cases for each rule above, generated and independently verified by
implementations that share no code. Until that exists, conformance to this
document's central rules is a claim an implementation makes and no artifact
checks.

The sensor-status fixture also exercises no encoding case the reading fixture
does not: it carries no non-ASCII string and no non-integer number. The
canonical rules are unchanged and proven by the reading fixture, but this body
is not independent evidence of them.

## Relationship To ori-gateway

`runtime.telemetry.v1` bodies on this contract are for direct product ingestion.
`gateway-api/v1.md` remains the Edge Node and site-gateway contract for MQTT
reasoning, runtime health, and bounded historical exports.

`ori-gateway` does not produce, consume, proxy, or define this direct telemetry
contract. Product tooling may use `ori-sdk-python` models and signing helpers;
that does not place either route inside the gateway authority boundary.

An Ori deployment may use both:

- direct telemetry export for phone/product dashboards;
- gateway MQTT exports for certified Edge Node reporting and local gateway
  services.

The two contracts must not share mutation semantics.

## Relationship To Android Runtime Mobile

`runtime-mobile/v1.md` uses this telemetry contract for APK-bundled phone
payloads. The mobile payload may produce events from a socket-bridged USB/PZEM
stream, and the signed HTTP batch format, HMAC rules and observational authority
boundary are unchanged from v1.

What changes for that payload is behavioural, and all of it is required here:
it must not end its process on a failed upload, it must retain and re-send a
failed batch under a stable identity, it must read the response body, and it
must report its sensor's state on the sensor-status route.
