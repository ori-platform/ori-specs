# Runtime Telemetry v2

> Status: maturity `draft`; compatibility `frozen` by shipment (runtime
> `f87be13`, 2026-09-16; release v2.5.0-rc.10), baseline audit `pending`;
> adoption: producer (runtime) `shipped` in v2.5.0-rc.10, `unassessed`; proof:
> end-to-end `none`, HIL `none`, production `none`. Record:
> [status/runtime-telemetry/v2.json](../status/runtime-telemetry/v2.json).
>
> Supersedes: `runtime-telemetry/v1.md`, which is retained and accurate for
> consumers that have not migrated.
>
> Primary consumer: product provisioning backends during phone and lightweight
> deployments.

This contract defines the direct HTTP telemetry boundary from `ori-runtime` to a
product backend. It exists for phone and lightweight deployments where running a
LAN `ori-gateway` is unnecessary or unavailable.

This is not the runtime/gateway MQTT boundary. Gateway exports remain defined in
`gateway-api/v1.md`.

## Why v2 Exists

Under v1 a producer and a receiver can both conform while readings are signed,
sent, answered `200`, stored as nothing, and recorded by the device as
delivered. v1 permits it because two of its sentences disagree: one lets a
receiver reject a whole batch on `sequence`, the other says event IDs are the
idempotency keys. `sequence` has no stated lifetime, a retried batch has no
stated identity, and the success response is undefined, so neither party is
obliged to notice.

v2 resolves it in the direction v1 already pointed, and the resolution is
breaking for a receiver that keys on `sequence` and for a producer that ignores
the response body. Those are shipped behaviours, so this is a new version
rather than an amendment in place.

**The request body shape does not change, and neither does its
`schema_version`.** A `sensor.reading` batch is byte-identical under v1 and v2,
including `"schema_version": "runtime.telemetry.v1"`, and the golden fixture
below is the one v1 carries. The payload's `schema_version` identifies the body
shape; this document's version identifies the behaviour around it. Re-stamping
an unchanged body would force every producer and every byte fixture to change
for no semantic reason, and the cross-language byte agreement is the expensive
part to re-prove.

**A receiver therefore cannot tell a v1 producer from a v2 one, and does not
need to.** v2 receiver behaviour is strictly safer for a v1 producer: per-event
idempotency never discards more than batch rejection did, and a defined
response body only adds members a v1 producer ignores. The migration is
receiver-first — **a receiver adopts v2 before or with its producers**, and the
reverse order is worse than not migrating at all. A v2 producer re-sends a
retained batch under its original `sequence`; a v1 receiver keying on `sequence`
then rejects every attempt rather than the first, so a batch that v1 would
eventually have delivered under a fresh sequence is never delivered. Retry
identity is safe only once the receiver has stopped treating `sequence` as a
key.

## Authority Boundary

Runtime telemetry export is observational only.

- It mirrors real runtime `sensor.reading` events, and sensor liveness, to a
  product backend.
- Backend availability must never affect Tier B, Tier C, or Tier D action
  authority.
- The backend must not use either route to mutate runtime configuration,
  thresholds, relay state, DevicePolicy, update intent, or actuator settings.
- Tier D remains deterministic and local.
- Nothing a receiver derives from either route may become an input to an action,
  a threshold, or a policy on the device.

## Routes

| Route | Body schema | Carries |
|---|---|---|
| `POST <endpoint>` | `runtime.telemetry.v1` | a batch of `sensor.reading` events |
| `POST <endpoint>/sensor-status` | `runtime.sensor_status.v1` | a full snapshot of declared sensor liveness |

The status route is the configured `telemetry_export.endpoint` with
`/sensor-status` appended. There is no second configuration key: a deployment
that can reach one route can reach the other, and a separate endpoint would let
the two diverge to different receivers holding one device's state.

Both routes use the same transport, headers, key, canonicalisation and signing
rules. They differ in their bodies, their responses, and their retention rules,
because one carries history and the other carries state.

Sensor status is a separate route rather than a new `event_type` in the reading
batch. A new `event_type` is breaking for a receiver that admits only
`sensor.reading` and answers anything else `422`, and that answer rejects the
readings travelling in the same batch — so a report that a meter has stopped
would cost the readings of every meter that has not. A separate route cannot do
that to a reading under any receiver behaviour, including a receiver that has
not implemented it.

## Transport

| Field | Value |
|---|---|
| Protocol | HTTPS POST |
| Content type | `application/json` |
| Runtime config | `telemetry_export` |
| Default state | Disabled |
| Loopback exception | `http://localhost` or `http://127.0.0.1` allowed for local development |

Production and public endpoints must use HTTPS.

## Request Headers

| Header | Required | Notes |
|---|---:|---|
| `Authorization` | Yes | `Bearer <device_api_key>` |
| `Content-Type` | Yes | `application/json` |
| `X-Ori-Device-Id` | Yes | Must match payload `device_id`. |
| `X-Ori-Timestamp-Ms` | Yes | Unix milliseconds UTC when the request was signed. |
| `X-Ori-Signature` | Yes | `v1=<hex hmac sha256>` |

The device API key is read from the runtime environment variable named by
`telemetry_export.api_key_env`. The secret must not be committed to `ori.yaml`.

The signature prefix stays `v1=`: the signing construction is unchanged, and a
new prefix would invalidate every fixture and every verifier for a rule that
did not move.

## Signature

The runtime signs:

```text
timestamp_ms + "." + canonical_json_body
```

Using HMAC-SHA256 with the device API key as the secret. The same rule applies
to both routes.

The JSON body must be canonicalized before signing:

- encode as UTF-8 and emit non-ASCII characters directly rather than as
  `\uXXXX` escapes;
- sort object keys lexicographically at every nesting level;
- preserve array order;
- emit no whitespace outside string values;
- escape JSON strings according to RFC 8259;
- reject `NaN`, `Infinity`, and `-Infinity`;
- require integers to satisfy `|n| <= 9007199254740991` (`2^53 - 1`);
- require non-integer numbers to be finite and either exactly zero or have
  magnitude in `[1e-4, 1e16)`;
- serialize non-integer numbers as the shortest round-trip decimal in fixed
  notation with a mandatory fractional part, preserving `-0.0`; and
- never emit exponent notation in canonical bytes.

These are the same proven Python/Rust numeric agreement rules used by
`firmware-telemetry/v1.md`. Producers must reject values outside the agreement
zone rather than sign implementation-dependent bytes.

The backend must, on both routes:

- verify the bearer token/device API key;
- verify `X-Ori-Device-Id` matches payload `device_id`;
- verify timestamp skew within backend policy;
- verify the HMAC signature before accepting the body.

## Idempotency

**The idempotency key is `(device_id, event_id)`, and it is per event.**

A receiver must store every event in a batch that it does not already hold, and
must ignore only those it already holds. A batch must not be rejected, in whole
or in part, because it carries an event the receiver already holds.

v1's licence to "reject replayed or duplicate batches using `device_id`,
`sequence`, and/or event IDs" is withdrawn. Batch-level rejection is what turns
one known event into the loss of every new reading beside it, and a receiver
that rejects on `sequence` alone discards readings it has never seen.

**Replay defence does not rest on `sequence`.** It rests on the HMAC signature,
the timestamp skew bound, and per-event idempotency. A replayed batch inside
the skew window is verified, read, and stores nothing new — which is the
property that matters, obtained from a key that cannot silently reset.

**A record's receipt is the moment it was first stored, and a replay does not
move it.** Storing nothing new is not sufficient on its own: a receiver that
refreshed receipt from the batch rather than from what it stored would let a
replayed older batch become the most recently received reading for its sensor,
which is the decision [Producer Time](#producer-time) rests on arrival order to
make.

## Producer Time

Three members on this surface are a producer's account of when something
happened: a reading's `timestamp`, a batch's or snapshot's `sent_at_ms`, and a
sensor entry's `last_success_ms`. This section says what a receiver may do with
all three, because no producer can promise the clock it read them from.

A runtime on a handset has no persistent monotonic source and no trusted
reference. A factory reset without network time leaves a clock that never
advances; an ordinary handset with network time still runs ahead of a receiver
by hundreds of milliseconds. A producer cannot detect either, so it cannot
refuse to report a wrong time, and a receiver is the only place a defence can
live.

Four obligations follow, and they are not the same obligation:

- **In the record, keep it as reported.** A receiver does not overwrite, clamp
  or correct a producer timestamp in what it stores. A reading's own time is the
  only account anyone has of when the world was measured, and a receiver that
  corrects it destroys the only copy.
- **In a ranking, never read it.** Which record is newer, which one is current,
  and whether what the receiver holds is stale are the receiver's own facts,
  established by its own observation. A receiver that ranks by a producer
  timestamp hands the device permanent control over what may be learned about
  it: a single record timestamped far in the future becomes the value the
  receiver reports forever, at an age computed from that same timestamp, while
  the device goes on delivering records the receiver stores and never shows.
- **In an age, it may make a record look older and never newer.** That is the
  one place a producer timestamp legitimately contributes, and it contributes in
  one direction only.
- **In a display, it is shown as the producer reported it, under its own name.**
  A receiver must not present its own receive time *as* the measurement time, or
  under any name that attributes the value to the producer. Substituting the
  receiver's clock inside a producer's field is not a cautious display; it
  fabricates the fact the field claims, and it makes one fact have two values,
  since the record keeps the reported one. This governs every representation
  the receiver produces — an API response, a file, a feed, the data handed to
  a presentation — because attribution happens at the field name, not at the
  pixel. Layout and visual treatment are the receiver's own.

### Three quantities, not two

Collapsing any two of these is how both instances of the defect arose.

| Quantity | Whose | Rule |
|---|---|---|
| When the world was measured | The producer's | Kept raw in the record. Compared only against a bound the caller supplied, never against another stored record. |
| When the receiver received it | The receiver's | The key for which record is current. |
| How old the record is | Limited on one side | A producer timestamp may make it **older** than the receiver observed, never newer or fresher. This is the only quantity a producer timestamp may move. |

**An age is the greater** of the interval since the receiver received the record
and the interval since the producer says it was measured. A handset that buffers
readings in a basement and flushes them on the way out measured them hours ago;
a receiver reporting those as current would be relabelling stale data as live,
which is what an age exists to prevent. Taking the greater keeps a late delivery
honest, and it is the receiver's whole contribution to how fresh anything looks.

**No producer timestamp is altered anywhere**: not clamped, substituted, or
rewritten, in storage or in any output. A value a device reports a year ahead
is shown as the device reported it. Where the receiver's own receipt time or
age sits beside it, that is what tells a reader not to trust it. Where a
receiver emits a producer timestamp with neither beside it — an extracted list
of entries, an export analysed elsewhere — it **marks** a value that exceeds
the moment it arrived, as a flag beside the value and never a change to it;
elsewhere the mark is permitted. A presentation ordered newest-first is
ordered by receipt; a producer column is shown in its place and may be sorted
on only under its own name. Layout and visual treatment are otherwise the
receiver's own concern. Applied to a producer timestamp, "bound" names only a
limit a caller supplies to a filter or a validation window; it never names a
change to the value.

Clamping such a value looks like caution and is the same substitution the
display obligation forbids, so an earlier version of this section permitted it
and this one does not. **A permission with no honest case is not neutral; it is
an invitation.** No surface has been found where clamping is the honest choice:
where the receiver's own field sits beside the value, clamping adds nothing a
reader did not have; a "last updated"
footer is `received_at_ms` under its own name; a relative rendering *is* the age
and carries the age's name, never the producer's;
a chart with one point in the next century is honestly handled by marking it,
or by leaving it off the axis as a presentation choice that is never reported
as the receiver's account of what it holds, since moving the point puts
consumption at a time it did not happen;
and an export carries the fabricated value into a file analysed later with
nothing beside it to reveal the substitution. Every route ends at the age, at
the receiver's own field, or at the mark.

### A filter is not a ranking

The distinction an implementer needs is **what the timestamp is compared
against**, and it is decidable without judgement:

- **Against a bound the caller supplied** — a window, a range, an operator's
  query — it is a *filter*, and a producer's timestamp is the only honest basis
  for one. "What was measured between these two instants" is a question about
  the world, not about a receiver's records. A weekly energy report must select
  readings by when they were measured: a device that lost signal on Sunday and
  flushed on Monday measured Sunday's consumption in the period the report is
  about, and filtering that window by receipt would move it into the next
  report and make every total wrong for any device that was offline across a
  period boundary.
- **Against another stored record** — a column, a held row, a previous value —
  it is a *ranking*, and that is the whole defect class. Nothing a receiver
  holds as current, latest, or fresh may be decided that way.

Against the receiver's own observation of the same record — its receipt, or
the receiver's clock — to derive an age or a mark, it decides nothing about
which record is held, and is neither a filter nor a ranking. The signature's
skew check is the same comparison on the request, and is required.

A receiver can enforce this without an exception list: a producer timestamp
compared with a bound parameter is legal; one compared with another stored
record to choose between records is not; one compared with the receiver's own
observation of the same record, to say how old it is or that it exceeds its
arrival, chooses nothing.

### The three decisions this settles

A contract that forbids a rule owes the rule that replaces it.

1. **Which snapshot a receiver holds** is the one it most recently accepted, per
   [Retention And Cadence](#retention-and-cadence).
2. **Which reading is current for a sensor** is the one most recently received
   for it, and within one batch the later position in `events`. What licenses
   arrival order here is a producer obligation this contract already imposes
   rather than an assumption about networks: a retained batch is re-sent as
   itself, in the order first attempted, **ahead of any newer batch**, and is
   never merged, split or re-ordered (see [Retry Identity](#retry-identity)).
   Under that obligation a batch cannot arrive after readings that were produced
   later, so arrival order is production order.
3. **A sensor's last success** is the `last_success_ms` carried by the snapshot
   the receiver holds. A receiver does not maximise over the values it has seen:
   the newest snapshot supersedes, including when the value it carries is lower
   than one reported before, which is what a clock correction looks like.

The rule a receiver reaches for instead of (2) — select the latest reading by
the producer's `timestamp`, so that a batch arriving late cannot present an old
value as the current one — does not buy what it appears to. It defends only
against a producer that misorders its batches while keeping an honest clock. A
producer that misorders batches is violating [Retry Identity](#retry-identity),
and a producer that violates its obligations controls its timestamps too, so
the defence fails in the case it was built for. What it costs is protection in
the case that actually occurs on handsets: correct ordering and a broken clock.

This is stated rather than left implied because the mistake has been made twice
in this estate, in both of the ways a contract can invite it — once where this
contract said nothing, on the reading route, and once where it specified the
wrong rule outright, on the sensor-status route. Neither silence nor a wrong
sentence is the cause. The cause is that resolving "newest" by whatever
timestamp arrived is what a receiver does by default, so the rule has to be
written down.

Receivers implementing an earlier reading of this contract may select a latest
reading by the producer's timestamp, or maximise over `last_success_ms`. Both
become non-conforming here, and both are poisonable by a device with a wrong
clock rather than by an attacker.

## `sequence`

**`sequence` is an ordering and diagnostic hint. A receiver must not use it to
discard, reject, or deduplicate anything.**

A producer must emit `sequence` as a positive integer that increases by one for
each batch it attempts, starting at 1 in each producer process. **It is not
unique across restarts, and a producer is not required to persist it.** A
replay key that silently resets to 1 on every restart is the defect this
version exists to remove; making `sequence` durable would instead require
producer-side persistence that this contract keeps out of scope, on a payload
that runs on a phone and has none.

A receiver may use `sequence` to detect gaps within a single run of batches it
has observed. It must not derive loss from a `sequence` that decreases or
repeats, because a restart and a retry both produce exactly that.

## Retry Identity

A retained batch is re-sent **as the same batch**: the same events, in the same
order, under the same `sequence`, with a fresh `sent_at_ms`, a fresh
`X-Ori-Timestamp-Ms`, and a signature recomputed over the resulting bytes.

- A retained batch must not be merged with events enqueued since.
- A retained batch must not be re-batched, split, or re-ordered.
- Retained batches are re-sent in the order they were first attempted, ahead of
  any newer batch, so `sequence` arrives monotonically within a run even when
  attempts fail.
- **A producer has at most one batch in flight.** It does not send the next
  until it has read the answer to the previous or that attempt has failed.
  Without this a producer could pipeline fresh batches, and the order a receiver
  observes would no longer be the order the readings were produced in — which is
  what [Producer Time](#producer-time) relies on for deciding which reading is
  current. Both implemented producers already send one batch at a time; the
  obligation is written down so a receiver does not rest on an implementation.

Per-event idempotency already prevents a merged retry from costing new
readings. A stable retry identity is required for a different reason: without
it neither a receiver nor an operator can tell a retry from a new batch, and the
`sequence` diagnostics above have nothing to mean.

## Response To A Reading Batch

A receiver must answer a verified batch with `200` and a JSON body:

```json
{
  "status": "accepted",
  "accepted_events": 2,
  "duplicate_events": 1,
  "rejected_events": []
}
```

Every member is required **of a receiver**; the producer tolerances below are
separate and describe reading a receiver that does not yet conform.

| Member | Receiver must send | Meaning |
|---|---:|---|
| `status` | Yes | `accepted`, `duplicate`, or `partial`. |
| `accepted_events` | Yes | Events newly stored by this request. |
| `duplicate_events` | Yes | Events the receiver already held. |
| `rejected_events` | Yes | One entry per event the receiver declined, each with `event_id` and a `reason` string. |

- `accepted` — every event in the batch is now held, and at least one was newly
  stored.
- `duplicate` — every event in the batch was already held. Nothing was stored,
  and nothing was lost.
- `partial` — at least one event was declined.

`accepted_events + duplicate_events + length(rejected_events)` must equal the
number of events in the batch. This invariant is what makes "stored nothing"
distinguishable from "stored everything"; without it a `200` carries no
information a producer can act on.

A producer must:

- read the body of every `2xx`;
- treat a rejected event as **permanently** refused: count it, log it, and
  discard it. The receiver's answer will not change on a second attempt, the
  rest of the batch is already stored, and retrying is a loop with no exit;
- count rejected events under a counter distinct from its queue-overflow and
  terminal-refusal counters, and report that counter, so events a receiver
  declined are never reported as sent;
- treat `duplicate` as delivered, and not as loss.

### Confirmation

A producer treats a batch as delivered only when a `2xx` answer **confirms** it.
An answer confirms a batch when its body is readable (below), is a JSON object,
and:

- `status` is `accepted`, `duplicate`, or `partial`;
- `accepted_events` is present and is a count;
- `duplicate_events`, where present, is a count;
- `rejected_events`, where present, is an array whose every entry is an object
  naming the event by a non-empty string `event_id`, no two entries naming the
  same event;
- `accepted_events + duplicate_events + length(rejected_events)` equals the
  number of events in the batch, with an absent `duplicate_events` or
  `rejected_events` read as zero.

A **count** is an integer token between zero and the number of events in the
batch: not a boolean, not a number written with a fraction or an exponent, and
not `-0`. No count of a batch's events can exceed the batch, and holding every
term to that bound is what keeps the sum from overflowing, wrapping, or
truncating in any producer.

**The tolerance reads an omission; it does not trust one.** `duplicate_events`
and `rejected_events` are required of a receiver. A producer reading a body that
omits either reads it as zero and records the body as non-conformant, so that a
v2 producer posting to a receiver part-way through its own migration reads a
body missing one member exactly. It is not a licence for a receiver to omit
them, and the invariant must still hold on that reading.

The reason is the answer an unmigrated receiver gives. A receiver still keying
batches on `sequence` answers a batch it rejected with
`200 {"status":"duplicate","accepted_events":0}`, omitting both members that
would let a producer check it. Read under an unconditional tolerance, that is a
full delivery of readings it stored none of — the loss this version exists to
remove, readmitted through the clause meant to ease migration. On the reading
above it sums to zero and confirms nothing.

### An Answer That Does Not Confirm

A batch that is not confirmed and not terminally refused is retained, and the
producer distinguishes two cases, because only one of them is the receiver's
application speaking.

- **Transport failure** — no response, a body that ends before it is complete, a
  non-`2xx` status that is not a terminal refusal, or a `2xx` that is not an
  unconfirmed answer below. The batch is retained and retried, bounded by
  `max_queue_size` and by nothing else, so a receiver answering unreadably costs
  queue capacity until it stops.
- **Unconfirmed answer** — a `2xx` over a JSON media type whose readable body is
  a JSON object carrying a `status` of `accepted`, `duplicate` or `partial`, and
  that does not confirm the batch. The batch is retained and retried, but a
  producer must
  discard it on the **fifth** unconfirmed answer to that batch, count its events
  under an unconfirmed counter distinct from its queue-overflow, declined and
  terminal-refusal counters, report that counter, and log the discard. Answers
  are counted across the batch's life in the producer and are not reset by an
  intervening transport failure.

The bound exists because such an answer is deterministic, and it is drawn that
narrowly because a discard needs evidence of who answered. A captive portal or a
proxy answering `200` with a JSON object of its own is not the receiver declining
to confirm a batch, and counting it toward the discard would let any
intermediary throw readings away; neither a media type alone nor an arbitrary
object is that evidence, and this contract's own `status` vocabulary over a JSON
media type is the least that is. Retained batches are
re-sent ahead of newer ones, so a batch the receiver will never confirm holds
every newer reading behind it until queue overflow starts dropping them, and the
loss is permanent and attributed to the wrong counter. Against a receiver still
keying batches on `sequence`, the bound turns that into the loss of the batches
the receiver discards anyway, counted as what it is. Five attempts is not a
tuning value: per-event idempotency means a retry stores nothing twice, so the
attempts before the discard cost bandwidth, and the number is fixed so that two
producers report the same count for the same receiver.

A producer must not POST an empty batch. The invariant above has no meaning over
zero events, and a `200` for nothing sent is indistinguishable from a `200` for
everything discarded.

### Reading A Body

A producer sends `Accept-Encoding: identity` and reads a response body
**strictly**. A body is readable only when it is:

- not content-coded: `Content-Encoding` is absent, empty or `identity`. A
  producer does not decode a coded body, which is unreadable whatever it would
  decode to;
- at most 64 KiB, counted in bytes as received. A declared `Content-Length`
  beyond that bound makes the body unreadable before any of it is read, and a
  producer stops reading beyond the bound and treats the body as unreadable,
  rather than parsing a truncated prefix;
- UTF-8, with no byte-order mark;
- JSON under RFC 8259, with no `NaN` or `Infinity`, no number whose magnitude
  rounds to infinity as an IEEE 754 double under correct round-to-nearest-even
  conversion — integer tokens included — and no escape decoding to an unpaired
  surrogate, in a string or in a member name;
- free of any object that names a member twice, with names compared after their
  escapes are decoded, wherever in the body that object is;
- nested at most 32 containers deep, counting every array and object open at
  once and the outermost as the first, outside strings, before any value is
  parsed.

A response is **no answer at all** — a transport failure exactly as if nothing
had arrived — unless it is a well-formed HTTP/1.1 message, read by these rules:

- A line ends at LF, and a CR before the LF is not part of it. The header
  section ends at the first empty line.
- The status line is `HTTP/`, one digit, `.`, one digit, one space, and three
  digits of at least `100`, optionally followed by one space and a reason of
  anything but NUL, CR, LF, VT or FF.
- A line beginning with space or tab continues the line before it, joined by
  one space; such a line with no line before it is malformed.
- Every other line is a field: a name of token characters, `:`, optional space
  or tab, and a value that holds no NUL, CR, LF, VT or FF, with its leading and
  trailing space and tab removed. Any other line is malformed.
- A `1xx` response other than `101` is read past, and the next response is the
  answer. A `101` is malformed: nothing asked for a protocol switch.
- `Content-Length` is one or more decimal numbers of at most 20 digits,
  separated by commas, in one or more fields; all of them must be written
  identically, so `83` and `083` conflict. `Transfer-Encoding` must appear at most once, and be `chunked`
  regardless of case. The body is chunked when `Transfer-Encoding` is present,
  whatever the HTTP version; otherwise it has the declared length, or runs to
  the end of the connection when none is declared. `204` and `304` have none.
- A chunked body is chunk sizes of 1 to 20 hexadecimal digits, each with an
  optional `;` extension, optional space or tab and CRLF, chunk data followed
  by exactly CRLF, and a trailer section read by the field rules above. A body
  that ends before its framing says it does is malformed.
- A response that begins before the request has been completely sent is read
  as the answer: a gateway refusing a credential may answer and close without
  reading the body. Only when no response follows is a failed send a transport
  failure.

On a well-formed response, three further conditions make it no answer:

- more than 100 KiB of field names and values in the header section, counted
  on the parsed fields;
- a byte outside visible ASCII, space and tab in any of `Content-Type`,
  `WWW-Authenticate`, `Content-Encoding`, `Content-Length` or
  `Transfer-Encoding`;
- both `Content-Length` and `Transfer-Encoding` present.

Bytes in any other field are not read and do not matter. The size is counted on
the parsed fields rather than the bytes received, so a section that is mostly
field content is refused alike however its bytes arrive.

A producer may refuse a header section, trailer section or chunk-size line that
has not ended within 164 KiB on the wire, to bound its own memory. A parser that
limits a section only while it is incomplete refuses one somewhere short of that,
depending on how the bytes arrive. So a response whose header section runs past
100 KiB on the wire without holding that much field content — padding around
values, folded lines, many small fields — and a trailer section or chunk
extension of that length, are not read alike by every producer. Nothing a
conformant receiver sends comes near any of them.

These rules are one parser's, stated so that every producer holds to them. HTTP
clients recover from malformed responses in different ways: one dropped lines it
could not parse, took the first of two lengths, treated `103 Early Hints` as the
final answer, and ended its process on a line without a colon. Each recovery
was measured to deliver or suspend on one producer and not another from the
same bytes, and the last broke the obligation above never to end a producer on
a failed POST.

Otherwise a header that appears more than once is read as its values joined
with `, ` in the order received, so `Content-Type` sent twice is not a JSON
media type whichever value came first.

Anything else is unreadable, which is a transport failure. These bounds are not
about size for its own sake. The common JSON libraries disagree beyond every one
of them: one strips a byte-order mark and decodes UTF-16 where another refuses
both; one accepts `NaN`, `1e400` and an escaped lone surrogate where another
refuses the body; one reads `-0` as an integer and another as a float; for a
repeated name, which occurrence is kept is the library's choice; and one parser
nests until the process's recursion limit raises. Without a stated boundary two
conforming producers reach opposite verdicts on identical bytes — and a refusal
served as UTF-16, or naming `detail` twice, would suspend one producer's export
for good and leave another's running. HTTP clients disagree the same way: one
decodes `gzip` and `deflate` unasked where another decodes nothing, one keeps
the first of two `Content-Type` headers where another joins them, and one
parser rounds a literal near the largest double approximately and refuses it
where another reads it. A decoded body also escapes the size ceiling, since a
few kilobytes on the wire can inflate without bound. Depth is counted before parsing so that no
parser's own recursion decides the answer. The size ceiling also bounds remote
input in a device's memory.

## Retry And Backpressure

Producer behaviour on the reading route:

- queue writes are non-blocking;
- queue size is bounded by `max_queue_size`;
- overflow drops new telemetry and increments a producer drop counter;
- failed batches are retained in memory when queue capacity permits;
- durable historical backfill is outside this contract. It removes the loss that
  a producer and a receiver cause between them, not the loss from a device that
  was switched off.

**A transport failure must never end a producer.** A producer must not
terminate its process, abandon its export loop, or discard a retained batch
because a POST failed — a connection failure, a timeout, a `5xx`, an unreadable
body, or any status this contract does not record as terminal. The one discard
of a retained batch this contract permits short of a terminal refusal is the
bounded discard of a batch the receiver has answered five times without
confirming it, above.

**Only a recorded terminal refusal stops export**, and it stops export alone:
the producer process continues, sensing continues, and action authority is
untouched.

A terminal refusal on either route suspends both, because it is a statement
about the credential rather than about the body — a device suspended for
readings is not entitled to report its sensors instead.

A terminal refusal is `403` with the exact `detail` the receiver's published
refusal contract records for it, over a JSON media type, with no authentication
challenge, in a body readable under the rules above. `detail` is compared after
removing ASCII space, tab, carriage return and line feed from both ends, and no
other character: each language's own notion of whitespace differs, and a
detail one producer matches and another does not is a suspension on one device
and not the next. `401` is re-issuable, `415` and `422` describe the
request rather than the credential, and this contract records no terminal case
for `404` or `410`; every one of those is retried, so a serialisation fault
stays visible instead of silencing export. The enumeration of refusal statuses
and details belongs to the receiver, and a producer vendors it and pins it by
digest rather than restating it here.

## Sensor Status

A producer whose sensor stops answering posts no readings, and a receiver cannot
tell a silent meter from a quiet one or from a dead network. This route makes
the producer's own observation of its sensors expressible.

### Body

```json
{
  "schema_version": "runtime.sensor_status.v1",
  "device_id": "phone-gateway-ikeja-01",
  "sent_at_ms": 1719000000000,
  "sensors": [
    {
      "sensor_id": "phone-main-power",
      "sensor_type": "usb_power",
      "state": "failing",
      "reason": "no_response",
      "last_success_ms": 1718999400000,
      "consecutive_failures": 120
    }
  ]
}
```

`sensors` is a **full snapshot of every sensor the producer has declared**, not
a report of the ones that changed. A snapshot needs no reconciliation and a
receiver never has to remember which sensors it has heard about.

| Member | Required | Meaning |
|---|---:|---|
| `sensor_id` | Yes | The declared sensor identifier, as the runtime configuration names it. |
| `sensor_type` | Yes | The declared sensor type. |
| `state` | Yes | One of the closed set below. |
| `reason` | Yes | One of the closed set below; `none` when `state` is `reading`. |
| `last_success_ms` | For `reading` and `failing` | Present for `reading` and `failing`, absent for `never_read`, and never `null`. Two spellings of one fact are two code paths in a receiver's ingest. |
| `consecutive_failures` | Yes | Failed read attempts since the last success, or since the producer started if there has been none. |

A receiver ignores a member it does not recognise, per the estate's
compatibility rule, so a later version may add one without breaking it.

### `export`

A producer that also posts readings includes `export` in every snapshot. It is
what that producer has done with the readings it took. Without it, what a
device dropped or is still holding is visible only on the device, and a
receiver cannot tell a phone with nothing to send from one sitting on a
backlog it cannot deliver.

```json
"export": {
  "delivered_events": 1180,
  "duplicate_events": 12,
  "declined_events": 1,
  "unconfirmed_events": 2,
  "dropped_events": 37,
  "refused_events": 0,
  "queued_events": 4,
  "retained_events": 50
}
```

| Member | Meaning |
|---|---|
| `delivered_events` | Events confirmed held by the receiver, [duplicates](#confirmation) included. |
| `duplicate_events` | Of those, events the receiver reported it already held. |
| `declined_events` | Events the receiver rejected. Discarded, not retried. |
| `unconfirmed_events` | Events in batches discarded after the fifth [unconfirmed answer](#an-answer-that-does-not-confirm). |
| `dropped_events` | Events the producer discarded itself: overflow of `max_queue_size`, or a batch it could not form. |
| `refused_events` | Events discarded under a terminal refusal. |
| `queued_events` | Events taken and not yet in a batch, now. |
| `retained_events` | Events in batches sent and not yet confirmed, now. |

Every member is required and is a non-negative integer. The first six count
from the start of the producer process, and a restart resets them, so a
receiver must not derive loss from a count that decreases. The last two are the
producer's holding at the moment the snapshot is taken.

A change in these counts is not a change of any sensor's `state` or `reason`,
so it does not make a snapshot due; the flush interval carries it. Suspension is
not a member: a suspended producer sends no snapshot, and the receiver that
refused its credential already holds that fact.

### `state`

A closed set of three, each decidable from the producer's own read attempts:

| `state` | Means |
|---|---|
| `reading` | The most recent read attempt succeeded. |
| `failing` | The most recent read attempt failed, and an earlier one succeeded. |
| `never_read` | No read attempt has succeeded in this producer's lifetime. |

`last_success_ms` is present for `reading` and `failing` and **absent** for
`never_read`. It is never `null`: two spellings of one fact is two code paths in
every receiver.

**The producer reports observations, not severity.** There is no threshold and
no "degraded" state, because any such state needs a window the producer would
have to be told, and a configured window on this path is a deployment-supplied
number deciding what counts as a fault. A receiver derives "the meter has
stopped" from `failing` and `last_success_ms`, and that derivation is the
receiver's.

### `reason`

`none` when `state` is `reading`. Otherwise one of a closed set, each a fact
about the read attempt rather than a diagnosis of the sensor:

| `reason` | Means |
|---|---|
| `no_response` | The sensor did not answer within the producer's read timeout. |
| `malformed_response` | An answer arrived that is not a reading under this sensor's protocol: it did not parse, it stopped before it was complete, or it was the protocol's own exception response. |
| `integrity_failed` | An answer parsed but failed its own checksum or CRC. |
| `interface_absent` | The producer could not reach the interface: no such device, or it disappeared. |
| `interface_denied` | The interface exists and the producer was refused access to it. |
| `not_configured` | The sensor is declared and the producer has no usable configuration for it. |
| `not_attempted` | No read has been attempted yet in this producer's lifetime. |

`interface_absent` and `interface_denied` are separate because an operator acts
differently on each: one is a cable, the other is a permission.

`not_attempted` is the startup state, paired with `never_read` and
`consecutive_failures: 0`. It exists because every other reason describes a read
that happened, and a producer that has declared a sensor and not yet polled it
has no such read to describe — without it a producer would have to claim a
failure it has not observed.

**There is no free-text detail.** An operator-facing string here is unbounded
producer input that a receiver stores and renders, and it is the obvious place
for a path or a credential to leak. The producer's own log is where detail
belongs; the closed `reason` is what a receiver may act on.

### Retention And Cadence

Sensor status is **state, not history**.

- A producer holds **at most one pending snapshot** per device. A newer snapshot
  replaces a pending one outright.
- A producer sends its first snapshot once it has attempted a read of every
  sensor it reads, and then once per reading flush interval. It also sends one
  when any sensor's `state` or `reason` has changed since the last snapshot,
  but only when the receiver accepted that snapshot and no sooner than **five
  seconds** after it.
- A snapshot reports state at the moment it is taken, not what happened since
  the last one. A change that persists is reported no later than five seconds
  after an accepted snapshot, or one flush interval after a discarded one; a
  change that reverts before then is not reported at all. A receiver that needs
  a short outage must find it in the readings, not in this route.

  The spacing exists because a change is otherwise sent at once, and a meter
  that answers every other poll changes on every poll. The condition on
  acceptance exists because a receiver that has not implemented this route
  discards every snapshot, and must cost a producer one request per interval
  however often a sensor changes. Both numbers are the contract's, not a
  deployment's.
- **Any non-`2xx` answer discards the pending snapshot.** It is not retained and
  not retried. A receiver that has not implemented this route answers `404`, and
  that must cost a producer nothing and grow nothing. The one answer that costs
  more is a terminal refusal, which suspends export on both routes under the
  rule above — it is a statement about the credential, not about this snapshot.
- A state-change edge lost to a failed POST is re-reported by the next snapshot,
  and the receiver's view converges. That is the trade this route makes
  deliberately: a snapshot that is always current is worth more here than an
  edge that is never lost.

There is no `sequence` on this route, and **`sent_at_ms` is not an ordering
key**. A receiver keeps the snapshot it most recently accepted for a device.

`sent_at_ms` is the producer's account of when it looked. Which state a receiver
currently holds is the receiver's own fact, and its ordering must not depend on
producer wall time: a producer holds at most one pending snapshot, replaces it
outright when it builds a newer one, and discards rather than retries one that
fails to post, so two snapshots from one device cannot race and the order they
arrive in is the order the device's states occurred in. A producer has no
persistent monotonic clock, and this contract does not ask it to promise one.

Ordering on the greatest `sent_at_ms` hands a device permanent control over what
a receiver may learn about it, and the harm does not need a hostile producer. A
handset whose clock has stopped — a factory reset with no network time — reports
honestly under a clock that never advances; a receiver keeping the greatest
`sent_at_ms` stores that device's first snapshot, answers `accepted` to every
correction that follows, and never records another state for the life of the
device. Device time also runs ahead of receiver time in ordinary operation, so
this is not a rare configuration.

**A receiver must not repair the ordering by comparing the two clocks.** Taking the
lesser of `sent_at_ms` and its own arrival time still admits producer wall time
to a decision that is the receiver's, and still lets a stopped clock hold a
device's state down: which snapshot is held is decided by arrival alone, and
`sent_at_ms` is carried for diagnosis.

That is a rule about **ordering**. `sent_at_ms` is displayed as the producer
reported it, like every other producer timestamp — see
[Producer Time](#producer-time), which settles all three quantities and why an
age is the receiver's contribution while a displayed producer value is never
the receiver's.

### Response

```json
{
  "status": "accepted",
  "accepted_sensors": 3,
  "rejected_sensors": []
}
```

`status` is `accepted` when every entry was accepted and `partial` when at
least one was rejected. There is no `duplicate`: a snapshot is state, and
re-sending the same state is not a duplicate of anything.

A receiver must reject an unknown `state` or `reason` **for that sensor entry
alone**, with an entry in `rejected_sensors` carrying `sensor_id` and `reason`,
and must accept the rest of the snapshot. A producer counts and logs rejected
entries and does not retry them; the next snapshot supersedes them.

**The rejection reasons a receiver may give are not a closed set.** This
contract names `unknown_state` and `unknown_reason`; a receiver may enumerate
others for faults it can name — a `reason` that contradicts its `state`, say, or
a `consecutive_failures` of zero on an entry whose `state` is `failing`. A
member outside the form the table above gives is a different matter and is not
a per-entry rejection: a receiver refuses such a snapshot whole. A producer therefore
identifies a rejected entry by its `sensor_id` and **must not** treat an
unrecognised `reason` as a malformed answer, which would turn a receiver's
better diagnosis into a discarded snapshot. A producer that refuses an answer it
does not fully recognise makes the compatibility rule above unusable in the one
direction the receiver controls.

A producer reads this answer under the rules of [Reading A Body](#reading-a-body).
It counts a snapshot as accepted only when `status` is `accepted` or `partial`,
`accepted_sensors` is a count no greater than the number of sensors in the
snapshot, every `rejected_sensors` entry is an object naming a sensor by a
non-empty string `sensor_id`, no two entries naming the same sensor, and
`accepted_sensors + length(rejected_sensors)` equals that number. An absent
`rejected_sensors` is read as none rejected, as an absent `rejected_events` is
on the reading route. Any other `2xx` discards the snapshot exactly as a non-`2xx`
does. Nothing on this route is retained, so the reading decides what a producer
counts and reports, and whether an answer is the terminal refusal — which it
recognises by the same rule as on the reading route, since one refusal suspends
both.

### What A Receiver May And May Not Derive

A receiver may use this route to display sensor liveness, to alert an owner that
a meter has stopped being read, and to distinguish that from a device that has
gone quiet.

- **Absence of a snapshot is not evidence of health.** A producer that is
  switched off, unreachable, or has not implemented this route sends nothing. A
  receiver's device liveness must still rest on its own last-seen time.
- **A rejected entry supersedes what was held for that sensor, and leaves
  nothing in its place.** Holding the last understood state would let a stale
  row go on claiming a meter is reading, so a receiver holds no state for a
  sensor whose entry it rejected. A snapshot whose every entry was rejected
  therefore leaves the receiver holding no sensor state at all — which is not
  the same as learning that no sensor answered, and must not be reported as a
  fault: a producer using a `state` or `reason` this receiver has not seen yet
  is exactly what the compatibility rule permits, and a receiver that read a
  fully rejected snapshot as a fault would report a healthy device as faulty for
  using it. What it has is an absence of information, and its device liveness
  rests on its own last-seen time as it does when no snapshot arrives at all.
- **`sensors` is never empty.** A snapshot is the full set of sensors a producer
  declares, and a producer with none has nothing to report on this route — the
  only implemented producer refuses to start in that state. An empty array is
  indistinguishable from a bug, so a receiver refuses that snapshot whole rather
  than deciding whether it supersedes everything or nothing.
- **A state this route reported is not a state a receiver can recover.** Only
  the most recently accepted snapshot is held, so a state that has been
  superseded — a cable out for six reads, a meter that stopped and resumed
  between two snapshots — is gone from the receiver whether or not it was
  accepted. Nothing may be built on this route that needs the history: an alert
  on "the cable came out" cannot be raised from snapshots, because a conforming
  receiver does not keep the edge. What a short outage leaves behind is the gap
  in the readings.
- **A snapshot is not evidence a reading was stored.** It reports what the
  producer observed of its sensor, not what the receiver holds.
- Nothing here may become an input to an action, a threshold, or a policy on the
  device. The authority boundary above is unchanged.

## What This Contract Does Not Yet Enforce

The fixtures are byte authorities for a request body. **Nothing here is a
corpus, and the rules this version exists for are the response and idempotency
rules, which no fixture exercises.** A receiver can reproduce both digests and
still reject a batch on `sequence`; a producer can reproduce both and still
treat a `duplicate` body as loss.

What is needed, and is not in this version, is a vector corpus over
`(receiver state, batch) → (status, counts, stored set)` with accept and reject
cases for each rule above, generated and independently verified by
implementations that share no code. Until that exists, conformance to this
document's central rules is a claim an implementation makes and no artifact
checks.

The sensor-status fixture also exercises no encoding case the reading fixture
does not: it carries no non-ASCII string and no non-integer number. The
canonical rules are unchanged and proven by the reading fixture, but this body
is not independent evidence of them.

## Relationship To ori-gateway

`runtime.telemetry.v1` bodies on this contract are for direct product ingestion.
`gateway-api/v1.md` remains the Edge Node and site-gateway contract for MQTT
reasoning, runtime health, and bounded historical exports.

`ori-gateway` does not produce, consume, proxy, or define this direct telemetry
contract. Product tooling may use `ori-sdk-python` models and signing helpers;
that does not place either route inside the gateway authority boundary.

An Ori deployment may use both:

- direct telemetry export for phone/product dashboards;
- gateway MQTT exports for certified Edge Node reporting and local gateway
  services.

The two contracts must not share mutation semantics.

## Relationship To Android Runtime Mobile

`runtime-mobile/v1.md` uses this telemetry contract for APK-bundled phone
payloads. The mobile payload may produce events from a socket-bridged USB/PZEM
stream, and the signed HTTP batch format, HMAC rules and observational authority
boundary are unchanged from v1.

What changes for that payload is behavioural, and all of it is required here:
it must not end its process on a failed upload, it must retain and re-send a
failed batch under a stable identity, it must read the response body, and it
must report its sensors' state and its export state on the sensor-status route.
