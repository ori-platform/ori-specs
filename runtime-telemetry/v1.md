# Runtime Telemetry v1

> Status: Implemented baseline in `ori-runtime`. Superseded by
> `runtime-telemetry/v2.md`, and retained as accurate for consumers that have
> not migrated. See Known Defects below before implementing against it.
> Primary consumer: product provisioning backends during phone and lightweight deployments.

This contract defines the direct HTTP telemetry boundary from `ori-runtime` to a
product backend. It exists for phone and lightweight deployments where running a
LAN `ori-gateway` is unnecessary or unavailable.

This is not the runtime/gateway MQTT boundary. Gateway exports remain defined in
`gateway-api/v1.md`.

## Authority Boundary

Runtime telemetry export is observational only.

- It mirrors real runtime `sensor.reading` events to a product backend.
- Backend availability must never affect Tier B, Tier C, or Tier D action
  authority.
- The backend must not use this endpoint to mutate runtime configuration,
  thresholds, relay state, DevicePolicy, update intent, or actuator settings.
- Tier D remains deterministic and local.

## Transport

| Field | Value |
|---|---|
| Protocol | HTTPS POST |
| Content type | `application/json` |
| Runtime config | `telemetry_export` |
| Default state | Disabled |
| Loopback exception | `http://localhost` or `http://127.0.0.1` allowed for local development |

Production and public endpoints must use HTTPS.

## Request Headers

| Header | Required | Notes |
|---|---:|---|
| `Authorization` | Yes | `Bearer <device_api_key>` |
| `Content-Type` | Yes | `application/json` |
| `X-Ori-Device-Id` | Yes | Must match payload `device_id`. |
| `X-Ori-Timestamp-Ms` | Yes | Unix milliseconds UTC when the request was signed. |
| `X-Ori-Signature` | Yes | `v1=<hex hmac sha256>` |

The device API key is read from the runtime environment variable named by
`telemetry_export.api_key_env`. The secret must not be committed to `ori.yaml`.

## Signature

The runtime signs:

```text
timestamp_ms + "." + canonical_json_body
```

Using HMAC-SHA256 with the device API key as the secret.

The JSON body must be canonicalized before signing. This byte-level contract is
a design target until both the Python runtime and Android runtime-mobile
producer adopt the golden fixture below:

- encode as UTF-8 and emit non-ASCII characters directly rather than as
  `\uXXXX` escapes;
- sort object keys lexicographically at every nesting level;
- preserve array order;
- emit no whitespace outside string values;
- escape JSON strings according to RFC 8259;
- reject `NaN`, `Infinity`, and `-Infinity`;
- require integers to satisfy `|n| <= 9007199254740991` (`2^53 - 1`);
- require non-integer numbers to be finite and either exactly zero or have
  magnitude in `[1e-4, 1e16)`;
- serialize non-integer numbers as the shortest round-trip decimal in fixed
  notation with a mandatory fractional part, preserving `-0.0`; and
- never emit exponent notation in canonical bytes.

These are the same proven Python/Rust numeric agreement rules used by
`firmware-telemetry/v1.md`. Producers must reject values outside the agreement
zone rather than sign implementation-dependent bytes.

The backend must:

- verify the bearer token/device API key;
- verify `X-Ori-Device-Id` matches payload `device_id`;
- verify timestamp skew within backend policy;
- verify HMAC signature before accepting the batch;
- reject replayed or duplicate batches using `device_id`, `sequence`, and/or
  event IDs.

## Request Body

```json
{
  "schema_version": "runtime.telemetry.v1",
  "device_id": "phone-gateway-ikeja-01",
  "sequence": 1,
  "sent_at_ms": 1719000000000,
  "events": [
    {
      "event_id": "uuid4-string",
      "event_type": "sensor.reading",
      "device_id": "phone-gateway-ikeja-01",
      "sensor_id": "phone-main-power",
      "timestamp": 1719000000000,
      "source": "usb_serial",
      "fingerprint": "sha256-hex-or-empty",
      "context": {},
      "reading": {
        "sensor_id": "phone-main-power",
        "sensor_type": "usb_power",
        "value": 1240.5,
        "unit": "watt",
        "timestamp": 1719000000000,
        "quality": 1.0,
        "metadata": {
          "source": "usb_serial"
        }
      }
    }
  ]
}
```

`reading.raw` is intentionally omitted from the HTTP payload.

## Runtime Config

```yaml
telemetry_export:
  enabled: false
  endpoint: "https://provisioning.example.invalid/runtime/telemetry"
  api_key_env: ORI_DEVICE_API_KEY
  flush_interval_s: 30
  batch_size: 50
  timeout_ms: 3000
  max_queue_size: 1000
```

## Retry And Backpressure

Runtime behavior:

- queue writes are non-blocking;
- queue size is bounded by `max_queue_size`;
- overflow drops new telemetry and increments a runtime drop counter;
- failed POST batches are retained in memory when queue capacity permits;
- durable historical backfill is outside the v1 runtime contract.

A transport failure never ends a producer. Retention above is an obligation, so
a producer must not terminate its process, abandon its export loop, or discard a
retained batch because a POST failed — a connection failure, a timeout, a `5xx`,
or any status this contract does not record as terminal. Only a recorded
terminal refusal stops export, and it stops export alone: the producer process
continues, sensing continues, and action authority is untouched. This states an
obligation v1 already carried rather than adding one, so a conformant
implementation is unaffected.

The backend should treat event IDs as idempotency keys.

## Known Defects

**Under this version a producer and a receiver can both conform while readings
are discarded.** The loss is on ordinary paths of a phone deployment, not on
hostile input, and the device records the discarded readings as delivered.

- The backend requirement to "reject replayed or duplicate batches using
  `device_id`, `sequence`, and/or event IDs" and the later statement that event
  IDs are the idempotency keys **disagree**. The first licenses rejecting a
  whole batch on `sequence` alone; the second, read as written, makes a known
  event ID a fact about that event.
- **`sequence` has no stated lifetime.** A producer that restarts it at 1 in
  each process and a receiver that treats it as a replay key both conform, and
  between them every reading is refused until the new counter passes the highest
  already stored.
- **A retried batch has no stated identity.** Whether a retry reuses its
  sequence, may be re-batched, or may be merged with newer events is unstated,
  so a batch carrying one already-stored event can cost the new readings
  travelling with it.
- **The success response is undefined.** A producer has no obligation to read
  anything from a `2xx`, and a receiver has no obligation to make "stored
  nothing" distinguishable from "stored everything".
- **A sensor that has stopped producing readings is inexpressible.** A producer
  whose meter stops answering posts nothing, so a receiver cannot tell a silent
  meter from a quiet one or from a dead network.

`runtime-telemetry/v2.md` resolves all five. The resolution is breaking for a
receiver that keys on `sequence` and for a producer that ignores the response
body, which is why it is a version rather than an amendment here. The request
body shape and its `schema_version` are unchanged by v2, so migrating a receiver
costs no producer change and is the first step.

## Relationship To ori-gateway

`runtime.telemetry.v1` is for direct product ingestion. `gateway-api/v1.md`
remains the Edge Node and site-gateway contract for MQTT reasoning, runtime
health, and bounded historical exports.

`ori-gateway` does not produce, consume, proxy, or define this direct telemetry
contract. Product tooling may use `ori-sdk-python` models and signing helpers;
that does not place the endpoint inside the gateway authority boundary.

An Ori deployment may use both:

- direct telemetry export for phone/product dashboards;
- gateway MQTT exports for certified Edge Node reporting and local gateway
  services.

The two contracts must not share mutation semantics.

## Relationship To Android Runtime Mobile

`runtime-mobile/v1.md` uses this telemetry contract for APK-bundled phone
payloads. The mobile payload may produce events from a socket-bridged USB/PZEM
stream, but the signed HTTP batch format, HMAC rules, idempotency expectations,
and observational authority boundary are unchanged.
