# Evidence Audit v1

> Status: Design target. This contract defines purpose-bound insurer and auditor
> reads from an evidence authority. It names no implementation, deployment,
> endpoint host, account, custody provider, or administrative surface.

`evidence-exchange/v1` owns artifact meaning and authenticated bytes.
`evidence-transport/v1` owns write-only Gateway ingest. This contract owns a
separate read boundary. An ingest credential grants no audit access, and an
audit credential grants no ingest, mutation, provisioning, or key authority.

## Endpoint and request

| Property | Value |
| --- | --- |
| Method | `POST` |
| Path | `/v1/evidence/audit/query` |
| Content type | `application/json` |
| Transport | HTTPS with server-certificate verification |

The canonical request body is:

```json
{
  "v": 1,
  "tenant_id": "tenant-test-01",
  "device_ids": ["energy-monitor-ikeja-01"],
  "evidence_classes": ["authority_artifact", "finding"],
  "from_ms": 1787000000000,
  "until_ms": 1787001000000,
  "page_size": 100,
  "page_token": ""
}
```

`device_ids` and `evidence_classes` MUST be non-empty, unique and
lexicographically ordered. The closed evidence-class vocabulary is
`submitted_artifact`, `authority_artifact`, and `finding`. `from_ms` is
inclusive, `until_ms` is exclusive, both are positive D-011 integers, and
`until_ms > from_ms`. `page_size` is `1..500`. A non-empty `page_token` fixes
all query fields other than `page_size`; changing any bound is refused.

## Dedicated authentication and authorisation

Every caller uses a secret whose sole purpose is `evidence_audit`. It MUST have
at least 256 bits of entropy and MUST be distinct in resolved bytes from every
ingest, fleet, runtime-Gateway, custody, and authority-signing secret. Its
identifier is derived, never configured:

```text
key_id = "hkdf-sha256:" || lowercase_hex(HKDF-SHA256(
  ikm = secret UTF-8,
  salt = "ori.evidence_audit_key_id.v1",
  info = "evidence_audit",
  length = 16
))
```

Registry construction MUST refuse duplicate identifiers, cross-purpose secret
reuse, and a configured `key_id`. Each credential record binds:

- `audience`, exactly `evidence_audit`;
- one `tenant_id`;
- a non-empty set of permitted `device_ids`;
- a non-empty set of permitted `evidence_classes`;
- `not_before_ms` and `expires_at_ms`;
- a stable opaque `client_id` and key generation.

The request MUST be a subset of those grants. A tenant, device, class, audience,
or validity mismatch grants nothing. Unknown and known-but-unauthorised devices
produce the same status, body, log classification, and timing class.

Required headers are `X-Ori-Evidence-Audit-Client`,
`X-Ori-Evidence-Audit-Key-Id`, `X-Ori-Evidence-Audit-Sent-At-Ms`,
`X-Ori-Evidence-Audit-Nonce`, `X-Ori-Evidence-Audit-Body-Digest`, and
`Authorization`. Identifiers are 1–128 printable ASCII; timestamps are positive
D-011 integers; the nonce is 32 lowercase hex characters; the digest is
`sha256:` plus 64 lowercase hex; and authorization is
`Ori-Evidence-Audit-HMAC hmac-sha256:` plus 64 lowercase hex.

The HMAC input is:

```text
"ori.evidence_audit_request.v1" || NUL || canonical({
  "body_digest": X-Ori-Evidence-Audit-Body-Digest,
  "client_id": X-Ori-Evidence-Audit-Client,
  "key_id": X-Ori-Evidence-Audit-Key-Id,
  "method": "POST",
  "nonce": X-Ori-Evidence-Audit-Nonce,
  "path": "/v1/evidence/audit/query",
  "sent_at_ms": integer(X-Ori-Evidence-Audit-Sent-At-Ms)
})
```

`canonical` has the same UTF-8 JSON rules as `evidence-transport/v1`. The body
digest covers the exact request bytes. Verification order is: size and shape,
body digest, purpose-and-key selection without trial verification, constant-time
HMAC, clock and nonce replay, credential validity, then tenant/device/class
authorisation. The default clock-skew bound is 300,000 ms. Nonces are atomically
reserved for at least twice that duration.

Revocation takes effect before the next request. During rotation, an explicitly
retained previous generation MAY verify until its bound expiry but MUST NOT sign
new server tokens. A retired identifier is not trial-verified. Audit and ingest
registries are separate even if operated by the same authority.

## Stable pagination

Accepted records have an authority-assigned, monotonically increasing
`observation_seq`. The first page transaction fixes `snapshot_seq` to the
largest committed sequence visible after authorisation. Results are ordered by
`observation_seq`; every later page applies:

```text
after_seq < observation_seq <= snapshot_seq
```

The opaque `next_page_token` authenticates the query digest, tenant, credential
generation, `snapshot_seq`, `after_seq`, and token expiry under a dedicated
server-side `evidence_audit_page_token` key. It reveals no device identity.
The token is unpadded RFC 4648 URL-safe Base64 over:

```text
canonical(token_payload) || HMAC-SHA256(
  page_token_key,
  "ori.evidence_audit_page_token.v1" || NUL || canonical(token_payload))
```

The payload fields and exact bytes are fixed by the vector. Tokens are
exact-byte; single-use is not required, and expiry or any binding mismatch is
refused. Concurrent ingest receives larger sequence numbers and cannot create a
skip or duplicate within the snapshot. `page_size` may decrease on continuation
but cannot increase beyond the authenticated first-page value.

## Response records

An accepted response is:

```json
{
  "v": 1,
  "snapshot_seq": 42,
  "records": [],
  "next_page_token": "",
  "complete": true
}
```

Every record contains `observation_seq`, `observed_at_ms`, `device_id`, and
`evidence_class`. A `submitted_artifact` or `authority_artifact` additionally
contains `artifact_type`, `artifact_digest`, and `artifact_b64`. `artifact_b64`
is standard padded Base64 over the exact stored wire bytes. Receipts and epoch
confirmations MUST be returned byte-for-byte; a service MUST NOT decode and
re-encode them.

A finding contains a closed `finding_type`, `window_from_ms`, `window_until_ms`,
and the digests or observation sequences that prove it. A positive finding may
state only what the authority can prove from accepted bytes and authority state.
`not_observed_by_authority` means no matching authority observation exists in a
complete queried window; it MUST NOT be represented as proof that an event did
not occur. No finding may infer Gateway custody, delivery attempt, site health,
or operator behaviour from silence.

## Neutral refusals

| HTTP | Meaning |
| ---: | --- |
| 400 | Malformed request or token. |
| 401 | Missing, unknown, expired, replayed, revoked, wrong-purpose, or invalid authentication. |
| 403 | Authenticated request exceeds its tenant, device, or class grant. |
| 429 | Rate limited; `Retry-After` is required. |
| 503 | A consistent read cannot currently be served. |

Responses before authorisation contain only `{"v":1,"outcome":"refused"}`.
They omit tenant, device, key, query digest, record count, snapshot and token.
Unknown and cross-tenant devices are indistinguishable. A successful empty page
is available only after complete authentication and authorisation.

## Access audit and limits

Every success and refusal appends an immutable access record before the response
is released. It records time, outcome, neutral reason class, resolved client and
key generation when known, request nonce digest, query digest, returned count,
and snapshot sequence when applicable. It MUST NOT record secrets,
`Authorization`, raw nonces, page-token keys, or bearer material. Pre-auth
records MUST NOT copy requested tenant or device identifiers into logs.

The service MUST bound body/header sizes, page size, query window, device count,
concurrency, per-client rate, replay state and token lifetime. Backpressure is
explicit; it never yields a partial page marked complete. Audit reads never
mutate evidence, create receipts or confirmations, or change retention.

## Vectors

[`vectors/audit-access.json`](vectors/audit-access.json) fixes key derivation,
request canonicalisation, HMAC bytes, snapshot continuation and neutral refusal
outcomes for success, cross-tenant denial, known-unauthorised and unknown
devices, wrong purpose, expiry, replay and page continuation. The two device
denials fix byte-identical status and response bodies. Published secrets and
token keys are test-only.
