# Skill Signing Contract v1

> Status: Canonical-manifest profile implemented in `ori-runtime`; artifact
> profile is an implementation target for the SDK, CLI, and Skills Hub.
>
> Runtime source of truth:
> `ori/skills/signing.py`, `ori/skills/loader.py`

This contract defines Ed25519 signing for Ori community skills. It separates
two payload profiles that have different security purposes:

1. a detached signature over exact package bytes, verified before extraction;
2. an embedded signature over canonical `skill.yaml` data, verified before
   runtime hook loading.

An implementation MUST select the expected profile explicitly. A signature or
key lookup from one profile MUST NOT be accepted as authority in the other.

## v1 Erratum

The original v1 text described only exact artifact bytes while also marking
the runtime as its implemented baseline. That was internally inconsistent:
the runtime has always verified the parsed `skill.yaml` mapping as canonical
JSON, while the SDK, CLI, and Skills Hub artifact pipeline remain unimplemented.

This revision records the existing manifest behavior and retains exact-byte
verification as the separate artifact profile needed before extraction. It
does not migrate a released Hub artifact format or an implemented SDK/CLI API,
so the correction remains within v1. Any future incompatible change to either
profile requires a new contract major version.

## Trust Boundaries

| Checkpoint | Payload profile | Expected signer | Trust source |
|---|---|---|---|
| Hub upload | Exact artifact bytes | Author | Public key already bound to the authenticated author |
| Hub download | Exact artifact bytes | Skills Hub | Pinned Hub artifact trust anchor |
| Runtime load | Canonical skill manifest | Skills Hub | Pinned Hub manifest trust anchor |

The Hub MAY operate the artifact and manifest profiles with the same Ed25519
keypair, but consumers MUST still use profile-specific APIs and expected-role
checks. Deployments that use separate Hub keys gain stronger operational
isolation.

Signer identity is not supplied by detached artifact metadata. It comes from
the authenticated author context during upload or from the pinned Hub trust
anchor during download. This prevents an unsigned metadata label from
misattributing a valid signature.

## Shared Ed25519 Encoding

Signatures use:

```text
ed25519:<standard-base64-signature>
```

Rules:

- The prefix is exactly `ed25519:`.
- Signature bytes use standard padded base64, not base64url.
- The decoded signature is exactly 64 bytes.
- Public keys are raw 32-byte Ed25519 keys encoded with standard padded
  base64.
- Invalid base64, non-canonical padding, wrong lengths, unsupported schemes,
  or verification failure MUST fail closed.

## Profile 1: Exact Artifact Bytes

A skill artifact is the final compressed package byte sequence distributed or
uploaded as one unit. Its signature is detached: placing the signature inside
the signed archive would create a circular payload.

The Ed25519 message is the artifact bytes exactly as received. Consumers MUST
NOT decompress, repack, normalize paths, rewrite metadata, or otherwise
transform the bytes before verification. Any byte change invalidates the
signature.

Detached metadata has this shape:

```json
{
  "artifact_sha256": "sha256:<64-lowercase-hex>",
  "schema": "ori.skill_artifact_signature.v1",
  "signature": "ed25519:<standard-base64-signature>"
}
```

Rules:

- `schema` is exactly `ori.skill_artifact_signature.v1`.
- `artifact_sha256` is SHA-256 over the same exact bytes and MUST match before
  signature verification.
- Detached metadata is strict: unknown or duplicate fields are rejected.
- A verifier MUST resolve the expected public key from trusted context before
  reading the detached metadata. Metadata MUST NOT select its own verifier.

### Author Upload Verification

The Hub MUST:

1. authenticate the author and resolve the already-registered author public
   key;
2. enforce the bounded upload size;
3. validate the detached metadata;
4. verify the SHA-256 digest and Ed25519 signature over the exact upload bytes;
5. only then extract, inspect, scan, or persist package contents beyond a
   bounded temporary upload spool.

An author-provided top-level `skill.yaml.signature` is not Hub authority. The
Hub replaces or adds that field only after validation and any required review.

### Hub Distribution Verification

The CLI or SDK installer MUST:

1. obtain the artifact bytes and detached metadata;
2. use the configured Hub artifact trust anchor;
3. verify the digest and signature before extraction;
4. reject traversal, symlink escape, duplicate paths, and unsafe file types
   during bounded extraction;
5. install atomically so failure leaves no partial skill directory.

The final Hub artifact signature is computed after the Hub has produced the
final archive, including the Hub-signed `skill.yaml`.

## Profile 2: Canonical Skill Manifest

The top-level `signature` field in `skill.yaml` is the Hub manifest signature
consumed by `ori-runtime`. It is not the detached artifact signature.

The signed object is the parsed top-level `skill.yaml` mapping with only the
top-level `signature` field removed. Before canonicalization, parsers MUST
reject duplicate YAML keys, non-string mapping keys, non-JSON values, and
non-finite numbers.

Canonical bytes use:

- JSON object keys sorted lexicographically at every level;
- compact `,` and `:` separators with no extra whitespace;
- UTF-8;
- unescaped Unicode (`ensure_ascii=false` semantics);
- JSON booleans, nulls, strings, arrays, objects, and finite numbers only.

Python-equivalent canonicalization:

```python
unsigned = {key: value for key, value in parsed_skill.items() if key != "signature"}
json.dumps(
    unsigned,
    sort_keys=True,
    separators=(",", ":"),
    ensure_ascii=False,
    allow_nan=False,
).encode("utf-8")
```

YAML comments, whitespace, key order, quoting style, and other lexical choices
are intentionally outside the manifest signature after parsing.

### Runtime Verification

For a community-installed skill, the runtime MUST:

1. parse `skill.yaml` with duplicate-key and type validation;
2. reject the `bundled` sentinel;
3. parse the `ed25519:<base64>` signature;
4. resolve the configured Hub manifest trust anchor;
5. reproduce the canonical unsigned manifest bytes;
6. verify before importing or executing any hook code.

The runtime verifier is defense in depth after installation. It does not
replace the installer's pre-extraction artifact verification.

## Bundled Sentinel

Runtime-bundled skills may carry:

```text
bundled
```

Rules:

- `bundled` is valid only on the trusted runtime-bundled path.
- It applies only to the manifest profile.
- Community uploads, downloads, and installed community skills MUST reject it.
- It is never an artifact signature.

## Publishing Sequence

The Skills Hub publish pipeline is:

1. authenticate the author;
2. verify the detached author artifact signature before extraction or storage;
3. safely extract, validate, and scan without executing hooks;
4. place Tier C/D skills into required review before public listing;
5. add or replace the embedded Hub manifest signature;
6. build the final distribution artifact;
7. compute its SHA-256 and detached Hub artifact signature;
8. publish the artifact and detached metadata atomically.

The Hub MUST NOT claim that an author signed the rebuilt Hub artifact. The
author signature applies only to the exact bytes uploaded by the author.

## API Separation

Implementations SHOULD expose distinct entry points such as:

```text
verify_artifact_signature(artifact_bytes, metadata, public_key)
verify_manifest_signature(parsed_skill, public_key)
sign_artifact(artifact_bytes, private_key)
sign_manifest(parsed_skill, private_key)
```

A generic `verify_skill_signature` that accepts both byte payloads and parsed
manifests is forbidden because it makes profile confusion easy.

## Shared Golden Vectors

[`vectors-v1.json`](vectors-v1.json) is the byte authority for both payload
profiles. It contains a disclosed test seed only for deterministic
interoperability tests.

The SHA-256 of the exact vector file is:

```text
13832babac98468ddd368aafd04c5140bba771f568500c50d4bac60c8588fddc
```

Consumers MUST assert:

- the canonical manifest bytes and SHA-256 match;
- the manifest signature verifies over those canonical bytes;
- the artifact signature verifies over the decoded exact bytes;
- either payload fails under the other payload's signature;
- changing one byte in either payload fails verification.

The vector artifact payload is intentionally small rather than a full tarball:
the cryptographic rule is over an opaque byte sequence. Safe archive structure
and extraction require implementation-local negative tests.

## Error Semantics

Implementations SHOULD expose typed errors:

| Condition | Recommended error |
|---|---|
| missing cryptography backend | `crypto_unavailable` |
| malformed signature field | `invalid_signature_format` |
| malformed public key | `invalid_public_key` |
| invalid detached metadata | `invalid_artifact_signature_metadata` |
| artifact digest mismatch | `artifact_digest_mismatch` |
| signature verification failed | `signature_verification_failed` |
| bundled sentinel outside bundled path | `bundled_signature_not_allowed` |

Verification failure is never a warning.

## Security Requirements

- Verify author upload bytes before extraction or storage.
- Verify Hub distribution bytes before extraction.
- Verify the embedded manifest before runtime hook loading.
- Never execute hooks during publishing or installation.
- Failed verification or extraction leaves no partial public artifact or
  installed skill.
- Private keys never appear in repositories, logs, API responses, fixtures
  other than explicitly disclosed test seeds, or error messages.
- Key rotation invalidates artifacts and manifests under the retired key until
  they are deliberately re-signed or a bounded previous-key verification
  policy is specified by a future contract.
