# Schema Descriptor Core v1

> Status: Design target, pre-ratification. No shipped consumer claims
> conformance. Amendable in place under the
> [pre-ratification exception](../VERSIONING.md#pre-ratification-exception).

More than one Ori contract needs to say "this key accepts a bounded integer, and
nothing undeclared may appear beside it". `sensor-configuration/v1` needs it for
adapter-declared protocol configuration; `skills-package/v3` needs it for
author-declared, signed skill configuration.

Those two have **different authority models** and different extensions. What
they share is the shape of a typed, recursively closed declaration, and only
that is defined here.

## What this contract is, and is not

**It is** the primitive layer: types, bounds, enumerations, defaults, and
recursive closure.

**It is not** a schema language anyone declares conformance to on its own. A
contract adopting this core states that it does, then adds its own rules. This
document has no consumers of its own.

## Why extract it rather than repeat it, or import it wholesale

Two copies of a type system drift, and the drift is invisible: each contract
looks internally consistent while two implementations disagree about whether
`7.0` satisfies `integer`.

Wholesale import is the opposite failure. `sensor-configuration/v1` lets a field
inherit a value from another section of the device configuration document —
which is exactly wrong in a **signed** package manifest, where a schema
inheriting from an unsigned deployment document would invert the trust model the
signature exists to establish. A contract must not acquire a feature by
inheritance that its authority model forbids.

So the core is deliberately small, and each adopting contract carries its own
extensions.

## Field descriptor grammar

| Property | Meaning |
| --- | --- |
| `type` | `string`, `integer`, `number`, `boolean`, `array`, `object`. Required. |
| `required` | Absent key is refused. Defaults to `false`. |
| `default` | Value used when the key is absent. Mutually exclusive with `required: true`. |
| `minimum`, `maximum` | Inclusive bounds. Numeric types only, and constrained below. |
| `enum` | Closed vocabulary. Non-empty; every member must satisfy the descriptor's own type and bounds. |
| `properties` | Required when `type: object`. Maps key name to a field descriptor. |
| `items` | Required when `type: array`. A field descriptor for every element. |

A descriptor property this core does not define, and the adopting contract does
not add, MUST be refused when the schema is loaded. An unrecognised property is
either a typo or an expectation the validator will not meet, and both are worth
refusing.

### Bounds are constrained at schema load

A bound is part of the declaration, so a malformed one is the schema author's
error and MUST surface before any document exists. Deferring it to document
validation contradicts this core's own rule that everything checkable without a
document is checked without one — and blames the wrong party when it finally
fails.

- **A bound MUST be a finite number.** `NaN` and infinity are refused. A `NaN`
  bound silently admits everything, because every comparison against it is
  false, so the declaration reads as a constraint and enforces nothing.
- **A bound MUST NOT be a boolean**, for the same reason a boolean is not an
  integer value.
- **On `type: integer`, a bound MUST itself be an integer.** `minimum: 1.5`
  describes a boundary no valid value can sit on, and implementations will
  disagree about whether `2` or `1` is the first admissible value.
- **`minimum` MUST NOT exceed `maximum`.** A descriptor admitting nothing is a
  declaration nobody can satisfy; refusing it once at load is better than
  refusing every document that tries.

## Types are checked, never coerced

`integer` means integer. **`7.0` is not `7`**: they are different documents, and
implementations disagree about whether they are the same number — a value that
round-trips through more than one parser must not depend on that disagreement.

**A boolean is not an integer**, whatever the host language says. In Python
`True` is an instance of `int`, so a naive check reads it as `1`.

Coercion is refused rather than performed. A coerced value turns a malformed
document into a working one whose author believes something else, and the
belief is never corrected because nothing failed.

## Closure is recursive

A declaration that permits `object` without saying what may sit inside it
reopens, one level down, exactly the surface a closed schema exists to close.

- **`type: object` MUST declare `properties`.** An object descriptor without it
  is itself invalid, and MUST be refused when the schema is loaded rather than
  when a document happens to exercise it.
- **`type: array` MUST declare `items`.** An array of unvalidated values is the
  same hole in a different shape.
- **An undeclared key at any depth MUST be refused**, and the refusal MUST name
  the full path to it, not just the leaf. A refusal naming only the leaf is
  unactionable in a nested document.
- **A `default` MUST itself validate against its own descriptor**, checked when
  the schema is loaded. A default the schema would reject is a defect that
  otherwise appears only for whoever omits the key.

## Two phases, and which errors belong to whom

A conforming implementation MUST distinguish:

| Phase | Subject | Meaning |
| --- | --- | --- |
| **Schema load** | The declaration | The schema is wrong. No document is needed to know it. |
| **Document validation** | The document | The document is wrong about a valid schema. |

The distinction is not cosmetic: the two blame different people. A malformed
bound surfacing as a type error during a later comparison blames the operator
for the schema author's mistake.

**Everything checkable without a document MUST be checked at schema load.** A
schema that has not been validated MUST NOT be used to validate a document —
otherwise an invalid declaration either fails at the wrong moment or, for a
document that never exercises it, does not fail at all.

## Adopting this core

A contract adopting `schema-descriptor/v1` states so, and MAY add:

- further descriptor properties, with their own load-time rules
- schema-level constraints across fields
- rules about where declarations live, who signs them, and what authority they
  carry

It MUST NOT weaken anything above. A contract that admitted coercion, or an
object without declared properties, would not be adopting this core; it would be
describing a different one under the same name.

| Contract | Adds |

## Vectors

Cases belong to the adopting contract's corpus, since a descriptor has no
meaning without a document to validate. A corpus claiming conformance to this
core MUST cover, at minimum:

- each primitive type accepted, and refused when given another type's value
- `7.0` against `integer`, refused
- a boolean against `integer` and against `number`, refused
- a value below `minimum` and above `maximum`, refused
- a value outside `enum`, refused
- a non-numeric, `NaN`, infinite, or boolean bound, refused at schema load
- a fractional bound on `type: integer`, refused at schema load
- `minimum` greater than `maximum`, refused at schema load
- an empty `enum`, and an `enum` member the descriptor's own type or bounds
  reject, both refused at schema load
- `type: object` without `properties`, and `type: array` without `items`,
  refused at schema load
- an undeclared key nested two levels deep, refused by full path
- a `default` its own descriptor rejects, refused at schema load
- an unrecognised descriptor property, refused at schema load
