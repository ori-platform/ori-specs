# Evidence Chain Contract v1

> Status: Mixed — each section below carries its own status label.
> Implemented sections are sourced from `ori-verity` (Rust chain artifact),
> `ori-runtime` (`ori/security/evidence.py`, `ori/state/store.py`,
> `ori/gateway/node_heartbeat.py`, `ori/runtime.py`), and `ori-gateway`
> (`internal/site/evidence.go`).

This contract defines the tamper-evident evidence chain surface across the Ori
ecosystem: how Tier C/D physical actions are cryptographically attested on the
device, how the resulting integrity signal travels to the gateway, and the
design targets for anchoring device keys and ingesting exported evidence
off-device.

The purpose is verifiability by adversarial third parties (auditors, insurers,
financiers): signed evidence cannot be backfilled, and evidence produced late
is explicitly marked as late. A deployment where evidence signing breaks keeps
acting (safety never waits for signing) but the gap stays visible until it is
repaired.

## Trust Model

- Each device holds an Ed25519 signing key, sealed at rest. The public key is
  the device's **verification anchor**.
- Events are hash-chained (SHA-256 over a canonical envelope) and signed. The
  chain lives in an append-only SQLite table on the device; signed columns are
  immutable at the database layer.
- The chain artifact (`ori_verity`) is consumed by the runtime as an exactly
  pinned, prebuilt artifact. The runtime verifies at startup that the loaded
  artifact declares protocol `verity.v1` and exposes the idempotent append
  surface; on mismatch, evidence signing stays unavailable and health says so.
  The pin is recorded in the runtime repo (`verity-artifact.pin`), and runtime
  CI builds the artifact from that exact ref and runs the real FFI against it,
  so runtime/artifact protocol agreement is demonstrated per change, not
  assumed.
- The device can prove chain integrity, not chain completeness: a device-local
  attacker can destroy or roll back the chain file. Completeness therefore
  comes from off-device observation — the gateway's truncation/regression
  detection (below) and, as a design target, anchored keys plus authenticated
  export ingestion.

## Chain Row

> Status: Implemented in `ori-verity`.

One chain row per attested event:

| Column            | Type            | Notes                                                              |
| ----------------- | --------------- | ------------------------------------------------------------------ |
| `seq`             | `integer`       | Monotonic, assigned at append.                                     |
| `event_id`        | `string` UNIQUE | Non-empty caller-supplied idempotency key. Runtime action          |
|                   |                 | attestations use deterministic UUIDv5 strings (below).             |
| `event_type`      | `string`        | One of the protocol event types (below).                           |
| `device_id`       | `string`        | Emitting device. Appends are device-scoped.                        |
| `emitted_at_ms`   | `integer`       | Original event time supplied by the caller — never write time.     |
| `payload_json`    | `string`        | Event payload as supplied.                                         |
| `canonical_json`  | `string`        | Canonical signed envelope: keys sorted, no extra whitespace.       |
| `event_hash`      | `string`        | SHA-256 over the canonical envelope, lowercase hex.                |
| `prev_event_hash` | `string`        | Head at append time; genesis rows use the protocol genesis value.  |
| `signature`       | `string`        | Ed25519 signature over the canonical envelope.                     |
| `exported`        | `integer`       | Export bookkeeping (mutable).                                      |
| `exported_at_ms`  | `integer\|null` | Export bookkeeping (mutable).                                      |
| `created_at_ms`   | `integer`       | Chain write time. Together with `emitted_at_ms`, makes late writes |
|                   |                 | independently visible.                                             |

Only `exported` and `exported_at_ms` are mutable; deletes and updates of signed
columns are refused at the SQLite layer.

## Event Type Vocabulary

> Status: Implemented in `ori-verity` (protocol `verity.v1`).

Wire names are SCREAMING_SNAKE_CASE:

`UPTIME_HEARTBEAT`, `OUTAGE_STARTED`, `OUTAGE_RESOLVED`, `DISPLACEMENT_RECORD`,
`MAINTENANCE_PERFORMED`, `REVENUE_COLLECTED`, `UTILISATION_RECORD`,
`KEY_ROTATION`, `SAFETY_ACTION_EXECUTED`.

`KEY_ROTATION` is a protocol event dual-signed by the outgoing and incoming
device keys, so a verifier can walk anchor → current key.

### Safety-action event type

> Status: Implemented — `ori-verity` artifact >= 0.2.0 provides the type;
> `ori-runtime` emits it when its loaded artifact supports it.

`SAFETY_ACTION_EXECUTED` is the dedicated event type for Tier C/D physical
actions attested by an agent runtime, letting verifiers filter
physical-authority events without payload inspection.

Emission is gated by the loaded artifact, not the runtime version: runtimes
select `SAFETY_ACTION_EXECUTED` when the artifact's version parses to
`>= 0.2.0` and conservatively fall back to `MAINTENANCE_PERFORMED` (the type
every artifact accepts) on older or unparseable versions — a misread version
must never produce a rejected append on the evidence path. The payload is
byte-identical across both forms.

**Verifiers must accept both forms.** Rows signed before the artifact upgrade
carry `MAINTENANCE_PERFORMED` with payload `kind: runtime_action`. Signing —
including late reconciliation of rows that were pending across the upgrade —
always uses the device's *current* `action_event_type`, so a reconciled row
can carry `SAFETY_ACTION_EXECUTED` with `attestation: reconciled_late`.
Lateness is determined by inspecting the payload `attestation` marker and the
chain timestamps, never by the event type. The vocabulary a device currently
emits is visible before its first Tier C/D action fires, as
`action_event_type` in the runtime health evidence object
(`runtime-health/v1.md`) and the heartbeat evidence block
(`gateway-api/v1.md`); it is `''` while signing is unavailable.

## Runtime Action Attestation

> Status: Implemented in `ori-runtime` (evidence signing is opt-in via
> `evidence.enabled`; see `runtime-config/v1.md`).

Every Tier C and Tier D action dispatch is attested into the local chain.
Attestation is **append-after-log** (Option B): the `action_log` row is
written first with attestation status `pending`, then signed. Signing failures
mark the row `failed` and never block or crash the action path.
Single-transaction atomicity across `action_log` and the chain remains the
verifier-grade design target.

### Attestation event

| Field           | Value                                                                          |
| --------------- | ------------------------------------------------------------------------------ |
| `event_type`    | `SAFETY_ACTION_EXECUTED` on vocabulary-capable (>= 0.2.0) artifacts;           |
|                 | `MAINTENANCE_PERFORMED` on older or unparseable ones (see above).              |
| `event_id`      | Deterministic UUIDv5 (below).                                                  |
| `device_id`     | Runtime `device.id`.                                                           |
| `emitted_at_ms` | The `action_log` row's dispatch timestamp — never signing time.                |

Payload (`payload_json`):

```json
{
  "kind": "runtime_action",
  "attestation": "at_emission|reconciled_late",
  "action_log_id": 0,
  "action_name": "string",
  "action_tier": "C|D",
  "executed": true,
  "approved": null,
  "action_taken": "string",
  "trigger_name": "string",
  "proposal_id": "string",
  "correlation_id": "string",
  "sensor_id": "string"
}
```

### Idempotency

`event_id` is `uuid5(namespace, "{device_id}:action_log:{action_log_id}")`
with the fixed namespace UUID `6f726920-7665-5269-7479-2065766e7431`. The
namespace must never change: ids derived from it are the idempotency keys of
already-signed evidence. `event_id` is UNIQUE in the chain; the attestor looks
the id up before appending, so a crash between the chain append and the
`action_log` status update cannot double-attest on retry.

### Late-signing semantics

An action that fires while signing is unavailable stays visible as a gap
(`attestation_status` of `pending` or `failed`). Startup reconciliation may
sign it late; when it does, the lateness is explicit twice over: the signed
payload carries `attestation: reconciled_late` (versus `at_emission` on the
normal path), and the chain independently records `created_at_ms` next to the
original `emitted_at_ms`. Rows that still cannot be signed remain `failed` and
visible. Late evidence must never be presented as emission-time evidence.

### `action_log` attestation columns

Additive columns on the runtime `action_log` table (see `events/v1.md` for the
base schema):

| Column               | Type            | Notes                                                             |
| -------------------- | --------------- | ----------------------------------------------------------------- |
| `attestation_status` | `string`        | `''` (not on the evidence path), `pending`, `signed`, `failed`,   |
|                      |                 | or `reconciled` (signed late by startup reconciliation).          |
| `attestation_seq`    | `integer\|null` | Chain `seq` of the attestation event when signed.                 |

Both fields appear in `action_log` export responses (`gateway-api/v1.md`).

## Heartbeat Evidence Signal

> Status: Implemented in `ori-runtime` and `ori-gateway`.

Evidence-enabled runtimes include an `evidence` block in the runtime node
heartbeat; the payload and bounds are defined in `gateway-api/v1.md`. The
signal is advisory liveness/integrity data — the persisted chain remains the
evidence object.

### Gateway integrity observation

The chain head is an opaque hash, so the gateway cannot order two heads. What
it detects, by remembering recent heads per device (bounded ring, newest 16),
is the two shapes a device-local tamper attempt takes:

- **truncation**: a device that previously reported a non-empty head reports
  an empty chain — the chain database was deleted or reset. An empty head from
  a device with no evidence history is normal (new provisioning).
- **head regression**: a device reports a head it had already advanced past —
  a rollback, not an append.

Both observations are **sticky** for the lifetime of the device's registry
entry: a later normal-looking heartbeat does not clear suspicion; an operator
must investigate. Eviction from the registry drops the memory, so a
legitimately reprovisioned device starts fresh.

An **omitted** evidence block from a device that previously reported evidence
is treated as evidence-unavailable (last known head retained,
`available=false`), not as "no evidence surface" — otherwise disabling
evidence would be a silent downgrade path.

Site health degrades a node on truncation, regression, or unavailability. Gap
count alone is informational: transient signing failures self-repair via the
runtime's startup reconciliation.

Detection limits (explicit): the ring is bounded, so a rollback deeper than
the retained history is not detected by head comparison; gateway restart
clears observation memory; and a device wiped and re-keyed presents as a new
chain. Closing those gaps requires the anchor registry and export ingestion
targets below.

The runtime health snapshot (local socket RPC and the `health` export type)

## Design Target: Anchor Registry

> Status: Design Target. Not implemented in any repo. Do not build consumers
> against this section yet.

Chain verification starts from the device's initial public key. Today the
anchor is only logged at first provisioning; registering it off-device is a
manual provisioning step. The target contract:

| Field                | Type     | Notes                                                        |
| -------------------- | -------- | ------------------------------------------------------------ |
| `device_id`          | `string` | Runtime device ID.                                           |
| `initial_pubkey_hex` | `string` | Ed25519 public key, 64 lowercase hex chars.                  |
| `registered_at_ms`   | `int`    | Registration time.                                           |
| `registered_by`      | `string` | Authenticated registrar identity (provisioning actor).       |

Open design questions to resolve before implementation:

- Registrar and store: the gateway has no persistent store; the registry
  likely belongs to ori-cloud (or a site-local signed file) with the gateway
  as transport.
- Transport: whether registration flows over an MQTT provisioning topic or an
  authenticated HTTP endpoint.
- Rebinding: legitimate re-provisioning must be an explicit, audited anchor
  replacement, never an implicit overwrite — an attacker who can silently
  rebind the anchor owns the chain.

## Design Target: Evidence Export Ingestion

> Status: Design Target. Not implemented in any repo. Do not build consumers
> against this section yet.

The chain marks rows `exported` locally, but nothing off-device receives them
yet. The target is an authenticated ingestion surface (working name
`/verity/ingest`, expected to live in the gateway/product layer) that accepts
batches of chain rows and returns signed receipts:

- Ingest request: ordered batch of chain rows for one `device_id`, carrying
  the full signed columns (`event_id` through `signature`) so the receiver can
  verify hash-chain continuity and signatures against the registered anchor
  before accepting.
- Receipt: an acknowledgment binding `device_id`, the accepted `seq` range,
  and the batch head hash, signed by the receiver. The device stores receipts;
  a receipt over seq N transfers custody of truncation detection for all rows
  up to N from heuristic (heartbeat observation) to proof.
- Rejection: batches failing signature, continuity, or anchor checks are
  rejected with a reason; the device must keep rows unexported (`exported=0`)
  and surface the rejection in health.

Ingestion must be pull-tolerant and offline-first: devices batch and retry;
the receiver is idempotent by `event_id`.

## Invariants

- Evidence signing never blocks, delays, or gates a Tier C/D action. Safety
  first, evidence second.
- Signed evidence cannot be backfilled silently: late signing is marked in the
  signed payload and visible in chain timestamps.
- The runtime never presents late evidence as emission-time evidence.
- The heartbeat evidence block is a signal, not an archive; consumers must not
  treat it as a substitute for chain export.
- Evidence state in projections must not expose key material, key or database
  paths, or device secrets. The chain head hash and public key are not
  secrets.
- The `event_id` namespace UUID and the canonical JSON form are frozen: both
  participate in already-signed evidence.
