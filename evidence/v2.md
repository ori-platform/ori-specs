# Evidence Chain Contract v2

> Status: **Design Target, pre-ratification.** Produced natively by
> `ori-runtime` (`ori/security/evidence_chain.py`, the private producer is
> retired) and verified by `ori-verity` (`tests/evidence_v2_golden.rs`), both
> against the vectors here. [v1](v1.md) is retained for verifying rows written
> before the native producer. Vectors in [`vectors/`](vectors/) are normative
> for the bytes.

## Why v2 exists

v1 defines the chain's *columns* but never its *bytes*. The canonical envelope's
field set, the genesis preimage, and the signing contexts were left inside a
single private implementation, and v1 says so explicitly: the chain "is produced
by an exactly pinned, prebuilt artifact consumed by the runtime". That was
workable while exactly one implementation existed.

It stops being workable the moment a second producer exists. A format that lives
only in one private codebase cannot be independently implemented, cannot be
verified against, and drifts silently the first time either side changes.

The second problem is disclosure. Four constants carry the private
implementation's identity into material that is signed, transmitted, and
retained:

| Constant | v1 value | Reaches |
| --- | --- | --- |
| Envelope schema version | `verity.v1` | every signed envelope, every exported row, every vector |
| Genesis preimage | `verity.genesis` | the genesis `prev_event_hash` of every chain |
| Rotation proof context | `verity.rotation.v1` | every `KEY_ROTATION` possession proof |
| Attestation UUIDv5 namespace | `6f726920-7665-5269-7479-2065766e7431` | every deterministic `event_id` |

The fourth is worth stating plainly rather than leaving as a hex value: those
sixteen bytes decode to the ASCII string `ori veRity evnt1`. An identifier that
is encoded rather than written is still an identifier, and it escapes a search
for the term as text — which is exactly how it survived review until a second
implementation had to reproduce it.

The evidence arrangement's value depends on the site being unable to reach,
influence, or be asked to carry the record. Naming the authority inside the
bytes a device produces and hands to a courier contradicts that, and no amount
of care at the operator-facing surface fixes it. The runtime already translates
the envelope version to a neutral alias where an operator reads it; the signed
bytes were never translated.

v2 changes exactly these two things: the vocabulary is neutral, and the format
is fully specified here rather than in an implementation.

## What is unchanged from v1

The column set, the hash chain construction, the signature algorithm, the event
vocabulary, the idempotency model, append-after-log attestation, and the
immutability rule are all as v1 defines them. v2 is not a redesign. A reader who
knows v1 needs only this document's vocabulary table and canonical-form section.

## Vocabulary

| Name | v2 value |
| --- | --- |
| Envelope schema version | `ori.evidence.v2` |
| Genesis preimage | `ori.evidence.genesis.v2` |
| Rotation proof context | `ori.evidence.rotation.v2` |
| Attestation UUIDv5 namespace | `3f3d6f03-be9c-50ac-b655-db9540cb5c45`, derived below |

`ori.evidence.v2` is also the value [runtime health](../runtime-health/v2.md)'s
`protocol_version` carries once a producer emits v2. No translation layer is
required, because the wire value is already neutral.

### Naming applies to implementations, not only to the wire

Neutral wire vocabulary is defeated by an implementation that names its own
storage after the authority. A database table, a module, a class, a package, a
symbol, a filename, or a migration name that carries the implementation's
identity is visible wherever that implementation is installed — in a schema
dump, a stack trace, a package listing, a process map — and the operator-facing
boundary does not distinguish between a name on the wire and a name in a table.

**The rule is scoped to what sits where an operator can reach it.** A component
installed on the runtime device, or on any other site component an operator can
access, MUST NOT name its evidence storage or modules after the evidence
authority. `evidence_chain` describes what the table holds; a table named after
the product that produces it does not.

The off-device authority is explicitly **not** covered. Its own schema, modules
and internal naming are its business: they are not part of this wire contract,
they are not installed anywhere an operator reaches, and requiring it to avoid
its own name inside its own service would be cargo-culting the boundary rather
than enforcing it. The boundary is about what a site can see, not about the word
itself.

This is not hypothetical. The v1 producer's schema is branded throughout —
seventeen table, index and trigger names, including the chain table and its
immutability triggers — and that schema is created **on the device**. A schema
dump, a `.tables` listing, an integrity-violation message naming a trigger, or a
stack trace carrying a table name each disclose the authority to whoever holds
the device. The database *filename* was already neutralised; its contents were
not, which is the same half-measure as neutralising the health field while
leaving the signed envelope branded.

That particular schema stops being on-device when the runtime produces rows
natively and the private artifact is removed from devices altogether. The rule
below is what keeps its replacement from repeating the pattern.

A conforming implementation names these after what they hold:

| Holds | Neutral name |
| --- | --- |
| chain rows | `evidence_chain` |
| device registry | `evidence_device_registry` |
| device anchors | `evidence_device_anchors` |
| anchor transitions | `evidence_anchor_transitions` |

Indexes and triggers follow their table.

The same applies to encoded values. An identifier concealed as hex, base64 or
escape sequences is still that identifier, and is caught by decoding rather than
by searching for the text — which is how the UUIDv5 namespace above survived
until a second implementation had to reproduce it.

## Canonical form

The platform already settled this, and v2 adopts that rule rather than
restating a second one. It is normative in
[`firmware-telemetry/v1.md`](../firmware-telemetry/v1.md) and implemented in C,
Rust and Python; Layer 1 and Layer 2 canonicalise identically, which is what
lets a firmware signer be cross-checked against a Layer 2 vector at all.

```text
canonical(value) = UTF-8 JSON bytes of `value` in which
                   object keys are sorted lexicographically at every
                   nesting level, arrays keep caller order, there is no
                   whitespace outside string values, strings are escaped
                   per RFC 8259, and numbers obey the constraints below
```

Sorting MUST be applied recursively and explicitly. An implementation MUST NOT
rely on a serialiser's insertion-order preservation or on a language's
dictionary ordering.

Equivalent in Python:

```python
json.dumps(obj, sort_keys=True, separators=(",", ":"),
           ensure_ascii=False, allow_nan=False).encode("utf-8")
```

### Numbers

Unconstrained JSON numbers are not interoperable. CPython and `serde_json`
produce different bytes for the same value outside a bounded range — `0.00001`
against `1e-05`, `1.5e-7` against `1.5e-07` — and bytes are the signing
contract, so a divergence there is a signature that verifies on one side and
not the other.

The platform's answer is the D-011 agreement zone, and v2 uses it unchanged:

- integers satisfy `|n| <= 9007199254740991` (2^53 − 1);
- non-integer numbers are finite, and either exactly zero or of magnitude in
  `[1e-4, 1e16)`;
- they serialise as the shortest round-trip decimal in **fixed notation**, with
  a mandatory fractional part — `.0` appended for integral doubles, `-0.0`
  preserved;
- exponent notation never appears on the wire.

A value outside the zone is refused by the serialiser rather than emitted. That
is deliberate: an evidence payload that cannot be reproduced byte for byte by
every verifier is worse than one that was refused at source.

RFC 8785 (JCS) was considered and rejected for the platform, because neither
`serde_json` nor CPython implements its number serialisation, and adopting it
would put a custom formatter into all three verifier languages. Inside the
agreement zone the stock serialisers already agree.

### Strings and keys

- Strings are escaped per RFC 8259. Non-ASCII characters are emitted as
  themselves, not as `\u` escapes.
- Object keys MUST be strings. Sorting a mixed-type key set is undefined.
- An object MUST NOT carry duplicate keys. The canonical form of such an object
  is undefined, and a parser that silently keeps the last occurrence would
  verify bytes that a stricter parser rejects.

### Rejections

Number checking is recursive: a value nested inside an array or object is
subject to the same constraints as one at the top level, because
canonicalisation reaches all of them.

**Which side enforces which refusal is not symmetric, and stating it as one
undivided list tells each side to do something it structurally cannot.**

A producer serialises a native mapping, and a native mapping cannot hold the
same key twice — by the time `{"a":1,"a":2}` reaches a producer it has already
collapsed to `{"a": 2}`, and no amount of checking recovers the duplicate. The
reverse holds for a non-string key: it cannot be written in JSON text at all,
so a parser refuses `{1:2}` as malformed without ever examining the key's type.

| Refusal | Producer, holding a native value | Verifier, parsing bytes |
| --- | --- | --- |
| `NaN`, `Infinity`, `-Infinity` | MUST refuse | MUST reject |
| number outside the agreement zone | MUST refuse | MUST reject |
| integer beyond 2^53−1 | MUST refuse | MUST reject |
| non-string object key | MUST refuse | not reachable — cannot be parsed from text |
| duplicate object key | not reachable — collapsed before it arrives | MUST reject, during parsing |

**"Not reachable" is not "optional".** It means the defect cannot exist on that
side, and an implementation MUST record it as structurally unreachable rather
than skip it silently. The two look identical afterwards: a test that exempts a
case it cannot construct and a test that covers it both report green. That is
not hypothetical — the first implementation of this contract exempted the
non-string-key case to make a test pass, which turned a known gap into a
passing assertion until someone read the exemption.

A verifier's duplicate-key obligation is strict for the same reason. A default
parser keeps the last occurrence and discards the evidence of the defect before
anything can inspect it, so detection MUST happen during parsing rather than by
examining the parsed result.

[`vectors/canonical-form.json`](vectors/canonical-form.json) carries the
accepted forms with their exact bytes and the refused forms as executable
inputs. Two of the refusals cannot be driven by parsing text and calling it
done:

- **Duplicate keys** do not survive an ordinary parse. Most parsers keep the
  last occurrence silently, so the defect is gone before anything can inspect
  it. A verifier must detect duplicates during parsing.
- **A non-string key cannot be written in JSON at all.** `{1:2}` is malformed
  text, and a parser refuses it for being unparseable without ever examining
  the key's type — so testing that string proves nothing about this rule. The
  vector therefore describes the native object to construct, and a verifier
  builds it rather than parsing it.

Every refusal must produce exactly the violation it declares. An implementation
whose types make a case unconstructible must record it as structurally
unreachable rather than exempt it, because an exemption and a passing test look
identical afterwards.

## The signed envelope

Exactly eight fields. A producer MUST emit all eight and no others; a verifier
MUST reject an envelope carrying a field this contract does not define.

| Field | Type | Notes |
| --- | --- | --- |
| `device_id` | `string` | Emitting device. Appends are device-scoped. |
| `emitted_at_ms` | `integer` | Original event time supplied by the caller — never signing or write time. |
| `event_id` | `string` | Non-empty idempotency key. Runtime action attestations use the deterministic UUIDv5 form below. |
| `event_type` | `string` | One of the event vocabulary below. |
| `payload` | `object` | Event payload as supplied. |
| `prev_event_hash` | `string` | Chain head at append time; the genesis value for the first row. Lowercase hex, no prefix. |
| `schema_version` | `string` | `ori.evidence.v2`. |
| `sequence_num` | `integer` | Monotonic, assigned at append. Matches the row's `seq`. |

The envelope excludes its own signature. `canonical_json` is
`canonical(envelope)`, and those exact bytes are what the device key signs and
what the hash covers.

```text
canonical_json = canonical(envelope)
event_hash     = lowercase_hex(SHA-256(canonical_json))
signature      = "ed25519:" || base64(Ed25519(device_key, canonical_json))
```

The signature covers `canonical_json` **directly**. There is no domain prefix on
the chain row, unlike the exchange artifacts in
[`evidence-exchange/v1.md`](../evidence-exchange/v1.md), because
`schema_version` inside the envelope already separates this format from every
other signed object in the platform. A verifier MUST verify against the stored
`canonical_json` bytes and MUST NOT re-canonicalise the envelope object to
obtain them.

## Genesis

```text
GENESIS_PREV_EVENT_HASH = lowercase_hex(SHA-256(utf8("ori.evidence.genesis.v2")))
                        = 84880636041c3715396109a3cb53c7984d0ddfd234d00a71585ce371efb1da61
```

See [`vectors/genesis.json`](vectors/genesis.json), which publishes the preimage
and its UTF-8 bytes so the value is reproducible rather than asserted.

The first row of a chain uses this as `prev_event_hash`. It is a protocol
constant. It MUST NOT be configurable: a chain whose genesis value came from
deployment configuration is not interoperable, and moves protocol authority into
provisioning.

## The attestation event identifier

`event_id` for a runtime action attestation is a deterministic UUIDv5, so a
retry after a crash reproduces the same identity and a row cannot be
double-attested.

The namespace is derived, not chosen, and every input is published so it can be
recomputed rather than trusted:

```text
root namespace     = RFC 4122 URL namespace
                     6ba7b811-9dad-11d1-80b4-00c04fd430c8
namespace name     = "https://oriplatform.dev/specs/evidence/v2/event-id"
EVENT_ID_NAMESPACE = UUIDv5(root namespace, namespace name)
                   = 3f3d6f03-be9c-50ac-b655-db9540cb5c45

per-event name     = "{device_id}:action_log:{action_log_id}"
event_id           = UUIDv5(EVENT_ID_NAMESPACE, per-event name)
```

The namespace name is a URI used as an input string. It is never resolved, and
nothing fetches it; it exists so the derivation is anchored to an identifier the
project controls rather than to an arbitrary constant.

`EVENT_ID_NAMESPACE` is frozen by publication. Changing the name would change
every derived identifier, and those identifiers are the idempotency keys of
signed evidence.

**v1 identifiers stay v1 identifiers.** Values derived under the v1 namespace
are not recomputed, reinterpreted or migrated under this one. A verifier reading
a v1 row treats its `event_id` as opaque.

See [`vectors/event-id.json`](vectors/event-id.json).

## Row storage

One row per attested event, as v1 defines:

| Column | Type | Notes |
| --- | --- | --- |
| `seq` | `integer` | Monotonic, assigned at append. Equals the envelope's `sequence_num`. |
| `event_id` | `string` UNIQUE | Idempotency key. |
| `event_type` | `string` | Event vocabulary. |
| `device_id` | `string` | Emitting device. |
| `emitted_at_ms` | `integer` | Caller-supplied event time. |
| `payload_json` | `string` | Payload as supplied. |
| `canonical_json` | `string` | The exact signed bytes. |
| `event_hash` | `string` | SHA-256 over `canonical_json`, lowercase hex. |
| `prev_event_hash` | `string` | Head at append time. |
| `signature` | `string` | `ed25519:` over `canonical_json`. |
| `exported` | `integer` | Export bookkeeping (mutable). |
| `exported_at_ms` | `integer\|null` | Export bookkeeping (mutable). |
| `created_at_ms` | `integer` | Chain write time. With `emitted_at_ms`, makes late writes independently visible. |

Only `exported` and `exported_at_ms` are mutable. Updates and deletes of signed
columns MUST be refused at the storage layer, not merely avoided by application
code.

## Event vocabulary

`UPTIME_HEARTBEAT`, `OUTAGE_STARTED`, `OUTAGE_RESOLVED`, `DISPLACEMENT_RECORD`,
`MAINTENANCE_PERFORMED`, `REVENUE_COLLECTED`, `UTILISATION_RECORD`,
`KEY_ROTATION`, `SAFETY_ACTION_EXECUTED`.

`SAFETY_ACTION_EXECUTED` is the dedicated type for Tier C/D physical actions
attested by an agent runtime, so a verifier can filter physical-authority events
without payload inspection. A v2 producer emits it unconditionally — the v1
fallback to `MAINTENANCE_PERFORMED` existed only to tolerate artifacts older
than the type, and v2 has no such artifacts.

## Rejection rules

A verifier MUST reject a row when any of the following holds. Each is a distinct
outcome and MUST be distinguishable in a finding rather than collapsed into a
single "invalid" result.

| # | Rule |
| --- | --- |
| 1 | `sequence_num` is not the expected successor of the previous row's |
| 2 | `prev_event_hash` does not equal the previous row's `event_hash` |
| 3 | `event_hash` does not equal SHA-256 of `canonical_json` |
| 4 | the signature does not verify against `canonical_json` under the device key |
| 5 | `sequence_num` inside the envelope disagrees with the row's `seq` |
| 6 | `prev_event_hash` inside the envelope disagrees with the row's column |
| 7 | `event_id` inside the envelope disagrees with the row's column |
| 8 | `event_type` inside the envelope disagrees with the row's column |
| 9 | `device_id` inside the envelope disagrees with the row's column |
| 10 | `emitted_at_ms` inside the envelope disagrees with the row's column |
| 11 | `schema_version` is not `ori.evidence.v2` |
| 12 | `payload_json` disagrees with the envelope's `payload` |
| 13 | the envelope carries a field this contract does not define |

Rules 5 to 10 exist because the row's columns are what a reader queries while
the envelope is what was signed. Without them a row could present columns that
describe an event different from the bytes that were attested.

**A v1 row MUST NOT be reinterpreted as v2.** Rule 11 makes that automatic:
`verity.v1` is not `ori.evidence.v2`, so a v1 row fails v2 verification rather
than being silently accepted. A verifier retaining v1 support MUST select the
verification path by `schema_version` and MUST attribute a finding to the
version it verified under.

## Key rotation

`KEY_ROTATION` is dual-signed so a verifier can walk anchor to current key. The
possession proof over the new key uses the context
`ori.evidence.rotation.v2`, terminated by a single NUL byte, followed by the
proof input, matching the domain-separation convention in
[`evidence-exchange/v1.md`](../evidence-exchange/v1.md).

The payload carries `old_public_key`, `new_public_key`, and `rotation_sig`. A
verifier MUST reject a rotation whose `old_public_key` is not the active key, or
whose possession proof does not verify under the new key.

## Runtime action attestation

Attestation is **append-after-log**: the `action_log` row is written first with
attestation status `pending`, then signed. Signing failures mark the row
`failed` and MUST NEVER block or crash the action path. Safety does not wait for
evidence.

`event_id` is a deterministic UUIDv5 over the `(device_id, action_log id)` pair,
so a retry after a crash produces the same identity and cannot double-attest.
The exact construction is given in [`vectors/event-id.json`](vectors/event-id.json).

Payload:

```json
{
  "kind": "runtime_action",
  "attestation": "at_emission|reconciled_late",
  "action_log_id": 0
}
```

Lateness is determined from the `attestation` marker and the chain timestamps,
never from the event type. A row reconciled after a restart carries
`reconciled_late` and MUST NOT be presented as emission-time evidence.

## Vectors

[`vectors/`](vectors/) is normative for the bytes. Every vector carries the
canonical bytes as hex so a disagreement is visible at the byte that differs
rather than as a mismatched hash.

Vectors MUST be verified by at least two independent implementations in
different languages before this contract's status changes. A vector generated
and checked by one implementation proves only that it agrees with itself.

**Verifiers live in the implementing repositories, not here.** This repository
is documentation-only and its CI enforces that, so the reconstruction code
cannot sit beside the vectors it checks. That is the same arrangement Layer 1
already uses: the contract is here, and `ori-edge-firmware` carries its own
generator and vectors.

A conforming verifier reconstructs every value from the inputs each vector
publishes — the genesis preimage, the namespace URI, the per-event name format,
the canonical rules, the seeds — rather than importing whatever produced them.
It must also check the `authenticator` posture on each rejection case: a case
marked `valid` whose signature does not actually verify never reaches the rule
it claims to test, and would pass while proving nothing.

Two languages have done that — the Python producer and the Rust verifier
named in the status line — so the vectors are cross-verified. The contract
stays pre-ratification because no released artifact claims it yet.

Rejection cases are executable, not descriptive. Each carries the artifact
itself, the chain position it was presented at, and the row's own stored
columns, so a verifier evaluates the rules rather than reading about them.

**A conforming verifier must find each case violating exactly the rule it names
and nothing else.** That is a stronger requirement than it looks. Two cases in
the first draft violated a second rule as well — moving a row's stored `seq` to
disagree with its envelope also moved it off its chain position — so a verifier
would have rejected them for the wrong reason and never exercised rules 5 and 6
at all. A rejection suite where every case is impure reports full coverage
while testing one rule repeatedly.

| Vector | Settles |
| --- | --- |
| `genesis.json` | the genesis constant and its derivation |
| `canonical-form.json` | recursive sorting, escapes, the number zone, and every refused form |
| `chain-row.json` | a complete signed row, and each rejection rule |
| `event-id.json` | the namespace derivation and the per-event construction |
| `key-rotation.json` | the dual-signed rotation and its proof context |

## Migration

**Producers switch outright.** A producer emits v2 only and carries no
dual-version production path.

**Verifiers retain v1.** A verifier keeps v1 verification for chains written
before the switch, selects the path by `schema_version`, and attributes every
finding to the version it verified under.

### On whether any v1 chain exists

The switch is cheap if no persistent v1 chain exists, and expensive if one does.
That is a rollout fact, and this contract records it as an attestation rather
than deriving it from evidence that cannot establish it.

What configuration defaults show is only that signing is opt-in and disabled in
shipped examples, and that it requires a private artifact configured through
deployment secrets. That makes a v1 chain *unlikely*. It does not make one
impossible: a deployment that enabled signing, a bench device, or a pilot would
each produce one, and none of them are visible from this repository.

> **Maintainer attestation required before a producer switches.** A maintainer
> with visibility of deployments confirms that no chain whose rows must remain
> verifiable was written under v1. Absent that confirmation, assume one exists.

Retaining v1 verification is the conservative safeguard either way, and is
required regardless of what the attestation says. It costs a verification path;
being wrong about it costs evidence that can no longer be verified.

### v1 event identifiers are v1 identifiers

`event_id` values derived under the v1 namespace stay as they are. They are the
idempotency keys of rows that were already signed, and they are not recomputed,
reinterpreted, or migrated under the v2 namespace. A v2 producer derives new
identifiers under the v2 namespace; a verifier reading a v1 row treats its
`event_id` as opaque and does not attempt to re-derive it.
