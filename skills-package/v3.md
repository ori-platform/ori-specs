# Skill Package Format v3

> Status: Design target, pre-ratification. No shipped consumer claims
> conformance. Amendable in place under the
> [pre-ratification exception](../VERSIONING.md#pre-ratification-exception).
>
> Supersedes [v2.md](v2.md), which remains the accurate description of what
> `ori-runtime` 2.4.x accepts. Adopts
> [schema-descriptor/v1.md](../schema-descriptor/v1.md) for its declaration
> grammar. Related: [signing/v1.md](../signing/v1.md) for signature encoding
> and profiles, [skill-hook-isolation/v1.md](../skill-hook-isolation/v1.md) for
> the design target that will re-enable community hook execution.

## Why v3 exists

v2 defines `config` as an arbitrary object with five reserved names and no
per-skill schema. Everything else is accepted, which is three defects wearing
one shape.

**An invented setting is indistinguishable from a working one.** A key nobody
reads looks, to whoever wrote it, exactly like a key that took effect. The
runtime has shipped this defect elsewhere: a sensor key silently dropped
because two adapters spelled it differently, and a documented `active_high` that
no code reads.

**A renamed setting fails silently.** An operator tunes a threshold the skill
stopped reading a version ago, and nothing says so.

**A configuration surface that cannot be closed cannot be delegated to.**
`runtime-config/v2` needs to close `skills[].config` recursively, and it cannot
delegate to a schema that does not exist. An earlier draft of that contract
claimed the delegation anyway and its corpus invented a table to make the claim
pass, which is why this version exists as a real target rather than a softer
claim.

v3 gives a skill a **declared, typed, signed** configuration surface.

It also removes Tier D from package authority entirely. v2 accepted
`action_tier: D` from packages shipping with the runtime, which kept the
authority away from community packages but left the safety envelope a property
of which skills are installed, expressed as untyped numbers in manifest YAML.
Restricting the author is not the same as owning the decision, and a
configuration grammar is the wrong place to make a Tier D parameter
well-defined: it would give the current shape a typed, signed definition to stay
compatible with, at the moment the design is moving it elsewhere.

Both changes refuse packages that v2 accepts, which is why this is a new version
rather than an edit.

## Why v2 exists

v1 affirmatively permitted community Python hooks executed through a restricted
in-process sandbox. That sandbox was removed in `ori-runtime` 2.4.0 rather than
hardened, because it could be escaped and, on Python 3.12, half of it was not
consulted at all. The runtime also took ownership of several decisions v1 read
from the package.

A package that v1 declares valid may therefore be refused by a v2 runtime. That
is a breaking change to the package contract, which is why this is a new version
rather than an edit to v1: v1 remains the accurate description of what runtimes
before 2.4.0 accept.

## Provenance model

v2 replaces v1's path-based classification. Provenance is established
positively.

| Class | Definition | Runtime treatment |
|---|---|---|
| First-party | Ships inside the runtime package | Signature field checked for shape only; `hooks.py` imported directly |
| Community | Everything else | Signature verified against the Hub trust anchor; `hooks.py` refused |

Provenance no longer decides tier authority. In v2 it did — first-party
packages could declare Tier D and community ones could not. In v3 no package
declares Tier D, so provenance governs hook execution and signature handling
only.

First-party roots are the packaged `skills/` directory in a source checkout and
`<sysconfig data>/share/ori-runtime/skills` in an installed wheel. Both resolve
through one definition, so the two layouts cannot disagree.

> v1 classified a skill as bundled when its path was *not* under
> `~/.ori/skills`. That treated the operator-managed skills directory beside
> `ori.yaml`, temporary directories and removable media as first-party.

## skill.yaml Top-Level Fields

| Field | Type | Required | Runtime use |
|---|---|---|---|
| `name` | `string` | Yes | Skill identity. Must be a string; max 64 chars; `^[A-Za-z0-9][A-Za-z0-9._-]*$`; unique within a load; a community skill may not use a packaged skill's name |
| `version` | `string` | Yes | Version/logging. Must be a string; max 32 chars |
| `author` | `string` | Yes | Metadata and trust mapping. Must be a string; max 128 chars |
| `triggers` | `array` | Yes (non-empty) | Rule/action behaviour |
| `sensors_required` | `array` | No | EventBus subscription mapping. Distinct `type` values only; duplicates collapse |
| `actions` | `object` | Effectively Yes | Defaults + capability declarations |
| `prompts` | `object` | No | Reasoning prompt templates |
| `config` | `object` | No | Hook/runtime custom config. Validated against `config_schema`; an undeclared key is refused |
| `config_schema` | `object` | No | Declares what `config` may contain. Absent means only an empty `config` is accepted |
| `signature` | `string` | Required for community packages | `ed25519:<signature>` for community packages, verified at load. `bundled` for packages shipping with the runtime — that value is a declaration prefix only and is **not** decoded or verified; a packaged skill's authenticity comes from the signed release artifact it was installed from |

Identity fields (`name`, `author`, `version`) must be strings and must not
contain control characters (Unicode category `Cc`, plus DEL), format characters
(`Cf`, which includes the bidirectional overrides such as U+202E), line or
paragraph separators (`Zl`, `Zp`), or surrogates (`Cs`). These fields appear in
action records and operator messages; a format character changes what an
operator reads without changing what was recorded.

### `config_schema`

`config_schema` declares what a skill accepts. It uses
[`schema-descriptor/v1`](../schema-descriptor/v1.md) — types, bounds,
enumerations, defaults, recursive closure, values checked rather than coerced,
and the two-phase split between a wrong declaration and a wrong document.

```yaml
config_schema:
  energy_cost_naira:
    type: number
    minimum: 0
    default: 225
  alert_contact:
    type: string
  quiet_hours:
    type: object
    properties:
      start_hour: {type: integer, minimum: 0, maximum: 23}
      end_hour: {type: integer, minimum: 0, maximum: 23}
```

v3 adds nothing to the descriptor grammar. What it adds is where the schema
lives, what its absence means, and what it may not describe.

### Absence is not permission

**A package with no `config_schema` accepts only an empty `config`.** A
populated `config` beside an absent schema is refused.

The alternative — treating absence as "anything goes" — would make v3
indistinguishable from v2 for every package that simply omits the field, so the
surface this version exists to close would stay open by default. Declaring
nothing is a statement, and the statement is that the skill takes no
configuration.

### Reserved names

`config_schema` MUST NOT declare `value`, `sensor_id`, `sensor_type`, `unit` or
`quality`. These name the sensor reading in rule conditions and are always taken
from the event.

> In v1 these were injected with `setdefault`, so a package-supplied value won.
> A package could decide what a Tier D condition compared against, in either
> direction.

Carried forward from v2 unchanged, and now enforced one step earlier: v2 refused
a reserved name in `config`, v3 refuses it in the schema that would have
declared it.

### The signature covers it, by placement

`config_schema` lives in `skill.yaml`, and the signature already covers the
canonicalised `skill.yaml`. So the schema is signed with the manifest and needs
no separate mechanism.

That placement is the requirement, not an implementation detail. An unsigned
schema beside a signed manifest is a schema an intermediary can widen, and the
schema decides what the skill will accept from a configuration document — it is
part of what the author asserted, not metadata about it.

### Tier A–C only

**Tier D parameters are outside package-config authority, and v3 does not
describe them.** No schema, no vector, no migration path.

Today three Tier D triggers in first-party skills read thresholds from
`skill.config`. Those values come from `skill.yaml` alone — `ori.yaml`'s
`skills[].config` never reaches the loader — and only first-party skills may
declare `action_tier: D`, so they are already release-owned. The defect is not
their owner: it is that they are untyped, unbounded manifest numbers, and that
Tier D coverage depends on which skills are installed.

That is a legacy runtime implementation to migrate under
`safety-profile/v1` (ori-specs#71, not yet written) and the runtime safety
registry (ori-runtime#324).
It is **not** a model for this contract to schematise. Giving it a typed, signed
package schema would ratify the wrong owner and make the migration harder, by
handing the current shape a definition to stay compatible with.

A schema validator cannot determine whether skill code uses a setting to
influence a Tier D decision — that is a data-flow property of the
implementation, and claiming a validator could prove it would be the invented
mechanism this version was written to avoid. The boundary belongs at the
runtime's authority check, not in this grammar.

## Trigger Fields

| Field | Type | Default | Notes |
|---|---|---|---|
| `name` | `string` | required | Regex-validated; unique per skill |
| `condition` | `string` | `""` | Evaluated by rule engine |
| `action_tier` | `string` | required | Must be `A`, `B` or `C`. **`D` is refused from every package, first-party included** |
| `cooldown_seconds` | `integer` | `0` | Trigger cooldown |
| `escalate_to` | `string` | `local_slm` | `rule/local_slm/gateway`. `cloud` is invalid |
| `bypass_llm` | `bool` | `false` | Refused. It exists only to mark a Tier D trigger, and v3 has none |
| `reasoning_policy` | `string` | `""` | `post_action` valid only for physical Tier B |
| `requires_approval` | `bool` | `false` | Tier B approval instead of post-action reasoning |
| `approval_timeout_seconds` | `integer` | `300` | Per-trigger Tier C timeout |
| `safe_default_action` | `string` | `log_to_dashboard` | Required non-empty for Tier C, **and must be non-actuating** |

### Tier D is not a package tier

Tier D fires immediately, before any LLM, and cannot be overridden — it is the
one tier that removes the operator rather than adding one.

**v3 refuses `action_tier: D` from every package**, first-party included, and
refuses a Tier D action in an `actions.available` declaration or a trigger's
default action list. A Tier D condition comes from the runtime safety registry,
selected by declared hardware, and a package cannot create, weaken, shadow or
replace one.

v2 accepted Tier D from packages that ship with the runtime. That was
containment rather than a model: it kept the authority away from community
packages, but left the safety envelope a property of which skills are installed,
expressed as untyped numbers in manifest YAML. Restricting the author is not the
same as owning the decision.

A capability grant binding package identity, trigger, action and permitted
maximum tier remains a design target for tiers A through C. It is **not** the
answer for Tier D, because the question there is not which package may act but
whether a package participates at all.

Three Tier D triggers exist in first-party packages today. They remain valid
**v2** packages and continue to load on a v2 runtime; they have no v3 form, and
acquire one only by migrating into a safety profile under `safety-profile/v1`
(ori-specs#71) and the runtime safety registry (ori-runtime#324).

## Action Authority

`actions.available[].tier` is a *declaration*, checked against a runtime-owned
registry. It is no longer the authority it was in v1.

| Rule | Detail |
|---|---|
| Minimum tier | Every action the runtime can execute has a minimum tier. A package declaring one below its minimum is refused at load and raised at dispatch |
| Escalation cap | A package's action list may raise an action's tier to at most **Tier C**. Tier D is not reachable from a package at all in v3, by escalation or by declaration |
| Safe defaults | Only non-actuating actions may be a `safe_default_action`. A safe default runs with no approval — it is what happens when the operator says NO or says nothing |
| Tier required | An action the runtime can execute must declare a `tier` |
| Duplicates | An action name may not appear twice in one default-action list; each entry is dispatched separately |

The registry is runtime-owned and not part of this contract; packages should
treat the declared tier as a floor they must meet, not a value they choose
freely.

## Manifest admission limits

Applied before signature verification, because a manifest must be parsed to be
canonicalised and verified. They therefore bind unsigned content.

| Limit | Value |
|---|---|
| File type | Regular file only. Symlinks, FIFOs and device nodes are refused |
| Size | 1 MiB |
| Encoding | UTF-8; invalid encoding is refused |
| YAML aliases (`*name`) and merge keys (`<<:`) | Refused. An unused anchor is permitted |
| Nesting depth | 32 |
| Total YAML nodes | 20000 |
| Entries in one collection | 1000 |
| Mapping keys | Strings; duplicates refused |

## Workload budgets

Registration produces one EventBus handler per trigger × distinct declared
sensor type, and each handler schedules a reasoning task on the event loop that
Tier D safety processing shares. These bound the work an accepted package
creates.

| Budget | Value |
|---|---|
| Triggers per skill | 64 |
| Declared sensors per skill | 32 |
| Trigger × sensor subscriptions per skill | 256 |
| `actions.available` entries | 64 |
| Default actions per trigger | 16 |
| Total default-action references per skill | 256 |
| Prompts per skill | 64 |
| Config entries per skill | 256 |
| Skills per load | 64 (counts candidates, not successes) |
| Cumulative subscriptions across a load | 1024 |

A package declaring no sensor type subscribes to the wildcard once per trigger,
which is the expensive case; it costs one subscription per trigger rather than
none.

## Load-Time Validation Invariants

`SkillValidationError` for: non-mapping manifest; oversized or non-UTF-8
manifest; manifest exceeding the YAML structural limits; missing `name`,
`version` or `author`; empty or non-list `triggers`; non-string, overlong or
control/format-character identity fields; invalid `name` charset; a trigger
declaring `action_tier: D`; `bypass_llm: true`; a Tier D action in an
`actions.available` declaration or a trigger's default list; a reserved
name declared in `config_schema`; a `config_schema` the descriptor core refuses;
a populated `config` with no `config_schema`; a `config` key the schema does not
declare, at any depth; any workload budget exceeded; a duplicate action in one default
list; missing/invalid `action_tier`; duplicate trigger names; `bypass_llm: true`
on a non-Tier-D trigger; `escalate_to: cloud`; `reasoning_policy: post_action`
on a non-Tier-B trigger; a physical Tier B trigger with neither
`requires_approval: true` nor `reasoning_policy: post_action`; a physical Tier B
`post_action` trigger without a Tier A default action; a Tier C trigger with an
empty or actuating `safe_default_action`; a governed action declared without a
`tier` or below its minimum; missing, extra or empty `actions.defaults` entries;
a default action not declared in `actions.available`; more than 16
`{history.*}` placeholders in a prompt.

`SkillSecurityError` for: a `skill.yaml` that is a symlink or not a regular
file; a community package using the `bundled` sentinel; an unconfigured
community trust anchor; a failed signature verification; a community package
whose `name` is a packaged skill's name; a non-first-party package carrying
`hooks.py`.

**A Tier D declaration is a validation error, not a security error, and the same
one from every package.** v2 raised `SkillSecurityError` for a *community*
package declaring `action_tier: D`, because provenance decided who held that
authority. In v3 no package holds it, so the refusal no longer depends on who
wrote the package and does not belong in the provenance-sensitive list. One
condition, one refusal.

Provenance still governs signature handling and `hooks.py`, which is why those
entries remain above.

## hooks.py

| Class | Behaviour |
|---|---|
| First-party | Imported directly into the runtime interpreter and runs with the runtime's authority |
| Community | **Not executed.** A community package carrying `hooks.py` is refused entirely |

A community package is refused rather than loaded with its hooks absent: its
triggers were written against derived values the runtime will not produce, and
quietly activating a different skill from the one the author wrote is not a safe
degradation.

Community packages are therefore YAML-only under v2 and v3. The interface below still
describes first-party hooks, and is the interface the isolated-worker contract
must preserve.

```python
def pre_trigger_eval(context: HookContext) -> None:
    ...

def post_reasoning(result: ReasoningResult, ctx: HookContext) -> ReasoningResult:
    return result
```

### Authority fields

Hooks must not set or influence `action_tier`, `bypass_llm`, or the reserved
sensor-reading names. The runtime re-applies the trigger-declared tier after
every extension point, including when a hook raises, and strips reserved names
from hook-derived values.

> In v1 the clamp ran before `post_reasoning`, which receives the mutable
> result object, so a hook could lower a Tier C action out of the approval
> workflow.

## Actions, Prompts and Tier B Post-Action Policy

The `actions` block shape, prompt lookup order, substitutions, `{history.*}`
handling and its 16-placeholder cap, prompt assembly order, and the Tier B
post-action policy and its `reasoning_status` values are unchanged from
[v1.md](v1.md) except where the *Action Authority* and *Workload budgets*
sections above constrain them.

## Signature Verification

- Community manifests are verified against the Hub manifest trust anchor before
  hooks are considered, using the profile in [signing/v1.md](../signing/v1.md).
- Verification applies to every package that does not ship with the runtime,
  **regardless of `security.skills.require_signed`**. In v1 that setting
  exempted anything outside `~/.ori/skills` from verification entirely.
- The signature covers the canonicalised `skill.yaml` only. It does **not** bind
  `hooks.py` or any other executable file. Binding executable bytes is a design
  target in [skill-hook-isolation/v1.md](../skill-hook-isolation/v1.md).
- Installers separately verify the detached Hub artifact signature over exact
  package bytes before extraction.

## Migration from v2

A v2 package is refused by a v3 runtime if any of the following is true.

| v2 package property | v3 outcome | Remedy |
|---|---|---|
| Populated `config`, no `config_schema` | Refused | Declare `config_schema`. This is the change v3 exists to make, and it is why v3 is a new version rather than an edit to v2 |
| Declares `action_tier: D`, or a Tier D action | Refused | **No v3 migration path.** See below |
| `config` key the schema does not declare | Refused, naming the full path | Declare it, or remove it. A key nobody reads is the defect, whichever way it is resolved |
| `config_schema` declaring a reserved reading name | Refused | Remove it. v2 refused these in `config`; v3 refuses them one step earlier, in the schema that would have declared them |
| `config_schema` the descriptor core refuses | Refused at load | Fix the declaration. A malformed schema is the author's error and must not wait for a document to surface it |
| Empty or absent `config`, no `config_schema` | **Accepted unchanged** | None. A skill that takes no configuration needs no schema |

The empty-`config` row matters for the migration's cost: a package that never
used `config` is a valid v3 package as it stands.

**A schema is not generated from an existing `config`.** Inferring one would
declare whatever the author happened to write, including the keys nobody reads —
which is the defect this version closes, preserved with a signature over it. The
author declares what the skill accepts.

### A package carrying Tier D has no v3 migration

The three first-party packages with Tier D triggers cannot be migrated to v3 by
declaring a `config_schema`. Doing so would give their threshold parameters
exactly the typed, signed package schema this version refuses to grant, and the
signature would then assert that a Tier D input is part of the package format.

Nor could a validator sort it out. A schema declares that
`dangerous_overcurrent_threshold` is a bounded number; it cannot see that a Tier
D expression reads it. Which tier consumes a key is a property of the trigger
that references it, not of the key's declaration.

**The path is the safety profile, not this contract.** Those packages migrate
their Tier D conditions into `safety-profile/v1` (ori-specs#71) and the runtime
safety registry (ori-runtime#324), keeping their Tier A through C intelligence,
and become v3 packages once they no longer declare Tier D. Until then they
remain valid v2 packages on a v2 runtime.

After the trigger rule above, this is mechanical rather than advisory: a package
declaring `action_tier: D` is refused by a v3 runtime, so there is no state in
which a Tier D parameter reaches a v3 `config_schema`.

## Migration from v1

A v1 package is refused by a v2 runtime if any of the following is true. Every
row still applies under v3, which adds the `config_schema` requirements above.

| v1 package property | v2 outcome | Remedy |
|---|---|---|
| Community package carrying `hooks.py` | Refused entirely | Remove `hooks.py`; community packages are YAML-only until the isolation contract lands |
| Community package declaring `action_tier: D` | Refused | Use Tier C, which proposes the action for operator approval |
| Unsigned package outside the runtime package | Refused | Sign it; `require_signed: false` no longer exempts it |
| Community package using `signature: bundled` | Refused | Use `ed25519:<signature>` |
| Community package whose `name` matches a packaged skill | Refused | Rename |
| `skill.yaml` using a YAML alias or merge key | Refused | Write the value out in full |
| `skill.yaml` over 1 MiB, deeper than 32 levels, over 20000 nodes, or with a collection over 1000 entries | Refused | Reduce |
| `skill.yaml` that is a symlink, FIFO or device node | Refused | Use a regular file |
| Non-string, overlong, or control/format-character `name`/`author`/`version` | Refused | Quote and simplify |
| `config` defining `value`, `sensor_id`, `sensor_type`, `unit` or `quality` | Refused | Rename the key |
| Tier C `safe_default_action` naming an actuating action | Refused | Use a non-actuating action |
| Governed action declared without a `tier`, or below its minimum | Refused | Declare the tier at or above the minimum |
| Same action twice in one default-action list | Refused | Remove the duplicate |
| Over any workload budget | Refused | Split the package or reduce |

Packages that comply with v2 also comply with v1, except that a v1 runtime
ignores the constraints v2 adds. There is no v2 feature a v1 runtime must
understand, so a v2-compliant package loads on a v1 runtime.

## Vectors

A corpus accompanies this contract, and **all three implementations consume it
unchanged**: the runtime that loads packages, the SDK that authors them, and the
Hub that admits them.

That is the point of it. The gap this estate has today is a package the SDK
writes, the Hub admits, and the device refuses — three implementations of one
format, disagreeing. A corpus each repo interprets for itself would reproduce
that; a corpus each repo loads verbatim cannot.

The corpus covers the descriptor core's required cases (see
[schema-descriptor/v1.md](../schema-descriptor/v1.md)), plus what v3 adds:

**Package admission, tier authority**:

- a first-party package declaring `action_tier: D`, refused
- a package declaring a Tier D action in `actions.available`, refused
- a package whose trigger default actions include a Tier D action, refused
- `bypass_llm: true` on any trigger, refused

**Schema load**, refused before any `config` is considered:

- a reserved reading name declared in `config_schema`
- a `config_schema` that is not a mapping
- every descriptor-core schema-load refusal, reached through a skill manifest

**Package admission**:

- a populated `config` with no `config_schema`, refused
- an empty or absent `config` with no `config_schema`, **accepted**
- a `config` key the schema does not declare, refused naming the full path
- an undeclared key nested inside a declared object, refused by full path
- a declared key whose value violates its type, bounds or enumeration, refused
- a declared key absent with a default, accepted with the default applied
- a `config` that satisfies its schema exactly, accepted

**Signature**:

- a `config_schema` altered after signing **to another grammar-valid schema** —
  a widened bound, an added key — refused at signature verification. The
  mutation must be grammar-valid for the case to prove anything about ordering:
  an invalid one may be refused by schema validation first, which is also
  correct behaviour and tests something else

Producer and verifier MUST NOT share code. A corpus checked only by the tool
that wrote it certifies that tool's defects.

## Downstream adoption

**v3 has no implementations.** `ori-runtime` >= 2.4.0 implements v2; nothing
implements v3 yet.

v2's own adoption is incomplete, and that state should be read before planning
v3 work. The runtime enforces v2, while the two producers do not: Hub admission
accepts packages the runtime refuses (`ori-skills-hub` #49), and SDK authoring
does the same (`ori-sdk-python` #48). An author can publish a package the
catalogue admits and the device rejects.

**Producers must reach v2 parity first.** Publishing v3 packages while every
deployed runtime enforces v2 would widen the same gap it is meant to close: the
Hub would admit packages no device accepts, and the author would learn at
install time instead of at publish time.

v3 support is added when a v3 runtime and the shared corpus exist — not before,
and not instead. A producer may structure its admission checks for versioned
validation so the later addition is small, but it cannot skip v2.

An earlier draft of this section advised implementing v3 directly and skipping
v2. That was wrong in the direction that matters: it would have made a live
correctness defect worse while appearing to save work.

References to `skills-package/v1` in `ori-skills`, `ori-sdk-python` and
`ori-cli` must be repointed deliberately — a v1 reference is **not** evidence of
compliance with anything later, and each repo has to confirm which behaviour it
actually implements. Tracked in [gaps/open.md](../gaps/open.md).
