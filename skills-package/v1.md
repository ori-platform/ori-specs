# Skill Package Format v1

> **Superseded by [v2.md](v2.md).** This document remains the accurate
> description of what `ori-runtime` **< 2.4.0** accepts. It is retained
> unchanged for that purpose and is not updated for later runtime behaviour.
>
> `ori-runtime` >= 2.4.0 implements v2 and does not accept all v1 packages —
> most notably, it does not execute community Python hooks. The *Sandbox
> Constraints* section below describes a mechanism that no longer exists.
> See [v2.md#migration-from-v1](v2.md#migration-from-v1).
>
> Status: Implemented in `ori-runtime` < 2.4.0
> Source of truth: `ori/skills/loader.py`, `ori/skills/sandbox.py`, `ori/skills/hooks_api.py`, `ori/skills/os_sandbox.py`, `ori/skills/signing.py`

## skill.yaml Top-Level Fields

| Field | Type | Required | Runtime use |
|---|---|---|---|
| `name` | `string` | Yes | Skill identity |
| `version` | `string` | Yes | Version/logging |
| `author` | `string` | Yes | Metadata and trust mapping |
| `triggers` | `array` | Yes (non-empty) | Rule/action behavior |
| `sensors_required` | `array` | No | EventBus subscription mapping |
| `actions` | `object` | Effectively Yes | Defaults + capability declarations |
| `prompts` | `object` | No | Reasoning prompt templates |
| `config` | `object` | No | Hook/runtime custom config |
| `signature` | `string` | Optional in schema, enforced for community install path | Embedded Hub manifest signature. Use `signature: bundled` for runtime-bundled skills; community skills must use `ed25519:<signature>` and verify against the Hub manifest trust anchor at load time. This is distinct from the detached package signature verified before extraction. |

## Trigger Fields

| Field | Type | Default | Notes |
|---|---|---|---|
| `name` | `string` | required | Regex-validated; unique per skill |
| `condition` | `string` | `""` | Evaluated by rule engine |
| `action_tier` | `string` | required | Must be `A/B/C/D` |
| `cooldown_seconds` | `integer` | `0` | Trigger cooldown |
| `escalate_to` | `string` | `local_slm` | Tier floor hint (`rule/local_slm/gateway`). `cloud` is invalid; cloud providers are gateway backends. |
| `bypass_llm` | `bool` | `false` | Must be true only for Tier D; loader enforces |
| `reasoning_policy` | `string` | `""` | Optional. `post_action` is valid only for physical Tier B triggers and executes the Tier B action before async reasoning enrichment. |
| `requires_approval` | `bool` | `false` | When true, a physical Tier B trigger is treated as requiring operator approval rather than immediate post-action reasoning. |
| `approval_timeout_seconds` | `integer` | `300` | Per-trigger Tier C timeout |
| `safe_default_action` | `string` | `log_to_dashboard` | Required non-empty for Tier C |

## Load-Time Validation Invariants

Skill loader raises `SkillValidationError` for:

1. missing/invalid `action_tier`
2. duplicate trigger names
3. `bypass_llm=true` on non-Tier-D trigger
4. `escalate_to: cloud`
5. `reasoning_policy: post_action` on a non-Tier-B trigger
6. physical Tier B trigger with neither `requires_approval: true` nor `reasoning_policy: post_action`
7. physical Tier B `post_action` trigger without a Tier A default action for operator follow-up
8. Tier C trigger with empty `safe_default_action`
9. missing `actions.defaults` entries for declared triggers
10. extra `actions.defaults` keys with no trigger
11. empty defaults list for a trigger
12. default action not declared in `actions.available`

## Tier B Post-Action Policy

Physical Tier B triggers must make execution semantics explicit. They either
require approval or declare `reasoning_policy: post_action`. With `post_action`,
the deterministic Tier B default action executes before any local or gateway LLM
reasoning. Reasoning then runs asynchronously to enrich operator/audit text.

Failure semantics:

- action succeeds and reasoning succeeds: `reasoning_status=complete`
- action succeeds and reasoning fails, times out, or no reasoner is available:
  `reasoning_status=incomplete`; action result remains successful
- action fails: post-action reasoning is skipped and `reasoning_status=skipped`

`bypass_llm: true` remains reserved for Tier D only.

## Actions Block

```yaml
actions:
  available:
    - name: alert_whatsapp
      tier: A
    - name: trip_main_breaker
      tier: C
  defaults:
    trigger_name: [alert_whatsapp]
```

`actions.available[].tier` is used as a dispatcher guardrail (escalation-only check), not purely decorative metadata.

## Prompts Block

Lookup order:

1. `prompts[trigger_name]`
2. fallback `prompts[sensor_type]`

Implemented substitutions:

- `{value}`
- `{unit}`
- `{sensor_id}`
- `{sensor_type}`
- `{device_id}`
- `{time}`
- `{quality}`

All untrusted values are sanitized before prompt interpolation.

`{history.*}` placeholders are evaluated expression-style using AST-safe parsing (no `eval`).

Supported methods:

- `history.last_n('sensor_id', n)`
- `history.avg_hours('sensor_id', hours)`
- `history.avg_last_n('sensor_id', n)`
- `history.last_value('sensor_id')`
- `history.last_timestamp('sensor_id')`
- `history.fetch_history('sensor_id', limit)`

History placeholder constraints:

1. Maximum 16 `{history.*}` placeholders per prompt template.
2. Limit is enforced at skill load time (`SkillValidationError` on violation).
3. Runtime also applies a defensive cap of 16 as a secondary guard.

Unresolved history placeholders:

- Unsupported or unresolvable expressions are replaced with sentinel `null` in the final prompt.
- Runtime emits `WARNING` logs for unresolved placeholders (operator visibility).

### Prompt Assembly Order Contract (v1 runtime behavior)

For LLM paths, runtime assembles one flat prompt string in this order:

1. Event header lines:
   - `Sensor: <sensor_id> (<sensor_type>)`
   - `Current value: <value> <unit>`
   - `Quality: <quality>`
   - `Device: <device_id>`
2. Skill template body with:
   - core placeholder substitution
   - `{history.*}` interpolation resolved inline
3. Rejection note section (optional; appended only when prior operator rejection context exists)

Runtime ContextEnricher snapshot insertion is implemented as an opt-in runtime
feature under `reasoning.context_enricher`; see `runtime-config/v1.md` for the
config keys and Tier-D-safe boundary. Skill packages must not depend on it being
enabled.

## Sandbox Constraints

### Community skills (`~/.ori/skills`)

- loaded via restricted sandbox loader
- import allowlist applied
- selected builtins blocked (`open`, `exec`, `eval`, `__import__`, `compile`, `breakpoint`)
- OS-level sandbox attempted first on supported Linux kernels (seccomp + Landlock)
- graceful fallback to Python-level sandbox unless strict OS sandbox mode is required by config

### Bundled skills (`skills/` in runtime repo)

- loaded directly (trusted path)

## Signature Verification Notes

- Community skill manifests are verified against the Hub manifest trust anchor
  before hooks are loaded.
- Installers separately verify the detached Hub artifact signature over exact
  package bytes before extraction.
- Bundled runtime skills use `signature: bundled` sentinel and are treated as trusted local code.
- Community skills are not allowed to use `signature: bundled`; loader raises `SkillSecurityError` with remediation guidance.
- The manifest and artifact profiles, Ed25519 encoding, bundled sentinel
  semantics, publishing sequence, and shared vectors are defined in
  [signing/v1.md](../signing/v1.md).
