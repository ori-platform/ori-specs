# Gateway Evidence Carriage v1

> Status: maturity `draft`; compatibility `amendable`; adoption: none
> recorded; proof: end-to-end `none`, HIL `none`, production `none`. Record:
> [status/gateway-evidence-carriage/v1.json](../status/gateway-evidence-carriage/v1.json).


This contract is the versioned runtime–gateway evidence surface: the MQTT
carriage of evidence artifacts from a runtime to its LAN gateway and back, the
acknowledgements that retire them, and the `evidence_delivery` member of the
gateway's site-health projection.
[evidence-exchange/v2.md](../evidence-exchange/v2.md) owns what each artifact
means and which bytes are authenticated, and
[evidence-transport/v2.md](../evidence-transport/v2.md) owns the hop from the
gateway to the evidence authority.

[gateway-api/v1.md](../gateway-api/v1.md) keeps the evidence carriage it
shipped, on the same topics and with the same artifact bytes, and nothing here
changes what that contract means. This contract is where the
surface changes: an outbound acknowledgement withheld for a device that is not
configured, the `queue_full` handoff and the artifact size bound, the wider
meaning of `binding_mismatch`, `superseded` as a retiring refusal, a fourth
inbound artifact type, `evidence_disposition`, and the per-device
`evidence_delivery` projection. An implementation claims conformance to this
contract or to `gateway-api/v1` for its evidence carriage, and a claim to one
is not a claim to the other.

Tier C approval is not carried here. It is runtime authority defined by
[tier-c-approval/v1.md](../tier-c-approval/v1.md).

## Outbound Evidence Carriage

> Status: Design target, pre-ratification. The carriage this section extends is
> implemented on main as [gateway-api/v1.md](../gateway-api/v1.md) carriage:
> runtime production in `ori-runtime` (`ori/gateway/evidence_outbound.py`) and
> gateway consumption in `ori-gateway` (`internal/evidence/runtime_ingress.go`),
> exercised on a loopback broker between the two, not in a deployment. Neither
> side claims this contract.

This is the LAN handoff from a runtime to its durable gateway courier. It does
not define the gateway-to-authority hop; that is `evidence-transport/v2`.

| Property | Value |
| --- | --- |
| Topic | `ori/{device_id}/evidence/outbound` |
| Direction | Runtime -> Gateway |
| QoS | 1 |
| Retained | No |

The payload is:

```json
{
  "device_id": "site-a-edge-01",
  "artifact_type": "delivery_envelope",
  "artifact_b64": "eyJhbmNob3JfZXBvY2hfaWQiOiIuLi4ifQ=="
}
```

`artifact_b64` is RFC 4648 standard Base64 with padding over the complete
canonical wire bytes fixed by `evidence-exchange/v2`. It is byte-literal rather
than a nested object because gateway custody digests the exact signed envelope,
and the authority requires the gateway to forward those same bytes. A receiver
MUST decode once and MUST NOT re-serialise the artifact.

The closed outbound vocabulary is `anchor_registration`, `delivery_envelope`,
and `checkpoint`. Type is named, never inferred by trial verification. The
commissioning authorisation is not carried: the device never holds it, per
`evidence-exchange/v2`, and a gateway MUST refuse a payload naming that type
rather than queue it. `device_id` MUST equal the topic segment
and the decoded artifact's `device_id` before the gateway spends durable queue
capacity.

The carriage payload deliberately has no runtime-gateway HMAC envelope. Every
artifact is already authenticated end to end, so a carriage HMAC would add no
artifact authenticity and could not constrain a gateway that holds that key.
The checkpoint's evidence authenticator remains the device signature; a gateway
secret never substitutes for it. Production transport security relies on
mutually authenticated broker access, per-device publish ACLs, and TLS for
non-loopback brokers. Omitting the HMAC is not permission to use anonymous or
shared MQTT clients.

### Outbound acknowledgement

MQTT PUBACK is not proof the gateway durably stored the bytes. After an atomic
queue commit or an explicit refusal for a configured device, the gateway
publishes:

| Property | Value |
| --- | --- |
| Topic | `ori/{device_id}/evidence/outbound/ack` |
| Direction | Gateway -> Runtime |
| QoS | 1 |
| Retained | No |

```json
{
  "device_id": "site-a-edge-01",
  "artifact_type": "checkpoint",
  "artifact_digest": "sha256:...",
  "outcome": "queued",
  "reason": "",
  "acknowledged_at_ms": 1787000001000,
  "auth": {
    "scheme": "hmac-sha256",
    "signed_at_ms": 1787000001000,
    "signature": "hmac-sha256:..."
  }
}
```

`artifact_digest` is SHA-256 over the decoded exact artifact bytes.
`outcome` is `queued` or `refused`. `reason` is empty for `queued`; the closed
transport refusal vocabulary is `malformed`, `binding_mismatch`, and
`queue_full`. `queue_full` is an acknowledgement only for a configured device
whose reserved queue share cannot presently accept the artifact; it is
retriable and MUST NOT be flattened into a drop.
For an authenticated admission, as
[evidence-transport/v2.md](../evidence-transport/v2.md) defines it — a carriage
received on a configured device's own outbound topic under the broker posture
the gateway asserts, whose topic, carriage and artifact `device_id` agree — a
`queue_full` decision MUST signal the existing courier worker for that device
after the refusal acknowledgement is published. No durable record of a
`queue_full` refusal exists. It MUST NOT create a queue row, retire the offered
artifact, bypass backoff, or imply custody. The runtime retries an artifact refused `queue_full`
with its existing bounded back-off.
An artifact larger than the evidence-transport maximum, 1,048,576 bytes, is
refused `malformed` before custody, since no authority will accept it. Queue
capacity is reserved per device, so one device cannot exhaust another's. Capacity and
the configured devices are courier configuration, reserved equally per
configured device; a gateway MUST reject an outbound-carriage topic whose device
is not configured before invoking admission: it does not admit the artifact,
issue custody, or publish an outbound acknowledgement, so an unconfigured
device cannot consume an implicit shared lane, and the runtime keeps the bytes
and retries. The gateway MUST NOT refuse an artifact at admission because of its
declared `v`; the evidence authority alone decides version support
([evidence-transport/v2.md](../evidence-transport/v2.md), courier opacity). A
gateway implementing `gateway-api/v1` answers `malformed` for any `v` other
than 1; that refusal is a statement about that gateway, not about the bytes,
and only a `malformed` from a gateway claiming this contract is terminal for
the artifact.

The acknowledgement uses the normal runtime-gateway envelope secret with
`message_type` `evidence_outbound_ack`, empty `request_id`, the target
`device_id`, and the usual canonical payload without `auth`. It is an
authenticated transport decision, not an evidence artifact and not an
authority receipt.

**Two timestamps, two meanings.** `acknowledged_at_ms` is the queue decision
time and repeats: re-admitting the same bytes recovers the same entry and the
same decision. `auth.signed_at_ms` is the gateway's signing time and MUST be
strictly increasing across the acknowledgements one gateway issues — one
millisecond past the previous when the clock has not moved, and durable
across a gateway restart so an unchanged or regressed clock cannot reissue an
earlier value — so two acknowledgements are never byte-identical. A runtime's replay defence keys on
the signature, and a re-acknowledgement that repeated the first would be
refused as a replay rather than applied.

For `delivery_envelope`, a `queued` acknowledgement does not advance runtime
custody state. The gateway also sends the separately authenticated
`custody_acknowledgement` through the inbound route below, and only that artifact
can mark custody. For the other outbound types, `queued` permits the runtime to
retire its courier handoff copy because the gateway's durable queue now owns
retry. For `anchor_registration` it does not retire the runtime's durable
epoch-confirmation obligation or its sealed re-offer bytes
([evidence-exchange/v2.md](../evidence-exchange/v2.md)).

An admission covered by a stop enters stopped custody only within the
applicable bounds. After the stopped bytes and their return obligation are
durable, the gateway publishes `queued`. For a `delivery_envelope`, it also
durably stages and subsequently delivers the custody acknowledgement; that
acknowledgement is what permits the runtime to release its local copy. Beyond
an applicable bound, the gateway accepts no custody and publishes neither
acknowledgement. The custody acknowledgement is staged durably before `queued`
is published, so `queued` never leads the runtime to expect proof of custody
that is not yet durable. The stop is that of
[evidence-transport/v2.md](../evidence-transport/v2.md), stopped scopes, and
the bounds are those of [gateway-config/v2.md](../gateway-config/v2.md), as
*Site Health `evidence_delivery` Projection* below states.

If an acknowledgement is lost, the runtime republishes the same carriage. The
gateway's queue is idempotent by `(artifact_type, artifact_digest)` and returns a
newly signed acknowledgement. A full queue never produces `queued` and never
produces custody.

Persistent MQTT sessions are required on the gateway subscriber. The runtime
retains each artifact until the corresponding authenticated acknowledgement (or
custody artifact for delivery envelopes) is applied; PUBACK alone retires
nothing.

[`gateway-api/vectors/outbound-evidence.json`](../gateway-api/vectors/outbound-evidence.json) fixes one
checkpoint carriage, its exact decoded bytes and digest, and the authenticated
queue acknowledgement.

## Inbound Evidence Delivery

> Status: Design target, pre-ratification. The three artifact types
> [gateway-api/v1.md](../gateway-api/v1.md) carries are implemented on main
> there: runtime-side routing and ingest in `ori-runtime`
> (`ori/gateway/evidence_inbound.py`) and gateway-side publishing in
> `ori-gateway` (`internal/evidence/return_publisher.go`), with custody
> acknowledgements travelling through the same durable return queue and retired
> by the runtime's acknowledgement. Evidence dispositions are a design target
> that neither side implements yet, and neither side claims this contract.

`evidence-exchange/v2` defines eight evidence artifacts, their authenticators and
their exact bytes. It does not define how they travel; that is this contract's
concern. Four of those artifacts move gateway to runtime, and this section
defines their carriage only.

The division is strict. `evidence-exchange/v2` owns what an artifact means and
which bytes are authenticated. This contract owns the topic, the envelope, the
authentication binding and the routing. Neither may restate the other: a
transport that re-specified artifact fields would become a second source of
truth for bytes that are already fixed.

### Topic and Delivery

| Property  | Value                              |
| --------- | ---------------------------------- |
| Topic     | `ori/{device_id}/evidence/inbound` |
| Direction | Gateway -> Runtime                 |
| QoS       | 1                                  |
| Retained  | No                                 |

QoS 1 rather than 0. A dropped authority artifact is not recoverable by asking
again: the runtime does not know one was sent, and the gateway is a courier
rather than an authority, so it cannot reissue one. Retained messages are
refused because an artifact is a statement about a moment, and a broker
replaying the last one to a reconnecting runtime would present a stale custody
claim as a current one.

Device-scoped, matching the rest of the `ori/{device_id}/...` namespace. The
envelope binds `device_id`, so a shared topic would carry artifacts every
subscriber but one must refuse, and a refusal that is routine stops being a
signal. Production broker ACLs must enforce the same boundary.

### Durability and Retirement

QoS 1 is not sufficient on its own, and a PUBACK is not a retirement signal.

**Sessions MUST be persistent.** The runtime subscribes with a stable client
identifier and a session that survives disconnection — `clean_session: false`
under MQTT 3.1.1, or a non-zero session expiry under MQTT 5. Under a clean
session the broker discards subscriptions on disconnect, so every artifact
published while a runtime is restarting is dropped with nothing recording that
it existed. Brokers bound the retained queue, so a persistent session narrows
the window rather than closing it; it is not the retirement signal.

**Retirement is by acknowledgement, never by PUBACK.** A PUBACK says the broker
accepted the packet. It says nothing about whether the runtime verified the
artifact, applied it, or was even running. A gateway that retired a delivery
receipt on PUBACK could lose it permanently, and a lost receipt is the failure
this whole exchange exists to prevent: the runtime's delivery state would stall
with no record of what was carried.

The runtime therefore publishes an ingest acknowledgement, and the gateway
retires an artifact from its durable queue only on receiving one.

**Return order is per device.** Authority artifacts are ordered independently
per runtime device. An unacknowledged or refused artifact for one device MUST
NOT delay publication to another device. Each device's return lane keeps its
own order and its own head, persisted and restored per `device_id`, and the
head of one device's lane never waits on another device's acknowledgement.

Gateway configuration declares each device's inbound evidence-carriage
contract as exactly `gateway-api/v1` or `gateway-evidence-carriage/v1`. Absence
defaults to `gateway-api/v1`. The gateway MUST NOT stage an
`evidence_disposition`, or another artifact unavailable in the declared
contract, into a legacy device's ordered return lane. The declaration is
[gateway-config/v2.md](../gateway-config/v2.md) `evidence.device_carriage`.

An authority artifact incompatible with the device's declared contract raises
`return_path_incompatible` for that device. It does not enter that device's
lane and cannot block another device. The gateway keeps it durably outside
every return lane, neither forwarding nor discarding it; the fault stays raised
while it keeps one, and a later change of that device's declaration to
`gateway-evidence-carriage/v1` stages the kept artifacts, after the entries
already in its lane, in the order the gateway received them.

Kept artifacts are idempotent by artifact digest, retain original arrival
order, count toward the return store's item and byte capacity, and are never
evicted. Removing a device from configuration does not delete its kept
artifacts; they remain associated with that retired device identity until it
is restored under a compatible declaration or an explicit future recovery
procedure removes them.

If an authority response artifact cannot be durably kept, the gateway has not
durably staged that response. It does not advance or retire the originating
lane entry and treats that response as unavailable for that device's lane,
causing the idempotent authority request to be retried. It MUST NOT block
another device's return lane.

| Property  | Value                                  |
| --------- | -------------------------------------- |
| Topic     | `ori/{device_id}/evidence/inbound/ack`  |
| Direction | Runtime -> Gateway                     |
| QoS       | 1                                      |
| Retained  | No                                     |

```json
{
  "device_id": "site-a-edge-01",
  "artifact_type": "custody_acknowledgement",
  "artifact_digest": "sha256:5f2c...",
  "outcome": "applied",
  "reason": "",
  "acknowledged_at_ms": 1787000001000,
  "auth": { "scheme": "hmac-sha256", "signed_at_ms": 1787000001000, "signature": "hmac-sha256:..." }
}
```

| Field                | Notes                                                                                        |
| -------------------- | -------------------------------------------------------------------------------------------- |
| `artifact_digest`    | SHA-256 over the artifact's canonical bytes, `sha256:` prefixed. Identity without a new field. |
| `outcome`            | `applied` or `refused`.                                                                       |
| `reason`             | `""` when applied; otherwise the `evidence-exchange/v2` rejection reason.                      |
| `acknowledged_at_ms` | When the receiver decided.                                                                     |

Identity is the digest rather than a correlation identifier. The artifacts
already carry their own identity in the bytes the authority signed, and
inventing a transport identifier would create a second name for the same thing
that the two sides could disagree about.

The acknowledgement is signed with the same envelope binding as the inbound
message, under `message_type` `evidence_inbound_ack`.

**An acknowledgement is not an assertion that the artifact was true.** It says
this receiver reached a decision, so the courier need not carry those bytes
again.

`outcome: refused` retires the artifact only when the refusal is a property of
the artifact's own bytes. A refusal that depends on receiver state MUST NOT
retire it, because that state can change without the bytes changing — a release
ships an authority key or adds a version, an operator resolves a retirement, a
later envelope is sealed. The classification follows from that rule rather than
from a list to be memorised:

| Rejection reason        | Retire? | Determined by                                             |
| ----------------------- | ------- | --------------------------------------------------------- |
| `malformed`             | yes     | The bytes. They are not a well-formed artifact and will not become one. |
| `bad_authenticator`     | yes     | The bytes and the named key. The authenticator does not verify, and resending cannot change that. |
| `binding_mismatch`      | yes     | The bytes. The artifact is about another device, another key, or an artifact this runtime never sealed. |
| `non_contiguous_range`  | yes     | The bytes. The claimed range is not a closed interval.     |
| `unrecognised_version`  | **no**  | Receiver capability. A later release may interpret that version. |
| `wrong_purpose`         | **no**  | Receiver state. The purpose a `key_id` is held under is registry state, not something readable from the artifact. |
| `unknown_key`           | **no**  | Receiver state. A later release may ship the authority key. |
| `retired_key`           | **no**  | Receiver state, resolved by operator action.               |
| `unknown_sequence`      | **no**  | Receiver state. The envelope may not be sealed yet.        |
| `superseded`            | yes     | The runtime's durable resolution of the disposition's subject, which never reverts. |

For a non-retiring refusal the gateway MUST keep the artifact and MUST NOT
retry it on a fixed short interval; the condition changes on a release or an
operator action, not on elapsed time. Queue bounds still apply, and a gateway
dropping an artifact under pressure MUST record that it did.

The gateway retries a retained artifact when it observes a relevant runtime
state-change signal, including a newly handed-off outbound artifact, or after an
operator restarts the courier following repair. This event-driven retry is not
permission to poll a receiver-state refusal on the ordinary delivery interval.

**Every delivery attempt MUST carry a newly signed envelope.** The artifact
bytes do not change between attempts; the envelope around them does, with a
fresh `signed_at_ms` and the signature that follows from it.

Retransmitting the byte-identical envelope does not work and MUST NOT be
attempted. Envelope replay protection is keyed on the message type, the signing
timestamp and the signature, so a byte-identical retransmission is
indistinguishable from a captured envelope replayed by an attacker. The
receiver refuses it, and because it is a transport refusal it produces no
acknowledgement — so a courier that retried by resending the same bytes would
be refused forever while waiting for an acknowledgement that can never come.
The queue would deadlock on its own retry.

This is why redelivery is the courier's to construct rather than the broker's
to repeat, and it is the reason the acknowledgement is bound to the artifact
digest rather than to anything in the envelope: the artifact keeps its identity
across attempts while every envelope carrying it is distinct.

Receivers MUST NOT relax replay protection to accommodate redelivery. The
protection is what stops a captured custody acknowledgement being replayed to
misreport a stalled queue, and a receiver cannot tell an honest retransmission
from a hostile one.

**A transport refusal produces no acknowledgement.** A message that fails
envelope authentication, or that carries no artifact this contract routes, is
not a statement about an artifact and has no digest to name. Answering one with
a signed acknowledgement would also hand anything that can reach the broker a
signing oracle. Such messages are simply dropped, and the courier redelivers.

### Envelope

```json
{
  "device_id": "site-a-edge-01",
  "artifact_type": "custody_acknowledgement",
  "artifact": {
    "v": 1,
    "device_id": "site-a-edge-01",
    "local_seq": 12,
    "envelope_digest": "sha256:a079...",
    "custody_at_ms": 1787000000900,
    "key_id": "hkdf-sha256:d6aff3c0837ca1a07a5124e30d9612ac",
    "mac": "hmac-sha256:b8bb..."
  },
  "auth": {
    "scheme": "hmac-sha256",
    "signed_at_ms": 1787000000950,
    "signature": "hmac-sha256:..."
  }
}
```

| Field           | Required | Notes                                                                         |
| --------------- | -------: | ----------------------------------------------------------------------------- |
| `device_id`     |      yes | The runtime that produced the evidence. Must match the topic segment.          |
| `artifact_type` |      yes | One of the four names below. Not inferred from the artifact's shape.           |
| `artifact`      |      yes | The `evidence-exchange/v2` artifact, unaltered. This contract fixes no field.  |
| `auth`          | see below | Transport envelope authentication, as for reasoning and export in `gateway-api/v1`. |

No `request_id`. Inbound evidence is not a response to anything the runtime
asked for, and correlating it with a request the runtime never made would
invent state on both sides.

### Artifact Type Vocabulary

| `artifact_type`           | `evidence-exchange/v2` artifact | Authenticated under                    |
| ------------------------- | ------------------------------- | -------------------------------------- |
| `custody_acknowledgement` | Custody acknowledgement         | The dedicated custody secret (HMAC)     |
| `delivery_receipt`        | Delivery receipt                | An authority key, purpose `evidence_authority_receipt` |
| `epoch_confirmation`      | Epoch confirmation              | An authority key, purpose `evidence_authority_epoch`   |
| `evidence_disposition`    | Evidence disposition            | An authority key, purpose `evidence_authority_disposition` |

The gateway forwards every evidence disposition an authority response carried,
from the response to the request that decided it or from the device's return
set ([evidence-transport/v2.md](../evidence-transport/v2.md)), whatever its
scope or value, and reads none of its fields but the routing projection. Only
the runtime acts on one.

The sender names the artifact and the receiver MUST NOT infer the type from the
object's shape. The four have disjoint field sets, so trying each verifier
until one succeeds would work — and it decides what an artifact is from whether
it passed, which is the same reasoning `evidence-exchange/v2` forbids when
selecting a key. An `artifact_type` outside this table MUST be refused without
reaching any verifier.

A receiver MUST refuse an artifact whose type it does not route, rather than
routing it as the nearest match. New types are added here and in
`evidence-exchange`, never by a receiver's leniency.

### Artifact Bytes

The artifact travels as a JSON object, not as an opaque string, and the
obligation is on **values** rather than on bytes.

The gateway MUST forward every field of `artifact` with its value unchanged: it
MUST NOT add, drop, rename, or alter any field, at any depth, and MUST NOT
re-sign or re-MAC anything inside it. Key order and whitespace are explicitly
**not** part of that obligation. A JSON object does not carry them, so a
receiver cannot observe them and a courier cannot preserve them; requiring it
would be an unverifiable rule that implementations would satisfy only by
accident.

The receiver reconstructs the authenticated bytes from the decoded object under
the canonicalisation `evidence-exchange/v2` fixes, which is the same derivation
its published vectors pair with each artifact. Canonicalisation is what makes
key order irrelevant: two encodings carrying the same values reduce to the same
authenticated bytes.

This works only because `evidence-exchange/v2` bounds integers to the D-011
agreement zone and fixes string and Unicode handling, so every value survives a
JSON decode and re-encode unchanged. A future artifact carrying a value outside
that zone could not travel this way, and would need an encoding that preserves
bytes literally.

The gateway holds no evidence-authority key and signs nothing on the evidence
path. The custody acknowledgement it produces is an artifact of its own, not a
modification of one it carries.

### Envelope Auth Envelope

When `gateway.auth.enabled: true`, the gateway signs the payload with the
per-device binding [gateway-api/v1.md](../gateway-api/v1.md) uses for reasoning
and export, over the canonical string:

```text
message_type\ndevice_id\nrequest_id\nsigned_at_ms\ncanonical_json
```

| Field            | Value                                          |
| ---------------- | ---------------------------------------------- |
| `message_type`   | `"evidence_inbound"`                           |
| `device_id`      | The target device ID                           |
| `request_id`     | `""` — inbound evidence is not correlated       |
| `signed_at_ms`   | String of the `signed_at_ms` integer            |
| `canonical_json` | The payload without `auth`, canonicalised       |

`message_type` is distinct from every other family in this contract and in
`gateway-api/v1` so an
envelope authenticating one exchange cannot be replayed onto another. The
secret is the runtime-gateway envelope secret named by
`gateway.auth.shared_secret_env` — **not** the custody secret, which
authenticates the custody artifact itself and is named by
`gateway.custody.secret_env`.

Replay protection and clock skew follow the reasoning and export envelopes of
[gateway-api/v1.md](../gateway-api/v1.md).

### Invariants

- **Envelope authentication precedes reading the artifact.** A receiver MUST
  verify the envelope, when authentication is enabled, before dispatching to any
  artifact verifier. Reaching a verifier is what spends the receiver's ingest
  path.
- **The envelope is not the proof.** Each artifact carries its own
  authenticator under key material this transport never sees. A verified
  envelope proves the site gateway sent the message and nothing about whether
  the artifact is true. Arrival grants no authority: only a verified receipt
  advances delivery state, and only a verified epoch confirmation activates an
  epoch.
- **Transport refusals are distinct from artifact rejections.** A receiver MUST
  NOT report a transport failure using `evidence-exchange/v2`'s closed rejection
  set. `bad_authenticator` means an artifact's own MAC or signature did not
  verify — the shape a forgery takes — and reusing it for an unsigned or stale
  envelope would present ordinary clock skew as a forgery.
- **Rejections are surfaced.** A refused artifact and one that never arrived
  leave identical receiver state, so a receiver MUST record or report each
  refusal with its reason rather than dropping it silently.
- **Delivery is not application.** Publishing to this topic does not entitle
  the gateway to consider an artifact applied, and neither does a PUBACK. The
  runtime's custody, delivery and epoch state changes only on verification, and
  the gateway retires an artifact only on an ingest acknowledgement.
- **An acknowledgement carries no authority.** It reports that a receiver
  decided, not that the artifact was true, and a receiver MUST NOT treat one it
  receives as evidence of anything.

### Fixtures

[`gateway-api/vectors/inbound-evidence.json`](../gateway-api/vectors/inbound-evidence.json) carries a
golden inbound message and its acknowledgement: the published test secret, the
exact canonical signing string, the canonical payload bytes as hex, and the
expected HMAC. It is the cross-language proof for the new message types, the
empty `request_id` binding and the nested artifact, and both implementations
MUST reproduce it byte for byte.

The secret in that file is a published test value and MUST NOT sign anything
real.

## Site Health `evidence_delivery` Projection

> Status: Design target, pre-ratification. The base site-health projection and
> its `evidence_delivery` summary are implemented in `ori-gateway` under
> [gateway-api/v1.md](../gateway-api/v1.md); the fields `faults`, `devices`,
> `incidents`, `stopped_custody` and the store probe are not on main.

The site-health HTTP projection is defined in
[gateway-api/v1.md](../gateway-api/v1.md), and so is everything in it but
`evidence_delivery`. A gateway implementing this contract projects
`evidence_delivery` as this section defines, in place of that contract's
paragraph.

When the durable evidence courier is enabled, gateway operational posture MUST
include `evidence_delivery`, carrying `pending`, `degraded` and `blocked`.
`pending` counts artifacts eligible for delivery or waiting for an active
handoff. Artifacts under a verified epoch or identity stop are excluded from
`pending` and `blocked` and reported separately as stopped custody. Stopped
custody continues to degrade evidence health and reports
`reprovisioning_required`. It
MAY carry `last_failure_at_ms` and `last_error` as a one-event diagnostic
summary. `last_error` is one of `channel_unavailable`, `channel_refused`,
`channel_permanent_refusal`, `channel_receiver_state_refusal`,
`malformed_channel_response`, `runtime_sink_unavailable`,
`queue_retirement_failed`, `delivery_pending`, `channel_capacity_exhausted`, or
`authority_retention_capacity_unavailable`, and `evidence_delivery` carries no
other field than those this section names.
A terminal refusal, whether archived on a verified retention or held without
one, is recorded as `channel_permanent_refusal`, and a
`507 retention_capacity_exhausted` as `channel_capacity_exhausted`. A
`503 retention_capacity_unavailable` is recorded as
`authority_retention_capacity_unavailable`, distinct from a generic `503`. `last_error` is not the complete active-fault state, and a consumer
MUST NOT infer clean delivery from its absence. A degraded or blocked courier
degrades the gateway and therefore the site. Raw transport errors, endpoints,
credentials, filesystem paths, and authority implementation identity MUST NOT
appear in this projection.

A producer implementing this revision MUST carry `faults`, an array that is
empty when no courier-level fault is active; an older producer MAY omit it. Each
entry is one of `store_unavailable`, `admission_failed`, `delivery_impaired`,
`device_unconfigured`, `return_path_incompatible`, `reprovisioning_required`,
or `stopped_custody_full`, and no entry repeats. `store_unavailable` means the
courier cannot read, write, or atomically update its durable store.
`admission_failed` means a valid artifact for a configured device could not
complete admission: durable outbound queueing, and for a delivery envelope,
durable staging of its required custody return. It remains active until a
later admission of the applicable form completes; a store probe never clears
it. `delivery_impaired` means the courier knows that one or more queued
artifacts are held, waiting for a handoff, or backing off, but cannot enumerate
every affected device and lane in `devices`; a producer that omits `devices` MUST raise
it whenever it knows a non-clean per-device delivery state. A present `devices`
is complete, so a projection never carries both `delivery_impaired` and
`devices`.
`device_unconfigured` means the gateway observed an outbound carriage for a
device that is not configured, despite its configured topic ACLs; the
projection never carries that device ID. A broker-denied publication creates
no gateway-side observation and so cannot raise it. It clears only when that
device becomes configured and a later valid handoff for it is admitted;
elapsed time, silence, or a lost broker connection never clear it.
`return_path_incompatible` means the gateway keeps an authority artifact that
a device's declared inbound carriage contract cannot carry, per *Return order
is per device*; this revision's projection does not identify the device; the
gateway's durable record of each kept artifact names it. It clears only when
no such artifact is kept. `reprovisioning_required` means the gateway
holds stopped custody: the device needs a new epoch under an epoch stop, or a
replacement identity under an identity stop. The `scope` of each
`stopped_custody` entry says which; the runtime's `delivery_stop_status` says
it for the runtime. It is raised exactly when
`stopped_custody` would be non-empty, and it clears only when no stopped
custody is held.
`stopped_custody_full` means retained stopped custody has reached or exceeds a
stopped-custody bound of [gateway-config/v2.md](../gateway-config/v2.md); it
clears only when retained stopped custody is below every applicable bound.

With the courier enabled, each durable outbound and return store MUST be
probed immediately after opening and then every `store_probe_interval_s`,
independently of admissions and gateway-health publication.
`store_probe_interval_s` MUST be 300 through 900 seconds and defaults to 900. A
probe reads the store's directory and atomically replaces a fixed private probe
file in that directory: it writes fresh bytes to a private temporary file,
syncs it, renames it over the probe file, then syncs the directory. It never
creates, removes, rewrites, counts toward capacity, or reorders a queue record.
A failed probe, or any failed read, write, or atomic update of a store, raises
`store_unavailable` for that store. Only a successful probe of that store clears
it; a later successful operation does not, so after a store recovers the fault
can remain raised for up to one probe interval. A probe never clears
`admission_failed`.

Delivery to the evidence authority is ordered and held per device and lane
([evidence-transport/v2.md](../evidence-transport/v2.md), refusal policy), so
the projection MAY report it per device and lane in `devices`. A producer that cannot
enumerate durable per-device state omits it, and its omission conveys no
per-device information: it is never evidence of clean delivery or an empty
list. When present, `devices` holds one entry for each device and lane whose
delivery is not clean, and none for a lane whose delivery is clean:

| Field | Type and domain |
| --- | --- |
| `device_id` | the runtime node's own `device_id`, as in its carriage topic: 1 to 128 Unicode scalar values, none of them a control character (general category `Cc`), a character with the Unicode `White_Space` property, `/`, `+`, or `#`; no subordinate device identity is carried |
| `lane` | `registration` or `evidence`: the device's anchor registrations, or every other artifact it delivers |
| `pending` | integer, at least 1, that lane's artifacts counted in the gateway-level `pending`; never a stopped one |
| `state` | `held`, `waiting_handoff`, or `backing_off` |
| `held` | present exactly when `state` is `held` |

No two entries share a `device_id` and `lane`. `held` describes the refused
artifact at the head of that lane's order; its `artifact_type` is
`anchor_registration` in the `registration` lane and never in the `evidence`
lane:

| Field | Type and domain |
| --- | --- |
| `queue_record` | 64 lowercase hex, the durable queue record identifier |
| `artifact_digest` | `sha256:` followed by 64 lowercase hex, over the artifact bytes |
| `artifact_type` | the closed outbound carriage vocabulary |
| `refusal_status` | the HTTP status that caused the hold |
| `reason` | a reason at which `refusal_status` holds in the evidence-transport refusal policy, or `unrecognised` |
| `first_held_at_ms` | integer, when the head was first refused, surviving restarts |
| `acknowledged` | boolean; `false` until an operator acknowledgement surface exists |

A terminal refusal the authority retained is archived rather than held, in
either lane ([evidence-transport/v2.md](../evidence-transport/v2.md), refusal
policy), and the archive keeps incident metadata, never the bytes. A producer
implementing this revision MUST carry `incidents`, an array with one entry for
each unacknowledged incident, and empty when there is none; an older producer
MAY omit it. This revision defines no `archived_registrations`: every archived
refusal, in either lane, is a member of exactly one incident. An archived
refusal is never in `devices`, never counted in `pending`, and never makes
`blocked` true:

| Field | Type and domain |
| --- | --- |
| `device_id` | as in `devices` |
| `anchor_epoch_id` | `sha256:` followed by 64 lowercase hex, or `""` when the retention names none |
| `artifact_type` | the closed outbound carriage vocabulary |
| `refusal_status` | the HTTP status of the retained refusal |
| `reason` | a reason at which `refusal_status` archives in the evidence-transport refusal policy |
| `count` | integer, at least 1, the incident's distinct member digests |
| `first_refused_at_ms` | integer, when the first member was archived, surviving restarts |
| `last_refused_at_ms` | integer, at least `first_refused_at_ms`, when the latest member was archived |
| `first_digest` | `sha256:` followed by 64 lowercase hex, the first member |
| `latest_digest` | as `first_digest`, the latest member; equal to `first_digest` exactly when `count` is 1 |

A producer implementing this revision MUST carry `stopped_custody`, an array
with one entry for each device and lane that holds stopped custody, and empty
when none does; an older producer MAY omit it. A lane holds stopped custody
when a verified `stop` projection
([evidence-transport/v2.md](../evidence-transport/v2.md), stopped scopes) covers
queued entries of it; they stay in custody, in order, and are never archived.
A stopped entry is never in `devices`, never counted in `pending`, and never
makes `blocked` true:

| Field | Type and domain |
| --- | --- |
| `device_id` | as in `devices` |
| `lane` | as in `devices` |
| `scope` | `epoch` or `identity` |
| `count` | integer, at least 1, that lane's entries in stopped custody |

`scope` is required and is exactly `epoch` or `identity`, copied from the
verified stop projection governing the stopped custody. A lane whose entries a
verified `identity` stop covers is governed by that stop, since it covers every
entry of that device.

No two entries share a `device_id` and `lane`. Stopped custody is bounded per
identity and in total by the stopped-custody bounds of
[gateway-config/v2.md](../gateway-config/v2.md), and no bound is ever met by
eviction or deletion. An artifact that would enter stopped custody beyond an
applicable bound is not accepted into gateway custody: the gateway publishes
no outbound acknowledgement and no custody acknowledgement for it, and the
runtime keeps its bytes. An entry already in gateway custody that a
verified stop covers moves into stopped custody whatever the bound, because
custody never moves backward, and the move raises `stopped_custody_full` when
it reaches or passes a bound. The retained stopped set stays readable and
recoverable. A courier that opens with retained stopped custody above a
configured bound opens, raises `stopped_custody_full`, refuses additional
stopped custody, and delivers every lane that is not stopped.

An incident coalesces the archived refusals that share `device_id`,
`anchor_epoch_id`, `artifact_type`, `refusal_status` and `reason`; refusals that
differ in any of them never coalesce, and no two entries share all five. The
gateway reads `anchor_epoch_id`, `refusal_status` and `reason` from the verified
retention, never from the artifact. It keeps, durably and for every incident,
the digest of each distinct member, so every member stays enumerable and
individually retrievable from the authority by digest, and `count` is the
number of those digests. Archiving a digest that is already a member, such as
an identical retry or a re-offer of the same bytes, changes no field.
Timestamps are the gateway's clock at archive and survive restarts, as does
every incident.

Acknowledgement changes alert visibility only: an acknowledged incident leaves
`incidents` and stops degrading the gateway, and nothing else changes — its
members, their retained bytes at the authority, and every evidence finding stay
as they were. A distinct member archived after acknowledgement reopens that
incident: it returns to `incidents` unacknowledged, with `count`,
`last_refused_at_ms` and `latest_digest` advanced and its first fields
unchanged. This revision defines no operator acknowledgement surface, so every
incident stays unacknowledged until one exists.

`degraded` is true exactly when `faults` is non-empty, `devices` is present
and non-empty, `incidents` is present and non-empty, or `stopped_custody` is
present and non-empty. When `faults`, `devices`, `incidents` and
`stopped_custody` are all absent, `degraded` keeps an older producer's advisory
meaning; their absence is unknown, never evidence of clean delivery.
`blocked` is true exactly when `pending` is positive, `devices` is present,
every pending artifact is represented by `devices`, and every represented
lane is held. Stopped custody never makes `blocked` true, and a lane whose
only queued entries are stopped has no entry in `devices`. A fault never makes
`blocked` true, and when `devices` is absent `blocked` is false. A lane
delivering cleanly has no entry in `devices`, so the entries' `pending` never
sum to more than the gateway-level `pending`. One held
lane degrades the gateway and the site; it does not report the gateway
blocked while another lane is still delivering. Every field here is within
the prohibition above: a digest identifies bytes, not an endpoint or a
credential, and a reason or fault is drawn from a closed vocabulary. A consumer
that does not know `devices`, `faults` or `stopped_custody` ignores them.

[`vectors/site-health-evidence-delivery.json`](vectors/site-health-evidence-delivery.json)
fixes accepted and refused projections, and
`scripts/check-gateway-site-health-evidence-vectors` holds them to these rules.

## Compatibility with gateway-api/v1

Both contracts use the topics `ori/{device_id}/evidence/outbound`,
`ori/{device_id}/evidence/outbound/ack`, `ori/{device_id}/evidence/inbound` and
`ori/{device_id}/evidence/inbound/ack`, the same payload fields and the same
envelope binding, so the published fixtures
[`outbound-evidence.json`](../gateway-api/vectors/outbound-evidence.json) and
[`inbound-evidence.json`](../gateway-api/vectors/inbound-evidence.json) hold
under both. A receiver implementing `gateway-api/v1` refuses an `artifact_type`
outside that contract's three without reaching any verifier, and that refusal
produces no acknowledgement. A gateway implementing this contract therefore
never stages an `evidence_disposition` into the return lane of a device whose
declared inbound carriage contract is `gateway-api/v1`: it keeps the artifact
outside every lane and raises `return_path_incompatible`, per *Return order is
per device*, so a device that can never acknowledge it holds no lane, its own
included, and every other device's return lane continues.
[`vectors/return-path.json`](vectors/return-path.json) fixes a mixed site, and
`scripts/check-gateway-return-path-vectors` holds it to these rules.
