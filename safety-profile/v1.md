# Safety Profile Contract v1

> Status: Design target, pre-ratification. No shipped consumer claims
> conformance. Amendable in place under the
> [pre-ratification exception](../VERSIONING.md#pre-ratification-exception).

A Tier D action fires without an operator and cannot be overridden. This
contract defines where its conditions come from: a **safety profile** is a
release-owned record binding an observed physical quantity to a
runtime-implemented condition evaluator and a protected-circuit outcome. The
runtime ships the profiles, evaluates them before any skill rule, and activates
them from the hardware a site has commissioned — never from the skills a site
has installed.

## Why This Contract Exists

In `ori-runtime` at `fe5eb9a`, every Tier D trip point is an untyped number in
a packaged skill's `skill.yaml`. Two of the five shipping conditions are
literals with no configuration key at all. Only first-party skills may declare
`action_tier: D`, so every trip point is already release-owned — but as a bare
float in a manifest whose action list decides what the trip does, and whose
presence decides whether the device has a cutoff at all.

Three consequences, each a contract-level problem:

**Coverage is an accident of selection.** A device with a current clamp and a
wired contactor has an overcurrent cutoff only if a particular skill is
installed. As skills move to the Hub, that makes the safety envelope a property
of the catalogue.

**The value is unbounded and untyped.** `dangerous_overcurrent_threshold: 20.0`
is compared against a reading by an expression evaluator. Nothing states its
unit, its permitted range, or what sensor must be able to observe it.

**The action is a mutable list.** The shipped overcurrent trigger dispatches
`[alert_whatsapp, log_to_dashboard]` and directs deployments to override that
list in configuration. No such override surface exists. The tier defined as
always autonomous sends a message.

## Vocabulary

These layers stay distinct in profiles, code, and tests. A test that asserts
one as a proxy for another is not evidence about the other.

| Layer | Owned by | Example values |
| --- | --- | --- |
| Profile | This contract; shipped with the runtime release | `electrical.overcurrent.v1` |
| Condition kind | This contract; evaluators implemented in the runtime | `upper_capacity_multiplier` |
| Zone | [commissioned-safety-binding/v1.md](../commissioned-safety-binding/v1.md) | sensor, actuator, rated capacity, proof |
| Physical outcome | This contract names it; the zone's commissioned mapping resolves it | `open_protected_circuit` |
| Coil state | The zone's commissioned mapping | `energised`, `de_energised` |
| Trip state | This contract | `inactive`, `armed`, `tripped` |

A profile commands an outcome. It never names a coil state, a contact state, an
actuator kind, or an actuator-specific verb. `trip_relay` describes how one
actuator behaves; it says nothing about the load, and it would mean the
opposite thing on a zone whose mapping is reversed.

## Scope And Trust Model

**The reviewed runtime release owns Tier D, and nothing else confers it.** Not
a skill, a model, an entitlement, a cloud service, a remote command, a
provisioning document, or a commissioning binding.

| Party | May | Never |
| --- | --- | --- |
| Runtime release | Ship profiles; implement evaluators; activate profiles from accepted zones | Accept a profile from any other source |
| Commissioning authority | Supply the zone: sensor identity, range, direction, unit, rated capacity, actuator, mapping, proof | Author a condition kind, a multiplier, a threshold, or an outcome |
| Provisioning authority | Declare that hardware exists | Supply any profile parameter |
| Skill package | Observe the same signal; add diagnosis, history, alerting, Tier C proposals | Create, weaken, shadow, remove, or replace a profile |
| Remote command, DevicePolicy, entitlement | Nothing | Alter a profile parameter, activation, trip state, or outcome |

**A profile has no deployment-supplied parameters.** Every number in a profile
is release-owned. The only site-specific inputs a profile consumes are the
commissioned facts in an accepted zone, and the contract that signs those facts
already excludes the provisioning signer structurally. `device.rated_capacity_amps`
in a runtime configuration document is not an input to any profile, and a
consumer MUST NOT read a capacity from a provisioning-signed document.

This is the resolution of the question raised in the commissioned binding
contract: a capacity is a safety parameter, so it arrives only from the
commissioning signer, and the release-owned multiplier applied to it is what
this contract fixes.

**Nothing gates a profile.** Activation and evaluation have no dependency on
an entitlement, a licence, a lease, a subscription or payment state, evidence
availability, or connectivity to a gateway or cloud. A consumer that consults
any of those before evaluating an active profile, or that lets any of them
deactivate one, is non-conforming. Safety is core, and a protection claim that
lapses with a subscription or a link is not a protection claim.

## Profile Shape

Profiles are release-shipped data. The v1 profile set is the file
[vectors/profiles.json](vectors/profiles.json), which a consumer vendors
byte-for-byte and pins; it is normative, not illustrative.

```json
{
  "v": 1,
  "id": "electrical.overcurrent.v1",
  "status": "candidate",
  "observes": { "quantity": "current", "unit": "ampere" },
  "condition": {
    "kind": "upper_capacity_multiplier",
    "capacity_parameter": "rated_capacity_amps",
    "multiplier": 2.0
  },
  "outcome": "open_protected_circuit"
}
```

| Field | Type | Constraint |
| --- | --- | --- |
| `v` | integer | exactly `1` |
| `id` | string | `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+\.v[1-9][0-9]*$`; unique within the set |
| `status` | string | `ratified` or `candidate` |
| `observes.quantity` | string | matched exactly against `zone.sensor.quantity` |
| `observes.unit` | string | matched exactly against `zone.sensor.unit` |
| `condition.kind` | string | closed vocabulary below |
| `condition.capacity_parameter` | string | `upper_capacity_multiplier` only; must equal `zone.rated_capacity.parameter` |
| `condition.multiplier` | number | `upper_capacity_multiplier` only; greater than `1.0`, at most `100.0` |
| `condition.threshold` | number | `upper_bound` only; finite |
| `outcome` | string | `open_protected_circuit` |

**The grammar is closed at every level.** A profile object admits exactly `v`,
`id`, `status`, `observes`, `condition`, `outcome`; `observes` admits exactly `quantity`
and `unit`; `condition` admits exactly `kind` plus the fields its kind names.
An unrecognised key, an unrecognised kind, a missing field, or a value outside
its constraint is a `malformed_profile`. A profile set that fails to load is a
broken release, and a consumer MUST refuse to start in every deployment posture:
there is no development-mode tolerance for a release that cannot state its own
safety conditions.

Numbers follow the D-011 agreement zone of
[evidence/v2.md](../evidence/v2.md): integers within ±(2^53 − 1), non-integers
finite and either exactly zero or of magnitude in `[1e-4, 1e16)`. `multiplier`
and `threshold` are numbers and MUST NOT be booleans; `v` is an integer and
`1.0` is not `1`.

### Condition Kinds

Conditions are typed records. The `kind` selects an evaluator the runtime
implements in code. **There is no expression string, no evaluation namespace,
and no AST allowlist anywhere on the Tier D path.** Expression evaluation stays
where it belongs, guarding untrusted skill conditions for Tiers A through C.

| `kind` | Fields | Trip point | Condition |
| --- | --- | --- | --- |
| `upper_capacity_multiplier` | `capacity_parameter`, `multiplier` | `zone.rated_capacity.value × multiplier` | `reading > trip point` |
| `upper_bound` | `threshold` | `threshold` | `reading > trip point` |

Comparisons are strict. The trip point for `upper_capacity_multiplier` is the
IEEE 754 double-precision product of the two values, computed at activation,
retained with the activation record, and recomputed whenever the accepted
binding changes — a trip point is never carried across a binding revision. The
corpus carries the expected product for every capacity case so that two
implementations cannot disagree about it.

Both v1 kinds are upper bounds. A lower-bound kind is not defined, because no
v1 profile would use it and a kind the corpus cannot exercise would be a rule
an implementation could omit while claiming conformance.

`kind` is a closed vocabulary. An unrecognised kind is `malformed_profile`,
never treated as the nearest known one. Adding a kind is a contract change.

### Status

A profile is `ratified` or `candidate`, and the difference is authority.

**A `candidate` profile activates nothing and executes nothing.** It is a
release's declaration of the condition it intends to own, carried so that the
migration target is representable, vendored, and drift-checked before it is
trusted. A consumer MUST NOT activate a candidate on any zone, MUST NOT
evaluate it, and MUST NOT execute its outcome. A zone that would be
eligible for it is reported as `pending_ratification`, by profile id, as
unprotected hardware — never as covered. A zone that would be eligible
for a candidate profile is `pending_ratification` for it.

**Ratification is a contract change.** It flips `status` in `profiles.json`,
which changes every consumer's pinned digest, and it is made only when the
questions recorded for that profile under Open Questions are closed. A
consumer MUST NOT carry a local override that treats a candidate as ratified.

**No v1 profile is ratified.** Every profile in the shipped set is a
`candidate`. The shipped set therefore activates nothing, which is the honest
state of a contract with no consumer and no safety argument yet for any of its
numbers. The corpus exercises activation, evaluation and trip state against
ratified fixture profiles that ship in the corpus files and nowhere else.

### Outcomes

`open_protected_circuit` is the only v1 outcome: isolate the protected load or
supply from its source. It is the semantic outcome the commissioned mapping
resolves to a coil state per zone, and on the firmware wire it is spelled
`relay_open` — the mapping table in
[commissioned-safety-binding/v1.md](../commissioned-safety-binding/v1.md#firmware-command-semantics)
is normative for that spelling.

`close_protected_circuit` is never a safety outcome. It is what arming and
reset do, under the rules below, and no profile may name it.

A gas supply valve is a protected circuit in this sense. Closing the valve
isolates the supply; the zone's mapping records which coil state achieves it.
The action name `close_gas_valve` therefore migrates to
`open_protected_circuit` on a zone whose actuator is the valve, and the word
"close" in the legacy name describes the valve, not the outcome.

## The v1 Profile Set

| `id` | Status | Observes | Condition | Outcome |
| --- | --- | --- | --- | --- |
| `electrical.overcurrent.v1` | `candidate` | `current` / `ampere` | `upper_capacity_multiplier`, `rated_capacity_amps` × `2.0` | `open_protected_circuit` |
| `electrical.overvoltage.v1` | `candidate` | `voltage` / `volt` | `upper_bound`, `260.0` | `open_protected_circuit` |
| `gas.concentration.v1` | `candidate` | `gas_concentration` / `ppm` | `upper_bound`, `400.0` | `open_protected_circuit` |

All three carry the numbers the shipping skills use today, and all three are
candidates for the same reason: a number that reproduces a legacy trigger has
been shown equivalent to it, not shown safe.

**The overcurrent multiplier is `2.0`, not `5.0`.** Earlier discussion used
`5.0` as an illustration. The shipping trigger trips at `20.0 A`, the
documented capacity is `10.0 A`, and the clamp the runtime documentation
recommends reads to `30 A`. A multiplier of `5.0` puts the trip point at
`50 A`, beyond the sensor's full scale — a cutoff that can never fire, which
the binding contract's trip-point bound now refuses. `2.0` reproduces the
shipping trip point exactly at the documented capacity and stays observable on
the documented sensor.

**That is equivalence and measurability, not a safety argument.** The legacy
path this number reproduces never reliably actuated, so matching it proves
nothing about whether an instantaneous 2× cutoff protects a conductor or
nuisance-trips a motor on inrush. The profile is a `candidate`: a consumer
cannot activate or execute it, and the number becomes a trip point only when
the open questions below are closed and the status flips.

## Activation

A profile activates on a zone, never on a device and never on a sensor type.
The zone comes from a binding that has passed every stage of the commissioned
binding contract's verification order; nothing in this contract re-decides a
binding verdict, and nothing here can rescue a zone the binding verifier
refused.

For each accepted zone and each profile in the set, in this order:

| # | Check | Refuses with |
| ---: | --- | --- |
| 1 | `zone.sensor.quantity == profile.observes.quantity` | not eligible; no verdict |
| 2 | `profile.status == ratified` | `pending_ratification` |
| 3 | `zone.sensor.unit == profile.observes.unit` | `unit_mismatch` |
| 4 | `zone.sensor.direction == positive_is_load_draw` | `direction_unsupported` |
| 5 | `upper_capacity_multiplier`: `zone.rated_capacity.parameter == capacity_parameter` | `parameter_mismatch` |
| 6 | trip point within `[zone.sensor.range_min, zone.sensor.range_max]` | `trip_point_unobservable` |
| 7 | zone proof method is not `undemonstrated` | `undemonstrated_binding` |

`pending_ratification` is decided before any site fact is examined, because
it is a property of the release and not of the zone. It is not a startup
refusal in any posture — the site has done nothing wrong — but the zone MUST
be reported as unprotected for that profile on the health surface, by id.

A zone that matches a profile's quantity is **eligible** for it, and every
subsequent check is a verdict about that eligible pair. A zone whose quantity
matches no profile activates nothing and is not an error: the device has
commissioned hardware this release has no condition for, which is a coverage
fact the health surface reports, not a refusal.

**Every eligible pair activates or refuses; the consumer does not choose.** A
runtime MUST NOT carry a list of enabled profiles, a per-site opt-out, or an
ordering preference. If a zone is eligible for a profile, the profile is either
active on that zone, pending that profile's ratification, or refused under
hardened posture.

**Checks 6 and 7 are deliberately redundant with the binding verifier.** Its
`bounds` stage refuses an unobservable capacity trip point as `out_of_bounds`
when it consults the profile set, and its `activation_posture` stage refuses an
undemonstrated zone. Activation recomputes both, because a check that holds
only because an earlier check held is not a boundary: a consumer whose binding
verifier was built without the profile set would otherwise activate a cutoff
that can never fire, and check 6 is in any case the only bound on a
fixed-threshold kind, which the binding contract does not cover.

**Direction is required, not assumed.** `positive_is_load_draw` is the only
direction v1 evaluators understand. A clamp mounted backwards reports a hazard
as a fall in magnitude, and an upper-bound evaluator would never fire; the
binding records the direction so that the profile can refuse rather than
silently evaluate the wrong sign.

### Activation is independent of skills

The set of installed skills, their manifests, their configuration, and their
trigger declarations are not inputs to activation. The corpus carries cases in
which no skill is installed, and cases in which an installed skill declares a
Tier D trigger on the same quantity; the activation result is identical.

### Hardened startup

Under `staging`, `production`, or `development` with
`security.enforce_production_posture: true`, a consumer MUST refuse to start
when:

- the profile set fails to load (`malformed_profile`) — in every posture;
- any eligible zone is refused (`unit_mismatch`, `direction_unsupported`,
  `parameter_mismatch`, `trip_point_unobservable`, `undemonstrated_binding`) —
  `pending_ratification` is not a refusal of the zone and does not block
  startup;
- declared actuating hardware is bound by no zone
  ([`unbound_actuator`](../commissioned-safety-binding/v1.md#error-semantics));
- an active profile's zone names an actuator whose backend cannot be verified
  available, matching the existing refusal of a configured GPIO relay with no
  GPIO library.

A device that quietly disables protection and reports healthy is the worst
available outcome. In `development` posture the consumer starts with a
consolidated WARNING, the refused zones' profiles inactive, health degraded,
and MUST NOT claim Tier D protection for those zones on any operator-visible
surface.

## Evaluation

An active profile is evaluated against every reading for its zone's
`sensor_id`, before any skill rule, before any LLM, and before the action
dispatcher. The reading's adapter-level `sensor_type` is not consulted; the
zone binds by `sensor_id`, and the profile binds the zone by quantity and unit.

### Credible readings

A reading is **credible** when all of the following hold:

- `value` is a finite number and not a boolean;
- `unit` equals `profile.observes.unit`;
- `quality` is greater than zero.

A reading that is not credible is **rejected input**. It does not trip, and it
does not silently vanish either: rejection MUST produce an immediate Tier A
operator alert and a degraded health state naming the zone, with bounded
suppression so that a persistent fault does not become a message flood. The
bound is an implementation choice; its existence is not.

A refused measurement window under the adapter's own measurement contract
(`ori-runtime` #398) produces no reading at all. It reaches this contract only
as an absence, which the measurement-loss rule below covers.

### Verdicts

| Verdict | When |
| --- | --- |
| `trip` | The reading is credible and the condition holds |
| `no_trip` | The reading is credible, the condition does not hold, and the value lies within `[range_min, range_max]` |
| `rejected_input` | The reading is not credible, or the condition does not hold and the value lies outside the declared range |

**The comparison is decided first.** A reading beyond full scale on the hazard
side of the trip point trips: a saturating sensor reporting above its range
still reports more than the trip point, because the trip point is bounded to
lie within range. Only a reading that does not satisfy the condition is then
tested against the range, and a value outside it on the non-hazard side is a
sensor reporting something it cannot have measured.

`rejected_input` carries a reason from a closed vocabulary, the first that
applies in this order: `boolean`, `non_numeric`, `non_finite`, `unit_mismatch`,
`zero_quality`, `out_of_range`. A boolean is tested before a number because in
some languages it is one; `zero_quality` covers a `quality` that is absent, not
a number, or not greater than zero.

### Attestation never gates a trip

Evidence grade describes how strongly an event can later be proven. It is not
permission to preserve physical safety. A credible reading that satisfies the
condition fires the outcome whether or not the resulting action row can be
attested, signed, sealed, delivered, or receipted; the attestation gap is
recorded under [evidence/v2.md](../evidence/v2.md) and reported, and the trip
is not delayed by any of it. A spurious trip is safe and annoying; a missed
trip is a fire.

### Measurement loss

When an active zone receives no credible reading for longer than a bound the
consumer derives from the sensor's declared poll interval and documents, the
consumer MUST degrade health for that zone, raise a Tier A alert under the same
bounded suppression, and continue to hold the current trip state. **v1 profiles do not open the
protected circuit on measurement loss.** Whether a zone should is a
commissioned property of the load, and expressing it requires a zone-level
declaration this contract does not yet define. It is recorded under Open
Questions and is not implied by anything here.

## Trip State

Every active profile holds one trip state per zone. The state is durable: it
survives a restart, and it is retained with the record of the reading, the
`binding_seq`, and the profile that produced it.

```text
                 arm                    trip
   inactive ──────────────▶ armed ───────────────▶ tripped
      │  ▲                    │                       │  ▲
      │  └────(restart)───────┘                       │  │
      │                                    (restart)──┘  │
      └───────────────── trip ───────────────────────────┘
                                                         │
                                           reset: local, manual,
                                           condition not active
                                                         ▼
                                                       armed
```

| State | Decision posture | Entered by |
| --- | --- | --- |
| `inactive` | No trip outcome decided; the circuit is whatever the startup rule, the coil's de-energised terminal state, or the platform's qualified line state leaves it | Startup with no durable trip and no unresolved intent; restart from `armed`; refusal; profile not active on this zone |
| `armed` | `close_protected_circuit` decided | `arm`, or a successful reset |
| `tripped` | `open_protected_circuit` decided | `trip`: a credible reading satisfies the condition, from `inactive` or from `armed`. The outcome is commanded immediately, then the state is recorded durably |

The middle column is a **decision posture, never an attempt and never an
observed physical state**. `tripped` records that opening was decided —
`command_pending` can exist before any driver call has happened; whether the
driver accepted a command is the command-status axis, and whether the
circuit physically moved is the effect-verification axis. Neither is implied
by a state name, in either direction.

**Startup commands the coil, it does not assume it — and the command is
conditioned on what de-energising does to this zone.** On entering `inactive`
at startup, a zone whose commissioned `de_energised_terminal_state` is `open`
has its coil explicitly commanded `de_energised` through the zone's
commissioned mapping and `active_high`, rather than left at whatever the
platform defaults to. A zone whose `de_energised_terminal_state` is `closed`
MUST NOT have its coil commanded at startup: for that zone, `de_energised`
closes the protected circuit, and a runtime that may have died between
commanding a trip and recording it would be reconnecting the very load a trip
opened. Its line is left unacquired until the first credible reading is
evaluated — a reading that satisfies a condition trips the zone, and only a
credible reading that satisfies none licenses commanding `de_energised`. What
the unacquired line does in the meantime is the platform's qualified
behaviour: on a platform whose pads retain across process death, a pre-crash
trip's coil state survives into the new process, which errs in the safe
direction. In every case the command, when it is given, is a coil state, not
a GPIO level: an implementation that writes a logical low and calls the coil
de-energised has derived a coil state from a board polarity it never checked.
What the protected circuit does at that moment is the zone's commissioned
`de_energised_terminal_state`, observed at commissioning and never claimed by
software.

**`inactive` means unarmed, not unprotected.** A zone whose de-energised
terminal state is `closed` carries load while inactive. A credible reading
that satisfies the condition trips the zone from `inactive` exactly as it does
from `armed`, and executes the outcome.

**Arming commands the circuit closed and is refused unless three things
hold**, tested in this order:

| Refusal | When |
| --- | --- |
| `tripped` | The zone is `tripped`. Only a reset leaves that state |
| `safety_path_unconfirmed` | Hardened startup has not confirmed, since the last start, that the zone's actuator can be driven to the outcome |
| `no_credible_reading` | No credible reading has been seen for the zone since the last start |

There is no `condition_active` refusal for arming, and the corpus cannot carry
one: a credible reading that satisfies the condition has already taken the
zone to `tripped`, so it can never be the most recent credible reading of a
zone that is merely `inactive`. Together with the trip-intent journal and the
conditioned startup command below, this is what closes the crash window. A
runtime that trips, dies before recording the trip, and restarts into a live
hazard never arms — it has no credible reading until the first one arrives,
and that one trips it — and it never closes the circuit on the way there,
because an unresolved intent loads as `tripped`, and a closed-terminal zone's
coil is not commanded until a credible reading has spoken.

**A trip latches.** From `tripped`, no reading, restart, configuration value,
skill, remote command, DevicePolicy, entitlement change, or binding revision
moves the zone anywhere. A restart reloads `tripped` from durable state and
does not close the circuit. `armed` is not durable: a restart from `armed`
returns to `inactive`, and the safety path is confirmed again before the
circuit is closed.

**Reset is local, manual, and conditional.** The only transition out of
`tripped` is an explicit reset performed at the device by the reviewed local
procedure. It is refused, in this order, with `not_tripped` when the zone is
not tripped, `no_credible_reading` when no credible reading has been seen since
the last start, and `condition_active` when the most recent credible reading
satisfies the condition. A successful reset arms the zone and executes
`close_protected_circuit`. A remote command is not a local action; a remote
reset does not exist in v1.

**No external input moves the state.** A remote command, a skill, a
configuration document, a DevicePolicy, or a binding revision attempting to
arm, trip, or reset a zone is refused with `no_authority`, in every state.

**The outcome executes before the record is written — and an intent is
attempted before either.** The record that must never gate execution is the
full durable trip record; a local **trip-intent** append is attempted first,
under these rules, so that two conforming consumers cannot implement
materially different crash guarantees:

- **The attempt is bounded by a deadline the consumer declares and
  documents, at most 250 ms.** On expiry or failure the command proceeds and
  the intent is treated as not recorded; nothing retries the append ahead of
  the command. The ceiling is a v1 bound, not a safety argument: a profile's
  ratification MUST demonstrate that the declared deadline is tolerable for
  that profile's hazard — the overcurrent profile's open time-current
  question includes this pre-command latency — and a profile whose hazard
  cannot tolerate the declared deadline cannot be ratified for consumers
  declaring it. The declared value is a **reviewed, release-owned constant**,
  or an authenticated platform-qualification value once that contract
  exists: no skill, configuration document, DevicePolicy, entitlement, or
  remote input may select, replace, or alter it, because whoever chooses
  this number controls Tier D response latency.
- **An intent record carries at least**: the `zone_id` and `profile_id`
  pair, the `binding_seq` in force, the commanded outcome, a unique
  `attempt_id` stable for the life of that attempt, and its creation time.
- **The order is**: attempt the intent append, command the outcome, write
  the full trip record durably, and only after that commit remove or mark
  the intent resolved. A crash between the record and the resolution is
  benign — the record governs, and a full trip record for a pair resolves
  every older intent for that pair.
- **At startup, an intent with no resolving record loads the pair as
  `tripped` with `command_pending` status**, and the retry obligation below
  applies. Duplicate unresolved intents for one pair collapse to the latest
  **by durable journal append order** — attempt ids are unique, not ordered,
  and order comes from the journal alone. A malformed intent entry whose
  pair is still identifiable loads that pair the same way — fail closed; an
  intent journal that cannot be read at all refuses hardened startup and
  degrades a development start, exactly as an unreadable durable state does.
  **An intent whose `binding_seq` does not match the binding in force loads
  the pair as tripped and orphaned**: latched and health-visible, and never
  actuated through a binding it was not commanded under. Every intent field
  is validated under a closed grammar — the pair fields are non-empty and
  name this journal's own pair, `attempt_id` is a non-empty string unique
  within the journal, `binding_seq` and `created_at_ms` are positive
  integers, the outcome is `open_protected_circuit`, and `resolved` is a
  boolean, not a string that happens to be truthy. A field violation is a
  malformed entry and fails closed; a repeated `attempt_id` is corruption
  beyond the entry level — two entries claim one identity — and the journal
  refuses to load, as an unreadable one does. **Resolution is a sequence
  invariant, not a flag**: an intent may be marked resolved only by a later
  full record or durable clear in the same journal, so a resolved intent
  with no such successor claims a resolution nothing durable performed — it
  is journal corruption and refuses to load.
- **A durable tripped record with no command status predates this
  vocabulary and proves no acceptance: it loads as `command_pending`.**
  Absence of evidence migrates to the retryable status, never to the one
  that stops retries.
- **A successful reset durably clears the pair's trip record** — that is
  what lets a restart after reset load `inactive` — and a full record, or
  that durable clear, resolves every intent appended before it and none
  appended after.
- **If the full record write fails after the command**, the intent is
  retained, the pair is held `tripped` in memory, and the pair's durability
  rests on the intent until the record lands. **Record persistence is its
  own obligation, independent of the outcome retries**: it continues on its
  own bounded-backoff schedule until the full record commits, whatever the
  command status — driver acceptance stops the outcome retries and stops
  nothing about persistence, and persistence recovery never re-issues an
  accepted physical command.

The residual window — the intent append itself failed *and* the process died
between command and record — is closed for a zone whose de-energised terminal
state is `open` by the startup command, and bounded for a `closed` zone by
the conditioned startup rule above: such a zone is reconnected no earlier
than its first credible non-hazard reading, and a hazard that cannot tolerate
that bound requires an `open` terminal state or an independent interlock,
because software cannot make a `closed`-terminal zone safe. That is a
commissioning decision, not a runtime behaviour.

**Command status is evidence-bounded.** What the runtime knows after
commanding an outcome is what the driver reported, not what the circuit did.
The per-pair command status vocabulary is `none`, `command_pending`,
`driver_refused`, and `command_issued`; physical verification, where a later
mechanism exists, is reported separately as `effect_verified: unknown`,
`matched`, or `mismatched`. A health surface says "trip command issued;
physical outcome unverified" — never "outcome executed" — until something
actually verified the effect.

**Retries are owned by the registry and independent of readings.** While a
pair is `tripped` with a command status other than `command_issued`, the
consumer MUST keep attempting the outcome on a bounded-backoff schedule with
no terminal attempt limit, from a loop that does not depend on sensor
delivery — the moment a sensor stops producing readings is exactly the moment
an unresolved trip must not stop retrying. The loop stops only when the
driver reports acceptance, a local reset succeeds, or the consumer shuts
down; a command already accepted is never re-issued merely because its
physical effect remains unverified. Reset and the retry loop MUST be
serialised: once a reset has licensed closing the circuit, no previously
scheduled retry of that trip's open command may execute — a retry that fires
after the reset would reopen a circuit an operator just closed.

**A tripped pair whose zone leaves the binding is orphaned, not erased.** It
stays latched and health-visible, and it cannot actuate through a missing or
mismatched binding. Ordinary reset cannot clear it either: reset requires a
current credible reading and condition evaluation, and an orphan may no
longer have a usable zone or sensor association. The only exit is **local
orphan retirement**, a distinct operation with its own semantics:

- it is local and manual, performed at the device under the same provenance
  as the reviewed local reset procedure, with no remote path;
- it actuates nothing — no coil is commanded, in either direction;
- it is refused with `not_orphaned` when the pair's zone exists in the
  current binding (then ordinary reset governs), and with `no_authority`
  from every external source, like every other state-moving attempt;
- it moves the record to a terminal `retired_orphan` disposition retained
  for audit, with the operator identity and time recorded — never deletion,
  never a return to `armed`, and never a licence to actuate.

Ordinary binding replacement, startup cleanup, and configuration changes
move nothing here, exactly as the latch rule states.

**A trip that cannot be executed is still a trip.** If the outcome fails — the
actuator backend is unavailable, the command is refused, the firmware channel
is unreachable — the zone still enters `tripped`, the failure is recorded and
alerted as a degraded safety state, and the consumer MUST keep attempting the
outcome while the zone is tripped and the failure persists. A zone that could
not be opened is reported as such, never as protected.

**Trip state is not a profile parameter.** It is runtime-owned state that no
document, package, or command supplies. The corpus carries lifecycle cases
proving each transition and each refusal.

## Authority Checks In Code

Three checks, each of which MUST hold on its own. None is redundant with the
others, because authority must not depend on a single boundary:

1. At skill load, `action_tier: D` from a non-first-party package remains
   refused as it is under [skills-package/v2.md](../skills-package/v2.md).
2. At dispatch, a Tier D action whose provenance cannot be proven is lowered
   to Tier C and logged, as it is today.
3. Immediately before a Tier D outcome executes, the consumer MUST verify
   that the authority source is the safety registry populated from the
   release-shipped profile set, and refuse otherwise.

A remote `SET_THRESHOLD` has no authority over any profile parameter, because
profiles have none. As each legacy Tier D trigger migrates, its configuration
key stops being a Tier D key and the threshold guard's authority over it is
removed rather than left standing beside the profile; a remote command that can
still move the old key once a profile owns the decision leaves two trip points,
only one of which is typed.

### Legacy action names

The runtime registers three actuator-specific executors. Each maps to exactly
one protected-circuit outcome, and the mapping fixes where that outcome may be
commanded from. The vocabulary is normative and carried in
[vectors/legacy-actions.json](vectors/legacy-actions.json).

| Legacy action | Outcome | Permitted as a profile outcome | Permitted from |
| --- | --- | ---: | --- |
| `trip_relay` | `open_protected_circuit` | Yes | A profile trip; a Tier C approved action |
| `close_gas_valve` | `open_protected_circuit` | Yes | A profile trip; a Tier C approved action. Today it is registered as the same executor as `trip_relay`, which is the mapping made explicit |
| `release_relay` | `close_protected_circuit` | **No** | Local arm and local reset only |

`release_relay` is the one that must not be allowed to drift. It restores the
load, and no safety profile may name that as an outcome; it is what arming and
a successful reset perform, under the trip-state rules, at the device. A
migration that carries `release_relay` into a profile outcome, a remote
command, or a skill action list has reopened the path this contract closes.

After migration none of the three names appears in a profile, a skill's Tier D
declaration, or the safety registry. They survive only as the runtime's
internal executor names behind the outcome resolver, which selects a coil state
through the zone's commissioned mapping and never through the name.

**Retained skills keep their Tier A through C intelligence intact.** The
migrated skills continue to observe the same sensors, keep their diagnosis and
alerting triggers, and lose only the Tier D declaration and its action list.
Until each profile is active on a device, the corresponding first-party trigger
remains a valid `skills-package/v2` declaration; `skills-package/v3` refuses
Tier D from every package and is adopted only after this migration completes.

## Consumer Obligations

- Ship the profile set byte-for-byte from [vectors/profiles.json](vectors/profiles.json)
  and pin its digest; refuse to start on any deviation.
- Populate the safety registry only from that set. There is no code path by
  which a skill, a configuration document, a binding, a remote command, or a
  policy adds, removes, or edits an entry, and none by which a `candidate` is
  treated as `ratified`.
- Evaluate active profiles before any skill rule, on every reading for a bound
  `sensor_id`.
- Execute the outcome through the zone's commissioned mapping, looked up at the
  moment of actuation, and record the `binding_seq` in force with every trip.
- Persist trip state durably; reload it at startup; never arm from `tripped`.
- Report, per zone, which profiles are active, which were refused and why, and
  the trip state, on the health surface — without naming any party other than
  the runtime.
- Under hardened posture, refuse to start rather than run with a refused
  eligible zone.

### Golden Vectors

The corpus is [vectors/](vectors/), six files:

| File | Carries |
| --- | --- |
| `profiles.json` | The v1 profile set, normative, vendored by every consumer |
| `profile-load.json` | Profile sets in, `loaded` or `malformed_profile` out — the closed grammar |
| `legacy-actions.json` | The three actuator-specific names, their outcomes, and where each may be commanded from |
| `activation.json` | Accepted zones and posture in, activated profiles and refusals out |
| `evaluation.json` | Profile, zone facts and a reading in, verdict out |
| `lifecycle.json` | Sequences of events in, trip-state transitions and refusals out |

The lifecycle file carries the crash window from both sides — the intent
path, whose restart finds an unresolved intent and loads the pair tripped
with a pending command, and the residual path, whose trip explicitly failed
its intent append so the restart legitimately finds nothing — and the
checker enforces their coherence: a case cannot declare an unresolved
durable intent its own history never appended, nor lose an appended one. It
also carries the conditioned startup command on both terminal states, the
zonal deferral across multiple active profiles, driver refusal retried with
no intervening reading, an accepted command never re-issued for unverified
effect, reset cancelling a scheduled retry, the orphan lifecycle including
its refused early retirement, and durable records outside the vocabulary
refusing to load. The journal protocol itself is vectored: a record
resolving only the intents appended before it, duplicates collapsing to the
latest by append order with the collapse observable through the binding
match, a binding-mismatched intent loading orphaned and never actuated, a
malformed entry failing closed, a legacy tripped record with no command
status loading as retryable rather than accepted, reset's durable clear, an
accepted command whose failed record write is recovered by persistence
alone, and an unreadable journal refusing to load at all. The intent
grammar is vectored field by field — wrong pair, empty attempt id, boolean
sequence, wrong outcome, string timestamp, and a string resolved flag that a
truthiness check would silently honour, each failing closed — with a
repeated attempt id refusing the journal outright; append-order precedence
is vectored from both sides, a newer intent governing over an earlier
record and over a record-then-clear; and the effect axis is vectored so
that acceptance never implies verification and neither verification result
moves the latch.

The activation, evaluation and lifecycle files each carry a `fixtures` list of
ratified profiles that exist only in the corpus. Cases reference profiles by
id, resolved against the file's fixtures and then the shipped set; a case
that would evaluate or arm a `candidate` is itself refused by the checker.

Every refusal and every verdict named in this document has at least one case,
each case is valid in every respect except the one it names, and
`scripts/check-safety-profile-vectors` enforces both, running as a pre-commit
hook and as an explicit workflow step.

| Verdict | Decided at | Cause |
| --- | --- | --- |
| `malformed_profile` | profile load | Closed-grammar violation, unknown kind, unknown status, constraint violation, duplicate `id`; refuses startup in every posture |
| `pending_ratification` | activation | The profile is a `candidate`; reported per zone, never activated, never a startup refusal |
| `unit_mismatch` | activation | Eligible zone's sensor unit differs from the profile's |
| `direction_unsupported` | activation | Eligible zone's sensor direction is not `positive_is_load_draw` |

## Open Questions

- **The overcurrent multiplier is unratified.** `2.0` is chosen for
  equivalence with the shipping trip point and observability on the
  documented sensor, and neither is a safety argument. Ratification needs
  three things this contract does not yet have. **What `rated_capacity_amps`
  is**: a load nameplate rating, a conductor ampacity, a breaker rating, a
  contactor rating, and a permitted continuous current are different safety
  quantities, and the binding's `provenance` vocabulary records what kind of
  claim was made, not which rating limits the circuit. **A validated
  measurement**: the evaluator compares against whatever the adapter reports,
  and the runtime's current path today is an uncalibrated instantaneous sample
  (`ori-runtime` #398); an instantaneous multiplier over an unvalidated window
  is not a trip rule. **A time-current answer**: whether v1 adopts a
  time-current characteristic, or restricts itself to circuits whose
  commissioning evidence shows an instantaneous 2× cutoff is appropriate.
  Changing the value is a change to `profiles.json` and to every consumer's
  pinned digest.
- **Every shipped profile is a candidate.** `electrical.overvoltage.v1` at
  `260.0 V` names no nominal voltage and no tolerance band, and
  `gas.concentration.v1` at `400.0 ppm` names no gas. Each carries the number
  its legacy trigger used and needs its own ratification argument before its
  status flips.
- **Removal of Tier D from `battery_emergency_cutoff` and `cpu_overheating`.**
  Both are recorded above as migrating out of Tier D because neither reaches
  an actuator. That is a change to what two shipping skills claim, and it needs
  ratification before the runtime migration lands.
- **Measurement-loss isolation.** Whether a zone opens its protected circuit
  on sustained measurement loss is a commissioned property of the load. v1
  holds state and alerts. A zone-level declaration would live in the binding
  contract, and the evaluator rule would live here; neither exists yet.
- **Reset procedure.** This contract fixes that reset is local, manual, and
  conditional. The physical procedure — a button, a console command on the
  device, a signed local token — is owned by `ori-runtime` #397 and is not
  specified here.
- **Source transfer as an outcome.** A profile that switches a supply rather
  than isolating a load would need an outcome vocabulary and a commissioned
  mapping shape this contract and the binding contract do not define.
