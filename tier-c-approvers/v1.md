# Tier C Approver Registry v1

> Status: maturity `draft`; compatibility `amendable`; adoption: none
> recorded; proof: end-to-end `none`, HIL `none`, production `none`. Record:
> [status/tier-c-approvers/v1.json](../status/tier-c-approvers/v1.json).

This proposed contract makes the runtime the sole holder of human Tier C
approver credentials. It applies to SMS, WhatsApp and an enrolled LAN
application key and credential-authenticated local-console replies. It is an
**ingress attribution and eligibility check** before an operator reply reaches
the durable admission of
[tier-c-approval/v1](../tier-c-approval/v1.md). It does not change that frozen
contract's authority snapshot, `policy_digest`, dispatch, safe default or
decision states. [offline-tokens/v2](../offline-tokens/v2.md) carries no human
identity and is outside this registry. Tier D never consults the registry.
No runtime or gateway implementation or conformance proof is recorded.

## Authority and state

Only the runtime may add a credential to its own durable registry. The product
may propose a viewing role, issue a LAN **read** pairing grant, or send a
revocation under the existing provisioning anchor; none adds an approver.
The gateway transports requests and replies and never decides eligibility.
A pairing grant, product customer ID, role, gateway HMAC, MQTT PUBACK or
`queued` response is not proof that a human can approve.

The registry belongs to one `(device_id, site_id, identity_epoch)`. `device_id`
is the validated `device.id` from the signed provisioning configuration (or
the host-local development identity in unsigned development posture).
`site_id` is the exact `device.site_id` value in a verified
[runtime-config/v2](../runtime-config/v2.md) provisioning document; it is a
provisioning-authority site identifier, not a customer role or pairing grant.
This PR amends that draft config surface with the optional field; a runtime
cannot enable this registry without a nonempty value. A site change in a
later signed document cannot silently rebind an existing registry: it locks
registry mutation and Tier C admission, and closes open proposals to their
safe default. V1 has no
site-transfer operation; the original signed site binding must be restored or
a separately reviewed site-transfer contract must be adopted. The runtime,
not the product, generates a fresh 128-bit random `identity_epoch` at first setup
and every recovery, encoded as canonical padded RFC 4648 Base64 of its 16 raw
bytes. The runtime generates unique opaque `approver_id` and `credential_id` values from
its own CSPRNG when it creates each candidate challenge, then commits those
exact IDs on success. A product document or LAN caller cannot choose them.
The symbolic approver, credential and challenge IDs in the state-model corpus
are fixtures, not a production ID allocator or challenge wire example. The
separate wire corpus carries canonical challenge bytes. `runtime-config/v2`
supplies only `device_id` and `site_id`; it
supplies neither the epoch nor an approver credential.

The durable header contains `initialized`, `revision` (an integer starting at 1),
`last_external_revision` (starting at 0), and a monotonically increasing
`credential_sequence`. Each active credential records an opaque
`approver_id`, a unique `credential_id`, a channel (`sms`, `whatsapp` or
`lan_ed25519`), its normalized phone number or the raw Ed25519 public key
and its RFC 8410 SubjectPublicKeyInfo DER SHA-256 digest, and its enrolment
sequence. The LAN digest is lowercase hexadecimal SHA-256 over the 12-byte
DER prefix `302a300506032b6570032100` followed by the raw 32-byte key.
The raw key is retained so the runtime can verify later authorizations;
the digest alone cannot verify a signature. Phone values are **only**
canonical E.164 strings matching `^\+[1-9][0-9]{1,14}$`; an ingress adapter
may remove exactly one transport prefix `whatsapp:` before validation, but
must not silently strip punctuation, add a country code or infer one from a
locale. Registration and lookup compare the same canonical value and channel.
The registry cannot make an asserted SMS sender number stronger than the
carrier or webhook authentication that supplied it; see
[runtime #873](https://github.com/ori-platform/ori-runtime/issues/873).
Removed credentials retain durable tombstones identifying the exact credential
and epoch; removal never recycles an ID or value **within that epoch**. The
runtime refuses duplicate active values under different IDs. Recovery after
total registry loss cannot recover tombstone bytes that were lost; it creates
a new identity epoch instead, so old epoch credentials and revocation documents
cannot authenticate or apply. Any credential added afterward is a fresh local
site act, not restoration by a provisioning document.
An empty registry, or no active credential for a channel, admits no reply
on that channel.

The runtime must commit the registry header, entries, tombstones, revision and
the operation result atomically. It serializes enrolment, revocation and
approval admission against the same registry state. Failure to read or commit
that state refuses a reply; it never falls back to provisioning contacts,
product roles, a gateway copy or an empty-registry default.
The current runtime's permissive phone-number stripping is not conformance to
the E.164 rule here; its ingress and configuration consumers must change
before any adoption claim.

## Bootstrap and recovery

For each bootstrap, recovery, local first-approver or enrolment attempt, the
runtime creates and durably records a fresh 128-bit random, single-use
challenge bound to its
device, site, identity epoch, operation and exact candidate credentials. The
challenge has exactly these Profile 2 JSON members: `v` (integer `1`),
`challenge_id` (canonical padded Base64 of 16 random bytes), `device_id`,
`site_id`, `identity_epoch`, `operation` (`bootstrap`, `recover`, `local_seed`
or `enrol`), `registry_revision` (nonnegative integer), and `candidates`
(array sorted by `credential_id`, with no duplicate IDs or values). For
`recover` it is empty; for `enrol` and `local_seed` it has exactly one member;
for `bootstrap` it is empty. Each candidate has exactly
`approver_id`, `credential_id`, `channel` (`sms`, `whatsapp` or
`lan_ed25519`), and `value`: canonical E.164 for phone channels, or
`ed25519:` followed by canonical padded Base64 of the 32-byte raw Ed25519
public key for LAN. `approver_id` and `credential_id` are nonempty ASCII
strings of at most 64 characters from `[A-Za-z0-9._-]`. `device_id`,
`site_id` matches `^[A-Za-z0-9._-]{1,64}$` and is compared byte-for-byte with
the verified config; `identity_epoch` is the runtime-minted canonical padded
Base64 value above. Neither is normalized or truncated. The runtime stores
the canonical challenge bytes and its monotonic deadline. Unexpected fields,
duplicate JSON members, wrong types,
oversize values and noncanonical Base64 are malformed.

It accepts a physical-control transition only during the challenge's
60-second monotonic window. A challenge presented for an operation is marked
used even when that operation is refused; refusal changes no credential,
proposal or registry revision. Successful consumption, credential addition
and revision increment commit atomically.
The challenge is invalidated at process restart; a persisted challenge does
not regain a monotonic deadline. An expired, reused or changed challenge or
candidate is refused without changing credential eligibility. The registry
revision must still
equal the challenge's revision when the operation commits; otherwise a fresh
challenge is required.
The authenticated local operator request and physical event are distinct
checks; one never stands in for the other.

First setup commits an **empty** initialized registry only. At challenge
issue the runtime reads the verified `device.site_id` and mints a prospective
epoch; a refused challenge never makes that epoch active. The runtime verifies
the signed provisioning document, `device.id` and `device.site_id` in
production, and requires both an authenticated runtime-local operator request
and challenge-bound physical presence before committing `initialized = true`
with the site and epoch bindings.
`actions.operator_contact` and `actions.secondary_contact` are legacy
notification destinations, not approver nominations; the runtime must not
copy them into this registry. The local operator then uses `local_seed` below
to establish the first LAN approver. This avoids granting approval to a
mistyped or reassigned phone number without proving its possession. An
unsigned development configuration with a locally supplied `device.site_id`
may initialize an empty registry and use `local_seed`, but cannot supply a
revocation. Production posture requires a
verified signed configuration. A remote API, gateway message or product login
cannot confirm first setup.

An absent, corrupt or unreadable registry is **locked**, not uninitialized.
The runtime never auto-seeds from a provisioning document at startup, restore
or reinstall. First setup and recovery are explicit local operations, each
requiring its own authenticated local request and physical presence event.
Recovery after prior state loss additionally requires a locally confirmed,
runtime-generated replacement of the device identity epoch and invalidates
all old credentials; it cannot be invoked by
backend account recovery or an old provisioning document alone. If the
runtime cannot establish whether it is first setup, it requires the recovery
path. This rule applies even when every registry byte has been lost.
An updated provisioning document after initialization cannot add or restore a
credential or clear a surviving tombstone.

An initialized registry with **zero active credentials** may accept
`local_seed` for exactly one new `lan_ed25519` credential with a new
`approver_id` and `credential_id`. This is the sole no-existing-approver path
after an empty bootstrap, recovery or revocation of all approvers. It requires
an authenticated local operator request, a fresh operation-bound physical
presence event and the candidate key's possession signature defined below.
The runtime commits the consumed challenge, key and revision atomically. It
refuses `local_seed` while any credential is active, when the registry is
locked, or for an ID or value tombstoned in the current epoch. It never reuses
an old identity epoch or clears a surviving tombstone. The locally seeded LAN
approver may then enrol phone credentials through the ordinary
existing-approver path, including the candidate possession proof below. Sites
unable to present a LAN key and the qualified physical input remain at the non-actuating
Tier C safe default; a backend must not fill that gap.

Distinguishing a genuine first install from total state loss requires a
one-time installation marker outside the registry's failure domain. If that
marker is absent or unreadable, history is **unknown** and bootstrap is
refused; only the local recovery path may proceed. The marker must not be
created or reset by a product-signed document or gateway message. The target
hardware, its anti-rollback property and the authenticated recovery procedure
have not been selected or demonstrated. This is a ratification blocker, not an
implementation detail to be guessed by a consumer.

## Site enrolment

For enrolment, an existing active approver must authorize the exact pending
challenge using a credential already enrolled **before** challenge creation.
The LAN authorization object has exactly `v: 1`, `challenge_id`,
`challenge_sha256` (lowercase hex SHA-256 of the runtime-stored canonical
challenge), `authorizer_credential_id`, and `signature` (canonical padded
Base64 of 64 bytes). The authorizer signs ASCII
`ori.tier_c_approver.enrol.v1`, one NUL byte, then Profile 2 canonical JSON
of that object without `signature`. A phone-channel authorizer sends exactly
three ASCII tokens through its already authenticated channel:
`ORI-ENROL-V1`, the `challenge_id`, and the `challenge_sha256`, separated by
one space with no trailing whitespace. Its attributed sender must map to an
active credential that predates challenge creation, and the challenge must
still be
pending. Neither a typed number nor the text alone authenticates the sender.

The candidate LAN possession object has exactly `v: 1`, `challenge_id`,
`challenge_sha256`, `candidate_credential_id`, and `signature`, with the same
field types and encoding. It signs ASCII
`ori.tier_c_approver.possession.v1`, one NUL byte, then canonical JSON
without `signature` under the candidate public key in the challenge. It is
required for `enrol` or `local_seed` of a LAN key; a phone candidate has no
Ed25519 possession proof. The runtime matches every ID and digest to its
pending challenge before verifying.

A phone candidate instead proves control through its **own** channel. At
challenge issue the runtime generates an independent 128-bit random code,
sends `ORI-POSSESS-V1 <challenge_id> <code>` to the candidate's canonical
E.164 value on the declared `sms` or `whatsapp` channel, and stores only a
SHA-256 digest of the code with the challenge. `<code>` is canonical padded
RFC 4648 Base64 of the 16 random bytes; tokens have one ASCII space between
them and no trailing whitespace. The code is never returned in the challenge,
local operator response, log or gateway disclosure. Before committing
enrolment, the runtime must receive that exact text **from the candidate value
on the same authenticated channel** within the challenge's 60-second window.
It compares the code digest in constant time and binds sender, channel,
challenge and candidate to the pending operation. No reply, an unauthenticated
reply, a wrong code, wrong sender, wrong channel, expired challenge or reuse refuses without adding
a credential. An attempted commit consumes the challenge. The sender
assertion remains only as strong as the channel authenticator. The
deterministic corpus uses a published code solely for test vectors; runtime
codes must use a CSPRNG.

All three Ed25519 uses in this contract
(authorizer, candidate and external revocation) apply
[ed25519-key-admission/v1](../ed25519-key-admission/v1.md) and
[ed25519-verification/v1](../ed25519-verification/v1.md), with this contract's
`signature_invalid` refusal for any failure. These forms and their signed
preimages appear in the vector corpus. Gateway transport never supplies the
authorizer identity.

The runtime also requires a fresh, authenticated request through its local
operator path and a separate physical presence event for this challenge and
exact candidate. The v1-qualified presence event is a transition on a
commissioned, directly wired local control input observed by the runtime
within the challenge's monotonic window. The runtime binds the event to the
pending challenge before consuming it. A remote shell, local Unix socket,
gateway message, photograph, static code or product login is not a presence
event. A site without such an input cannot enrol or recover approvers under
v1; it must not substitute a weaker proof. This requirement needs hardware
and runtime feasibility review before ratification.

The runtime commits consumption of the challenge, the new credential and
the incremented registry revision in one transaction. Missing authorizer,
missing or invalid possession proof, missing local request or presence event, expiry,
changed candidate or a reused challenge refuses with no credential or
registry-revision change. The failed presentation consumes its challenge;
if that used marker cannot be committed, the runtime locks that challenge
state and refuses further attempts until a fresh state can be established.
An enrolled credential cannot authorize itself into existence. A replacement
key is a new credential ID and sequence; it never inherits an old key's
eligibility. The concrete local operator transport is the authenticated
runtime service boundary of [operator-socket/v2](../operator-socket/v2.md).
That socket authenticates the operator process only; it does not itself prove
presence.

## External revocation only

The product may issue a **removal-only** document under the current
**runtime configuration-signature provisioning anchor**, as fixed by
[runtime-config-orchestration/v1](../runtime-config-orchestration/v1.md) and
read from `ORI_CONFIG_TRUST_ANCHOR_PUBLIC_KEY_B64` (or the host-level
`ORI_CONFIG_TRUST_ANCHOR_ENV` override, never from a signed document).
This is the config-signature key, **not** the per-device key named a
provisioning anchor by firmware telemetry. If the current anchor is missing,
unusable or collides with another anchor, or the runtime is in unsigned
development posture without a verified config anchor, revocation is refused;
it does not fall back to a document key or accept unsigned removal. The
previous provisioning anchor is verify-only and cannot author new revocations.

The revocation's exact signed Profile 2 JSON object has `v: 1`,
`device_id`, `site_id`, `identity_epoch`, `revision` (positive integer),
`targets` (nonempty sorted unique array of at most 32 strings of the form
`credential:<credential_id>` or `approver:<approver_id>`),
`signing_key` (`ed25519:` plus canonical padded Base64 of the raw 32-byte
public key), and `signature` (canonical RFC 4648 padded Base64 Ed25519).
The preimage is ASCII `ori.tier_c_approver.revoke.v1`, one NUL byte, then
canonical JSON without `signature`. Unknown, duplicate or wrong-type
members are malformed. The runtime selects `signing_key` by byte comparison
across configured anchors, verifies the signature, then accepts only the
current provisioning class; a previous key is `superseded_signer` and another
class is `wrong_authority`. The document cannot select an anchor location.
It never contains an add, replacement, role or whole-list field.
The anchor-wide selection and previous-key behavior are design targets in
runtime-config-orchestration/v1; the current runtime has not been shown to
enforce them for this new document.

The proposed delivery path is an authenticated **local operator socket**
request. Its exact JSON object has `operation: "approver_registry_revoke"` and
`document` (the signed object above), and no other members. The entire UTF-8
request is limited to 16,384 bytes before parsing; excess bytes refuse before
parsing, and duplicate JSON members or concurrent requests refuse before state
change. The runtime
serializes one in-flight revocation per device with registry admission. A
successful response has exactly `status: "revoked"`, `registry_revision`
(positive integer) and `last_external_revision` (the document's revision); an
idempotent repeat returns `status: "replayed"` and the unchanged two revisions.
Other refusal codes are the named revocation verdicts in this section. The
proposed authenticated local readback request has exactly
`operation: "approver_registry_binding"`; its response has exactly the current
`device_id`, `site_id`, `identity_epoch` and `registry_revision`, or
`registry_unavailable` when locked. The socket authenticates and authorizes
the local operator using kernel peer credentials before either operation
reads or changes registry state. The product can issue a document for a
binding learned during a physically local visit, but a
gateway, MQTT topic, product login or provisioning-config update cannot submit
it. `operator-socket/v2` currently rejects every operation except its two
named ones, so a successor operator-socket contract and runtime consumer must
adopt these request/response shapes before this path works. This draft grants
no existing socket a new operation. A future remote path would need its own authenticated epoch
disclosure, topic, payload bound and rate under `gateway-api/v2`; until then
remote revocation is unavailable.

After recovery, the runtime has minted a new epoch. It may reveal the current
`device_id`, `site_id` and `identity_epoch` only to an authenticated local
operator over that same future socket contract; the operator may carry the
binding to the product to request a signed local-delivery document. The
product has no authenticated automatic disclosure today, so it cannot address
a remote revocation in the new epoch. The local operator's authenticated
session is not a runtime attestation to the product; that separate trust path
remains an adoption blocker. Old-epoch revocations refuse closed.

The runtime checks the exact device, site and epoch before any state change.
An external revision greater than `last_external_revision` atomically
tombstones its targets, increments registry revision and records the new
external revision. An `approver:` target atomically removes every active
credential belonging to that approver and permanently tombstones the
approver ID; a subsequent enrolment may not reuse that ID. A `credential:`
target removes only that credential. A repeat of the same parsed document
after Profile 2 canonicalization is idempotent, including when JSON source
whitespace or key order differs. The runtime fingerprints canonical JSON of
the **entire** signed object, including `signature`, so a same-revision object
with different signed members or signature is `revision_conflict`; a lower
revision is `revision_regressed`. Both refuse
without changes. A target already tombstoned remains tombstoned; an approver
or credential never enrolled is `unknown_target`, not an invitation to create
an entry. A document with one unknown target refuses atomically; it must not
partially revoke its other targets. This avoids an unauditable partial result.
The runtime cannot infer a regrant from a later provisioning document.

## Proposal cutoff and admission

When a Tier C proposal opens, the runtime records its current
`credential_sequence` and `identity_epoch` as an **eligibility cutoff**
alongside the proposal. That value is registry state, not an extra member of
the frozen authority
snapshot. An enrolment committed later has a higher sequence and cannot
answer that proposal, even if it names the same human, phone or replacement
key. The runtime verifies the channel's existing ingress authenticator,
maps its exact credential to one active registry entry, and checks that
entry's sequence is at or below the proposal cutoff.
An epoch mismatch refuses admission. Recovery closes every open proposal
before making its new epoch visible; it cannot carry an old cutoff across
identity recovery. A process restart already aborts open proposals under
the frozen Tier C contract.

At durable approval admission the runtime repeats that mapping and check
inside the transaction serialized with registry changes. If revocation
commits first, the reply is refused. If approval commits first, that approval
remains valid; later revocation does not undo or replay it. The decision
records the exact `credential_id`, `identity_epoch` and registry revision
used. A reply's signed application key or authenticated phone identity must
match the registered credential; a product customer ID is advisory only.
A `no` reply is a refusal, not approval. All other Tier C checks and the
durable commit remain governed by tier-c-approval/v1.
The local console is a transport, not a credential. Its Tier C reply must
present a signed reply from an active registered `lan_ed25519` key and pass this
same cutoff and admission check. If its current path cannot do that, it
refuses; an empty registry never treats a local-console button press as an
approver. Offline tokens remain the separate frozen-contract exception and
carry no human registry identity.
The signed LAN reply format and its site transport belong to the open
[lan-app-api/v1 PR #344](https://github.com/ori-platform/ori-specs/pull/344).
Until that contract lands and the runtime consumes it, a freshly seeded or
recovered site has no working Tier C human-approval path; it remains at the
non-actuating safe default. This draft's state-model approval result is not
evidence of a LAN reply implementation.

## LAN disclosure and offline operation

An enrolled LAN key authenticates directly to the site. It may renew its
site-local session without a product backend or internet connection; a read
pairing grant neither enrolls the key nor substitutes for this check.
For each proposal read, the gateway sends the presented key's exact SPKI
digest and requested proposal scope to the local runtime. The runtime
checks the current registry for that request and answers allow or deny.
The gateway caches no eligibility; absent, invalid or timed-out replies
refuse disclosure. The MQTT request/response, bounds and timeout vector
belong in [gateway-api/v2](../gateway-api/v2.md) with the proposed
[lan-app-api/v1 PR](https://github.com/ori-platform/ori-specs/pull/344) after
this registry contract is reviewed. This contract grants no gateway authority
to infer eligibility.

## Migration constraints

An existing deployment has no registry and therefore cannot claim this
contract merely by upgrading the runtime. Production enablement first
requires a verified `runtime-config/v2` document with `device.site_id` and a
consumer that enforces the signed field; the current v1 config path is not
sufficient. Enabling the registry also requires an explicit
site visit for locally confirmed bootstrap or recovery and `local_seed`;
the runtime must not copy current provisioning contacts into the registry.
Each phone candidate then needs its own channel possession exchange. Pending
Tier C proposals close to the frozen non-actuating safe default while identity
is unavailable. A local console that cannot present a signed enrolled key
cannot approve Tier C under
v1. Tier D behavior is unchanged. These are rollout requirements, not evidence
that any installer or runtime currently enforces them.

## Required vectors and proof limit

[vectors/transitions.json](vectors/transitions.json) exercises first setup,
blocked reseeding, explicit recovery, enrolment and proof failures, external
revision and tombstone behavior, proposal cutoff, replacement keys and both
revocation/admission race orders. The deterministic generator and independent
checker are `scripts/generate-tier-c-approver-vectors` and
`scripts/check-tier-c-approver-vectors`. These are state-model fixtures,
not evidence that a runtime store, authenticated local operator path,
channel authenticator, MQTT transport or physical site implements the rules.
The checker verifies ordinary signatures; it does not exercise the full
ed25519-verification/v1 adversarial corpus for each channel consumer.
Independent runtime and gateway consumer tests are required before a
conformance claim.
