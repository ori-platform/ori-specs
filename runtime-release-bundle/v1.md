# Runtime Release Bundle Contract v1

> Status: Design Target
>
> Intended consumers: `ori-runtime` release automation and Linux installers.

This contract defines how an Ori Runtime release is packaged, authenticated,
installed, upgraded, verified, and removed on supported Linux systems. It makes
installation convenient without weakening the offline, hash-locked
supply-chain posture.

## Security boundary and verification order

The release bundle is untrusted until its detached signature, byte length, and
digest have all been verified. Before verification succeeds, an installer MUST
NOT extract or import bundle contents, execute a bundle file, change an Ori
environment or configuration, alter a service, or install from the bundle.
Downloading into a new mode `0700` temporary directory is not installation.

The release-bundle key is a dedicated authority. Implementations MUST NOT
accept skill, config, firmware, gateway, remote-command, or evidence keys as
release-bundle authority, even when they use Ed25519.

## Bootstrap trust

The convenience command:

```sh
curl -fsSL https://github.com/ori-platform/ori-runtime/releases/latest/download/install-linux.sh | bash
```

trusts the HTTPS origin and GitHub release delivery for the bootstrap script.
An embedded public key authenticates the bundle; it cannot retroactively
authenticate the script containing that key. Documentation MUST state this
limitation and provide a high-assurance path that pins an installer version and
checks its digest against an independently obtained release record.

A piped interactive install reads from `/dev/tty`. If no terminal exists it
MUST fail with instructions for unattended mode or for downloading the script
first. It MUST NOT silently choose security-relevant defaults.

## Published release set

Each target publishes these files atomically under an immutable version tag:

```text
ori-runtime-<version>-<target>.tar.gz
ori-runtime-<version>-<target>.signature.json
ori-runtime-<version>-<target>.sha256
install-linux.sh
install-linux.sh.sha256
```

`latest` MAY redirect to an immutable tag. Audit output reports the resolved
version and exact digest, never `latest`.

The v1 targets are:

```text
linux-x86_64-python3.11
linux-x86_64-python3.12
linux-x86_64-python3.13
linux-aarch64-python3.11
linux-aarch64-python3.12
linux-aarch64-python3.13
```

An implementation MAY publish a subset, but cross-target fallback is forbidden.

The set is additive. A consumer written against an earlier reading of this
contract refuses a target it does not know, which is the correct direction: it
declines an artifact rather than installing one it cannot reason about. A
producer that publishes a target absent from this list is the error, because a
conforming consumer will reject it as `unsupported_target` and the artifact
becomes unusable by anything that follows the contract.

## Bundle layout and archive safety

The archive contains one top-level directory:

```text
ori-runtime-<version>-<target>/
  BUNDLE-MANIFEST.json
  wheelhouse/
    requirements.txt
    requirements-pi.txt        # target-specific; optional
    *.whl
  templates/
    ori.linux.yaml.example
  systemd/
    ori-runtime.service
```

The archive MUST contain only regular files and directories. Absolute paths,
`..` traversal, duplicate or case-colliding paths, links, devices, FIFOs,
sockets, and setuid/setgid files are forbidden. The installer validates the
complete member table before extracting into a new mode `0700` directory on the
destination filesystem.

`BUNDLE-MANIFEST.json` is strict JSON; duplicate and unknown fields fail. Its
shape is:

```json
{
  "files": {"wheelhouse/example.whl": "sha256:<64-lowercase-hex>"},
  "python": "3.12",
  "runtime_version": "2.3.0",
  "schema": "ori.runtime_release_bundle_manifest.v1",
  "target": "linux-x86_64-python3.12"
}
```

`files` enumerates every regular file except the manifest exactly once. After
safe extraction, the installer verifies the exact file set and every digest
before using any file.

## Detached signature envelope

The detached envelope is strict JSON with exactly these fields:

```json
{
  "artifact": "ori-runtime-2.3.0-linux-x86_64-python3.12.tar.gz",
  "artifact_sha256": "sha256:<64-lowercase-hex>",
  "artifact_size": 123456,
  "key_id": "ori-runtime-release-2026-01",
  "runtime_version": "2.3.0",
  "schema": "ori.runtime_release_bundle_signature.v1",
  "signature": "ed25519:<standard-padded-base64>",
  "target": "linux-x86_64-python3.12"
}
```

The signed message is canonical JSON of the envelope with `signature` removed,
prefixed by this ASCII domain separator and NUL byte:

```text
ori.runtime_release_bundle_signature.v1\0<canonical-json-bytes>
```

Canonical JSON has recursively sorted keys, compact separators, UTF-8,
unescaped Unicode, and finite JSON values only. Ed25519 keys are raw 32-byte
public keys and signatures are raw 64-byte values encoded in standard padded
base64 with the exact `ed25519:` prefix.

The installer MUST resolve `key_id` from its local purpose-bound key registry,
verify the signature, stream-check artifact size and SHA-256 in constant memory,
and require artifact filename, requested version, detected target, and envelope
fields to agree before inspecting the archive. Unknown, revoked, malformed, and
wrong-purpose keys fail closed. The `.sha256` file is a convenience corruption
check, not an authenticity mechanism.

## Key lifecycle

- Private keys exist only in the approved release-signing system. They are not
  committed, stored in ordinary CI variables, logged, or exposed to PR jobs.
- Normal CI builds unsigned candidates. Only a protected immutable-tag release
  job after required checks pass may request signing.
- Bundles name a known `key_id`; they cannot supply public-key bytes.
- Rotation adds a reviewed public key before releases depend on it. Previous
  keys are verify-only for a documented bounded window.
- Revoked keys fail closed. Offline installers cannot learn new revocations;
  current revocation assurance requires refreshing bootstrap trust through a
  trusted channel or managed provisioning.
- Threshold or delegated signing is outside v1.

The pinned key registry is strict JSON shipped with or embedded into the
reviewed installer, never loaded from `ori.yaml`, a bundle, or an environment
variable:

```json
{
  "keys": [
    {
      "key_id": "ori-runtime-release-2026-01",
      "public_key_b64": "aDlW3MqinQM8y96szEqNske2ytKkxbmMDl87CuLbAQ8=",
      "purpose": "runtime_release_bundle",
      "status": "active"
    }
  ],
  "schema": "ori.runtime_release_keys.v1"
}
```

The registry and every key entry reject duplicate or unknown fields. `key_id`
values are unique. `purpose` is exactly `runtime_release_bundle`; accepted
statuses are `active`, `verify_only`, and `revoked`. Both `active` and
`verify_only` keys may verify existing releases; `revoked` keys fail closed.
Only `active` keys may sign new releases. A signature envelope names a key but
cannot add key bytes or change registry status.

The active v1 verification key was generated non-exportably in AWS KMS during
the approved release-key ceremony on 2026-08-11. Its identity is:

| Field | Value |
| --- | --- |
| Key ID | `ori-runtime-release-2026-01` |
| Public key encoding | Standard padded Base64 of the raw 32-byte Ed25519 key |
| Public key | `aDlW3MqinQM8y96szEqNske2ytKkxbmMDl87CuLbAQ8=` |
| Raw public-key SHA-256 | `d4f44308d60fb78a33f709eebc85271f2b8c0d4e59e50bb77bf08f5864918c90` |
| KMS key spec and usage | `ECC_NIST_EDWARDS25519`, `SIGN_VERIFY` |
| Signing profile | `ED25519_SHA_512`, `MessageType=RAW` |

The public key was retrieved from and confirmed against the exact KMS key ID
during the ceremony. The private key remains non-exportable. Registry status
`active` means that installers accept signatures from this key and approved
release infrastructure may use it for new signatures; it does not establish
that production release publication controls are complete. Least-privilege
signer delegation, durable KMS audit logging, named emergency ownership,
short-lived CI federation, and protected immutable release publication remain
separate operational gates.

## Offline installation

The installer creates an isolated environment under `${HOME}/.local/ori` or
`/opt/ori`. Dependencies are installed only with:

```text
--no-index --find-links <verified-wheelhouse> --require-hashes
```

The exact Runtime wheel is then installed with `--no-deps`. Network package
resolution, editable installs, unpinned package names, and registry fallback
are forbidden. Installed and signed versions MUST match.

## Host prerequisites

An installation MAY require operating-system packages the host does not have.
The installer MAY offer to install them, subject to all of the following.

Prerequisite installation MUST NOT begin until the release bundle has been
authenticated and, in interactive mode, until the operator has confirmed the
collected identity. A run rejected at either point MUST leave host packages
untouched.

Candidate packages MUST come from a fixed allowlist and MUST be passed as an
argument vector, never through a shell. Operating-system components on which
unrelated software depends — at minimum the init system, the system Python, and
the system shell — MUST NOT be candidates. No step here may resolve Python
packages: runtime dependencies come only from the verified wheelhouse under
`## Offline installation`.

The operator MUST be shown the exact packages and the exact command before
being asked, and the default answer MUST be negative. Declining, cancelling,
insufficient privilege, and an unrecognised distribution are all equivalent:
the host is left unmodified and the installation stops with
`prerequisite_install_failed` and the remediation command. Declining MUST NOT
be interpreted as consent to continue without the prerequisite.

Unattended mode MUST NOT prompt and MUST NOT modify host packages. It fails
with `prerequisite_install_failed` and the remediation command.

A package-manager failure MUST stop the installation with
`prerequisite_install_failed`. Packages installed before that failure are NOT
rolled back, because removing them could break unrelated software; the failure
detail MUST state that the host may be partially modified.

After a successful package-manager run the installer MUST re-check the
capability. A zero exit status is not evidence that the requirement is now
satisfied for the interpreter that will use it.

## Configuration

Interactive and unattended paths generate from the verified template and call
the installed bridge's `config validate --path <candidate>` before atomically
replacing a mode `0600` active config. Failure preserves the prior config.

Unattended mode requires explicit device id, name, location, and timezone. It
does not infer production posture or synthesize secrets. Secrets use environment
references and a separate mode `0600` file. Optional model download is a
separate authenticated artifact operation with an expected digest; failure
cannot leave configuration selecting a missing model.

## Service lifecycle

User installs use a systemd user unit; system installs use a system unit. Units
use absolute paths, an explicit working directory and config, an unprivileged
identity, `Restart=on-failure` with bounded delay, and no shell interpretation.
The runtime never runs as root. Service flags MUST NOT disable Tier D behavior.

User-unit documentation explains `loginctl enable-linger`. The installer reports
whether boot startup is actually enabled and does not claim persistence when
linger is absent.

## Transaction, rollback, and removal

Installations use versioned directories and an atomic active pointer:

```text
<root>/releases/<version>/
<root>/current -> releases/<version>
```

A new release is built and validated without changing `current`. After the
atomic switch, the service restarts and health is checked. Failure restores and
restarts the prior release and reports both failure and rollback outcome. A
failed first install leaves no enabled broken unit.

Reinstalling the same verified version is idempotent. Downgrades require
`--allow-downgrade` and interactive confirmation when interactive.
`--uninstall` removes units and environments but retains config, secrets, state,
and logs. Data removal requires a separate explicit flag and confirmation. All
deletion targets are resolved and proven beneath the install root.

## Post-install verification

The installer waits a bounded time for the configured Unix socket and invokes:

```text
health snapshot --socket <configured-path>
```

Success requires bridge exit zero, the expected bridge schema, and non-critical
health. Output includes version, artifact digest, service state, socket path,
and health outcome without secrets. Failure exits non-zero after rollback with
exact diagnostic commands. Success points to `ori doctor` without requiring
`ori-cli` at install time.

## Release automation

Release automation triggers only from an immutable version tag matching project
version; uses least privilege, no dependency cache, hash-locked tools, and
pinned action SHAs; builds in matching trusted environments; and runs normal
tests, workflow, license, capability-matrix, package-smoke, and installer
negative tests before signing. PR code never accesses signing authority.

The final exact artifacts are signed only after content is fixed. Bundle,
signature, checksum, installer, and installer checksum publish as one set, then
are downloaded and verified again before the release is declared usable.

## Required negative tests

Tests MUST cover missing, malformed, unknown-key, wrong-purpose, and invalid
signatures; byte mutation; digest, size, version, and target mismatch; skill or
config cross-profile signatures; truncation; duplicate JSON keys; traversal,
absolute paths, links, special files, duplicate paths, undeclared or missing
files, and post-extraction mismatch; live package resolution attempts; invalid
config and secret leakage; service and health failures; rollback failure;
reinstallation; downgrade; uninstall retention; and guarded data removal.

## Stable error identifiers

These identifiers are exhaustive for v1 failure conditions. Service lifecycle
failures use `service_start_failed` for compatibility even when the failed
operation is stop, disable, or restart; the accompanying detail MUST identify
the exact operation that failed.

| Condition | Error |
| --- | --- |
| malformed requested release version | `invalid_release_version` |
| unsupported platform | `unsupported_target` |
| unknown or revoked key | `untrusted_release_key` |
| unavailable Ed25519 backend | `crypto_unavailable` |
| malformed envelope | `invalid_signature_envelope` |
| failed signature | `signature_verification_failed` |
| release signing failure | `signing_failed` |
| artifact mismatch | `artifact_integrity_mismatch` |
| unsafe archive | `unsafe_bundle_archive` |
| manifest mismatch | `bundle_manifest_mismatch` |
| unsafe install root, active pointer, or deletion target | `unsafe_install_root` |
| downgrade attempted without explicit authorization | `downgrade_forbidden` |
| offline dependency failure | `offline_install_failed` |
| config validation failure | `config_validation_failed` |
| missing host prerequisite not installed | `prerequisite_install_failed` |
| service failure | `service_start_failed` |
| health failure | `post_install_health_failed` |
| rollback failure | `rollback_failed` |

Verification and rollback failures are errors, never warnings.

## Non-goals

- Android/Termux provisioning.
- Firmware flashing or sealed-flash provisioning.
- `.deb` or `.rpm` packages.
- Installing or requiring `ori-cli`.
- Moving runtime policy, action-tier, or physical authority into the installer.
