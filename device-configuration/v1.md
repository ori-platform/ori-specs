# Device Configuration Contract v1

> Status: Contract target. No implementation is claimed until the
> implementing repositories cite this contract from a tagged release.

This contract defines authenticated management of a firmware device's
**attested configuration**: values the device enforces against later
authenticated messages, which therefore have to be commissioned rather than
asserted.

A capability manifest describes device state. It is evidence, not a write
mechanism — a device signing a manifest proves what it believes about itself,
not that anyone was authorised to make it believe that. This contract is the
missing half: it defines who may change attested configuration, over what
signed wire operation, with what persistence and failure behaviour, and how the
resulting manifest transition is ordered.

The v1 configuration surface is exactly one value, the deployment maintenance
limit. The grammar admits further values only as additive contract changes.

## Scope And Trust Model

The trust root is the **provisioning-authority Ed25519 key** — the same key
that authorises the Layer 1 approval in
[firmware-commands/v1.md](../firmware-commands/v1.md) and the requests in
[firmware-mqtt-provisioning/v1.md](../firmware-mqtt-provisioning/v1.md). This
contract introduces no new fleet authority.

**The runtime command key is explicitly not sufficient.** The deployment
maintenance limit bounds how long a runtime may suppress the Local Interlock;
a runtime able to raise its own suppression ceiling would make the limit
decorative. The separation is the entire mechanism, not a defence in depth.

This contract grants no physical-action authority and no evidence authority.
It changes values the device consults; it never actuates anything.

## Relationship To Neighbouring Contracts

| Contract | Owns |
| --- | --- |
| This contract | Who may change attested configuration, and the signed operation that does it |
| [firmware-telemetry/v1.md](../firmware-telemetry/v1.md) | The manifest that carries the resulting value, and its hash |
| [firmware-commands/v1.md](../firmware-commands/v1.md) | What the value bounds, and the capability-transition lifecycle a change triggers |
| [device-provisioning/v1.md](../device-provisioning/v1.md) | Anchor lifecycle — registration, epochs, rotation, revocation |

Anchor lifecycle is not device configuration, which is why the maintenance
limit is not a provisioning field. Provisioning establishes *who the device
is*; this contract sets *what it has been commissioned to permit*.

## Actor And Reason

Every request carries `actor` and `reason`, with the meanings, bounds, and
operator-authentication obligation defined in
[firmware-mqtt-provisioning/v1.md](../firmware-mqtt-provisioning/v1.md#actor-and-reason).
Firmware verifies the provisioning-authority signature over both; it does not
authenticate `actor` through a second credential.

Changing a limit on interlock suppression is a safety-relevant act. An audit
trail naming who requested it and why is not optional. Both fields are
structurally required, so a request missing or violating either is `malformed`
and is rejected before signature verification — there is no separate
audit-specific verdict, because the parser cannot distinguish an omitted field
from any other shape violation.

## Configuration Freshness

`config_seq` is a strictly increasing positive integer per `device_id`.

- It is distinct from telemetry `(boot_id, seq)`, command `cmd_seq`, and
  transport-provisioning `provision_seq`. A shared counter would let one
  contract's traffic advance another's replay window, and would make an
  operator's configuration work invalidate a transport request already in
  flight under the same key.
- It is within `1 .. 2^53 - 1`, canonical decimal, no sign and no leading
  zeros.
- Its high-water mark persists across reboot, Layer 1 re-approval, device-key
  rotation, command-key rotation, MQTT certificate replacement, transport
  revocation, and Layer 1 revocation and reinstatement.
- Gaps are valid. A repeated or lower value is `replayed`.
- Malformed, wrong-device, bad-signature, wrong-epoch, and replayed requests do
  not consume it.

Once grammar, device binding, provisioning-authority signature, active approved
epoch, and freshness all pass, the request is **spent before any state
changes** — including before refusals that depend on device policy. A request
that reached this point is authenticated, device-bound, epoch-bound and fresh;
whether the device then declines it is a matter of local state the signer could
not have known, and returning the sequence to the pool would let that same
signed bytes be replayed until local state happened to permit it.

A crash after the mark is durable and before the value is written loses the
operation but cannot leave it replayable. The provisioner retries with a higher
`config_seq`.

## Signature And Canonical Grammar

All signatures use `ed25519:<standard-base64-64-byte-signature>`.

Requests have one outer form:

```json
{"request":{"...":"request fields"},"signature":"ed25519:<base64-64-byte-signature>"}
```

The provisioning authority signs the exact canonical UTF-8 bytes of the
`request` object, excluding the outer wrapper and `signature`.

Rules shared by every request and result:

- the two request shapes below are exhaustive: a `kind` outside them, or a
  field set that does not match the named `kind` exactly, is `malformed`;
- object fields appear in the exact lexicographic order shown;
- there is no whitespace outside string values;
- duplicate, reordered, missing, unknown, or extra fields are `malformed`;
- `v` is the integer `1`;
- identifiers use `[A-Za-z0-9._-]`;
- integers are canonical decimal, no sign and no leading zeros;
- `anchor_epoch_id` and every hash are `sha256:` plus exactly 64 lowercase hex
  characters.

Any deviation is `malformed` and is rejected before signature verification is
attempted. **Every structural requirement in this section yields exactly
`malformed`** — including a missing, empty, or over-long `actor` or `reason`,
and including an unrecognised `kind`. There is no second verdict for a request
the parser could not accept, because a request the parser could not accept was
never attributable to anyone: its signature covers bytes whose meaning the
device could not determine.

The grammar therefore bounds *shape*, never *policy*. It accepts any canonical
`deployment_maintenance_limit_ms` in `1 .. 2^53 - 1`; whether that value is
within `contract_absolute_ceiling` is a policy question decided after
authentication, as `limit_above_ceiling`. A parser that enforced the ceiling
would make an authenticated out-of-range request indistinguishable from
malformed bytes, and would silently change its own accept set whenever the
ceiling moved.

### `set_maintenance_limit`

```json
{"actor":"operator-17","anchor_epoch_id":"sha256:<64-lowercase-hex>","config_seq":7,"deployment_maintenance_limit_ms":900000,"device_id":"ori-fw-7c9f2b3a","kind":"set_maintenance_limit","reason":"commissioning-initial-limit","v":1}
```

`deployment_maintenance_limit_ms` is a canonical integer in `1 .. 2^53 - 1` —
the grammar's bound. The contract ceiling is enforced after authentication: a
value above `contract_absolute_ceiling`, which
[firmware-commands/v1.md](../firmware-commands/v1.md) fixes, is
`limit_above_ceiling` and spends its sequence. It is **refused, not clamped**:
a clamped limit is one the commissioner believes is larger than it is.

Acceptance sets the value whether or not one was already present, and whether
the new value is higher or lower. Raising and lowering follow the identical
path — a lower limit is the safer direction, but it is still a change to a
safety parameter, and a mechanism that treated the two differently would be one
an operator could be induced to misread.

### `clear_maintenance_limit`

```json
{"actor":"operator-17","anchor_epoch_id":"sha256:<64-lowercase-hex>","config_seq":8,"device_id":"ori-fw-7c9f2b3a","kind":"clear_maintenance_limit","reason":"decommissioning-maintenance-capability","v":1}
```

Acceptance removes the value. The manifest reverts to the shape that omits
`deployment_maintenance_limit_ms`, and the device refuses every subsequent
maintenance entry.

Withdrawal exists so maintenance capability can be revoked without
re-provisioning the device. It is a clearing operation rather than a magic
sentinel value in `set_maintenance_limit`, because "the value zero" and "no
value" would otherwise both have to mean *no maintenance*, and a parser
accepting two spellings of one meaning is one that can be made to disagree with
its signer.

Clearing an absent value is accepted and idempotent. It still spends
`config_seq` and still yields a result; the manifest and `capability_hash` are
unchanged, because they already described a device with no limit.

## Initial State

A device that has never accepted a configuration request **has no maintenance
limit**. There is no default and no fallback to the contract ceiling.

The consequence is deliberate: an uncommissioned device cannot enter
maintenance at all. A default would mean a device that had never been assessed
for its installation nonetheless permitted interlock suppression for some
duration nobody chose.

Per the lifecycle rules in
[firmware-commands/v1.md](../firmware-commands/v1.md), the first value is
commissioned before runtime authority and unattended-load operation are
enabled, so the transition it causes costs nothing. Every later change is
subject to
[A Configuration Change Is The Armed Transition](#a-configuration-change-is-the-armed-transition).

## Ordering: Persistence, Manifest, Authority Retirement

The manifest is **derived**, never independently stored. A device recomputes it
from persisted configuration at every boot and before every publication. There
is therefore no state in which a stored manifest can disagree with the
configuration it describes, which is what makes the crash windows below
tractable.

On a request that has passed grammar, device binding, signature, epoch, and
freshness:

1. **Spend** — persist the `config_seq` high-water mark.
2. **Persist** — durably write the new configuration value, or remove it.
3. **Derive** — recompute the manifest and its `capability_hash`.
4. **Transition** — the changed hash retires runtime command authority and
   lapses liveness supervision, exactly as any other capability change does.
   On an operational device this is the `armed -> unsupervised` transition the
   open window authorised, and the device emits `capability_transitioned`;
   suppression begins and runs to the deadline fixed at entry. The device
   follows the ordinary capability-transition lifecycle in
   `firmware-commands/v1.md`; this contract defines no separate path.
5. **Publish** — sign and publish the new manifest on the retained manifest
   topic, then return the signed result.

The ordering is not interchangeable:

- **Spend before persist**, so a crash cannot leave the request replayable.
- **Persist before derive**, so a published manifest never advertises a value
  the device would not honour after a reboot.
- **Derive before transition**, because the retirement is *caused by* the new
  hash rather than accompanying it. A device that retired authority and then
  failed to change its configuration would have paid the transition for
  nothing.

Crash between steps 2 and 5 is safe and self-correcting: the value is durable,
the manifest is derived from it, and the retained manifest is republished on
every connect. The device converges on the correct published hash without the
provisioner retrying. The provisioner learns the outcome from the retained
manifest, not only from the result message.

Failure at step 2 is `storage_failure`. The sequence is already spent, nothing
changed, and the value in force remains the previous one — including "no
value".

## A Configuration Change Is The Armed Transition

An accepted configuration request changes `capability_hash`, and a changed
capability hash retires runtime authority and lapses supervision. On an
operational device that is not an administrative side effect — it is a
transition into an unsupervised state, with a load possibly running.

Performing it outside a maintenance window would orphan the device during the
operation with its Local Interlock backstop unprotected by any authorised
bound. That is the exact hazard safe-maintenance windows exist to contain, so
the configuration change **is** the authorised transition rather than something
done before or after one.

> The state names `maintenance_armed` and `maintenance_unsupervised`, the
> `to_capability_hash` field, and the `capability_transitioned` and
> `maintenance_transition_mismatch` events belong to the safe-maintenance state
> machine in [firmware-commands/v1.md](../firmware-commands/v1.md). That
> section is agreed but not yet written, pending the duration bounds. This
> contract is a target until it is: the two must be ratified together, because
> a configuration change is one of the transitions that state machine governs.

### The rule

A configuration request that would change `capability_hash` is accepted only
in these states:

| Device state | Outcome |
|---|---|
| Pre-operational (`normal`, no runtime command authority installed) | **Accepted.** Initial commissioning. |
| Operational (`normal`, runtime command authority installed) | **Refused**, `maintenance_required`. Sequence spent. |
| `maintenance_armed`, and the device's derived prospective hash equals the window's `to_capability_hash` | **Accepted.** Applying it *is* the authorised `armed -> unsupervised` transition. |
| `maintenance_armed`, prospective hash differs from `to_capability_hash` | **Refused**, `destination_mismatch`. Sequence spent. |
| `maintenance_unsupervised` | **Refused**, `maintenance_active`. Sequence spent. |

A request that would **not** change `capability_hash` — re-setting the value
already in force, or clearing a limit that is already absent — is accepted in
any state other than `maintenance_unsupervised`. It causes no transition, so
there is nothing for a window to protect. This is one rule, not an exception:
**a window is required exactly when the hash would change.**

### Why armed, and not any other state

`maintenance_armed` is the only state in which a hash change is both authorised
in advance and bounded in duration. The entry that armed the window named
`to_capability_hash`, so the destination was approved by the same authority
before the change was attempted, and the deadline fixed at entry bounds how
long suppression may last if re-supervision does not arrive.

The device therefore does not merely check that *a* window is open. It derives
the prospective manifest hash the request would produce and requires equality
with the armed destination. Anything else is `destination_mismatch`: a request
that is authentic but was not the change this window authorised.

That check is also what keeps the transition legible. Because the applied hash
equals the armed destination by construction, the device emits
`capability_transitioned` and never `maintenance_transition_mismatch` — the
mismatch event stays reserved for a hash change nobody authorised, which is the
only reading that makes it a drift signal.

### What the provisioner must do

The prospective hash is computable off-device. The manifest is retained and
published, so the provisioner:

1. reads the device's current retained manifest;
2. substitutes the new value, or removes it;
3. canonicalises and hashes the result to obtain the prospective hash;
4. enters a maintenance window naming that hash as `to_capability_hash`;
5. sends the configuration request;
6. installs a new approval and restores supervision under the new hash.

Step 6 is not optional courtesy. The window ends in good order only through
re-supervision, and a provisioner that changes a limit and walks away has
converted a bounded window into a device running to its deadline unsupervised.

### Pre-operational commissioning

The first value is commissioned before runtime command authority exists, so
there is no authority to retire and no supervision to lapse — the transition
costs nothing and needs no window.

The device's test is whether a runtime command authority is currently
installed. That is the condition it can actually check. The commissioner's
obligation — not to energise an unattended load before the limit is set — is
not device-checkable, and this contract does not pretend otherwise; it is
recorded in the provisioner obligations below.

Once a runtime command authority exists, the device is operational for the
purposes of this rule, permanently and regardless of whether that authority is
currently live. A refusal here is `maintenance_required`, which names the
operator's next step rather than leaving them to infer it.

## Device-Signed Result

A result is a **Layer 1 signed envelope**, carrying the same identity and
freshness binding as telemetry, faults, and maintenance lifecycle events, and
drawn from the same `(boot_id, seq)` stream:

```json
{"result":{"alg":"ed25519","anchor_epoch_id":"sha256:<64-lowercase-hex>","boot_id":41,"capability_hash":"sha256:<64-lowercase-hex>","config_seq":7,"device_id":"ori-fw-7c9f2b3a","device_uptime_ms":812345,"kind":"set_maintenance_limit","posture":"sealed_flash","seq":9182,"v":1,"verdict":"accepted"},"signature":"ed25519:<base64-64-byte-signature>"}
```

`alg`, `boot_id`, `seq`, `posture` and `device_uptime_ms` have the semantics
defined in [firmware-telemetry/v1.md](../firmware-telemetry/v1.md), and a
receiver verifies a result exactly as it verifies any other Layer 1 envelope:
anchor eligibility, manifest pin, signature, `(boot_id, seq)` freshness against
the shared high-water mark, posture agreement, canonical shape.

An earlier draft omitted these and called the result "diagnostic". That was
wrong. A device-signed message that a provisioner acts on is device-origin
evidence whatever it is called, and without `boot_id` and `seq` it is
replayable: an old `accepted` result could be re-presented to convince a
provisioner that a change it never made is in force. Calling a message
diagnostic does not remove its need for replay-safe semantics — it only removes
the reader's guard against replay.

Because results draw on the shared sequence stream, a consumer reconstructing
that stream from the telemetry topic alone will observe gaps where results were
issued. Gaps are already valid under `firmware-telemetry/v1.md` and are not
diagnostic of loss.

`capability_hash` is the manifest hash **in force after** the operation,
whether or not it changed. It is what lets a provisioner join the request it
signed to the manifest transition it caused, without inferring the join from
timing. `config_seq` joins it to the specific request.

A result still does not assert that the device is reachable, that supervision
resumed, or that the transition completed its lifecycle — the retained manifest
and the maintenance lifecycle events in `firmware-telemetry/v1.md` carry
those.

An implementation MUST NOT reflect untrusted request fields in a signed result
before grammar, device binding, and signature verification pass. Earlier
failures are returned as local adapter errors, unsigned.

## Transport Binding

| Topic | QoS | Retained | Payload |
| --- | --- | --- | --- |
| `ori/fw/<device_id>/config` | 1 | **no** | One signed configuration request. **Never retained**: the high-water mark makes redelivery harmless, but a broker must not hold a standing instruction to change a safety parameter, and a retained request would be re-presented on every subscribe for as long as it remained. |
| `ori/fw/<device_id>/config/result` | 1 | no | One device-signed result. Never retained; a stale result would describe a `capability_hash` the device may have since left. |

The device subscribes only to its own topics, never a wildcard. Topic identity
is routing only: a configuration request arriving on the command or provision
topic fails that verifier's grammar and is rejected, never re-routed. Requests
MUST NOT be carried on the retained `ori/fw/<device_id>/provision` approval
topic.

Ingress loss is not silent. A dropped request or a failed subscription raises
`ingress_degraded` per `firmware-telemetry/v1.md`, and a request that produced
neither a result nor a fault must be treated by the provisioner as lost and
retried with a fresh `config_seq`.

Adapters other than MQTT may carry these objects unchanged; the signed bytes
are the contract, and a transport is never authority.

## Normative Verdicts

| Condition | Verdict | Consumes `config_seq`? |
| --- | --- | --- |
| Any structural violation: grammar, field set, bounds, unrecognised `kind`, absent or invalid `actor`/`reason` | `malformed` | No |
| `device_id` names another device | `wrong_device` | No |
| Provisioning-authority signature fails | `bad_signature` | No |
| No active approved Layer 1 anchor exists | `anchor_not_approved` | No |
| `anchor_epoch_id` differs from the active approved epoch | `anchor_epoch_mismatch` | No |
| `config_seq` is not above the persisted mark | `replayed` | No |
| `deployment_maintenance_limit_ms` exceeds `contract_absolute_ceiling` | `limit_above_ceiling` | Yes |
| The hash would change, the device is operational, and no window is armed | `maintenance_required` | Yes |
| A window is armed, but the prospective hash differs from `to_capability_hash` | `destination_mismatch` | Yes |
| A window is suppressing (`maintenance_unsupervised`) | `maintenance_active` | Yes |
| A required durable write fails | `storage_failure` | Yes |
| The operation is applied | `accepted` | Yes |

The division is exact. Every verdict above `limit_above_ceiling` is reached
before the freshness check, changes nothing, and spends nothing. Every verdict
from `limit_above_ceiling` down is reached after it, and spends — including the
four that refuse, in keeping with the spend-on-sight rule above: each depends
on device state the signer could not have known, and returning the sequence
would leave those exact signed bytes replayable until local state happened to
permit them.

One verdict per condition, and one condition per verdict. A request the parser
rejects is only ever `malformed`; there is no structural condition that also
has a policy verdict, and no policy condition reachable without authentication.

## Provisioner Obligations

The provisioning authority MUST:

- authenticate the operator before signing, and record actor, reason, the exact
  request digest, the result, and the resulting `capability_hash` in append-only
  audit;
- allocate one durable, strictly increasing `config_seq` per device;
- derive `anchor_epoch_id` from the active approved anchor held by the runtime
  and evidence store;
- verify the device's Layer 1 signature on the result against the eligible
  anchor before recording it;
- choose the limit from an assessment of the installation — the load, and what
  the interlock protects — and never from the contract ceiling by default;
- derive the prospective `capability_hash` from the device's retained manifest
  before requesting a change, and arm the maintenance window with that hash as
  `to_capability_hash`;
- treat re-approval and re-supervision under the new hash as part of the same
  operation. An accepted change *is* the transition into an unsupervised state;
  a provisioner that changes a limit and walks away has converted a bounded
  window into a device running to its deadline unsupervised;
- not energise an unattended load before a limit is commissioned. The device
  cannot check this — it can only refuse maintenance while no limit exists —
  so it is the commissioner's obligation, and it is why initial commissioning
  is permitted without a window.

## Firmware Obligations

Firmware MUST:

- verify the fixed grammar before signature verification, and the signature
  before any state change;
- bind every request to its own `device_id` and active approved epoch;
- apply the ordering in [Ordering](#ordering-persistence-manifest-authority-retirement)
  exactly, including spending before persisting;
- derive the manifest from persisted configuration rather than storing it,
  so the published hash cannot drift from the value in force;
- refuse every maintenance entry while no limit is configured;
- require an armed window whose `to_capability_hash` equals the derived
  prospective hash before applying any change that would alter
  `capability_hash`, once a runtime command authority has been installed;
- keep configuration handling entirely outside the Local Interlock path;
- use bounded static storage and declared input limits;
- preserve buffered signed evidence, telemetry counters, and every other
  sequence high-water mark across configuration changes.

## Required Implementation Artifacts

Before an implementation may claim this contract:

- shared golden vectors for both request grammars and the device-signed result,
  with a runtime signer and a firmware verifier proving byte-identical
  canonical bytes;
- a test that a result verifies under the ordinary Layer 1 rules, that its
  `seq` comes from the shared evidence stream, and that a replayed result from
  an earlier `boot_id` is rejected;
- negative vectors for every verdict above, each changing exactly one field of
  an accepted baseline;
- replay and persistence tests proving `config_seq` is independent from
  `cmd_seq`, `provision_seq`, and telemetry `seq`, and preserved alongside them
  across reboot and every rotation and revocation path;
- failure-injection tests at each ordering boundary, proving that a crash
  between spend and persist leaves the request non-replayable, and that a crash
  between persist and publish converges on the correct published hash without
  provisioner retry;
- a test that an uncommissioned device refuses maintenance entry, and that
  `clear_maintenance_limit` returns it to that state;
- state-machine tests covering every row of
  [the acceptance table](#the-rule): pre-operational acceptance in `normal`,
  `maintenance_required` on an operational device in `normal`, acceptance under
  a matching armed destination, `destination_mismatch` under a differing one,
  `maintenance_active` while suppressing, and acceptance of a hash-preserving
  no-op in each permitted state — each refusal asserting that the sequence was
  spent;
- a test that the device derives the prospective hash itself and compares it to
  `to_capability_hash`, rather than accepting any request while a window
  happens to be armed. Mutating the comparison must turn the
  `destination_mismatch` case green-to-red;
- a test that an accepted change under an armed window emits
  `capability_transitioned` and never `maintenance_transition_mismatch`;
- HIL evidence for initial commissioning, a limit change with the resulting
  capability transition and re-supervision, refusal during a window, and
  persistence across restart.

Golden vectors are not generated here: they require
`contract_absolute_ceiling`, which is unset.

The ceiling is **a safety judgement**, not a measurement — the longest period
for which suppressing a physical backstop is tolerable on any supported
deployment. Hardware timing does not determine it. What measurement supplies is
the *lower* bound: the worst-case duration of the full capability-transition
sequence, below which a window cannot complete and every maintenance operation
would fail.

Both bounds must be established independently, and they must **overlap** — the
measured lower bound must be comfortably below the judged ceiling. If they do
not, no safe window exists for that deployment, and the answer is to shorten
the transition or to stop treating the installation as maintainable, never to
raise the ceiling until the numbers fit.
