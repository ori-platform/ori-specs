# Evidence Exchange Contract v1

> Status: **Design Target, pre-ratification** throughout. **No conforming
> consumer has shipped.** Every half is implemented on a main branch —
> `ori-runtime` (producer, delivery ledger, envelope and checkpoint sealing,
> outbound carriage, inbound ingest; `ori-runtime#326` remains open),
> `ori-gateway` (courier) and the evidence authority (ingest and registration
> resolution) — and the runtime-to-gateway carriage and custody round-trip has
> been exercised on a loopback broker. No end-to-end exchange through an
> authority is operational. Do not build consumers against this document as
> though it described shipped behaviour.
>
> Those three states are kept distinct deliberately. *Implemented* means code
> exists on a main branch; *shipped* means a released artifact claims this
> contract; *proven end to end* means artifacts have actually crossed the
> exchange. Only the first is true today, and the pre-ratification exception in
> [VERSIONING.md](../VERSIONING.md#pre-ratification-exception) turns on the
> second, not the first.
>
> What exists: `ori-runtime` main carries the chain-row producer, the delivery
> ledger, and the ingest verifier in `ori/security/evidence_*`; `ori-gateway`
> main carries the custody producer in `internal/evidence/custody.go`. Neither
> is wired into a running system — the runtime has no inbound route, and the
> gateway's producer is reached only from tests.
>
> Source of truth for current *runtime* behaviour:
> `ori/security/firmware_confirmation.py`,
> `ori/security/firmware_reconciliation.py` and `ori/state/store.py` in
> `ori-runtime`; `internal/site/evidence.go` in `ori-gateway`, which is
> heartbeat-derived health tracking rather than the courier.
>
> On-device attestation — how a Tier C/D action becomes a signed chain row —
> remains [evidence/v2.md](../evidence/v2.md), which specifies the row's bytes
> publicly and neutrally; [evidence/v1.md](../evidence/v1.md) is retained only
> for verifying rows written before that switch. The two design-target sections
> there, *Anchor Registry* and *Evidence Export Ingestion*, are superseded by
> this document.

## Topology

The evidence authority does not run on the runtime device and is not reachable
from the site network. Only the gateway may sit alongside the runtime, and only
the gateway may move anything outward.

```text
firmware ──► runtime ──► gateway ──► evidence authority   (evidence channel)
                             └─────► fleet manager        (operations channel)
```

The runtime holds no address for the authority and cannot distinguish "the
authority refused" from "the gateway did not carry it" except through the
artifacts below. Both outbound channels leave through the gateway; they are
independent in authority, keys, storage, acknowledgement and failure status.

### Disclosure boundary

This is a public contract and the runtime is open source, so a runtime carrying
a trust anchor and a receipt verifier necessarily reveals that some independent
evidence authority exists. A contract claiming otherwise would assert something
its own publication disproves.

MUST NOT reach an operator-visible surface:

- the authority's implementation identity or product name
- its endpoint, hostname, or deployment location
- credentials, key custody detail, or administrative interfaces
- any instruction implying the operator transfers, imports, or forwards anything

MAY remain visible, and SHOULD: generic evidence-delivery health — pending
counts, oldest unreceipted age, degraded or healthy — carrying no identity and
no administrative surface. An operator must be able to see that delivery is
failing without learning who it is failing to.

**Concealment is not the security property.** A site can cut power, drop the
link, or unplug the gateway. What this contract guarantees is that interference
leaves a *measurable absence* rather than a clean record.

## Canonical encoding

Every signed or authenticated payload in this contract is canonicalised
identically, matching `canonical_config_signature_payload` in `ori-runtime`:

```text
canonical(obj) = json.dumps(obj, sort_keys=True, separators=(",", ":"),
                            ensure_ascii=False, allow_nan=False).encode("utf-8")
```

That line is a reference implementation, not the rule. Implementations exist in
Go and Rust, whose stock serialisers do not reproduce those bytes by default, so
the rule is stated explicitly:

- **Key ordering** is by Unicode scalar value (code point) at every nesting
  level, applied recursively. It is **not** UTF-16 code unit order: the two
  disagree across the BMP/astral boundary, where `U+FFFD` precedes `U+1F525` by
  scalar value while the astral character's leading surrogate `D83D` sorts first
  by code unit. An implementation MUST NOT rely on a serialiser's insertion
  order or a language's dictionary ordering.
- **Escaping** follows RFC 8259. Escape only `"` and `\`, plus C0 controls,
  using the short forms `\b`, `\f`, `\n`, `\r`, `\t` and `\u00xx` with
  lowercase hex for the rest. Every other scalar is emitted literally, including
  `<`, `>`, `&`, `U+2028`, `U+2029`, `DEL` and all non-ASCII. Go's
  `encoding/json` escapes the first three by default and escapes `U+2028` and
  `U+2029` unconditionally, so a Go implementation cannot use the stock
  serialiser here; `SetEscapeHTML(false)` suppresses only the first three.
- **Numbers** carry no exponent notation and no redundant digits. Integers
  satisfy `|n| <= 9007199254740991`. Non-integer numbers are finite and either
  exactly zero or of magnitude in `[1e-4, 1e16)`, serialised as the shortest
  round-trip decimal in fixed notation with a mandatory fractional part — `.0`
  appended for integral doubles, `-0.0` preserved. This is the D-011 agreement
  zone that [`evidence/v2.md`](../evidence/v2.md) defines, and it applies here
  for the same reason: an evidence artifact controls its own numeric domain, and
  a value no verifier can reproduce byte for byte is worse than one refused at
  source. `NaN` and `Infinity` are not valid JSON and MUST NOT be emitted.
- **Unicode** in the payload bytes MUST be valid UTF-8 and MUST NOT contain
  unpaired surrogate escapes. A verifier MUST refuse such a payload before
  decoding it, because implementations disagree on what it means: Go substitutes
  `U+FFFD` where Python surfaces the surrogate and then fails to encode it.

The runtime-gateway MQTT transport specifies the same key and string rules in
[`gateway-mqtt-canonical-json/v1.md`](../gateway-mqtt-canonical-json/v1.md), and
carries executable cross-language vectors for them. It deliberately does **not**
adopt the numeric zone above, because that transport carries operational
telemetry whose range is broader than an evidence artifact's. Do not treat the
two as interchangeable.

Signed bytes are `DOMAIN || canonical(obj)`, where `DOMAIN` is an ASCII string
terminated by a single NUL byte, following `SIGNATURE_DOMAIN` in
`ori/security/release_bundles.py`. A verifier MUST reject a payload whose
re-canonicalisation does not reproduce the bytes it verified.

| Artifact | Domain | Algorithm | Key purpose |
| --- | --- | --- | --- |
| Commissioning authorisation | `ori.evidence_commissioning_authorization.v1\0` | Ed25519 | `commissioning_authority` |
| Anchor registration | `ori.evidence_anchor_registration.v1\0` | Ed25519 | `evidence_device` |
| Delivery envelope | `ori.evidence_delivery_envelope.v1\0` | Ed25519 | `evidence_device` |
| Checkpoint | `ori.evidence_checkpoint.v1\0` | Ed25519 | `evidence_device` |
| Custody acknowledgement | `ori.evidence_custody_ack.v1\0` | HMAC-SHA256 | `gateway_custody` |
| Delivery receipt | `ori.evidence_delivery_receipt.v1\0` | Ed25519 | `evidence_authority_receipt` |
| Epoch confirmation | `ori.evidence_epoch_confirmation.v1\0` | Ed25519 | `evidence_authority_epoch` |

Key purposes are disjoint. A verifier MUST reject an artifact whose signature
verifies under a key registered for any other purpose: purpose separation is
what stops a receipt-signing key from asserting that an epoch is active.

Every artifact excludes its own authenticator — the `signature` field, or `mac`
for the custody acknowledgement — from the bytes it signs. Everything else the
artifact defines is covered.

Every artifact carries `"v": 1`. A receiver MUST reject an unrecognised version
rather than ignoring unknown fields, and MUST reject any object carrying a
field this contract does not define.

**Every artifact names the key that signed it.** Each carries a `key_id`, and a
verifier selects the key by `(key_purpose, key_id)` rather than trial-verifying
against everything it holds. Trial verification would make "which key signed
this" unanswerable in a finding, and would silently succeed against a
superseded key when it should have said so.

| Purpose | Held by | Trust root |
| --- | --- | --- |
| `evidence_device` | evidence authority | the anchor registry, per registration below |
| `commissioning_authority` | evidence authority | a registry the authority holds, established out of band at organisation setup |
| `evidence_authority_receipt` | runtime | the signed release bundle it is running |
| `evidence_authority_epoch` | runtime | the signed release bundle it is running |
| `gateway_custody` | runtime | a dedicated custody secret, shared with the gateway and distinct from the runtime–gateway envelope secret |

Rotation follows the release key registry model for every purpose: an outgoing
key stays `verify_only` while its successor is `active`, so artifacts signed
before a rotation keep verifying, and a retired key verifies nothing. A
verifier MUST reject an artifact whose `key_id` it does not hold for that
purpose, and MUST reject one whose `key_id` is held for a *different* purpose.

A device MUST NOT accept an authority key delivered through the exchange
itself. An authority that can hand a device new trust roots over the channel it
is being trusted on has no independent standing; new authority keys arrive only
in a signed release.

The `commissioning_authority` registry is deliberately not release-rooted: a
release cannot know which people commission a given site. It is established
when the authority is set up and rotated by the same administrative path,
outside this contract.

## Artifacts

Seven, and none is interchangeable with another. Conflating any two collapses a
distinction some fail-closed rule depends on.

| Artifact | Produced by | Asserts |
| --- | --- | --- |
| Commissioning authorisation | commissioning authority | this actor authorised this device key and epoch. Delivered to the evidence authority through the organisational commissioning path; it never crosses the exchange from the device side |
| Anchor registration | runtime | this device's verification key, under this epoch |
| Delivery envelope | runtime | this device recorded this event |
| Checkpoint | runtime | this device has sealed up to this `local_seq` |
| Custody acknowledgement | gateway | the courier holds it durably |
| Delivery receipt | evidence authority | the authority recorded this contiguous range |
| Epoch confirmation | evidence authority | this anchor epoch is active |

### Anchor registration

Chain verification starts from the device's verification key. Registration binds
that key to the device and the epoch authorising it, and is signed by the key
being registered — which proves control of the key and nothing else.

**Control is not authorisation.** A self-signed registration carrying `actor`
and `reason` as plain fields proves only that whoever holds the new key wrote
those strings, so anyone with a fresh keypair could claim any actor. The right
to deploy a key comes from a separately signed **commissioning authorisation**,
which the device never holds, and the registration binds it by digest:

| Field | Type | Notes |
| --- | --- | --- |
| `v` | `int` | `1`. |
| `device_id` | `string` | Device authorised. |
| `pubkey_hex` | `string` | Exact key authorised, 64 lowercase hex. |
| `anchor_epoch_id` | `string` | Epoch this authorisation covers. |
| `actor` | `string` | Authenticated commissioning actor. |
| `reason` | `string` | Operator-supplied reason. |
| `issued_at_ms` | `int` | Commissioning authority clock. |
| `key_id` | `string` | Identifies the commissioning key, selected by `(commissioning_authority, key_id)`. |
| `signature` | `string` | `ed25519:` over the commissioning domain, NUL-terminated as above. |

The authority MUST verify the authorisation before applying a registration.
It resolves the registration's `commissioning_digest` against the
authorisations it holds — delivered to it through the commissioning path
described below, never by the device — and MUST NOT apply a registration whose
digest resolves to no held authorisation, MUST reject one whose resolved
authorisation names a different `device_id`, `pubkey_hex` or
`anchor_epoch_id`, and MUST reject one that names a digest other than an
authorisation it holds for that device and epoch. The fuller commissioning
model lives in the commissioned safety binding contract; this defines only what
the evidence authority requires to accept an anchor.

| Field | Type | Notes |
| --- | --- | --- |
| `v` | `int` | `1`. |
| `device_id` | `string` | Runtime device identity. |
| `pubkey_hex` | `string` | Ed25519 verification key, 64 lowercase hex. |
| `anchor_epoch_id` | `string` | Epoch this anchor is registered under. |
| `alg` | `string` | `ed25519`. |
| `posture` | `string` | Key custody posture. The vocabulary is the union of [`device-provisioning/v1.md`](../device-provisioning/v1.md) and [`runtime-evidence-anchor/v1.md`](../runtime-evidence-anchor/v1.md); the latter defines `software_wrapped`, which a runtime uses and which `device-provisioning` does not carry. |
| `capability_profile` | `object` | The complete evidence capability profile the epoch was derived from, per [`runtime-evidence-anchor/v1.md`](../runtime-evidence-anchor/v1.md). Carried in full rather than as a digest so the authority can recompute `capability_hash` and `anchor_epoch_id` itself. |
| `registered_at_ms` | `int` | Runtime clock at signing. |
| `commissioning_digest` | `string` | `sha256:` over `canonical(commissioning_authorization)`, hashing the **complete** authorisation object including its `signature` field. Binding to the unsigned body would let a valid body be paired with a different signature. This is the **commissioning reference**: the only thing the device holds about the authorisation, and it grants nothing on its own. |
| `key_id` | `string` | Identifies this device key; registration is what binds it. |
| `signature` | `string` | `ed25519:` over the registration domain. |

**The authority MUST recompute both `anchor_epoch_id` and `key_id` before
accepting a registration**, per `runtime-evidence-anchor/v1.md`, and MUST refuse
the registration if either claimed value differs from the recomputed one.

Recomputing only the epoch would leave `key_id` caller-supplied. Since a verifier
selects by `(evidence_device, key_id)`, an unmatched value would let a
registration file its key under a selector that does not correspond to the key it
carries — which is the same circular trust the epoch rule removes, arriving
through the selector instead.

Without this the epoch is only an assertion. A device would name the trust
proposition it wants to be judged under, and the authority would have no way to
check that the name matches the properties — which is the circular trust the
derivation exists to remove. Carrying the profile in full, rather than a digest,
is what makes the claim inspectable as well as derivable: an authority can see
*what* was claimed, not merely that a hash matched.

The commissioning authorisation continues to bind `anchor_epoch_id`, and the
authority MUST recompute that epoch before accepting the
authorisation-registration pair, so the authorisation cannot vouch for an epoch
whose inputs say something else.

Both derivations consume `public_key_b64`, while a registration carries
`pubkey_hex`. The conversion is normative, because a verifier that guesses it
computes different bytes and refuses a conforming registration:

1. `pubkey_hex` MUST be exactly 64 lowercase hexadecimal characters.
2. Decode it to exactly 32 bytes.
3. Re-encode those bytes with RFC 4648 standard Base64 **with** padding, and
   with the standard alphabet — not URL-safe, not unpadded.
4. Use that value as `public_key_b64` in both derivations.

A registration whose `pubkey_hex` is the wrong length, contains a non-hex
character, or contains uppercase hex MUST be refused **before** derivation is
attempted, rather than being normalised. Normalising would make two distinct wire
forms derive the same identifiers, so a device could present a key in a spelling
the authority did not record.

Recomputation also changes how a conflicting registration is caught. A
registration naming a held epoch with a different `pubkey_hex` now fails
recomputation first, because the epoch is derived *from* the key: a different key
yields a different epoch. The quarantine rule below therefore becomes defence in
depth -- for an epoch stored before recomputation was required, or a derivation
collision -- rather than the first line of refusal.

#### Commissioning authorisation delivery

The authorisation is an authority object: a signed statement, under a key the
device does not hold, that a named actor licensed this device key for this
epoch. It therefore MUST NOT be delivered to the device, carried by the
gateway, or routed through the fleet manager. An authorisation held on an
operator-controlled device is authority material inside the perimeter the
artifact exists to make claims about, and the disclosure boundary above
forbids the transfer step that delivering it would require.

Three parties, three paths:

| Concern | Party | Path |
| --- | --- | --- |
| Issue and sign the authorisation | commissioning authority | An authenticated organisational workflow at commissioning time, requested by the commissioning actor. The signing key never resides in the runtime, the gateway, the CLI, or anything else in the site environment; the actor requests issuance and is not thereby the key holder |
| Hold and verify it | evidence authority | The signed authorisation reaches the authority through the purpose-bound write path in [evidence-commissioning-ingest/v1.md](../evidence-commissioning-ingest/v1.md), which retains it keyed by `commissioning_digest` under the `commissioning_authority` registry it already holds and promotes a registration retained pending under that digest in the same transaction. Revocation travels the same path. Both are outside this exchange |
| Present a registration under it | runtime | Receives only the **commissioning reference** — `commissioning_digest` — through the local commissioning surface at the device, per [cli-commands/v1.md](../cli-commands/v1.md), never through configuration, the gateway, a remote command, or the fleet manager. It seals the registration with that reference and delivers it through the courier as any other artifact |

The reference is opaque and purpose-bound: a digest over a domain-separated
signed object, carried in a field whose name says what it is. It reveals
nothing about the authorisation's content, and a device holding a wrong,
stale or foreign reference gains nothing — the authority resolves it and
refuses. That is why it may pass through an installer's tool and sit in the
device's durable state where the authorisation itself may not.

**The reference is bound to one epoch.** The authorisation names
`anchor_epoch_id`, so a reference licenses exactly one `(device_id,
pubkey_hex, anchor_epoch_id)`. When the epoch changes — a new key, a changed
custody posture, a changed capability profile — the reference does not carry
over: a new authorisation is issued through the same path and a new reference
delivered, and until then the new epoch's registration is pending as below. A
reference is never rewritten to name a different epoch.

**`pending_authorisation` is a durable working state, not a terminal one.**
A runtime holding no reference for its current epoch:

- emits no registration and grants itself no authority — commands and
  provisioning approvals stay ungranted, as the fail-closed rule below
  requires;
- keeps the obligation alive and retries when a reference arrives, rather than
  closing the attempt;
- reports the state on its health surface as generic evidence-registration
  status, naming no authority, endpoint or transfer step; and
- never lets the pending state block, delay or gate a local Tier D safety
  action. Physical safety does not wait on evidence infrastructure, and an
  unregistered anchor must not become a reason a relay failed to open.

**Resolution at the authority.** A registration's `commissioning_digest` is
resolved against held authorisations:

| Resolution | Outcome |
| --- | --- |
| Resolves to an authorisation naming the same `device_id`, `pubkey_hex` and `anchor_epoch_id` | Apply, recomputing epoch and `key_id` as above; issue the epoch confirmation |
| Resolves to nothing, and the authority holds no authorisation for that device and epoch | Retain the registration pending; `accepted` with no confirmation; no gap. The authorisation may still arrive through the commissioning path |
| Resolves to nothing, but the authority holds an authorisation for that device and epoch under a different digest | Reject `commissioning_digest_mismatch`. The device was given the wrong reference; a refusal, not a quarantine, because the device is not attacking and a corrected reference repairs it |
| Resolves to an authorisation naming a different device, key or epoch | Reject `commissioning_digest_mismatch` |
| The device presents the authorisation object itself | Refused at transport as an artifact the courier does not carry, per [evidence-transport/v1.md](../evidence-transport/v1.md) |

Re-issuance is idempotent by digest: an authority MAY hold more than one
authorisation for a device and epoch, and a registration applies under any
held, unrevoked one it names. Revocation of an authorisation travels the same
administrative path as the registry and is outside this exchange.

`(device_id, anchor_epoch_id)` is the idempotency key. Re-registering an
identical binding MUST return the same outcome without side effects. A
registration naming an epoch the authority already holds with a **different**
`pubkey_hex` MUST be refused and quarantined, never applied: an attacker who can
silently rebind an anchor owns the chain. The authority MUST retain superseded
anchors so evidence stays attributable to the epoch that authorised it.

### Delivery envelope

A delivery wrapper around a chain row. **It does not replace the chain row and
does not re-sign it.** The chain row remains the canonical evidence record with
its own signature per [`evidence/v2.md`](../evidence/v2.md); the envelope adds delivery framing and
signs the framing together with the exact chain row bytes, so neither can be
substituted for the other in transit.

| Field | Type | Notes |
| --- | --- | --- |
| `v` | `int` | `1`. |
| `device_id` | `string` | Runtime device identity. |
| `anchor_epoch_id` | `string` | Epoch whose anchor signed this envelope. |
| `key_id` | `string` | Device key that signed it, selected by `(evidence_device, key_id)`. |
| `local_seq` | `int` | Delivery ordering. Distinct from the chain row's `seq`. |
| `chain_row` | `object` | The chain row's immutable columns, named exactly as [`evidence/v2.md`](../evidence/v2.md) defines them: `seq`, `event_id`, `event_type`, `device_id`, `emitted_at_ms`, `payload_json`, `canonical_json`, `event_hash`, `prev_event_hash`, `signature`, `created_at_ms`. Its `canonical_json` MUST carry `schema_version` `ori.evidence.v2`; a row declaring any other version is rejected rather than reinterpreted. The mutable export bookkeeping columns are local and MUST NOT be carried. |
| `chain_row_digest` | `string` | `sha256:` over the UTF-8 bytes of `chain_row.canonical_json`. |
| `sealed_at_ms` | `int` | When the runtime sealed the envelope, not when it was sent. |
| `signature` | `string` | `ed25519:` over the envelope domain, covering every field above except `signature`. |

**Epoch enforcement.** The authority selects the verification key by
`(evidence_device, key_id)` and MUST check that `key_id` is the anchor
registered for `anchor_epoch_id`. An envelope naming a superseded epoch is
accepted and attributed to it — evidence signed under an epoch that was active
when it was produced stays valid — while one naming an epoch the device never
held, or whose `key_id` is not that epoch's anchor, is rejected. Without both
fields the receiver would trial-verify against every retained key and could not
distinguish current, superseded and unknown.

**Byte preservation without ambiguity.** The chain row already carries its own
canonical bytes in `canonical_json`, and its `signature` covers exactly those
bytes. A receiver therefore verifies the row's signature against
`canonical_json` **directly and never re-canonicalises the row object**; the
surrounding JSON is transport for a string whose bytes are already fixed.
`chain_row_digest` is taken over the same bytes, so digest, signature and
transport agree by construction.

**Binding the envelope to the row it carries.** Verifying both signatures is
not sufficient on its own: a valid envelope from one device could otherwise
wrap a valid signed row from another. A receiver MUST additionally check that

- the envelope's `device_id` equals `chain_row.device_id`;
- the identity and event fields in `chain_row` reproduce those inside
  `canonical_json`, so the outer object cannot describe a row different from
  the bytes that were signed; and
- the chain row's signature resolves to a key registered for **that same
  device identity**, under the epoch that was active when the row was emitted —
  a superseded key is acceptable, a key belonging to another device is not.

The envelope's signature is end-to-end. The gateway MUST forward the bytes
unaltered and MUST NOT re-canonicalise, re-serialise or re-sign them. A
receiver MUST verify the chain row's signature over `canonical_json`, verify
the envelope signature, and reject a mismatch between `chain_row_digest` and
the digest recomputed from `canonical_json`.

**`local_seq` allocation.** Allocated within the delivery ledger alone, in the
same durable transaction as the ledger row it numbers, and gapless by
construction. A failure before that commit allocates nothing and therefore
creates no gap; there is no envelope to be missing. Local failure rows record
*delivery* failures of sealed envelopes only.

Deliberately **not** atomic with the originating action row. `evidence/v2.md`
appends after the action is logged and states that cross-store atomicity
remains a design target, so requiring one transaction across both would
contradict the contract this one builds on. The consequence is explicit: an
action may exist with no envelope if the runtime dies between logging and
sealing, which is an attestation gap `evidence/v2.md` already defines and
reports, not a delivery gap this contract can observe.

### Checkpoint

A device-signed assertion of the highest `local_seq` sealed. It is what turns
unexplained silence into a missed obligation, so it MUST be signed by the
device key.

> It MUST NOT ride the runtime–gateway HMAC envelope. The gateway holds that
> shared secret, so an HMAC-authenticated checkpoint is forgeable by the party
> the checkpoint exists to constrain — a stalling gateway could manufacture
> checkpoints proving nothing was missing.

| Field | Type | Notes |
| --- | --- | --- |
| `v` | `int` | `1`. |
| `device_id` | `string` | Runtime device identity. |
| `high_water_seq` | `int` | Highest `local_seq` sealed. `0` before any envelope. |
| `anchor_epoch_id` | `string` | Epoch whose anchor signed this checkpoint. |
| `boot_id` | `int` | Durably allocated, strictly increasing across reboots, so a restart is visible rather than a regression. |
| `key_id` | `string` | Device key that signed it. |
| `issued_at_ms` | `int` | Runtime clock at signing. |
| `signature` | `string` | `ed25519:` over the checkpoint domain. |

**Cadence and grace.** A checkpoint is issued every `checkpoint_interval_s`
(default 900) and on every clean shutdown.

**The deadline is measured on the authority's clock, never the device's.** The
authority records `received_at_ms` from its own clock when a checkpoint is
accepted, and raises a missed checkpoint when
`authority_now > last_received_at_ms + interval + grace`, with `grace` at least
twice the interval so ordinary transport delay is not a finding. The obligation
begins at the epoch confirmation, so a device that never checkpoints is
detected rather than exempt.

`issued_at_ms` is retained as signed diagnostic evidence — it shows what the
device believed the time was — and is never an input to the deadline. Deriving
the deadline from it would let a future-dated checkpoint postpone the obligation
indefinitely, which hands the schedule to the party the checkpoint constrains,
and would turn ordinary clock skew into false findings.

**Ordering.** Ordering comes from `high_water_seq` and `boot_id`, not from any
clock. A checkpoint whose `issued_at_ms` moves backwards relative to the
previous accepted checkpoint is retained and flagged as a device clock anomaly,
including when the higher `boot_id` shows that the clock regressed across a
reboot. It is evidence about the device, and rejecting it would discard the only
signed record of the anomaly.

**Reboot.** `high_water_seq` never resets; `boot_id` increments. Both are
allocated durably and are strictly increasing for the life of the device
identity — neither wraps, and neither may be reset by reinstallation, since a
counter an operator can restart is a counter that cannot evidence anything. A
64-bit counter incremented once per boot does not exhaust in any plausible
deployment; an implementation that would exhaust MUST fail rather than wrap. A
checkpoint whose `high_water_seq` is lower than one already accepted for the
same `device_id` MUST be rejected as rollback regardless of `boot_id`, and a
`boot_id` lower than one already accepted MUST be rejected likewise. Equal
`boot_id` is the normal periodic-checkpoint case within one boot and is accepted
when `high_water_seq` does not regress. A higher `boot_id` records a reboot. A
byte-identical checkpoint replay is idempotent and creates no second state row.

### Rejection cases carry their defect

Every vector file publishes cases marked `expected: reject`. Each must differ
from that file's valid case in the field or authenticator its name identifies,
and a regeneration that erases the difference has removed the test while
leaving something that still looks like one.

`authenticator: valid` is the trap. It marks a case that must verify
cryptographically **so the semantic rule under test is reached** — not a case
that is correct. A generator that re-signs every case carrying that marker
produces a file where the rejections are byte-identical to the acceptance,
and the suite goes on passing: each case is still refused, for reasons that
have nothing to do with what it was written to prove.

That happened here. Both rejections in
[`vectors/delivery-receipt.json`](vectors/delivery-receipt.json) were flattened
by a regeneration that re-signed on exactly that rule, and the damage was
invisible until an implementation tried to use them —
`signed_with_epoch_key` was being refused as an unknown sequence rather than as
a cross-purpose signature.

**A conforming generator MUST fail rather than emit a set where a rejection
case has become indistinguishable from the valid case.** Byte-level
reconstruction does not detect this: the bytes were internally consistent
throughout, and every hash and signature reproduced. Reconstruction proves
consistency, not that a negative case still carries a defect.

## Wire bytes

Two byte sequences exist for every signed artifact here, and conflating them is
a real defect rather than a pedantic distinction.

```text
signing preimage = DOMAIN || canonical(artifact without its authenticator)
wire bytes       = canonical(artifact including its authenticator)
```

The preimage is what a signature is computed over. The **wire bytes** are what
travels, what the gateway stores, and what it MUST forward unaltered.

A producer serialises the complete artifact canonically, and those bytes are the
wire form. Fixing it this way is what makes "the exact bytes received"
reproducible by a third party rather than a property only the original sender
could confirm; a receiver that re-serialises differently would compute a
different digest for an artifact nobody altered.

`wire_hex` in [`vectors/delivery-envelope.json`](vectors/delivery-envelope.json)
carries these bytes for every case, alongside the `canonical_hex` preimage, so
the difference is visible rather than inferred.

**Custody digests the wire bytes.** An earlier revision digested the preimage,
which is the same bytes minus the signature. That would let a gateway
acknowledge custody of an artifact whose signature it never received — the
acknowledgement would verify while asserting possession of something other than
the signed evidence it exists to commit to. Custody is a claim about holding the
signed artifact, so it must bind the bytes that carry the signature.

### Custody acknowledgement

The gateway signs nothing on the envelope. It does authenticate its own custody
claims, because a runtime uses custody state to manage its local queue and an
unauthenticated acknowledgement is forgeable by any process on the site network.

| Field | Type | Notes |
| --- | --- | --- |
| `v` | `int` | `1`. |
| `device_id` | `string` | Device the envelope belongs to. |
| `local_seq` | `int` | Envelope acknowledged. |
| `envelope_digest` | `string` | `sha256:` over the envelope's **wire bytes** as defined below — the complete artifact including its `signature`, not the signing preimage. |
| `custody_at_ms` | `int` | When custody became durable. |
| `key_id` | `string` | Identifies the custody secret generation, derived from the secret as defined below. Selected by `(gateway_custody, key_id)`. |
| `mac` | `string` | Exactly `hmac-sha256:` followed by 64 lowercase hexadecimal characters, over the custody domain, matching the encoding the runtime-gateway envelope contract already uses. |

Authenticated under a **dedicated custody secret** with the domain above.

#### Custody key material

The custody secret MUST be distinct from the runtime–gateway envelope secret.
Both are symmetric secrets shared between the same two parties, which is
exactly why they must not be the same bytes: the envelope secret authenticates
operational traffic that the gateway both sends and receives, while the custody
secret authenticates a claim the gateway makes about evidence it is carrying. A
single secret would let any component holding it for one purpose mint artifacts
for the other, and domain separation alone does not prevent that — it only
ensures the two preimages differ.

An earlier revision of this section said custody was authenticated under the
existing runtime–gateway shared secret. That text was wrong and is withdrawn.
The vectors have always defined two distinct secrets and stated that a custody
MAC verifies only under the custody one, and the producer and verifier
conformance tests follow the vectors. Runtime production construction
demonstrably does not, which is a defect in that implementation rather than an
ambiguity in this contract.

The custody secret MUST be generated from a cryptographically secure random
source with at least 256 bits of entropy. This is normative because the
identifier below is a deterministic function of it: a low-entropy secret is
guessable offline from any single acknowledgement, and that is true of the MAC
alone, but the contract should not require deriving anything from a secret it
has not required to be strong.

#### The identifier is derived, not configured

`key_id` MUST be derived from the custody secret:

```text
key_id = "hkdf-sha256:" || lowercase_hex( HKDF-SHA256(
    ikm    = the custody secret, encoded UTF-8,
    salt   = "ori.evidence_custody_key_id.v1" as ASCII, no NUL,
    info   = "gateway_custody" as ASCII, no NUL,
    length = 16 bytes ) )
```

The result is the literal prefix `hkdf-sha256:` followed by exactly 32
lowercase hexadecimal characters.

**The `mac` is shape-checked the same way, and before it is compared.** A value
that is not `hmac-sha256:` followed by exactly 64 lowercase hexadecimal
characters is `malformed`, not `bad_authenticator`. The distinction is the
boundary of the vocabulary rather than a nicety: a MAC of the wrong length or
alphabet was never a candidate authenticator, and reporting it as a failed
authentication invites an operator to hunt for a key mismatch that does not
exist. A well-formed MAC that simply does not recompute is `bad_authenticator`. A verifier MUST compare identifiers as exact
byte strings and MUST NOT case-fold, normalise, or accept an uppercase or
abbreviated form. An artifact whose `key_id` does not match that shape is
`malformed`, which is a different outcome from one whose shape is valid but
whose value is not held.

Derivation rather than configuration is what makes the rotation window
enforceable. A configured name survives a rotation unless an operator
remembers to change it, and an identifier that names two different secrets
cannot select between them — which is the whole function of the selector. A
derived identifier changes with overwhelming probability when the secret bytes
change, so the property holds without depending on operator diligence.

That is a probabilistic claim, not an algebraic one. The identifier is a
128-bit truncation, so distinct secrets deriving the same identifier is
possible in principle even though no implementation will encounter it by
chance. The registry rule below therefore refuses the collision rather than
assuming it cannot arise.

The salt and info are fixed strings and MUST NOT be varied per device or per
site. The identifier names a **secret generation, not a device**: where one
gateway holds custody for several devices under one secret, every
acknowledgement it issues carries the same `key_id`, and that is correct rather
than a collision. The device is named by `device_id`, which is a separate
field covered by the same MAC.

#### Selection and rotation

A verifier holds a registry of custody generations keyed by `(gateway_custody,
key_id)`, each with status `active`, `verify_only`, or `retired`. It MUST
select by `key_id` and MUST NOT trial-verify against every secret it holds.

At most one generation is `active`. During a rotation the outgoing generation
becomes `verify_only`, so acknowledgements already in flight keep verifying.

**A `retired` generation is a tombstone: it holds the `key_id` and MUST NOT
hold the secret.** Retiring a generation means destroying the secret and
keeping only its identifier. A tombstone therefore verifies nothing — there is
nothing to verify with — and its sole function is to let the verifier answer
*which* refusal applies.

Without the tombstone, `retired_key` is not implementable. A generation simply
deleted from the registry is indistinguishable from one that never existed, so
the only honest answer is `unknown_key`, and the distinction this contract
draws between the two would be unreachable. The distinction is worth the
retained identifier: `unknown_key` says a gateway is presenting a secret this
runtime has never shared with it, which is a misconfiguration or an intrusion;
`retired_key` says the courier is holding evidence acknowledged under a
generation that has since been destroyed, which is a stalled queue and a
different remedy entirely.

**Retention.** A tombstone MUST be retained while any envelope sealed before
that generation was retired remains undelivered, because that is exactly the
window in which an acknowledgement under it can still arrive. An implementation
MAY prune it once no such envelope remains. Tombstones are one identifier each
and accrue only per rotation, so retaining them indefinitely is a conforming
choice and the simpler one.

The registry MUST refuse construction when two generations derive the same
`key_id`. Two cases produce that, and both are refused:

- the same secret bytes configured as both current and previous, which is an
  operator error that would silently collapse the rotation window;
- distinct secrets that derive the same identifier, which is the truncation
  collision above — vanishingly unlikely, and refused rather than assumed away
  because the consequence would be selecting the wrong secret.

This check belongs at registry construction rather than at configuration load:
a derived identifier is not knowable until the secret bytes have been resolved
from the environment, so configuration validation cannot see it.

An implementation MUST NOT accept a `key_id` supplied alongside the secret in
configuration. Accepting one would let a misconfigured or hostile value name a
secret it was not derived from, reintroducing exactly the mismatch derivation
removes.

**Custody is not delivery.** It advances no authoritative state. A runtime MUST
NOT discard an envelope on custody alone and MUST NOT report it as delivered.

### Delivery receipt

The only artifact that advances authoritative status.

| Field | Type | Notes |
| --- | --- | --- |
| `v` | `int` | `1`. |
| `device_id` | `string` | Device the range belongs to. |
| `from_seq` | `int` | First `local_seq` accepted, inclusive. |
| `to_seq` | `int` | Last `local_seq` accepted, inclusive. |
| `range_digest` | `string` | `sha256:` over the concatenation of the **raw 32-byte** `chain_row_digest` values for `from_seq..to_seq`, in ascending `local_seq` order, with no separators and no hex encoding. |
| `accepted_at_ms` | `int` | Authority clock. |
| `key_id` | `string` | Authority receipt key, from the running release. |
| `signature` | `string` | `ed25519:` over the receipt domain. |

**Receipts commit to a contiguous inclusive range.** A receipt over
`from_seq..to_seq` asserts that every `local_seq` in that closed interval was
received and verified. This is what makes the prefix claim true: without
contiguity a receipt over `to_seq` would say nothing about what lies beneath it.

An authority MUST NOT issue a receipt spanning a `local_seq` it did not accept.
Where a batch is incomplete it issues receipts for the contiguous runs it can,
and records the missing sequences as internal-gap findings.

| Batch condition | Outcome |
| --- | --- |
| Contiguous, all verify | One receipt for the whole range |
| Duplicate of an already-receipted range | Re-issue the identical receipt; no new state |
| Partially overlapping an receipted range | Receipt covers the union only if contiguous; otherwise split |
| Non-contiguous (missing interior seq) | Receipts for each contiguous run; missing seqs recorded as internal gaps |
| Reordered within the batch | Accept; ordering is by `local_seq`, not arrival |
| Arriving after a later range was receipted | Accept and receipt; a later receipt never closes an earlier gap implicitly |
| Any row fails signature, digest or chain continuity | Whole batch rejected with reason; **no gap recorded** |

**What a receipt does and does not prove.** A receipt over `from_seq..to_seq`
proves that closed interval and nothing outside it. A receipt for 20..30 says
nothing about 1..19.

The prefix property — truncation detection for everything up to N moving from
heuristic to proof — holds only once the authority holds **verified contiguous
coverage from `local_seq` 1 through N**, assembled from one or more receipts.
An authority MUST track that contiguous frontier per device separately from
individual receipts, and MUST NOT report prefix coverage it cannot assemble.
The frontier, not the newest receipt, is what a truncation finding compares a
checkpoint against.

### Epoch confirmation

States that an epoch was made active, and under whose attribution. It is **not**
a receipt and MUST NOT share its format or key purpose: one says evidence was
recorded, the other says authority became effective. A verifier accepting either
for the other has lost the distinction the provisioning gate depends on.

| Field | Type | Notes |
| --- | --- | --- |
| `v` | `int` | `1`. |
| `device_id` | `string` | Device whose epoch is confirmed. |
| `anchor_epoch_id` | `string` | The epoch made active. |
| `pubkey_hex` | `string` | Anchor active under that epoch. |
| `actor` | `string` | Attribution carried from the registration. |
| `confirmed_at_ms` | `int` | Authority clock. |
| `key_id` | `string` | Authority epoch key, from the running release. |
| `signature` | `string` | `ed25519:` over the epoch domain. |

Anchor lifecycle remains normative in
[device-provisioning/v1.md](../device-provisioning/v1.md).

## Three state models

Delivery status, epoch obligation and evidence findings are independent. A gap
can coexist with later receipts; an epoch quarantine is not an envelope
delivery state.

**Envelope delivery**, per `local_seq`:

```text
sealed ──► pending custody ──► in custody ──► receipted
```

**Epoch obligation**, per `(device_id, anchor_epoch_id)`:

```text
pending ──► confirmed
   └──────► quarantined        (authority holds a different active epoch)
```

`quarantined` is terminal until an operator clears it and MUST NOT be resolved
by retry.

**Registration status at the runtime**, per current epoch, is what the device
can observe of that obligation, and is the value its health surface reports:

```text
pending_authorisation ──► pending_confirmation ──► confirmed
```

`pending_authorisation` means no commissioning reference is held for the
epoch; `pending_confirmation` means the reference is held and the registration
has been sealed for the courier but no epoch confirmation has arrived; and
`confirmed` means a verified epoch confirmation for that epoch is held. The
runtime cannot see the authority's acceptance, a pending pairing, or a
quarantine — only artifacts that reach it — so it MUST NOT report any of those,
and a device that stays `pending_confirmation` is exactly what an authority-side
quarantine or refusal looks like from the device. `disabled` is reported when
evidence is not enabled.

**Evidence findings**, per device, independent of both:

| Finding | Observer | Established by | Provable |
| --- | --- | --- | --- |
| Internal gap | Evidence authority | `local_seq` N and N+2 receipted, N+1 absent | Yes |
| Custodied, unreceipted | Runtime | verified custody acknowledgement with no receipt within policy | Yes, to the runtime holding both states |
| Missed checkpoint | Evidence authority | no checkpoint received within interval plus grace, on the authority's clock | Yes |
| Unexplained silence | Evidence authority | no records, no obligation outstanding | No |
| Proven tail truncation | Evidence authority | a checkpoint asserts `high_water_seq` above the authority's verified contiguous frontier | Yes |

The authority MUST NOT claim `custodied, unreceipted` from the current transport:
the custody acknowledgement is purpose-bound to the runtime and is not sent to
the authority. Conversely, the runtime cannot claim an authority-side internal
gap from its own delivery ledger. A future contract may add a separately
authenticated custody observation, but neither side may infer one today.

Findings are not states an envelope passes through; a device may hold several at
once, and receipting later envelopes does not clear an earlier internal gap.

**Silence is not truncation.** A checkpoint converts unexplained silence into a
missed checkpoint, and a checkpoint asserting sequences the authority never
received converts it into proven truncation. Without a checkpoint, absence
proves nothing and MUST NOT be reported as truncation.

### Gaps arise only from authenticated obligations

A malformed, wrongly-signed, or unknown-device submission MUST be rejected and
security-audited **without creating a device-history gap**. Otherwise an
unauthenticated party manufactures insurer-visible holes by submitting rubbish.

A runtime records local failure rows only for delivery failures of envelopes it
sealed. Detecting missing sequences is the authority's responsibility, because
only it can see what did not arrive.

## Adversarial outcomes

Normative. Every row is a required test vector.

| Condition | Required outcome |
| --- | --- |
| Replayed envelope (same `device_id`, `local_seq`, digest) | Idempotent accept; no duplicate chain state; re-issue existing receipt |
| Envelope with same `local_seq`, different `chain_row_digest` | Reject; record as conflict; do not overwrite |
| Reordered batch | Accept; order by `local_seq` |
| Rollback: `local_seq` below the highest receipted, unseen digest | Reject; security-audit; no gap |
| Wrong device: `device_id` not registered | Reject; security-audit; no gap |
| Envelope signature valid, chain row signature invalid | Reject whole batch; no gap |
| `chain_row_digest` mismatch | Reject whole batch; no gap |
| Wrong epoch: envelope naming an epoch the device never held, or whose `key_id` is not that epoch's anchor | Reject; leave epoch obligation `pending`. An epoch the device *did* hold is accepted and attributed to it. |
| Conflicting epoch: registration for an active epoch with a different key | Quarantine; never apply |
| Registration whose `commissioning_digest` resolves to no held authorisation, and none is held for that device and epoch | Retain pending; `accepted` with no confirmation; no gap |
| Registration naming a digest other than the authorisation held for that device and epoch, or resolving to one naming a different device, key or epoch | Reject `commissioning_digest_mismatch`; no gap |
| Commissioning authorisation submitted from the device side | Reject at transport; the courier vocabulary does not include it |
| Custody ack with invalid MAC | Reject `bad_authenticator`; envelope stays `pending custody` |
| Custody ack naming a `key_id` the registry does not hold | Reject `unknown_key`; distinct from a bad MAC, because the causes and the operator remedies differ |
| Custody ack whose `key_id` is held for a different purpose | Reject `wrong_purpose` |
| Custody ack naming a generation held as a `retired` tombstone | Reject `retired_key`. The tombstone holds the identifier and not the secret, so the artifact is unverifiable by construction; the distinction from `unknown_key` is what makes a stalled courier queue diagnosable |
| Custody ack whose `key_id` is not `hkdf-sha256:` followed by 32 lowercase hex characters | Reject `malformed`; shape is checked before the registry is consulted |
| Custody ack whose `mac` is not `hmac-sha256:` followed by 64 lowercase hex characters — wrong length, non-hex, or uppercase | Reject `malformed`; shape is checked before the MAC is compared, so a value that was never a candidate authenticator is not reported as a failed authentication |
| Custody ack issued under the previous generation during a rotation window | Accept; selected by `key_id` alone, with no trial verification against the active secret |
| Custody ack issued under the active generation while a previous is still `verify_only` | Accept; selected by `key_id` alone |
| Custody ack for an unknown `local_seq` | Runtime ignores; security-audit |
| Receipt signed under a non-receipt key purpose | Reject |
| Epoch confirmation signed under the receipt purpose | Reject |
| Checkpoint `high_water_seq` below one already accepted | Reject as rollback |
| Checkpoint `issued_at_ms` regressing relative to the previous accepted checkpoint | Accept, flag device clock anomaly, including across a reboot; the deadline is unaffected because it runs on the authority clock |
| Checkpoint signed under the gateway custody secret | Reject; not a device signature |
| Unrecognised `v` | Reject |
| Unknown field present | Reject |

### Test vectors

Vectors live in [`evidence-exchange/vectors/`](vectors/) as JSON, one file per
artifact, each carrying a `valid` case and one case per adversarial row above.
Every case records the artifact object, the canonical bytes as lowercase hex,
the expected verifier outcome, and why.

**Every case in a file MUST carry the same keys.** Where a case has nothing to
say for a key it carries the key with a null value rather than omitting it — an
acceptance records `reject_reason: null`. A family whose cases differ in shape
lets a case quietly lose a field, and a case that has lost a field may have lost
the defect it was written to carry. Uniform shape is what makes that mechanically
detectable rather than a matter of reading every case.

Where a file names the refusal a case must produce, that name is normative: it
is what distinguishes `unknown_key` from `retired_key` in an implementation, and
a consumer that maps case names to outcomes in its own test has written a second
copy of this contract. Each file names its domain, its
canonicalisation, and the published test seed its signatures were produced
with.

Producers and verifiers in every repo MUST reproduce the canonical bytes
exactly before comparing signatures. A canonicalisation disagreement surfaces
as a signature failure and is diagnosed as tampering, which is the most
expensive way to discover that two implementations sort keys differently.

All seven artifact files exist — one per artifact plus the commissioning
authorisation the registration binds — and every valid case's authenticator was verified
against the seed its file names after being written, not merely as it was
constructed. The commissioning authorisation file is verified by the authority
alone, against the artifact it receives through the commissioning path; its
`commissioning_digest_mismatch` companion in the registration file is decided
by resolution against a held authorisation, not against one presented
alongside. The delivery envelope's embedded chain-row signature verifies over
`canonical_json` on its own terms, and its `event_hash` reproduces from those
same bytes.

Key purposes are demonstrated as disjoint rather than asserted: the receipt file
carries a case signed with the epoch key and the confirmation file one signed
with the receipt key, both expected to be rejected.

**Some defects live in receiver state rather than in bytes**, and those belong
in [`vectors/receiver-state/`](vectors/receiver-state/) rather than beside a
valid case. Custody purpose separation is one: because `key_id` is derived from
the custody secret, an acknowledgement whose identifier is held under another
purpose is byte-identical to a conforming one, so emitting it as a wire case
would produce a rejection indistinguishable from the acceptance — precisely
what this contract forbids above. It is tested as stored state plus one
conforming artifact, as anchor quarantine already is.

Commissioning resolution is another. Whether a registration is applied,
retained pending, or refused depends on the authorisations the authority
already holds, so
[`vectors/receiver-state/commissioning-resolution.json`](vectors/receiver-state/commissioning-resolution.json)
carries one case per row of the resolution table above — the held state, the
arriving artifact and its source, the outcome, whether a confirmation is
issued, and that nothing is quarantined or recorded as a gap — plus the
device-side submission of an authorisation, which the transport refuses. Its
artifacts reuse the published registration and authorisation vectors, with one
registration newly signed under the published device seed so that a resolved
authorisation naming another key is exercised.
`scripts/check-evidence-commissioning-vectors` verifies every signature and
digest binding and recomputes every outcome from the contract.

**`custody-acknowledgement.json` carries the rotation pair.** Two cases must be
accepted, one under the active generation and one under the `verify_only`
previous, each selected by `key_id` alone. A third,
`key_id_not_derived_from_signing_secret`, is the discriminating case: its MAC
verifies under the *active* secret while its `key_id` derives from the
*previous* one. A verifier that selects by `key_id` checks the previous secret
and refuses it; a verifier that trial-verifies against everything it holds finds
the active secret and wrongly accepts. That case is what distinguishes a
conforming implementation from one that merely appears to work.

## Fail-closed and fail-open

The direction differs by what is at stake:

- **Granting authority fails closed.** An unreachable authority leaves an epoch
  `pending`. Commands and provisioning approvals do not reach firmware. A
  conflicting active epoch quarantines for operator review.
- **Recording what happened fails open.** An unreachable authority MUST NOT
  block, delay or gate a Tier C/D action. Evidence accrues locally, in order,
  and forwards later. Safety first, evidence second.

The gateway may delay; it can never alter. A delay MUST remain detectable
downstream rather than being absorbed into a healthy status.

## Registry ownership

The evidence authority MUST independently retain the `(device_id,
anchor_epoch_id, pubkey_hex)` binding. It cannot verify a chain against an
anchor it does not hold, and an authority that must ask another party what to
trust is not independent.

The fleet manager MAY authorise commissioning and MAY hold its own record for
operational purposes. It MUST NOT be the sole registry: making the commercial
control plane authoritative for verification keys would couple the independent
evidence channel back to the party the channel exists to be independent of.

## Invariants

- The gateway holds no evidence-authority key and signs no envelope.
- Custody never advances authoritative delivery state.
- Every artifact has a disjoint key purpose; cross-purpose verification fails.
- A gap is created only from an authenticated obligation.
- Checkpoints are device-signed; a gateway-authenticated checkpoint is invalid.
- Receipts commit to contiguous inclusive ranges.
- Evidence never gates a safety action.
- Envelope signatures are end-to-end; forwarded bytes are byte-identical.
- No operator-visible surface exposes the authority's identity, endpoint,
  location, credentials or custody; generic delivery health remains visible.
- The commissioning authorisation never crosses onto the device; the device
  holds and presents only its digest.

## Chain row format

This contract wraps an [`evidence/v2`](../evidence/v2.md) row.

An earlier revision named `evidence/v1` and, more seriously, its vectors carried
an abbreviated five-field object that matched no chain contract at all — missing
`prev_event_hash`, `schema_version` and `sequence_num`. A receiver implemented
against those bytes would have rejected every real row. The vectors now carry
real v2 rows, and `chain_row_digest`, every envelope signature, the custody
acknowledgement's `envelope_digest`, and the receipt's `range_digest` are all
recomputed from them.

**Gateway forwarding behaviour is unchanged.** The courier still forwards bytes
unaltered and still signs nothing on the envelope. Only the bytes it forwards
are different, so its vector fixtures change while its logic does not.

## Open questions

Named rather than silently decided:

- **Checkpoint defaults.** The 900-second interval and doubled grace are
  proposed, not measured. They should be set against observed site link
  behaviour before implementation.
- **Batch size ceiling.** Receipts commit to contiguous ranges; the maximum
  rows per batch is a transport concern this contract does not fix.
- **Authority-side authorisation ingress.** The commissioning path delivers
  the signed authorisation to the evidence authority, and this contract places
  that path with the `commissioning_authority` registry: administrative,
  organisation-level, outside the exchange. Its transport, authentication and
  audit are not specified anywhere yet. Until they are, an authority holds
  authorisations only by whatever means its operator loads the registry, and
  no conformance claim about registration end to end is possible.
- **Matching without the reference.** An authority could pair a registration
  to a held authorisation by `(device_id, pubkey_hex, anchor_epoch_id)` alone,
  and nothing would need delivering to the device. The digest is retained
  because it binds a registration to the one authorisation it was made under
  — a device cannot be registered under an authorisation the commissioner
  superseded — and because removing it changes signed bytes across every
  consumer. If that binding is ever judged unnecessary, this is the change.
- **Authority key rotation cadence.** Distribution is settled — new authority
  keys arrive only in a signed release, never over the exchange. What is not
  settled is cadence and overlap: how long an outgoing key stays `verify_only`,
  and therefore the oldest release still able to verify current artifacts. That
  bound is a release-policy question, not a wire-format one.
