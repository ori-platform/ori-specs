# Device Provisioning Lifecycle Contract v1

> Status: Contract target. No implementation is claimed until the
> implementing repositories cite this contract from a tagged release.

This contract defines the lifecycle of a firmware device's **anchor**: how an
identity is first registered, what happens when it re-appears, and what it
takes to change or revoke it.

It exists because registration is the one moment where a receiver decides
which key it will trust for everything afterwards. Telemetry verification,
command authority, and evidence attribution all resolve to the anchor stored
here, so a lifecycle that quietly overwrites an anchor — or quietly clears a
revocation — undermines every guarantee built on top of it.

Scope: the state machine and its obligations. The wire formats it operates on
are defined in [firmware-telemetry/v1.md](../firmware-telemetry/v1.md)
(capability manifest, telemetry envelope, trust grades) and
[firmware-commands/v1.md](../firmware-commands/v1.md) (provisioning approval,
command authority).

## Terms

| Term | Meaning |
| --- | --- |
| `device_id` | The stable physical/fleet identity. It never changes for a given device. |
| **anchor** | The `(device_id, device public key, posture, capability_hash)` tuple a receiver trusts. |
| **key epoch** | A period during which the device's public key is constant. A new device key starts a new key epoch. |
| **manifest epoch** | A period during which `capability_hash` is constant. A new manifest starts a new manifest epoch **within** the same key epoch. |
| **reinstatement** | The explicit, audited act of returning a revoked identity to service. |

A key epoch may contain many manifest epochs. A manifest epoch never spans two
key epochs.

## Epoch Identity

Epochs are compared across independent stores, so they MUST be values, not
positions. Both identifiers below are **deterministically derived**: two stores
holding the same anchor compute the same identifier without coordinating, which
is what makes "both accepted the same epoch" a checkable claim rather than an
assertion.

Both are SHA-256 over canonical JSON bytes as defined in
[firmware-telemetry/v1.md](../firmware-telemetry/v1.md), encoded lowercase hex
with a `sha256:` prefix — the same construction as `capability_hash`.

### `key_epoch_id`

Over the identity and its key:

```json
{"device_id":"ori-fw-7c9f2b3a","public_key_b64":"<base64-32-byte-key>","v":1}
```

`key_epoch_id` changes **only** when the device key changes. It is the epoch
that governs telemetry replay state.

### `anchor_epoch_id`

Over the whole anchor:

```json
{"capability_hash":"sha256:<64-lowercase-hex>","device_id":"ori-fw-7c9f2b3a","posture":"sealed_flash","public_key_b64":"<base64-32-byte-key>","v":1}
```

`anchor_epoch_id` changes when the key, posture, **or** capability hash
changes. It identifies the exact anchor a receiver accepted, and it is the
value cross-store agreement is expressed in.

Posture is included because a device that becomes `sealed_flash` is materially
a different trust proposition from the same device in `development`, even with
an unchanged key and manifest.

Consumers MUST compare epochs by these identifiers. Comparing by arrival order,
row id, or timestamp is not interoperable across stores.

## Identity And Revocation

- `device_id` is the stable identity. Manifests, capability hashes, and keys
  change beneath it; the identity does not.
- **Revocation belongs to the identity.** It survives reconnects, new
  manifests, key changes, and any registration attempt.
- Revocation MUST NOT be clearable as a side effect of registration. A device
  re-publishing its manifest is not a decision to trust it again.
- Returning a revoked identity to service is **reinstatement**: an explicit
  operation by an authenticated operator, recorded (see [Audit](#audit)).

This is the rule the rest of the contract exists to protect. A receiver that
erases revocation on registration offers no revocation at all, because any
device able to publish can undo its own.

## Anchor States

An identity holds at most one **active** anchor and at most one **pending**
anchor at a time. Separately, the **identity itself** carries a revoked flag:
while it is set, nothing is accepted and no anchor may become active.

| State | Meaning |
| --- | --- |
| **pending** | Registered and verified, but not approved. Nothing is accepted against it: no telemetry, no commands, no evidence. |
| **active** | Approved and unrevoked. The anchor all verification resolves against. |
| **revoked** | A retained anchor that was active when the identity was revoked. Held so reinstatement has something to return to. Never used for acceptance while the identity is revoked. |
| **superseded** | A formerly active anchor retained in history. Not used for new acceptance while in this state. |
| **discarded** | A pending candidate replaced before promotion. Retained in history; was never active, so no evidence is attributed to it. |

`superseded` and `discarded` are not terminal **within the identity's current
key epoch**: an identity that returns to a configuration it previously held
under its current key re-registers that same anchor epoch, which brings it back
to **pending**. An anchor belonging to a superseded key epoch is not reachable
this way and stays where it is. See
[Re-registering an anchor the identity has held before](#re-registering-an-anchor-the-identity-has-held-before).

**Promotion** is the operator act that makes a pending anchor active. It is a
trust transition and is audited. Promotion of a new anchor moves the previous
active anchor to **superseded**; it is retained, never deleted.

A pending anchor MUST NOT affect anything about the active one — not
acceptance, not freshness, not authority. An identity with an active anchor and
a pending anchor continues operating entirely under the active anchor until
promotion.

## Registration Lifecycle

A receiver presented with a verified capability manifest for `device_id` MUST
resolve exactly one of these cases.

| Incoming registration | Required behaviour |
| --- | --- |
| No existing anchor | Store as **pending**. Nothing is accepted until promotion. |
| Anchor matches the **active** anchor exactly | **Idempotent no-op.** Succeed and change nothing — not state, not freshness, not revocation, not history. |
| Anchor matches the **pending** anchor exactly | **Idempotent no-op.** Re-publishing does not re-approve or promote. |
| Same key, new `capability_hash` (new `anchor_epoch_id`, same `key_epoch_id`) | Store as **pending** candidate. The active anchor **remains active**. Preserve revocation and freshness. |
| Same key, new `capability_hash`, **a different pending candidate already exists** | The arriving anchor **replaces** the pending candidate; the replaced one is recorded **discarded**. The active anchor is untouched. |
| **New key** (new `key_epoch_id`) | **Refuse.** Requires an explicit re-provisioning transaction. |
| Revoked identity, **any** of the above | **Refuse.** Requires explicit reinstatement. |

### Telemetry during a pending manifest epoch

While a new manifest epoch is pending, the device is still bound to the active
anchor. Therefore:

- Telemetry whose `capability_hash` equals the **active** anchor's MUST continue
  to be accepted normally.
- Telemetry whose `capability_hash` equals the **pending** anchor's MUST be
  **refused** until promotion. It is not an error on the device's part — it has
  published a manifest an operator has not yet approved — but accepting it would
  let a device grant itself a new capability surface by publishing.
- After promotion, the roles invert: the promoted anchor is active, and
  telemetry against the superseded hash is refused.

Freshness is untouched throughout, because `key_epoch_id` never changed.

### Replacing a pending candidate

If a pending anchor exists and a **different** manifest arrives under the same
key, the newly arrived anchor **replaces** the pending candidate. The active
anchor is untouched.

Replacement is safe because a pending anchor grants nothing: discarding one
loses no authority. Refusing instead would strand the identity — a device that
published a manifest an operator never promoted could not publish a corrected
one without manual intervention.

The replaced candidate is recorded in history as **discarded**, distinct from
**superseded**: it was never active, so no evidence was ever attributed to it.
Replacement is not itself a trust transition and does not require actor or
reason, but implementations SHOULD record it, because a device rapidly
replacing its own pending manifest is a signal worth seeing.

## Operations

Four operator operations change trust. Each is audited, and **promotion is
always a separate operation** — no other operation may activate an anchor as a
side effect.

### Promotion

The only path to **active**. Takes a pending anchor and activates it, moving
any previously active anchor to **superseded**.

Promotion MUST refuse if the identity is revoked.

### Re-provisioning (key replacement)

Used when the device's key has changed — for example after its NVS was erased
and it generated a new key.

1. The operator confirms the device identity **independently** of the manifest
   (see [above](#why-a-changed-key-cannot-arrive-through-ordinary-registration)).
2. The new-key anchor is stored as **pending**, with a new `key_epoch_id`.
3. **The previously active anchor remains active until promotion.**
4. Promotion activates the new anchor; the old becomes superseded.

Step 3 is deliberate. A device that has genuinely rotated its key cannot sign
against the old anchor, so nothing will verify under it — but leaving it active
means an unpromoted new key is trusted for nothing. Telemetry under the pending
key is refused with `epoch_not_promoted` until an operator acts.

Re-provisioning MUST refuse if the identity is revoked. Reinstate first.

### Revocation

Takes an identity out of service.

1. The identity's revoked flag is set.
2. The **active** anchor moves to **revoked**, retained in history so
   reinstatement has something to return to.
3. Any **pending** candidate is **discarded** — an unpromoted candidate must not
   survive a revocation and become promotable later.

After revocation the identity has no active and no pending anchor. Nothing is
accepted.

An identity that was registered but never promoted has no active anchor to
retain; revocation still sets the flag and discards the pending candidate,
leaving no retained anchor.

### Reinstatement

Returns a **revoked identity** to service. Reinstatement:

1. clears the identity's revoked flag, and
2. moves the retained **revoked** anchor back to **pending**.

It **never activates anything**. That keeps one invariant true everywhere: an
anchor becomes active only through promotion. Moving the retained anchor to
pending — rather than leaving it in `revoked` — is what makes the next step
legal, since promotion accepts only a pending anchor.

If no retained anchor exists — the identity was revoked before it was ever
promoted — reinstatement clears the flag alone, and the identity returns to the
same state as a never-registered one: it must register again before it can be
promoted.

If the device's key has also changed, the reinstated pending anchor is the wrong
one; re-provisioning then replaces it as the pending candidate before
promotion.

| Situation | Required sequence |
| --- | --- |
| Revoked, key unchanged, prior anchor still correct | reinstate → promote the retained anchor |
| Revoked, manifest changed | reinstate → register the new manifest (replaces the reinstated pending candidate) → promote |
| **Revoked and key changed** | **reinstate → re-provision (pending) → promote** — all three |

### Why a changed key cannot arrive through ordinary registration

A new key under an existing `device_id` is indistinguishable, on the wire,
from an attacker presenting a key they control for a `device_id` they do not
own. The manifest is self-signed: verifying it against the key carried inside
it proves internal consistency, never provenance.

Accepting a changed anchor through ordinary registration would therefore let
anyone who can publish to the manifest topic take over an identity. Key
replacement MUST be an explicit re-provisioning transaction with independent
operator confirmation of the device identity — for example the public key read
from the device itself over a physically attached channel, rather than from
the manifest asserting it.

## Freshness Across Epochs

Freshness rules are defined in
[firmware-telemetry/v1.md](../firmware-telemetry/v1.md) and
[firmware-commands/v1.md](../firmware-commands/v1.md); this section states how
they interact with epochs and adds no new counters.

- Telemetry replay state is per `device_id` **and key epoch**. A **new key
  epoch MAY begin with fresh telemetry counters**; the previous epoch's
  counters remain historical and MUST NOT be usable to accept new telemetry.
- A **new manifest epoch MUST NOT reset telemetry freshness.** The key is
  unchanged, so the replay window is unchanged. Resetting on a manifest change
  would let a manifest publish re-open a closed replay window.
- The command high-water mark is per `device_id`, **not** per key, and
  continues across command-key rotation. Rotating the runtime command key MUST
  NOT reset `cmd_seq`.

Note the deliberate asymmetry: the **device** key epoch governs telemetry
freshness, while **runtime command-key** rotation does not affect `cmd_seq`.
They are different keys with different rotation events.

## Anchor History

- Anchors MUST NOT be overwritten in place. Superseded anchors are retained in
  **append-only history**.
- History MUST be sufficient to answer, for any past evidence, which anchor was
  current when it was produced. Evidence outlives the anchor that authorised
  it; an overwritten anchor makes old evidence unverifiable and silently
  unattributable.
- Retaining history is what makes a key epoch meaningful: the old epoch remains
  inspectable while being unusable for new acceptance.

### What is immutable, and what may change

An anchor record has two kinds of field, and "MUST NOT be overwritten in place"
above governs only the first.

- **Identity fields** — `device_id`, the public key, `posture`,
  `capability_hash`, and the derived `anchor_epoch_id` — are **immutable** once
  written. An anchor's meaning never changes, which is what makes an
  `anchor_epoch_id` a stable name for a specific trust proposition.
- **State** is the anchor's current position in the lifecycle and **does**
  change as it moves through the states above.

The append-only history this document requires is the **transition log**. It is
the record that is never rewritten; the state field is a projection of where
each anchor currently sits.

An anchor epoch has exactly one record. This has to be stated because an anchor
epoch is derived from the key, posture, and capability hash, so an identity
returning to a configuration it previously held arrives at an epoch it already
has a record for. Without a rule, one implementation would reuse that record
and another would add a second, and the two would disagree about a device's
history while both believed they were retaining it.

### Re-registering an anchor the identity has held before

**Scope.** This applies only when the arriving anchor's `key_epoch_id` equals
the identity's **current** key epoch. It creates no new path for a key change:
ordinary registration still refuses any changed key
(`key_change_requires_reprovisioning`), and re-provisioning still refuses a key
the identity has previously held (`key_epoch_reused`). An anchor belonging to a
superseded key epoch is therefore unreachable by registration, and this section
does not make it reachable.

Within the current key epoch, an anchor epoch whose state is `discarded` or
`superseded` returns to **pending** when it is registered again. It does not
resume its former state, and promotion remains the only path to active.

Returning is permitted rather than refused because refusing strands devices. A
device that published a bad manifest and needs to revert to its previous one —
under an unchanged key, which is not a takeover — must be able to. Refusing
would force an operator to replace a key that was never compromised in order to
roll back.

For a `discarded` anchor, no evidence is attributed to it, because it was never
active. That is not the same as being inconsequential: re-registering it
replaces whatever pending candidate currently exists, discarding that one, and
an anchor may have been discarded for a reason an operator cared about.
Re-registration grants no authority, but it is not a neutral act, and the
judgement belongs at promotion.

For a `superseded` anchor there is a consequence implementations MUST handle.
The anchor **was** active, so evidence is attributed to it, and once its record
reads `pending` the state field no longer shows that it ever was. Therefore:

- Implementations MUST be able to determine, for any anchor epoch, whether it
  was ever active and **over which intervals**. This follows from the history
  requirement above and MUST be answerable from the transition log.

Two questions must not be conflated, because they are asked at different times
and have different answers:

| Question | Decided against |
| --- | --- |
| May this arriving telemetry or command be accepted **now**? | The anchor's **current** state — `pending` gives `epoch_not_promoted`, `superseded` gives `epoch_superseded` |
| Was this **already recorded** evidence authorised when it was produced? | Whether the anchor was active at that evidence's position in a **receiver-anchored** ordering (see below) |

Deciding the second question from current state would read correctly signed
history as unauthorised the moment a device re-registered an old manifest — the
anchor would read `pending`, and evidence legitimately produced while it was
active would appear never to have been authorised.

**The ordering MUST NOT be device wall-clock time.** Per
[firmware-telemetry/v1.md](../firmware-telemetry/v1.md), `emitted_at_ms` is an
optional device wall-clock timestamp, `null` when no trusted clock exists and
advisory otherwise — and it is supplied by the same party whose authorisation
is being decided. Using it would let a device place its own
evidence inside an interval when its anchor was active, which is precisely the
question at issue. Conforming implementations MUST resolve the interval against
one of:

- the receiver's recorded ordering of anchor transitions relative to its
  recorded ingest of that evidence;
- a receipt time assigned by the receiver, not by the device; or
- the evidence's position in the Verity hash chain, which is receiver-ordered
  by construction.

Device-reported timestamps MAY be retained as observations and MAY be shown to
operators. They MUST NOT decide authorisation.

A conforming implementation MAY instead keep a durable marker on the anchor
record, provided both questions can still be answered. What is forbidden is
having no way to answer them.

## Audit

**Every trust transition MUST be audited** — not only the dramatic ones. A
transition is any operator act that changes what a receiver will accept:

| Transition | Audited |
| --- | --- |
| Promotion (initial, manifest-epoch, or post-re-provisioning) | MUST |
| Re-provisioning (key replacement, new `key_epoch_id`) | MUST |
| Revocation | MUST |
| Reinstatement | MUST |
| Registration (storing a pending anchor) | SHOULD |
| Replacing a pending candidate | SHOULD |

Registration is only SHOULD because it is device-initiated and grants nothing;
the others are operator decisions that change acceptance.

Each audited transition MUST record:

- **actor** — the authenticated operator responsible,
- **reason** — why the transition was made,
- **timestamp**,
- **`anchor_epoch_id`** before and after (absent where there was no prior
  anchor),
- **`key_epoch_id`** after, so key changes are greppable without recomputing.

Auditing only the exceptional transitions would leave the ordinary ones —
initial approval and manifest promotion — as the unattributed path an attacker
would prefer. An unattributed anchor change is indistinguishable from a
compromise after the fact.

## Authority And Cross-Store Consistency

- The **runtime is the provisioning authority.** It decides registration,
  approval, revocation, and reinstatement.
- **Verity enforces and evidences** the transition. It does not independently
  decide it, and it MUST NOT accept firmware-derived action evidence for an
  identity whose approved, unrevoked anchor it does not hold.
- A provisioning approval MUST NOT be published until **both** the runtime and
  Verity have accepted the **same `anchor_epoch_id`**. Publishing earlier admits
  a window where firmware holds authority the evidence chain will not honour.
  Because the identifier is derived, both stores can confirm agreement without
  exchanging anything beyond it.
- Because two stores cannot be updated atomically, implementations MUST keep an
  **outbox or reconciliation record** so an interrupted transition is
  recoverable and its outcome deterministic rather than discovered later.

### Failure semantics

Cross-store failure is not one behaviour. What the runtime does when Verity is
unreachable depends on **what kind of authority is in play**, because the
safe direction differs:

> **Fail closed on granting or changing authority; fail stable on previously
> confirmed authority; fail immediately on withdrawal of authority.**

**Granting or changing authority** — promotion, and the promotion half of
re-provisioning — MUST **fail closed**. The approval MUST NOT be published until
Verity confirms it holds the identical `anchor_epoch_id`. If Verity is
unreachable, the transition stays **pending** in the durable outbox and is
retried with idempotency. The runtime MUST NOT substitute the previous epoch and
MUST NOT publish optimistically: an unconfirmed grant is
[`epoch_not_confirmed`](#error-semantics), not a provisional yes.

**Previously confirmed authority** — an anchor whose epoch both stores have
already accepted — MUST **fail stable**. It remains operational during a Verity
outage. Temporary unavailability of the evidence store MUST NOT revoke
established trust; a confirmed active epoch keeps working while confirmation of
*new* transitions is deferred.

**Withdrawal of authority** — revocation — MUST **fail immediately**, but
"immediately" applies to the runtime's own enforcement, not to the evidence
store it may not be able to reach. Concretely:

- The runtime withdraws authority **locally at once**: the identity stops being
  accepted the moment it is revoked. A safety withdrawal MUST NOT depend on
  Verity availability.
- The revocation is **queued for durable propagation** and delivered to Verity
  when it is reachable again. It does not await confirmation of an
  `anchor_epoch_id` and publishes no grant — there is nothing for the two
  stores to agree on, only a withdrawal to deliver.
- Because an unreachable Verity cannot learn the revocation immediately, Verity
  MAY **quarantine** firmware-derived evidence it receives for that identity
  during the unresolved interval — between the runtime's local withdrawal and
  Verity learning of it — rather than accept it under an anchor the runtime has
  already revoked.

### Confirming an approval across the two stores

The state machine below governs **approval confirmation only** — the grant of a
new or changed active epoch (promotion, and the promotion half of
re-provisioning). Revocation follows the separate propagation rules above; it
does not enter these states, because it awaits no epoch agreement and publishes
no grant.

A grant awaiting cross-store agreement occupies one of these states. They are
named to avoid colliding with the anchor lifecycle's own `pending` state, which
is a different thing:

| State | Meaning |
| --- | --- |
| **confirmation_pending** | Awaiting Verity's confirmation of the same `anchor_epoch_id`. Retried idempotently from the outbox. The grant is not published. |
| **confirmed** | Both stores accepted the same `anchor_epoch_id`. The grant is published and operational. |
| **quarantined** | Reconciliation found the two stores disagree about the epoch. Held for operator review. |

- Retry MUST be **idempotent**: re-sending a confirmation for an epoch Verity
  already holds is a no-op, never a duplicate or an error, so a crash between
  send and record cannot double-apply or wedge the grant.
- Reconciliation MUST **detect disagreement** — the two stores holding different
  `anchor_epoch_id` values for the same identity — and **quarantine** the grant
  for operator review. It MUST NOT overwrite either store to force agreement; a
  silent overwrite would destroy the evidence of divergence an operator needs.
- A `confirmation_pending` grant that cannot confirm within an
  implementation-defined timeout MUST become **operator-visible**, distinct from
  a `confirmed` one, so a stuck grant surfaces rather than lingering unnoticed.
- Crash recovery MUST be deterministic: on restart, an interrupted grant is
  resolved from the outbox to exactly one of these three states, never left in
  an ambiguous condition discovered only when evidence is later rejected. A
  queued revocation is likewise recovered and re-delivered, independently of any
  grant confirmation.

## Consumer Obligations

Consumers MUST:

- refuse telemetry, commands, and evidence for an identity that is unknown,
  unapproved, or revoked;
- treat a **key change** arriving through ordinary registration as a rejection,
  and never let ordinary registration **replace the active anchor** — a
  same-key capability change is permitted, but only as a pending candidate;
- preserve revocation across every registration path;
- record the `anchor_epoch_id` alongside accepted evidence, so attribution
  survives later transitions;
- refuse anything citing a pending or superseded anchor, with the codes above.

Consumers MUST NOT:

- clear revocation as a side effect of any automatic path;
- reset telemetry freshness on a manifest-only change;
- reset `cmd_seq` on command-key rotation;
- accept an approval whose `anchor_epoch_id` the evidence store has not
  accepted;
- promote a pending anchor as a side effect of the device re-publishing it;
- activate an anchor through any operation other than promotion — in
  particular, reinstatement returns an anchor to **pending**, never to active;
- leave a pending candidate promotable across a revocation.

## Error Semantics

These codes are **normative**: a conforming implementation MUST use them for
the conditions below, so a refusal means the same thing in every store.

Each condition is scoped precisely, because a changed `capability_hash` is a
**permitted** transition (it becomes a pending anchor) while a changed key is a
**refusal**. A single "anchor mismatch" code covering both would report a
routine manifest update as a security event and hide a key takeover among the
noise.

| Condition | Error | Refusal? |
| --- | --- | --- |
| Identity is revoked | `device_revoked` | Yes |
| `key_epoch_id` differs from the stored anchor's | `key_change_requires_reprovisioning` | Yes — ordinary registration may never change a key |
| Telemetry or command cites a `capability_hash` that is neither the active nor a known anchor | `unknown_anchor_epoch` | Yes |
| Telemetry or command cites the **pending** anchor before promotion | `epoch_not_promoted` | Yes — not a fault, awaiting operator approval |
| Telemetry or command cites a **superseded** anchor | `epoch_superseded` | Yes |
| An audited transition is attempted without actor or reason | `audit_required` | Yes |
| An approval would be published before the evidence store accepted the same `anchor_epoch_id` | `epoch_not_confirmed` | Yes |
| Re-provisioning submits the identity's **current** key | `same_key_not_a_rotation` | Yes |
| Re-provisioning submits a key the identity has **held before** | `key_epoch_reused` | Yes |

A changed `capability_hash` under an unchanged key is **not** an error. It
produces a pending anchor and, until promotion, `epoch_not_promoted` for
anything citing it.

### Why re-provisioning refuses a key that is not new

Re-provisioning exists to replace a key. Submitting one that is not a
replacement is refused rather than treated as a no-op, and the two cases are
named separately because they fail for different reasons.

`same_key_not_a_rotation` means nothing is being replaced. Accepting it would
create a pending anchor for a key that is already active, leaving the registry
and the anchor history disagreeing about which anchor is trusted — a
split-brain produced by an operation that changed nothing.

`key_epoch_reused` means the identity has used the submitted key before. The
key rotated away from may be exactly the one that was compromised, so
accepting a return to it would make rotation reversible by whoever still holds
it. An implementation MUST check the identity's whole anchor history, not only
its current anchor; checking only the current key would refuse the immediate
predecessor while accepting one from two rotations ago.

Neither condition is affected by revocation, which is evaluated first:
re-provisioning a revoked identity is `device_revoked` regardless of the key
submitted.

The names in this table are the **reported** condition identifiers. A store's
internal return values need not be these strings, but whatever it surfaces at
the contract boundary — to an operator, an API caller, or an audit record —
MUST be. Two implementations that refuse for the same reason under different
names have not agreed on anything an operator can act on.

## Required Implementation Artifacts

Before an implementation may claim this contract:

- shared cross-repo lifecycle vectors covering **duplicate registration,
  manifest change (pending and promoted), key rotation, revocation, and
  reinstatement**, agreed byte-for-byte by every implementing repository;
- `key_epoch_id` and `anchor_epoch_id` vectors, so independent derivations are
  proven identical rather than assumed;
- evidence that revocation survives each registration path;
- evidence that an anchor change through ordinary registration is refused;
- evidence that a pending anchor grants nothing until promotion;
- evidence that revocation discards any pending candidate and retains the
  formerly active anchor;
- evidence that reinstatement returns the retained anchor to pending and
  activates nothing;
- evidence that a replaced pending candidate is retained as discarded and never
  becomes active without explicit re-registration and promotion;
- evidence that re-provisioning refuses both the current key and any key the
  identity has previously held;
- evidence that re-registering a `discarded` or `superseded` anchor **in the
  current key epoch** returns it to pending and activates nothing;
- evidence that re-registration opens no path to an anchor in a superseded key
  epoch;
- evidence that an anchor which was active remains identifiable as
  having-been-active, with its active intervals, after it has been superseded
  **and re-registered**, so already-recorded evidence produced under it is not
  later read as unauthorised.

The corpus satisfying these lives at
`ori-runtime/tests/fixtures/device_lifecycle_vectors.json`, generated by
`ori-runtime/scripts/generate_device_lifecycle_vectors.py` and mirrored
byte-for-byte into `ori-verity/tests/fixtures/`. Its SHA-256 is pinned in both
repositories: pinning it in one alone would not detect divergence, because
each copy would still match its own stale constant.

Scenario expectations in that corpus are authored from the sections of this
document, not recorded from an implementation. A corpus produced by running a
store certifies whatever that store does, including its defects, and cannot
detect that the store is wrong.

Adoption is partial and tracked rather than assumed. ori-verity derives both
epoch identifiers from the shared bytes but does not yet implement the anchor
lifecycle, and it declares the scenarios it does not execute in an exact list
that fails when the corpus gains a case nobody has triaged.
