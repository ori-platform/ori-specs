# Operator Socket v3

> Status: maturity `draft`; compatibility `amendable`; adoption: none
> recorded; proof: end-to-end `none`, HIL `none`, production `none`. Record:
> [status/operator-socket/v3.json](../status/operator-socket/v3.json).

The runtime's operator-facing bridge: how a local operator tool invokes it, the
response and error envelopes, the exit mapping, the operations it serves, and
the authenticated local operator socket through which a person at the device
submits the commissioning reference, a Tier C reconciliation, and the approver
registry's local operations.

## What changed from v2

[v2](v2.md) refuses every operation except `reconcile_tier_c` and
`evidence_commission`, while
[tier-c-approvers/v1.md](../tier-c-approvers/v1.md) delivers the approver
registry's local operations through this socket. v3 adds them under
[Approver Registry Operations](#approver-registry-operations): the challenge
that `recover`, `local_seed` and `enrol` require, those three operations,
external revocation and the binding readback, with their requests and answers,
caller authorisation, serialisation, order of refusal and codes. Because a
bound applied before parsing cannot know a request's operation, the request
framing and the 16,384-byte bound that section states apply to every request
on the socket; v2 states neither, and every request the bridge sends is far
below the bound. An oversized request is refused `payload_too_large`, for
`reconcile_tier_c` and `evidence_commission` as for the registry operations, so
that code joins the closed `error.code` lists of both v2 operations. For those
two operations the 16,384-byte bound replaces the 8,192 bytes the runtime ships
today, a limit v2 never stated. The change is acceptable because the bound is
the one [tier-c-approvers/v1.md](../tier-c-approvers/v1.md) sets for its
requests, applied to the whole request before parsing, and every request the
bridge sends for either operation stays far below both limits. Everything else
is v2's.

## Runtime-Owned CLI Bridge

`ori-cli` must treat the runtime bridge as the source of truth for runtime
configuration parsing, skill validation, and runtime health snapshot semantics.
The CLI may format bridge output for humans, but it must not duplicate runtime
validation rules.

Bridge invocation:

```bash
python -m ori.cli_bridge <command> [args...]
```

The canonical bridge command shape is noun/verb, matching the public
operator CLI vocabulary. For example:

```bash
python -m ori.cli_bridge config validate --path ori.yaml
python -m ori.cli_bridge skills validate --skills-dir skills/
python -m ori.cli_bridge health snapshot --socket /tmp/ori-health.sock
```

Legacy single-token bridge commands remain accepted as compatibility aliases
while sibling tools migrate. New CLI implementations should use the canonical
noun/verb form.

Bridge response envelope:

```json
{"schema_version":1,"ok":true,"command":"config validate","result":{}}
```

Bridge error envelope:

```json
{"schema_version":1,"ok":false,"command":"config validate","error":{"code":"config_validation_error","detail":"..."}}
```

Bridge exit codes:

- `0`: command completed and `ok=true`
- `2`: expected operator/user error such as invalid arguments, invalid config,
  invalid skill, unavailable health socket, or malformed health response
- `1`: unexpected bridge/runtime error

Bridge output is exactly one JSON object followed by a newline. Sensitive values
are redacted by the runtime bridge before stdout emission.

### Canonical Bridge Commands

| Bridge command | Legacy alias | Required args | Optional args | Purpose |
|---|---|---|---|---|
| `config validate` | `config-validate` | `--path <ori.yaml>` | none | Load config through runtime parser and return summarized posture when valid. |
| `config show` | `config-show` | `--path <ori.yaml>` | none | Same parser path as validate; intended for human-friendly CLI display. |
| `skills list` | `skills-list` | `--skills-dir <dir>` | `--require-signed` | Discover and validate loadable skills under a skill root. |
| `skills validate` | `skills-validate` | `--skills-dir <dir>` | `--require-signed` | Validate one skill directory or every skill directory under a skill root. |
| `health snapshot` | `health-snapshot` | `--socket <path>` | `--timeout-ms <int>` | Read one runtime health snapshot from the runtime health socket. |
| `state action-log` | `state-action-log` | `--path <ori.yaml>` | `limit=<int>` | Read recorded actions from the state store the named installation declares. |
| `state history` | `state-history` | `--path <ori.yaml>`, `sensor_id=<id>` | `limit=<int>` | Read retained readings for one sensor from that installation's state store. |

`config validate` and `config show` return a summary containing:

- `device`: id, name, location, timezone, country, deployment type/profile, and site type
- `sensors`: id, type, protocol, poll interval, metadata keys, and
  `device_path_kind` (`none`, `socket`, `direct_serial`, `url`, or `path`)
- `skills`: configured skill names and versions
- `config_signature`: signed-config posture without exposing signature secrets
- `telemetry_export`: endpoint posture and API-key environment variable name
- `device_policy`: policy URL/signing/auth posture without exposing secrets
- `phone_runtime_mobile`: phone authority ceiling and socket-bridge sensor posture

`skills list` and `skills validate` return:

- `valid`: true only when no skill errors are present
- `skill_count` and `error_count`
- `skills`: loaded skill summaries including triggers and action tiers
- `errors`: per-skill error code/detail entries

## Commissioning Reference Delivery

> Status: Implemented in `ori-runtime` (its operator socket and its bridge's
> `evidence commission`), without a conformance claim and without the installer
> recording `operator-uid`; not implemented in `ori-cli`.
> Defines the device-side ingress that
> [evidence-exchange/v2.md](../evidence-exchange/v2.md) requires for the
> commissioning reference.

A runtime registers its evidence anchor under a commissioning authorisation it
never holds. What it holds is the **commissioning reference** — the
authorisation's `commissioning_digest`, `sha256:` plus 64 lowercase hex — and
this is the only path by which that reference reaches a device.

```bash
python -m ori.cli_bridge evidence commission --reference sha256:<64 lowercase hex>
```

| Bridge command | Legacy alias | Required args | Optional args | Purpose |
|---|---|---|---|---|
| `evidence commission` | none | `--reference <sha256:hex>` | `--socket <path>`, `--force` | Submit the commissioning reference for this device's current evidence epoch to the running runtime |

**Submitted to the running runtime.** `evidence commission` submits one
request to the running runtime over its authenticated local operator socket,
the socket and path of *The operator socket* under
[Tier C Reconciliation](#tier-c-reconciliation), with `operation`
`evidence_commission`, `reference` and `force` and no other member, and no
member named twice. The bridge opens and writes neither runtime store,
reads no configuration document and no health snapshot, creates no file, and
relays the runtime's answer in the bridge envelope. Before trusting a response, the bridge verifies the connected socket peer
through kernel-provided credentials and requires the expected runtime service
identity for that install scope. Socket-path ownership and directory
permissions are defence in depth. An explicit `--socket` does not waive peer
verification. A response from an unverified peer is `runtime_unavailable` and
causes no reported success. The runtime obtains the
caller's effective numeric user ID and, where available, audit login user ID
from kernel-provided peer credentials; no caller-supplied field participates in
authentication. Socket filesystem permissions are defence in depth and do not
replace peer-credential authorization. The callers it admits, the installed
operator identity and how it is read, and the rule that it authorizes the
caller before reporting any state are those of `evidence reconcile-tier-c`.
After authorization and validation, the runtime records the reference through
its sole state-store writer and returns success only after the record is
durable. Admission needs no permission on the state store, and a store that
does not exist is never created by this command.

The command:

- runs locally on the device with no network access, and MUST NOT be reachable
  through any remote command, configuration document, gateway topic, or fleet
  API — a reference arriving by any of those is refused by the consumer that
  sees it, and `runtime-config/v2` declares no field for it;
- refuses a reference that is not exactly `sha256:` plus 64 lowercase
  hexadecimal characters, in the bridge before it connects and again in the
  runtime, before any state is read;
- is recorded by the runtime against its own device identity and its own
  current `anchor_epoch_id` — durably, atomically, readable by the runtime at
  startup and on every registration retry. A reference is never recorded
  without an epoch, and never rewritten to name a different one;
- replaces a previously recorded reference for the same epoch only with
  `--force`, reporting the replacement; and
- returns the recorded epoch and reference, and the registration status the
  runtime will now report, per *Registration status at the runtime* in
  [evidence-exchange/v2.md](../evidence-exchange/v2.md): `confirmed` if a
  confirmation for that epoch is already held; the runtime's reported status
  unchanged when the epoch or identity is stopped by a disposition or the
  attempt under this reference was refused, since recording a reference never
  lifts a disposition or reopens a refused attempt; otherwise
  `pending_confirmation`, since holding a reference is what leaves
  `pending_authorisation`.

The tool holds no commissioning key and cannot verify that the reference
resolves to anything. A wrong, stale or foreign reference grants nothing: the
evidence authority retains a registration naming one it does not hold pending,
never confirmed, and refuses one naming an authorisation that binds another
device, key or epoch, or is revoked or cancelled, as
`commissioning_digest_mismatch`, per *Resolution at the authority* in
[evidence-exchange/v2.md](../evidence-exchange/v2.md); that is why
a hash may pass through an installer's tool where the authorisation itself may
not. Recording a reference with `--force` is also how an operator repairs a
registration attempt a terminal disposition closed, per *Registration status at
the runtime* there; it never lifts an `epoch` or `identity` disposition. The
command MUST NOT display, log, or accept any identity, endpoint, or credential
of the evidence authority.

Successful response, in the bridge response envelope, whose `ok` is the only
success flag; `result` carries none of its own:

```json
{
  "schema_version": 1,
  "ok": true,
  "command": "evidence commission",
  "result": {
    "device_id": "<runtime device ID>",
    "anchor_epoch_id": "sha256:<64 lowercase hex>",
    "commissioning_reference": "sha256:<64 lowercase hex>",
    "replaced": false,
    "registration_status": "pending_confirmation"
  }
}
```

Every refusal records nothing and is answered in the bridge error envelope with
exit `2` and exactly one of these `error.code` values; the list is closed.
Checks run in this order, and the first that fails is the answer:
`payload_too_large`, `invalid_arguments`, `invalid_reference`, `unauthenticated`,
`evidence_epoch_unavailable`, `reference_device_mismatch` and
`reference_already_recorded`. `runtime_unavailable`, `runtime_store_unavailable`,
`state_store_locked` and `cancelled` are operational outcomes with the meanings
they have for `evidence reconcile-tier-c`, and none of them records a
reference; `runtime_store_unavailable` is returned only to an admitted caller.

| `error.code` | Refused when |
| --- | --- |
| `payload_too_large` | The request exceeds the 16,384-byte bound of [Requests on the socket](#requests-on-the-socket). Decided by the runtime before the request is parsed. |
| `invalid_arguments` | An argument or request member is missing, repeated, named twice, or not one this command accepts. An unaccepted argument is named, never echoed with its value. |
| `invalid_reference` | The reference is not exactly `sha256:` plus 64 lowercase hexadecimal characters, decided before any state is read. |
| `unauthenticated` | The runtime cannot establish the caller's identity from the connection's kernel-provided peer credentials, or that identity is neither root nor the installed operator identity. Decided before any state is read or its condition reported. |
| `evidence_epoch_unavailable` | The running runtime does not enable evidence, its evidence signing is unavailable, or it holds no current anchor epoch. |
| `reference_device_mismatch` | The reference recorded for this epoch names another `device_id`. |
| `reference_already_recorded` | A different reference is recorded for this epoch and `--force` was not given. |
| `runtime_unavailable` | No running runtime answers on the socket, the connection ends before the runtime answers, or the socket peer is not verified as the expected runtime service identity. The bridge never falls back to the state store or the configuration. |
| `runtime_store_unavailable` | The runtime's state store cannot serve the records the checks read or the durable record. Returned only to an admitted caller. |
| `state_store_locked` | The required write transaction is not granted at its execution point within the release-defined timeout. |
| `cancelled` | The runtime abandons the request before its record begins. |

Exit codes:

- `0`: reference recorded, or already recorded identically;
- `2`: any refusal in the table above;
- `1`: unexpected bridge/runtime error, as `internal_error`.

## Tier C Reconciliation

> Status: Implemented in `ori-runtime` (its operator socket and its bridge's
> `evidence reconcile-tier-c`), without a conformance claim and without the
> installer recording `operator-uid`; not implemented in `ori-cli`.
> Defines form (a) of reconciliation in
> [tier-c-approval/v1.md](../tier-c-approval/v1.md).

Live or after restart a Tier C approval can be left `dispatch_outcome_unknown` or
`dispatch_not_proven`, and [tier-c-approval/v1.md](../tier-c-approval/v1.md) admits no
later Tier C proposal commanding the same physical outcome on the same
commissioned zone until it is reconciled. This command is the authenticated local operator command that records what the
operator observed. It belongs here because, like `evidence commission`, it is a
local request that only a person at the device can make, and this is the
surface through which such requests reach a device's durable state. It
reconciles only a Tier C action capable of changing physical state, the scope of
[tier-c-approval/v1.md](../tier-c-approval/v1.md#scope); a host-state Tier C
action or a Tier B action requiring approval is on the existing approval
workflow, which records no proposal under that contract, so a request naming
one is refused `unknown_proposal`.

```bash
python -m ori.cli_bridge evidence reconcile-tier-c --proposal-id <id> --device-id <id> --zone <zone_id> --outcome executed --reason site_inspection
```

| Bridge command | Legacy alias | Required args | Optional args | Purpose |
|---|---|---|---|---|
| `evidence reconcile-tier-c` | none | `--proposal-id <id>`, `--device-id <id>`, `--zone <zone_id>`, `--outcome <outcome>`, `--reason <code>` | `--note <text>`, `--socket <path>` | Submit the operator's observed terminal outcome for one uncertain Tier C dispatch to the running runtime |

The CLI form is `ori evidence reconcile-tier-c` with the same arguments.

**Submitted to the running runtime.** `evidence reconcile-tier-c` submits one
reconciliation request to the running runtime over its authenticated local
operator socket. The bridge never opens or writes the runtime state store. The
runtime obtains the caller's effective numeric user ID and, where available,
audit login user ID from kernel-provided peer credentials; no caller-supplied
field participates in authentication. Socket filesystem permissions are
defence in depth and do not replace peer-credential authorization. After
authorization and semantic validation, the runtime appends the reconciliation
through its sole state-store writer and returns success only after the append
is durable.

**The operator socket.** `--socket` names that socket. No path is universal:
the default is `operator.sock` in the runtime directory of the install the
bridge belongs to, which is `/run/ori/` for a system install and
`/run/user/<uid>/ori/` for a user-scope install, `<uid>` being the numeric user
ID the user-scope service runs as. The bridge derives it from the install
scope, never from a configuration document. It is a local Unix domain stream
socket that the runtime binds, shared by every command this contract submits
to the running runtime, and the bridge sends the validated arguments as one
JSON object, `operation` (`reconcile_tier_c`), `proposal_id`, `device_id`,
`zone_id`, `outcome`, `reason` and `note`, with no other field and no member
named twice. A request whose `operation` is absent, is not one of the
operations of [Requests on the socket](#requests-on-the-socket), or is named
more than once is refused `invalid_arguments`.
The bridge reads no configuration document and no state store,
creates no file, and relays the runtime's answer in the bridge envelope.
Before trusting a response, the bridge verifies the connected socket peer
through kernel-provided credentials and requires the expected runtime service
identity for that install scope. Socket-path ownership and directory
permissions are defence in depth. An explicit `--socket` does not waive peer
verification. A response from an unverified peer is `runtime_unavailable` and
causes no reported success. The
runtime creates the socket granting no world access; because no group admits a
caller in this version, it grants the installed operator identity connect
permission by an access-control entry naming that user ID. Connecting also
needs search permission on the runtime directory, which is created with no
group or world access. Each time the runtime creates or opens its runtime
directory, the runtime grants the installed operator identity search permission
on it by an access-control entry naming that user ID, and on every ancestor the
operator cannot otherwise search; if it cannot, it binds no operator socket and
reports it. No other user or group is granted any access to the runtime
directory. In a user-scope install the service account is the user, so the
installed operator is a different user. These entries are defence in depth;
none admits a caller.

**Local and authenticated.** The command runs locally on the device and MUST
NOT be reachable through any remote command, configuration document, gateway
topic, or fleet API. It has no unauthenticated invocation. The runtime
establishes the caller only from the peer credentials the kernel reports for
the connection: never from an argument, flag, request field, environment
variable, configuration document or piped input. A request carrying any field
beyond those above, including one naming a user ID, account or principal, or
naming any member twice, is refused `invalid_arguments` and decides nothing. The runtime establishes and
authorizes the caller before reporting any state: an unauthorized caller
receives `unauthenticated` whatever the condition of the runtime's store, the
proposal, the device or the zone.

**Who may reconcile.** Two callers are admitted: root, and the installed
operator identity. A caller is admitted when the peer's effective numeric user
ID is `0` or equals the installed operator identity; no group membership
admits a caller in this version. The numeric user ID and, where the platform
keeps one, the Linux audit login user ID are authoritative; the account name is
diagnostic only, recorded and never compared. Admission is decided on the
effective user ID alone. The audit login user ID is authoritative for the
recorded principal and for comparing principals, and neither admits nor
refuses a caller. The installed operator identity
is one numeric user ID that the installer records at install time in the file
`operator-uid` at the install root, beside `releases/` and `current`
([runtime-release-bundle/v1.md](../runtime-release-bundle/v1.md)). The runtime
reads it only when the file, the install root and every ancestor directory
are owned by user ID `0` and writable by no other user or group; the file is
opened without following symbolic links and holds one decimal user ID without
leading zeros, other than `0` and other than the runtime service account's,
optionally followed by one LF; otherwise no operator identity is installed and
only root is admitted. The operator identity is never read from `ori.yaml`, any other
configuration document, the environment, or any file the runtime's service
account or a remote party can write. Admission needs no permission on the
state store: the installed operator reconciles without being able to read or
write it.

**The request.** `--proposal-id` names the uncertain dispatch. `--device-id`
must equal the device identity of the running runtime that answers on the
socket, and `--zone` the commissioned zone the
uncertain dispatch commanded, so a request written for another device or zone
changes nothing. `--outcome` is `executed` or `not-executed`, recorded as
`reconciled_executed` or `reconciled_not_executed`. `--reason` is one of
`site_inspection`, `instrument_measurement` and `actuator_position_observed`.
The reason records the observation method, not proof of electrical outcome.
`actuator_position_observed` proves a protected-circuit outcome only where the
commissioned feedback mapping explicitly binds that observed position to the
outcome.
`site_inspection` means the operator inspected the protected circuit or its
load at the site; `instrument_measurement` that the operator measured it with
an instrument; `actuator_position_observed` that the operator observed the
actuator's position. `--note` is optional and at most 280 bytes of UTF-8. A
note MUST contain none of U+0000–U+001F, U+007F or U+0080–U+009F.

**The record.** A reconciliation is one durable, append-only record linked to
the uncertain dispatch, carrying the proposal identifier, device, zone,
recorded state, reason, note, the caller's principal (numeric user ID, account
name, and, where the platform keeps one, the audit login user ID, which a
change of user does not alter; `null` when unset), the entry point
`local_operator_socket`, and the runtime-observed time. The kernel's peer
credentials carry the effective user ID and not the audit login user ID, which
the runtime reads for the peer process it pins by `SO_PEERPIDFD` (Linux 6.5 and
later); it is `null` when the peer cannot be pinned that way, and a value read
for a process identifier that was not pinned is never recorded. The append is durable before the command reports
success, and a command whose append fails reports failure and records nothing.
It never rewrites the uncertain record or any evidence.

**It commands nothing.** Reconciliation only appends: it never rewrites
evidence, replays the action or reaches Tier D. It never dispatches, repeats or
cancels an action and never drives an actuator. A Tier D execution is not a
Tier C proposal, so a request naming one is refused `unknown_proposal`.

**Effect.** Once recorded, the uncertain dispatch no longer blocks a later Tier
C proposal commanding the same physical outcome on the same commissioned zone.
The runtime evaluates the reconciliation state when creating a Tier C proposal
and again when admitting an operator reply, so reconciliation takes effect
without restart and an uncertainty arising after proposal creation cannot be
bypassed by an already-open proposal.

**Idempotency and cancellation.** Both are the runtime's. A request identical
in proposal, outcome, reason and note to the recorded reconciliation is an
identical repeat, answered with that record.
An identical repeat appends no second reconciliation and returns
`already_recorded: true`. If the authenticated caller principal differs from
the principal on the existing reconciliation, the runtime appends a separate
audit-attempt record containing the caller, referenced reconciliation, time and
`identical_repeat`; that audit record does not alter reconciliation state.
An identical repeat by the principal on the existing reconciliation appends
nothing; identical repeats by one other principal may be coalesced into a
single `identical_repeat` audit-attempt record per principal. Principals are compared by
numeric user ID and audit login user ID, never by account name. An identical
operator request may return a reconciliation previously recorded through
commissioned feedback, which carries the reason `actuator_position_observed` and
a `null` note. In that case `already_recorded` is `true`, `entry_point` is
`commissioned_feedback`, and every `operator` member is `null`. No new
reconciliation is appended; the authenticated repeat may still produce the
`identical_repeat` audit-attempt record specified above. The runtime
alone decides cancellation: it may abandon a request before its append begins,
answering `cancelled`, and an append once begun completes or fails as one
transaction whatever the bridge does. A bridge that is interrupted or loses the
connection cancels nothing already begun; it reports `runtime_unavailable`,
which does not establish whether the append occurred, and an identical repeat
then answers `already_recorded` if it did.

**Refusals.** Every refusal records nothing and is answered in the bridge error
envelope with exit `2`. Argument, authentication and semantic refusals are
evaluated in the order below. The bridge decides `invalid_arguments` before it
connects, and the runtime decides it again. `runtime_unavailable` is returned by the bridge
when no running runtime answers on the socket, or the connection ends before an
answer. `runtime_store_unavailable` is returned by the runtime, only to an
admitted caller and only after `unauthenticated` is decided, when its state
store cannot serve the records the checks read or the append. `state_store_locked` is
returned when the required write transaction cannot be acquired at its execution point.
`cancelled` may terminate the operation before commit. No operational
outcome commits a reconciliation. Checks run in this order, and the first that
fails is the answer: `payload_too_large`, `invalid_arguments`, `unauthenticated`,
`device_mismatch`, `unknown_proposal`, `zone_mismatch`, `already_reconciled`
and `not_uncertain`. The list of `error.code` values is closed:

| `error.code` | Refused when |
| --- | --- |
| `payload_too_large` | The request exceeds the 16,384-byte bound of [Requests on the socket](#requests-on-the-socket). Decided by the runtime before the request is parsed. |
| `invalid_arguments` | An argument or request field is missing, repeated, or not one this command accepts; a request member is named twice; `--outcome` or `--reason` is outside its set; or `--note` exceeds its bound or carries a control character. Decided before any state is read. |
| `unauthenticated` | The runtime cannot establish the caller's identity from the connection's kernel-provided peer credentials, or that identity is neither root nor the installed operator identity. Decided before any state is read or its condition reported. |
| `device_mismatch` | `--device-id` differs from the device identity of the running runtime that answers on the socket. |
| `unknown_proposal` | No Tier C proposal with this identifier is recorded for this device. |
| `zone_mismatch` | `--zone` differs from the commissioned zone the uncertain dispatch commanded. |
| `already_reconciled` | The dispatch is already reconciled, and the request is not identical to that reconciliation. |
| `not_uncertain` | The proposal is recorded but is neither `dispatch_outcome_unknown` nor `dispatch_not_proven`. |
| `runtime_unavailable` | No running runtime answers on the socket, the connection ends before the runtime answers, or the socket peer is not verified as the expected runtime service identity. The bridge never falls back to the state store. |
| `runtime_store_unavailable` | The runtime's state store cannot serve the records the checks read or the durable append. Returned only to an admitted caller. |
| `state_store_locked` | The required write transaction is not granted at its execution point within the release-defined timeout. |
| `cancelled` | The runtime abandons the request before its append begins. |

Successful response:

```json
{
  "schema_version": 1,
  "ok": true,
  "command": "evidence reconcile-tier-c",
  "result": {
    "proposal_id": "AB12CD34",
    "device_id": "<runtime device ID>",
    "zone_id": "<commissioned zone ID>",
    "decision_state": "reconciled_executed",
    "reason": "site_inspection",
    "note": null,
    "operator": {"uid": 1001, "account": "installer", "login_uid": 1001},
    "entry_point": "local_operator_socket",
    "recorded_at_ms": 1787000400000,
    "already_recorded": false
  }
}
```

Exit codes: `0` when a reconciliation is recorded or was already recorded
identically; `2` for any `error.code` above; `1` for an unexpected bridge or
runtime error, as `internal_error`.

[vectors/tier-c-reconcile-v2.json](vectors/tier-c-reconcile-v2.json) fixes these
rules, and `scripts/check-tier-c-approval-vectors` replays it through the

reasons, the refusal codes and their order from this section.

## Approver Registry Operations

> Status: Not implemented. Defines the authenticated local operator delivery
> that [tier-c-approvers/v1.md](../tier-c-approvers/v1.md) requires for the
> approver registry's local operations.

[tier-c-approvers/v1.md](../tier-c-approvers/v1.md) makes the runtime the sole
holder of Tier C approver credentials and delivers its local operations through
this socket: first setup and recovery (`recover`), seeding the first LAN
credential (`local_seed`), enrolment (`enrol`, including a phone candidate's
authorisation), external revocation, and the binding readback. That contract
owns what each operation means: the registry state, the challenge, the
authorisation and possession objects, the revocation document, and what each
commits. This section owns how each reaches the runtime: the request and answer
on this socket, who may send it, the order in which a request is refused, and
how requests are serialised. Where this section names a rule of that contract,
the rule is that contract's.

These operations run locally on the device and MUST NOT be reachable through
any remote command, configuration document, gateway topic, product API or fleet
API. No bridge or CLI command submits them in this version.

### Requests on the socket

The socket of *The operator socket* under
[Tier C Reconciliation](#tier-c-reconciliation) serves one request per
connection. A request is the UTF-8 bytes of one JSON object followed by one LF;
the runtime answers with one JSON object followed by one LF and closes the
connection. The request is the bytes before the first LF, and the runtime
ignores any bytes after it. The JSON text MUST NOT contain an LF byte: a
request that holds one is judged on the bytes before its first LF, which are not
one JSON object, and is refused `invalid_arguments`. A connection that ends
before any LF, with no more than the bound received, is refused
`invalid_arguments`. The runtime reads a request under a release-defined
deadline; a connection that has sent no LF when the deadline passes is
answered on the bytes received, `payload_too_large` if they exceed the bound
and `invalid_arguments` otherwise, and nothing beyond the bound is ever parsed.
This framing and the bound below apply to every request on
the socket, including `reconcile_tier_c` and `evidence_commission`.

**The bound.** A request is at most 16,384 bytes, not counting its LF. The
bound counts UTF-8 bytes, not characters. The
runtime counts bytes as they arrive and refuses a request that exceeds the
bound `payload_too_large` before parsing any of it: before reading its
`operation`, before establishing the caller, and before reading any state. A
request of exactly 16,384 bytes is parsed. `payload_too_large` answers an
oversized request for every operation on the socket, `reconcile_tier_c` and
`evidence_commission` included, in the runtime's answer and in the bridge's
error envelope with exit `2`.

**Members.** The request is one JSON object. A member named twice in the
request, at the top level or inside any nested object other than a revocation
`document`, refuses the request `invalid_arguments`; so does a request that is
not one JSON object, and a request whose `operation` is absent, is not a
string, is not one of the eight operations below or `runtime_device_key`, or is
named more than once.
Member names are compared byte for byte after JSON unescaping: `"\u006fperation"`
is `operation`, and a member that differs from an accepted name only in case
is an unaccepted member. Each operation's members are closed: a missing member, a
member the operation does not accept, or a member outside its stated form is
`invalid_arguments`. Every such refusal is decided from the request alone,
before the caller is established and before any state is read or changed.
The request is parsed once, as a whole, and each of these is a parse failure,
refused `invalid_arguments` wherever in the request it occurs, a revocation
`document` included: text that is not JSON; a JSON string with no UTF-8 form,
such as an escaped lone surrogate; and nesting deeper than 32 levels, each
object or array counting one level and the request object being level 1. A
member named twice inside a revocation `document` is the document's fault, not
the request's: [Revoke](#revoke) refuses it `malformed`, as
[tier-c-approvers/v1.md](../tier-c-approvers/v1.md) defines.

| `operation` | Defined by |
| --- | --- |
| `reconcile_tier_c` | [Tier C Reconciliation](#tier-c-reconciliation) |
| `evidence_commission` | [Commissioning Reference Delivery](#commissioning-reference-delivery) |
| `approver_registry_challenge` | [Challenge](#challenge) |
| `approver_registry_recover` | [Recover](#recover) |
| `approver_registry_local_seed` | [Local seed](#local-seed) |
| `approver_registry_enrol` | [Enrol](#enrol) |
| `approver_registry_revoke` | [Revoke](#revoke) |
| `approver_registry_binding` | [Binding](#binding) |

The six `approver_registry_*` operations are the **registry operations**.

**The answer.** The runtime answers a registry operation with
`{"schema_version":1,"ok":true,"result":{...}}`, whose `result` members are the
operation's and closed, or with
`{"schema_version":1,"ok":false,"error":{"code":"...","detail":"..."}}`, whose
`code` is one of the codes this section names. `detail` is diagnostic text,
never a credential value, a phone possession code or a signature, and a client
decides nothing from it.

**Clients.** A client that submits a registry operation verifies the connected
socket peer as the runtime service identity of its installation before trusting
an answer, as the bridge does under *The operator socket*. An answer from an
unverified peer reports no success.

### Authorisation

A registry operation is admitted on the rules of *Local and authenticated* and
*Who may reconcile* under [Tier C Reconciliation](#tier-c-reconciliation): the
runtime establishes the caller from the kernel's peer credentials for the
connection alone, and admits root and the installed operator identity. Any other
caller, or a connection whose peer credentials the runtime cannot establish, is
refused `unauthenticated`. The runtime decides this before the operation reads
or changes any registry state, so an unadmitted caller receives
`unauthenticated` whatever the registry's condition, whether another registry
operation is in flight, and whatever challenge the request names; its request
consumes no challenge.

Admission authenticates the operator process and nothing more. It proves no
physical presence: the installer being at the panel is a commissioning
procedure requirement, as [tier-c-approvers/v1.md](../tier-c-approvers/v1.md)
states, and a process holding the installed operator identity can request
recovery and seed an empty registry.

### Serialisation

The runtime holds at most one registry operation in flight per device. A
registry operation is in flight from the moment its caller is admitted until
its answer is written or its connection ends, and, when it commits, until its
transaction completes. An admitted registry operation that arrives while
another is in flight is refused `registry_busy` before it reads or changes any
registry state, and consumes no challenge.

Registry operations are serialised with registry admission: the Tier C approval
admission, the phone possession commit and the other registry readers and
writers of [tier-c-approvers/v1.md](../tier-c-approvers/v1.md) run against the
same registry state in one serial order with them. Those wait for each other;
they are not refused `registry_busy`. `reconcile_tier_c` and
`evidence_commission` are not registry operations, and nothing here changes
how they are served.

### Order of refusal

The checks run in this order, and the first that fails is the answer:

1. the bound: `payload_too_large`;
2. the request's form and members: `invalid_arguments`;
3. the caller: `unauthenticated`;
4. another registry operation in flight: `registry_busy`;
5. no verified nonempty `device.site_id`: `registry_unavailable`;
6. the operation's own checks, in the order its section lists them.

The registry is **locked** when it is absent, corrupt or cannot be read; a
locked registry is not initialized, and an operation that needs an initialized
registry refuses it `registry_unavailable`. The runtime's device identity and
its verified `device.site_id` are those of the provisioning document it
currently holds accepted, as
[tier-c-approvers/v1.md](../tier-c-approvers/v1.md) defines them. A change of
either locks registry mutation, as
[tier-c-approvers/v1.md](../tier-c-approvers/v1.md) states: every registry
operation on an initialized registry whose device binding differs from the
runtime's device identity is refused `device_binding_mismatch`, and one whose
site binding differs from the verified `device.site_id` is refused
`site_binding_mismatch`, each at the row its section gives, the binding
readback included. When both differ, `device_binding_mismatch` is the answer. A
locked registry has neither binding.

Rows marked *defence in depth* below can fail only in a state the earlier
checks or the runtime's own minting prevent: a registry revision change since
the challenge, which `challenge_stale` refuses first, or a collision of
runtime-minted IDs. The runtime keeps them; the corpus reaches them only through
fixtures that hold such a state directly.

A refusal changes no credential, tombstone, registry revision, proposal or
pending phone operation. The one state a refusal may change is a challenge's
used marker, as [Challenges presented](#challenges-presented) states.
`runtime_store_unavailable`, `state_store_locked` and `cancelled` are
operational outcomes with the meanings they have under
[Tier C Reconciliation](#tier-c-reconciliation), returned only to an admitted
caller; none of them commits a registry change. A commit once begun completes
or fails as one transaction whatever the client does; a client that loses the
connection learns nothing about whether it committed and reads the
[binding](#binding) to find out.

### Value forms

The forms below are those of
[tier-c-approvers/v1.md](../tier-c-approvers/v1.md), repeated so a request can
be refused on its form before any state is read.

- A **challenge ID** is canonical padded RFC 4648 Base64 of 16 bytes.
- An **approver ID** and a **credential ID** are 1 to 64 characters from
  `[A-Za-z0-9._-]`.
- A **channel** is `sms`, `whatsapp` or `lan_ed25519`.
- A **value** is canonical E.164 matching `^\+[1-9][0-9]{1,14}$` for `sms` and
  `whatsapp`, and `ed25519:` followed by canonical padded Base64 of a 32-byte
  raw Ed25519 public key for `lan_ed25519`. A transport prefix such as
  `whatsapp:` is not part of a value.
- A **digest** is 64 lowercase hexadecimal characters.
- A **signature** is canonical padded Base64 of 64 bytes.
- `v` is the integer `1`. No integer member accepts `true` or `false`.
- Every integer member, `v`, `revision` and `registry_revision` among them, is
  written as a JSON integer, with no fraction or exponent: `1.0` and `1e0` are
  not integers. `revision` and every registry revision are at most
  2^53 − 1 (9007199254740991). A revocation document that breaks either rule is
  `malformed`; any other request member that breaks it is `invalid_arguments`.

A **candidate** is an object with exactly `approver_id`, `credential_id`,
`channel` and `value`. An **authorization** is the LAN authorization object
and a **possession** the candidate LAN possession object of *Site enrolment* in
[tier-c-approvers/v1.md](../tier-c-approvers/v1.md): each has exactly `v`,
`challenge_id`, `challenge_sha256`, a credential ID member
(`authorizer_credential_id` or `candidate_credential_id`) and `signature`.

**Recognising a key.** Every comparison that recognises an Ed25519 key, namely
selecting the anchor a revocation's `signing_key` is, finding two configured
anchors that collide, and matching a `lan_ed25519` value against active and
tombstoned values, compares the keys' identity as
[ed25519-key-admission/v1.md](../ed25519-key-admission/v1.md) *Recognising a
key* defines it: the 32 bytes with bit 255 cleared. A key and its negation are
the same key. A phone value is compared as its canonical E.164 string alone,
whatever its channel: the same number on `sms` and on `whatsapp` is the same
value.

### Challenge

`approver_registry_challenge` asks the runtime to create the challenge that
`recover`, `local_seed` and `enrol` each require. Its members are exactly:

- `operation`: `approver_registry_challenge`;
- `challenge_operation`: `recover`, `local_seed` or `enrol`;
- `candidate`: `null` for `recover`; for `local_seed`, an object with exactly
  `channel` and `value`; for `enrol`, an object with exactly `approver_id`,
  `channel` and `value`, where `approver_id` is `null` or an approver ID.

The request names no credential ID, epoch or revision: the runtime mints the
challenge ID and the candidate's credential ID from its own CSPRNG, and for
`recover` a prospective identity epoch, as
[tier-c-approvers/v1.md](../tier-c-approvers/v1.md) requires. The candidate's
approver ID is minted too, except for an `enrol` candidate whose `approver_id`
is a string: that names an existing approver with at least one active
credential in the current epoch, and the new credential joins it. Such an
enrolment adds a key for the same human, so it must be authorised by one of
that approver's own active credentials; [Enrol](#enrol) refuses any other
authoriser `authorizer_not_approver`. A
`local_seed` candidate always has a newly minted approver ID. A `recover`
challenge's `registry_revision` is `0` and its `identity_epoch` the prospective
epoch; a `local_seed` or `enrol` challenge carries the registry's current epoch
and revision.

After the steps of [Order of refusal](#order-of-refusal), the checks are:

| `error.code` | Refused when |
| --- | --- |
| `lan_key_required` | `challenge_operation` is `local_seed` and the candidate's `channel` is not `lan_ed25519`. |
| `device_binding_mismatch` | The registry's device binding differs from the runtime's device identity. |
| `site_binding_mismatch` | The registry's site binding differs from the verified `device.site_id`. |
| `recovery_not_available` | `challenge_operation` is `recover` and the registry is initialized. |
| `registry_unavailable` | `challenge_operation` is `local_seed` or `enrol` and the registry is locked. |
| `channel_unauthenticated` | `challenge_operation` is `enrol` and the candidate's `channel` has no authenticated ingress under [tier-c-approvers/v1.md](../tier-c-approvers/v1.md): in this version every `whatsapp` candidate, and an `sms` candidate while the runtime has no authenticated SMS ingress. |
| `active_authorizer_exists` | `challenge_operation` is `local_seed` and the registry holds an active credential. |
| `approver_revoked` | An `enrol` candidate's `approver_id` is tombstoned in this epoch. |
| `approver_unknown` | An `enrol` candidate's `approver_id` is a string that names no approver with an active credential in this epoch and is not tombstoned. |
| `value_tombstoned` | The candidate's value is tombstoned in this epoch. |
| `duplicate_value` | The candidate's value is active under a credential. |
| `phone_pending_for_value` | The candidate is a phone value with a pending phone operation, on either phone channel. |

Every check above runs before the runtime generates or sends a possession code.
A refusal creates no challenge, sends nothing to a candidate and starts no
window. On success the runtime records the challenge with its 60-second
monotonic deadline and answers with exactly one `result` member, `challenge`:
the challenge object of *First setup and recovery* in
[tier-c-approvers/v1.md](../tier-c-approvers/v1.md), with exactly its members.
A signer's `challenge_sha256` is the lowercase hexadecimal SHA-256 of that
object's Profile 2 canonical JSON. For a phone candidate the runtime then sends
the possession code to the candidate's value on its channel, as that contract
states; the code appears in no answer, and the answer does not report whether
the code was delivered.

### Challenges presented

`approver_registry_recover`, `approver_registry_local_seed` and
`approver_registry_enrol` each present one challenge by its `challenge_id`, and
are the fresh, authenticated local request
[tier-c-approvers/v1.md](../tier-c-approvers/v1.md) requires for that
challenge. After the steps of [Order of refusal](#order-of-refusal), each runs
these checks first:

| `error.code` | Refused when |
| --- | --- |
| `device_binding_mismatch` | The registry's device binding differs from the runtime's device identity. |
| `site_binding_mismatch` | The registry's site binding differs from the verified `device.site_id`. |
| `challenge_reused` | The runtime holds the challenge as used (already presented). |
| `challenge_unavailable` | The runtime holds no challenge with this ID, pending, used or expired; it holds no challenge, used or not, issued before it last started. |
| `challenge_expired` | The challenge's 60-second deadline has passed. Expiry is decided at this row, in this table's order. |
| `candidate_changed` | The challenge was created for another operation, or the request's `candidate` is not exactly the challenge's. |

A request refused at or before `challenge_unavailable` consumes nothing. From
`challenge_expired` on, the challenge is used whether the operation commits or
is refused, as [tier-c-approvers/v1.md](../tier-c-approvers/v1.md) requires; a
used marker the runtime cannot commit locks that challenge state as that
contract states. A success consumes the challenge in the transaction that
commits the operation.

The set of authenticated ingresses is fixed for a run, as
[tier-c-approvers/v1.md](../tier-c-approvers/v1.md) states under *Authenticated
channel*: it changes only across a restart, which invalidates every challenge,
used or not, and every pending phone operation.

### Recover

Members: exactly `operation` (`approver_registry_recover`) and `challenge_id`.

After the checks of [Challenges presented](#challenges-presented):

| `error.code` | Refused when |
| --- | --- |
| `recovery_not_available` | The registry is initialized. |
| `challenge_stale` | The challenge's `device_id` or `site_id` differs from the runtime's device identity or its verified `device.site_id`. |

On success the runtime commits an empty initialized registry under the
challenge's prospective epoch, the runtime's device identity and the verified
site, with the effects
[tier-c-approvers/v1.md](../tier-c-approvers/v1.md) gives recovery, and answers
with exactly `status` (`recovered`) and `registry_revision` (`1`). In the same
transaction it clears every challenge it holds, every phone authorisation it
has received and every pending phone operation.

### Local seed

Members: exactly `operation` (`approver_registry_local_seed`), `challenge_id`,
`candidate` and `possession`.

After the checks of [Challenges presented](#challenges-presented):

| `error.code` | Refused when |
| --- | --- |
| `registry_unavailable` | The registry is locked. |
| `challenge_stale` | The registry's revision or identity epoch differs from the challenge's. |
| `active_authorizer_exists` | The registry holds an active credential. Defence in depth. |
| `possession_invalid` | The possession's `challenge_id`, `challenge_sha256` or `candidate_credential_id` differs from the challenge's. |
| `signature_invalid` | The candidate key fails [ed25519-key-admission/v1.md](../ed25519-key-admission/v1.md), or the possession signature fails [ed25519-verification/v1.md](../ed25519-verification/v1.md) under it. |
| `approver_revoked` | The candidate's approver ID is tombstoned in this epoch. Defence in depth. |
| `credential_reused` | The candidate's credential ID is active or tombstoned in this epoch. Defence in depth. |
| `value_tombstoned` | The candidate's value is tombstoned in this epoch. Defence in depth. |

On success the runtime commits the credential and answers with exactly
`status` (`seeded`) and `registry_revision`.

### Enrol

Members: exactly `operation` (`approver_registry_enrol`), `challenge_id`,
`candidate`, `authorization` and `possession`.

- `authorization` is an authorization object when the existing approver
  authorises with a `lan_ed25519` credential, and `null` when it authorises
  through a phone channel; that `ORI-ENROL-V1` text reaches the runtime through
  the channel's own ingress, never through this socket, and must have been
  received and attributed before this request. The first ORI-ENROL-V1 text
  received on an authenticated ingress for a challenge ID, whoever its sender,
  is its authorization; a later text for the same challenge ID is ignored and
  changes nothing.
- `possession` is a possession object when the candidate's `channel` is
  `lan_ed25519`, and `null` when it is a phone channel; any other combination
  is `invalid_arguments`.

After the checks of [Challenges presented](#challenges-presented):

| `error.code` | Refused when |
| --- | --- |
| `registry_unavailable` | The registry is locked. |
| `challenge_stale` | The registry's revision or identity epoch differs from the challenge's. |
| `authorizer_unavailable` | `authorization` names no active `lan_ed25519` credential; or `authorization` is `null` and the first `ORI-ENROL-V1` text received for this challenge ID is absent, is not attributed to an active phone credential, or carries a `challenge_sha256` that is not this challenge's. The text's `challenge_sha256` is the digest of the challenge object, which carries the challenge ID, so it binds both; the runtime still checks each. |
| `authorizer_not_preexisting` | The authorizing credential was enrolled after the challenge was created. Defence in depth. |
| `signature_invalid` | The authorization's `challenge_id` or `challenge_sha256` differs from the challenge's, or its signature fails [ed25519-verification/v1.md](../ed25519-verification/v1.md) under the authorizing key. |
| `authorizer_not_approver` | The challenge's candidate names an approver that has an active credential, and the authorizing credential is not one of that approver's. |
| `possession_invalid` | A LAN candidate's possession `challenge_id`, `challenge_sha256` or `candidate_credential_id` differs from the challenge's. |
| `signature_invalid` | A LAN candidate's key fails [ed25519-key-admission/v1.md](../ed25519-key-admission/v1.md), or its possession signature fails [ed25519-verification/v1.md](../ed25519-verification/v1.md) under it. |
| `approver_revoked` | The candidate's approver ID is tombstoned in this epoch. Defence in depth. |
| `credential_reused` | The candidate's credential ID is active or tombstoned in this epoch. Defence in depth. |
| `value_tombstoned` | The candidate's value is tombstoned in this epoch. Defence in depth. |
| `duplicate_value` | The candidate's value is active under a credential. Defence in depth. |
| `phone_pending_for_value` | A phone candidate's value already has a pending phone operation, on either phone channel. |

`channel_unauthenticated` is decided when the challenge is created; a
`whatsapp` candidate never reaches this operation.

On success for a LAN candidate the runtime commits the credential and answers
with exactly `status` (`enrolled`) and `registry_revision`. For a phone
candidate it records the pending phone operation of
[tier-c-approvers/v1.md](../tier-c-approvers/v1.md) and answers with exactly
`status` (`phone_pending`) and `registry_revision`, unchanged: no credential
exists until the candidate's possession reply commits it through its channel,
with the rechecks and refusals that contract gives that second commit.

### Revoke

Members: exactly `operation` (`approver_registry_revoke`) and `document`, the
signed removal-only document of *External revocation only* in
[tier-c-approvers/v1.md](../tier-c-approvers/v1.md). The envelope is checked
under [Requests on the socket](#requests-on-the-socket); the document's own
members, types and encodings are checked below, so a document that is present
but not that object is `malformed`, not `invalid_arguments`. A member named
twice inside the document makes it `malformed`.

After the steps of [Order of refusal](#order-of-refusal):

| `error.code` | Refused when |
| --- | --- |
| `anchor_unavailable` | The current provisioning anchor is missing or fails [ed25519-key-admission/v1.md](../ed25519-key-admission/v1.md), any two configured anchors (current, previous and other-class) are recognised as the same key, or the runtime is in unsigned development posture without a verified config anchor. |
| `malformed` | The document is not exactly the signed object: a missing, unknown, repeated or wrong-type member, `device_id` not matching `^[A-Za-z0-9._-]{1,128}$` or `site_id` not matching `^[A-Za-z0-9._-]{1,64}$`, `v` not `1`, `revision` not a positive integer, `targets` empty, unsorted, repeated, longer than 32 or not of the form `credential:<credential_id>` or `approver:<approver_id>`, or a noncanonical Base64 `identity_epoch`, `signing_key` or `signature`. |
| `unknown_signer` | `signing_key` is recognised as no configured anchor. |
| `signature_invalid` | `signing_key` fails [ed25519-key-admission/v1.md](../ed25519-key-admission/v1.md), or the signature fails [ed25519-verification/v1.md](../ed25519-verification/v1.md) under `signing_key`. |
| `superseded_signer` | `signing_key` is recognised as the previous provisioning anchor. |
| `wrong_authority` | `signing_key` is recognised as an anchor of another class. |
| `registry_unavailable` | The registry is locked. |
| `device_binding_mismatch` | The registry's device binding differs from the runtime's device identity. |
| `site_binding_mismatch` | The registry's site binding differs from the verified `device.site_id`. |
| `binding_mismatch` | The document's `device_id` differs from the runtime's device identity, or its `site_id` or `identity_epoch` from the registry's. |
| `revision_regressed` | `revision` is below `last_external_revision`. |
| `revision_conflict` | `revision` equals `last_external_revision` and the document's Profile 2 canonical JSON, `signature` included, differs from the one recorded. |
| `unknown_target` | A target names an approver or credential that is neither active nor tombstoned in this epoch. No target is revoked. |

A credential's tombstone records its approver ID, so an approver whose
credentials were all removed by `credential:` targets stays known.

Replay is decided after every row from `anchor_unavailable` to
`binding_mismatch`: the document's form, the anchor its `signing_key` is
recognised as, that anchor's class, the signature and the binding are all
checked first, and only then is its revision compared with
`last_external_revision`. A recorded document whose signer has since become
the previous provisioning anchor is therefore `superseded_signer`, not a
replay.

Revoking a credential tombstones its credential ID and its value, since
[tier-c-approvers/v1.md](../tier-c-approvers/v1.md) never recycles an ID or value
within an epoch; an `approver:` target also tombstones the approver ID.

On success the runtime commits the removal and answers with exactly `status`
(`revoked`), `registry_revision` and `last_external_revision` (the document's
`revision`). A repeat of the recorded document, compared as Profile 2
canonical JSON, is idempotent and answers `status` `replayed` with the two
revisions unchanged.

After the steps of [Order of refusal](#order-of-refusal):

| `error.code` | Refused when |

| `device_binding_mismatch` | The registry's device binding differs from the runtime's device identity. |

On success the runtime answers with exactly the registry's current
`device_id`, `site_id`, `identity_epoch` and `registry_revision`. It changes no
state.

## Runtime Device Key Readback

> Status: Not implemented. Defines the local discovery of the runtime's posture
> key that [runtime-posture/v1.md](../runtime-posture/v1.md) requires for
> commissioning a gateway's pin.

`runtime_device_key` reads the public key the runtime signs its posture
records with, so that an installer at the device can install it in the
gateway's configuration under
[gateway-config/v2.md](../gateway-config/v2.md#posture). It is **public-key
discovery, not enrolment**: it proves which key the runtime holds, and neither
which device the installer intended nor which site the device is at. It
changes no state, and grants, approves or enrols nothing.

It runs locally on the device, on the socket and under the framing and bound
of [Requests on the socket](#requests-on-the-socket), and MUST NOT be reachable
through any remote command, configuration document, gateway topic, MQTT topic,
product API or fleet API. It is not a registry operation and is not serialised
with them.

**Request.** Exactly one member: `operation`, the string `runtime_device_key`.

**Admission.** As [Authorisation](#authorisation) admits a registry operation:
from the kernel's peer credentials for the connection alone, root and the
installed operator identity.

**Order of refusal.** The first that fails is the answer:

1. the bound: `payload_too_large`;
2. the request's form and members: `invalid_arguments`;
3. the caller: `unauthenticated`;
4. the posture key is not loaded in this run, as when evidence is disabled or
   its key failed to unseal or load at start: `key_unavailable`.

**Answer.** `{"schema_version":1,"ok":true,"result":{...}}`, whose `result` has
exactly:

- `device_id`: the runtime's device identity, as runtime-posture/v1.md defines
  it;
- `public_key`: `ed25519:` followed by canonical padded RFC 4648 Base64 of the
  raw 32-byte posture key;
- `key_identity`: that key's `key_identity` as runtime-posture/v1.md defines
  it, the value its records carry.

A refusal is `{"schema_version":1,"ok":false,"error":{"code":"...","detail":"..."}}`.
The codes are closed: `payload_too_large`, `invalid_arguments`,
`unauthenticated` and `key_unavailable`; an unexpected runtime fault is
`internal_error`. `detail` is diagnostic text and a client decides nothing
from it. A client verifies the connected socket peer as the runtime service
identity of its installation before trusting an answer, as
[Requests on the socket](#requests-on-the-socket) requires of a registry
operation's client.

The answer holds a public key and nothing secret. It is read from the same
loaded key the runtime's health reports, so the two cannot disagree within a
run; a key that is not loaded is refused, never answered from a stored copy.

## Limits and later versions

- **No bridge or CLI command.** This version defines the socket requests only.
  A bridge or CLI command that submits them, with its arguments, envelope and
  exit codes, is a later version's.
- **No presence proof.** Admission authenticates a process. A wired presence
  input, its signed binding and its qualified local pin backend belong to a
  later version of [tier-c-approvers/v1.md](../tier-c-approvers/v1.md) and of
  this contract.
- **Local delivery only.** Revocation, recovery and enrolment reach a device
  only through this socket. A remote path needs its own authenticated epoch
  disclosure, topic, payload bound and rate under
  [gateway-api/v2.md](../gateway-api/v2.md); until then a compromised
  credential stays active until an operator reaches the site.
- **Phone authorisation outside the socket.** A phone-channel authorizer's
  `ORI-ENROL-V1` text and a phone candidate's possession reply arrive through
  the channel's own ingress. This contract carries neither and records no
  ingress for them.
- **No delivery report.** The challenge answer does not say whether a phone
  possession code reached its candidate.
- **Uncapped held state.** The runtime caps neither the challenges it holds nor
  the possession codes it sends for one admitted local operator, and keeps used
  markers until it restarts. Only root and the installed operator identity are
  admitted. A later version may cap them.
- **No rollback protection.** Restoring an old registry image can resurrect a
  revoked credential, as [tier-c-approvers/v1.md](../tier-c-approvers/v1.md)
  states. This socket cannot detect it.

## Representable and enforced

The registry operations, their bound, member strictness, authorisation,
serialisation, order of refusal and codes are representable here and exercised
by [vectors/approver-registry-v3.json](vectors/approver-registry-v3.json); its
cases for the rows marked defence in depth hold the states those rows guard
against directly, as fixtures, and show no path the runtime can reach. The read
deadline is stated and not exercised. No
production consumer serves them. The runtime is the enforcing repository: it
serves this socket and holds the registry, and until its consumer lands and
records its adoption, every registry operation on a runtime is refused, as it
is under [v2](v2.md). The bound and framing apply to `reconcile_tier_c` and
`evidence_commission` only once a runtime adopts this version.
