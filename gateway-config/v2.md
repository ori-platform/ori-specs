> end-to-end `none`, HIL `none`, production `none`. Record:

> `gateway.state_directory` except that it still admits work after deciding to
> stop, which rule 13 forbids; see the section's limits.


This document defines the `gateway.yaml` configuration surface for `ori-gateway`.
It covers all keys recognised by the config loader, their types, defaults, and
validation rules. The MQTT contract between runtime and gateway is in
[`gateway-api/v1.md`](../gateway-api/v1.md), and its versioned evidence carriage
in [`gateway-evidence-carriage/v1.md`](../gateway-evidence-carriage/v1.md).

## `gateway`

Core LAN transport settings.

| Key                    | Type       | Default | Required | Notes                                                                                                                                           |
| ---------------------- | ---------- | ------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `broker_url`           | `string`   | —       | Yes      | MQTT broker URL, e.g. `tcp://localhost:1883` or `mqtts://broker:8883`.                                                                          |
| `device_ids`           | `string[]` | —       | Yes      | Runtime device IDs this gateway will serve. Must contain at least one entry. IDs must not contain MQTT separators/wildcards or auth delimiters (`/`, `+`, `#`, `|`). A device that declares `gateway-evidence-carriage/v1` in `evidence.device_carriage` is additionally held to the evidence routing domain under [`evidence`](#evidence). |
| `heartbeat_interval_s` | `int`      | `30`    | No       | Must be positive. Gateway publishes `ori/gateway/health` on this interval.                                                                      |
| `state_directory`      | `string`   | `""`    | When `gateway.auth.enabled`, or when `posture.runtime_keys` has an entry | Absolute path of the gateway's own durable state, under the rules in [`gateway.state_directory`](#gatewaystate_directory). |

### `gateway.auth`

Authenticates runtime-gateway MQTT envelopes with the shared HMAC secret used by
both runtime and gateway. The value in YAML is an environment variable **name**,
not the secret itself.

| Key                          | Type     | Default                 | Required | Notes |
| ---------------------------- | -------- | ----------------------- | -------- | ----- |
| `enabled`                    | `bool`   | `false`                 | No       | Signs gateway health and verifies runtime node heartbeats. |
| `shared_secret_env`          | `string` | `GATEWAY_SHARED_SECRET` | No       | Env var containing the current shared HMAC secret. |
| `previous_shared_secret_env` | `string` | `""`                    | No       | Verify-only previous HMAC secret during rotation. |

When enabled, malformed, stale, replayed, retained, or unsigned runtime node
heartbeats are ignored. Reasoning/export/enrichment MQTT handling uses the same
runtime-gateway message-authentication family where implemented.

### `gateway.encryption`

Decrypts AES-GCM encrypted sensitive runtime export responses (`sensor_history`,
`action_log`, `reasoning_log`, and `tier_c_decision_log`). Requires
`gateway.auth.enabled: true`. Health exports remain plaintext operational posture.

| Key       | Type   | Default | Required | Notes |
| --------- | ------ | ------- | -------- | ----- |
| `enabled` | `bool` | `false` | No | Enables decryption for sensitive runtime exports. |

### `gateway.custody`

Names the secret that authenticates custody acknowledgements, per
[`evidence-exchange/v2.md`](../evidence-exchange/v2.md). It is key material
distinct from the runtime-gateway envelope secret, so it is a section of its
own. There is no `key_id`: the identifier is derived from the secret.

| Key          | Type     | Default | Required | Notes |
| ------------ | -------- | ------- | -------- | ----- |
| `secret_env` | `string` | —       | When `evidence.enabled` | Environment variable **name** holding the custody secret. Must be a variable name, and must differ from `gateway.auth.shared_secret_env` and `gateway.auth.previous_shared_secret_env`; the values they name must also differ, and differ from the ingest secret. The courier does not start without it and without `gateway.auth.enabled`. |

### `gateway.state_directory`

The gateway's own durable state, kept apart from evidence forwarding. It holds
the mark of the clock from which the gateway takes `signed_at_ms` for every
envelope it signs under the runtime–gateway HMAC outside the evidence path.
That clock is held to the Senders rule of
[`gateway-api/v2.md`](../gateway-api/v2.md#senders), with the exceptions the
limits below state. The clocks the gateway signs evidence-path envelopes from
are not kept here.

The directory confers no authority. No component reads it as a credential, a
grant or proof of identity. It holds only state a contract defines: this
section defines the marker, the lock, the mark, the posture store, and their
staged files.

**Load rules.** Before any rule applies, surrounding whitespace is removed from
the value, from the queue directories alike. Whitespace here is every character
with the Unicode `White_Space` property. A value that is then empty is absent.
The trimmed value is the configured state directory. The rules below apply in
order, whether or not authentication is enabled unless a rule says otherwise,
and a configuration is refused at load for the first rule it breaks, which the
refusal names:

- `required_under_auth`: `state_directory` is required when `gateway.auth.enabled` is true. A
  configuration that enables authentication without it, which loaded before
  this key existed, is refused, so upgrading such a gateway means adding the
  key.
- `required_under_posture`: `state_directory` is required when [`posture.runtime_keys`](#posture) has at
  least one entry, whether or not authentication is enabled, because the
  posture store lives there.
- `absolute`: a value that is present is an absolute path: it begins with `/`.
- `separate_from_evidence_queues`: while `evidence.enabled` is true, a present state directory is neither equal
  to, inside, nor containing `evidence.queue_directory` or
  `evidence.return_queue_directory`. Each path is first cleaned lexically:
  repeated and trailing `/` and `.` components are removed, each `..` removes
  the component before it, and a `..` at the root stays at the root. Inside and containing
  are decided on whole components, so `/` contains every queue directory and
  `/a/b-c` is not inside `/a/b`.

Components compare exactly, so letter case matters. Load refuses nothing else
about the value: characters inside it are left to the start requirements.

[`vectors/state-directory-v2.json`](vectors/state-directory-v2.json) fixes
these rules, and `scripts/check-gateway-config-state-directory-vectors` holds
the corpus to this section. The corpus is representable only until the gateway
vendors it and runs every case through its configuration loader; that
enforcement lives in `ori-gateway`.

**Start and mark requirements.** These bind the gateway at every start with
authentication enabled or a posture key configured, and while it runs. Rules 1
to 4 and 13 to 14 bind it in both cases; rules 5 to 12, the mark, bind it only
with authentication enabled; and the posture store rules below bind it only
with a posture key configured. They are not load rules, and the vectors do not
cover them.

The directory:

1. The gateway MUST open the directory at the lexically cleaned form of the
   configured state directory, before it signs anything or reads posture
   state.
2. It MUST refuse to start if that path is a symbolic link or not a directory,
   grants any access to group or other users, or is owned by a user other than
   the one the gateway runs as. If the path does not exist, it MUST create it
   with mode `0700`, and any parent it creates MUST grant no more than `0700`.
3. It MUST hold the directory exclusively for the life of the run, through an
   operating-system lock on `.ori-gateway-state.lock` that is released however
   the process exits, and MUST refuse to start when it cannot take that lock.
   It MUST NOT release the lock while a write of the mark or of the posture
   store is outstanding: the
   lock ends only once no write is outstanding, or with the process, as rule
   13 states.
4. The directory MUST hold the marker `.ori-gateway-state-v1`, whose content is
   exactly `ori-gateway state directory v1` followed by one line feed. A marker
   with any other content MUST refuse the start. A directory without a marker
   MUST be adopted, by writing one, when it is empty, and MUST refuse the start
   otherwise. In judging emptiness the gateway MUST disregard its lock file and
   its staged marker files, named `.ori-gateway-state-v1.` followed by a
   suffix. It MUST write the marker so that an interrupted write leaves either
   no marker or a complete one, and MUST take the lock of rule 3 only after
   the marker is in place.

The mark:

5. The mark is the file `.ori-signed-at-messages`. The gateway MUST write it
   through a staged file in the same directory, named
   `.ori-signed-at-messages.` followed by a suffix, renamed over it. A staged
   file is never the mark.
6. A mark is a regular file of at most 64 bytes holding a non-negative
   decimal integer number of milliseconds, possibly with leading zeros, a
   leading `+` and surrounding whitespace as the load rules define it, below
   the ceiling of 2^63 − 1 − 2,001. Any other mark, a longer file included, is
   corrupt and MUST refuse the start, and the gateway MUST NOT read more than
   65 bytes of it to decide.
7. The gateway MUST read the mark only after taking the lock of rule 3. The
   mark found at a start is the mark in the state directory, if any.
   Before issuing anything, the gateway MUST persist a mark no lower than the
   mark found, or than its wall clock when it found none, within rule 9's
   bounds, and MUST refuse the start if that write fails or has not completed
   within rule 11's write bound. Rule 11's episodes never apply to this write,
   and a start refused while it is outstanding ends as rule 13 states.
8. Each value it issues MUST be the latest of its wall clock, one past the last
   value it issued, and, when a mark was found, one past it.
9. A write of the mark **completes** when the mark's whole content has been
   written to the staged file and the staged file synced, then the staged file
   renamed over the mark, then the directory synced, and each step returned
   success. A write is outstanding from its first step until it completes or
   returns failure. A mark that is visible, or renamed but not yet synced, has
   not completed, and a write that failed or is still outstanding raises no
   coverage. The **covered value** is the highest mark whose write completed
   in this run, or the mark persisted at the start under rule 7.
   Each mark it persists MUST be at least every value it has issued, and at
   most the latest of its wall clock plus 1,000 ms, the mark found, the
   highest mark it has written before in this run, and the latest value it
   has issued or is issuing. Rewriting a mark already written adds no lead.
   The upper bound is judged against
   the wall clock the gateway reads when it chooses the mark, so a step back
   before the write lands does not breach it; the lower bound is judged when
   the write lands, so a mark never lands below a value already issued, except
   as rule 11 allows. Each mark it persists MUST also be no lower than the
   mark found and every mark it has written before in this run, whatever
   that write's outcome, so a mark never lowers one already written. It MUST persist a mark at or above a value
   before it issues that value, except as rule 11 allows. It SHOULD persist
   each mark off the signing path, ahead of the values that need it, where the
   bound allows.
10. It MUST NOT issue or persist a value at or above the ceiling. A start whose
    first value would reach the ceiling MUST refuse, and a running gateway
    MUST stop signing from this clock rather than reach it.
11. Writes of the mark while it runs, and **episodes**:
    - At most one write of the mark is outstanding at a time. The gateway
      MUST NOT start a write while another is outstanding, and MUST take each
      write's outcome once.
    - The **write bound** is 1,000 ms, measured on a monotonic clock from the
      start of the write. It bounds the disruption a stalled disk causes; it
      does not mark when coverage runs out, which signing time decides.
    - An episode opens, when none is open, as soon as a write returns failure,
      a write is still outstanding past its write bound, or a value has waited
      for coverage for the write bound. A write past its bound has not
      failed: it stays outstanding, and its outcome is taken when it returns.
    - Before an episode opens, values the covered value covers are issued
      without waiting, and a value beyond it waits for a write to cover it,
      for no longer than the write bound in all, measured on the same
      monotonic clock, and never past the moment an episode opens. While an
      episode is open, no
      value waits on any write, and the gateway MAY issue values the covered
      value does not cover. Rule 9's persist-before-issue requirement and its
      lower bound are suspended for that time; its upper bound, its rule that
      a mark never lowers one already written, and rule 10 are not.
    - While an episode is open the gateway MUST keep attempting the write.
      Whenever no write is outstanding, it MUST start a fresh one, even when
      the covered value still covers every value issued, no sooner than
      1,000 ms after the previous write started, and never once per message.
      Rule 13 ends these attempts.
    - An episode closes when, and only when, a write completes whose mark is
      at least the last value issued, judged when the completion is taken,
      under the same exclusion as issuing. A completion below that raises the
      covered value and leaves the episode open.
    - The gateway MUST log a warning each time an episode opens, and while it
      is open MUST report `degraded` in its heartbeat `status` and in its site
      health. Neither report may wait on a write. An open episode is not a
      failure to build or publish the gateway heartbeat; failing to build or
      publish it, rule 10 included, still is.

    The limits below state what that costs.
12. It MUST log a warning each time its signing time first runs more than
    300,000 ms, the default receiver skew, ahead of its wall clock.

The posture store:

- The posture store is the file `.ori-runtime-posture-v1`. It holds the held
  state of [`runtime-posture/v1.md`](../runtime-posture/v1.md) *Receiving*:
  for each configured device and each recognised key the gateway has held a
  record under, the held record's bytes, its pair, its `issued_at_ms`, the
  wall clock at its receipt, and the sticky reason of that device and key.
  Its encoding is the gateway's own.
- The gateway MUST read it only after taking the lock of rule 3, MUST NOT open
  it through a symbolic link, and MUST read at most 16,777,217 bytes of it. A
  store that does not exist holds no state. A store that is not a regular file,
  is longer than 16,777,216 bytes, cannot be read, or does not parse is
  unavailable: every configured device with a pinned key reads `unknown` with
  reason `store_unavailable`, nothing is accepted into it, and the gateway
  still starts, since the store carries a report and no authority. It reads the
  store only at start, and again only while it is unreadable, off the receive
  path and no sooner than 1,000 ms after the previous attempt began, until a
  read succeeds. It MUST NOT replace an unreadable store with an empty one.
- It MUST write the store through a staged file in the same directory, named
  `.ori-runtime-posture-v1.` followed by a suffix, renamed over it. A write
  completes as rule 9 defines completion for the mark, and its state is in
  force only once it completes. A write that fails, or is still outstanding
  1,000 ms after it began on a monotonic clock, makes the store unavailable
  until a write of the gateway's whole state in memory completes, which the
  gateway retries no sooner than 1,000 ms after the previous attempt began,
  never once per message; it never reads the store meanwhile. Every write
  carries every device's state, a change made while a write is outstanding
  waits for the next write, a change is in force only once a write that began
  after it completes, and once unwritten the store stays so until a completed
  write carries the generation of the state in memory. A write that would make the
  store longer than 16,777,216 bytes fails. While the store is unavailable for
  either cause, the gateway reports `degraded` in its heartbeat `status` and in
  its site health.
- At most one read or write of the store is outstanding at a time, none starts
  while another is, and a write never waits on the broker's delivery of other
  messages.

The end of a run:

13. To stop, the gateway MUST first stop issuing values and admitting work,
    and start no further write of the mark or of the posture store, then wait
    for the outstanding write of each, if any, for no longer than the
    **quiescence bound**.
    The release defines that bound and documents it, and it is finite. It is
    measured on a monotonic clock from the decision to stop, once for the
    whole stop: no later step restarts it. Stopping MUST NOT depend on
    signing a final heartbeat. When no write of either is outstanding it
    releases the lock and ends the run. When the bound passes with a write still
    outstanding, it MUST end the process with a non-zero status without
    releasing the lock first, and MUST NOT begin another run in that process.
    A start refused while its first write of the mark is outstanding ends the same way,
    its bound measured from the decision to refuse.

Supported storage:

14. The state directory MUST be on persistent storage local to the gateway's
    host, on a filesystem where the lock of rule 3 excludes every other
    process, a rename is atomic, and a successful sync of a file or a
    directory makes it durable. Rules 3, 9 and 13 rest on that: they keep one
    owner only where no process on another host can take the lock, and rule
    9's completion means durable only where sync does. NFS and other network or remote
    filesystems are not supported by this version. The gateway does not
    check this requirement.

#### Limits and later versions (state directory)

- **A value no persisted mark covers can repeat after a restart.** Rule 11
  lets the gateway issue values no persisted mark covers, and anything that
  lowers the mark leaves earlier values uncovered. Examples are deleting the
  mark, restoring an older copy of it, and configuring a different state
  directory. After a restart, such a value can be issued again, contrary to the
  Senders rule of [`gateway-api/v2.md`](../gateway-api/v2.md#senders).
  - An envelope repeated byte for byte is then refused under that contract's
    replay rules, outside the cases its limits name.
  - Fresh envelopes can be refused too, whatever their content. A receiver
    whose memory was full may have evicted the keys of values the gateway
    issued before the restart, raising its replay floor past them. An envelope
    the gateway then signs below that floor, and within the receiver's skew, is
    refused as `before_replay_floor`, the gateway heartbeat included, until its
    signing time passes the floor.

  This version accepts both costs rather than require the gateway to stop
  signing. Stopping would end every message signed from this
  clock, the gateway heartbeat among them, for as long as writes fail, and
  runtimes would treat the gateway as unreachable for that whole time.

  An episode has no end bound: a disk that never answers keeps it open, and
  every value issued meanwhile beyond the covered value stays uncovered. A write that lands late, below
  values issued since it started, covers only its own mark. A heartbeat
  published during an episode shows the gateway reachable, not its values
  covered. Receivers can still refuse what it signs, as `future_timestamp` or
  `before_replay_floor`, so an open episode can cost availability too.
- **A mark that ran ahead is kept.** Under rules 7 and 8 a gateway whose clock
  once ran fast keeps signing ahead of its wall clock until the wall clock
  passes its mark. The same holds when signing runs ahead without a fast
  clock, after a burst above one value per millisecond or a clock stepped back.
  While the value it issues is at least 1,000 ms ahead of its wall clock, a
  mark it chooses can reach no further than that value under rule 9. Values an
  earlier persisted mark already covers are issued without a write; once that
  coverage is used up, it persists a mark covering each value before issuing
  it, except as rule 11 allows, and signing waits on the disk, each wait no
  longer than the write bound, until the wall clock is less than 1,000 ms
  behind. A bound allowing more lead would
  let a gateway that restarts repeatedly while ahead add about 1,000 ms at
  every start.
  Receivers refuse what it signs beyond their skew as `future_timestamp`.
  Lowering the mark to recover leaves earlier values uncovered, as the limit
  above states.
- **Placement is checked lexically.** The load rule compares cleaned paths,
  not the filesystem. A symbolic link above the state directory, a queue
  directory reached through one, a bind mount, or a case-insensitive filesystem
  can place the state directory inside evidence storage without breaking the
  load rule. Among symbolic links, rule 2 refuses only a state directory that
  is itself one.
- **Storage is not checked either.** Rule 14 is an operator requirement. A
  state directory on a network filesystem loads and starts. There a lock can
  admit a process on another host while a write from this one is outstanding,
  and that write can then land over the other owner's mark and lower it. This
  breaks the ownership rules themselves, so it is a placement this version
  excludes, not a cost it accepts.
- **Ending the process is the bound, not its teardown.** Rule 13 bounds how
  long the gateway waits before ending its process. It cannot bound how long
  the operating system takes to end it. A process held in a write that the
  kernel cannot interrupt, on a device that has stopped answering, may not
  exit, and keeps its lock until it does. The cost is a gateway that is stuck,
  never two that own the directory at once.
- **What is enforced.** These rules are representable here. No corpus covers
  the start and mark requirements, and their proof lives in `ori-gateway`: its
  tests must stall a write through the real entry point, in a child process
  where rule 13 ends one. At ori-gateway `ec162f4`, which merged that work, a
  reading finds rules 3, 7, 9 and 11 implemented, and the write half of rule
  13. A review reproduced that it still admits work after deciding to stop: it
  stops signing at the decision, but closes its broker callback gate only
  during later cleanup, so a heartbeat delivered in between is admitted. Its
  evidence is host tests and CI, not storage that hangs, power loss or a
  deployment.

## `evidence`

The durable evidence courier, per
[`evidence-transport/v2.md`](../evidence-transport/v2.md) and the
`evidence_delivery` projection in
[`gateway-evidence-carriage/v1.md`](../gateway-evidence-carriage/v1.md).
The courier's own keys are validated at load whenever it is enabled; the keys
marked **Design target** and the rules that read them apply only to a site that
declares the versioned carriage, as stated below the table, except
`authority_ca_file`, whose rules apply whenever the courier is enabled.

| Key                      | Type     | Default | Required when enabled | Notes |
| ------------------------ | -------- | ------- | --------------------- | ----- |
| `enabled`                | `bool`   | `false` | —                     | Start the courier. Disabled, the other keys are not validated. |
| `queue_directory`        | `string` | —       | Yes                   | Absolute path of the durable outbound queue. |
| `return_queue_directory` | `string` | —       | Yes                   | Absolute path of the durable return queue; distinct from `queue_directory`. |
| `max_items`              | `int`    | `10000` | No                    | Positive. Total active-delivery entries; one gateway-wide share, reserved per device only under the rules below. |
| `max_bytes`              | `int`    | `268435456` | No                | Positive. Total active-delivery encoded bytes; one gateway-wide share, reserved per device only under the rules below. |
| `retry_interval_s`       | `int`    | `5`     | No                    | Positive. The delivery interval. |
| `backoff_base_s`         | `int`    | `retry_interval_s` | No         | Back-off base. |
| `backoff_max_s`          | `int`    | `300`, or `backoff_base_s` if longer | No | Back-off bound. |
| `store_probe_interval_s` | `int`    | `900`   | No                    | 300 through 900 under the rules below. |
| `endpoint_env`           | `string` | —       | Yes                   | Environment variable **name** holding the evidence authority endpoint. |
| `client_id_env`          | `string` | —       | Yes                   | Environment variable **name** holding the ingest client identifier. |
| `secret_env`             | `string` | —       | Yes                   | Environment variable **name** holding the ingest secret. |
| `authority_ca_file`      | `string` | `""`    | No                    | Implemented by the gateway at `22c3969`, not yet in a release. Path of a PEM bundle of the evidence authority's CA certificates, trusted in place of the system trust store. Empty: the system trust store. |
| `device_carriage`        | `map` | `{}` | No | **Design target.** Each device's declared inbound evidence-carriage contract, keyed by device ID. |
| `stopped_max_items`      | `int`    | `10000` | No                    | **Design target.** Positive. Total entries in stopped custody. |
| `stopped_max_bytes`      | `int`    | `268435456` | No                | **Design target.** Positive. Total encoded bytes in stopped custody. |
| `stopped_device_max_items` | `int`  | `stopped_max_items` divided equally across `gateway.device_ids` | No | **Design target.** Positive, and at most `stopped_max_items`. Entries in stopped custody for one device identity. |
| `stopped_device_max_bytes` | `int`  | `stopped_max_bytes` divided equally across `gateway.device_ids` | No | **Design target.** Positive, and at most `stopped_max_bytes`. Encoded bytes in stopped custody for one device identity. |

**Two rule sets, and only the courier's applies to a site that declares no
carriage.** The courier keys the gateway's loader consumes today are `enabled`,
the two queue directories, `max_items`, `max_bytes`, `retry_interval_s` and the
three environment variable names, and `authority_ca_file`; they are validated whenever `enabled` is
true: the directories are absolute and distinct, the bounds and the interval are
positive, and each environment variable name is a name, containing no whitespace
or `=`. Surrounding whitespace is removed from each queue directory before these
rules apply, and the courier uses the trimmed path. The `authority_ca_file` rule too applies whenever `enabled` is true, carriage declared or not.
A non-empty `authority_ca_file` is an absolute,
clean path: it begins with a single `/`, and has no `.` or `..` component, no
repeated or trailing `/`, and no leading or trailing whitespace. Nothing else is validated for a site whose configured devices all use
`gateway-api/v1` carriage, and a configuration the shipped loader accepts stays
accepted: the back-off keys, `store_probe_interval_s`, the stopped-custody bounds
and the evidence routing domain are design targets that production code does
not consume, and `enabled: true` on its own activates none of the rules below.

`device_carriage` declares each device's inbound evidence-carriage contract as
exactly `gateway-api/v1` or `gateway-evidence-carriage/v1`. Absence defaults to
`gateway-api/v1`. Every key MUST be one of `gateway.device_ids`, and every value
one of those two strings; any other key or value is refused. A device the map
does not name is declared `gateway-api/v1`, and the gateway MUST NOT stage an
`evidence_disposition` into its return lane, per
[`gateway-evidence-carriage/v1.md`](../gateway-evidence-carriage/v1.md).

**The rules below apply exactly when at least one configured device declares
`gateway-evidence-carriage/v1` in `device_carriage`, and a configuration that
breaks one is refused at load, before any lane opens:**

- the evidence routing domain applies to each device that declares that
  carriage, and to no other: its ID is 1 to 128 Unicode scalar values, none of
  them a control character (general category `Cc`), a character with the
  Unicode `White_Space` property, `/`, `+`, or `#`. A device on `gateway-api/v1`
  carriage is held only to the `gateway.device_ids` rule above;
- The back-off MUST satisfy `backoff_max_s >= backoff_base_s >= retry_interval_s`.
- capacity is reserved per configured device, as an equal share of `max_items`
  and `max_bytes`, so every lane the gateway serves, legacy lanes included,
  consumes its share. Each share MUST hold the registration reserve of
  [`evidence-transport/v2.md`](../evidence-transport/v2.md) plus one maximum
  encoded evidence record: at least two items, and at least the encoded bytes of
  one maximum-size registration record plus one maximum-size evidence record, as
  the gateway's own record format encodes them;
- `store_probe_interval_s` lies in its range, 300 through 900;
- the stopped-custody bounds are positive, and each per-device bound is at most
  its total.

Removing every declaration restores the courier's own validation; the gateway
migrates and deletes nothing it retains when a declaration is added or removed.
The three environment variable names are names, not values, and none of the
values they name appears in this file.

**The authority CA bundle.** Implemented by the gateway at `22c3969`, not yet in a release. When `authority_ca_file` is set, the courier trusts
only the bundle's certificates for the evidence authority's TLS endpoint, and
never the system trust store. Whoever can change the bundle decides whom the
gateway delivers evidence to, so the gateway MUST refuse to start unless every
one of these holds:

- no component of the path is a symbolic link;
- the file is a regular file, and it and every directory above it are owned by
  root and writable by no group or other user;
- the file is at most 1 MiB;
- it holds one or more PEM `CERTIFICATE` blocks and nothing else, each a CA
  certificate (basic constraints present, with the CA flag set). A private
  key, a leaf certificate or trailing data is refused.

During a CA rotation the bundle holds the old and the new CA. The bundle is read
when the courier starts, so a change takes effect on restart. These are startup
rules, not load rules: the vectors fix only the path's form.


The durable return store under `return_queue_directory` holds every staged
authority artifact: each device's return lane and the artifacts kept outside
every lane alike. Kept artifacts count toward the return store's item and byte
capacity and are never evicted; they count toward neither `max_items` and
`max_bytes` nor the stopped-custody bounds, and a retired device identity's
kept artifacts count until they leave the store. This revision configures no
key for the return store's capacity. An authority artifact the return store
cannot durably keep is a response the gateway has not durably staged, which
leaves the originating lane entry unadvanced and retried and blocks no other
device's return lane, per
[`gateway-evidence-carriage/v1.md`](../gateway-evidence-carriage/v1.md).

Stopped custody is bounded apart from active-delivery capacity: it counts
toward the stopped-custody bounds and never toward `max_items` or `max_bytes`.
The per-device bounds apply to each device identity, configured or retired, and
the totals to all stopped custody together. No bound is met by eviction or
deletion. Beyond an applicable bound a new artifact receives no gateway custody
and no acknowledgement, and a courier that opens with retained stopped custody
above a bound still opens, reports `stopped_custody_full`, refuses additional
stopped custody and delivers every lane that is not stopped, per
[`gateway-evidence-carriage/v1.md`](../gateway-evidence-carriage/v1.md). A bound
is therefore never a reason to refuse to start.
[`vectors/evidence-config-v2.json`](vectors/evidence-config-v2.json) fixes these
rules, and `scripts/check-gateway-config-evidence-vectors` holds the corpus to
this section.

## `posture`

The posture keys the gateway verifies runtime posture records under, as
[`runtime-posture/v1.md`](../runtime-posture/v1.md) defines them. Absent, or
with no entry, the gateway verifies no record, and every device reads
`unknown` with reason `no_pinned_key`.

| Key            | Type                  | Default | Notes |
| -------------- | --------------------- | ------- | ----- |
| `runtime_keys` | map of string to string | `{}` | Each key is one of `gateway.device_ids`. Each value is `ed25519:` followed by canonical padded RFC 4648 Base64 of the device's raw 32-byte posture key. |

**Load rules.** A configuration is refused at load for the first of these it
breaks, in this order, and the refusal names the rule:

1. `unknown_device`: a key of `runtime_keys` is not one of `gateway.device_ids`;
2. `malformed_key`: a value is not exactly `ed25519:` followed by canonical
   padded Base64 of 32 bytes;
3. `inadmissible_key`: a value's key fails
   [`ed25519-key-admission/v1.md`](../ed25519-key-admission/v1.md);
4. `duplicate_key`: two values are the same recognised key, as that
   contract's *Recognising a key* defines it, since one key identifies one
   device.

The [`gateway.state_directory`](#gatewaystate_directory) load rules are
judged before these, so a pin with no state directory is refused there, as
`required_under_posture`.

Rules 1 to 3 are judged entry by entry, in the order of the keys sorted by
code point, and an entry is judged against every rule from 1 to 3 before the
next entry is.

**Where a pin comes from.** A pin is installed at commissioning by an
installer who reads the key at the runtime device itself, through the
`runtime_device_key` operation of
[`operator-socket/v3.md`](../operator-socket/v3.md). That operation discovers
a key; it does not authorise one. The gateway never learns or replaces a pin
from MQTT, a product, a record or any source other than this configuration. A
changed pin is a configuration change and takes effect at the gateway's next
start. A pin is used for posture records only: the gateway never uses it to
verify, hold or classify an evidence artifact, nor any evidence key to verify
a posture record. Changing a pin never resets what the gateway holds under any key:
[`runtime-posture/v1.md`](../runtime-posture/v1.md) keeps each key's held
state across pins.

## Key Separation Invariants

- `provider` is for Tier 3 runtime reasoning requests only. Cloud reasoning
  remains a gateway backend — the runtime never calls cloud APIs directly.
- `reporting` is for advisory/product features. Failures here must not affect
  the reasoning path.
- API keys (`provider.cloud_llm.api_key_env`, `reporting.gemini.api_key_env`)
  must be environment variable **names**, not values. Never commit key values.
- `reporting.*` credentials must not appear in `ori.yaml` (runtime config) and
  must not be passed through MQTT reasoning envelopes.
