# CLI Commands v1

> Status: Implemented baseline bridge surface, with additional ecosystem commands planned
> Notes: the runtime owns parsing/validation semantics; `ori-cli` delegates to the runtime bridge instead of reimplementing them.

This document defines the minimum viable operator/developer CLI surface expected for `ori-cli`.

## Existing Runtime Entrypoint

| Item | Value |
|---|---|
| runtime entrypoint | `python -m ori.runtime` / `ori-runtime` |
| CLI bridge entrypoint | `python -m ori.cli_bridge` |
| `--config` | optional, default `ori.yaml` |
| `--log-level` | `DEBUG/INFO/WARNING/ERROR` |

## Runtime-Owned CLI Bridge

`ori-cli` must treat the runtime bridge as the source of truth for runtime
configuration parsing, skill validation, and runtime health snapshot semantics.
The CLI may format bridge output for humans, but it must not duplicate runtime
validation rules.

Bridge invocation:

```bash
python -m ori.cli_bridge <command> [args...]
```

The canonical bridge command shape is noun/verb, matching the public
operator CLI vocabulary. For example:

```bash
python -m ori.cli_bridge config validate --path ori.yaml
python -m ori.cli_bridge skills validate --skills-dir skills/
python -m ori.cli_bridge health snapshot --socket /tmp/ori-health.sock
```

Legacy single-token bridge commands remain accepted as compatibility aliases
while sibling tools migrate. New CLI implementations should use the canonical
noun/verb form.

Bridge response envelope:

```json
{"schema_version":1,"ok":true,"command":"config validate","result":{}}
```

Bridge error envelope:

```json
{"schema_version":1,"ok":false,"command":"config validate","error":{"code":"config_validation_error","detail":"..."}}
```

Bridge exit codes:

- `0`: command completed and `ok=true`
- `2`: expected operator/user error such as invalid arguments, invalid config,
  invalid skill, unavailable health socket, or malformed health response
- `1`: unexpected bridge/runtime error

Bridge output is exactly one JSON object followed by a newline. Sensitive values
are redacted by the runtime bridge before stdout emission.

### Canonical Bridge Commands

| Bridge command | Legacy alias | Required args | Optional args | Purpose |
|---|---|---|---|---|
| `config validate` | `config-validate` | `--path <ori.yaml>` | none | Load config through runtime parser and return summarized posture when valid. |
| `config show` | `config-show` | `--path <ori.yaml>` | none | Same parser path as validate; intended for human-friendly CLI display. |
| `skills list` | `skills-list` | `--skills-dir <dir>` | `--require-signed` | Discover and validate loadable skills under a skill root. |
| `skills validate` | `skills-validate` | `--skills-dir <dir>` | `--require-signed` | Validate one skill directory or every skill directory under a skill root. |
| `health snapshot` | `health-snapshot` | `--socket <path>` | `--timeout-ms <int>` | Read one runtime health snapshot from the runtime health socket. |

`config validate` and `config show` return a summary containing:

- `device`: id, name, location, timezone, country, deployment type/profile, and site type
- `sensors`: id, type, protocol, poll interval, metadata keys, and
  `device_path_kind` (`none`, `socket`, `direct_serial`, `url`, or `path`)
- `skills`: configured skill names and versions
- `config_signature`: signed-config posture without exposing signature secrets
- `telemetry_export`: endpoint posture and API-key environment variable name
- `device_policy`: policy URL/signing/auth posture without exposing secrets
- `phone_runtime_mobile`: phone authority ceiling and socket-bridge sensor posture

`skills list` and `skills validate` return:

- `valid`: true only when no skill errors are present
- `skill_count` and `error_count`
- `skills`: loaded skill summaries including triggers and action tiers
- `errors`: per-skill error code/detail entries

## MVP Command Set

### `ori doctor`

- checks configuration presence/validity
- checks runtime importability
- checks environment readiness (model file, SQLite path writable, alert env vars)

Exit codes:

- `0`: no FAIL checks
- `1`: at least one FAIL
- `2`: config file missing/unreadable

### `ori config validate`

- validates config against runtime config parser rules

Exit codes:

- `0`: valid
- `1`: invalid
- `2`: file not found / parse failure

### `ori skills list`

- lists skill packages discoverable from configured skills directory

Exit codes:

- `0`: one or more skills loaded
- `1`: no skills loaded / all invalid

### `ori skills validate`

- validates one skill (`--skill-path`) or all configured skills (`--config`)

Exit codes:

- `0`: all requested skills valid
- `1`: one or more invalid

### `ori skills reload --pid`

- sends `SIGHUP` to running runtime process

Exit codes:

- `0`: signal delivered
- `1`: process missing / signal error

### `ori state action-log`

- reads `action_log` SQLite table

Exit codes:

- `0`: query success
- `1`: DB error

### `ori state history --sensor-id`

- reads `sensor_history` SQLite table

Exit codes:

- `0`: query success
- `1`: DB error
- `2`: sensor not found

## Device Deployment Identity Preparation

### `ori deploy`

`ori deploy` prepares a device-local Ed25519 identity and reports public
material for a later, separately specified registration flow. It is not itself
a cloud-registration command in v1.

Options:

| Option | Type | Default | Meaning |
|---|---|---|---|
| `--key-dir` | path | `~/.ori` | Directory containing the device identity files. |
| `--force` | bool | `false` | Deliberately replace an existing valid identity. |
| `--dry-run` | bool | `false` | Generate an ephemeral public key without reading runtime health, writing files, or making network calls. |
| `--socket` | path | `/run/ori/health.sock` | Runtime health socket used for non-dry-run validation. |

`--json` and `--output json` select the repository-wide JSON output mode.
Cloud destination, credential, and confirmation flags are not part of this
command version. The CLI must reject unknown cloud-mutation flags rather than
guessing an unpublished request contract.

### Runtime preconditions

Except in dry-run mode, the CLI must read a canonical
[runtime-health/v1](../runtime-health/v1.md) success envelope before creating or
replacing key material. Legacy flat health responses are insufficient for
deployment preparation.

The canonical response must contain:

- a non-empty string `health.device_id`;
- the required `health.evidence` object;
- boolean `evidence.enabled` and `evidence.available` fields; and
- a string `evidence.public_key_hex`.

If evidence is enabled, `available` must be true and `public_key_hex` must be
exactly 64 lowercase hexadecimal characters. Missing or malformed evidence
posture fails closed before key files are changed. When evidence is disabled,
`available` must be false and `public_key_hex` must be empty.

### Local identity state

The identity is stored as:

| File | Contents | Required posture |
|---|---|---|
| `device.key` | PKCS#8 PEM Ed25519 private key | regular, non-symlink file; owner read/write only (`0600`) |
| `device.pub` | lowercase hexadecimal Ed25519 public key plus newline | derived from `device.key`; no private material |

The private key is authoritative and never appears in output, logs, runtime
health, or network requests. An existing identity may be reused only after its
private-file type and permissions are validated and its public projection is
confirmed or safely regenerated.

Only one process may inspect, recover, create, or replace a key store at a
time. The exclusive lock covers recovery through the final durable commit.
Concurrent invocations must serialize or fail without modifying the identity;
they must never both report successful creation of different identities.

Normal retries reuse the existing identity. `--force` replaces it through a
crash-recoverable transaction:

1. durably write both candidate files;
2. retain the previous authoritative private key;
3. commit the candidate private key and its derived public projection;
4. durably establish the matching final pair as the commit point; and
5. remove the previous private-key backup.

Recovery must deterministically retain either the previous valid identity or
the fully committed replacement. A missing or stale public projection may be
regenerated from a valid private key. Invalid, non-regular, symlinked, or
over-permissive private material fails closed and is not silently deleted.

### JSON results

Successful dry-run output:

```json
{
  "ok": true,
  "dry_run": true,
  "identity_pubkey_hex": "<64 lowercase hex>",
  "message": "<operator-readable status>"
}
```

Successful persisted output:

```json
{
  "ok": true,
  "dry_run": false,
  "device_id": "<runtime device ID>",
  "identity_pubkey_hex": "<64 lowercase hex>",
  "evidence_pubkey_hex": "<64 lowercase hex or empty when disabled>",
  "key_dir": "<key directory>",
  "cloud_registration": "deferred",
  "message": "<operator-readable status>"
}
```

`cloud_registration` is exactly `deferred` in this contract version. A future
authenticated registration operation requires an obtainable ori-cloud
request/authentication/response contract before CLI adoption.

Exit codes:

- `0`: dry run completed, or a valid local identity is ready;
- `1`: invalid arguments, unavailable/malformed runtime health, unsafe key-file
  posture, lock failure, or key-store persistence/recovery failure.

## Commissioning Reference Delivery

> Status: Design target. Not implemented in `ori-runtime` or `ori-cli`. Defines
> the device-side ingress that [evidence-exchange/v1.md](../evidence-exchange/v1.md)
> requires for the commissioning reference.

A runtime registers its evidence anchor under a commissioning authorisation it
never holds. What it holds is the **commissioning reference** — the
authorisation's `commissioning_digest`, `sha256:` plus 64 lowercase hex — and
this is the only path by which that reference reaches a device.

```bash
python -m ori.cli_bridge evidence commission --path ori.yaml --reference sha256:<64 lowercase hex>
```

| Bridge command | Legacy alias | Required args | Optional args | Purpose |
|---|---|---|---|---|
| `evidence commission` | none | `--path <ori.yaml>`, `--reference <sha256:hex>` | `--socket <path>`, `--force` | Record the commissioning reference for this device's current evidence epoch in the runtime's durable state |

`--path` locates the runtime's state store through the configuration's
`database.path`, exactly as the `config` commands locate the document;
`--socket` names the runtime health socket, default `/run/ori/health.sock`.

The command:

- runs locally on the device with no network access, and MUST NOT be reachable
  through any remote command, configuration document, gateway topic, or fleet
  API — a reference arriving by any of those is refused by the consumer that
  sees it, and `runtime-config/v2` declares no field for it;
- refuses a reference that is not exactly `sha256:` plus 64 lowercase
  hexadecimal characters, before touching any state;
- reads the runtime's current `anchor_epoch_id` from the
  [runtime-health/v2](../runtime-health/v2.md) snapshot's `evidence` object,
  failing closed when it is absent or malformed, and records the reference
  against **that epoch** in the runtime's state store — durably, atomically,
  readable by the runtime at startup and on every registration retry, and
  with the same exclusive-lock and crash-recovery posture as the local
  identity state above. A reference is never recorded without an epoch, and
  never rewritten to name a different one;
- replaces a previously recorded reference for the same epoch only with
  `--force`, reporting the replacement; and
- returns the recorded epoch and reference, and the registration status the
  runtime will now report, per *Registration status at the runtime* in
  [evidence-exchange/v1.md](../evidence-exchange/v1.md): `pending_confirmation`
  once the reference is held, since holding one is what leaves
  `pending_authorisation`, and `confirmed` if a confirmation for that epoch is
  already held.

The tool holds no commissioning key and cannot verify that the reference
resolves to anything. A wrong, stale or foreign reference is refused by the
evidence authority as `commissioning_digest_mismatch` and grants nothing; that is why
a hash may pass through an installer's tool where the authorisation itself may
not. The command MUST NOT display, log, or accept any identity, endpoint, or
credential of the evidence authority.

Successful JSON result:

```json
{
  "ok": true,
  "device_id": "<runtime device ID>",
  "anchor_epoch_id": "sha256:<64 lowercase hex>",
  "commissioning_reference": "sha256:<64 lowercase hex>",
  "replaced": false,
  "registration_status": "pending_confirmation"
}
```

Exit codes:

- `0`: reference recorded, or already recorded identically;
- `2`: malformed reference, unavailable or malformed runtime health, an
  existing different reference without `--force`, or a lock failure;
- `1`: unexpected bridge/runtime error.

## Runtime Health Snapshot

The runtime health socket is one input used by the bridge command
`health snapshot`. It is not the only socket in the phone/APK architecture and
must not be confused with Android USB serial bridge sockets.

Runtime health socket contract:

- transport: local Unix domain socket
- Linux default path: `/run/ori/health.sock`
- phone/Android paths must be read from runtime config, typically under the
  app/runtime-writable sandbox rather than `/run`
- request: `GET_HEALTH\n`
- response: JSON line with `schema_version`, `ok`, and `health` payload
- CLI timeout default: 3000 ms

The CLI should discover or accept the configured socket path. It must not assume
`/run/ori/health.sock` works for phone deployments.

Recommended CLI shape:

### `ori doctor runtime-health`

- call `python -m ori.cli_bridge health snapshot --socket <path>`
- print summary for:
  - capability posture
  - sensor connectivity/staleness
  - device policy state
  - last alert timestamps
- return non-zero on unavailable socket or malformed response

## Android USB Serial Bridge Note

Phone/APK USB serial support uses a separate loopback TCP serial bridge, not the
runtime health Unix socket.

For phone USB meter profiles, the signed runtime config uses a sensor
`device_path` such as:

```yaml
device_path: socket://127.0.0.1:39871
```

That `socket://` path is consumed by the runtime USB serial adapter or mobile
runtime payload as a serial transport. Android Java owns USB Host permission,
binds the approved VID/PID/serial identity, and exposes bytes through the
loopback socket. The runtime must not open Android USB devices directly.

`ori-cli` should display this as sensor transport posture (`device_path_kind:
socket`) when presenting `config show`, but it must not treat it as the runtime
health socket.
