# Tier C Approval Contract v1

> Status: maturity `draft`; compatibility `amendable`; adoption: none
> recorded; proof: end-to-end `none`, HIL `none`, production `none`. Record:
> [status/tier-c-approval/v1.json](../status/tier-c-approval/v1.json).
>
> The runtime implementation is in progress and not on main.


This contract defines how the runtime admits an operator's approval of a Tier C
proposal and dispatches the approved action: the proposal, durable admission,
dispatch, restart, reconciliation, the safe default, the decision states and
their severity. [events/v1.md](../events/v1.md) defines the action record; the
approval record this admission produces is proposed in
[events/v2.md](../events/v2.md) and not yet ratified.

Tier C approval is runtime authority. The runtime admits an approval and
dispatches the approved action; no gateway grants or replaces that authority; a
gateway may relay an operator reply, which is not an approval. A relayed reply
reaches approval only through the admission below, and
[gateway-api/v1.md](../gateway-api/v1.md) retains its shipped request, response
and export semantics.

## Scope

`tier-c-approval/v1` requires a commissioned zone and commissioned outcome for
Tier C actions capable of changing physical state. A generic `coap_command`
without that mapping MUST NOT be proposed as Tier C. Host-state Tier C actions
remain on the existing approval workflow outside this contract for v2.5.0, as
do Tier B actions requiring approval. A future resource-scoped approval
contract may unify those workflows.

Every clause of this contract, of the Tier C binding in
[offline-tokens/v2.md](../offline-tokens/v2.md) and of `evidence
reconcile-tier-c` in [operator-socket/v1.md](../operator-socket/v1.md) applies to a
Tier C action capable of changing physical state, and "Tier C proposal",
"approval" and "dispatch" below mean that action's. A CoAP-backed commissioned
actuator participates only through its commissioned zone and outcome, never
through the generic `coap_command` action. A host-state Tier C action, such as
`terminate_process`, is neither admitted nor refused by this contract, and its
tier is not lowered to fit it: it stays on the existing approval workflow with
its authority unchanged, and no v1 offline token approves it there. A runtime
conforming to this contract MUST NOT accept a v1 token as approval for any Tier
C action. This includes host-state Tier C actions that remain on the existing
approval workflow. Because [offline-tokens/v2.md](../offline-tokens/v2.md)
requires a commissioned zone, a host-state Tier C action has no offline-token
approval path until a resource-scoped approval contract defines one.

## The Proposal

Every Tier C proposal binds at least `proposal_id`, `device_id`, the action
and its target, the commissioned zone it commands, the observation or event
identity it was derived from, the commissioned binding identity, the authority
snapshot under which execution would be permitted, `created_at_ms`, and
`expires_at_ms`. Every Tier C proposal carries a runtime-owned
`expires_at_ms`, derived from a bounded release or commissioned-policy duration
and not supplied or extended by the operator reply. The lifetime is the
release-defined maximum, shortened by `approval_timeout_seconds` where
runtime-config/v2 permits. A reply received after expiry is not an approval:
the runtime records `proposal_expired` and notifies the operator.

If the proposal row cannot be committed durably, no proposal exists and none is
sent to the operator. No reply can approve it and no physical action executes.
The runtime attempts the configured non-actuating safe default and raises a
CRITICAL operational notification, but MUST NOT claim that either was durably
recorded or executed when the store or its relevant writer is unavailable. Tier
D remains unaffected.

The authority snapshot is one closed canonical object, and the proposal binds
its exact bytes:

```json
{
  "action": "trip_relay",
  "action_capability": "sha256:<64 lowercase hex>",
  "binding_digest": "sha256:<64 lowercase hex>",
  "outcome": "open_protected_circuit",
  "policy_digest": "sha256:<64 lowercase hex>",
  "resource": "relay-gpio-26",
  "safety_profile": "sha256:<64 lowercase hex>",
  "v": 1,
  "zone_digest": "sha256:<64 lowercase hex>",
  "zone_id": "zone-feeder-a"
}
```

| Member | Binds |
| --- | --- |
| `v` | The integer `1`. |
| `binding_digest` | The in-force commissioned binding the proposal was created under. |
| `zone_id` | The commissioned zone the proposal commands. |
| `zone_digest` | That zone's entry in the binding. |
| `safety_profile` | The digest of the safety profile in force on the zone, or `""` when none is. |
| `action` | The proposed action, as the runtime's action registry names it. |
| `action_capability` | The digest of that action's registry capability: its minimum tier, whether it is physical, its consequence class, one of `informational`, `soft`, `hard`, and whether it is safe-default eligible. |
| `outcome` | The commissioned outcome the action commands. |
| `resource` | The resource the zone's commissioned mapping resolves that outcome to. |
| `policy_digest` | The digest of every policy input that can change Tier C admission of this action: the release-defined admission policy, any device-policy capability grant governing it, and each deployment setting runtime-config/v2 permits to affect admission. |

Every digest other than an empty `safety_profile` is `sha256:` followed by 64
lowercase hexadecimal characters over the canonical bytes of what it names. The snapshot carries exactly these
members, each a string except `v`, and is serialised in the Profile 2 canonical
form of [signing/v2.md](../signing/v2.md). A snapshot missing a member, carrying
another, or naming a member twice is malformed, and a proposal cannot be
created under it.

At proposal creation the runtime records `created_at_ms` and `expires_at_ms`
for audit, and establishes a monotonic deadline in the creating process.
Admission and dispatch expiry are decided exclusively against that monotonic
deadline. Wall-clock movement MUST NOT shorten or extend execution authority.
An open proposal does not regain a monotonic deadline after process restart:
it is closed as `proposal_aborted_restart`, the operator is notified, and a
fresh proposal derived from current observations is required.

## Admission

An operator reply becomes an approved Tier C decision only when
the runtime has durably committed the decision, proposal identifier,
authenticated ingress identity, and the in-force authority and commissioned
binding under which execution is permitted. Before that commit it is a received
reply, not an approval. A reply whose commit fails is not an approval: the
proposal remains open until it expires, and the operator receives an explicit
failure and retry indication. Remote replies, the local console and offline
tokens reach approval through this same durable admission, and a duplicate
reply for an admitted decision is idempotent. An offline token reaches it only
as [offline-tokens/v2.md](../offline-tokens/v2.md) binds it to the proposal; a
v1 token is not Tier C approval.

At approval admission, the current commissioned binding identity and authority
snapshot MUST byte-match those bound into the proposal. A mismatch means the
reply is not an approval: the runtime records `approval_binding_changed`,
notifies the operator, applies no physical action, and requires a fresh proposal
under the current binding and authority. The comparison is of the canonical
authority snapshot bytes above.

## Dispatch

Once the approval commit succeeds, dispatch MUST proceed without
waiting for evidence signing, evidence delivery, action-log persistence, Tier C
decision export, gateway availability or any further state-store write. After
the approval commit, dispatch must begin immediately in the same live
execution attempt. If dispatch has not begun before expiry, the runtime records
`approval_expired_undispatched`, applies the non-actuating safe default, and
requires a fresh proposal. The action outcome is appended after dispatch.
Failure to record the outcome MUST NOT repeat, roll back or obscure the
physical action. The durable approval remains, and the outcome is reported as
unknown until reconciled.

The durable approval-admission commit reserves capacity for a terminal
uncertainty record before the reply becomes an approval. If the complete
outcome cannot be appended after dispatch, including because the
pending-outcome ceiling has been reached, the reserved record resolves as
follows. Reaching the ceiling MUST NOT delay dispatch, discard the approval, or
cause replay. The resulting uncertainty blocks the same physical outcome on the
same commissioned zone until reconciliation under this contract.

An unknown outcome held in memory is not a durable `dispatch_outcome_unknown`.
While the live runtime cannot append the outcome, its outcome is counted in
`action_records.pending`, or in `action_records.unknown_live` once `pending`
is at `ceiling`:
the runtime holds an in-memory unknown-outcome diagnostic and reports it
through `action_records`, and it claims no durable state it has not written.
`unknown_live` is process-local diagnostic state. It is never represented as
durable `dispatch_outcome_unknown` until a durable write succeeds. After
process loss, recovery selects `dispatch_outcome_unknown` only from a durable
dispatch marker and otherwise selects `dispatch_not_proven`.
When its store accepts the write while it still runs, it appends the outcome
the executor reported, which is `dispatch_outcome_unknown` for a result that
cannot establish the physical outcome. After a restart, the reserved record
becomes `dispatch_outcome_unknown` only where a durable dispatch marker exists,
and `dispatch_not_proven` otherwise, as *Restart* states.

## Restart

A durable Tier C approval grants execution authority only to the
live runtime execution attempt that admitted it. If that process terminates
before dispatch begins, restart MUST NOT execute or replay the approved action.
Only where the runtime possesses affirmative durable proof that dispatch was
never invoked, it durably records `approval_aborted_undispatched` with reason
`runtime_restart`, performs the proposal's non-actuating safe default, alerts
the operator, and requires a fresh proposal derived from current observations
if the condition persists; absence of `dispatch_started` is not such proof.
A runtime that forbids any write between the approval commit and the executor
call can hold no such proof, so for it `approval_aborted_undispatched` with
reason `runtime_restart` is unreachable, and every restart that finds an
approval without a durable outcome records `dispatch_outcome_unknown` where a
durable dispatch marker exists and `dispatch_not_proven` otherwise.
Once dispatch has begun, absence of a durable
outcome MUST NOT cause automatic replay. The runtime records
`dispatch_outcome_unknown`, raises a CRITICAL operator and audit event, and requires
observation or operator reconciliation before another equivalent Tier C action
is admitted. An equivalent Tier C action is one commanding the same physical
outcome on the same commissioned zone, and observation and operator
reconciliation are the two forms of reconciliation defined below.

The dispatch-start marker is diagnostic evidence, not the actuation boundary.
After restart, absence of that marker does not prove that dispatch did not
begin. A durable approval with neither a durable outcome nor affirmative proof
that dispatch was never invoked becomes `dispatch_not_proven`; it MUST NOT be
replayed, raises a CRITICAL operator and audit event, and requires the same
reconciliation as `dispatch_outcome_unknown`.

## Reconciliation

An unresolved `dispatch_outcome_unknown` or
`dispatch_not_proven` blocks only a later Tier C proposal commanding the same
physical outcome on the same commissioned zone. It does not block another
outcome, another zone, Tier A/B, or any Tier D evaluation or execution.

An unresolved `dispatch_outcome_unknown` or `dispatch_not_proven` prevents
creation of a later Tier C proposal commanding the same physical outcome on the
same commissioned zone. The runtime evaluates the block again when admitting an
operator reply, because an uncertainty may arise after the proposal was
created. A reply against a now-blocked outcome and zone is not an approval: the
runtime durably closes the proposal as `proposal_blocked_uncertain_outcome`,
applies its non-actuating safe default, notifies the operator, and requires a
fresh proposal after reconciliation. The block does not affect another outcome,
another zone, Tier A/B, or any Tier D evaluation or execution. At proposal
creation, an approval for the same outcome and zone whose outcome the live
runtime could not append blocks creation as an unresolved uncertainty does; one
merely in flight is caught at reply admission.

At reply admission the block is evaluated inside the approval commit
transaction. An approval commanding the same physical outcome on the same
commissioned zone blocks the reply while it is `approved_pending_dispatch` or
`dispatch_started`, or while it is `dispatch_outcome_unknown` or
`dispatch_not_proven` and not reconciled. No other state blocks it: an
approval that is `executed`, `dispatch_failed`,
`dispatch_refused_contention`, `approval_expired_undispatched`,
`approval_aborted_undispatched`, `reconciled_executed` or
`reconciled_not_executed` does not.

Reconciliation is either:
(a) an authenticated local operator command recording an observed terminal
outcome; or
(b) a deterministic observation from commissioned feedback for that zone whose
mapping proves the commanded outcome.
Reconciliation appends a record linked to the uncertain dispatch; it never
rewrites the original uncertainty. An uncommissioned sensor, model inference,
gateway response or absence of an alarm cannot reconcile it. It moves
`dispatch_outcome_unknown` or `dispatch_not_proven` to `reconciled_executed` or
`reconciled_not_executed`. Form (a) is `evidence reconcile-tier-c` in
[operator-socket/v1.md](../operator-socket/v1.md#tier-c-reconciliation). Form (b) has
no contract shape yet.

## Safe Defaults

A Tier C safe default MUST be Tier A and non-actuating. It MUST NOT invoke any
executor, command or transport capable of changing relay, contactor, valve,
protected-circuit, supply-transfer or other physical state. The runtime MUST
additionally refuse any safe default whose action-registry entry is marked
`physical`. Registry metadata is a redundant enforcement check, not the
definition of physicality. A safe default may alert, log, escalate or request
reevaluation.

The actions `trip_relay`, `close_gas_valve` and `release_relay` named in
[safety-profile/vectors/legacy-actions.json](../safety-profile/vectors/legacy-actions.json),
the outcomes `open_protected_circuit` and `close_protected_circuit` they
resolve to, and `coap_command` are a pinned instance of this rule: each is
refused as a safe default. The list is an instance, not the definition. An
action outside it that can change physical state is refused by the rule above,
whatever its registry entry says.

A Tier C proposal is invalid unless its safe-default action has a registered
capability classified `informational` and `safe_default_eligible`. An absent
registry entry is refused. The runtime may emit its own release-owned
diagnostic log or alert for that refusal, but that diagnostic is not the
proposal's safe default. The classification is the capability's consequence
class, one of `informational`, `soft`, `hard`, recorded in the runtime's action
registry beside its `physical` and `safe_default_eligible` flags, and a physical
capability is never `safe_default_eligible`. The registry entry is necessary and not sufficient:
the semantic rule above and the independent guard below still refuse an entry
that claims `informational` for an action able to change physical state.

This repository cannot read the runtime's action registry, so the rule is
enforced in `ori-runtime` by a guard that:

- exports or enumerates every action the runtime can execute;
- classifies every one of them exhaustively by physicality: `informational`,
  `host_state`, `physical`;
- fails on a new action it has not classified;
- rejects as a safe default every action it does not classify
  `informational`, and every physically capable action whatever its tier or registry entry;
- rejects as a safe default every action with no registry entry, and every
  entry whose consequence class is not `informational` or that is not
  `safe_default_eligible`;
- is independent of the registry: its classification table is pinned in the
  guard, not read from the registry it checks;
- detects a mutation that falsely changes a physical action's `physical`
  flag.

The two axes are distinct: the registry's consequence class, `informational`,
`soft` or `hard`, and the guard's physicality, `informational`, `host_state` or
`physical`. Safe-default eligibility requires `informational` under the
physicality guard and eligibility under the registry. Neither axis may silently
default: an action the guard has not classified, and one with no registry entry
or no consequence class, is refused as a safe default and never treated as
`informational`.

Closing an open proposal as `proposal_aborted_restart` or
`approval_binding_changed` applies its non-actuating safe default, records that
outcome separately from the proposed action, notifies the operator and requires
a fresh proposal. Neither state authorizes the proposed physical action.

The runtime durably creates at most one safe-default intent per proposal, keyed
by `proposal_id`. Execution uses the applicable executor's delivery semantics.
Alert delivery is retried at least once through the durable alert outbox and
may be duplicated after an ambiguous provider result; every attempt carries the
proposal identifier. Local durable logging is idempotent by that identifier. No
safe-default intent may actuate. Every clause of this contract that applies a
safe default applies it through that one intent, except where the proposal row
could not be committed, when no proposal and no intent exists and the attempt is
made as *The Proposal* states: a repeated reply, a restart or a later refusal of
the same proposal creates no second intent.

## Decision States

`decision_state` is one of `proposed`, `proposal_expired`,
`rejected`, `approved_pending_dispatch`, `dispatch_started`, `executed`,
`approval_expired_undispatched`, `approval_aborted_undispatched`,
`proposal_aborted_restart`, `approval_binding_changed`,
`proposal_blocked_uncertain_outcome`, `dispatch_refused_contention`, `dispatch_failed`, `dispatch_outcome_unknown`,
`dispatch_not_proven`, `reconciled_executed`, and `reconciled_not_executed`.
`executed` means the outcome was durably recorded
as executed; `dispatch_failed` means the outcome was durably recorded and the
executor reported that the actuation failed. `dispatch_failed` is permitted
only when the executor can affirm that the commanded physical outcome did not
occur. A timeout, lost response, partial execution, or any result that cannot
establish the physical outcome is `dispatch_outcome_unknown`, not
`dispatch_failed`. `dispatch_refused_contention`
means the dispatcher refused the approved act before actuation because an
opposing act already held its resource; the runtime applies the non-actuating
safe default, alerts the operator, and requires a fresh proposal.

## Severity

| Condition | Severity |
| --- | --- |
| An approved decision record is lost | Critical invariant violation; structurally impossible, because execution cannot begin before the approval commit |
| Dispatch began and its outcome was not recorded | Evidence health `degraded`, plus a CRITICAL operator and audit event; never replayed |
| A durable approval whose dispatch is not proven either way | `dispatch_not_proven`: evidence health `degraded`, plus a CRITICAL operator and audit event; never replayed |
| An admitted approval refused before actuation because an opposing action holds the resource | `dispatch_refused_contention`: not evidence loss; a CRITICAL operational event; apply the proposal's non-actuating safe default through its one safe-default intent, perform no automatic retry, and require a fresh evaluation |
| An admitted approval whose executor definitively reports that the commanded physical outcome did not occur | `dispatch_failed`: not evidence loss; a CRITICAL operational event; no automatic replay, and a fresh evaluation is required |
| Approved but undispatched, proven, because of restart or expiry | Not evidence loss, since the decision is durable; a CRITICAL operational event, the non-actuating safe default only, and a fresh evaluation |
| A proposal closed `proposal_blocked_uncertain_outcome` | Not evidence loss; a CRITICAL operational event; apply its non-actuating safe-default intent, notify the operator, and require reconciliation followed by a fresh proposal |
| A proposal closed `approval_binding_changed` | Not evidence loss; a CRITICAL operational event because the approved authority context changed; apply its non-actuating safe-default intent and require a fresh proposal under the current binding and authority |
| An open, unapproved proposal closed `proposal_aborted_restart` | Not evidence loss and not an approved mitigation failure; an operational warning, the non-actuating safe-default intent, operator notification, and fresh evaluation |
| A proposal row could not be committed | No proposal or evidence record exists; Tier C is operationally unavailable for that attempt and a CRITICAL operational notification is attempted. The safe default and notification are attempted but neither is claimed durable, and evaluation may resume only after durable proposal storage recovers |
| A late reply refused before admission | Not critical; `proposal_expired` recorded and the operator notified |

The runtime reports these through `action_records` in
[runtime-health/v3.md](../runtime-health/v3.md).

## Exports

The `tier_c_decision_log` export in [gateway-api/v1.md](../gateway-api/v1.md)
is unchanged by this contract, and carries neither `decision_state` nor the
proposal's `expires_at_ms`. Exporting either, or any other state this contract
defines, changes that wire surface and needs gateway-api/v2 or a separately
versioned export contract. Gateway API v1 retains its shipped request, response
and export semantics; it MUST NOT emit an events/v2 approval record on a surface
that declares events/v1.

## Vectors

[`vectors/admission.json`](vectors/admission.json) fixes each transition, the
safe-default cases with their registry entries, which proposals this contract
governs, refuses or leaves outside it, and the authority snapshot's closed
canonical form, and `scripts/check-tier-c-approval-vectors` holds the corpus to
this contract, with `--mutations`.
