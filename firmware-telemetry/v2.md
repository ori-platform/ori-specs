# Firmware Telemetry Contract v2

> Status: maturity `draft`; compatibility `amendable`; adoption: verifier
> (runtime) `implemented-unreleased`, `unassessed`; proof: end-to-end `none`,
> HIL `none`, production `none`. Record:
> [status/firmware-telemetry/v2.json](../status/firmware-telemetry/v2.json).

This version exists so a device can sign a refusal it makes under
[firmware-commands/v2.md](../firmware-commands/v2.md): a `command_rejected`
fault whose `detail` is `rate_limited`.

## What changed from v1

Two things change. A consumer of this version admits a device key under
[ed25519-key-admission/v1](../ed25519-key-admission/v1.md) and verifies every
signature it accepts under this version, on the manifest, the telemetry
envelope, the fault and the maintenance lifecycle event alike, under
[ed25519-verification/v1](../ed25519-verification/v1.md). v1 named neither
rule, and a v1 consumer whose verifier takes the cofactored equation or
decodes R loosely accepts signatures this version refuses, none of which a
device makes by signing under RFC 8032. A signature that contract refuses,
under any of its clauses, is `signature_verification_failed`, and a device key
admission refuses is never registered. No signed bytes change.

The other change is to the signed fault event. A fault object may carry
`"v":2`, and under `v` `2` the closed `detail` sets are the ones this document
lists. Against v1 as it was frozen, they differ in two tokens:

- `rate_limited` is added to `command_rejected`, for
  [firmware-commands/v2.md](../firmware-commands/v2.md);
- `liveness_authority_failed` is listed under `ingress_degraded`. v1's text
  gained it in place after its freeze, its classification there is still owed
  by v1's baseline audit, and consumers of v1 differ on it. At `v` `2` it is a
  member, whatever that audit decides for v1.

[v1](v1.md)'s closed `command_rejected` set cannot take the token in place.
v1 calls extending a closed set an additive change, but its consumers refuse
a token outside the set, so every existing consumer would stop conforming the
moment the token became valid. Under
[VERSIONING](../VERSIONING.md#compatibility) that is not additive. A device has
no way to tell whether the consumer reading its evidence is one of them. The
version therefore travels inside the signed fault, where the device that
chose it is the only party that could have.

Everything else is v1's, as its text stands at ori-specs `d979402`,
incorporated unchanged: the trust model except for the key admission and
signature verification above, the signature encoding, canonical JSON, the capability manifest and its validation, the
telemetry envelope and heartbeats, sequence and freshness, the MQTT transport,
the fault code vocabulary and every non-closed `detail` category, signed
maintenance lifecycle events, error semantics and the required artifacts.

**No other object changes version.** The manifest, the telemetry envelope and
the maintenance lifecycle event keep `"v":1` and their v1 grammar. In
particular the manifest's bytes do not change, so adopting this version
changes no device's `capability_hash` and is not a capability transition.

## Signed Fault Events

A fault object is v1's, field for field, except for `v`:

| Field | Type | Notes |
| --- | --- | --- |
| `v` | `int` | The fault object's version: `1` or `2`. Unlike v1, it is not the telemetry envelope's `v`, which stays `1`. |

```json
{
  "fault": {
    "v": 2,
    "alg": "ed25519",
    "device_id": "ori-fw-7c9f2b3a",
    "boot_id": 41,
    "seq": 130485,
    "capability_hash": "sha256:<64-lowercase-hex>",
    "posture": "sealed_flash",
    "device_uptime_ms": 925000,
    "code": "command_rejected",
    "subject": "command",
    "detail": "rate_limited"
  },
  "signature": "ed25519:<base64-64-byte-signature>"
}
```

### Closed `detail` sets at `v` 2

| Code | Tokens |
| --- | --- |
| `command_rejected` | The verdicts of [firmware-commands/v2.md](../firmware-commands/v2.md#error-semantics): `malformed`, `wrong_device`, `bad_signature`, `replayed`, `capability_mismatch`, `unknown_action`, `rate_limited`, `storage_failure`. |
| `ingress_degraded` | `inbound_overflow`, `subscribe_failed`, `anchor_persist_failed`, `mqtt_provision_epoch_failed`, `provisioning_serial_io_failed`, `provisioning_serial_overflow`, `liveness_authority_failed`, each with the meaning v1's fault code table gives it. |
| `storage_degraded` | `buffer_write_failed`, `buffer_mount_failed`, with v1's meanings. |

These are complete. Under `v` `2` a consumer MUST reject a fault whose `detail`
for one of these codes is outside its row, empty included, even when its
signature verifies. Every other code keeps v1's category and v1's rule.

A fault object at `v` `1` keeps v1's shape and `detail` rules, with one rule
stronger here: v1 says a consumer SHOULD reject a token outside a closed set,
and a consumer of this version MUST reject `rate_limited` in a `v` `1` fault,
because no conforming producer signs it there. Its signature, like that of
every object a consumer of this version accepts whatever its `v`, is verified
under the key admission and signature verification above.

### Producers

A producer that implements this version signs every fault object at `v` `2`,
including a fault it signs late from state carried across a reboot or an
update. It MUST NOT sign `rate_limited` at `v` `1`. Messages it signed before
it implemented this version and still holds in its offline buffer are
retransmitted unchanged, at `v` `1`: retransmission is not signing.

A fault at `v` `2` consumes `seq` from the same counter as every other signed
family, exactly as in v1. There is one monotonic stream per key epoch whatever
the versions of the objects in it.

### Consumers

A consumer that implements this version accepts a fault object at `v` `1` or
`v` `2`, applies the `detail` rules of the fault's own version, and rejects any
other `v`, including a `v` of another JSON type. It holds no record of which
version a device last used: `v` is inside the signed bytes, so only the device
chooses it, and a `v` `1` fault from a device that has also signed `v` `2`
faults is judged under v1 like any other.

A consumer that implements only v1 rejects every `v` `2` fault, because v1
requires `v` to be `1`. A device that signs at `v` `2` is therefore read only by
consumers that implement this version.

Everything else about verification is v1's: anchor, manifest pin, signature
encoding, freshness, the subject and detail bounds, and the trust grades. The
signature itself is verified, and the device key admitted, under the shared
contracts named in [What changed from v1](#what-changed-from-v1). A fault is
evidence about the device's own conduct; it is never converted into a
`SensorReading` and never triggers an action.

A `command_rejected` fault whose `detail` is `rate_limited` reports a command
that was genuine, current and permitted, and that the device declined to
actuate. A consumer records it as a refusal and never as an execution, and
it is not an input to any safety condition. See
[firmware-commands/v2.md](../firmware-commands/v2.md#rate-limited-refusal).

## Adoption Order

The runtime adopts this version and
[firmware-commands/v2.md](../firmware-commands/v2.md) before any device signs a
`v` `2` fault. A runtime on v1 refuses every `v` `2` fault, and under
firmware-commands/v1 a command whose fault it refused is a command it must
treat as lost and retry, which is the late actuation the successor exists to
prevent.

Every other verifier adopts this version before the devices whose evidence it
reads. A producer on this version signs every new fault at `v` `2`, so a
verifier on v1 alone refuses all of that device's faults, `interlock_tripped`
included, from the moment the device adopts.

## Golden Vectors

The authoritative corpus for this version's fault events is
[fault-vectors-v2.json](fault-vectors-v2.json), held here beside this
document. Its SHA-256 is
`7c54e32f65e02e9b58f7eb28a669977277863c81f2349b78970a69354b30bff0`.

Implementing repositories copy it byte for byte, pin that digest, and never
generate its expectations from their own behaviour.

It holds signed fault events at `v` `2` for every fault code and every token of
every closed set above, a `v` `1` fault a consumer of this version still
accepts, and refusals whose signatures verify: `rate_limited` at `v` `1`, a
token outside its code's set at `v` `2`, an empty closed-set `detail`, and
unsupported versions. Each refusal names its reason, and its signature is valid,
so a consumer that refuses it has refused it for that reason rather than at the
signature.

`scripts/generate-firmware-fault-vectors-v2` reproduces the file byte for byte.
`scripts/check-firmware-fault-vectors-v2` shares no code with it: it recomputes
canonical bytes, re-derives the key from the disclosed seed and verifies every
signature with its own curve arithmetic, reads the closed sets from this
document and [firmware-commands/v2.md](../firmware-commands/v2.md), and
confirms that each refusal is refused for its declared reason and for no
other.

The disclosed test seed is a fixture only and MUST NOT be provisioned on any
device.

## Required Implementation Artifacts

In addition to v1's:

- consumer tests driving the corpus through the consumer's real verification
  entry point, accepting every case and refusing every refusal for its declared
  reason;
- consumer tests driving the corpora of
  [ed25519-key-admission/v1](../ed25519-key-admission/v1.md) and
  [ed25519-verification/v1](../ed25519-verification/v1.md) through the
  verifier the consumer uses for this version's signatures, accepting every
  accepted case and refusing every refused one;
- a producer test that the device signs the `rate_limited` refusal of
  [firmware-commands/v2.md](../firmware-commands/v2.md) at `v` `2`, and that no
  fault is signed at `v` `1` once the producer implements this version.
