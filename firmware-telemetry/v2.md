# Firmware Telemetry Contract v2

> Status: maturity `draft`; compatibility `amendable`; adoption: verifier
> (runtime) `implemented-unreleased`, `unassessed`, producer (edge-firmware)
> `implemented-unreleased`, `unassessed`; proof: end-to-end `none`, HIL
> `none`, production `none`. Record:
> [status/firmware-telemetry/v2.json](../status/firmware-telemetry/v2.json).

This version exists so a device can sign a refusal it makes under
[firmware-commands/v2.md](../firmware-commands/v2.md): a `command_rejected`
fault whose `detail` is `rate_limited`. It also settles what a manifest's
`device_mode` means, and makes every bridged channel name the controller
profile that decoded it.

## What changed from v1

Four things change what a consumer accepts, and one meaning v1 left open is
settled. A consumer of this version admits a device key under
[ed25519-key-admission/v1](../ed25519-key-admission/v1.md) and verifies every
signature it accepts under this version, on the manifest, the telemetry
envelope, the fault and the maintenance lifecycle event alike, under
[ed25519-verification/v1](../ed25519-verification/v1.md). v1 named neither
rule, and a v1 consumer whose verifier takes the cofactored equation or
decodes R loosely accepts signatures this version refuses, none of which a
device makes by signing under RFC 8032. A signature that contract refuses,
under any of its clauses, is `signature_verification_failed`, and a device key
admission refuses is never registered. No signed bytes change.

The second change is to the signed fault event. A fault object may carry
`"v":2`, and under `v` `2` the closed `detail` sets are the ones this document
lists. Against v1 as it was frozen, they differ in two tokens:

- `rate_limited` is added to `command_rejected`, for
  [firmware-commands/v2.md](../firmware-commands/v2.md);
- `liveness_authority_failed` is listed under `ingress_degraded`. v1's text
  gained it in place after its freeze, its classification there is still owed
  by v1's baseline audit, and consumers of v1 differ on it. At `v` `2` it is a
  member, whatever that audit decides for v1.

[v1](v1.md)'s closed `command_rejected` set cannot take the token in place.
v1 calls extending a closed set an additive change, but its consumers refuse
a token outside the set, so every existing consumer would stop conforming the
moment the token became valid. Under
[VERSIONING](../VERSIONING.md#compatibility) that is not additive. A device has
no way to tell whether the consumer reading its evidence is one of them. The
version therefore travels inside the signed fault, where the device that
chose it is the only party that could have.

The third change is to manifest validation. v1 lists `device_mode` values
without defining them, and accepts any string there, any disagreement with the
manifest's arrays, and a manifest that declares no channel. A consumer of this
version refuses all three: see [Device Mode](#device-mode). These rules
deliberately tighten v1's acceptance, and a manifest a v1 producer may sign is
refused under them. Producers and consumers are updated together.

[Late Faults](#late-faults) settles what a fault's freshness fields describe
when it is signed after the condition it reports, which v1 said only of
`storage_degraded`. It changes no grammar and refuses nothing.

The fourth change is to bridged channels. v1 signs that a channel is bridged
and nothing about what decoded it. Under this version every bridged channel
names, in the signed manifest, the controller profile that decoded it, by a
digest over the profile's full interpretation, and the qualification the
device attests for it; a foreign controller's alarm registers are read as
bridged channels interpreted through that profile. See
[Controller Profiles](#controller-profiles). This too tightens v1's
acceptance, in three ways: a bridged channel that names no profile is refused,
a bridged channel on a protocol other than `modbus_rtu` is refused, and the
sensor type `controller_alarm_word` and the unit `bitmask` are refused on any
channel that is not a bridged alarm word, which can refuse a device that
declares no bridged channel at all.

Everything else is v1's, as its text stands at ori-specs `d979402`,
incorporated unchanged: the trust model except for the key admission and
signature verification above, the signature encoding, canonical JSON, the capability manifest and its validation, the
telemetry envelope and heartbeats, sequence and freshness, the MQTT transport,
the fault code vocabulary and every non-closed `detail` category, signed
maintenance lifecycle events, error semantics and the required artifacts,
except as [Late Faults](#late-faults), [Device Mode](#device-mode) and
[Controller Profiles](#controller-profiles) state.

**No other object changes version.** The manifest, the telemetry envelope and
the maintenance lifecycle event keep `"v":1` and their v1 grammar. The manifest
gains the validation rules of [Device Mode](#device-mode), and one field, on
bridged channels only: `controller_profile`. A device that declares no bridged
channel signs the same bytes as before, so adopting this version changes its
`capability_hash` only if it declares a bridged channel, and for such a device
adoption is a capability transition. A reading envelope gains no field.

## Signed Fault Events

A fault object is v1's, field for field, except for `v`:

| Field | Type | Notes |
| --- | --- | --- |
| `v` | `int` | The fault object's version: `1` or `2`. Unlike v1, it is not the telemetry envelope's `v`, which stays `1`. |

```json
{
  "fault": {
    "v": 2,
    "alg": "ed25519",
    "device_id": "ori-fw-7c9f2b3a",
    "boot_id": 41,
    "seq": 130485,
    "capability_hash": "sha256:<64-lowercase-hex>",
    "posture": "sealed_flash",
    "device_uptime_ms": 925000,
    "code": "command_rejected",
    "subject": "command",
    "detail": "rate_limited"
  },
  "signature": "ed25519:<base64-64-byte-signature>"
}
```

### Closed `detail` sets at `v` 2

| Code | Tokens |
| --- | --- |
| `command_rejected` | The verdicts of [firmware-commands/v2.md](../firmware-commands/v2.md#error-semantics): `malformed`, `wrong_device`, `bad_signature`, `replayed`, `capability_mismatch`, `unknown_action`, `rate_limited`, `storage_failure`. |
| `ingress_degraded` | `inbound_overflow`, `subscribe_failed`, `anchor_persist_failed`, `mqtt_provision_epoch_failed`, `provisioning_serial_io_failed`, `provisioning_serial_overflow`, `liveness_authority_failed`, each with the meaning v1's fault code table gives it. |
| `storage_degraded` | `buffer_write_failed`, `buffer_mount_failed`, with v1's meanings. |

These are complete. Under `v` `2` a consumer MUST reject a fault whose `detail`
for one of these codes is outside its row, empty included, even when its
signature verifies. Every other code keeps v1's category and v1's rule.

A fault object at `v` `1` keeps v1's shape and `detail` rules, with one rule
stronger here: v1 says a consumer SHOULD reject a token outside a closed set,
and a consumer of this version MUST reject `rate_limited` in a `v` `1` fault,
because no conforming producer signs it there. Its signature, like that of
every object a consumer of this version accepts whatever its `v`, is verified
under the key admission and signature verification above.

### Producers

A producer that implements this version signs every fault object at `v` `2`,
including a fault it signs late from state carried across a reboot or an
update. It MUST NOT sign `rate_limited` at `v` `1`. Messages it signed before
it implemented this version and still holds in its offline buffer are
retransmitted unchanged, at `v` `1`: retransmission is not signing.

A fault at `v` `2` consumes `seq` from the same counter as every other signed
family, exactly as in v1. There is one monotonic stream per key epoch whatever
the versions of the objects in it.

### Consumers

A consumer that implements this version accepts a fault object at `v` `1` or
`v` `2`, applies the `detail` rules of the fault's own version, and rejects any
other `v`, including a `v` of another JSON type. It holds no record of which
version a device last used: `v` is inside the signed bytes, so only the device
chooses it, and a `v` `1` fault from a device that has also signed `v` `2`
faults is judged under v1 like any other.

A consumer that implements only v1 rejects every `v` `2` fault, because v1
requires `v` to be `1`. A device that signs at `v` `2` is therefore read only by
consumers that implement this version.

Everything else about verification is v1's: anchor, manifest pin, signature
encoding, freshness, the subject and detail bounds, and the trust grades. The
signature itself is verified, and the device key admitted, under the shared
contracts named in [What changed from v1](#what-changed-from-v1). A fault is
evidence about the device's own conduct; it is never converted into a
`SensorReading` and never triggers an action.

A `command_rejected` fault whose `detail` is `rate_limited` reports a command
that was genuine, current and permitted, and that the device declined to
actuate. A consumer records it as a refusal and never as an execution, and
it is not an input to any safety condition. See
[firmware-commands/v2.md](../firmware-commands/v2.md#rate-limited-refusal).

## Late Faults

A fault's `boot_id`, `seq` and `device_uptime_ms` are those of the moment it is
signed. A producer that reports a condition late signs each report with the
freshness fields of its own reporting, never with those of the condition. That
covers a report made from a latch, a report made on a later boot, and every
retry of a report the producer could not make durable: each attempt is stamped
when it is signed.

A consumer cannot tell a late report from a prompt one, so these rules attach
to the code, whenever the fault was signed. They do not touch verification: a
fault's freshness fields are still checked exactly as v1 checks them, and they
still establish that the report itself is fresh. What they cannot establish is
when the condition occurred, or anything about authority or the device's
current state. For a fault whose code is `storage_degraded`,
`brownout_relay_fault`, `sensor_fault` or `ingress_degraded`:

- A consumer MUST NOT use its freshness fields to locate the condition, to
  derive how long it lasted, or to derive any authority. The fault asserts that
  the condition occurred on the device, not when, and not that it still held
  when the fault was signed.
- A consumer MAY count the reports it accepted, named as reports, and MUST NOT
  present or use that number as a count of failures, outages or affected
  commands. One condition can be reported more than once: a producer that made
  a report durable but could not then clear the latch that owed it reports it
  again, on the same boot or a later one. Several conditions can also be
  coalesced into one report.
- A consumer MUST NOT treat the absence of such a fault as evidence that the
  condition did not occur. v1 says this of `storage_degraded`; it holds for
  each of these codes.

An `ingress_degraded` fault with `detail` `liveness_authority_failed` says
that the runtime liveness authority could not be installed, so the device was
left without runtime supervision. It is not a measure of how long the device ran unsupervised, and it neither opens
nor closes any liveness window. Its absence is not evidence that the device is
supervised.

The interlock codes and `command_rejected` keep v1's meaning.

The fault object has no field for the time of the condition. If one is ever
needed, it is a separately named field with its own boot semantics, in a
successor version. `device_uptime_ms` is never overloaded with it.

## Device Mode

The capability manifest's `device_mode` names the roles its `channels` and
`actions` declare. A channel whose `source` is `foreign_device` is bridged;
every other channel meters.

| Value | The manifest declares |
| --- | --- |
| `sensor_node` | Metering channels only, and no actions. |
| `bridge_node` | Bridged channels only, and no actions. |
| `actuator_node` | Actions only, and no channels. |
| `mixed` | More than one of the three: metering channels, bridged channels, actions. |

`mixed` covers actuation: a device that meters or bridges and also declares an
action is `mixed`, and so is an actuator that declares the channel its
interlock reads.

In addition to v1's [manifest validation](v1.md#manifest-validation), a
consumer of this version MUST reject a manifest when:

- `device_mode` is not one of the four values above, including a value of
  another JSON type (recommended error `invalid_device_mode`);
- `device_mode` is not the value its `channels` and `actions` determine
  (`invalid_device_mode`);
- `channels` is empty (`no_channels`).

`actuator_node` is therefore defined and never accepted under this version. A
manifest with no channel stays refused until a contract defines how an
actuator that reports nothing has its actuation commissioned and its outcome
observed. The refusal is not itself that evidence: a declared channel can
measure something unrelated to the load the action drives.

A producer MUST sign the value its manifest's arrays determine, and MUST NOT
sign a manifest with no channel. Each public boundary that builds a manifest
(a device's own serializer, an SDK's builder) enforces both rules itself,
rather than relying on a caller that happens to.

The mode is a summary and confers nothing. A consumer MUST NOT derive a
channel, an action, an authority or a trust grade from it, and MUST NOT make an
authority or trust decision differently because of it. What a device reports is
in `channels`; what it may do is in `actions` and each action's `authority`; what
a runtime may command is governed by its own tier and commissioning rules. A
surface that shows a device's roles to an operator derives them from the
verified arrays, which the rules above make agree with the mode.

## Controller Profiles

A bridged channel reports a value a foreign controller holds in its registers,
read and decoded by the device. What the value means depends on how it was
decoded: which registers, at what width and word order, under what scale and
offset, and, for an alarm register, which bit means which alarm. A controller
profile is that interpretation, written down once per supported controller and
shipped in the device's reviewed release. A site selects a profile; it never
supplies or edits one.

Under this version the signed manifest names, for every bridged channel, the
profile that decoded it and the profile channel it reads, by a digest over the
profile's complete interpretation. A change to anything in the profile changes
the digest, so it changes the manifest and its `capability_hash`, and is a
capability transition. A receiver that follows this section cannot read an
unchanged register value under a new interpretation unless the manifest
changed too.

A signature over a reading attests what the device read and which
interpretation applied. It does not attest that the foreign controller
reported truthfully.

A fleet identifier, wherever Controller Profiles names one, is a string of 1 to 48
characters, each from the fleet alphabet: `A`–`Z`, `a`–`z`, `0`–`9`, `.`,
`_` and `-`.

### The `controller_profile` field

A channel object gains one field:

```json
{
  "channel": "ch1",
  "sensor_type": "current",
  "unit": "ampere",
  "protocol": "modbus_rtu",
  "source": "foreign_device",
  "quality_floor": 0.8,
  "controller_profile": {
    "id": "example-rectifier",
    "digest": "sha256:<64-lowercase-hex>",
    "profile_channel": "output_current",
    "qualification": "qualified",
    "record": "controllers/records/example-rectifier.md"
  }
}
```

| Field | Type | Notes |
| --- | --- | --- |
| `id` | string | The profile's `id`, a fleet identifier. |
| `digest` | string | `sha256:` and 64 lowercase hex: SHA-256 over the canonical bytes of the profile document. |
| `profile_channel` | string | The `name` of the profile channel this channel reads, a fleet identifier. |
| `qualification` | string | `qualified` or `unqualified`. |
| `record` | string or null | The repository path of the qualification record, relative to the root of the repository that ships the profile; `null` exactly when `qualification` is `unqualified`. |

A `record` is 1 to 127 characters, each from the fleet alphabet or `/`. It
does not begin or end with `/`, never has two `/` in a row, and never contains
`..` anywhere, even inside a segment.

The object's keys are exactly these five. Qualification and its record are not
part of the profile document and not covered by its digest: they are the
device's signed statement about the profile, carried beside it, and the
manifest's own hash covers them. A change of qualification is therefore a
capability transition as well.

In addition to v1's [manifest validation](v1.md#manifest-validation) and
[Device Mode](#device-mode), a consumer of this version MUST reject a manifest
when:

- a bridged channel carries no `controller_profile` (`controller_profile_missing`);
- a channel that is not bridged carries `controller_profile` (`controller_profile_unexpected`);
- a `controller_profile` breaks the grammar above, or a bridged channel's
  `protocol` is not `modbus_rtu` (`invalid_controller_profile`);
- a channel declares `sensor_type` `controller_alarm_word` or `unit`
  `bitmask`, unless it is a bridged channel that declares both
  (`invalid_alarm_channel`).

A consumer applies these rules from the manifest alone. It does not need the
profile document to register a device, and holding one changes nothing about
whether a manifest is accepted.

A producer MUST NOT sign a manifest these rules refuse. A device signs a
bridged channel only when the profile that decodes it is in the device's
reviewed release, and signs the digest of that profile's document as the
device holds it. The release that ships a profile publishes its document beside
the release, so a receiver can hold it before any device signs a reading
through it. A device signs each alarm-word reading alone in its envelope.
Each public boundary that builds a manifest (a device's own
serializer, an SDK's builder) enforces these rules itself, rather than relying
on a caller that happens to.

Channels that name the same profile `id` carry the same `digest`,
`qualification` and `record`, and channels that name the same `digest` name the
same `id`: a device holds one document and one qualification per profile. A
consumer MUST reject a manifest in which they differ
(`invalid_controller_profile`).

The manifest does not say which unit on the bus a channel reads. Two channels
reading the same `profile_channel` of two identical controllers are
distinguished only by their manifest `channel`, and moving a controller to
another bus address is not a capability transition.

### The profile document

A profile document is a JSON object, hashed as its canonical bytes under v1's
[canonical JSON](v1.md#canonical-json). Every number in it is an integer.

A document is held, published and hashed as bytes. A receiver hashes the bytes
it holds, and uses them only if they are exactly the canonical bytes of the
object they parse to: valid UTF-8, no duplicate key at any depth, and nothing a
canonical serializer would write differently. A document whose bytes are not
canonical is refused, even when re-serializing its parse would yield the pinned
digest, because two parsers can read two interpretations from one such
document.

```json
{
  "v": 1,
  "id": "example-rectifier",
  "source": "Example Corp R48 Modbus register map, revision C",
  "baud_rate": 9600,
  "poll_interval_ms": 5000,
  "channels": [
    {
      "name": "output_current",
      "kind": "measurement",
      "function": "read_input_registers",
      "start_register": 40,
      "register_count": 1,
      "word_order": null,
      "raw_signed": false,
      "raw_min": 0,
      "raw_max": 2000,
      "scale": {"mantissa": 1, "exponent": -1},
      "offset": {"mantissa": 0, "exponent": 0},
      "sensor_type": "current",
      "unit": "ampere"
    },
    {
      "name": "alarm_word_1",
      "kind": "alarm_word",
      "function": "read_holding_registers",
      "start_register": 100,
      "register_count": 2,
      "word_order": "high_first",
      "alarms": [
        {"bit": 0, "active": "set", "id": "ac_input_fail", "meaning": "AC input failure"},
        {"bit": 17, "active": "clear", "id": "fan_stopped", "meaning": "Fan stopped"}
      ]
    }
  ]
}
```

Top-level fields, exactly these:

| Field | Rule |
| --- | --- |
| `v` | `1`. |
| `id` | A fleet identifier. |
| `source` | The document the map is taken from: 1 to 256 printable ASCII characters, U+0020 to U+007E. Never parsed. |
| `baud_rate` | One of `1200`, `2400`, `4800`, `9600`, `19200`, `38400`, `57600`, `115200`. Framing is 8N1; a controller that needs another is not describable by this document. |
| `poll_interval_ms` | `100` to `3600000`; at most `1190000` in a profile with an `alarm_word` channel, so that three missed polls and the transport allowance fit within the receiver's one-hour bound. |
| `channels` | 1 to 16 channel objects. |

Every channel carries:

| Field | Rule |
| --- | --- |
| `name` | A fleet identifier; unique in the profile. |
| `kind` | `measurement` or `alarm_word`. |
| `function` | `read_holding_registers` or `read_input_registers`. |
| `start_register` | `0` to `65535`. |
| `register_count` | `1` or `2`, with `start_register + register_count <= 65536`. |
| `word_order` | `null` when `register_count` is `1`; `high_first` or `low_first` when it is `2`. Declared, never assumed. |

A `measurement` channel also carries exactly these, and no other field:

| Field | Rule |
| --- | --- |
| `raw_signed` | Boolean: the register, or register pair, is two's complement. |
| `raw_min`, `raw_max` | The validity range in raw counts, inclusive, `raw_min <= raw_max`, each representable at the channel's width and signedness. A frame outside it is a failed read, never a reading. |
| `scale` | `{"mantissa": m, "exponent": e}`: the decimal m × 10^e, with m a nonzero integer, `-2147483647 <= m <= 2147483647`, and `-4 <= e <= 6`. |
| `offset` | The same form; its mantissa may be zero. |
| `sensor_type`, `unit` | What a manifest channel reading this profile channel declares: fleet identifiers, never `controller_alarm_word` or `bitmask`. |

The decoded value is `raw × scale + offset`. A device never signs a bridged
measurement whose `value` is not the decode of some raw count in
`[raw_min, raw_max]`; a receiver holding a usable document for the reading's
channel, the one the manifest it was accepted under names, that receives one
reports the producer defect and does not use the reading. Let f be the smaller of the two
exponents. Each of `m_scale × 10^(e_scale − f)` and
`m_offset × 10^(e_offset − f)` is at most 999999999999999 in magnitude, and at
`raw_min` and at `raw_max` so are `raw × m_scale × 10^(e_scale − f)` and its sum
with the offset term, and the decoded value is at most 10^15 in magnitude. A channel
outside these bounds breaks the decode rule. Within them every decoded value is
exact in decimal, has at most fifteen significant digits, lies in v1's
canonical number zone, and is recovered exactly from the double nearest it.

A rule that depends on another field is judged only once that field is valid:
`word_order` against a `register_count` of `1` or `2`, the range against a
boolean `raw_signed`, a valid `register_count` and present bounds, the fields a
channel carries against a known `kind`, and a `bit` against a valid
`register_count`. A channel with no `kind` breaks the `kind` rule. The decode
rule is judged only once `raw_signed`, the range, `scale`, `offset` and
`register_count` are valid. A document whose
`register_count` is `3` breaks the `register_count` rule, not also the
`word_order` rule.

An `alarm_word` channel also carries exactly one more field, `alarms`: at least
one object, each with exactly these fields:

| Field | Rule |
| --- | --- |
| `bit` | `0` to `16 × register_count − 1`, counted from the least significant bit of the word value; unique in the channel. |
| `active` | `set` when the alarm is asserted by a 1 in that bit, `clear` when it is asserted by a 0. |
| `id` | A fleet identifier; unique in the profile. |
| `meaning` | The condition that holds while the alarm is asserted, as the controller's documentation states it: 1 to 256 printable ASCII characters, U+0020 to U+007E. An operator and a model read it, and nothing outside that range can hide, break or reorder what they read. |

The word value of an `alarm_word` channel is its registers as one unsigned
integer, combined in its `word_order`: for `high_first` the first register is
the high 16 bits. A manifest channel reading an `alarm_word` channel declares
`sensor_type` `controller_alarm_word` and `unit` `bitmask`, and its reading's
`value` is the word value, an integer in `0` to `2^(16 × register_count) − 1`,
which a consumer reads by value whether it is encoded as `5` or `5.0`. A
profile has no severity, threshold or action. Its scale, offset and range decide
the value any rule compares, so a profile is reviewed with the release that
ships it. Nothing in this section makes a bridged reading an input to a safety
condition. Whether one may be is not yet decided: safety-profile/v1 binds a
zone's channel without regard to its source or qualification.

The digest covers every field above, so it covers each channel's register
identity, width, word order, signedness, validity range, scale and offset,
and each alarm's bit, polarity, identifier and meaning.

### Receivers

A receiver interprets a bridged channel's reading only through a profile
document whose digest is the one named by the manifest the reading was
accepted under, which the reading's own `capability_hash` identifies, never by
whichever manifest is pinned when the reading is read again. It holds that
document locally, so that it can
interpret readings with no network. It never fetches a document from the device
whose reading it interprets, and never interprets through a document with
another digest, however close its `id`. Before using a document it checks that
the document is valid under the grammar above, that its `id` is the manifest's,
that it has the named `profile_channel`, and that the profile channel agrees
with the manifest channel: a `measurement` channel's `sensor_type` and `unit`
equal the manifest channel's, and an `alarm_word` channel's manifest channel
declares `controller_alarm_word` and `bitmask`; a document that
fails any of these is not used, and the receiver reports the disagreement
rather than interpreting.

Without a usable document, the profile is unknown to that receiver. It
presents the channel's readings as bridged values from an unknown profile and
an alarm word as its raw value, interprets no bit, and names no alarm.

For qualification:

- A receiver MUST NOT present a reading as qualified unless the manifest the
  reading was accepted under says `qualified` for its channel, and presents a reading whose channel says
  `unqualified` as unqualified wherever it describes it.
- Qualification is the device's attested statement that the reviewed release
  shipped a qualification record for the profile. It is not a permission, it
  is not proof that the foreign controller reports truthfully, and it is not
  physical proof of anything. It never changes a tier, an approval, a trust
  grade or any authority.

For an alarm word, read through a usable document:

- A reading is a snapshot of the controller's word at the poll it reports. A
  mapped alarm is asserted in that reading when its bit has the value its
  `active` names, and not asserted otherwise.
- A receiver presents an alarm's state as of the reading it was read from,
  never as the controller's state now. Not asserted means not asserted at that
  poll and nothing more: a receiver MUST NOT present it as proof that the alarm
  did not occur between polls, that it cleared at any particular time, or that
  it is clear now.
- How long ago a reading's poll was is not something a receiver can bound from
  this version. A device delivers buffered readings long after their polls, and
  the device's uptime and the receiver's clock run at rates this version does
  not relate, so a receiver never infers from accepting a reading recently, or
  from its `device_uptime_ms`, that the poll was recent.
- The channel's latest reading is the last reading for the channel the
  receiver accepted under the device's active anchor, with its active key epoch
  and active manifest. Any change to the active anchor, the promotion of a
  manifest, the promotion of a rotated key or a revocation, leaves the channel
  with no latest reading until the receiver accepts one under the new state.
  While no anchor is active there is none, and a reinstated anchor is active
  only once a promotion makes it so. Creating or replacing a pending anchor,
  for a new manifest or a re-provisioned key, changes nothing here: under
  [device-provisioning/v1](../device-provisioning/v1.md) a pending anchor
  affects nothing about the active one, so the channel's latest reading, any
  fault hold and the silence bound continue under the active anchor, and a
  reading signed under the pending anchor is refused. A message v1's freshness rules refuse,
  including a duplicate of one already accepted, is not accepted and changes
  nothing here.
- Every alarm on the channel is unknown while the channel has no latest
  reading, and while the receiver has accepted no reading for the channel
  within `3 × poll_interval_ms + 30000` milliseconds on a monotonic clock
  that keeps counting while the receiver's host is suspended: three missed
  polls and a transport allowance, which the profile grammar holds to an hour
  at most. A receiver MAY use a shorter bound and MUST NOT use a longer
  one. A receiver that restarts has accepted nothing, so every alarm is unknown
  until it accepts a reading after the restart.
- When the receiver accepts a `sensor_fault` naming the channel, every alarm on
  the channel is unknown until it accepts a later reading for the channel, or
  until the active anchor changes, which leaves no latest reading anyway. This orders the fault and the reading by when each was signed and
  locates nothing: under [Late Faults](#late-faults) a fault signed after a
  recovered reading reports an earlier condition, and the channel is then
  unknown until its next reading, which is expected.
- A receiver MUST NOT treat silence, a refused reading or a fault as an alarm
  clearing.
- An alarm-word reading is interpreted only from an envelope in which it is the
  only reading. One from an envelope carrying any other reading, a second
  reading of the same channel included, is not interpreted: two values under
  one label could be read two ways, and a reading refused beside it would leave
  conforming receivers with different latest readings.
- A receiver does not refuse an alarm-word reading because its `quality` is
  below its channel's `quality_floor`: quality describes a measurement. v1's
  grammar for `quality` still applies.
- A reading that is accepted and not interpreted, because it shares its
  envelope or because its `value` is not an integer in the word's range, is still the
  channel's latest reading, and every alarm on the channel is unknown while it
  is. A message that is not a reading of the channel, a heartbeat or another
  channel's reading, never becomes its latest reading and never restarts its
  bound.
- A bit no alarm maps is unknown: neither its meaning nor its polarity is
  known. A receiver may present the unmapped bits that are set, as set and
  unmapped, and MUST NOT name an unmapped bit, present it as an alarm, or
  present it as clear.

Whether or not a receiver holds the document:

- The word value of a `controller_alarm_word` channel is never a measurement:
  it is not averaged, compared with a numeric threshold or presented as a
  quantity.
- These rules bind every use of an alarm word, a rule's or a model's input as
  much as a display. A state presented as of a reading names that reading by
  its key epoch and its `(boot_id, seq)`; any time shown with it is named for
  where it came from, the receiver's acceptance time or the device's own
  report, and never as the time of the poll.

A foreign controller's alarm is evidence about that controller, read by the
device. It is not a fault of the device: it is never signed as a fault event,
never mapped onto the fault code vocabulary, and its absence from the fault
stream means nothing. An alarm's `id` or `meaning` confers no authority. A
receiver may reason about an alarm, and anything it then does is decided by its
own rules for that action's tier, approval and safety conditions, exactly as
for any other reading.

A separate signed event for individual alarm transitions is not defined here.
It would be a successor's, if equipment is shown to need transitions that
polling cannot capture.

## Adoption Order

The runtime adopts this version and
[firmware-commands/v2.md](../firmware-commands/v2.md) before any device signs a
`v` `2` fault. A runtime on v1 refuses every `v` `2` fault, and under
firmware-commands/v1 a command whose fault it refused is a command it must
treat as lost and retry, which is the late actuation the successor exists to
prevent.

Every other verifier adopts this version before the devices whose evidence it
reads. A producer on this version signs every new fault at `v` `2`, so a
verifier on v1 alone refuses all of that device's faults, `interlock_tripped`
included, from the moment the device adopts.

A device signs a bridged channel only once the consumers that read its evidence
implement [Controller Profiles](#controller-profiles). A consumer on v1, or on
this version before that section, refuses the manifest's unknown
`controller_profile` key, so a device that adopts first loses its registration
rather than having its bridged readings misread. A device whose release ships
controller profiles before its manifest can name them ships none: a reading
decoded through a profile the signed evidence cannot name has no provenance a
receiver can check.

In the other direction, a consumer that adopts this section refuses every
device that still signs a bridged channel without a profile, or declares
`controller_alarm_word` or `bitmask` outside a bridged alarm word, until that
device adopts it too.

## Golden Vectors

The authoritative corpus for this version's fault events is
[fault-vectors-v2.json](fault-vectors-v2.json), held here beside this
document. Its SHA-256 is
`7c54e32f65e02e9b58f7eb28a669977277863c81f2349b78970a69354b30bff0`.

Implementing repositories copy it byte for byte, pin that digest, and never
generate its expectations from their own behaviour.

It holds signed fault events at `v` `2` for every fault code and every token of
every closed set above, a `v` `1` fault a consumer of this version still
accepts, and refusals whose signatures verify: `rate_limited` at `v` `1`, a
token outside its code's set at `v` `2`, an empty closed-set `detail`, and
unsupported versions. Each refusal names its reason, and its signature is valid,
so a consumer that refuses it has refused it for that reason rather than at the
signature.

`scripts/generate-firmware-fault-vectors-v2` reproduces the file byte for byte.
`scripts/check-firmware-fault-vectors-v2` shares no code with it: it recomputes
canonical bytes, re-derives the key from the disclosed seed and verifies every
signature with its own curve arithmetic, reads the closed sets from this
document and [firmware-commands/v2.md](../firmware-commands/v2.md), and
confirms that each refusal is refused for its declared reason and for no
other.

The authoritative corpus for [Device Mode](#device-mode) is
[manifest-vectors-v2.json](manifest-vectors-v2.json), held beside it. Its
SHA-256 is
`fc1c630891422f52d1dc26aa7e9cda7a59534314130d6e6137018cff6c847eea`.
Implementing repositories copy and pin it the same way.

Each case is a signed manifest message whose manifest is otherwise valid under
v1, judged as the first manifest registered against the provisioning anchor
in its `verifier_context`. It holds `sensor_node`, `bridge_node`, and `mixed`
over each combination of metering channels, bridged channels and actions, and
refusals whose signatures verify: a `device_mode` outside the four values, as
an unknown string, a variant in letter case and values of other JSON types;
each mode over arrays that determine another; and `actuator_node` with an
action and no channel, refused only as `no_channels`. It covers these rules
and none of v1's other manifest validation.

`scripts/generate-firmware-manifest-vectors-v2` reproduces the file byte for
byte. `scripts/check-firmware-manifest-vectors-v2` shares no code with it: it
recomputes canonical bytes and the manifest hash with its own serializer,
verifies every signature with its own curve arithmetic, reads the mode table
and the bridged source from this document, derives each manifest's mode from
its arrays, and confirms that each case is accepted and each refusal is
refused for its declared reason and for no other.

The manifest corpus also covers [Controller Profiles](#controller-profiles):
bridged channels naming a profile qualified and unqualified, an alarm-word
channel, two channels reading one profile, and refusals whose signatures
verify for a bridged channel with no profile, a profile on a metering channel,
each way a `controller_profile` breaks its grammar, one profile `id` under two
digests, two qualifications or two records, one digest under two ids, a
bridged channel on another protocol, and each
misuse of `controller_alarm_word` and `bitmask`.
Each `digest` an accepted case names is the digest of a document in the
profile corpus, whose `id`, `profile_channel` and channel kind, `sensor_type`
and `unit` agree with the case.

The authoritative corpus for the profile document is
[controller-profile-vectors-v2.json](controller-profile-vectors-v2.json), held
beside them. Its SHA-256 is
`3504e144432b3c8f05f66850c60d974ed44588f175702a0a2f2162dbaa6ea6d3`.
Implementing repositories copy and pin it the same way. It holds valid
documents with their canonical bytes and digests, covering both kinds, both
widths, both word orders, signed and unsigned ranges, negative offsets and
both polarities; documents each breaking exactly one rule of the grammar,
including numbers of the wrong JSON type and each way a decode leaves fifteen
digits or 10^15; byte strings refused as not canonical, each but one of which
re-serializes to a pinned digest, among them a duplicate key whose two values
give opposite polarities; and interpretation cases, each an alarm-word `value`
read through the document of the manifest it was accepted under, with the
registers it combines from and the document pinned when it is read again,
which in some cases is another document of the same `id`, giving every
mapped alarm as asserted or not asserted and the unmapped bits that are set,
or the value as not interpreted; range cases, each a measurement `value` read
through a document, giving whether it lies within the decode of the channel's
range; agreement cases, each a manifest channel and
a document, giving whether the receiver may use the document for that channel;
and state cases, each a sequence of readings,
uninterpretable readings, other messages, faults, pending anchors for a new
manifest or a re-provisioned key and readings signed under them, promotions of
rotated keys, manifest promotions, revocations, reinstatements and receiver restarts on one channel,
each sequence legal under
[device-provisioning/v1](../device-provisioning/v1.md), with the receiver
time each was accepted, giving the channel's alarms at a query time as unknown
or as of a named reading, covering the silence bound at the alarm-word poll ceiling,
faults, key rotation with restarted counters, a superseded epoch, manifest
promotion, receiver restart, a drained backlog, a reboot, and refused replays,
duplicates and boot rollbacks.

`scripts/generate-firmware-controller-profile-vectors-v2` reproduces it byte
for byte. `scripts/check-firmware-controller-profile-vectors-v2` shares no code
with it: it reads the grammar's bounds and closed sets from this document,
recomputes canonical bytes and digests with its own serializer, confirms that
each refused document breaks exactly the rule it declares, refuses each byte
string on its bytes, combines each case's registers in its word order,
recomputes every interpretation, range case and agreement case, and recomputes
every state case from the rules in [Receivers](#receivers).

The disclosed test seed, shared by both signed corpora, is a fixture only and MUST
NOT be provisioned on any device.

## Required Implementation Artifacts

In addition to v1's:

- consumer tests driving the corpus through the consumer's real verification
  entry point, accepting every case and refusing every refusal for its declared
  reason;
- consumer tests driving the corpora of
  [ed25519-key-admission/v1](../ed25519-key-admission/v1.md) and
  [ed25519-verification/v1](../ed25519-verification/v1.md) through the
  verifier the consumer uses for this version's signatures, accepting every
  accepted case and refusing every refused one;
- a producer test that the device signs the `rate_limited` refusal of
  [firmware-commands/v2.md](../firmware-commands/v2.md) at `v` `2`, and that no
  fault is signed at `v` `1` once the producer implements this version;
- a producer test that each retry of a late fault carries the freshness fields
  of its own signing, not those of the condition or of an earlier attempt;
- a producer test, at each public boundary that builds a manifest, that it
  signs the `device_mode` its `channels` and `actions` determine for every
  combination it can declare, reproducing the mode of each accepted case of
  the manifest corpus from that case's arrays, and refuses to build a manifest
  with no channel or with any other mode;
- a producer test that, for every profile in the device's release, the bytes
  it hashes for `digest` are the canonical bytes of the profile's document
  under the grammar above, reproducing the canonical bytes and digest of each
  accepted document of the profile corpus from an equivalent profile;
- a producer test that the device combines an alarm word's registers in its
  declared word order, reproducing each interpretation case's `value` from its
  `registers`;
- consumer tests driving the profile corpus's range cases through the
  receiver's check of a bridged measurement against its channel's range;
- consumer tests driving the profile corpus's agreement cases through the
  receiver's check of a document against a manifest channel, using each
  agreeing document and refusing each disagreeing one;
- consumer tests that an alarm-word reading sharing its envelope with any other
  reading is accepted, is not interpreted and becomes the channel's latest
  reading, and that one below its channel's `quality_floor` is not refused;
- a producer test that the device signs each alarm-word reading alone in its
  envelope;
- consumer tests that a receiver refuses each byte string of the profile
  corpus's `reject_bytes`, and hashes the bytes it holds rather than a
  re-serialization;

  channel and on no other, with `qualification` and `record` as its release
  states them;
- consumer tests driving the profile corpus through the consumer's document
  validation, alarm interpretation and alarm state, accepting and refusing every
  document as the corpus declares and reproducing every interpretation and
  every state case; the state cases are stated at the longest bound, and a
  consumer using a shorter one expects unknown in every case whose query falls
  later than its bound after the last accepted reading;
- consumer tests driving the manifest corpus through the consumer's real
  registration path, accepting every case and refusing every refusal for its
  declared reason.
