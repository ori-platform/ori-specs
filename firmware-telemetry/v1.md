# Firmware Telemetry Contract v1

> Status: Contract target. No implementation is claimed in `ori-edge-firmware`,
> `ori-runtime`, the private evidence-store implementation, or `ori-gateway` until those repositories cite
> this contract from a tagged release.

This contract defines evidence Layer 1: device-origin attestation for telemetry
measured at the physical edge before it reaches the Ori runtime. Layer 1 closes
the sensor-to-runtime provenance gap; evidence Layer 2 (`evidence/v1.md`) remains
the runtime action evidence chain.

The firmware can run as a sensor node, wire-level bridge node, or actuator node.
Those are firmware personalities, not separate protocols. IP-reachable foreign
devices may be handled by `ori-gateway`; wire-level devices use firmware bridge
mode.

## Trust Model

- Each firmware node owns one Ed25519 device keypair.
- The private key is generated on-device at first provisioning and must never
  leave the device.
- Production devices must use Secure Boot v2, flash encryption, and eFuse-backed
  key protection where the board supports it.
- The public key becomes the provisioning-time verification anchor for
  `device_id`.
- `device_id` is a fleet identifier drawn from `[A-Za-z0-9._-]`, at most 48
  characters. The alphabet is simultaneously MQTT-topic-safe and
  JSON-literal-safe, so a provisioning identity can never inject into topic
  paths or unsigned transport payloads.
- Telemetry envelopes are signed at measurement time; runtimes and gateways
  verify signatures before treating readings as device-origin attestations.
- A valid Layer 1 signature proves origin and envelope integrity. It does not
  by itself prove chain completeness, correct sensor calibration, or physical
  wiring safety.

## Relationship To Evidence Layer 2

Layer 1 signs measurements and capability manifests from firmware nodes.
Layer 2 signs runtime Tier C/D action evidence.

The runtime may carry verified Layer 1 metadata into `SensorReading.metadata`
and later into Layer 2 action evidence payloads, but Layer 1 telemetry rows are
not `SAFETY_ACTION_EXECUTED` events. Firmware must not claim Tier D ownership;
local interlocks are defense-in-depth and remain outside the SIL-1 Tier D
safety-function scope unless a future safety case explicitly changes that.

## Signature Encoding

All signatures use the shared Ori signature-field encoding:

```text
ed25519:<base64-64-byte-signature>
```

Rules:

- Prefix is exactly `ed25519:`.
- Signature bytes use standard base64, not base64url.
- Decoded signature length must be 64 bytes.
- Ed25519 public keys are raw 32-byte public keys encoded with standard base64.
- Invalid format, invalid length, unknown key, or failed verification must fail
  closed.

## Canonical JSON

Signed bytes are canonical UTF-8 JSON bytes of the unsigned object:

- object keys sorted lexicographically at every nesting level,
- arrays preserved in caller-provided order,
- no whitespace outside string values,
- JSON strings escaped according to RFC 8259,
- integers and finite JSON numbers only,
- `NaN`, `Infinity`, and `-Infinity` are forbidden,
- signature fields are excluded from signed bytes.

Number serialization is constrained to the range where the C, Rust
(`serde_json`), and Python (CPython `json`) serializers provably produce
identical bytes:

- integers must satisfy `|n| <= 9007199254740991` (2^53 - 1),
- non-integer numbers must be finite and either exactly zero or have
  magnitude in `[1e-4, 1e16)`,
- non-integer numbers are serialized as the shortest round-trip decimal in
  fixed notation with a mandatory fractional part (`8.0` serializes as
  `"8.0"`, never `"8"`; `-0.0` is preserved),
- exponent notation never appears in canonical bytes,
- values outside this zone must be rejected fail-closed by producers and
  treated as invalid by consumers.

This zone is where CPython and `serde_json` notation agrees; outside it they
diverge (`1e-05` vs `0.00001`, `1.5e-07` vs `1.5e-7`), which would silently
break byte-identical signatures across verifier languages.

Golden vectors are mandatory before implementation work begins.

## Capability Manifest

> The lifecycle of the anchor a manifest establishes — registration,
> pending versus active state, key rotation, revocation, and epoch
> identity — is normative in
> [device-provisioning/v1.md](../device-provisioning/v1.md). A receiver
> implementing this contract MUST implement that lifecycle: verifying a
> manifest establishes what it says, not that it may replace a stored
> anchor.

A firmware node must publish a capability manifest before telemetry is accepted.
The manifest binds firmware identity, board profile, secure posture, channels,
and actions into a stable hash.

Signed manifest message:

```json
{
  "manifest": {
    "v": 1,
    "alg": "ed25519",
    "device_id": "ori-fw-7c9f2b3a",
    "firmware_version": "0.1.0",
    "board_profile": "esp32s3-poe-8di8do",
    "device_mode": "sensor_node|bridge_node|actuator_node|mixed",
    "public_key_b64": "base64-32-byte-ed25519-public-key",
    "posture": "development|sealed_flash|hardware_key",
    "secure_boot_enabled": true,
    "flash_encryption_enabled": true,
    "key_storage": "efuse_derived|nvs_encrypted|hardware_key|dev_flash",
    "transports": ["mqtt", "uart", "rs485"],
    "channels": [
      {
        "channel": "ch0",
        "sensor_type": "current",
        "unit": "ampere",
        "protocol": "adc|gpio|i2c|uart|modbus_rtu|rs232|pulse|one_wire",
        "source": "pzem|ads1115|dry_contact|foreign_device",
        "quality_floor": 0.8
      }
    ],
    "actions": [
      {
        "action": "relay_open",
        "channel": "relay0",
        "authority": "local_interlock_only|runtime_commanded"
      }
    ],
    "interlocks": [
      {
        "name": "local_overcurrent_interlock",
        "channel": "ch0",
        "action": "relay_open"
      }
    ]
  },
  "manifest_hash": "sha256:<64-lowercase-hex>",
  "signature": "ed25519:<base64-64-byte-signature>"
}
```

`manifest_hash` is SHA-256 over the canonical JSON bytes of `manifest`, encoded
as lowercase hex with prefix `sha256:`. `signature` is over the same canonical
manifest bytes. `hardware_key` is reserved for boards whose private key is
held in a dedicated hardware security element; ESP32 flash encryption alone is
not hardware isolation. The phrase `hardware-isolated` may describe only the
`hardware_key` posture, never `sealed_flash`.

### Trust Grades

Consumers may derive a local trust grade after verification:

| Grade | Meaning |
|---|---|
| `attested` | Signature valid, sequence fresh, and posture is `sealed_flash` or `hardware_key`. |
| `attested_dev` | Signature valid and sequence fresh, but posture is `development`. |
| `unattested` | No device signature was supplied; acceptable only where the deployment explicitly allows weak evidence. |
| `rejected` | Signature, anchor, manifest, posture, freshness, or value validation failed. |

A trust grade is receiver-derived metadata. It is not signed by firmware and must
not be confused with the signed `posture` field.

### Manifest Validation

Consumers must reject a manifest when:

- `device_id` does not match the provisioning record,
- `public_key_b64` does not match the provisioning anchor,
- `manifest_hash` does not equal SHA-256 over canonical `manifest`,
- `signature` does not verify against `public_key_b64`,
- `alg` is not `ed25519`,
- `posture` claims production security but the boolean posture fields disagree,
- any channel has unsupported `sensor_type`, `unit`, or `protocol`,
- any action attempts to claim Tier C/D authority.

## Signed Telemetry Envelope

Telemetry is transported as a signed message containing an unsigned envelope and
an adjacent signature.

```json
{
  "envelope": {
    "v": 1,
    "alg": "ed25519",
    "device_id": "ori-fw-7c9f2b3a",
    "boot_id": 41,
    "seq": 130482,
    "capability_hash": "sha256:<64-lowercase-hex>",
    "posture": "sealed_flash",
    "device_uptime_ms": 918233,
    "emitted_at_ms": null,
    "readings": [
      {
        "channel": "ch0",
        "sensor_type": "current",
        "unit": "ampere",
        "value": 8.21,
        "quality": 1.0
      }
    ]
  },
  "signature": "ed25519:<base64-64-byte-signature>"
}
```

`signature` is computed over canonical JSON bytes of `envelope` only.

### Envelope Fields

| Field | Type | Notes |
|---|---|---|
| `v` | `int` | Contract version. Must be `1`. |
| `alg` | `string` | Signature algorithm. Must be `ed25519` in v1. |
| `device_id` | `string` | Firmware node id bound at provisioning. |
| `boot_id` | `int` | Monotonic boot counter. Must not decrease for a device. |
| `seq` | `int` | Monotonic envelope sequence within a device key epoch. |
| `capability_hash` | `string` | `sha256:<hex>` of the accepted capability manifest. |
| `posture` | `string` | Security posture claimed by the current boot. |
| `device_uptime_ms` | `int` | Monotonic uptime from boot. |
| `emitted_at_ms` | `int|null` | Optional device wall-clock timestamp. `null` when no trusted clock exists. |
| `readings` | `array` | Reading objects. May be empty only for signed heartbeat/liveness envelopes (see Heartbeat Envelopes). |

### Reading Fields

| Field | Type | Notes |
|---|---|---|
| `channel` | `string` | Stable channel id from the accepted capability manifest. |
| `sensor_type` | `string` | Runtime-compatible sensor type. |
| `unit` | `string` | Runtime-compatible unit. |
| `value` | `number` | Finite numeric value only. |
| `quality` | `number` | `0.0 <= quality <= 1.0`. Consumers may reject below manifest floor. |

Additional reading fields are forbidden in v1. If a device needs extra context,
it must add a new manifest channel or wait for a contract version bump.

### Heartbeat Envelopes

A telemetry envelope with `readings: []` is a signed heartbeat/liveness
envelope. It exists so a node that is alive, sealed, and provisioned can prove
liveness without pretending to measure: sensor warm-up, a temporary bus fault,
a calibration window, a relay-only actuator node, or a bridge waiting on its
foreign device are all normal states with no sample available. Forcing at
least one reading into every envelope would incentivize fabricated or stale
readings — worse evidence than an honest empty array.

Heartbeat envelopes:

- are signed and carry `boot_id`, `seq`, `device_uptime_ms`, `posture`, and
  `capability_hash` exactly like any other envelope,
- consume `seq` and advance the receiver's freshness high-water mark,
- prove device liveness, key posture, freshness, and manifest binding,
- must not be converted into runtime `SensorReading` objects or gateway
  telemetry records,
- must not trigger skills, rules, actions, or any tier authority.

## Sequence And Freshness

> The key epoch this section scopes replay state to is identified by
> `key_epoch_id` in
> [device-provisioning/v1.md](../device-provisioning/v1.md), which also
> requires that a manifest-only change MUST NOT reset freshness.

Receivers must maintain replay state per `device_id` and public-key epoch.

- `seq` is assigned from an NVS reservation ceiling, not from a write-after-send
  counter. A device reserves a ceiling, emits up to that ceiling, and advances
  the ceiling before it can reuse the range after reboot.
- `seq` must increase for accepted telemetry. A message with `seq` less than or
  equal to the receiver's high-water mark for the same key epoch is a replay and
  must be rejected or treated as a duplicate of an already-accepted envelope.
- `boot_id` must not decrease. A lower `boot_id` is a rollback/tamper signal.
- `device_uptime_ms` may reset only when `boot_id` increases.
- `emitted_at_ms` is advisory unless the device has a trusted wall clock. It
  must never be the only freshness mechanism.

## Provisioning Anchor

Provisioning records must store at least:

```json
{
  "device_id": "ori-fw-7c9f2b3a",
  "public_key_b64": "base64-32-byte-ed25519-public-key",
  "initial_manifest_hash": "sha256:<64-lowercase-hex>",
  "posture": "development|sealed_flash|hardware_key",
  "provisioned_at_ms": 0
}
```

The first production provisioning flow must persist this anchor off-device
before accepting telemetry as Layer 1 evidence. A self-signed manifest
without an off-device anchor is useful for diagnostics only.

## Consumer Verification Flow

Consumers must verify in this order:

1. Load the provisioning anchor for `device_id`.
2. Verify the latest accepted capability manifest against the anchor.
3. Reject telemetry whose `alg` is not `ed25519`.
4. Reject telemetry whose `capability_hash` does not match the accepted
   manifest hash.
5. Canonicalize `envelope` and verify `signature` against the anchored public
   key.
6. Validate `boot_id`, `seq`, `device_uptime_ms`, posture, channel names,
   sensor types, units, values, and quality bounds.
7. Derive a trust grade.
8. Only after those checks, convert readings into runtime `SensorReading`
   objects or gateway telemetry records.

A failed verification must not be converted into a normal sensor reading.

## Local Interlock Boundary

Firmware may implement local hardware interlocks for orphaned-device protection.
Those interlocks are not Tier D in this contract. They must be represented as
capabilities with `authority: local_interlock_only` and must not be advertised
as runtime action authority.

The authoritative Tier D safety function lives in the runtime safety kernel
roadmap and is specified separately. Firmware interlock events may be logged or
reported as Layer 1 telemetry, but they do not become Layer 2
`SAFETY_ACTION_EXECUTED` rows unless the runtime dispatches and attests an
action under `evidence/v1.md`.

## MQTT Transport Binding

Firmware nodes speaking MQTT publish under `ori/fw/<device_id>/`:

| Topic | QoS | Retained | Payload |
|---|---|---|---|
| `ori/fw/<device_id>/manifest` | 1 | yes | The signed capability-manifest message, re-published on every connect so late subscribers always hold the current manifest. |
| `ori/fw/<device_id>/telemetry` | 1 | no | Signed telemetry messages, heartbeats included. Signed fault-event messages are published on this topic too. |
| `ori/fw/<device_id>/status` | 1 | yes | **Unsigned** connection status. The firmware publishes `online` on connect and registers the broker last-will as `offline` on the same topic. |

The status payload is transport metadata, never evidence:

```json
{"boot_id":41,"device_id":"ori-fw-7c9f2b3a","online":true,"signed":false}
```

A last-will payload is composed before the failure it reports and is published
by the broker, not the device — signing it would manufacture attestation for
an event the device never observed, and a pre-signed will's stale `seq` would
race live telemetry. Receivers must treat status as an unattested liveness
hint; signed heartbeat envelopes remain the only liveness evidence.

QoS 1 throughout: duplicates are already handled by the sequence-and-freshness
contract; exactly-once broker state buys nothing. Consumers subscribe with
`ori/fw/+/telemetry` (and `+/manifest`, `+/status`) per site.

## Signed Fault Events

A fault event is device-signed evidence about the device's own conduct: what
it refused, what it protected against, and where it could not keep a guarantee
it is supposed to keep. A rejected command, corrupt sensor input suspending a
local interlock, an interlock trip, a brownout-path failure, a sensor that
stopped answering, evidence the device could not make durable. The common
property is that the device is reporting on itself, not on the world it
measures. It shares the telemetry envelope's identity and freshness fields,
consumes `seq` from the same counter (one monotonic stream per key epoch — one
replay state), and follows the same canonical JSON and signature rules.

```json
{
  "fault": {
    "v": 1,
    "alg": "ed25519",
    "device_id": "ori-fw-7c9f2b3a",
    "boot_id": 41,
    "seq": 130485,
    "capability_hash": "sha256:<64-lowercase-hex>",
    "posture": "sealed_flash",
    "device_uptime_ms": 925000,
    "code": "command_rejected",
    "subject": "relay0",
    "detail": "replayed"
  },
  "signature": "ed25519:<base64-64-byte-signature>"
}
```

### Fault Fields

| Field | Type | Notes |
|---|---|---|
| `v`, `alg`, `device_id`, `boot_id`, `seq`, `capability_hash`, `posture`, `device_uptime_ms` | — | Identical semantics to the telemetry envelope. |
| `code` | `string` | One of the fault codes below. Closed vocabulary; additions are additive contract changes. |
| `subject` | `string` | The channel, rule, or action the fault concerns, from the fleet identifier alphabet. May be empty when no subject applies. At most 63 characters. |
| `detail` | `string` | A short machine-readable token qualifying the code (for `command_rejected`, the command verdict exactly as named in `firmware-commands/v1.md`; for interlock faults, the rule name). May be empty. At most 63 characters. |

`subject` and `detail` are bounded at **63 characters** and restricted to the
fleet identifier alphabet (`A-Z`, `a-z`, `0-9`, `.`, `_`, `-`). The bound is
normative on both sides: producers cannot emit a longer token, and consumers
MUST reject a fault carrying one even when its signature verifies. A valid
signature over an unrepresentable shape means the two implementations disagree
about the contract, which is exactly what the shared fault vectors exist to
prevent.

### Fault Codes

| Code | Meaning |
|---|---|
| `command_rejected` | An inbound command failed verification; `detail` carries the command error code (see `firmware-commands/v1.md`). |
| `interlock_input_fault` | Corrupt input (NaN/Inf/out-of-range) suspended a local interlock rule. Reported once per suspension. |
| `interlock_recovered` | Valid input resumed a suspended interlock rule. |
| `interlock_tripped` | A local interlock rule tripped and its relay action was applied. Remains defense-in-depth reporting, not Tier C/D action evidence. |
| `sensor_fault` | A sensor or bridge transaction failed persistently. |
| `brownout_relay_fault` | The brownout sequence could not drive the relays to rest (recovered from the platform's non-flash sink on the next boot). |
| `ingress_degraded` | The inbound ingress path lost or could not accept messages. `detail` carries the condition: `inbound_overflow` (a delivered message was dropped before verification), `subscribe_failed` (an inbound topic subscription did not complete), or `anchor_persist_failed` (a verified approval could not be persisted; command authority is active this boot but will not survive reboot). |
| `storage_degraded` | The device could not make signed evidence durable. `detail` carries the condition: `buffer_write_failed` (an append to the offline evidence buffer failed and the affected signed messages are lost) or `buffer_mount_failed` (the offline evidence buffer could not be mounted, so nothing can be buffered this boot). `subject` names the affected store, e.g. `evidence_buffer`. Reported late — see below. |

Consumers verify fault events exactly like telemetry (anchor, manifest pin,
signature, freshness) and record them with the same trust grades. A fault
event must never be converted into a `SensorReading` and must never trigger
actions; it is evidence about the device's own conduct — what it refused, what
it protected, and where it could not keep its own guarantees.

### `storage_degraded` Is Late and Incomplete by Construction

> Status: Open Gap. The code and its semantics are defined here; no producer
> emits it and no consumer requires it yet. See `gaps/open.md`.

This code reports a failure of the mechanism that carries evidence, so it
cannot obey the timing rules the other codes follow. Three properties are
normative.

**It is emitted late.** A device signs a fault and appends it to the same
offline buffer whose failure it would be reporting, so a report emitted at the
moment of failure is destroyed by the condition causing it. Producers MUST
therefore emit `storage_degraded` once storage recovers, or on a subsequent
boot, from a latch held outside the failed store. This mirrors
`brownout_relay_fault`, which is likewise recovered from a non-flash sink on
the next boot.

**The latch clears only on durable success.** This is the rule the whole
mechanism turns on, and getting it wrong reproduces the loss it exists to
prevent. A producer MUST retain the latch when signing, appending, or mounting
fails, and MUST clear it only once the `storage_degraded` event has itself been
durably stored. Clearing on an emission *attempt* means a report lost to the
same failing storage silently closes the outage, which is the original defect
wearing a fault code. While a report is owed, further durability failures MUST
be coalesced into it rather than opening new ones, and retries MUST be bounded
so a device that cannot store anything does not spend its sequence space
trying. A latch that survives reboot MUST be retried on the next boot.

**Its own freshness fields do not locate the loss.** Because the event is
late, and may be emitted in a later boot than the failure, its `boot_id`,
`seq`, and `device_uptime_ms` describe the moment of *reporting*, not the
moment of loss. Consumers MUST NOT infer the affected range from them. The
event asserts *that* a durability failure occurred on this device; it does not
assert when, or how much was lost.

**Its absence is not evidence of health.** A device whose storage is failing
badly enough may never emit it at all. Consumers MUST NOT treat the absence of
`storage_degraded` as proof that no evidence was lost.

Note that a receiver cannot derive this condition from freshness alone.
Because `seq` is assigned from a reservation ceiling, a reboot legitimately
skips a range, so gaps in `(boot_id, seq)` are expected and MUST NOT by
themselves be treated as evidence loss. That is precisely why this code
exists: it carries a fact the sequence stream cannot express.

A device reporting `storage_degraded` has told the truth about its own
limits, which is the behaviour Layer 1 exists to make possible. Consumers
SHOULD treat it as a durability warning about the device rather than as a
defect in the evidence already accepted from it: messages that did arrive
remain individually verifiable and are unaffected.

## Error Semantics

Recommended error codes:

| Condition | Error |
|---|---|
| unknown device id | `unknown_device` |
| no provisioning anchor | `anchor_missing` |
| malformed signature | `invalid_signature_format` |
| public key mismatch | `public_key_mismatch` |
| signature failed | `signature_verification_failed` |
| manifest hash mismatch | `capability_hash_mismatch` |
| stale or replayed sequence | `sequence_replay` |
| boot counter rollback | `boot_rollback` |
| unsupported channel | `unsupported_channel` |
| unsupported posture claim | `invalid_posture` |
| invalid reading value | `invalid_reading` |

Verification failures must be auditable. They must not be silently downgraded to
low-quality readings.

## Required Implementation Artifacts

Before any implementation is considered complete, the responsible repos must
provide:

- canonical JSON golden vectors for manifest and telemetry signing,
- signature verification tests against the golden vectors,
- replay/rollback tests for `seq` and `boot_id`,
- manifest hash mismatch tests,
- explicit tests that firmware does not claim Tier D authority,
- documentation of board-specific secure boot, flash encryption, and key
  storage posture.
