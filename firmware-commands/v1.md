# Firmware Commands Contract v1

> Status: Contract target. No implementation is claimed until the
> implementing repositories cite this contract from a tagged release.

This contract defines authenticated inbound commands: the runtime instructing
a firmware node to perform a physical action. A replayed "open relay" command
is an attack; every rule here exists to make replay, redirection, and
forgery structurally impossible rather than merely detected.

## Trust Model

- The runtime owns a command signing keypair (Ed25519). Its public key is
  registered on the device at provisioning, alongside the device's own
  identity; it is the only key commands verify against.
- The device accepts a command only when ALL of the following hold, in this
  order: the message parses under the fixed grammar below; the command's
  `device_id` equals the device's own id; the signature verifies over the
  exact command-object bytes against the provisioned runtime key; `cmd_seq`
  strictly exceeds the device's persisted command high-water mark; the
  command's `capability_hash` equals the device's accepted manifest hash;
  and the `(action, channel)` pair appears in that manifest with
  `runtime_commanded` authority.
- **A signed, device-bound, fresh command is spent the moment it is seen.**
  Once grammar, device binding, signature, and freshness pass, the
  high-water mark is persisted — even when the capability hash or authority
  check then rejects the command. A rejected intent must never remain
  bankable against a future manifest change: without consumption, a command
  refused today as `unknown_action` could be replayed successfully after an
  operator adds that action to the manifest.
- Commands additionally bind the manifest epoch: `capability_hash` inside
  the signed object ties the instruction to the capability set the runtime
  believed accepted. After capability drift and re-approval, previously
  signed commands are dead by construction — the runtime must re-sign
  against the new hash.
- The high-water mark is persisted **before** actuation. A crash between
  persist and actuate loses the command — the runtime retries with a fresh
  `cmd_seq` — and never leaves one replayable. Commands are operator-rate,
  so write-through persistence applies (unlike telemetry counters).
- Freshness is the counter alone. Commands carry no expiry timestamps: an
  offline device has no trustworthy clock, and a counter is the only
  freshness it can enforce.

## Wire Format

One fixed grammar, byte for byte. Because only this canonical form is
accepted, the signed bytes and the parsed meaning cannot diverge, and no
parser-differential surface exists (no whitespace, duplicate keys, extra
fields, or alternative orderings):

```json
{"command":{"action":"relay_open","capability_hash":"sha256:<64-lowercase-hex>","channel":"relay0","cmd_seq":42,"device_id":"ori-fw-7c9f2b3a","v":1},"signature":"ed25519:<base64-64-byte-signature>"}
```

Rules:

- Field order is exactly as shown: `action`, `capability_hash`, `channel`,
  `cmd_seq`, `device_id`, `v` — the lexicographic canonical order.
- `capability_hash` is `sha256:` plus exactly 64 lowercase hex characters —
  the hash of the capability manifest the runtime believes accepted.
- `action`, `channel`, and `device_id` are fleet identifiers:
  `[A-Za-z0-9._-]`, non-empty, within the receiver's declared length limits.
- `cmd_seq` is a canonical decimal integer (no leading zeros, no sign) within
  `1 .. 2^53 - 1`.
- `v` must be `1`.
- The signature is computed over the canonical bytes of the `command` object
  exactly as transmitted, in the shared `ed25519:<base64>` wire encoding
  (standard base64, 64-byte signature, canonical padding).
- Any deviation — whitespace, reordered or extra fields, non-canonical
  integers, out-of-alphabet identifiers, a malformed signature field — is
  `malformed` and must be rejected before signature verification is
  attempted.

## Action Vocabulary

The v1 action vocabulary is `relay_open` and `relay_close`. The strings are
part of signed payloads (manifests and commands): changing one is a wire
contract change, not a rename. Additions are additive contract changes and
must appear in the capability manifest's action list before any device
accepts them.

## Error Semantics

Rejections are auditable verdicts; the device surfaces them as signed fault
events (`firmware-telemetry/v1.md`, code `command_rejected`) with the verdict
in `detail`:

| Verdict | Meaning |
|---|---|
| `malformed` | The message violates the fixed grammar. |
| `wrong_device` | `device_id` names another device. A command signed for one device must never actuate another. |
| `bad_signature` | Signature verification against the provisioned runtime key failed. |
| `replayed` | `cmd_seq` does not strictly exceed the persisted high-water mark. |
| `capability_mismatch` | The command's `capability_hash` does not equal the device's accepted manifest hash. Consumes the sequence. |
| `unknown_action` | The `(action, channel)` pair is not in the accepted manifest with `runtime_commanded` authority. Consumes the sequence. |
| `storage_failure` | The high-water mark could not be read or persisted; nothing was actuated and nothing was consumed. |

Gaps in `cmd_seq` are valid (the mark is a high-water mark, not a sequence);
regressions and repeats are replays. A rejected command actuates nothing;
verdicts after the freshness check (`capability_mismatch`, `unknown_action`)
consume the sequence so the rejected instruction can never be replayed, while
verdicts before it (`malformed`, `wrong_device`, `bad_signature`,
`replayed`) persist nothing.

## MQTT Transport Binding

Inbound messages travel under the same per-device prefix as
`firmware-telemetry/v1.md` outbound topics. The device subscribes only to
its own topics — never a wildcard:

| Topic | QoS | Retained | Payload |
|---|---|---|---|
| `ori/fw/<device_id>/cmd` | 1 | no | One signed command message per publish, in the wire format above. Never retained: a retained command would be redelivered on every subscribe, and although the high-water mark makes redelivery harmless, a broker must not hold standing instructions to actuate. |
| `ori/fw/<device_id>/provision` | 1 | yes | The current signed provisioning approval (below). Retained like the manifest, so a device that reconnects or reboots receives the standing approval without waiting for a fresh publish. Key rotation replaces the retained message. |
| `ori/fw/<device_id>/runtime` | 1 | **no** | One signed runtime-liveness message (below). **Never retained.** A retained liveness message is the broker asserting, on behalf of a runtime that may since have died, that an authority is watching — the precise claim this signal exists to make unforgeable. |

Topic identity is transport routing only. A message's meaning comes from its
signed payload: a command arriving on the provisioning topic (or vice versa)
fails its verifier's grammar and is rejected, never re-routed. The device
processes only complete single-publish messages; a payload exceeding the
device's declared inbound limit is dropped at the transport layer and is not
a `malformed` verdict, because it was never presented to the verifier.

Ingress loss is never silent. If the device drops a delivered inbound
message before verification (ingress queue exhaustion), or an inbound topic
subscription fails to complete, it emits a signed `ingress_degraded` fault
(`firmware-telemetry/v1.md`) with the condition in `detail`. A command that
produced neither a relay action nor a `command_rejected` fault must be
treated by the runtime as lost and retried with a fresh `cmd_seq` — the same
rule as a device crash between persist and actuate.

The retained provisioning approval authorizes the runtime command key only.
It does not authorize MQTT certificate installation, rotation, revocation, or
broker trust-root changes. Those operations use the separate signed contract in
[firmware-mqtt-provisioning/v1.md](../firmware-mqtt-provisioning/v1.md) and
MUST NOT be carried as retained approval messages.

## Provisioning Approval

> When an approval may be issued and published — including that it MUST
> NOT be published before the evidence store has accepted the same
> `anchor_epoch_id`, and that command-key rotation MUST NOT reset
> `cmd_seq` — is normative in
> [device-provisioning/v1.md](../device-provisioning/v1.md).

Registration of the runtime command key is itself a signed operation. A
provisioning authority keypair (Ed25519), whose public key is built into the
device at flash time, signs an approval binding the runtime command key to
one device and one manifest epoch:

```json
{"approval":{"capability_hash":"sha256:<64-lowercase-hex>","device_id":"ori-fw-7c9f2b3a","posture":"development","public_key_b64":"<base64-device-key>","runtime_public_key_b64":"<base64-runtime-command-key>","v":1},"signature":"ed25519:<base64-64-byte-signature>"}
```

- The grammar discipline of commands applies: fixed field order (the
  lexicographic canonical order shown), canonical JSON, any deviation
  rejected before signature verification.
- The device accepts an approval only when the signature verifies against
  the built-in provisioning authority key AND `device_id`,
  `public_key_b64`, `posture`, and `capability_hash` all match the device's
  own identity and current manifest. An approval for another device, another
  key, or a stale manifest epoch registers nothing.
- Approvals are idempotent: re-applying the current approval changes
  nothing. They carry no freshness counter because acceptance is bound to
  the manifest epoch — after capability drift, only an approval naming the
  new hash can register a key, and the old retained approval dies by
  construction.
- A device with no verified approval holds no runtime command key and
  refuses every command (`bad_signature`); commands fail closed, telemetry
  is unaffected.
- The device persists the verified anchor (runtime public key + approved
  manifest hash) locally and reloads it at boot only while the stored hash
  still equals its current manifest hash. The command high-water mark is
  independent of this anchor and survives re-approval and key rotation.

## Runtime Liveness

> Status: Open Gap. Defined here; no producer publishes it and no consumer
> requires it yet. Tracked in `ori-edge-firmware` #68.

A device must be able to tell whether an authority is alive and watching it,
because that is what decides whether its Local Interlock may act on its own.
Broker connectivity does not answer the question: a live broker with a dead
runtime leaves the device connected and unsupervised, and the backstop
suppressed while nothing upstream can respond.

### Wire format

One fixed grammar, byte for byte, on the same terms as the command object
above — so the runtime signer and the device verifier cannot implement
different accepted languages:

```json
{"liveness":{"boot_id":41,"capability_hash":"sha256:<64-lowercase-hex>","device_id":"ori-fw-7c9f2b3a","runtime_seq":9007,"v":1},"signature":"ed25519:<base64-64-byte-signature>"}
```

Rules:

- Field order is exactly as shown: `boot_id`, `capability_hash`,
  `device_id`, `runtime_seq`, `v` — the lexicographic canonical order.
- `boot_id` is a canonical decimal integer within `1 .. 2^32 - 1`, equal to
  the device's current boot. Zero is not a valid `boot_id`: device counters
  persist a boot before use and issue from one upward.
- `capability_hash` is `sha256:` plus exactly 64 lowercase hex characters,
  equal to the device's accepted manifest hash.
- `device_id` is a fleet identifier: `[A-Za-z0-9._-]`, non-empty, within the
  receiver's declared length limit.
- `runtime_seq` is a canonical decimal integer (no leading zeros, no sign)
  within `1 .. 2^53 - 1`. **Zero is refused by the parser**, matching
  `provision_seq` and unlike `cmd_seq`, because a liveness message is only
  meaningful as a member of a strictly increasing series.
- `v` must be `1`.
- The signature is computed over the canonical bytes of the `liveness`
  object exactly as transmitted, in the shared `ed25519:<base64>` wire
  encoding (standard base64, 64-byte signature, canonical padding), using
  **the same runtime command key** the device already pins. No new key
  material, no second trust root.
- Any deviation — whitespace, reordered or extra fields, non-canonical
  integers, out-of-alphabet identifiers, a malformed signature field — is
  `malformed` and must be rejected before signature verification is
  attempted.

There is deliberately **no TTL field**. The expiry window is a contract
constant applied by the device, not a value the publisher chooses: a message
field would let a compromised or misconfigured runtime suppress a fleet's
backstops indefinitely by declaring a long window.

A liveness message carries no verdict back to the runtime. A device that
refuses one is silent about it, and the refusal surfaces only as the device
marking the runtime unreachable when its expiry window lapses.

### Freshness without a device clock

Devices have no trustworthy wall clock, so liveness reuses the freshness
mechanism the rest of this contract already uses — a monotonic counter —
combined with the device's own elapsed time since it accepted one.

A device accepts a liveness message when, in order: it parses; `device_id`
matches; the signature verifies against the provisioned runtime key;
`boot_id` equals the device's current boot; `capability_hash` equals the
device's accepted manifest hash; and `runtime_seq` strictly exceeds the last
accepted value **for this boot**.

**The `boot_id` binding is what removes the need to persist anything.**
Replay within a boot fails the counter check. Replay after a reboot fails
the boot check, because the device's `boot_id` has increased. No NVS write
per message, so the mechanism does not trade flash wear for freshness.

The runtime cannot publish valid liveness for a device until it has seen
that device's current `boot_id` in telemetry. That is a starting condition
only, and it is important not to overread it: **once the runtime knows a
`boot_id` it can keep signing valid messages indefinitely, whether or not it
is still receiving from that device.** `boot_id` is not secret and does not
expire.

So the signature proves that a holder of the runtime key produced the
message. It does not, and cannot, prove continued supervision. That gap is
closed by an obligation on the runtime, not by cryptography:

> **Supervision window.** A runtime MUST publish liveness for a device only
> while it has accepted authenticated telemetry from that device, for the
> same `boot_id` and the same accepted manifest epoch, within the
> supervision window below, measured on the runtime's own monotonic clock.
> When that window lapses, the runtime MUST stop publishing until fresh
> telemetry arrives.

**A device cannot verify this.** The contract is explicit about that
boundary: everything above the supervision rule is enforced by the device
and fails closed; the supervision rule is enforced by the runtime and is
verified by its test suite, not at the wire. Implementations must not
describe liveness as proof that a runtime is receiving — it is proof that a
key holder claims to be, bound to a device, a boot, and a manifest epoch.

### Expiry, and what a device does before it hears anything

A device treats the runtime as reachable while the elapsed time since its
last accepted liveness is under the expiry window, and unreachable
otherwise. Combined with gateway reachability, that produces the orphan
condition the Local Interlock gates on.

Every boot starts with no accepted liveness, so the same question arises at
every restart, not only the first: a device that has heard nothing yet is
**not** immediately marked runtime-unreachable. It observes a **boot grace
window** during which the interlock's debounce counter saturates without
tripping — the behaviour it already has while connected. When the grace
window expires without accepted liveness, the device sets
`runtime_reachable` to false.

> **Liveness controls `runtime_reachable` only.** It never bypasses the
> gateway half of the authority gate. The device is orphaned only when
> `gateway_reachable` is also false:
>
> ```text
> orphaned = !runtime_reachable && !gateway_reachable
> ```
>
> An expired liveness window while a gateway still supervises the device
> leaves it **not** orphaned. Treating expiry as orphaning would let the
> Local Interlock act while another authority is watching — the two-writer
> divergence the gate exists to prevent.

Failing toward runtime-unreachable after the grace is deliberate. A device
that has never been told an authority is watching demonstrably has none from
this path, and the backstop exists for exactly that case. The grace window
is what stops a device reporting a healthy runtime unreachable during the
seconds between power-on and its first publish.

### Timing

| Constant | Provisional value | Constraint |
|---|---|---|
| Publication interval | 15 s | Runtime obligation, per device. |
| Supervision window | 45 s | Runtime-side. The runtime stops publishing for a device it has not heard from within this. MUST be shorter than the device's expiry window, so a device learns of lost supervision by silence rather than by the runtime racing it. |
| Expiry window | 60 s | Device-side. MUST be at least 3× the publication interval, so isolated message loss does not mark a healthy runtime unreachable. |
| Boot grace window | 90 s | MUST exceed the expiry window, and SHOULD accommodate the measured worst-case boot-to-first-telemetry plus one publication interval. |

**These values are provisional and must be ratified against measurement on
real hardware** — reconnect behaviour, broker jitter, and boot-to-first-
telemetry latency. They are recorded here so implementations share a
starting point, not because they are yet justified.

Both directions of error are hazardous, and this contract does not rank them.

- **Too short.** A healthy runtime is reported unreachable while it is in
  fact watching. Where no gateway is reachable either, the device then
  orphans and actuates on local thresholds — the two-writer divergence the
  orphan gate exists to prevent, arriving through the mechanism meant to
  avoid it.
- **Too long.** After a supervising runtime dies, the device continues to
  report it reachable for the length of the window, so a dangerous load runs
  without its backstop for that long.

Which dominates depends on the installation and on what the interlock rule
actually does: opening a contactor on overcurrent has a different hazard
profile from an actuation that interrupts a process. **The window is derived
from measured loss and jitter bounds together with the deployment safety
case**, never from an implementation default and never from a general claim
about which failure is worse.

### Golden vectors

The authoritative corpus for this section is
[liveness-vectors-v1.json](liveness-vectors-v1.json), held **here**, beside
this document. Its SHA-256 is
`199c9a3363e4fd05073ee43ce67a8cff278945f0fc2a5fc644df02e7ee70c44d`.

Implementing repositories copy it byte-for-byte and pin that digest —
`ori-edge-firmware/test/golden/liveness_vectors.json` and
`ori-runtime/tests/fixtures/firmware_liveness_vectors.json` — and never
generate its expectations from their own behaviour.

**The artifact lives here, not merely its digest, because a digest is not
reviewable.** A CODEOWNER asked to ratify a bare SHA-256 can only confirm that
it is a hexadecimal number; the accept, reject and transport cases it stands
for have to be readable in the change that ratifies them. Holding the file in
the contract repository is also what makes a single-repository change
detectable: two constants coordinated by hand are not a parity mechanism,
because a change made in one implementer leaves the other still matching its
own unchanged constant while the corpora diverge.

`ori-edge-firmware/test/golden/generate_liveness_vectors.py` is the authoring
tool that produced this file and can reproduce it byte-for-byte, so a proposed
change can be regenerated and reviewed rather than hand-edited. The tool is
not the authority; this file is.

Case expectations are authored from the sections above, not recorded from an
implementation. A corpus produced by running a signer certifies whatever that
signer does, including its defects, and cannot detect that the signer is
wrong.

Reject cases carry two fields that make them meaningful:

- `signature_valid` distinguishes a refusal decided *before* the signature is
  checked from one decided *after* it. A binding or freshness refusal is only
  evidence that the device performed that check if the signature was good;
  otherwise the device could refuse the message earlier and the check under
  test stays unproven.
- `verifier_context` carries the device state the case is evaluated against —
  current `boot_id`, accepted `capability_hash`, and
  `last_accepted_runtime_seq` for this boot. The freshness rules are stateful,
  so "refuse a replayed `runtime_seq`" has no meaning without it. A verifier
  that accepted replays indefinitely would otherwise satisfy every byte-level
  vector.

`transport_reject_cases` are refused on how the message arrived rather than on
its bytes, and are byte-identical to messages the device must accept when
delivered live. No content-level case can express them.

The disclosed test seeds are fixtures only and MUST NOT be used outside
deterministic tests.

### Manifest-epoch binding, and the maintenance problem it exposes

Liveness binds to `capability_hash`, so it lapses on a manifest transition
exactly as command authority does.

An earlier draft omitted the field, reasoning that supervision is separable
from command authority. That was wrong on the mechanism, not merely on the
policy: a device reloads the approved runtime key **only while the stored
approval hash equals its current manifest hash**, and otherwise runs with an
all-zero key that no signature matches. After capability drift there is no
active runtime key, so liveness signed with the old one would not verify
regardless of which fields it carried. Omitting the hash would have
described a behaviour the device cannot exhibit.

A supervision authority that genuinely outlives capability changes would
need its own provisioned key and role. That is a larger change than a field,
and it is not proposed here.

**This makes a real lifecycle problem visible rather than solving it.** A
firmware update or capability change now lapses supervision, so the device
reports the runtime unreachable — and where no gateway is reachable, orphans
and its interlock may actuate during a maintenance window. The fix
belongs in the lifecycle — an explicit safe-maintenance mode, or a
deliberate supervision handoff — not in weakening the binding, which would
hide the problem while leaving the hazard. **Tracked as an open question;
this contract must not be implemented for unattended physical loads until it
is answered.**

## Runtime Obligations

- Maintain one strictly increasing `cmd_seq` per target device, continuing
  across command-key rotation; never reuse a value, including for retries of
  lost commands.
- Record every issued command and every fault-event rejection; a
  `bad_signature` or `replayed` fault from a device is a security signal,
  not noise.
- Command-key rotation is a provisioning operation: the new public key is
  registered on the device through the provisioning path, and the sequence
  space continues (the mark is per device, not per key).
- Publish runtime liveness per device at the interval above, on the
  device-scoped topic, unretained, carrying the device's current `boot_id`
  and accepted `capability_hash` as last seen in its telemetry.
- Observe the supervision window above: stop publishing for a device the
  runtime has not heard from within it. This is the rule that makes liveness
  mean supervision rather than mere process existence, and the device cannot
  check it, so it is carried by tests on both sides of the boundary:
  - **Runtime-side:** the runtime stops publishing liveness for a device no
    later than one supervision window after the last accepted authenticated
    telemetry from it. That is a statement about the publisher and is all a
    runtime test can establish.
  - **Integration/HIL:** with the broker still connected **and no gateway
    reachable**, a device whose runtime has stopped receiving from it
    becomes orphaned. The gateway condition is not incidental — with a
    gateway reachable the same device must stay unorphaned, and both cases
    belong in the evidence. Note the delay compounds — up to one supervision
    window plus one expiry window, 105 s at the provisional values — and a
    deployment safety case must size against that total, not against either
    window alone.
- Maintain one strictly increasing `runtime_seq` per device, separate from
  `cmd_seq`, and **persist it across runtime restarts**. A device holds the
  last accepted value for its current boot, so a runtime that restarts with
  an in-memory counter reset to zero has every subsequent message rejected
  and cannot recover while that device stays booted — the device reports a
  healthy runtime unreachable, and keeps doing so. The same per-device
  registry row that carries `cmd_seq` is the natural home, and the
  reservation-ceiling pattern the device uses for its own counters bounds
  the write rate.
- If a runtime loses that state entirely, it MUST NOT attempt to bypass the
  check. The failure is safe by construction: affected devices report the
  runtime unreachable, and orphan if no gateway is reachable either.
  **Recovery requires the device to enter a new boot** — nothing else in
  this contract resets the device's boot-local high-water mark.
  Re-provisioning does not: it changes neither `boot_id` nor the accepted
  sequence, so it is not a recovery path and must not be described as one.
  Making it one would need a distinct signed liveness epoch with a
  replay-safe transition, because otherwise every message already signed for
  the same boot, key and manifest becomes valid again. That is a future
  contract change, not an implementation detail.
- **Stop publishing liveness for a device the runtime is deliberately
  releasing** — during maintenance, decommissioning, or when handing
  authority elsewhere. Silence is the supported way to tell a device it is
  on its own; there is no "goodbye" message, because a message asserting
  absence could not be trusted from an absent party.

## Required Implementation Artifacts

- Device-side verification tests: grammar rejection variants, cross-device
  refusal, tamper and rogue-key refusal, replay and gap semantics,
  persist-before-actuate ordering, storage-failure fail-closed.
- Runtime-side signing tests against the same fixed grammar, byte-exact.
- Shared golden command and provisioning-approval vector sets once the
  runtime signing side lands. Each set pins the entire signed object and wire
  message byte-for-byte across the runtime signer and device verifier;
  provisioning vectors cover both development and sealed-flash postures.
- **Runtime liveness**, once that section leaves Open Gap status:
  - Shared byte-exact liveness golden vectors, pinning the signed object and
    the wire message across the runtime signer and the device verifier.
  - Runtime-side signer tests against the fixed grammar, with negative cases.
  - Device-side parser and verifier tests: wrong device, wrong `boot_id`,
    manifest-epoch mismatch, rogue key, malformed signature, non-canonical
    integers, extra or reordered fields, an unsupported `v`, integers above
    their maximums, and identifiers or capability hashes outside their
    grammars.
  - Sequence semantics: a repeated or regressing `runtime_seq` is refused; a
    gap is accepted, because loss is expected and only monotonicity matters.
    The counter is per-boot and is never persisted, so a low `runtime_seq` is
    accepted after a reboot while a high one captured from the previous boot
    is refused on `boot_id` — which is what removes the flash write per
    message.
  - Ingress: a liveness message delivered **retained** is refused even though
    its bytes are those of a message the device must accept when delivered
    live.
  - Reachability outcomes, keeping `runtime_reachable` and `orphaned`
    distinct: fresh liveness yields `runtime_reachable == true`; an expired
    window **while MQTT remains connected** yields `runtime_reachable ==
    false`; nothing ever received yields the boot-grace behaviour and then
    `runtime_reachable == false`.
  - The gate itself, which liveness must never bypass: no liveness after
    grace **and no reachable gateway** yields `orphaned == true`; no
    liveness after grace **but a reachable gateway** yields
    `orphaned == false`.
  - Runtime restart with durable sequence state: publication resumes and the
    device keeps accepting, with no device reboot.
  - Supervision: the runtime stops publishing within one supervision window
    of the last accepted telemetry from a device.
  - HIL evidence for the broker-alive/runtime-dead case, which is the whole
    reason the signal exists.
