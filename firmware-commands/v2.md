# Firmware Commands Contract v2

> Status: maturity `draft`; compatibility `amendable`; adoption: none
> recorded; proof: end-to-end `none`, HIL `none`, production `none`. Record:
> [status/firmware-commands/v2.json](../status/firmware-commands/v2.json).

This version exists for one verdict and the runtime obligation it forces. A
device whose release-owned actuation rate policy refuses a command reports
that refusal as `rate_limited`, and a runtime never reissues a command on its
own, so that a refusal it did not hear cannot become an actuation it did not
time.

## What changed from v1

Two changes, both breaking:

- **A verdict is added.** `rate_limited` joins the verdict table, and it
  answers `relay_close` only: no rate policy refuses or delays `relay_open`.
  A v1 device never returns it, and a v1 consumer of `command_rejected` faults refuses it,
  because [firmware-telemetry/v1.md](../firmware-telemetry/v1.md) holds that
  detail to a closed set.
- **A lost command is never reissued automatically.** v1 requires a runtime to
  treat a command that produced neither a relay action nor a `command_rejected`
  fault as lost and to retry it with a fresh `cmd_seq`, and requires the same
  after a device crash between persist and actuate. This version forbids that
  retry. See [Unresolved Commands](#unresolved-commands).

Everything else is [v1](v1.md)'s, as its text stands at ori-specs `d979402`,
incorporated unchanged: the trust model, the wire format, the action
vocabulary, the MQTT transport binding, the provisioning approval, runtime
liveness (including its Open Gap status), the runtime obligations and the
required artifacts, each except where this document replaces a rule by name.
That text includes sections v1 gained after its freeze, runtime liveness among
them, whose classification is still owed by v1's baseline audit; this version
carries them as its own text, whatever that audit decides for v1.

**The command bytes do not change.** The command object keeps `"v":1`, because
its `v` names the command grammar and this version does not change the
grammar. A command a v2 runtime signs is byte-identical to the v1 command for
the same fields, and a v1 device and a v2 device verify exactly the same
commands. What differs is that a v2 device may decline a verified command as
`rate_limited`, and what a v2 runtime may do afterwards. The provisioning
approval and the liveness message are likewise unchanged and keep their
`"v":1`.

A device reports v2 verdicts in fault objects of
[firmware-telemetry/v2.md](../firmware-telemetry/v2.md), whose `v` is `2`. A
device MUST NOT report `rate_limited` in a fault object whose `v` is `1`.

## Error Semantics

This table replaces v1's:

| Verdict | Meaning |
| --- | --- |
| `malformed` | The message violates the fixed grammar. |
| `wrong_device` | `device_id` names another device. A command signed for one device must never actuate another. |
| `bad_signature` | Signature verification against the provisioned runtime key failed. |
| `replayed` | `cmd_seq` does not strictly exceed the persisted high-water mark. |
| `capability_mismatch` | The command's `capability_hash` does not equal the device's accepted manifest hash. Consumes the sequence. |
| `unknown_action` | The `(action, channel)` pair is not in the accepted manifest with `runtime_commanded` authority. Consumes the sequence. |
| `rate_limited` | The command was verified, fresh and authorised, and the device's release-owned actuation rate policy refused it. Consumes the sequence. Nothing was actuated. |
| `storage_failure` | The high-water mark could not be read or persisted; nothing was actuated and nothing was consumed. |

Gaps in `cmd_seq` are valid and regressions and repeats are replays, as in v1.
A rejected command actuates nothing. Verdicts after the freshness check
(`capability_mismatch`, `unknown_action`, `rate_limited`) consume the sequence,
so the rejected instruction can never be replayed. Verdicts before it
(`malformed`, `wrong_device`, `bad_signature`, `replayed`) persist nothing.

## Rate-Limited Refusal

**It is decided last.** A device applies its rate policy only to a command that
has passed every acceptance check in v1's trust model, in v1's order: grammar,
device binding, signature, freshness, capability hash, and `runtime_commanded`
authority for the `(action, channel)` pair. A command refused by any of those
carries that verdict, never `rate_limited`. A `rate_limited` fault is
therefore evidence that the command was genuine, current and permitted, and
that the device declined to act on it at that moment.

**It spends the command.** The high-water mark was persisted when freshness
passed, so the same bytes delivered later are `replayed`. A refused command
cannot be held and actuated once the policy would admit it.

**It actuates nothing, and it is never execution.** The device writes no
output for a refused command, records no operation for it in the policy's own
history, and reports no relay action. A consumer MUST NOT record a
`rate_limited` command as executed or applied, and MUST NOT count it toward
anything that counts executions. Where the command was the dispatch of an
approved Tier C action, the approval
[tier-c-approval/v1.md](../tier-c-approval/v1.md) committed before dispatch
remains as committed, and the refusal never revokes or rewrites it. The
refusal is signed evidence that the command did not execute; it does not
reconcile the dispatch. The dispatch's record follows tier-c-approval/v1
(`dispatch_outcome_unknown` or `dispatch_not_proven`), and only that
contract's two forms of reconciliation resolve it. Whether such a fault may
serve as commissioned feedback for a zone, or as an executor's own result,
belongs to the specification that admits firmware-backed actuators into an
in-force safety zone, which [runtime-health/v3.md](../runtime-health/v3.md)
requires before any may.

**It is final.** A runtime MUST NOT reissue a `rate_limited` command
automatically, under any `cmd_seq`. Reissuing is a new decision, made by the
authority that issued the first command, and it is signed as a new command
under a fresh `cmd_seq`.

**The policy is the release's.** Its intervals, windows and counts are fixed
in the reviewed device release. No command, manifest field, configuration
document or runtime message sets or changes them, and this contract defines
none of them.

**It never refuses an open.** A release's rate policy MUST NOT refuse or delay
`relay_open`, and a device MUST NOT return `rate_limited` for it.
[commissioned-safety-binding/v1.md](../commissioned-safety-binding/v1.md#firmware-command-semantics)
makes `relay_open` the wire spelling of `open_protected_circuit`, the outcome a
Tier D trip commands. A command carries an action and no intent, so a device
cannot tell an `open_protected_circuit` issued under release-owned Tier D
authority from ordinary switching; the only policy that never refuses the
first is one that refuses no open. An open the policy admits MAY still count
toward its history. `rate_limited` therefore answers only `relay_close`.

**It never suppresses safety evaluation.**

- A device's rate policy MUST NOT refuse or delay an action an armed Local
  Interlock rule takes, MUST NOT disarm an armed rule, and MUST NOT run before
  or in place of Local Interlock evaluation. Which rules a device may arm, and
  how it reports a configuration it refuses to arm, are not decided by this
  contract.
- A `rate_limited` fault MUST NOT suppress, defer or alter a runtime's
  autonomous Tier D evaluation. It is evidence about one command, not an input
  to any safety condition.

## Unresolved Commands

This section replaces v1's rule that a lost command is retried, wherever v1
states it: the Trust Model's sentence on a crash between persist and actuate,
and the MQTT Transport Binding's paragraph on ingress loss.

A command for which the runtime has received neither a relay action nor a
`command_rejected` fault is **unresolved**. That covers a command lost in
transport, one dropped at ingress, one lost to a device crash between persist
and actuate, and one the device refused under a verdict whose fault never
arrived.

- A runtime MUST NOT reissue an unresolved command automatically, under the
  same or a fresh `cmd_seq`.
- A runtime MUST NOT record an unresolved command as executed.
- Reissuing is a new decision by the authority that issued the first command,
  signed as a new command under a fresh `cmd_seq`.

This contract does not define when a runtime may conclude that a command is
unresolved, because no rule here depends on it: the rule above holds at every
moment.

**Tier D attempts are not reissues.** Zero automatic reissue applies to
command-delivery recovery. It does not cancel the safety registry's existing
obligation to make fresh `open_protected_circuit` attempts for a latched Tier D
trip. Each attempt requires a new intent identity and fresh command sequence
under the original commissioned binding.

- [safety-profile/v1.md](../safety-profile/v1.md) governs those attempts: while
  a pair is tripped and its command status is not `command_issued`, the
  consumer keeps attempting on a bounded-backoff schedule with no terminal
  attempt limit, until the driver accepts, a local reset succeeds, or the
  consumer shuts down.
- An attempt is licensed by the latched trip and owned by the safety registry,
  independent of readings, as safety-profile/v1 states. It continues whatever
  became of earlier attempts short of the driver accepting one, including an
  attempt whose fate is still unknown after a restart. It is never a re-send
  of an earlier command's bytes: each attempt is signed as a new command
  under a fresh `cmd_seq`, with a new intent identity.
  safety-profile/v1 does not itself require an intent identity per attempt;
  this version does, for attempts made through firmware commands.
- An accepted command is never reissued merely because its physical effect is
  unverified, and an attempt never actuates through a binding other than the
  one the trip latched under: an orphaned trip stays latched and visible and
  cannot actuate, as safety-profile/v1 states.
- Every such attempt is a `relay_open`, which no rate policy refuses or delays.

**Why the bound is zero.** An automatic retry turns a refusal the runtime did
not hear into an actuation at a time no authority chose. A device that refused
a close under its rate policy, and whose fault was lost, admits the same
instruction once its interval has passed, so a runtime that retried would
actuate later than it asked to, on a decision that may no longer hold. Any
bound above zero keeps that path open for as long as the bound allows. The
device's own guarantee, persist before actuate, is unchanged: a lost command
is still lost rather than replayable.

The bound closes the runtime's own path to a late actuation, and only that one.
Freshness is the counter alone, so a command delayed in a broker or at ingress
still arrives with a fresh `cmd_seq` and is admitted when it arrives.

## Runtime Obligations

v1's obligations hold, with these replacements:

- v1's first obligation reads, in this version: maintain one strictly
  increasing `cmd_seq` per target device, continuing across command-key
  rotation, and never reuse a value.
- Record every issued command and every fault-event rejection. A
  `rate_limited` fault is recorded as a refusal that actuated nothing. A
  `bad_signature` or `replayed` fault from a device remains a security signal,
  not noise.
- Never reissue a command automatically, as
  [Unresolved Commands](#unresolved-commands) and
  [Rate-Limited Refusal](#rate-limited-refusal) state.

## Required Implementation Artifacts

In addition to v1's:

- **Device-side:** a command that passes every acceptance check and that the
  rate policy refuses yields `rate_limited`, writes no output, spends its
  `cmd_seq` (the same bytes delivered again yield `replayed`), and is signed as
  a `command_rejected` fault at `v` `2`. A command that fails an earlier check
  yields that check's verdict even while the policy would also refuse it. The
  Local Interlock acts while the policy would refuse a commanded action on the
  same channel. A `relay_open` is admitted at once in every state in which the
  policy refuses a `relay_close`, including any period after boot in which it
  refuses every close.
- **Runtime-side:** a `rate_limited` fault is recorded as a refusal and never
  as an execution; no path reissues a command automatically, after
  `rate_limited` or after any unresolved command; a `rate_limited` detail in a
  fault whose `v` is `1` is refused. A runtime that drives a commissioned zone
  through firmware commands also tests that a latched Tier D trip keeps making
  fresh `open_protected_circuit` attempts, each under a new `cmd_seq`, while
  every other command is published once.
- The fault corpus of [firmware-telemetry/v2.md](../firmware-telemetry/v2.md),
  which carries the signed `rate_limited` refusal.
