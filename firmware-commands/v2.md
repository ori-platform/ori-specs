# Firmware Commands Contract v2

> Status: maturity `draft`; compatibility `amendable`; adoption: producer
> (runtime) `implemented-unreleased`, `unassessed`, consumer (edge-firmware)
> `implemented-unreleased`, `unassessed`; proof: end-to-end `none`, HIL
> `none`, production `none`. Record:
> [status/firmware-commands/v2.json](../status/firmware-commands/v2.json).

This version exists for one verdict and the runtime obligation it forces. A
device whose release-owned actuation rate policy refuses a command reports
that refusal as `rate_limited`, and a runtime never reissues a command on its
own, so that a refusal it did not hear cannot become an actuation it did not
time. It also adds a nonce to runtime liveness, so that the runtime that
signed a liveness message can bound, from above and on its own clock, how
long ago a device began the transaction behind a reading it signed after
accepting it. The bound dates that transaction, not the measured quantity,
and is defined by
[firmware-telemetry/v2.md](../firmware-telemetry/v2.md#how-old-a-reading-is).
And it binds each signature the runtime command key makes to one purpose, so
that a liveness signature is never a command signature.

## What changed from v1

Five changes to what v1 defines, all breaking; runtime liveness, which v1 does
not define, follows below:

- **A verdict is added.** `rate_limited` joins the verdict table, and it
  answers `relay_close` only: no rate policy refuses or delays `relay_open`.
  A v1 device never returns it, and a v1 consumer of `command_rejected` faults refuses it,
  because [firmware-telemetry/v1.md](../firmware-telemetry/v1.md) holds that
  detail to a closed set.
- **A lost command is never reissued automatically.** v1 requires a runtime to
  treat a command that produced neither a relay action nor a `command_rejected`
  fault as lost and to retry it with a fresh `cmd_seq`, and requires the same
  after a device crash between persist and actuate. This version forbids that
  retry. See [Unresolved Commands](#unresolved-commands).
- **Keys and signatures follow the shared Ed25519 contracts.** The device
  admits the provisioning authority key and the runtime command key an
  approval carries under
  [ed25519-key-admission/v1](../ed25519-key-admission/v1.md), and verifies the
  command, the provisioning approval and the liveness message under
  [ed25519-verification/v1](../ed25519-verification/v1.md). v1 named neither
  rule, and a v1 device whose verifier takes the cofactored equation or
  decodes R loosely accepts signatures this version refuses. None of them is
  one a runtime produces by signing under RFC 8032. A command whose signature
  that contract refuses, under any of its clauses, is `bad_signature`; a
  liveness message it refuses is refused silently, as [Runtime Liveness](#runtime-liveness) refuses any
  liveness message, and carries no verdict back; an approval it refuses, or one
  carrying a key that admission refuses, registers nothing.
- **A liveness message may carry a nonce.** A liveness object at `"v":2`
  carries `nonce`, 128 bits the runtime generates fresh for that message. A
  device accepts liveness at `v` `1` and at `v` `2`, holds the nonce of the
  last one it accepted, and signs it into each reading it measures afterwards.
  A device whose manifest carries `runtime_key_domains`
  accepts liveness at `v` `2`, and a runtime publishes liveness to it at `v` `2`
  alone. See [Runtime Liveness at `v` 2](#runtime-liveness-at-v-2).
- **Commands and liveness are signed in separate domains.** The runtime
  command key signs a command, and a liveness message at either `v`, over a
  preimage that names its purpose, never over the object bytes alone, and only for a device whose signed manifest carries `runtime_key_domains`. A device that verifies v1's form refuses a command signed in them
  as `bad_signature`, and a liveness message silently, and a device governed by
  this version refuses v1's signatures the same ways. See
  [Signing Domains](#signing-domains).

Everything else is [v1](v1.md)'s, incorporated unchanged: the trust model
and the wire format, except for the key admission, the signature verification
and the signing domain above, the action vocabulary, the MQTT transport binding, the provisioning
approval, the runtime obligations and the required artifacts, each except
where this document replaces a rule by name or adds to it. Runtime liveness is
not in v1: v1's text gained it after its freeze, and v1's baseline audit moved
it here. This version defines it in [Runtime Liveness](#runtime-liveness), at
`v` `1`, and in [Runtime Liveness at `v` 2](#runtime-liveness-at-v-2).

**Runtime liveness is not an Open Gap in this version.** It is a defined
section with a runtime signer and a device verifier implemented against it:
the runtime signs and publishes liveness for each supervised device, and the
reference device firmware verifies it and records whether the runtime is
reachable. That is implementation, not proof. No end-to-end or HIL evidence
shows a device losing or regaining supervision through it, and no device
image yet gates a Local Interlock on it. A claim that liveness protects
anything needs that evidence first.

**The command bytes do not change; what the signature covers does.** The
command object keeps `"v":1`, because its `v` names the command grammar and
this version does not change the grammar. A command a v2 runtime signs is
byte-identical to the v1 command for the same fields, and its wire message
differs only in its signature, which covers the command domain's preimage of
[Signing Domains](#signing-domains) instead of the object bytes alone. A
command whose signature verifies is held to every other check v1 makes:
device binding, manifest, freshness and authority. A v2 device also refuses
the signatures [ed25519-verification/v1](../ed25519-verification/v1.md)
refuses, which no honest signer makes, it may decline a verified command as
`rate_limited`, and what a v2 runtime may do afterwards differs. The
provisioning approval is unchanged: it keeps its `"v":1` and is signed by the
provisioning authority key, as in v1. The liveness message keeps the grammar
of [Runtime Liveness](#runtime-liveness) at `"v":1` and gains a second grammar
at `"v":2`, and both are signed in the liveness domain.

A device reports v2 verdicts in fault objects of
[firmware-telemetry/v2.md](../firmware-telemetry/v2.md), whose `v` is `2`. A
device MUST NOT report `rate_limited` in a fault object whose `v` is `1`.

## Signing Domains

The runtime command key signs two kinds of message under this version, a
command and a runtime liveness message, and each of its signatures is valid
for one of them only. It signs a preimage of three parts, in this order: the
domain of the message's purpose; one zero byte, NUL; and the canonical bytes
of the signed object exactly as transmitted.

| Purpose | Domain | Signed object |
| --- | --- | --- |
| Command | `ori.firmware_command.v2` | the `command` object |
| Runtime liveness, at `v` `1` and at `v` `2` | `ori.firmware_liveness.v2` | the `liveness` object |

- A domain's bytes are its characters in ASCII, without quotes:
  `ori.firmware_command.v2` is 23 bytes and `ori.firmware_liveness.v2` is 24.
- The `v2` in a domain names this contract version, not the object's `v`. A
  command at `"v":1`, and liveness at `"v":1` and at `"v":2`, are signed in
  these domains.
- Neither the domain nor the NUL is transmitted. The wire message has the
  grammar its own section gives, and a verifier builds the preimage from the
  object bytes it received.
- A verifier takes the domain from the message's purpose, which the entry
  point it reaches already fixes: a command verifier verifies in the command
  domain only, and a liveness verifier in the liveness domain only. It never
  tries another domain or the object bytes alone, before or after a failure.
- A signature that does not verify in its purpose's domain is `bad_signature`
  for a command and `signature_invalid` for liveness, whatever other preimage
  it verifies over.
- A runtime signs with this key only these two preimages. It never signs the
  object bytes alone, as v1 did, nor a preimage in a domain this table does
  not list.

No preimage of one purpose is a preimage of the other, or of v1's form. The
two domains differ before either NUL, and v1's preimage is a JSON object,
whose first byte is `{`, which neither domain begins with. So a liveness
signature is never a command signature, whatever bytes it covers, and the
runtime's signatures over identical object bytes differ between the two
purposes.

**A device declares what it accepts.** A device governed by this version
carries the `runtime_key_domains` member of
[firmware-telemetry/v2.md](../firmware-telemetry/v2.md#runtime-key-domains)
in its signed capability manifest, and that section alone defines what the
member declares. A runtime signs in these domains for a device only while that
device's accepted manifest carries it. A runtime never signs v1's form, for any device, so a
device whose manifest does not carry it receives no command and no liveness
from it: the runtime treats its `runtime_commanded` actions as
unavailable from the moment it accepts that manifest, or, for a manifest it
already held, from its first start under this version, and the device reports
the runtime unreachable once its expiry window lapses, with the consequences
[Runtime Liveness](#expiry-and-what-a-device-does-before-it-hears-anything)
gives. A runtime learns what a device accepts from that member and from nothing
else, and never sends a form to see whether it is accepted.
The same declaration is how a later version would let a device select another
domain.

The provisioning approval is signed by the provisioning authority key, not the
runtime command key, and this section does not change it.

### Command vectors

The command corpus for this section is
[command-vectors-v2.json](command-vectors-v2.json), held here beside this
document. Its SHA-256 is
`8be782aa1848b458dd58369dd03e3ee967cff4d7dd503768a17215468f9b387d`.
Implementing repositories copy it byte for byte, pin that digest, and never
generate its expectations from their own behaviour.

Each case is a command message evaluated against its `verifier_context`: the
device's `device_id`, its accepted `capability_hash`, its persisted `cmd_seq`
high-water mark, and the `(action, channel)` pairs its manifest grants
`runtime_commanded` authority. It holds commands the device accepts, and
refusals, each `bad_signature` and each passing every other check, whose
signature was made by:

- the runtime key over the command object bytes alone, v1's form;
- the runtime key in the liveness domain;
- the runtime key over the command domain and the object bytes with no NUL
  between them;
- a rogue key in the command domain.

An accepted case assumes a device whose rate policy admits it, since the
policy is decided after every check this corpus exercises; a device-side test
puts the policy in a state that admits each case.

It also holds cross-purpose pairs: a command object and a liveness object,
each with the runtime key's signatures over it in the command domain, in the
liveness domain, and alone. The three signatures over one object differ, and
each verifies over its own preimage only.

`scripts/generate-firmware-command-vectors-v2` reproduces the file byte for
byte. It signs with OpenSSL through `cryptography`, under the disclosed
runtime and rogue test seeds of the liveness corpora.
`scripts/check-firmware-command-vectors-v2` shares no code with it: it reads
the domains from the table above and the command grammar from v1's Wire
Format, verifies every signature with its own curve arithmetic, and confirms
that each case is accepted and each refusal is refused as `bad_signature`
while passing every other check.

The disclosed test seeds are fixtures only and MUST NOT be used outside
deterministic tests.

## Error Semantics

This table replaces v1's:

| Verdict | Meaning |
| --- | --- |
| `malformed` | The message violates the fixed grammar. |
| `wrong_device` | `device_id` names another device. A command signed for one device must never actuate another. |
| `bad_signature` | Signature verification against the provisioned runtime key failed. |
| `replayed` | `cmd_seq` does not strictly exceed the persisted high-water mark. |
| `capability_mismatch` | The command's `capability_hash` does not equal the device's accepted manifest hash. Consumes the sequence. |
| `unknown_action` | The `(action, channel)` pair is not in the accepted manifest with `runtime_commanded` authority. Consumes the sequence. |
| `rate_limited` | The command was verified, fresh and authorised, and the device's release-owned actuation rate policy refused it. Consumes the sequence. Nothing was actuated. |
| `storage_failure` | The high-water mark could not be read or persisted; nothing was actuated and nothing was consumed. |

Gaps in `cmd_seq` are valid and regressions and repeats are replays, as in v1.
A rejected command actuates nothing. Verdicts after the freshness check
(`capability_mismatch`, `unknown_action`, `rate_limited`) consume the sequence,
so the rejected instruction can never be replayed. Verdicts before it
(`malformed`, `wrong_device`, `bad_signature`, `replayed`) persist nothing.

## Rate-Limited Refusal

**It is decided last.** A device applies its rate policy only to a command that
has passed every acceptance check in v1's trust model, in v1's order: grammar,
device binding, signature, freshness, capability hash, and `runtime_commanded`
authority for the `(action, channel)` pair. A command refused by any of those
carries that verdict, never `rate_limited`. A `rate_limited` fault is
therefore evidence that the command was genuine, current and permitted, and
that the device declined to act on it at that moment.

**It spends the command.** The high-water mark was persisted when freshness
passed, so the same bytes delivered later are `replayed`. A refused command
cannot be held and actuated once the policy would admit it.

**It actuates nothing, and it is never execution.** The device writes no
output for a refused command, records no operation for it in the policy's own
history, and reports no relay action. A consumer MUST NOT record a
`rate_limited` command as executed or applied, and MUST NOT count it toward
anything that counts executions. Where the command was the dispatch of an
approved Tier C action, the approval
[tier-c-approval/v1.md](../tier-c-approval/v1.md) committed before dispatch
remains as committed, and the refusal never revokes or rewrites it. The
refusal is signed evidence that the command did not execute; it does not
reconcile the dispatch. The dispatch's record follows tier-c-approval/v1
(`dispatch_outcome_unknown` or `dispatch_not_proven`), and only that
contract's two forms of reconciliation resolve it. Whether such a fault may
serve as commissioned feedback for a zone, or as an executor's own result,
belongs to the specification that admits firmware-backed actuators into an
in-force safety zone, which [runtime-health/v3.md](../runtime-health/v3.md)
requires before any may.

**It is final.** A runtime MUST NOT reissue a `rate_limited` command
automatically, under any `cmd_seq`. Reissuing is a new decision, made by the
authority that issued the first command, and it is signed as a new command
under a fresh `cmd_seq`.

**The policy is the release's.** Its intervals, windows and counts are fixed
in the reviewed device release. No command, manifest field, configuration
document or runtime message sets or changes them, and this contract defines
none of them.

**It never refuses an open.** A release's rate policy MUST NOT refuse or delay
`relay_open`, and a device MUST NOT return `rate_limited` for it.
[commissioned-safety-binding/v1.md](../commissioned-safety-binding/v1.md#firmware-command-semantics)
makes `relay_open` the wire spelling of `open_protected_circuit`, the outcome a
Tier D trip commands. A command carries an action and no intent, so a device
cannot tell an `open_protected_circuit` issued under release-owned Tier D
authority from ordinary switching; the only policy that never refuses the
first is one that refuses no open. An open the policy admits MAY still count
toward its history. `rate_limited` therefore answers only `relay_close`.

**It never suppresses safety evaluation.**

- A device's rate policy MUST NOT refuse or delay an action an armed Local
  Interlock rule takes, MUST NOT disarm an armed rule, and MUST NOT run before
  or in place of Local Interlock evaluation. Which rules a device may arm, and
  how it reports a configuration it refuses to arm, are not decided by this
  contract.
- A `rate_limited` fault MUST NOT suppress, defer or alter a runtime's
  autonomous Tier D evaluation. It is evidence about one command, not an input
  to any safety condition.

## Unresolved Commands

This section replaces v1's rule that a lost command is retried, wherever v1
states it: the Trust Model's sentence on a crash between persist and actuate,
and the MQTT Transport Binding's paragraph on ingress loss.

A command for which the runtime has received neither a relay action nor a
`command_rejected` fault is **unresolved**. That covers a command lost in
transport, one dropped at ingress, one lost to a device crash between persist
and actuate, and one the device refused under a verdict whose fault never
arrived.

- A runtime MUST NOT reissue an unresolved command automatically, under the
  same or a fresh `cmd_seq`.
- A runtime MUST NOT record an unresolved command as executed.
- Reissuing is a new decision by the authority that issued the first command,
  signed as a new command under a fresh `cmd_seq`.

This contract does not define when a runtime may conclude that a command is
unresolved, because no rule here depends on it: the rule above holds at every
moment.

**Tier D attempts are not reissues.** Zero automatic reissue applies to
command-delivery recovery. It does not cancel the safety registry's existing
obligation to make fresh `open_protected_circuit` attempts for a latched Tier D
trip. Each attempt requires a new intent identity and fresh command sequence
under the commissioned binding authorized for that attempt by the governing
safety-profile contract. Under safety-profile/v1, that is the binding the trip
latched under; a successor may authorize a durably recorded continuity
adoption.

- [safety-profile/v1.md](../safety-profile/v1.md) governs those attempts: while
  a pair is tripped and its command status is not `command_issued`, the
  consumer keeps attempting on a bounded-backoff schedule with no terminal
  attempt limit, until the driver accepts, a local reset succeeds, or the
  consumer shuts down.
- An attempt is licensed by the latched trip and owned by the safety registry,
  independent of readings, as safety-profile/v1 states. It continues whatever
  became of earlier attempts short of the driver accepting one, including an
  attempt whose fate is still unknown after a restart. It is never a re-send
  of an earlier command's bytes: each attempt is signed as a new command
  under a fresh `cmd_seq`, with a new intent identity.
  safety-profile/v1 does not itself require an intent identity per attempt;
  this version does, for attempts made through firmware commands.
- An accepted command is never reissued merely because its physical effect is
  unverified, and an attempt never actuates through a binding other than the
  one the governing safety-profile contract authorizes for it. Under
  safety-profile/v1 an orphaned trip stays latched and visible and cannot
  actuate.
- Every such attempt is a `relay_open`, which no rate policy refuses or delays.
- An attempt the runtime refuses before signing, because the device's manifest does not carry `runtime_key_domains`
  ([Signing Domains](#signing-domains)), is not a command: it consumes no `cmd_seq`, does not
  end the attempts, and is reported as
  [runtime-health/v4.md](../runtime-health/v4.md#safety_zones-object) reports
  any attempt refused before signing: `driver_refused`, so the trip it was for
  is unresolved and critical from that attempt.

**Why the bound is zero.** An automatic retry turns a refusal the runtime did
not hear into an actuation at a time no authority chose. A device that refused
a close under its rate policy, and whose fault was lost, admits the same
instruction once its interval has passed, so a runtime that retried would
actuate later than it asked to, on a decision that may no longer hold. Any
bound above zero keeps that path open for as long as the bound allows. The
device's own guarantee, persist before actuate, is unchanged: a lost command
is still lost rather than replayable.

The bound closes the runtime's own path to a late actuation, and only that one.
Freshness is the counter alone, so a command delayed in a broker or at ingress
still arrives with a fresh `cmd_seq` and is admitted when it arrives.

## Runtime Liveness

A device must be able to tell whether an authority is alive and watching it,
because that is what decides whether its Local Interlock may act on its own.
Broker connectivity does not answer the question: a live broker with a dead
runtime leaves the device connected and unsupervised, and the backstop
suppressed while nothing upstream can respond.

### Wire format

One fixed grammar, byte for byte, on the same terms as v1's command object
— so the runtime signer and the device verifier cannot implement
different accepted languages:

```json
{"liveness":{"boot_id":41,"capability_hash":"sha256:<64-lowercase-hex>","device_id":"ori-fw-7c9f2b3a","runtime_seq":9007,"v":1},"signature":"ed25519:<base64-64-byte-signature>"}
```

Rules:

- Field order is exactly as shown: `boot_id`, `capability_hash`,
  `device_id`, `runtime_seq`, `v` — the lexicographic canonical order.
- `boot_id` is a canonical decimal integer within `1 .. 2^32 - 1`, equal to
  the device's current boot. Zero is not a valid `boot_id`: device counters
  persist a boot before use and issue from one upward.
- `capability_hash` is `sha256:` plus exactly 64 lowercase hex characters,
  equal to the device's accepted manifest hash.
- `device_id` is a fleet identifier: `[A-Za-z0-9._-]`, non-empty, within the
  receiver's declared length limit.
- `runtime_seq` is a canonical decimal integer (no leading zeros, no sign)
  within `1 .. 2^53 - 1`. **Zero is refused by the parser**, matching
  `provision_seq` and unlike `cmd_seq`, because a liveness message is only
  meaningful as a member of a strictly increasing series.
- `v` must be `1`.
- The signature is computed in the liveness domain of
  [Signing Domains](#signing-domains), over the canonical bytes of the
  `liveness` object exactly as transmitted, in the shared `ed25519:<base64>` wire
  encoding (standard base64, 64-byte signature, canonical padding), using
  **the same runtime command key** the device already pins. No new key
  material, no second trust root.
- Any deviation — whitespace, reordered or extra fields, non-canonical
  integers, out-of-alphabet identifiers, a malformed signature field — is
  `malformed` and must be rejected before signature verification is
  attempted.

There is deliberately **no TTL field**. The expiry window is a contract
constant applied by the device, not a value the publisher chooses: a message
field would let a compromised or misconfigured runtime suppress a fleet's
backstops indefinitely by declaring a long window.

A liveness message carries no verdict back to the runtime. A device that
refuses one is silent about it, and the refusal surfaces only as the device
marking the runtime unreachable when its expiry window lapses.

### Freshness without a device clock

Devices have no trustworthy wall clock, so liveness reuses the freshness
mechanism the rest of this contract already uses — a monotonic counter —
combined with the device's own elapsed time since it accepted one.

A device accepts a liveness message when, in order: it parses; `device_id`
matches; the signature verifies against the provisioned runtime key;
`boot_id` equals the device's current boot; `capability_hash` equals the
device's accepted manifest hash; and `runtime_seq` strictly exceeds the last
accepted value **for this boot**.

**The `boot_id` binding is what removes the need to persist anything.**
Replay within a boot fails the counter check. Replay after a reboot fails
the boot check, because the device's `boot_id` has increased. No NVS write
per message, so the mechanism does not trade flash wear for freshness.

The runtime cannot publish valid liveness for a device until it has seen
that device's current `boot_id` in telemetry. That is a starting condition
only, and it is important not to overread it: **once the runtime knows a
`boot_id` it can keep signing valid messages indefinitely, whether or not it
is still receiving from that device.** `boot_id` is not secret and does not
expire.

So the signature proves that a holder of the runtime key produced the
message. It does not, and cannot, prove continued supervision. That gap is
closed by an obligation on the runtime, not by cryptography:

> **Supervision window.** A runtime MUST publish liveness for a device only
> while it has accepted authenticated telemetry from that device, for the
> same `boot_id` and the same accepted manifest epoch, within the
> supervision window below, measured on the runtime's own monotonic clock.
> When that window lapses, the runtime MUST stop publishing until fresh
> telemetry arrives.

**A device cannot verify this.** The contract is explicit about that
boundary: everything above the supervision rule is enforced by the device
and fails closed; the supervision rule is enforced by the runtime and is
verified by its test suite, not at the wire. Implementations must not
describe liveness as proof that a runtime is receiving — it is proof that a
key holder claims to be, bound to a device, a boot, and a manifest epoch.

### Expiry, and what a device does before it hears anything

A device treats the runtime as reachable while the elapsed time since its
last accepted liveness is under the expiry window, and unreachable
otherwise. Combined with gateway reachability, that produces the orphan
condition the Local Interlock gates on.

Every boot starts with no accepted liveness, so the same question arises at
every restart, not only the first: a device that has heard nothing yet is
**not** immediately marked runtime-unreachable. It observes a **boot grace
window** during which the interlock's debounce counter saturates without
tripping — the behaviour it already has while connected. When the grace window
expires without accepted liveness, the device sets `runtime_reachable` to false.
The grace window covers only a device that has held its active runtime key and
accepted manifest since the boot began; a capability transition during the boot
ends it at once, as [Manifest-epoch
binding](#manifest-epoch-binding-and-the-maintenance-problem-it-exposes) states.

> **Liveness controls `runtime_reachable` only.** It never bypasses the
> gateway half of the authority gate. The device is orphaned only when
> `gateway_reachable` is also false:
>
> ```text
> orphaned = !runtime_reachable && !gateway_reachable
> ```
>
> An expired liveness window while a gateway still supervises the device
> leaves it **not** orphaned. Treating expiry as orphaning would let the
> Local Interlock act while another authority is watching — the two-writer
> divergence the gate exists to prevent.

Failing toward runtime-unreachable after the grace is deliberate. A device
that has never been told an authority is watching demonstrably has none from
this path, and the backstop exists for exactly that case. The grace window
is what stops a device reporting a healthy runtime unreachable during the
seconds between power-on and its first publish.

### Timing

| Constant | Provisional value | Constraint |
|---|---|---|
| Publication interval | 15 s | Runtime obligation, per device. |
| Supervision window | 45 s | Runtime-side. The runtime stops publishing for a device it has not heard from within this. MUST be shorter than the device's expiry window, so a device learns of lost supervision by silence rather than by the runtime racing it. |
| Expiry window | 60 s | Device-side. MUST be at least 3× the publication interval, so isolated message loss does not mark a healthy runtime unreachable. |
| Boot grace window | 90 s | MUST exceed the expiry window, and SHOULD accommodate the measured worst-case boot-to-first-telemetry plus one publication interval. |

**These values are provisional and must be ratified against measurement on
real hardware** — reconnect behaviour, broker jitter, and boot-to-first-
telemetry latency. They are recorded here so implementations share a
starting point, not because they are yet justified.

Both directions of error are hazardous, and this contract does not rank them.

- **Too short.** A healthy runtime is reported unreachable while it is in
  fact watching. Where no gateway is reachable either, the device then
  orphans and actuates on local thresholds — the two-writer divergence the
  orphan gate exists to prevent, arriving through the mechanism meant to
  avoid it.
- **Too long.** After a supervising runtime dies, the device continues to
  report it reachable for the length of the window, so a dangerous load runs
  without its backstop for that long.

Which dominates depends on the installation and on what the interlock rule
actually does: opening a contactor on overcurrent has a different hazard
profile from an actuation that interrupts a process. **The window is derived
from measured loss and jitter bounds together with the deployment safety
case**, never from an implementation default and never from a general claim
about which failure is worse.

### Golden vectors

The authoritative corpus for this section is
[liveness-at-v-1-vectors-v2.json](liveness-at-v-1-vectors-v2.json), held **here**, beside
this document. Its SHA-256 is
`0967d6fb5740ebb2e29cc2d8113eb60ac7b0337277d2100fce8906b811794cb2`.

Implementing repositories copy it byte-for-byte and pin that digest —
`ori-edge-firmware/test/golden/liveness_at_v_1_vectors_v2.json` and
`ori-runtime/tests/fixtures/firmware_liveness_vectors.json` — and never
generate its expectations from their own behaviour.

**The artifact lives here, not merely its digest, because a digest is not
reviewable.** A CODEOWNER asked to ratify a bare SHA-256 can only confirm that
it is a hexadecimal number; the accept, reject and transport cases it stands
for have to be readable in the change that ratifies them. Holding the file in
the contract repository is also what makes a single-repository change
detectable: two constants coordinated by hand are not a parity mechanism,
because a change made in one implementer leaves the other still matching its
own unchanged constant while the corpora diverge.

`scripts/generate-firmware-liveness-vectors-v2` reproduces this file byte for
byte, beside the corpus of [Runtime Liveness at `v` 2](#runtime-liveness-at-v-2),
so a proposed change can be regenerated and reviewed rather than hand-edited.
The tool is not the authority; this file is.

Its refusals include a signature by the runtime key over the object bytes
alone, one in the command domain, one in the liveness domain with no NUL, and
one by a rogue key, each `signature_invalid`.

Case expectations are authored from the sections above, not recorded from an
implementation. A corpus produced by running a signer certifies whatever that
signer does, including its defects, and cannot detect that the signer is
wrong.

Reject cases carry two fields that make them meaningful:

- `signature_valid` distinguishes a refusal decided *before* the signature is
  checked from one decided *after* it. A binding or freshness refusal is only
  evidence that the device performed that check if the signature was good;
  otherwise the device could refuse the message earlier and the check under
  test stays unproven.
- `verifier_context` carries the device state the case is evaluated against —
  current `boot_id`, accepted `capability_hash`, and
  `last_accepted_runtime_seq` for this boot. The freshness rules are stateful,
  so "refuse a replayed `runtime_seq`" has no meaning without it. A verifier
  that accepted replays indefinitely would otherwise satisfy every byte-level
  vector.

`transport_reject_cases` are refused on how the message arrived rather than on
its bytes, and are byte-identical to messages the device must accept when
delivered live. No content-level case can express them.

The disclosed test seeds are fixtures only and MUST NOT be used outside
deterministic tests.

### Manifest-epoch binding, and the maintenance problem it exposes

Liveness binds to `capability_hash`, so it lapses on a manifest transition
exactly as command authority does.

An earlier draft omitted the field, reasoning that supervision is separable
from command authority. That was wrong on the mechanism, not merely on the
policy: a device reloads the approved runtime key **only while the stored
approval hash equals its current manifest hash**, and otherwise runs with an
all-zero key that no signature matches. After capability drift there is no
active runtime key, so liveness signed with the old one would not verify
regardless of which fields it carried. Omitting the hash would have
described a behaviour the device cannot exhibit.

A supervision authority that genuinely outlives capability changes would
need its own provisioned key and role. That is a larger change than a field,
and it is not proposed here.

**This makes a real lifecycle problem visible rather than solving it.** A
firmware update or capability change now lapses supervision, so the device
reports the runtime unreachable — and where no gateway is reachable, orphans
and its interlock may actuate during a maintenance window. The fix
belongs in the lifecycle — an explicit safe-maintenance mode, or a
deliberate supervision handoff — not in weakening the binding, which would
hide the problem while leaving the hazard.

**This version decides how liveness may be used until that lifecycle
exists.**

- **A device may derive `runtime_reachable` from accepted liveness,** as
  [Expiry](#expiry-and-what-a-device-does-before-it-hears-anything) states,
  and gate its Local Interlock on the orphan condition it yields.
- **A capability transition ends supervision at once.** A device whose
  accepted manifest changes holds no active runtime key from that moment, as
  above, and a device whose approved runtime key changes holds a key nothing
  has yet been heard from. Either way, it MUST NOT report `runtime_reachable`
  from the moment of the change until it accepts liveness under its new
  manifest and key, and the boot grace window does not apply to that period.
  It reports the runtime unreachable at once, not when its expiry window
  would have lapsed. It is orphaned if no gateway is reachable
  either. This version defines no maintenance mode, so nothing suspends that
  across a transition.
- **A transition lasts until the device next accepts liveness under its new
  manifest and key.** After a manifest change, the new manifest must reach the
  runtime, an operator must promote it, a new approval must be installed, and
  fresh telemetry must arrive under it before any liveness can verify. After a
  rotation of the runtime command key alone, the manifest need not change; the
  device holds the new key and accepts liveness only once a runtime signs with
  it. A person's act sits in either chain, so this version bounds neither.
- **An installation that gates an unattended physical load on liveness MUST NOT
  perform a capability transition** (a manifest change, a firmware update that
  changes the manifest, or a change of the approved runtime key) unless, for the
  whole transition, a person is present at the load or the load is held in its
  safe state by means outside the device. A reachable gateway does not count: a
  gateway holds no device command key, so during a transition, while no runtime
  key can be heard from, a device that is not orphaned because a gateway is
  reachable has its backstop suppressed and no writer. This is a deployment
  obligation. No device or runtime can enforce it, and this version does not
  claim either does.
- **The runtime has no obligation here.** The device's own rule above ends
  supervision at the moment of the change, and it depends neither on the
  runtime discovering the transition nor on the runtime stopping publication.
  After a manifest change, liveness signed for the old manifest no longer
  verifies, and after a key rotation, liveness signed with the old key no
  longer verifies, whatever the runtime goes on publishing. A transition the
  device makes itself, such as a firmware update, reaches the runtime only
  afterwards. One the runtime's own side starts, such as a new provisioning
  approval or a configuration change, is started by a person, and that person
  is the one the deployment obligation above binds.
- **Other lapses are the orphan gate working.** A runtime that deliberately
  releases a device, a revoked device, and a runtime or broker outage longer
  than the supervision window each end supervision too, and with no gateway
  reachable each orphans the device. That is the intended direction of
  failure, and the deployment obligation above does not cover them.

**Limits and later versions.**

- An explicit safe-maintenance mode, entered before a transition and ended by
  re-supervision, cancellation or timeout, with signed lifecycle evidence, is
  the later answer
  ([ori-specs#49](https://github.com/ori-platform/ori-specs/issues/49)). So is
  a supervision authority that outlives capability changes. Neither is in this
  version, which therefore keeps a lapse of supervision at every transition.
- This version defines no way to clear a latched Local Interlock trip other
  than a reboot. A device that gates its interlock on liveness orphans more
  often than one that gates it on broker connectivity, so a latched trip
  becomes a more common path. How a latch clears is outside this contract,
  and a device decides it before it gates an interlock on liveness.
- A device that reconnects on a persistent session can accept liveness that
  was queued before its runtime stopped, and each message it accepts restarts
  its expiry window. `runtime_reachable` then stays true until one expiry
  window after the last queued message it accepts. Nothing in this version
  bounds how queued messages are spaced or how long a backlog takes to drain,
  so it gives no fixed bound from reconnecting, or from the runtime's death,
  to the device treating the runtime as unreachable, beyond the bound
  [Runtime Obligations](#runtime-obligations) gives for a live session.
- A device that derives `runtime_reachable` from liveness can treat the
  runtime as unreachable while commands from that runtime still arrive:
  liveness and commands are separate messages, so liveness can fail to reach
  the device while commands do, and a command carries no age limit, so one
  issued before the lapse can arrive after it. The Local Interlock and a
  runtime command can then both act on one load. This version does not
  arbitrate between them. A later version would have a command name the
  liveness epoch it was issued under, admitted only while that epoch is the
  one the device holds valid, and would take any distinction between
  protective and hazardous commands from commissioned circuit behaviour,
  never from a command's name.
- This contract does not define how a device decides `gateway_reachable`.
  The orphan condition depends on it, so a device that gates its interlock on
  liveness defines it before it does.

## Runtime Liveness at `v` 2

### Wire format

```json
{"liveness":{"boot_id":41,"capability_hash":"sha256:<64-lowercase-hex>","device_id":"ori-fw-7c9f2b3a","nonce":"<32-lowercase-hex>","runtime_seq":9007,"v":2},"signature":"ed25519:<base64-64-byte-signature>"}
```

Rules:

- Field order is exactly as shown: `boot_id`, `capability_hash`,
  `device_id`, `nonce`, `runtime_seq`, `v`, the lexicographic canonical
  order.
- `nonce` is a JSON string of exactly 32 characters, each one of `0`-`9` or
  `a`-`f`. A string of any other length, one containing an uppercase letter
  or any other character, `null`, and any other JSON type are `malformed`.
- `v` is `2`.
- `boot_id`, `capability_hash`, `device_id` and `runtime_seq`, the signature
  and its encoding, and the rule that any deviation is `malformed` and is
  refused before the signature is verified, are those of
  [Runtime Liveness](#wire-format), unchanged.

A liveness object at `"v":1` has the grammar of [Wire format](#wire-format) exactly, and a `nonce` in it is
an extra field and `malformed`. A `v` other than the integer `1` or `2` is
`malformed`.

### Acceptance

A device accepts a liveness message at either `v` only if it was not
delivered retained, and then in the order of
[Freshness without a device clock](#freshness-without-a-device-clock): it parses; `device_id` matches;
the signature verifies against the provisioned runtime key; `boot_id` equals
the device's current boot; `capability_hash` equals the device's accepted
manifest hash; and `runtime_seq` strictly exceeds the last value accepted for
this boot. One high-water mark serves both versions: a `v` `2` message whose
`runtime_seq` does not exceed that of an accepted `v` `1` message is refused,
and the reverse. A refused message changes nothing, including the held nonce
below.

Each check that fails names the refusal, with the same reason names the
[`v` `1` liveness corpus](#golden-vectors) uses. The checks are made in this order, and a message that
fails more than one is refused for the first that fails:

| Order | Check | Reason |
| --- | --- | --- |
| 1 | it was not delivered retained | `retained` |
| 2 | it parses under the grammar of its `v` | `malformed` |
| 3 | `device_id` matches | `device_mismatch` |
| 4 | the signature verifies | `signature_invalid` |
| 5 | `boot_id` equals the current boot | `boot_mismatch` |
| 6 | `capability_hash` equals the accepted manifest hash | `capability_hash_mismatch` |
| 7 | `runtime_seq` exceeds the last accepted value | `seq_not_increasing` |

Delivery is decided before content, so a retained delivery is refused as
`retained` whatever its bytes. Checks 2 to 7 are those of
[Runtime Liveness](#runtime-liveness), in its order, and apply to a `v` `1` message unchanged. A refusal carries no verdict back to
the runtime.

### The held nonce

A device holds at most one liveness nonce, in memory only, and never persists
it. Holding none, which a reading envelope signs as `null`, means the device
has no usable freshness reference. It does not mean that no runtime was
watching.

- Accepting a `v` `2` message sets the held nonce to that message's `nonce`.
- Accepting a `v` `1` message clears it.
- Every boot starts with none held.
- A change of the device's accepted manifest, or of its active runtime command
  key, clears it.
- The expiry of the liveness expiry window ([Timing](#timing)) clears it: once the device treats
  the runtime as unreachable, it holds no nonce until it accepts a `v` `2`
  message again.

Clearing the held nonce, for any of these reasons, never alters a nonce
already captured for a measurement in progress, or one already signed into an
envelope, buffered or not.

What the device does with the held nonce is defined in
[firmware-telemetry/v2.md](../firmware-telemetry/v2.md#how-old-a-reading-is):
it signs it into each reading envelope it measures afterwards.

### The runtime's nonce

- The runtime generates each `nonce` from a cryptographically secure random
  source, 128 bits, fresh for every liveness message it signs. It never
  derives one from `runtime_seq`, from its state store, from a clock or from
  another message, and never reuses one, including for a message it signs
  again under a `runtime_seq` it has signed before.
- Before using a nonce, the runtime checks it against the nonces its live
  table holds (firmware-telemetry/v2, How Old A Reading Is), and generates
  another on a collision.
- The runtime records the nonce in that table under the signing-start rule
  of [firmware-telemetry/v2.md](../firmware-telemetry/v2.md#the-bound).
- The supervision window, the publication interval and every other
  obligation on publishing liveness in
  [Runtime Obligations](#runtime-obligations) apply to `v` `2` unchanged.

**Why a nonce and not `runtime_seq`.** `runtime_seq` is persisted across
runtime restarts, so restoring an older state store reissues a value the
runtime has already signed. For the same boot and manifest, the reissued
message is byte-identical to the earlier one, signature included. A bound
keyed by `runtime_seq`, or by any digest of the message or its signature,
would then date a reading taken under the first message by the time of the
second. A fresh random nonce does not repeat across a restore. `runtime_seq`
stays because the device still needs it to refuse replays without persisting
anything, and the nonce gives no order.

### Which `v` the runtime publishes

The runtime publishes one liveness message to each supervised device in every
publication interval, at `v` `2`, and never publishes liveness at `v` `1`.

- **The declaration is the signal.** A device whose accepted manifest declares
  `runtime_key_domains`
  ([firmware-telemetry/v2.md](../firmware-telemetry/v2.md#runtime-key-domains))
  accepts liveness at `v` `2`. A device whose manifest does not declare it is
  sent no liveness message at either `v`, under
  [Signing Domains](#signing-domains). So every device the runtime may
  supervise has told it, in signed configuration its provisioning approval
  accepted, that it accepts `v` `2`.
- **No inferred support.** The runtime MUST NOT infer that a device accepts
  `v` `2` from a timeout, from the absence of a refusal, or from anything else
  its liveness traffic shows. A refused liveness message carries no verdict
  back, so silence proves nothing. The declaration is the only signal.
- **No substitute at `v` `1`.** A failure to generate, sign or publish an
  interval's message leaves that interval with no message. The runtime MUST
  NOT send a `v` `1` message in its place. This gives up a second, independent
  chance per interval to refresh supervision: a `v` `1` message published beside
  the `v` `2` one could survive a failed nonce draw, a transient signing or
  publish failure of the `v` `2` message, or the loss of that message in
  delivery. That cost is accepted. The expiry window is sized for one message
  per interval and tolerates isolated loss ([Timing](#timing)); a failure that
  outlasts it is one the device should learn of by silence, not have masked by
  a message that clears its held nonce. A clock the runtime cannot read costs
  only the table entry, under the no-clock rule of
  [firmware-telemetry/v2.md](../firmware-telemetry/v2.md#the-bound), and the
  message is still published. What a failed signing leaves in the liveness
  table is the signing-start rule of
  [firmware-telemetry/v2.md](../firmware-telemetry/v2.md#the-bound). A runtime
  that cannot publish for longer than the expiry window leaves the device
  treating it as unreachable, and orphaned if no gateway is reachable either.
- **Conservative delivery.** When a message is lost, the device holds the
  nonce of the last message it accepted, or none. When messages arrive out of
  order, a late one is refused as `seq_not_increasing` and changes nothing.
  Lost or reordered messages may leave a reading with no bound, and never give
  a tighter bound than the truth.
- **Liveness never takes command capacity.** A device that reconnects on a
  persistent session can receive several queued liveness messages at once,
  beside its queued commands and its retained provisioning approval. A device
  governed by this contract MUST NOT let liveness messages, however many
  arrive together, take inbound capacity that a command or provisioning
  message would otherwise have, for example by giving liveness a separate
  inbound lane, or by reserving depth for commands and provisioning that
  liveness cannot use. It may drop liveness messages instead. A dropped
  liveness message loses a bound or a refresh of supervision. Liveness dropped
  for longer than the expiry window leaves the device treating the runtime as
  unreachable, with the consequences
  [Runtime Liveness](#expiry-and-what-a-device-does-before-it-hears-anything)
  gives, which with no reachable gateway include orphaning. That is the
  intended direction of failure: toward local protection, never toward a stale
  claim of supervision. A device SHOULD also keep inbound capacity for
  liveness that commands and provisioning cannot take, so that command load,
  including a flood of commands it refuses, cannot by itself starve
  supervision. This version does not require a clean session.
- **Authority is unchanged.** Supervision comes from accepted liveness at
  either `v`, exactly as at `v` `1`, and nothing about what licenses an action
  changes. Whether the device holds a nonce governs age evidence
  only, never supervision or authority.

A device still accepts liveness at `v` `1` under [Acceptance](#acceptance),
with one high-water mark across both versions. A runtime that adopted this
version before this section signs `v` `1` messages in the liveness domain, and
a device that carries `runtime_key_domains` accepts them and clears its held nonce.

**Why no rollout pair and no fleet-wide cut-over.** A device that carries
`runtime_key_domains` accepts `v` `2`, and a device that does not is sent no
liveness message, so this version admits no device that accepts only `v`
`1` and could be supervised. Publishing `v` `1` beside `v` `2` would supervise no
one, would clear the held nonce between the two messages, and would double the
liveness traffic a constrained device's inbound lane takes. A fleet-wide
cut-over would decide by date what the manifest already states per device.

**Limits.** A device whose manifest carries `runtime_key_domains` but whose verifier
accepts only `v` `1` misstates its capability. It refuses every message as
`malformed`, reports the runtime unreachable once its expiry window lapses,
and orphans when no gateway is reachable. The runtime cannot detect this, and
this version owes such a device nothing more: its own signed manifest is
wrong, and it fails as lost supervision does. The producer test of
[firmware-telemetry/v2.md](../firmware-telemetry/v2.md#required-implementation-artifacts)
checks that a device's declaration and its verifier agree.

### Golden vectors

The authoritative corpus for this section is
[liveness-vectors-v2.json](liveness-vectors-v2.json), held here beside this
document. Its SHA-256 is
`456efbd957fc53ebc71087593d8ed96f7312a5a3b8cb3ed419d21944e3d7b98e`.
Implementing repositories copy it byte for byte, pin that digest, and never
generate its expectations from their own behaviour.

Each case is a liveness message evaluated against its `verifier_context`: the
device's current `boot_id`, accepted `capability_hash`, the last
`runtime_seq` accepted in this boot, and the nonce held, or `null`. Each case
gives the nonce held afterwards. It holds `v` `2` messages that set the held
nonce, including ones at the smallest and largest `boot_id`, one at the
largest `runtime_seq`, and one whose nonce is all zeros, which the grammar admits because a device does not judge randomness;
`v` `1` messages that clear it; and refusals, each refused for one declared
reason and leaving the held nonce unchanged:

- `v` `2` without `nonce`, and `v` `1` with one;
- a `nonce` with an uppercase letter, a character outside the hexadecimal
  digits, 31 or 33 characters, the empty string, `null`, an integer, or a
  boolean;
- a `v` `2` message with an extra key;
- `nonce` out of canonical order, and an unsupported `v`;
- an accepted `v` `2` message replayed byte for byte, a regressing
  `runtime_seq`, the accepted `runtime_seq` reissued under a fresh nonce, a `v` `2` message at the
  `runtime_seq` of an accepted `v` `1` message, and a `v` `1` message at the
  `runtime_seq` of an accepted `v` `2` message;
- a wrong device, a wrong boot, a manifest mismatch, and a rogue key;
- a signature by the runtime key over the object bytes alone, in the command
  domain, and in the liveness domain with no NUL;
- a message delivered retained.

Each of those breaks exactly one check. The corpus also holds precedence
cases, each breaking two adjacent checks in the order above and refused for
the earlier: retained and malformed, malformed and a wrong device, a wrong
device and a rogue key, a rogue key and a wrong boot, a wrong boot and a
manifest mismatch, and a manifest mismatch and a replayed `runtime_seq`.
Every refusal decided after the signature carries a valid signature.

The corpus also holds delivery sequences that mix the two versions, as a
device sees them from a runtime that signs `v` `1` messages beside `v` `2`
ones, which [Which `v` the runtime publishes](#which-v-the-runtime-publishes)
no longer permits but a runtime that adopted this version before that section
does. Each is a run of
deliveries to one device, from its `verifier_context`, by a device that
accepts only `v` `1` or one that accepts both, each delivery giving its
reason, or none when accepted, and the held nonce and last accepted
`runtime_seq` after it. Their names begin `rollout_`. They cover:

- a verifier of the `v` `1` grammar alone, which accepts every `v` `1`
  message and holds no nonce; no device that carries `runtime_key_domains`
  may be one;
- a device that accepts both, which ends holding the last `v` `2` nonce, and
  holds none between a `v` `1` message and the `v` `2` message after it;
- a `v` `2` message delivered before the `v` `1` message signed ahead of it,
  where the late `v` `1` message is refused and the device keeps the `v` `2`
  nonce;
- either message of such a pair missing.

`scripts/generate-firmware-liveness-vectors-v2` reproduces the file byte for
byte. It signs with OpenSSL through `cryptography`, under the disclosed
runtime and rogue test seeds of the `v` `1` liveness corpus. Its nonces are fixed
fixture values, not random ones.
`scripts/check-firmware-liveness-vectors-v2` shares no code with it: it
recomputes the object and wire bytes, verifies every signature with its own
curve arithmetic, applies the grammar and the acceptance order above, and
confirms that each case is accepted with the declared held nonce and each
refusal is refused for its declared reason and for no other.

The disclosed test seeds are fixtures only and MUST NOT be used outside
deterministic tests.

## Runtime Obligations

v1's obligations hold, with these replacements and additions:

- v1's first obligation reads, in this version: maintain one strictly
  increasing `cmd_seq` per target device, continuing across command-key
  rotation, and never reuse a value.
- Record every issued command and every fault-event rejection. A
  `rate_limited` fault is recorded as a refusal that actuated nothing. A
  `bad_signature` or `replayed` fault from a device remains a security signal,
  not noise.
- Never reissue a command automatically, as
  [Unresolved Commands](#unresolved-commands) and
  [Rate-Limited Refusal](#rate-limited-refusal) state.
- Sign every command and every liveness message in its domain of
  [Signing Domains](#signing-domains), only for a device whose accepted
  manifest carries `runtime_key_domains`, and sign nothing else with the runtime
  command key. For a device whose manifest does not carry it, sign nothing, and treat its `runtime_commanded` actions as unavailable from the
  moment the manifest is accepted, or, for a manifest held before adopting this
  version, from the runtime's first start under it.
- Generate, check and record each liveness nonce as
  [Runtime Liveness at `v` 2](#runtime-liveness-at-v-2) states.
- Publish runtime liveness per device at the interval above, at `v` `2`
  alone, as [Which `v` the runtime publishes](#which-v-the-runtime-publishes)
  states, on the device-scoped topic, unretained, carrying the device's current `boot_id`
  and accepted `capability_hash` as last seen in its telemetry.
- Observe the supervision window above: stop publishing for a device the
  runtime has not heard from within it. This is the rule that makes liveness
  mean supervision rather than mere process existence, and the device cannot
  check it, so it is carried by tests on both sides of the boundary:
  - **Runtime-side:** the runtime stops publishing liveness for a device no
    later than one supervision window after the last accepted authenticated
    telemetry from it. That is a statement about the publisher and is all a
    runtime test can establish.
  - **Integration/HIL:** with the broker still connected **and no gateway
    reachable**, a device whose runtime has stopped receiving from it
    becomes orphaned. The gateway condition is not incidental — with a
    gateway reachable the same device must stay unorphaned, and both cases
    belong in the evidence. Note the delay compounds — up to one supervision
    window plus one expiry window, 105 s at the provisional values — and a
    deployment safety case must size against that total, not against either
    window alone.
- Maintain one strictly increasing `runtime_seq` per device, separate from
  `cmd_seq`, and **persist it across runtime restarts**. A device holds the
  last accepted value for its current boot, so a runtime that restarts with
  an in-memory counter reset to zero has every subsequent message rejected
  and cannot recover while that device stays booted — the device reports a
  healthy runtime unreachable, and keeps doing so. The same per-device
  registry row that carries `cmd_seq` is the natural home, and the
  reservation-ceiling pattern the device uses for its own counters bounds
  the write rate.
- If a runtime loses that state entirely, it MUST NOT attempt to bypass the
  check. The failure is safe by construction: affected devices report the
  runtime unreachable, and orphan if no gateway is reachable either.
  **Recovery requires the device to enter a new boot** — nothing else in
  this contract resets the device's boot-local high-water mark.
  Re-provisioning does not: it changes neither `boot_id` nor the accepted
  sequence, so it is not a recovery path and must not be described as one.
  Making it one would need a distinct signed liveness epoch with a
  replay-safe transition, because otherwise every message already signed for
  the same boot, key and manifest becomes valid again. That is a future
  contract change, not an implementation detail.
- **Stop publishing liveness for a device the runtime is deliberately
  releasing** — during maintenance, decommissioning, or when handing
  authority elsewhere. Silence is the supported way to tell a device it is
  on its own; there is no "goodbye" message, because a message asserting
  absence could not be trusted from an absent party.

## Required Implementation Artifacts

In addition to v1's, and in place of its shared golden command vector set:

- **Device-side:** a command that passes every acceptance check and that the
  rate policy refuses yields `rate_limited`, writes no output, spends its
  `cmd_seq` (the same bytes delivered again yield `replayed`), and is signed as
  a `command_rejected` fault at `v` `2`. A command that fails an earlier check
  yields that check's verdict even while the policy would also refuse it. The
  Local Interlock acts while the policy would refuse a commanded action on the
  same channel. A `relay_open` is admitted at once in every state in which the
  policy refuses a `relay_close`, including any period after boot in which it
  refuses every close.
- **Runtime-side:** a `rate_limited` fault is recorded as a refusal and never
  as an execution; no path reissues a command automatically, after
  `rate_limited` or after any unresolved command; a `rate_limited` detail in a
  fault whose `v` is `1` is refused. A runtime that drives a commissioned zone
  through firmware commands also tests that a latched Tier D trip keeps making
  fresh `open_protected_circuit` attempts, each under a new `cmd_seq`, while
  every other command is published once.
- The fault corpus of [firmware-telemetry/v2.md](../firmware-telemetry/v2.md),
  which carries the signed `rate_limited` refusal.
- **Device-side:** the corpora of
  [ed25519-key-admission/v1](../ed25519-key-admission/v1.md) and
  [ed25519-verification/v1](../ed25519-verification/v1.md) driven through the
  verifier that checks commands, approvals and liveness, on the target as well
  as the host, accepting every accepted case and refusing every refused one.
- **Device-side:** the liveness corpus above driven through the device's real
  liveness entry point, accepting every case with its declared held nonce and
  refusing every refusal for its declared reason with the held nonce
  unchanged; tests that a boot, a manifest change, a runtime command key
  change and the expiry of the liveness expiry window each leave no nonce
  held; a test that an expiry during a measurement leaves that
  measurement's captured nonce unchanged; and a test, run in three orders,
  that commands and provisioning messages up to the capacity the device's
  implementation documents for them, delivered with a burst of liveness
  messages larger than any capacity the device has for liveness, are all
  accepted, and only liveness messages are dropped. The orders are the
  liveness burst first and then the commands and provisioning messages; the
  commands and provisioning messages first and then the burst; and the two
  interleaved.
- **Runtime-side:**
  - the signer reproduces the object and wire bytes of each accepted `v` `2`
    case from that case's fields and nonce;
  - two messages signed in sequence, including two under the same
    `runtime_seq`, never carry the same nonce;
  - a generated nonce that collides with one the live table holds is replaced
    before signing, tested with an injected source;
  - the signing start is read before signing, and a message whose signing
    start could not be read is recorded as no entry.
- **Runtime-side:** the command corpus of [Command vectors](#command-vectors)
  driven through the signer, which reproduces each accepted case's object and
  wire bytes and, for the object of its own purpose, each cross-purpose
  signature; and the liveness signer reproducing the accepted cases of both
  liveness corpora.
- **Device-side:** the command corpus driven through the device's real command
  entry point, accepting every case and refusing every refusal as
  `bad_signature` with nothing persisted, and the signature refusals of both
  liveness corpora refused as `signature_invalid`.
- A shared golden provisioning-approval vector set once the runtime signing
  side lands. It pins the entire signed object and wire message byte-for-byte
  across the runtime signer and device verifier, and covers both development
  and sealed-flash postures.
- **Runtime liveness:**
  - Shared byte-exact liveness golden vectors, pinning the signed object and
    the wire message across the runtime signer and the device verifier.
  - Runtime-side signer tests against the fixed grammar, with negative cases.
  - Device-side parser and verifier tests: wrong device, wrong `boot_id`,
    manifest-epoch mismatch, rogue key, malformed signature, non-canonical
    integers, extra or reordered fields, an unsupported `v`, integers above
    their maximums, and identifiers or capability hashes outside their
    grammars.
  - Sequence semantics: a repeated or regressing `runtime_seq` is refused; a
    gap is accepted, because loss is expected and only monotonicity matters.
    The counter is per-boot and is never persisted, so a low `runtime_seq` is
    accepted after a reboot while a high one captured from the previous boot
    is refused on `boot_id` — which is what removes the flash write per
    message.
  - Ingress: a liveness message delivered **retained** is refused even though
    its bytes are those of a message the device must accept when delivered
    live.
  - Reachability outcomes, keeping `runtime_reachable` and `orphaned`
    distinct: fresh liveness yields `runtime_reachable == true`; an expired
    window **while MQTT remains connected** yields `runtime_reachable ==
    false`; nothing ever received yields the boot-grace behaviour and then
    `runtime_reachable == false`; a change of the accepted manifest or of the
    approved runtime key yields `runtime_reachable == false` at once, even
    with liveness accepted inside the expiry window; and queued liveness
    accepted after a reconnect, delivered both in a burst and staggered across
    the expiry window, keeps `runtime_reachable == true` until one expiry
    window after the last message accepted, and no longer.
  - The gate itself, which liveness must never bypass: no liveness after
    grace **and no reachable gateway** yields `orphaned == true`; no
    liveness after grace **but a reachable gateway** yields
    `orphaned == false`.
  - Runtime restart with durable sequence state: publication resumes and the
    device keeps accepting, with no device reboot.
  - Supervision: the runtime stops publishing within one supervision window
    of the last accepted telemetry from a device.
  - HIL evidence for the broker-alive/runtime-dead case, which is the whole
    reason the signal exists.
