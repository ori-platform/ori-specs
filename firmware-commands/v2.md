# Firmware Commands Contract v2

> Status: maturity `draft`; compatibility `amendable`; adoption: producer
> (runtime) `implemented-unreleased`, `unassessed`; proof: end-to-end `none`,
> HIL `none`, production `none`. Record:
> [status/firmware-commands/v2.json](../status/firmware-commands/v2.json).

This version exists for one verdict and the runtime obligation it forces. A
device whose release-owned actuation rate policy refuses a command reports
that refusal as `rate_limited`, and a runtime never reissues a command on its
own, so that a refusal it did not hear cannot become an actuation it did not
time. It also adds a nonce to runtime liveness, so that the runtime that
signed a liveness message can bound, from above and on its own clock, how
long ago a device began the transaction behind a reading it signed after
accepting it. The bound dates that transaction, not the measured quantity,
and is defined by
[firmware-telemetry/v2.md](../firmware-telemetry/v2.md#how-old-a-reading-is).

## What changed from v1

Four changes, all breaking:

- **A verdict is added.** `rate_limited` joins the verdict table, and it
  answers `relay_close` only: no rate policy refuses or delays `relay_open`.
  A v1 device never returns it, and a v1 consumer of `command_rejected` faults refuses it,
  because [firmware-telemetry/v1.md](../firmware-telemetry/v1.md) holds that
  detail to a closed set.
- **A lost command is never reissued automatically.** v1 requires a runtime to
  treat a command that produced neither a relay action nor a `command_rejected`
  fault as lost and to retry it with a fresh `cmd_seq`, and requires the same
  after a device crash between persist and actuate. This version forbids that
  retry. See [Unresolved Commands](#unresolved-commands).
- **Keys and signatures follow the shared Ed25519 contracts.** The device
  admits the provisioning authority key and the runtime command key an
  approval carries under
  [ed25519-key-admission/v1](../ed25519-key-admission/v1.md), and verifies the
  command, the provisioning approval and the liveness message under
  [ed25519-verification/v1](../ed25519-verification/v1.md). v1 named neither
  rule, and a v1 device whose verifier takes the cofactored equation or
  decodes R loosely accepts signatures this version refuses. None of them is
  one a runtime produces by signing under RFC 8032. A command whose signature
  that contract refuses, under any of its clauses, is `bad_signature`; a
  liveness message it refuses is refused silently, as v1 refuses any liveness
  message, and carries no verdict back; an approval it refuses, or one
  carrying a key that admission refuses, registers nothing.
- **A liveness message may carry a nonce.** A liveness object at `"v":2`
  carries `nonce`, 128 bits the runtime generates fresh for that message. A
  device accepts liveness at `v` `1` and at `v` `2`, holds the nonce of the
  last one it accepted, and signs it into each reading it measures afterwards.
  A v1 device refuses every `v` `2` liveness message as `malformed`, so it
  silently loses supervision from a runtime that publishes only `v` `2`. See
  [Runtime Liveness at `v` 2](#runtime-liveness-at-v-2).

Everything else is [v1](v1.md)'s, as its text stands at ori-specs `d979402`,
incorporated unchanged: the trust model except for the key admission and
signature verification above, the wire format, the action
vocabulary, the MQTT transport binding, the provisioning approval, runtime
liveness, the runtime obligations and the required artifacts, each except
where this document replaces a rule by name.
That text includes sections v1 gained after its freeze, runtime liveness among
them, whose classification is still owed by v1's baseline audit; this version
carries them as its own text, whatever that audit decides for v1.

**Runtime liveness is not an Open Gap in this version.** v1's text marks it
one, and that status stands in v1, which is frozen. Here it is a defined
section with a runtime signer and a device verifier implemented against it:
the runtime signs and publishes liveness for each supervised device, and the
reference device firmware verifies it and records whether the runtime is
reachable. That is implementation, not proof. No end-to-end or HIL evidence
shows a device losing or regaining supervision through it, and no device
image yet gates a Local Interlock on it. A claim that liveness protects
anything needs that evidence first.

**The command bytes do not change.** The command object keeps `"v":1`, because
its `v` names the command grammar and this version does not change the
grammar. A command a v2 runtime signs is byte-identical to the v1 command for
the same fields. A signature RFC 8032 produces under an admitted key verifies
on a v1 device and on a v2 device alike, and the command is then held to every
other check v1 makes: device binding, manifest, freshness and authority. What
differs is that a v2 device refuses the signatures
[ed25519-verification/v1](../ed25519-verification/v1.md) refuses, which no
honest signer makes, that it may decline a verified command as
`rate_limited`, and what a v2 runtime may do afterwards. The provisioning
approval is likewise unchanged and keeps its `"v":1`. The liveness message
keeps v1's grammar at `"v":1` and gains a second grammar at `"v":2`.

A device reports v2 verdicts in fault objects of
[firmware-telemetry/v2.md](../firmware-telemetry/v2.md), whose `v` is `2`. A
device MUST NOT report `rate_limited` in a fault object whose `v` is `1`.

## Error Semantics

This table replaces v1's:

| Verdict | Meaning |
| --- | --- |
| `malformed` | The message violates the fixed grammar. |
| `wrong_device` | `device_id` names another device. A command signed for one device must never actuate another. |
| `bad_signature` | Signature verification against the provisioned runtime key failed. |
| `replayed` | `cmd_seq` does not strictly exceed the persisted high-water mark. |
| `capability_mismatch` | The command's `capability_hash` does not equal the device's accepted manifest hash. Consumes the sequence. |
| `unknown_action` | The `(action, channel)` pair is not in the accepted manifest with `runtime_commanded` authority. Consumes the sequence. |
| `rate_limited` | The command was verified, fresh and authorised, and the device's release-owned actuation rate policy refused it. Consumes the sequence. Nothing was actuated. |
| `storage_failure` | The high-water mark could not be read or persisted; nothing was actuated and nothing was consumed. |

Gaps in `cmd_seq` are valid and regressions and repeats are replays, as in v1.
A rejected command actuates nothing. Verdicts after the freshness check
(`capability_mismatch`, `unknown_action`, `rate_limited`) consume the sequence,
so the rejected instruction can never be replayed. Verdicts before it
(`malformed`, `wrong_device`, `bad_signature`, `replayed`) persist nothing.

## Rate-Limited Refusal

**It is decided last.** A device applies its rate policy only to a command that
has passed every acceptance check in v1's trust model, in v1's order: grammar,
device binding, signature, freshness, capability hash, and `runtime_commanded`
authority for the `(action, channel)` pair. A command refused by any of those
carries that verdict, never `rate_limited`. A `rate_limited` fault is
therefore evidence that the command was genuine, current and permitted, and
that the device declined to act on it at that moment.

**It spends the command.** The high-water mark was persisted when freshness
passed, so the same bytes delivered later are `replayed`. A refused command
cannot be held and actuated once the policy would admit it.

**It actuates nothing, and it is never execution.** The device writes no
output for a refused command, records no operation for it in the policy's own
history, and reports no relay action. A consumer MUST NOT record a
`rate_limited` command as executed or applied, and MUST NOT count it toward
anything that counts executions. Where the command was the dispatch of an
approved Tier C action, the approval
[tier-c-approval/v1.md](../tier-c-approval/v1.md) committed before dispatch
remains as committed, and the refusal never revokes or rewrites it. The
refusal is signed evidence that the command did not execute; it does not
reconcile the dispatch. The dispatch's record follows tier-c-approval/v1
(`dispatch_outcome_unknown` or `dispatch_not_proven`), and only that
contract's two forms of reconciliation resolve it. Whether such a fault may
serve as commissioned feedback for a zone, or as an executor's own result,
belongs to the specification that admits firmware-backed actuators into an
in-force safety zone, which [runtime-health/v3.md](../runtime-health/v3.md)
requires before any may.

**It is final.** A runtime MUST NOT reissue a `rate_limited` command
automatically, under any `cmd_seq`. Reissuing is a new decision, made by the
authority that issued the first command, and it is signed as a new command
under a fresh `cmd_seq`.

**The policy is the release's.** Its intervals, windows and counts are fixed
in the reviewed device release. No command, manifest field, configuration
document or runtime message sets or changes them, and this contract defines
none of them.

**It never refuses an open.** A release's rate policy MUST NOT refuse or delay
`relay_open`, and a device MUST NOT return `rate_limited` for it.
[commissioned-safety-binding/v1.md](../commissioned-safety-binding/v1.md#firmware-command-semantics)
makes `relay_open` the wire spelling of `open_protected_circuit`, the outcome a
Tier D trip commands. A command carries an action and no intent, so a device
cannot tell an `open_protected_circuit` issued under release-owned Tier D
authority from ordinary switching; the only policy that never refuses the
first is one that refuses no open. An open the policy admits MAY still count
toward its history. `rate_limited` therefore answers only `relay_close`.

**It never suppresses safety evaluation.**

- A device's rate policy MUST NOT refuse or delay an action an armed Local
  Interlock rule takes, MUST NOT disarm an armed rule, and MUST NOT run before
  or in place of Local Interlock evaluation. Which rules a device may arm, and
  how it reports a configuration it refuses to arm, are not decided by this
  contract.
- A `rate_limited` fault MUST NOT suppress, defer or alter a runtime's
  autonomous Tier D evaluation. It is evidence about one command, not an input
  to any safety condition.

## Unresolved Commands

This section replaces v1's rule that a lost command is retried, wherever v1
states it: the Trust Model's sentence on a crash between persist and actuate,
and the MQTT Transport Binding's paragraph on ingress loss.

A command for which the runtime has received neither a relay action nor a
`command_rejected` fault is **unresolved**. That covers a command lost in
transport, one dropped at ingress, one lost to a device crash between persist
and actuate, and one the device refused under a verdict whose fault never
arrived.

- A runtime MUST NOT reissue an unresolved command automatically, under the
  same or a fresh `cmd_seq`.
- A runtime MUST NOT record an unresolved command as executed.
- Reissuing is a new decision by the authority that issued the first command,
  signed as a new command under a fresh `cmd_seq`.

This contract does not define when a runtime may conclude that a command is
unresolved, because no rule here depends on it: the rule above holds at every
moment.

**Tier D attempts are not reissues.** Zero automatic reissue applies to
command-delivery recovery. It does not cancel the safety registry's existing
obligation to make fresh `open_protected_circuit` attempts for a latched Tier D
trip. Each attempt requires a new intent identity and fresh command sequence
under the commissioned binding authorized for that attempt by the governing
safety-profile contract. Under safety-profile/v1, that is the binding the trip
latched under; a successor may authorize a durably recorded continuity
adoption.

- [safety-profile/v1.md](../safety-profile/v1.md) governs those attempts: while
  a pair is tripped and its command status is not `command_issued`, the
  consumer keeps attempting on a bounded-backoff schedule with no terminal
  attempt limit, until the driver accepts, a local reset succeeds, or the
  consumer shuts down.
- An attempt is licensed by the latched trip and owned by the safety registry,
  independent of readings, as safety-profile/v1 states. It continues whatever
  became of earlier attempts short of the driver accepting one, including an
  attempt whose fate is still unknown after a restart. It is never a re-send
  of an earlier command's bytes: each attempt is signed as a new command
  under a fresh `cmd_seq`, with a new intent identity.
  safety-profile/v1 does not itself require an intent identity per attempt;
  this version does, for attempts made through firmware commands.
- An accepted command is never reissued merely because its physical effect is
  unverified, and an attempt never actuates through a binding other than the
  one the governing safety-profile contract authorizes for it. Under
  safety-profile/v1 an orphaned trip stays latched and visible and cannot
  actuate.
- Every such attempt is a `relay_open`, which no rate policy refuses or delays.

**Why the bound is zero.** An automatic retry turns a refusal the runtime did
not hear into an actuation at a time no authority chose. A device that refused
a close under its rate policy, and whose fault was lost, admits the same
instruction once its interval has passed, so a runtime that retried would
actuate later than it asked to, on a decision that may no longer hold. Any
bound above zero keeps that path open for as long as the bound allows. The
device's own guarantee, persist before actuate, is unchanged: a lost command
is still lost rather than replayable.

The bound closes the runtime's own path to a late actuation, and only that one.
Freshness is the counter alone, so a command delayed in a broker or at ingress
still arrives with a fresh `cmd_seq` and is admitted when it arrives.

## Runtime Liveness at `v` 2

### Wire format

```json
{"liveness":{"boot_id":41,"capability_hash":"sha256:<64-lowercase-hex>","device_id":"ori-fw-7c9f2b3a","nonce":"<32-lowercase-hex>","runtime_seq":9007,"v":2},"signature":"ed25519:<base64-64-byte-signature>"}
```

Rules:

- Field order is exactly as shown: `boot_id`, `capability_hash`,
  `device_id`, `nonce`, `runtime_seq`, `v`, the lexicographic canonical
  order.
- `nonce` is a JSON string of exactly 32 characters, each one of `0`-`9` or
  `a`-`f`. A string of any other length, one containing an uppercase letter
  or any other character, `null`, and any other JSON type are `malformed`.
- `v` is `2`.
- `boot_id`, `capability_hash`, `device_id` and `runtime_seq`, the signature
  and its encoding, and the rule that any deviation is `malformed` and is
  refused before the signature is verified, are v1's, unchanged.

A liveness object at `"v":1` has v1's grammar exactly, and a `nonce` in it is
an extra field and `malformed`. A `v` other than the integer `1` or `2` is
`malformed`.

### Acceptance

A device accepts a liveness message at either `v` only if it was not
delivered retained, and then in v1's order: it parses; `device_id` matches;
the signature verifies against the provisioned runtime key; `boot_id` equals
the device's current boot; `capability_hash` equals the device's accepted
manifest hash; and `runtime_seq` strictly exceeds the last value accepted for
this boot. One high-water mark serves both versions: a `v` `2` message whose
`runtime_seq` does not exceed that of an accepted `v` `1` message is refused,
and the reverse. A refused message changes nothing, including the held nonce
below.

Each check that fails names the refusal, with the same reason names v1's
liveness corpus uses. The checks are made in this order, and a message that
fails more than one is refused for the first that fails:

| Order | Check | Reason |
| --- | --- | --- |
| 1 | it was not delivered retained | `retained` |
| 2 | it parses under the grammar of its `v` | `malformed` |
| 3 | `device_id` matches | `device_mismatch` |
| 4 | the signature verifies | `signature_invalid` |
| 5 | `boot_id` equals the current boot | `boot_mismatch` |
| 6 | `capability_hash` equals the accepted manifest hash | `capability_hash_mismatch` |
| 7 | `runtime_seq` exceeds the last accepted value | `seq_not_increasing` |

Delivery is decided before content, so a retained delivery is refused as
`retained` whatever its bytes. Checks 2 to 7 are v1's, in v1's order, and
apply to a `v` `1` message unchanged. A refusal carries no verdict back to
the runtime.

### The held nonce

A device holds at most one liveness nonce, in memory only, and never persists
it. Holding none, which a reading envelope signs as `null`, means the device
has no usable freshness reference. It does not mean that no runtime was
watching.

- Accepting a `v` `2` message sets the held nonce to that message's `nonce`.
- Accepting a `v` `1` message clears it.
- Every boot starts with none held.
- A change of the device's accepted manifest, or of its active runtime command
  key, clears it.
- The expiry of v1's liveness expiry window clears it: once the device treats
  the runtime as unreachable, it holds no nonce until it accepts a `v` `2`
  message again.

Clearing the held nonce, for any of these reasons, never alters a nonce
already captured for a measurement in progress, or one already signed into an
envelope, buffered or not.

What the device does with the held nonce is defined in
[firmware-telemetry/v2.md](../firmware-telemetry/v2.md#how-old-a-reading-is):
it signs it into each reading envelope it measures afterwards.

### The runtime's nonce

- The runtime generates each `nonce` from a cryptographically secure random
  source, 128 bits, fresh for every liveness message it signs. It never
  derives one from `runtime_seq`, from its state store, from a clock or from
  another message, and never reuses one, including for a message it signs
  again under a `runtime_seq` it has signed before.
- Before using a nonce, the runtime checks it against the nonces its live
  table holds (firmware-telemetry/v2, How Old A Reading Is), and generates
  another on a collision.
- The runtime records the nonce in that table under the signing-start rule
  of [firmware-telemetry/v2.md](../firmware-telemetry/v2.md#the-bound).
- The supervision window, the publication interval and every other v1
  obligation on publishing liveness apply to `v` `2` unchanged.

**Why a nonce and not `runtime_seq`.** `runtime_seq` is persisted across
runtime restarts, so restoring an older state store reissues a value the
runtime has already signed. For the same boot and manifest, the reissued
message is byte-identical to the earlier one, signature included. A bound
keyed by `runtime_seq`, or by any digest of the message or its signature,
would then date a reading taken under the first message by the time of the
second. A fresh random nonce does not repeat across a restore. `runtime_seq`
stays because the device still needs it to refuse replays without persisting
anything, and the nonce gives no order.

### Publication during rollout

While devices that accept only `v` `1` may still be supervised, the runtime
publishes two liveness messages to each supervised device in every
publication interval: one at `v` `1`, then one at `v` `2`.

- **Distinct, increasing sequences.** It signs the `v` `1` message at a
  `runtime_seq` N and the `v` `2` message at N+1, both from the one durable
  `runtime_seq` allocator, and never uses one `runtime_seq` for both.
- **Independent failure.** A failure to generate, sign or publish the `v` `2`
  message MUST NOT suppress that interval's `v` `1` message. What a failed
  signing leaves in the liveness table is the signing-start rule of
  [firmware-telemetry/v2.md](../firmware-telemetry/v2.md#the-bound).
- **Conservative delivery.** A device that accepts the `v` `1` message clears
  its held nonce, and one that then accepts the `v` `2` message holds its
  nonce. A device that accepts only `v` `1` refuses the `v` `2` message as
  `malformed` and is supervised by the `v` `1` message alone. When the pair
  arrives out of order, the `v` `1` message is refused as
  `seq_not_increasing` and the device keeps the `v` `2` nonce, whose signing
  still precedes everything the device measures after accepting it. When
  either message is lost, the device holds the nonce of the last message it
  accepted, or none. Reordered or missing messages may leave a reading with
  no bound, and never give a tighter bound than the truth. A refused message
  changes neither supervision nor the held nonce.
- **Captured references stand.** Accepting a `v` `1` message never alters a
  nonce already captured for a measurement in progress, or one already
  signed into an envelope, buffered or not.
- **Liveness never takes command capacity.** The pair arrives milliseconds
  apart, and a device that reconnects on a persistent session can receive
  several queued pairs at once, beside its queued commands and its retained
  provisioning approval. A device governed by this contract that accepts both
  versions MUST NOT let liveness messages, however many arrive together, take
  inbound capacity that a command or provisioning message would otherwise
  have, for example by giving liveness a separate inbound lane, or by
  reserving depth for commands and provisioning that liveness cannot use. It
  may drop liveness messages instead. A dropped liveness message loses a bound
  or a refresh of supervision. Liveness dropped for longer than the expiry
  window leaves the device treating the runtime as unreachable, with v1's
  consequences, which with no reachable gateway include orphaning. That is
  the intended direction of failure: toward local protection, never toward a
  stale claim of supervision. A device SHOULD also keep inbound capacity for
  liveness that commands and provisioning cannot take, so that command load,
  including a flood of commands it refuses, cannot by itself starve
  supervision. This version does not require a clean session.
- **No inferred support.** The runtime MUST NOT infer that a device accepts
  `v` `2` from a timeout, from the absence of a refusal, or from anything else
  its liveness traffic shows. A refused liveness message carries no verdict
  back, so silence proves nothing.
- **Authority is unchanged.** Supervision comes from accepted liveness at
  either `v`, exactly as in v1, and nothing about what licenses an action
  changes. Whether a nonce is held governs age evidence only, never
  supervision or authority.

This version does not decide when the runtime may stop publishing `v` `1`.

### Golden vectors

The authoritative corpus for this section is
[liveness-vectors-v2.json](liveness-vectors-v2.json), held here beside this
document. Its SHA-256 is
`26296ed9e2a9e5b2fafff4dd1be3cf0deccef674c148818e9f1205ff805da13d`.
Implementing repositories copy it byte for byte, pin that digest, and never
generate its expectations from their own behaviour.

Each case is a liveness message evaluated against its `verifier_context`: the
device's current `boot_id`, accepted `capability_hash`, the last
`runtime_seq` accepted in this boot, and the nonce held, or `null`. Each case
gives the nonce held afterwards. It holds `v` `2` messages that set the held
nonce, including ones at the smallest and largest `boot_id`, one at the
largest `runtime_seq`, and one whose nonce is all zeros, which the grammar admits because a device does not judge randomness;
`v` `1` messages that clear it; and refusals, each refused for one declared
reason and leaving the held nonce unchanged:

- `v` `2` without `nonce`, and `v` `1` with one;
- a `nonce` with an uppercase letter, a character outside the hexadecimal
  digits, 31 or 33 characters, the empty string, `null`, an integer, or a
  boolean;
- a `v` `2` message with an extra key;
- `nonce` out of canonical order, and an unsupported `v`;
- an accepted `v` `2` message replayed byte for byte, a regressing
  `runtime_seq`, the accepted `runtime_seq` reissued under a fresh nonce, a `v` `2` message at the
  `runtime_seq` of an accepted `v` `1` message, and a `v` `1` message at the
  `runtime_seq` of an accepted `v` `2` message;
- a wrong device, a wrong boot, a manifest mismatch, and a rogue key;
- a message delivered retained.

Each of those breaks exactly one check. The corpus also holds precedence
cases, each breaking two adjacent checks in the order above and refused for
the earlier: retained and malformed, malformed and a wrong device, a wrong
device and a rogue key, a rogue key and a wrong boot, a wrong boot and a
manifest mismatch, and a manifest mismatch and a replayed `runtime_seq`.
Every refusal decided after the signature carries a valid signature.

The corpus also holds rollout sequences under
[Publication during rollout](#publication-during-rollout). Each is a run of
deliveries to one device, from its `verifier_context`, by a device that
accepts only `v` `1` or one that accepts both, each delivery giving its
reason, or none when accepted, and the held nonce and last accepted
`runtime_seq` after it. They cover:

- a device that accepts only `v` `1`, which stays supervised and holds no
  nonce;
- a device that accepts both, which ends holding the last `v` `2` nonce, and
  holds none between an interval's `v` `1` message and its `v` `2` message;
- the pair delivered out of order, where the late `v` `1` message is refused
  and the device keeps the `v` `2` nonce;
- either message of the pair missing.

`scripts/generate-firmware-liveness-vectors-v2` reproduces the file byte for
byte. It signs with OpenSSL through `cryptography`, under the disclosed
runtime and rogue test seeds of v1's liveness corpus. Its nonces are fixed
fixture values, not random ones.
`scripts/check-firmware-liveness-vectors-v2` shares no code with it: it
recomputes the object and wire bytes, verifies every signature with its own
curve arithmetic, applies the grammar and the acceptance order above, and
confirms that each case is accepted with the declared held nonce and each
refusal is refused for its declared reason and for no other.

The disclosed test seeds are fixtures only and MUST NOT be used outside
deterministic tests.

## Runtime Obligations

v1's obligations hold, with these replacements:

- v1's first obligation reads, in this version: maintain one strictly
  increasing `cmd_seq` per target device, continuing across command-key
  rotation, and never reuse a value.
- Record every issued command and every fault-event rejection. A
  `rate_limited` fault is recorded as a refusal that actuated nothing. A
  `bad_signature` or `replayed` fault from a device remains a security signal,
  not noise.
- Never reissue a command automatically, as
  [Unresolved Commands](#unresolved-commands) and
  [Rate-Limited Refusal](#rate-limited-refusal) state.
- Generate, check and record each liveness nonce as
  [Runtime Liveness at `v` 2](#runtime-liveness-at-v-2) states.

## Required Implementation Artifacts

In addition to v1's:

- **Device-side:** a command that passes every acceptance check and that the
  rate policy refuses yields `rate_limited`, writes no output, spends its
  `cmd_seq` (the same bytes delivered again yield `replayed`), and is signed as
  a `command_rejected` fault at `v` `2`. A command that fails an earlier check
  yields that check's verdict even while the policy would also refuse it. The
  Local Interlock acts while the policy would refuse a commanded action on the
  same channel. A `relay_open` is admitted at once in every state in which the
  policy refuses a `relay_close`, including any period after boot in which it
  refuses every close.
- **Runtime-side:** a `rate_limited` fault is recorded as a refusal and never
  as an execution; no path reissues a command automatically, after
  `rate_limited` or after any unresolved command; a `rate_limited` detail in a
  fault whose `v` is `1` is refused. A runtime that drives a commissioned zone
  through firmware commands also tests that a latched Tier D trip keeps making
  fresh `open_protected_circuit` attempts, each under a new `cmd_seq`, while
  every other command is published once.
- The fault corpus of [firmware-telemetry/v2.md](../firmware-telemetry/v2.md),
  which carries the signed `rate_limited` refusal.
- **Device-side:** the corpora of
  [ed25519-key-admission/v1](../ed25519-key-admission/v1.md) and
  [ed25519-verification/v1](../ed25519-verification/v1.md) driven through the
  verifier that checks commands, approvals and liveness, on the target as well
  as the host, accepting every accepted case and refusing every refused one.
- **Device-side:** the liveness corpus above driven through the device's real
  liveness entry point, accepting every case with its declared held nonce and
  refusing every refusal for its declared reason with the held nonce
  unchanged; tests that a boot, a manifest change, a runtime command key
  change and the expiry of the liveness expiry window each leave no nonce
  held; a test that an expiry during a measurement leaves that
  measurement's captured nonce unchanged; and a test, run in three orders,
  that commands and provisioning messages up to the capacity the device's
  implementation documents for them, delivered with a burst of liveness
  messages larger than any capacity the device has for liveness, are all
  accepted, and only liveness messages are dropped. The orders are the
  liveness burst first and then the commands and provisioning messages; the
  commands and provisioning messages first and then the burst; and the two
  interleaved.
- **Runtime-side:**
  - the signer reproduces the object and wire bytes of each accepted `v` `2`
    case from that case's fields and nonce;
  - two messages signed in sequence, including two under the same
    `runtime_seq`, never carry the same nonce;
  - a generated nonce that collides with one the live table holds is replaced
    before signing, tested with an injected source;
  - the signing start is read before signing, and a message whose signing
    start could not be read is recorded as no entry.
