# Runtime Health Socket RPC v4

> Status: maturity `draft`; compatibility `amendable`; adoption: none
> recorded; proof: end-to-end `none`, HIL `none`, production `none`. Record:
> [status/runtime-health/v4.json](../status/runtime-health/v4.json).

Read-only runtime health RPC over a Unix domain socket, for local diagnostics,
the CLI, the installer and the gateway health export.

## What changed from v3

- **Severity is defined.** `status` is always present, `ok`, `degraded` or
  `critical`, and is the maximum over a closed table of conditions.
  `critical` is always present and is derived from `status`. Each condition
  names its reason token, and the snapshot carries `degradation_reasons`.
- **The firmware liveness condition is split** into five conditions, three
  critical and two degraded. The umbrella token stays and decides no severity.
- **Shape.** Every top-level member is always present. Every top-level
  object block carries `state`, except `last_alert_timestamps` and
  `diagnostics`; the arrays `sensors` and `safety_zones` carry none.
  Members outside the contract live only under `diagnostics`. `null` never
  means unknown and never means "does not expire". `device_policy` carries
  `expiry` in place of the int64 sentinel. Every integer is in its row's
  range, by default `0` to 2^53−1.
- **Startup reads `degraded`.** A subsystem that decides severity and is
  still initialising is `starting`, and names `subsystem_starting`; one that
  could not be read names the applicable unknown-state token.
- **A malformed snapshot is reported.** The heartbeat publishes `critical`
  with `health_snapshot_invalid`.
- **Alerts, trips, stale sensors and losses decide severity.**
  `alert_outbox` decides severity; a failed or unverified protective trip is
  critical; a stale sensor, a refused zone activation and a skill hook failure
  are named; a lost record is a persisted incident that keeps its severity
  across restarts until an authenticated operator acknowledges it.
- **Unreadable critical visibility is critical.** A block that can raise a
  critical condition and cannot be read names
  `subsystem_state_unknown_critical`; one that decides only degraded
  conditions keeps `subsystem_state_unknown`.
- **The gateway export is a projection.** The gateway-api `health` export
  carries the [remote health projection](#remote-health-projection), an
  allowlist, not the snapshot. It no longer carries
  `remote_command_lockout.senders`, which the v3 export did.
- **Request framing is exact.** A request is one line, compared as bytes.
  Four requests are accepted; everything else is refused, and bytes after
  the terminating LF are discarded.
- **New blocks:** `commissioning`, `community_skills`, `config_authority`,
  `action_log_records`, `safety_registry`, `firmware_liveness`,
  `firmware_reading_age`, `firmware_controller_profiles`, `skill_hooks`,
  `telemetry_export`, `diagnostics`.
- **New rows:** `sensors[].connection`, `measurement_degraded` and
  `consecutive_refusals`; `alert_outbox.oldest_queued_at_ms` and its Tier D
  and overdue members; `device_policy.policy_held`;
  `safety_registry.trip_verification_deadline_ms`;
  `safety_zones[].trip_age_ms`; `action_log_records.loss_incidents`;
  `evidence.action_records.recovery_failed`; the evidence section flags; the
  evidence rows `courier_answer_faults`, `contributor_links_unresolved`,
  `awaiting_receipt_count` and `oldest_awaiting_receipt_age_ms`.
- **Moved out of the contract:** the firmware MQTT operator socket, the
  safety registry's internals, the community anchor's fault text, sensor
  refusal text, the liveness loop's last error and the telemetry exporter's
  refusal detail. Each may appear under `diagnostics`.

Every v3 row not named above is carried unchanged, except that its `null`
"when unavailable" is replaced by the block or section state that says so.

## Transport

- Protocol: AF_UNIX stream socket.
- Default path: `/run/ori/health.sock` for a runtime whose configuration names
  no path. An installed runtime's configuration names
  `<install root>/data/health.sock`, per install scope, and the socket is
  served there.
- Dev fallback path: `/tmp/ori-health.sock` when `/run/ori/health.sock` is not
  writable.
- Default mode: `0o660`.
- Security model: local file permissions. No network listener.

## Request

The request is line-framed, with one request per connection. A request is
the bytes up to and including its first LF, or up to the end of the stream
when no LF comes first. It is compared as exact bytes: nothing is decoded,
trimmed, case-folded or normalised. Bytes after the terminating LF are
discarded and never judged, so whether a request is accepted
never depends on how the transport splits writes, or on what follows its LF.
A connection closed before any byte arrives is the empty request.

The server decides in this order, and the first rule that applies decides:

| Step | Rule | Result |
| --- | --- | --- |
| 1 | The request is longer than 1024 bytes, counting its LF | `request_too_large` |
| 2 | The request has not ended when a time bound expires | `unsupported_request` |
| 3 | The request is exactly one of `GET_HEALTH`, `GET_HEALTH` LF, the empty request, or LF | success |
| 4 | Anything else | `unsupported_request` |

Step 1 applies as soon as the server holds more than 1024 bytes of a request
that has not ended, however they arrive. The time bound is finite, and its
value is the producer's. The server writes one response line, a JSON object
followed by LF, then closes the connection. It may close with discarded bytes
unread, and on some platforms, Linux AF_UNIX among them, the client then sees
a connection reset
after the complete response rather than a clean end of stream. A client
sends nothing after its request and reads exactly one response line.

`GET_HEALTH` is the ten ASCII bytes `47 45 54 5f 48 45 41 4c 54 48`; LF is
the byte `0a`. A carriage return, any other ASCII or Unicode whitespace or
separator (`\t`, `\x0b`, `\x0c`, `\x1c` to `\x1f`, NEL U+0085, NBSP U+00A0,
U+2028, U+2029, a byte order mark), a NUL, and any byte that is not valid
UTF-8, anywhere before the terminating LF, makes the request one that step 4
refuses.

Why lines and not end of stream: a client that does not half-close gives the
server no way to know whether more bytes follow the LF, so requiring end of
stream would break those clients. The endpoint is read-only and grants no
authority, so nothing requires judging what follows a complete request.

## Response Envelope

The envelope is v3's. Success:

```json
{
  "schema_version": 1,
  "ok": true,
  "health": { "...": "..." }
}
```

Failure:

```json
{
  "schema_version": 1,
  "ok": false,
  "error": {
    "code": "unsupported_request",
    "detail": "send GET_HEALTH or empty request"
  }
}
```

Error codes, closed:

| Code | When |
| --- | --- |
| `request_too_large` | Request step 1. |
| `unsupported_request` | Request steps 2 and 4. |
| `internal_error` | The snapshot could not be built, including when it would carry a value this contract cannot represent, such as an integer outside its range. The runtime serves no snapshot rather than a clamped or rounded one. |

The set is v3's.

`detail` is diagnostic text and carries no path, secret or exception text.

## Representation

These rules hold for every member of `health`, at every depth, except inside
`diagnostics`, whose content no rule here judges.

- **Integers.** A member typed `int` is a JSON number written with no
  fraction and no exponent, in the range its row gives. A row that gives no
  range means `0` to `9007199254740991` (2^53−1). A producer never clamps,
  wraps or rounds a value into range: a value outside it is
  `internal_error`, and no snapshot is served. A consumer refuses a snapshot
  carrying an `int` member outside its range or not in integer form.
- **Floats.** A member typed `float` is a finite JSON number, at least `0`.
- **`null`** means that the thing the member names does not exist: no
  oldest item because there are none, no reading yet. It never means unknown,
  and it never means "does not expire".
- **Unknown** is carried by a block's `state`, or by a section flag, never by
  a default value. A default never stands in for an observation the runtime
  did not make.
- **Durations and ages** are whole milliseconds, rounded down, except
  `age_upper_ms`, which is rounded up so that it stays an upper bound.
- **Arrays of strings** that this contract calls sets are sorted by byte
  order and hold no duplicates.

### Block states

Every top-level object block whose section names its states carries
`state`; `last_alert_timestamps` and `diagnostics` carry none:

| `state` | Meaning |
| --- | --- |
| `disabled` | The subsystem is not configured to run. It has no obligation, contributes no condition, and its block carries only the members marked *always*. |
| `starting` | The subsystem is configured or required and still initialising: the runtime has not yet brought it up, and the [startup deadline](#startup-deadline) has not passed. Its block carries only the members marked *always*. Only a block whose section names `starting` takes it. It contributes `subsystem_starting` only for a block the condition table lists there, which are the blocks that decide severity. |
| `unavailable` | The subsystem is configured or required and its state cannot be read: its source failed, or it was still initialising when the startup deadline passed. Its block carries only the members marked *always*. |
| `available` | The subsystem's state was read for this snapshot. Every member of its table is present. |

#### Startup deadline

`starting` is bounded. The producer sets a finite startup deadline, measured
on a monotonic clock from the start of the runtime process. Once the time
since that start reaches the deadline, a block that is not yet ready reports
`unavailable`, never `starting`, and a sensor whose adapter has not been
connected reports `connection: "unavailable"`. A hung initialisation is
therefore reported as a failure to read, never as benign startup. The
deadline's value is the producer's.

Each block's section names the states it may take. In the tables below,
**Present** is `always`, or `available` when the member appears only in that
state. A table with no Present column, and no sentence saying otherwise, lists
members that are always present. A section flag or a block's own member, such
as `device_policy.policy_held`, narrows Present further where its section
says so.

The two bounds and the threshold are configuration, so like the outbox's other
configured members they are present in every state. Each is finite and at
least `1`, and the runtime reports the value in force. A deployment may set
one lower than its default, never higher: a configured value above the
default is refused when the configuration loads, never clamped.

**Resolution.** An alert is resolved once any configured alert channel, the
primary or a failover channel, confirms it: the channel's provider accepts
that message for delivery and returns its message identifier. A dashboard or
log entry resolves nothing, and neither does an attempt the provider did not
accept. What the conditions report is that delivery is unconfirmed: a
provider's acceptance can be lost and another channel may have reached the
operator, so neither condition says the operator was never told.

Notification failure never blocks, delays or retries a physical act. The
protective act has already been attempted when its notification is queued.

### Diagnostics

`diagnostics` is an object, always present, possibly empty. It is the only

## Remote Health Projection

The gateway-api/v2 `health` export carries this projection, never the
snapshot. It is an allowlist: it holds only the members below, so a member
added to the snapshot later stays local until a version of this contract
approves it. Paths, exception text, sender identities and subordinate device
identities never leave the health socket; counts and stable reason codes do.
Remote device-level diagnosis needs a separately authorised, encrypted
detailed export, which this contract does not define.

closed vocabulary; prose never leaves the socket. The projection follows this
contract's representation rules.

**A snapshot that fails the triple check**, T1 to T5, projects to the minimal
projection: `projection`, the runtime's own `device_id`, `status:
"critical"`, `critical: true` and `degradation_reasons:
["health_snapshot_invalid"]`, and nothing else from the snapshot.

Removing `senders` from the export changes v3's behaviour, under which the
export returned the whole snapshot. The gateway's runtime client, which reads
sender risk from the export, migrates to the two sender counts before a
runtime serves this projection.

## Consumers

A consumer reads a block's members only while its `state` is `available`, and
never reads a member's absence, or a block that is not `available`, as a
healthy or zero value.

**Adoption order.** Before any runtime emits this version, on the socket or
in a heartbeat:

1. the gateway, which accepts and projects the gateway-api/v2 heartbeat
   (`critical`, the full vocabulary, steps 1, 9 and 11) and claims that
   version, then reads the remote health projection in place of the v3
   snapshot, including in its alert-outbox posture mapping, which today
   reports the outbox as available whatever the runtime said;
2. ori-cli, whose runtime health client (`internal/rpc/health.go`) parses
   this version's snapshot;
3. the Python SDK's health client and helpers.

Only then does a runtime serve or publish this version. A runtime emitting
ahead of its gateways would make a conforming older gateway refuse its
heartbeats, turning an additive change into a loss of health reporting.
Every consumer of the gateway's site projection gains `critical`.

## Severity

### Conditions

`status` is the maximum severity over every condition in this table that
holds, in the order `ok` < `degraded` < `critical`, and `ok` when none
holds. Each predicate reads only contracted members of the same snapshot, so
a reader recomputes it from what was served. A predicate on a block that is
not `available` does not hold, except where it says otherwise.
`evidence.action_records` is a block of its own for this rule: its
conditions are decided by its own `state`, whatever the evidence state. An
evidence row behind a section flag is decided by that flag, not by the
evidence state: its predicate can hold only when its flag is `true`.

| Token | Severity | Holds when |
| --- | --- | --- |
| `firmware_liveness_stopped` | `critical` | `firmware_liveness.loop` is `stopped_unexpectedly`. |
| `firmware_liveness_tick_stale` | `critical` | `firmware_liveness.loop` is `running` or `stopped_unexpectedly`, and either `last_successful_tick_age_ms` is not `null` and `≥ expiry_window_ms`, or it is `null` and `started_age_ms ≥ expiry_window_ms`. |
| `firmware_liveness_device_expired` | `critical` | `firmware_liveness.loop` is not `stopped_cleanly`, and `expiring_device_ids` is non-empty. |
| `firmware_liveness_over_capacity` | `degraded` | `firmware_liveness.loop` is not `stopped_cleanly`, and `supervised_devices > supported_device_capacity`. |
| `firmware_liveness_tick_failures` | `degraded` | `firmware_liveness.loop` is not `stopped_cleanly`, and `consecutive_tick_failures > 0`. |
| `decision_record_lost` | `critical` | Some `action_log_records.loss_incidents[]` entry has `kind: "decision_record_lost"` and `acknowledged: false`. |
| `action_log_records_lost` | `degraded` | Some `action_log_records.loss_incidents[]` entry has `kind: "action_record_lost"` and `acknowledged: false`. |
| `action_log_records_stalled` | `degraded` | `action_log_records.oldest_pending_age_ms` is not `null` and `> stall_bound_ms`. |
| `tier_c_records_degraded` | `degraded` | `evidence.action_records` is `available` and `lost > 0`, `unknown_live > 0`, or `pending ≥ ceiling`. |
| `tier_c_recovery_failed` | `degraded` | `evidence.action_records.recovery_failed` is `true`. |
| `sensor_unconnected` | `degraded` | Some `sensors[]` entry has `connection: "failed"`. |
| `sensor_measurement_degraded` | `degraded` | Some `sensors[]` entry has `measurement_degraded: true`. |
| `sensor_stale` | `degraded` | Some `sensors[]` entry has `stale: true`. |
| `tier_d_alert_delivery_unconfirmed` | `critical` | `alert_outbox.tier_d_unresolved_count > 0`, and `tier_d_max_attempts ≥ tier_d_critical_warning_threshold` or `tier_d_oldest_age_ms ≥ tier_d_age_bound_ms`. |
| `alert_delivery_overdue` | `degraded` | `alert_outbox.oldest_non_tier_d_age_ms` is not `null` and `≥ overdue_bound_ms`. |
| `skill_required_hooks_unavailable` | `critical` | `skill_hooks.required_unavailable > 0`. |
| `skill_optional_hooks_unavailable` | `degraded` | `skill_hooks.optional_unavailable > 0`. |
| `community_skills_refused` | `degraded` | `community_skills.refused_skills > 0`. |
| `config_unsigned_value_source` | `degraded` | `config_authority.unsigned_value_source` is `true`. |
| `evidence_posture_problem` | `degraded` | `evidence.posture_problems` is non-empty. Holds in every evidence state. |
| `evidence_courier_answer_unrecognised` | `degraded` | `evidence.delivery_ledger_available` is `true` and `courier_answer_faults > 0`. |
| `evidence_contributor_link_unresolved` | `degraded` | `evidence.attestation_summary_available` is `true` and `contributor_links_unresolved > 0`, in every evidence state. |
| `commissioning_problem` | `degraded` | `commissioning.problems` is non-empty. |
| `safety_zone_active_unprotected` | `degraded` | Some `safety_zones[]` entry has `activation: "active"`, and either its `protection_claim` is `unprotected`, or the `commissioning.zones[]` entry with its `zone_id` names a sensor whose `sensors[]` entry has `stale: true` or a `connection` other than `connected`. |
| `safety_zone_activation_refused` | `degraded` | Some `safety_zones[]` entry has an `activation` that is a refusal verdict: `unit_mismatch`, `direction_unsupported`, `parameter_mismatch`, `trip_point_unobservable` or `undemonstrated_binding`. Not `pending_ratification`. |
| `safety_zone_trip_unresolved` | `critical` | Some `safety_zones[]` entry has `activation: "active"` and `trip_state: "tripped"`, and its `command_status` is `driver_refused`, or its `effect_verified` is `mismatched`, or its `effect_verified` is `unknown` and `trip_age_ms ≥ safety_registry.trip_verification_deadline_ms`. |
| `subsystem_starting` | `degraded` | Any of `alert_outbox`, `commissioning`, `safety_registry`, `community_skills`, `config_authority`, `action_log_records`, `firmware_liveness`, `skill_hooks`, `evidence` or `evidence.action_records` has `state: "starting"`; or some `sensors[]` entry has `connection: "pending"`. |
| `subsystem_state_unknown_critical` | `critical` | A [critical-capable block](#unknown-critical-visibility) has `state: "unavailable"`. |
| `subsystem_state_unknown` | `degraded` | Any of `commissioning`, `community_skills`, `config_authority`, `evidence` or `evidence.action_records` has `state: "unavailable"`; or some `sensors[]` entry has `connection: "unavailable"`; or `evidence.state` is `available` and `attestation_summary_available`, `registration_available` or `delivery_ledger_available` is `false`. |

`firmware_liveness_degraded` is an umbrella token, not a condition. It holds
exactly when one of the five `firmware_liveness_*` conditions above holds,
and has no severity of its own: the severity is that of the liveness
conditions that hold. `firmware_liveness.degraded` is `true` exactly when it
holds.

Why the liveness split falls where it does: a loop that died, a tick older
than the window, and an expired device each mean a supervised device has
lost, or is losing, the runtime's liveness, and is critical. Over-capacity
and failing ticks are risks while supervision is still inside its window, and
are degraded; either reaches critical only through a critical condition that
also holds. None of this says a physical protection failed: the firmware
backstop's state is not reported here.

A `disabled` subsystem contributes nothing, because it has no obligation,
and neither does one that does not apply to the device. A subsystem whose
conditions decide severity and is still initialising is `starting` and
contributes `subsystem_starting`; one whose state could not be read is
`unavailable` and contributes the unknown-state token its critical capability determines. Either way `status`
is not `ok`, because reporting `ok` for a state the runtime has not observed
would be a default standing in for an observation, and the tokens let a
reader tell initialisation from a failure. A critical condition that is known
during startup still makes `status` `critical`. Past the startup deadline,
what is still not ready is `unavailable` and names its applicable unknown-state token,
not `subsystem_starting`. Evidence that is enabled and did not open names
both `subsystem_state_unknown` and, through its posture problem
`signing_unavailable`, `evidence_posture_problem`.

**A failed trip.** `safety_zone_trip_unresolved` holds for a commanded
protective trip that the runtime could not establish: its command was refused
or failed, its observed effect mismatched the required one, or its effect
went unverified past the deadline, so a trip never verified cannot escape it.
The `command_status` vocabulary has no failed value: a command that errors
without the driver refusing it stays unverified, and the deadline catches it.
A refusal does not prove the circuit stayed closed. It proves the runtime
failed to establish the required protective outcome. Health reporting never
delays the trip attempt, and nothing here retries one.

**Protection outranks the generic sensor condition.** A sensor that feeds an
active pair and stops reporting names `sensor_stale` and also
`safety_zone_active_unprotected`, so the generic condition never stands in
for the safety finding.

### Unknown critical visibility

A block is **critical-capable** when one of the conditions it decides is
critical in the table above. The rule yields exactly `safety_registry`
(`safety_zone_trip_unresolved`), `alert_outbox`
(`tier_d_alert_delivery_unconfirmed`), `action_log_records`
(`decision_record_lost`), `skill_hooks` (`skill_required_hooks_unavailable`)
and `firmware_liveness` (`firmware_liveness_stopped`, `_tick_stale`,
`_device_expired`). Every other block decides only degraded conditions and
keeps `subsystem_state_unknown`.

`subsystem_state_unknown_critical` holds when a critical-capable block is
`unavailable`: its source failed, or it was still not ready when the startup
deadline passed. Until the deadline, such a block is `starting` and names
`subsystem_starting`. A `disabled` block, or one that does not apply to the
device, never counts.

It means that the runtime cannot see whether a critical condition holds:
critical visibility is unavailable. It never means that a trip failed, that a
notification went unconfirmed, or that any physical fault occurred. Unknown
state never overwrites or clears a known critical condition: the fold takes
the maximum, so a known critical beside it is still named and still
critical. It never blocks or delays Tier D, and never grants permission to
actuate.

The heartbeat carries only the token, because it has no per-subsystem field.
The [remote health projection](#remote-health-projection) names the blocks,
in `unknown_critical_blocks`.

### Severities other contracts state

Each severity another contract assigns to runtime health is carried here:

| Contract | What it states | Carried by |
| --- | --- | --- |
| [safety-profile/v1.md](../safety-profile/v1.md) | A development start with a refused eligible zone leaves health degraded | `safety_zone_activation_refused` |
| [tier-c-approval/v1.md](../tier-c-approval/v1.md) | A lost approved decision record is critical | `decision_record_lost` |
| tier-c-approval/v1 | `dispatch_outcome_unknown` and `dispatch_not_proven` leave evidence health degraded | `tier_c_records_degraded`, through `action_records.lost` |
| [skill-hook-isolation/v1.md](../skill-hook-isolation/v1.md) | A required-hook failure is critical; an optional hook unavailable is degraded | `skill_required_hooks_unavailable`, `skill_optional_hooks_unavailable` |
| [evidence/v1.md](../evidence/v1.md) | Site health degrades a node on truncation, regression or evidence unavailability | The runtime reports evidence it cannot open as `subsystem_state_unknown` and `evidence_posture_problem`; truncation and regression are the gateway's observations, applied in its site projection, never in this snapshot |

Startup never delays or gates Tier D. No subsystem waits for another to
leave `starting` before the protection path runs, and nothing in this section
is read by it.

*Non-normative.* A runtime therefore reads `degraded` while it starts. A
deployment check, such as an installer or `ori doctor`, waits up to a bounded
deadline for the snapshot to stop naming `subsystem_starting` before it reads
`ok` as healthy, and reports the deadline's expiry as a failure. This
contract adds no separate readiness field.

### `status`, `critical` and `degradation_reasons`

- `status` is the fold above. It is computed once, over every condition,
  after every condition is evaluated. No condition assigns `status`, so the
  order of evaluation never changes it, and `degraded` never overwrites
  `critical`.
- `critical` is `true` exactly when `status` is `critical`. It is a
  compatibility field for readers of `critical`, and is removed only through
  an explicit consumer migration.
- `degradation_reasons` is the set of tokens of the conditions that hold,
  plus `firmware_liveness_degraded` when it holds, sorted by byte order. It
  is `[]` exactly when `status` is `ok`, and is non-empty whenever `status`
  is not `ok`.
- The snapshot carries the reasons, rather than leaving a reader to derive
  them, so that the severity and its explanation are one observation taken at
  one instant: a reader recomputing them from blocks read at another time
  could name a reason that no longer holds. The heartbeat copies them; it
  does not recompute them.
- The vocabulary is owned by the closed table in
  [gateway-api/v2.md](../gateway-api/v2.md#degradation_reasons). This
  section assigns each token its predicate and severity; it adds no token
  that table does not hold.

Because each token names one condition of known severity, `status` is also a
function of `degradation_reasons` alone. A triple `(status, critical,
degradation_reasons)` is **self-consistent** when all of these hold:

- `degradation_reasons` is empty exactly when `status` is `ok`;
- `firmware_liveness_degraded` is in it exactly when at least one
  `firmware_liveness_*` condition token is;
- when `status` is not `ok`, it is the maximum severity of the tokens in
  `degradation_reasons`, `firmware_liveness_degraded` counting for nothing;
- `critical` is `status == "critical"`;
- `health_snapshot_invalid` is not in it: that token is the heartbeat's, and
  a snapshot never carries it.

A snapshot whose triple is not self-consistent is malformed. The
[triple check](#heartbeat-mapping) decides it, in four ordered steps.

### What health is not

Nothing in a health snapshot grants actuation authority, licenses a tier,
approves an action, or is read by the protection path. No condition, state,
count or reason gates, delays or suppresses any Tier D execution, an approved
Tier C action, or an in-force commissioned safety binding, zone or profile.
`critical` reports; it does not act.

## Heartbeat Mapping

The runtime node heartbeat of [gateway-api/v2.md](../gateway-api/v2.md)
takes its `status` and `degradation_reasons` from this snapshot. The
publisher decides whether the snapshot can be mapped with the **triple
check** below, and with nothing else. The steps run in order, and the first
that fails names the failure:

| Step | Check | Failure |
| --- | --- | --- |
| T1 | The snapshot is a JSON object, and `status` is the string `ok`, `degraded` or `critical` | `status_invalid` |
| T2 | `critical` is a boolean equal to `status == "critical"` | `critical_mismatch` |
| T3 | `degradation_reasons` is an array of at most 32 strings, unique, sorted by byte order, each in the gateway-api/v2 vocabulary and none `health_snapshot_invalid` | `reasons_malformed` |
| T4 | The triple is self-consistent: the reasons are empty exactly when `status` is `ok`; `firmware_liveness_degraded` is present exactly when a `firmware_liveness_*` condition token is; and a `status` other than `ok` is the maximum severity of the reasons | `reasons_inconsistent` |
| T5 | The whole snapshot passes [snapshot checks](#snapshot-checks) 2 to 5 | `snapshot_unservable` |

T1 to T4 restate the self-consistency rule of [Severity](#severity) as
ordered steps. T5 is stricter than the socket, which refuses only a value it
cannot represent: a snapshot the socket would still serve, but that fails a
shape or type check, goes to the fallback heartbeat. That disagreement runs
one way on purpose, because it can only report a node as `critical`, never
as healthier than its snapshot. The publisher adds no judgement of its own: a
snapshot that passes all five is mapped, and one that fails any is malformed.

| Snapshot | Heartbeat `status` | Heartbeat `degradation_reasons` |
| --- | --- | --- |
| Passes, `status: "ok"` | `healthy` | absent |
| Passes, `status: "degraded"` | `degraded` | the snapshot's reasons |
| Passes, `status: "critical"` | `critical` | the snapshot's reasons |
| Fails a step | `critical` | `["health_snapshot_invalid"]` |

A malformed snapshot never maps to `healthy`. It maps to the **fallback
heartbeat**, because a verdict the runtime cannot read may be hiding a
critical one:

- The fallback heartbeat carries nothing from the failed snapshot. It is
  exactly `device_id` (the runtime's own, from its configuration),
  `status: "critical"`, `last_seen_ms` (the runtime's clock at
  publication), `gateway_seen_ms: 0`, `active_triggers: []` and
  `degradation_reasons: ["health_snapshot_invalid"]`, with `auth` when
  heartbeat authentication is enabled. It carries no `evidence` block and
  no other field.
- A stateful gateway projector that has seen evidence from the node then
  reads the missing block as evidence unavailable, which is consistent with
  a critical node.
- The runtime logs the failing step locally, and exports none of the
  snapshot's contents.
- Each heartbeat is mapped from the snapshot taken for it, so the next
  snapshot that passes resumes normal reporting, and no heartbeat before it
  does.
- It reports a failure to report. It confers no authority, and Tier D does
  not read it.

**Where each heartbeat field comes from**, for a snapshot that passes:

| Field | Source |
| --- | --- |
| `device_id` | The runtime's own device id, from its configuration; never from the snapshot. |
| `status` | The table above. |
| `last_seen_ms` | The runtime's wall clock at publication. |
| `gateway_seen_ms` | `0`; the gateway stamps it. |
| `active_triggers` | Always `[]`. This contract defines no source for it: trigger names are site-authored, and nothing in the snapshot carries them. |
| `degradation_reasons` | The table above; absent when `status` is `ok`. |
| `evidence` | Present only when `evidence.state` is `available` and `attestation_summary_available` is `true`: `chain_head_hash`, `attestation_gap_count` and `action_event_type` from the snapshot, and `available: true`. Otherwise absent, never filled with `0` or `''`. |
| `auth` | Present when heartbeat authentication is enabled, over the fields above. |

## Conformance

### Snapshot checks

A conformance check reads a served snapshot over the real socket and applies
these steps in order. The first that fails names the verdict. A member that
fails step 3 or step 4 leaves the conditions it feeds undefined, so steps 9
and 10 are not judged for that response; its verdict is still the first
failing step.

| Step | Check | Verdict |
| --- | --- | --- |
| 1 | The response is one line, one JSON object followed by LF, and the object carries exactly `schema_version: 1`, `ok: true` and a `health` object, each named once | `envelope_invalid` |
| 2 | `health` carries exactly the top-level members of the payload table, `diagnostics` names only the listed namespaces, and no object anywhere in `health` names a member twice | `members_invalid` |
| 3 | Every member typed `int` is a JSON number in integer form and in range; every member typed `float` is a finite JSON number `≥ 0`; nothing inside `diagnostics` is judged | `integer_invalid` |
| 4 | Every other member present, at every depth, has the JSON type its row gives, and every member listed under [Value vocabularies](#value-vocabularies) holds one of its values, and each `diagnostics` namespace's value is an object; `status`, `critical` and `degradation_reasons` are left to steps 6 to 8, and the value of `state` to step 5 | `type_invalid` |
| 5 | Every block's `state` is one its section allows, every boolean tied to `state` agrees, each member is present exactly when its Present column and section flags say, every [set](#representation) other than `degradation_reasons` is in byte order and holds no duplicates, `unmapped_set_bits` is ascending without duplicates, and every [consistency rule](#consistency-rules) holds | `shape_invalid` |
| 6 | `status` is `ok`, `degraded` or `critical` | `status_invalid` |
| 7 | `critical` is a boolean equal to `status == "critical"` | `critical_mismatch` |
| 8 | `degradation_reasons` is a set of at most 32 tokens of the gateway-api/v2 vocabulary other than `health_snapshot_invalid` | `reasons_malformed` |
| 9 | `degradation_reasons` equals the reasons recomputed from the snapshot's members by the condition table | `reasons_mismatch` |
| 10 | `status` equals the fold of the recomputed conditions | `status_mismatch` |

#### Consistency rules

Snapshot check 5 enforces each of these:

- `safety_zones[].trip_age_ms` is an integer exactly when `trip_state` is
  `tripped`, and `null` otherwise;
- `safety_registry.trip_verification_deadline_ms` is at most `60000`;
- `alert_outbox.tier_d_critical_warning_threshold` is `1` to `3`,
  `tier_d_age_bound_ms` is `1` to `300000`, and `overdue_bound_ms` is `1` to
  `3600000`;
- `action_log_records.lost` is the sum of `count` over every
  `action_record_lost` incident, and `decision_records_lost` the sum over
  every `decision_record_lost` incident;
- each `loss_incidents[]` entry's `acknowledged_at_ms` is `null` exactly when
  `acknowledged` is `false`;
- `loss_incidents` is ordered by `incident_id` in byte order, without a
  repeated `incident_id`.

### Behavioural checks

Each row is driven through the runtime's real snapshot builder or its socket,
and is observed in the served snapshot.

| Stimulus | Observation |
| --- | --- |
| Each request of [Request](#request), including the refused classes, split writes, bytes after the LF, a 1000 + 25 byte split, the 1024-byte boundary, and a request left unfinished past the bound | The response, or error code, the request table gives. |
| Nothing wrong | `status: "ok"`, `critical: false`, `degradation_reasons: []`. |
| Each condition alone | Its token, its severity, and only the companions it implies: `firmware_liveness_degraded` for a liveness condition, and `safety_zone_active_unprotected` for `safety_zone_trip_unresolved`, whose unresolved trip leaves the pair unprotected. |
| Each critical-capable block `unavailable`, and a degraded-only block `unavailable` | `subsystem_state_unknown_critical`, `critical`; then `subsystem_state_unknown`, `degraded`. |
| A critical-capable block still not ready past the startup deadline | `subsystem_state_unknown_critical`, `critical`; before the deadline, `subsystem_starting`. |
| A known critical condition beside an unreadable critical-capable block | Both tokens, `critical`; the known condition is still named. |
| A lost decision record together with a commissioning problem and an active unprotected pair, in each order the builder can raise them | `status: "critical"`, `critical: true`, all three tokens. |
| A liveness loop that stopped after starting, not by shutdown | `firmware_liveness_stopped`, `firmware_liveness_degraded`, `critical`. |
| A liveness tick age equal to the expiry window, and one millisecond under it | `firmware_liveness_tick_stale` at the window; not under it. |
| Supervision over capacity, with every device in window | `degraded`, never `critical`. |
| A subsystem whose conditions decide severity, before it has started and within the startup deadline | `subsystem_starting`, `degraded`; with a lost decision record beside it, `critical`. |
| A degraded-only subsystem still not ready once the startup deadline passes | `state: "unavailable"`, `subsystem_state_unknown`, not `subsystem_starting`; with a lost decision record beside it, `critical`. |
| A degraded-only subsystem whose state cannot be read | `subsystem_state_unknown`, `degraded`. |
| A configured sensor before and after a failed connection | `subsystem_starting`, then `sensor_unconnected`. |
| Evidence disabled | `evidence.state: "disabled"`; registration rows present with their disabled values; no attestation summary or delivery-ledger row present. |
| A DevicePolicy that never expires | `expiry: "never"`, `valid_until: null`; no integer outside its range, by default `0` to 2^53−1, anywhere. |
| An integer the snapshot cannot represent | `internal_error`; no snapshot. |
| Each kind of malformed snapshot triple fed to the heartbeat | The fallback heartbeat, exactly; a local log entry naming the failing step; the next snapshot that passes resumes normal reporting. |
| A snapshot holding an integer the socket would refuse, fed to the heartbeat | The fallback heartbeat, failing step `snapshot_unservable`. |
| A negative or oversized number inside `diagnostics` | The snapshot is served; the heartbeat is mapped normally. |
| An eligible zone refused at activation, in development posture | `safety_zone_activation_refused`, `degraded`. |
| A commanded trip refused by the driver; one whose effect is `mismatched`; one unverified at, and one millisecond under, its deadline | `safety_zone_trip_unresolved`, `critical`, except under the deadline; the trip attempt was not delayed. |
| The sensor of an active pair stops reporting past its silence bound | `sensor_stale` and `safety_zone_active_unprotected`. |
| A Tier D notification unconfirmed at its attempt threshold, and one at its age bound | `tier_d_alert_delivery_unconfirmed`, `critical`; the physical act was neither delayed nor retried. |
| A Tier D notification confirmed by its failover channel | Resolved: no condition. |
| Another alert unconfirmed past `overdue_bound_ms`; a large backlog of young alerts | `alert_delivery_overdue`; then nothing. |
| A lost decision record, then a restart | `decision_record_lost`, `critical`, before and after the restart, the same `incident_id`, `decision_records_lost` unchanged. |
| The same incident after an authenticated acknowledgement | `acknowledged: true`, the incident still listed and counted, `decision_record_lost` no longer named; any other condition that held still holds. |
| Loss incidents that cannot be read at start | `action_log_records.state: "unavailable"`, `subsystem_state_unknown_critical`, `critical`; Tier D runs. |
| The gateway `health` export of a snapshot carrying senders, expiring devices, reading-age devices, alarm channels, refused documents, trigger timestamps and diagnostics | The remote health projection, with none of them and their counts in place. |
| A heartbeat with evidence `unavailable`, or its attestation summary not read | No `evidence` block in the heartbeat. |

## Vectors

`runtime-health/health-vectors-v4.json`, written by
`scripts/generate-runtime-health-vectors-v4`, holds:

- `conditions`: every token with its severity, `null` for the umbrella,
  and `heartbeat_only`, the token a snapshot never carries;
- `fold_cases`: ordered lists of the conditions that hold, as the producer
  raised them, and the `status`, `critical` and `degradation_reasons` that
  result, covering every condition alone and every ordered pair;
- `snapshot_cases`: the blocks the condition table reads, and the reasons and
  `status` they give, including each liveness condition alone and combined,
  disabled, starting and unavailable subsystems and every boundary. A case
  with `startup` gives the producer's inputs, the blocks not yet ready, the
  time since the process started and the startup deadline, and its snapshot
  shows the states they resolve to;
- `served_cases`: those blocks with a served triple, and the verdict of
  snapshot checks 6 to 10;
- `heartbeat_cases`: a snapshot's triple, as JSON values, judged by T1 to T4
  alone, the step that fails (`null` when it passes), and the heartbeat
  `status` and `degradation_reasons` it maps to;
- `fallback_heartbeat_case`: a malformed snapshot carrying triggers and an
  evidence block, the runtime's own `device_id`, clock and whether heartbeat
  authentication is enabled, and the exact fallback heartbeat;
- `response_cases`: a served response, as text, and the verdict of snapshot
  checks 1 to 10, `accept` when every step passes;
- `unrepresentable_cases`: an integer member's path and the value the
  runtime holds for it, as JSON text, and whether the runtime serves the
  snapshot or answers `internal_error`;
- `gateway_reason_cases`: a heartbeat's `status` and `degradation_reasons`,
  and the gateway-api/v2 verdict of its validation steps;
- `request_cases`: a request as the writes that deliver it, each in hex, and
  how the stream then behaves: `eof` (the client half-closes after the last
  write) or `silent` (the client sends nothing more until the bound expires);
  and the result;
- `integer_cases`: the JSON text of an `int` member whose row gives no range,
  and whether it is accepted;
- `projection_cases`: a whole snapshot, the exact remote health projection it
  gives, and strings from its local-only members that the projection must not
  contain;
- `heartbeat_snapshot_cases`: a whole snapshot, judged by T1 to T5, the step
  that fails (`null` when it passes), and the exact heartbeat it maps to, with the
  runtime's `device_id`, clock and authentication setting given;
- `expiry_cases`: `device_policy` expiry members, and whether they are
  accepted.

A `snapshot_cases` or `served_cases` snapshot carries the members the
condition table reads, and any block whose state the case exercises, each
present exactly as the Present column and section flags say; the rest of the
payload is out of scope there. A `response_cases` response is a whole
served response. A checker recomputes every expected
value from this text and gateway-api/v2 alone.
