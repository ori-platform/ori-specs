# Runtime Health Socket RPC v3

> Status: maturity `draft`; compatibility `amendable`; adoption: none
> recorded; proof: end-to-end `none`, HIL `none`, production `none`. Record:
> [status/runtime-health/v3.json](../status/runtime-health/v3.json).
>
> Released runtime versions up to and including `2.4.x` serve [v1](v1.md); the
> `2.5.0` release candidates serve [v2](v2.md).
>
> Source of truth for current behaviour: `ori/runtime_health_socket.py`,
> `ori/runtime.py`.


## What changed from v2

`protocol_version` reports `ori.evidence.v2` and `available` means the ledger
and the device key are open, which is what the shipped runtime does and what v2's
frozen text did not say; the additive `evidence` rows and the `safety_zones`
projection that v2's baseline audit moved here; `registration_status` has no
`refused` value, a terminally closed attempt being `registration_offer: closed`;
and the cross-references name [evidence-exchange/v2.md](../evidence-exchange/v2.md)
and [tier-c-approval/v1.md](../tier-c-approval/v1.md).

## What changed from v1

One field is removed: `evidence.artifact_version`.

The private evidence component is not something an operator has a part in, and
the disclosure boundary settled in
[evidence-exchange/v2.md](../evidence-exchange/v2.md) puts implementation
identity outside what operator-facing surfaces may carry. This document already
drew that line one field lower down — the note on `protocol_version` says the
loaded artifact's declared identifier "remains internal to runtime validation"
— and the version was simply not carried across with it.

The exposure is thin, and overstating it would be its own kind of inaccuracy: a
bare version string names no implementation, endpoint, location, credential or
custody detail. What makes the change worth a major version is consistency
rather than severity. Leaving it means the health contract and the exchange
contract disagree about whether the private component is visible at all, and a
future reader has to guess which one governs.

`available` and `protocol_version` already answer the operational question —
whether this device can sign, and against which public contract. Nothing an
operator does depends on the artifact's version.

### Migration

Both sides adopted v2; nothing claims this version yet, and the runtime and the
CLI target it once it is ratified. What follows records what the migration to v2
actually required, because this section originally understated it and the
correction is the part worth carrying forward.

- **`ori-runtime` stopped emitting the field** in the release following
  `2.4.0`. Released versions up to and including `2.4.x` still send it, and a
  consumer must accept that rather than reject it.

- **`ori-cli` dropped the field and every render of it.** This section
  originally described one consumer that "reads and renders" it, and concluded
  that removal could not break anything because the field was parsed with an
  optional accessor and the render guarded on a non-empty value — so a runtime
  that stopped sending it would simply produce one fewer line.

  That was wrong in a way worth recording. The CLI exposed the field on four
  surfaces, not one, and the guard covered only the first two:

  | Surface | Behaviour before removal |
  |---|---|
  | `ori doctor` | `artifact: <version>`, guarded on non-empty |
  | `ori doctor --json` | report field carried no `omitempty`; key emitted unconditionally, even when blank |
  | `ori doctor runtime-health --json` | raw passthrough of the whole runtime envelope |
  | `ori --json doctor runtime-health` | raw passthrough of the whole runtime envelope |

  The raw surfaces marshal the parsed envelope directly, so removing the typed
  struct field did not touch them: a field removed from a type is not a field
  removed from a passthrough map. Those two would have kept emitting the key
  no matter what the runtime did. The CLI now deletes `artifact_version` from
  the evidence object after parsing, on both the canonical and legacy flat
  paths.

  The general lesson for any field this contract removes: check the raw
  passthrough surfaces, not only the typed projections. A consumer that
  forwards a parsed payload wholesale does not inherit a field's removal from
  its own struct definitions.

- **`ori-gateway` was unaffected.** It projects node evidence health from the
  heartbeat block — `chain_head_hash`, `attestation_gap_count`, `available`,
  `action_event_type` — which never carried `artifact_version`. Its
  `NodeEvidence` struct has no corresponding field.

A consumer must treat absence as the normal case rather than an error. Per the
compatibility rules in `VERSIONING.md`, unknown fields are ignored; a *missing*
field is the other direction and needs a default.

Everything else in this contract is unchanged from v1, including the transport,
the request forms, the response envelope, and every other health object.

Read-only runtime health RPC over Unix domain socket for local CLI diagnostics.

## Transport

- Protocol: AF_UNIX stream socket
- Default path: `/run/ori/health.sock` for a runtime whose configuration names
  no path. An installed runtime's configuration names
  `<install root>/data/health.sock`, per install scope, and the socket is
  served there.
- Dev fallback path: `/tmp/ori-health.sock` when `/run/ori/health.sock` is not writable
- Default mode: `0o660`
- Security model: local file permissions (no network listener)

## Request

Accepted request payloads:

- `GET_HEALTH`
- empty payload

Maximum request bytes: `1024`.

## Response Envelope

Success:

```json
{
  "schema_version": 1,
  "ok": true,
  "health": { "...": "..." }
}
```

Failure:

```json
{
  "schema_version": 1,
  "ok": false,
  "error": {
    "code": "unsupported_request",
    "detail": "send GET_HEALTH or empty request"
  }
}
```

#### `protection_claim` is not derived by the reader

The field exists so that a consumer cannot compute a protection claim out of
`activation` and `trip_state` and get it wrong. The producer sets it, and the
conditions are conjunctive rather than a summary of the two obvious fields:

| Value | When |
| --- | --- |
| `unavailable` | `qualification.state` is anything but `none`. Decided first, in every posture and regardless of every field below |
| `protected` | **All** of: `activation` is `active`; the profile's status is `ratified`; the actuator backend is drivable; `measurement_degraded` is false; `rejected_input_active` is false; and there is no unresolved or failed physical trip outcome — that is, the pair is not `tripped`, or it is `tripped` with `command_status: command_issued` and `effect_verified: matched` |
| `unprotected` | Anything else |

**Each condition is there because a pair can satisfy the obvious ones and
protect nothing.** An active, ratified pair whose sensor stopped reporting has
nothing to evaluate. One whose readings are being rejected is evaluating
nothing credible. One that tripped and whose command was refused, or whose
effect was never verified or came back `mismatched`, has decided to open a
circuit that may still be closed. A claim computed from `activation` and
`trip_state` alone reports every one of those as protected.

**A pair that tripped and was verified is still `protected`**, because its
outcome is resolved and the circuit is isolated. A pair that tripped with an
unverified or contradicted effect is not, because nothing established that the
circuit moved.

**A pair under qualification is `unavailable`, never `protected`.** A consumer
rendering this field MUST show it as *supervised qualification; protection
claim unavailable*, and MUST NOT include such a pair in any count, badge,
summary, or aggregate a reader would take as protection coverage. The wording is
normative because the failure it prevents is a screenshot of a working
demonstration being read as a protection claim later.

A gateway site-health projection MAY carry `safety_zones`. It MUST NOT
aggregate `protection_claim` across nodes in a way that renders an
`unavailable` pair as covered.

| `last_disposition` | `object \| null` | **Design target, additive and optional.** The most recent verified evidence disposition as `{disposition, scope, observed_at_ms}`, with values from [evidence-exchange/v2.md](../evidence-exchange/v2.md). | `ingest_refusal_count` | `int \| null` | **Additive and optional.** Authority artifacts — custody acknowledgements, delivery receipts, epoch confirmations, evidence dispositions — that ingest verified and refused, as retained by the delivery ledger across restarts; the ledger keeps the newest 200, so this is a bounded count rather than a lifetime total. `null` when unavailable. | `last_ingest_refusal` | `object \| null` | **Additive and optional.** The most recent refusal as `{artifact_type, reason, observed_at_ms}`, with `reason` from the [evidence-exchange/v2.md](../evidence-exchange/v2.md) rejection vocabulary. | `posture_problems` | `array` | **Additive and optional.** Why evidence trust is not established on this device, from the closed vocabulary `signing_unavailable` (the ledger or device key did not open), `authority_keys_missing` (the signed release ships no authority-key registry, so no receipt, epoch confirmation or evidence disposition can verify) and `custody_unconfigured` (a gateway carries evidence but no custody secret is configured, so no custody acknowledgement can verify). `stopped_local_artifact_count`, `stopped_local_bytes` and
`oldest_stopped_local_since_ms` are reported together.
All three are evidence diagnostics only. They MUST NOT gate, delay or suppress
an approved Tier C action or any Tier D execution. A stopped-local artifact
leaves local counts only when the runtime verifies a `queued` acknowledgement
for the identical bytes and can prove that their handoff began before the
covering stop disposition was durably applied. An acknowledgement for a
handoff initiated after durable stop application is refused as inconsistent
state and does not reduce local counts. A delivery envelope leaves local
custody only on a verified custody acknowledgement, never on `queued`, so for
an envelope the same rule applies to that custody acknowledgement in place of
the `queued` acknowledgement. Restart, a configuration change, a new
commissioning reference and a new epoch lift no stop, so none of them lowers
these values; the move to gateway custody follows
[evidence-exchange/v2.md](../evidence-exchange/v2.md).

Identity replacement retains the retired identity's stop and evidence records
under that retired identity. They remain queryable in its retirement/archive
record but do not contribute to the replacement identity's `stopped_local_*`
fields. Historical epochs of the current identity do contribute.
`evidence-exchange/vectors/evidence-disposition-v2.json` fixes their values, and
`scripts/check-evidence-disposition-vectors` holds the corpus to them.

Gateway site-health projection may include broker posture, state-store encryption,
and alert outbox posture per runtime node. It must exclude `remote_command_lockout`
sender maps because keys are phone numbers or channel identities.
