# Alert Delivery Report Contract v1

> Status: maturity `draft`; compatibility `amendable`; adoption: none
> recorded; proof: end-to-end `none`, HIL `none`, production `none`. Record:
> [status/alert-delivery/v1.json](../status/alert-delivery/v1.json).

A runtime sends optional notices and safety notices over SMS and WhatsApp from
its own durable outbox. This contract defines **the runtime's signed report of
what it did with each notice**: one record for each observation of a provider
submission, and one cumulative tally for each kind of notice it withheld. It
defines how the report is signed and ordered, how a gateway takes custody of it
and forwards it, and what a reader may and may not conclude from it. Its one
rule above every other: **a report is an observation, and nothing in it grants,
withholds or restores authority anywhere.**

v1 provides individual submission history and aggregate withholding history. It
is not a record of every withheld notice.

## What this contract is not

- **It is not delivery to a person.** `accepted` says a provider accepted custody
  of a message and returned an identifier. It never says that a handset
  received it, that anyone read it, that an operator acted on it, or that
  anything physical happened. `delivered` is reserved and refused in this
  version; see [Outcomes](#outcomes).
- **It is not the notice.** The runtime submits notices to providers directly,
  under its own outbox. Reporting never withholds a submission. Its total
  attributable delay to any submission, including contention from reporting
  work, a backlog or a flood of it included, is at most 100 ms. Reporting
  never enters or blocks Tier D evaluation or execution, nor local safety. The
  runtime owns how it satisfies these guarantees, under ori-runtime#528; this
  contract prescribes no storage, transaction or scheduling for them.
- **A missing report says nothing about the notice.** A reader that holds no
  report for a notice, or no tally for a month, knows that the report is
  unavailable. It never concludes that the notice was not sent, or that none
  was withheld.
- **It grants no authority.** No member authorises, approves, enables or
  restores anything on any consumer, and no consumer's acceptance, refusal or
  silence changes anything on the device. Tier D never reads it, and no Tier C
  admission consults it.
- **It does not report Tier C approval traffic.** Approval and escalation
  messages to approvers, and the runtime's startup notice, are outside this
  version; see [Limits](#limits-and-later-versions).

## Identities

| Identity | What it names | Where it comes from |
| --- | --- | --- |
| `device_id` | The runtime device | `device.id` of the provisioning document the runtime holds accepted, under [runtime-config/v2.md](../runtime-config/v2.md) |
| The runtime's **report key** | The Ed25519 key that signs every record | The runtime's evidence device key, the key that signs [runtime-posture/v1.md](../runtime-posture/v1.md) records |
| `key_identity` | One report key, as a record names it | As runtime-posture/v1.md *Identities* defines it |
| `alert_id` | One logical notice: one event the runtime decided to tell the operator about | Minted by the runtime when it records the notice in its outbox, before any submission |
| `delivery_attempt_id` | One **submission attempt**: one provider call, on one channel, for one notice | Minted by the runtime before the provider call, and made durable then when the store allows; see [Reporting never gates a notice](#reporting-never-gates-a-notice) |
| An **observation** | One thing the runtime learned about one attempt | `(device_id, delivery_attempt_id, observation_seq)`, within one epoch |
| A **tally key** | One kind of withheld notice in one month | `(channel, class, reason, month)`, within one epoch; a tally snapshot's identity is its key and its `count` |

A withheld notice makes no provider call, so it has no `delivery_attempt_id`
and no submission record; it is counted in a [tally](#withholding-tallies). A
retry or a failover to another channel is a new provider call and so a new
attempt with a new `delivery_attempt_id`, under the same `alert_id`. The one
exception is a resend, after an `unconfirmed` observation, of the same request
to the same provider under the same provider idempotency key, where the
provider supports one: the provider treats it as the same call, so it is the
same attempt, and what the runtime learns from it is a later observation of
that attempt. Only what the provider says about the original request is an
observation of it: a resend that itself never leaves the runtime, or that the
provider refuses for itself, as for a rate limit, says nothing about the first
request, and is not recorded as one. After `failed`, which ends an attempt, a
resend is a new attempt under a new idempotency key. A retransmission of a record is
the same record, with the same bytes.

### Opaque identifiers

`alert_id` and `delivery_attempt_id` are opaque. Neither is computed from a
recipient's number or address, message text, template variables, or any other
content of the notice, unless the computation is keyed with a secret that never
leaves the runtime. A hash of a phone number is not opaque: numbers are a small
space, and a reader can search it. A runtime whose internal notice identifier
is such a hash publishes a different, opaque `alert_id` for that notice, and
keeps that `alert_id` durably with the notice, so that every record about the
notice names the same one.

A report **epoch** is one enrolled report key: its records, from its first to
its last. A new report key, for whatever reason it was made, begins a new
epoch, and nothing in this version links one epoch to another. Observation
identity, `attempt_seq` uniqueness, the rules of
[Consistency across records](#consistency-across-records), tallies, and
[Reading a notice](#reading-a-notice) all hold within one `device_id` and one
epoch. A later version may link epochs through an explicit migration, without
changing any identity this one defines.

**Every record has one key.** An attempt's epoch is fixed, and never changes,
when its identity is first made durable, before any record about it is
serialised; an attempt made durable while no key is loaded takes the key that
next loads. An attempt of a notice recorded before a
reset's or a move's act is unreported and counted, whenever its identity
becomes durable. A withheld notice's increment belongs
to the key in force at the decision. Every record about an attempt, and every
tally, is signed under its own epoch's key or not at all: a record that cannot
be signed under that key is **unreported**, and counted. At a rotation, before
the new key signs anything, the runtime signs under the outgoing key every
observation and tally derivable from its committed outbox state. At a destructive reset or a move,
nothing more is signed under the outgoing key. A key made again because the
earlier one could not be unsealed begins a new epoch like any other new key,
and nothing is signed under the key it replaces.

### Key changes

- **Rotation.** A rotation of the evidence device key gives the runtime a new
  report key and so a new epoch. Records already signed under the earlier key
  are published and forwarded as before, and verify under that key's
  enrolment, whenever they arrive. A later observation of an attempt of an
  earlier key, as a provider's receipt that comes after the rotation, is never
  signed under the new key: it is unreported and counted, and the attempt's
  state stays what its last record under the earlier key says. An earlier `accepted` stays visible; nothing turns it,
  or an `unconfirmed`, into `failed`.
- **Destructive reset.** A runtime that detects that its store was reset,
  lost, replaced or restored, or that is re-commissioned, makes a new report key
  before it signs anything, so no key ever signs records over counters it has
  signed before. How it detects one is ori-runtime's (#528). That key is made by re-commissioning the
  evidence device key, not by an `ori.evidence.rotation.v2` rotation, so it
  begins a new evidence epoch too. Like any new key it changes the posture pin,
  as runtime-posture/v1 *Rotation is a new pin* says: until the new pin is
  installed, posture reads what the old pin's state reads, which goes
  `stale`. No contract yet names that act; see
  [Limits](#limits-and-later-versions). It drops every report it has not yet
  signed, each counted as unreported. A restore it cannot detect is a limit:
  see [Limits](#limits-and-later-versions).
- **A move needs an explicit act.** Moving a device to another site or tenant,
  or changing its `device_id`, is a local act at the device. The act drops every
  record still in the report queue, signed or not, each counted as unreported,
  and makes a new report key, which the new owner's authorised installer
  enrols. A notice still pending in the outbox is submitted as before; its
  later attempts after the act are unreported and counted, so the earlier
  owner's notice is never reported to the new owner. Records of the earlier
  epoch stay with the owner its key was enrolled to, wherever they travel. A
  rotation alone never moves a device: a new key enrolled to another owner
  without the act is outside this contract, and
  [Limits](#limits-and-later-versions) states what it costs.

## Records

Every record is one JSON object. Its canonical bytes, its integer and string
rules, and its publication as exactly its canonical bytes are those of
runtime-posture/v1.md *The record*: members sorted by name, no insignificant
whitespace, every integer a JSON integer token from `1` to 2^53 − 1 with no
sign, fraction, exponent or leading zero, and every string ASCII matching its
pattern, so that no string needs a JSON escape. Bytes that parse to a record
but are not its canonical bytes are not a record.

**A member's form** is its own type, pattern, bounds and vocabulary, as the
tables below give them. A rule that relates two members, as the observation
table, the class rules and the detail table do, belongs to no member's form,
and is judged after the signature.

### Submission observation

| Member | Value |
| --- | --- |
| `v` | The integer `1`. |
| `kind` | `"submission"`. |
| `device_id` | Matches `^[A-Za-z0-9._-]{1,128}$`. |
| `key_identity` | The `key_identity` of the report key that signs this record. |
| `alert_id` | Matches `^[A-Za-z0-9_-]{16,64}$`; see [Opaque identifiers](#opaque-identifiers). |
| `notice` | `optional`, `tier_d` or `protection_degraded`; see [Notices](#notices). |
| `class` | A device-policy/v2 alert class name matching `^[a-z][a-z0-9_]{0,31}$`, or `null`; see [Class](#class). |
| `channel` | `sms` or `whatsapp`. |
| `delivery_attempt_id` | Matches `^[A-Za-z0-9_-]{16,64}$`. |
| `attempt_seq` | The attempt's position in the runtime's attempt order (below), at least `1`. |
| `attempted_at_ms` | The signing-clock value claimed for the attempt, at or before its provider call where the 100 ms bound of [Attempt order](#attempt-order) allows. |
| `observation_seq` | `1`, `2` or `3`: this observation's position within its attempt. |
| `prior_outcome` | `null`, `accepted`, `failed` or `unconfirmed`: the `outcome` of the attempt's previous observation, or `null` for its first; see [Observations of one attempt](#observations-of-one-attempt). |
| `outcome` | `accepted`, `failed` or `unconfirmed`; see [Outcomes](#outcomes). |
| `detail` | `null`, or one of the codes the table of [Detail codes](#detail-codes) lists. |
| `issued_at_ms` | The record's signing time, from the runtime's signing clock. |
| `signature` | The Ed25519 signature, canonical padded RFC 4648 Base64 of its 64 bytes. |

### Withholding tally

| Member | Value |
| --- | --- |
| `v` | The integer `1`. |
| `kind` | `"withheld_tally"`. |
| `device_id` | As above. |
| `key_identity` | As above. |
| `channel` | `sms` or `whatsapp`. |
| `class` | As above, or `null`. |
| `reason` | `disabled` or `capped`. |
| `month` | A calendar month in UTC, `YYYY-MM`, matching `^[0-9]{4}-(0[1-9]\|1[0-2])$`. |
| `count` | The number of notices withheld under this tally key, at least `1`. |
| `issued_at_ms` | As above. |
| `signature` | As above. |

A record whose `kind` is neither value, or whose members are not exactly those
its kind lists, is `malformed`.

## Outcomes

Each outcome says what the runtime observed about one attempt, and nothing more.

| Outcome | What the runtime knows |
| --- | --- |
| `accepted` | The provider accepted custody of the message and returned a message identifier. |
| `failed` | The submission definitely did not occur, or the provider refused it authoritatively: a refusal the provider returned, or a later provider report that it could not deliver an accepted message. |
| `unconfirmed` | The submission may have occurred, and no acceptance was observed: the call timed out, or its response was lost or unreadable, after the request may have reached the provider. |

"No acceptance observed" alone is never `failed`. A runtime that cannot tell
whether the provider received the request reports `unconfirmed`. A local
timeout that abandons a call the provider's client may still complete, as when
the call runs on a thread the timeout does not stop, is `unconfirmed`. So is a
modem that stops answering after the message was written to it. `failed` with
`not_submitted` is only for a call the runtime knows never left it: no
credentials, a destination it refused before sending, no template, or a
provider client that was not ready.

**`delivered` is reserved.** `outcome` is not in a record's form unless it is one
of the three values above, so a record whose `outcome` is `delivered`, or any
other value, is `malformed`. A later version may
define a receipt observation kind, with a qualifying provider receipt for each
channel; until then, no report says a handset received anything, even where a
provider has said so to the runtime.

### Observations of one attempt

An attempt's observations form a path, and each record names the step it takes
by its `prior_outcome` and `outcome`:

| `observation_seq` | `prior_outcome` | Permitted `outcome` |
| --- | --- | --- |
| `1` | `null` | `accepted`, `failed`, `unconfirmed` |
| `2` | `unconfirmed` | `accepted`, `failed` |
| `2` | `accepted` | `failed` |
| `3` | `accepted` | `failed` |

Any other combination is refused as `transition_refused`. `failed` ends an
attempt. An `unconfirmed` attempt that is never resolved stays `unconfirmed`.
A third observation follows only an `unconfirmed` resolved as `accepted`; one
record cannot show that, so a receiver judges it across records, under the
`prior_outcome` rule of [Consistency across records](#consistency-across-records).

A later observation never replaces an earlier one: an attempt that was
`accepted` and later `failed` keeps its `accepted` observation, under its own
identity. A runtime binds every later observation to the exact attempt it
concerns: by the provider message identifier it holds for that attempt, or, for
an attempt that has none, as an `unconfirmed` one has none, by the client
reference or idempotency key it sent with the request. It never binds one to an
`alert_id` alone, since one notice can have several provider messages. A
runtime that holds neither for an `unconfirmed` attempt cannot resolve it, and
the attempt stays `unconfirmed`.

A provider report about an `unconfirmed` attempt that names a message
identifier shows that the provider accepted it. The runtime records that as
`accepted`, and, when the report is a failure, records the failure as the next
observation, `failed` with `provider_reported_failure`.

### Attempt order

`attempt_seq` is a durable, strictly increasing counter of the runtime's store.
Every provider call, a first call and every retry and failover alike, has an
attempt with its own `delivery_attempt_id` and `attempt_seq`. `attempt_seq` is
unique within its epoch, never reused and never lowered on the same store, and
a new key neither resets nor restarts it. It orders attempts; arrival order and
every clock value are ignored for that purpose. `attempted_at_ms` is
informational: the signing-clock value taken for the attempt, which may fall
after the call began. An attempt's identity is made once and never rewritten.
The runtime makes it durable before the call where it can within the delay
guarantee of *It is not the notice*. Durability is not a precondition of the
call: an identity that becomes durable after its call has started is reported
like any other. Only an attempt whose identity never becomes durable is
unreported.

**Every provider call is bounded.** The runtime bounds every provider call it
makes, an SMS gateway's or a modem's as much as an HTTP provider's, and an
attempt whose call outlives its bound is observed `unconfirmed`,
`timeout_after_submit`. No claimed attempt waits for its first observation
without end.

### Reporting never gates a notice

The runtime records a notice in its outbox, and submits it, whatever happens
to its report. When an attempt's identity cannot be made durable, because the
store cannot be written or the signing clock cannot issue a value, the runtime
makes the call anyway, for every notice. An attempt whose identity never
becomes durable is then **unreported**: no
record is ever signed for it, and the runtime counts it durably where it can,
and in memory otherwise, and reports the count in its health. A full
report queue, a report that cannot be signed, or a report write that fails
leaves the outbox and the notice exactly as they would be with no report at
all. An attempt needs no report key to be made durable: one made durable while
the key was not loaded is reported once it loads, under [Publication](#publication), unless a
destructive reset or a move comes first, under *Every record has one key*. No later record names an unreported attempt, so its absence is visible to
a reader only as a gap in `attempt_seq`, where it is one.

### Consistency across records

Some members describe the attempt or the notice, not the observation, and
every record about it carries the same values. Every rule here holds within one
`device_id` and one epoch: records under different keys are never judged
against each other.

- **Every observation of one `delivery_attempt_id`** carries the same
  `alert_id`, `notice`, `class`, `channel`, `attempt_seq` and
  `attempted_at_ms`.
- **Every attempt of one `alert_id`** carries the same `notice` and `class`.
- **One `attempt_seq`** names one `delivery_attempt_id`.
- **An observation's `prior_outcome`** is the `outcome` of the observation of
  the same attempt whose `observation_seq` is one lower.
- **The observations of one attempt** that a receiver holds admit at least one
  complete path through the table of
  [Observations of one attempt](#observations-of-one-attempt), even where they
  are not adjacent. A record whose holding would leave them none, as an
  observation 3 beside an observation 1 that was `failed` or `accepted`, is a
  `conflict`. Missing records may leave a path uncertain; they never make an
  impossible one consistent.

A receiver that holds an earlier verified record, and verifies one that breaks
any of these, holds the later one as `conflict` and keeps the earlier, under
[Verifying](#verifying). An observation's identity is
`(device_id, delivery_attempt_id, observation_seq)`. A receiver that does not hold the earlier record cannot
judge the later, and accepts it if it passes every other check. The gateway
judges none of these, since it verifies nothing.

## Notices

`notice` names what kind of notice the attempt carried:

- `optional`: a notice a verified device-policy/v2 `alerts` member or a monthly
  channel cap may withhold.
- `tier_d`: a notice raised by a Tier D trigger, whatever acts it grants, a
  notify-only Tier D trigger included, and a notice of a Tier D act or its
  refusal. The tier of the trigger or act that raised the notice decides it,
  never the tier an alert action declares.
- `protection_degraded`: the mandatory notice that protection is degraded.

`tier_d` and `protection_degraded` are **mandatory**. Neither preferences nor
caps withhold a mandatory notice, so no tally counts one: a tally has no
`notice` member and counts only `optional` notices. A mandatory notice is
reported like any other notice, and its `class` is always `null`.

## Class

`class` is the device-policy/v2 class of the notice, and is not `null` only
when the runtime bound the first-party skill and trigger that raised the notice
to that class, under device-policy/v2 *Alert Class Preferences*. A notice from a
community skill's trigger never has a class, whatever its name.

A name that matches the pattern but that device-policy/v2 does not define is
carried unchanged, as runtime-posture/v1 carries one in `alert_classes`. A
receiver never refuses a record for it. A reader presents it as a class it does
not know, never as one of the classes it knows, and it makes no switch.

- In a submission observation, a mandatory notice with a non-`null` class is
  refused as `class_refused`.
- In a tally, `reason: "disabled"` with `class: null` is refused as
  `class_refused`: only a class can be switched off. `capped` may have a class
  or `null`.

**What the signature proves about a class.** The signature authenticates the
runtime's assertion that it bound the notice to that class. It does not prove
which trigger ran. A receiver can refuse a class on a mandatory notice, and a
`disabled` tally with no class, from the record alone. It cannot refuse a class
the runtime bound wrongly: no binding table owned by the release is published
for a receiver to check against. See [Limits](#limits-and-later-versions).

## Detail codes

`detail` is a bounded code, never free text and never a provider's error
string:

| `outcome` | Permitted `detail` |
| --- | --- |
| `accepted` | `null` |
| `failed` | `provider_refused`, `provider_reported_failure`, `not_submitted`, or `null` |
| `unconfirmed` | `timeout_after_submit`, `response_unreadable`, or `null` |

A code no row lists is outside `detail`'s form, and is `malformed`. A listed
code is refused as `detail_refused` when its row is not the record's `outcome`,
and also when `prior_outcome` is `accepted` and the code is not
`provider_reported_failure` or `null`, or `prior_outcome` is not `accepted` and
the code is `provider_reported_failure`. After an `unconfirmed`, `failed` may
carry `not_submitted` or `provider_refused`, for a runtime that later learns
which.

No record carries a recipient's number or address, a provider message
identifier, a provider account, message text or template variables.

## Withholding tallies

A tally counts the notices withheld under one tally key.

- **What increments it.** One eligible `optional` notice withheld at the
  runtime's policy decision point, by a verified device-policy/v2 `false` for its
  class (`disabled`) or by a spent monthly channel cap (`capped`), increments
  the count by one. The decision point is where the runtime would otherwise
  record the notice in its outbox, after the trigger's cooldown has applied. A
  continuing condition therefore counts once for each time its trigger raises a
  notice: once per cooldown window, or once per matching reading for a trigger
  with no cooldown. A notice the runtime would not otherwise have raised
  increments nothing. The preference and the cap are judged before the
  recipient, so a notice withheld by either is counted whether or not a
  recipient is configured.
- **The month.** `month` is the calendar month in UTC of the signing-clock value
  at the decision. The signing clock never goes back, so a step of the wall
  clock never moves a count into an earlier month. The month is not claimed to
  match any period a cap is counted over.
- **Durable.** The count is durable and survives every restart on the same
  store. It is committed before the record that carries it is signed, after the
  withholding decision and off every notice's path: it delays no other notice.
- **A snapshot, not an increment.** Each tally record carries the cumulative
  count for its tally key. A receiver keeps, for each tally key and epoch, every
  snapshot it stored, and presents the one with the greatest `count`; it never
  adds records together. A record with a count below the greatest held is
  `lower_count` and changes nothing; a record with the same count as any held
  one but different bytes is `conflict`, as check 6 of [Verifying](#verifying)
  says.
- **Coalesced.** The runtime publishes a tally only when its count has risen
  since the last one it published for that key, at most once in any 60 seconds
  for each tally key, and carries only the latest count when it does. A record
  is signed once and retransmitted with its exact bytes.
- **Bounded.** A runtime keeps tallies for the current month and the month
  before it. When a month begins, it drops every tally of any month before the
  previous one, with its queued snapshots, and counts as an unreported
  withholding each increment that no acknowledged snapshot carried.
  Within one month, it keeps tallies for at most 10 distinct class names on
  each channel, plus `null` for `capped`, whatever classes it binds across that
  month's reloads. So for each channel and month there are at most 10
  `disabled` tallies and 11 `capped` tallies, and a runtime keeps at most
  (10 + 11) × 2 channels × 2 months = 84 tallies. A withheld notice whose class
  would be an eleventh name in its month is counted in that month's `capped`
  or `disabled` **overflow**: the runtime counts it durably and reports it in its
  health. It increments no tally, and no record carries it.
- **Overflow.** A count that reaches 2^53 − 1 stays there, and no further
  snapshot is published for its key.
- **At a rotation.** Before the new report key signs anything, the runtime
  signs, under the outgoing key, each tally whose count rose since its last
  published snapshot. An increment it cannot sign so is counted as an
  unreported withholding. The new epoch's counts start from the withheld
  notices after the rotation.
- **Never gates.** A withholding decision whose month cannot be read from the
  signing clock, or whose count cannot be committed, increments no tally: the
  runtime counts it as an unreported withholding in its health. The notice is
  withheld, or not, exactly as it would be with no report.

**Epochs and resets.** Tallies are kept and compared per epoch. A new report key
starts every tally again from its first withheld notice, and a reader presents
the tallies of each epoch apart, never summed. A runtime store that is lost,
replaced or restored under the same key, which [Key changes](#key-changes)
forbids a runtime that can tell, restarts its counts. A later snapshot equal to the held count with
other bytes is `conflict`, which makes the reset visible then. A snapshot below
it is `lower_count`, which ordinary reordering on the way also produces, so it
shows nothing by itself. A snapshot that has already passed the held count, as coalescing
can make the first one after a reset, is `stored`, and the count presented then
undercounts what was withheld, without any sign.

**Presenting a tally.** A reader presents a tally as "N notices withheld this
month" for its channel, class and reason, with the epoch it belongs to. It never
invents alert identifiers or per-notice entries for a tally. A tally key with no
record held is **unknown**, not zero.

## Reading a notice

A reader that holds submission observations derives, for each `alert_id` and
`channel` of one `device_id` and one epoch, from the records it
holds as `stored`:

- **Latest attempt state**: the `outcome` of the highest-`observation_seq`
  observation held for the attempt with the greatest `attempt_seq`.
- **Ever accepted**: whether any observation held for any attempt on that
  channel is `accepted`.

For each `alert_id`, it also derives **accepted on some channel**: whether
*Ever accepted* holds for any channel. A failover that succeeded on the other
channel then stays visible from the notice as a whole, within its epoch. A
notice whose attempts span epochs, as one pending across a rotation does, is
presented per epoch, each apart: a reader never joins epochs on `alert_id`,
since nothing links epochs and a receiver cannot tell whether two share a
store, so an earlier epoch's acceptance stays
in view in its own epoch's presentation. Every attempt of a retired epoch whose
last held observation is not `failed` is presented as last reported, its
reporting possibly incomplete.

A reader presents all three. A newer `failed` attempt never erases an earlier
attempt's acceptance, and a later provider failure of an accepted attempt reads
"provider accepted, then reported failure". SMS and WhatsApp are presented
separately, and neither stands in for the other. A reader never knows that it
holds every attempt of a notice, nor every observation of an attempt whose
`observation_seq` has a gap, so it presents what it derived as what the records
it holds say, never as complete.

## Signature

The signing input is the ASCII bytes `ori.alert_delivery.v1`, one NUL byte,
then the canonical bytes of the record without its `signature` member. The
report key signs it with Ed25519. A verifier applies
[ed25519-key-admission/v1.md](../ed25519-key-admission/v1.md) to the key and
verifies under [ed25519-verification/v1.md](../ed25519-verification/v1.md); any
failure is `signature_invalid`. Both kinds share the one signing input, and
`kind` is a signed member, so a signature over one kind verifies for no record
of the other.

**Why the evidence device key may sign it.** Every other input the evidence
device key signs either begins with `{` and contains no NUL byte, or begins
with an ASCII prefix other than `ori.alert_delivery.v1` followed by a NUL byte.
A report signing input begins with `o` and contains a NUL, so it is none of
those, and none of them is a report signing input. The known uses are those
runtime-posture/v1.md *Why the evidence device key may sign it* lists,
`ori.runtime_posture.v1`, and this contract's two prefixes:
`ori.alert_delivery.v1` for records and `ori.report_key_enrolment.v1` for the
enrolment proof under [Key trust](#key-trust). Neither prefix is a prefix of
the other, because each is followed by its NUL. A runtime MUST NOT sign under this key any input that
breaks the rule.

**Signing clock.** `issued_at_ms` and `attempted_at_ms` come from the signing
clock of runtime-posture/v1.md *Publication*: never issued twice, strictly
increasing across restarts on the same store, durable, and no more than 30000
ms ahead of the runtime's wall clock. A runtime without such a clock signs no
record.

## Publication

The runtime publishes each record on `ori/{device_id}/runtime/alert-delivery`,
under [gateway-api/v2.md](../gateway-api/v2.md), as an MQTT message at QoS 1
with the retain flag clear.

- **Its own queue.** Records wait in a durable report queue, separate from the
  notice outbox. A record is committed to the queue after the outbox state it
  reports is committed, in a step of its own; nothing in the notice outbox
  waits on the report queue, as [Reporting never gates a notice](#reporting-never-gates-a-notice)
  requires. A runtime that stops between the two steps derives the record again
  from the outbox's state when it starts. The runtime queues the report's state
  and signs a record when it can. A record is signed once, and its bytes are
  then the ones every retransmission sends.
- **Retired only by custody.** A record leaves the queue only when the gateway's
  `queued` acknowledgement for it is applied (below). MQTT PUBACK retires
  nothing. A record not acknowledged is republished with its exact bytes, with
  bounded back-off, and every publication, a republication included, keeps the
  runtime's pace under [gateway-api/v2.md](../gateway-api/v2.md#payload-volume)
  *Payload Volume*: at most 10 records in any 10 seconds to one gateway.
- **A tally replaces its own predecessor.** A new snapshot of a tally key
  replaces any unacknowledged snapshot of the same key in the queue, so the
  queue holds at most one snapshot per tally key, and at most 84 of the current
  epoch.
- **Bounded.** The report queue holds at most 4096 records. When a record
  arrives at a full queue:
  1. if the new record is an observation of an `optional` notice, the runtime
     drops the oldest queued observation of an `optional` notice, which may be
     the new record itself;
  2. if the new record is an observation of a mandatory notice, the runtime
     drops the oldest queued observation of an `optional` notice, and when
     there is none, the oldest queued observation of a mandatory notice;
  3. a tally always has room, since the queue reserves 84 places for tallies
     that observations never take.

  These rules rank records of the current epoch. A record signed under an
  earlier report key takes no reserved place, and is dropped before any record
  of the current epoch, oldest first, whatever its kind. A dropped tally's
  increments since its last acknowledged snapshot are counted as unreported
  withholdings.

  Each dropped observation is counted durably by the kind of its notice, and
  the counts are reported in the runtime's health. They never reset within an
  epoch. A dropped observation can be the only `accepted` of its attempt, so a
  reader's *Ever accepted* can read false for a notice a provider accepted;
  see [Reading a notice](#reading-a-notice).

## Carriage and custody

The gateway is a **blind courier**. It takes custody of each record and forwards
it, and it never verifies a signature, judges an outcome or orders records: a
record's authenticity and meaning are the receiver's to decide, under
[Verifying](#verifying). It holds no runtime key, and its acceptance of a record
says that it holds the bytes durably, never that they are the runtime's.

A gateway that serves `device_id` subscribes to its alert-delivery topic and
judges each message in this order. The first check that fails is the answer.

1. [Payload Size](../gateway-api/v2.md#payload-size), then
   [Payload Volume](../gateway-api/v2.md#payload-volume).
2. [Payload Member Rule](../gateway-api/v2.md#payload-member-rule).
3. Not the canonical bytes of the object it parses to: `not_canonical`.
4. `v` is an integer under the integer rule of [Records](#records), other than
   `1`: `unsupported_version`. A `v` outside that rule, `0`, a negative or one
   above 2^53 − 1 among them, is `malformed`. Otherwise, not a
   record of either kind, with every member present, of its type and within
   its form: `malformed`.
5. The topic's device is not in `gateway.device_ids`: `unknown_device`.
6. The record's `device_id` differs from the topic's device: `device_mismatch`.
7. The gateway's custody queue, by the SHA-256 digest of the record's exact
   bytes: a digest already held is `replayed`, and changes nothing. A queue
   holding `max_records_per_device` records for the device is `queue_full`.
   Otherwise the record is committed to the queue. A held digest is `replayed`
   even when the queue is full. While the gateway cannot read or
   write its custody queue, a record that passes checks 1 to 6 is
   `store_unavailable`, and changes nothing.

**Different bytes under one identity are both carried.** Records with the same
observation identity, or the same tally key and count, but different bytes have
different digests, and the gateway queues each. It cannot tell which one the
runtime signed, and a record it could not verify must never displace one it
could not verify either: a party that publishes on the topic could otherwise
block the runtime's genuine record by sending its own first. The receiver
verifies each and judges them; see [Verifying](#verifying).

After the queue commit, or a refusal at checks 3 to 7 for a configured device,
the gateway publishes an acknowledgement on
`ori/{device_id}/runtime/alert-delivery/ack`, QoS 1, not retained, under the
runtime–gateway envelope with `message_type` `alert_delivery_ack`, as
gateway-api/v2.md *Runtime Alert Delivery Acknowledgement* defines it. The gateway's
custody is configured under gateway-config/v2.md `alert_delivery`. A message
refused at check 5 is not acknowledged: as in gateway-evidence-carriage/v1, an
unconfigured device is neither admitted nor answered, and the runtime keeps the
record and retries.

```json
{
  "acknowledged_at_ms": 1787000001000,
  "auth": {
    "scheme": "hmac-sha256",
    "signature": "hmac-sha256:...",
    "signed_at_ms": 1787000001000
  },
  "device_id": "site-a-edge-01",
  "outcome": "queued",
  "reason": "",
  "record_digest": "sha256:..."
}
```

| Member | Value |
| --- | --- |
| `acknowledged_at_ms` | The gateway's wall clock when it decided: its claim, which orders nothing. |
| `device_id` | The device of the topic the record arrived on. |
| `outcome` | `queued` for a commit or a `replayed` record; `refused` otherwise. |
| `reason` | `""` when `queued`; otherwise the refusing check's reason. |
| `record_digest` | `sha256:` and the lowercase hexadecimal SHA-256 of the record's exact bytes. |

A runtime ignores an acknowledgement whose `record_digest` matches no record it
holds, as a forged record's acknowledgement does, and one whose `outcome` it
does not know. It treats a `reason` it does not know as retryable, so a later
gateway's reason never makes it drop a record. A `queued` acknowledgement
retires the record from the runtime's queue: it says the gateway holds the
bytes durably, and never that a receiver stored them.

`queue_full` and `store_unavailable` describe the gateway's state, and
`unsupported_version` the versions the gateway takes, never a fault in the
record, so all three are **retryable**: the runtime keeps the record and
republishes it with bounded back-off, and a record waiting on a retry never
holds back another record. Every other refusal is terminal for the record: the
runtime counts it by reason in its health, and drops it. The acknowledgement's
signing time is strictly increasing, as gateway-evidence-carriage/v1
*Outbound acknowledgement* requires of `auth.signed_at_ms`.

The gateway's custody queue is bounded per device, so one device cannot exhaust
another's. The gateway reports its backlog and every refusal at checks 3, 4, 6
and 7 in its site health, under gateway-api/v2.md *Alert-delivery custody*, and
counts an unconfigured device's messages, with size, volume and member-rule
refusals, in its operational posture. `replayed` is not a refusal. It retires a record only as the forwarding hop's contract allows, and
never on its own acknowledgement to the runtime.

## Forwarding

The forwarding hop is defined by its own contract, alert-delivery-transport/v1 (#405).

The gateway forwards each queued record to the report receiver, as its exact
bytes, under its own contract: the endpoint, the gateway's credential scoped to
alert-report forwarding and to the devices and sites it may forward for, and
the responses that let the gateway retire custody. That contract decides when a
record leaves the gateway's queue. Nothing in this one does: no transport
error, no response it does not define, and no acknowledgement to the runtime
retires a record. The gateway's credential authorises carriage only: it never
authors a report.

## Verifying

The **receiver** is the reader that verifies records and decides what they say:
the product's report receiver, and any later reader that holds the same
enrolment. It judges each record in this order:

1. Checks 2 to 4 of [Carriage and custody](#carriage-and-custody), and, in
   place of check 1's MQTT bounds, its own bound of 4096 bytes on the record:
   `payload_too_large`. A receiver receives no topic and holds no
   `gateway.device_ids`, so it runs neither check 5 nor check 6: the forwarding
   permission of check 2, judged against the record's own `device_id`, stands
   in for both.
2. **Forwarding permission.** The gateway that forwarded the record is
   permitted, under the forwarding hop's contract, to forward for `device_id`,
   and, when the receiver holds the record's key enrolled, revoked or not, on
   behalf of the owner its enrolment
   names, as the receiver's own authenticated registry holds it: never as any
   label in the record or the request says, and never as the device's current
   owner. Otherwise `not_owned`. A record whose key is not enrolled for the
   device passes this check on the device alone, and check 3 refuses it.
3. **Key binding.** `key_identity` names a report key enrolled for `device_id`,
   for report signing, under [Key trust](#key-trust): otherwise
   `key_not_enrolled`. A key so enrolled and since revoked: `key_revoked`.
4. The signature fails under that key: `signature_invalid`.
5. The rules that relate members, in this order: the observation table,
   `transition_refused`; the class rules of [Class](#class), `class_refused`;
   the detail table, `detail_refused`.
6. Against the records it holds verified, in this order: bytes identical to a
   record it holds, as `stored` or as `conflict`, are `duplicate`.
   Different bytes under a held identity, an observation's or a tally
   snapshot's, or a record that breaks
   [Consistency across records](#consistency-across-records) against one held,
   are `conflict`. A tally whose count is below the greatest held for its key
   is `lower_count`; a tally with the same count as a held one but different
   bytes is `conflict` even when a greater count is held, since one key signed
   both. Any other record is `stored`.

A record refused at checks 2 to 4 is never presented as the runtime's, and
changes nothing the receiver holds. It can be the forwarder's or the network's,
or the runtime's own record under a key not yet enrolled: see
[Limits](#limits-and-later-versions). Only a verified record
can make another `conflict`, and a `conflict` between two verified records says
that the runtime's key signed both: it is the runtime's equivocation, the key's
compromise, or the runtime's store reset or restored under the same key, and the receiver keeps both and presents neither as settled. A record held as
`conflict` is never the earlier record a later, different one is judged
against, and no reading uses it. Every notice and every tally key that a record
held as `conflict` names, and every one the record it conflicted with names,
is presented as unsettled in its epoch.
A record a receiver cannot verify is never presented as the runtime's.

A record is never refused for its age: one queued while the runtime was
disconnected arrives late and is still the runtime's report. `issued_at_ms` is
the runtime's claim, and is presented as one.

## Key trust

A receiver trusts a runtime's report key only through **enrolment**: an
authorised commissioning act that the receiver records in its own registry, and
that binds:

- the exact public key, as its `key_identity`;
- the runtime device, as its `device_id`;
- the site or tenant the device belongs to;
- the purpose, report signing under this contract, and no other;
- an enrolment revision, strictly increasing for the device.

The owner, the device and the actor's authority come from the receiver's own
authenticated registry and the actor's own authentication, never from the
proof: the proof shows only that the runtime holds the key.

**Discovery is not enrolment.** The installer reads the key at the device,
through the `runtime_device_key` operation of
[operator-socket/v3.md](../operator-socket/v3.md), and that proves only which key
the runtime holds. A key the gateway supplies, one carried with a report, and
one read from any product or fleet API establish nothing.

**Enrolment requires proof of possession.** The runtime signs a challenge the
receiver issues, naming the device, the purpose and the receiver's nonce, under
its report key and under a signing input of its own. The receiver enrols the key
only when that proof verifies, and only for an actor its registry authorises to
commission that device at that site. Each enrolment, replacement, retirement
and revocation is recorded with its actor and time, and is never deleted.

**The enrolment proof.** The receiver issues a nonce: 16 to 32 random bytes,
written as 32 to 64 lowercase hexadecimal characters, an even number, matching
`^(?:[0-9a-f]{2}){16,32}$`, and never issued twice. The
runtime signs, under its report key, the ASCII bytes
`ori.report_key_enrolment.v1`, one NUL byte, then the canonical bytes, as
[Records](#records) defines them, of exactly this object:

```json
{
  "device_id": "site-a-edge-01",
  "key_identity": "sha256:...",
  "nonce": "4f3c2a...",
  "purpose": "alert_delivery_report",
  "v": 1
}
```

`device_id` and `key_identity` are the runtime's own, and `purpose` is the
constant `alert_delivery_report`. The runtime builds the whole input itself. A
caller supplies the nonce and nothing else, and a nonce outside its form is
refused before anything is signed, so the operation never signs bytes a caller
chose. The receiver verifies the proof under the key being enrolled, against the
nonce it issued for that enrolment, and consumes the nonce whether or not the
proof verifies. It judges the proof in this order, and the first failure is the
answer:

1. The challenge bytes are not the canonical bytes of exactly the object above:
   not canonical, or members
   missing, extra or of the wrong form, `v` not `1`, or `purpose` not
   `alert_delivery_report`: `challenge_malformed`.
2. `nonce` is not the nonce the receiver issued for this enrolment, or that
   nonce was already consumed: `nonce_mismatch`.
3. `device_id` is not the device being enrolled: `device_mismatch`.
4. `key_identity` is not the `key_identity` of the key being enrolled:
   `key_mismatch`.
5. The key fails ed25519-key-admission/v1.md, or the signature fails under it:
   `signature_invalid`.
6. The key being enrolled is, by the recognised-key rule of
   ed25519-key-admission/v1.md, a key the receiver already holds enrolled, for
   any device and to any owner, this one included, and revoked or not:
   `key_already_enrolled`. A key is enrolled once, and a revoked key is never
   enrolled again. Only an enrolment that passed every check, made by an actor
   the registry authorises, is held: a proof refused, or a request no
   authorised actor made, holds nothing, so no one can claim a key by asking
   first.

Here and in [Verifying](#verifying), a key the receiver **holds enrolled** for
a device is one it has enrolled for report signing, revoked since or not. A key
enrolled only for another purpose is not held.

The proof is produced locally, at the device, by the `report_key_enrolment_proof`
operation of [operator-socket/v3.md](../operator-socket/v3.md), beside
`runtime_device_key` and under that contract's reach and caller authority. It
is never reachable through a remote command, a configuration document, a
gateway or MQTT topic, or a product or fleet API.

**Retirement is not revocation.**

- **Replacement.** An evidence key rotation gives the runtime a new report key,
  which is enrolled as a new revision. The key it replaces is **retired**: the
  receiver keeps verifying records under it, which can arrive long after the
  rotation, and presents them as that key's epoch. Retirement bounds nothing a
  holder of the retired key can still sign: a record's epoch is its key, and its
  signed times are the signer's claim, so a receiver cannot tell a late genuine
  record from one signed after the rotation. Only revocation stops a key.
- **Revocation** says the key is no longer trusted. A receiver verifies nothing
  under a revoked key from the revocation on, whatever its records'
  `issued_at_ms`: a party that holds a compromised key can sign any time it
  likes, so a signed time cannot show that a record predates the compromise.
  A record already verified and stored keeps its bytes and its history, and is
  presented as "verified when received; its signing key has since been
  revoked", never as verified without that qualification.

**Ownership follows the key.** A report key is enrolled for one device, and
to one site or tenant,
and a receiver refuses, at check 6 of *The enrolment proof*, to enrol a key it
already holds. A device moved to another site or tenant is enrolled again,
after the act of [Key changes](#key-changes), under a new report key, so its new
owner's records begin a new epoch and nothing of the earlier owner's is signed
under it. A
verified record belongs to the owner its key is enrolled to: never to the
device's current owner, nor to the owner of the gateway that forwarded it. A
report that arrives late therefore stays with the customer whose epoch it
belongs to, and is admitted only through a gateway permitted to forward for that
owner. The act of a move drops the earlier owner's records
still queued at the device, so none leaves the device for the new owner's
gateway. Records already in a gateway's custody are the gateway's: a gateway
that stays when its site changes owner keeps them, and the receiver refuses
them `not_owned` when they are forwarded on the new owner's behalf, so they are
lost to the earlier owner, and readable by whoever now runs that gateway. The
other way round, a moved device's new records that reach a gateway still
subscribed for the earlier owner are refused `not_owned` there, but held and
readable by that gateway.

**Stale trust is shown as stale.** A receiver whose view of a key's enrolment,
retirement or revocation cannot be refreshed presents the records it verifies
under that key with the age of that view. It never presents them as current.

## Limits and later versions

- **No receipt kind.** `delivered` is refused until a later version defines a
  qualifying provider receipt for each channel.
- **Class bindings are asserted, not checked.** A receiver cannot refuse a class
  the runtime bound to the wrong trigger. A later version may check classes
  against a binding table the release owns and publishes.
- **Tier C approval and startup messages are not reported.**
- **A retry after `unconfirmed` can duplicate a message.** When the runtime
  cannot tell whether a provider received a request, any retry that is a new
  attempt, a failover to the other channel included, may deliver the notice
  twice. A resend under the same provider idempotency key, where the provider
  supports one, is the same attempt and does not.
- **A tally cannot show what it counted.** A tally has no `notice` member, so a
  receiver cannot detect a mandatory notice wrongly counted in a `capped`
  tally. ori-runtime is the enforcing repository for counting only `optional`
  notices.
- **No report without the evidence key.** The report key is the evidence device
  key, so a runtime with evidence disabled, or whose evidence key did not load,
  signs and publishes no record. Its notices are submitted as before, and its
  health says reports are unavailable. A reader holds no report for any of its
  notices until the key loads, and that means unavailable, never unsent;
  attempts whose claims committed meanwhile are reported then, unless a reset
  or a move comes first.
- **A notice must be marked mandatory where it is recorded.** `notice` requires
  the runtime to know, at its outbox, whether a notice is `tier_d`,
  `protection_degraded` or `optional`. A runtime that records a mandatory
  notice the way it records an optional one cannot report it truthfully, and
  does not conform. On ori-runtime that marking is ori-runtime#971.
- **A publisher on the topic can fill a device's custody share.** The gateway
  verifies nothing, so it queues every distinct record a party that can publish
  on the device's alert-delivery topic sends. Payload Volume and the gateway's
  per-device custody share bound how much it can queue, and the device's
  genuine records then meet `queue_full` and wait. They are delayed, not lost,
  while the runtime's own queue holds them. Broker access control bounds who
  can publish there. Its messages also spend the device's Payload Volume
  bucket, which delays the genuine records further. The receiver refuses each
  forged record, at `key_not_enrolled` when it names a key not enrolled and at
  `signature_invalid` otherwise, so none is ever presented. How long a gateway
  keeps a record a receiver refused, and so how long a forgery spends custody,
  is alert-delivery-transport/v1's.
- **A record is readable on the broker.** Records are signed, not encrypted, so
  any party that can subscribe to the topic, or read the gateway's custody
  queue, learns each notice's `notice`, `class`, `channel` and outcome, and
  when it was sent: when protection was degraded, among them. Broker access
  control and the ownership and mode of the gateway's custody queue directory
  bound who reads them.
- **The act of a move or a reset is not yet named.** No operation of any
  contract defines it; ori-runtime owns it, and a later operator-socket version
  names it. A device moved by a rotation alone, a new key enrolled to another
  owner without the act, is not detected by a receiver: the earlier owner's
  pending notices can then have later attempts signed under the new owner's
  key, and so be reported to the new owner.
- **An enrolment to the wrong owner, or a `device_id` changed without the act,
  is a dead end.** A key is enrolled once, so a key enrolled to the wrong owner
  is corrected only by revoking it and performing the act, which no contract
  names yet; records it signed stay with that owner. A `device_id` changed
  without the act leaves every later record `key_not_enrolled`, since the key
  cannot be enrolled again for the new identity: it fails safe, and reports
  stop until the act.
- **A rotation leaves a reporting gap.** An attempt of an earlier key that the provider resolves after the rotation never gets that resolution
  reported. How often this happens depends on how often keys rotate and how long
  provider receipts take, neither of which this contract measures; the runtime's
  count of unreported observations is the only measure of it.
- **Dropped observations are counted, not recovered.** A runtime whose report
  queue overflows loses the dropped observations; its health says how many.
- **A wall clock stepped back stops signing until it catches up.** The signing
  clock never goes back and runs at most 30000 ms ahead of the wall clock, so
  after a step back larger than that, the runtime signs no record until its
  wall clock passes the last value issued. Its notices are unaffected. Reports
  of attempts claimed before the step wait as queued state, so they are late,
  not lost. An attempt made during the step cannot claim `attempted_at_ms`, so
  it is unreported, under [Reporting never gates a notice](#reporting-never-gates-a-notice).
- **Records under a key not yet enrolled are refused until it is.** Between a
  key change and the new key's
  enrolment, every record the runtime signs is `key_not_enrolled` at the
  receiver. The runtime has already retired them on the gateway's `queued`.
  Whether the gateway keeps them for a later attempt, and for how long, is
  alert-delivery-transport/v1's. A key replaced before it was ever enrolled can
  never be enrolled, since the proof is signed only by the key loaded in the
  run, so its records are lost, unless a restore of the store loads it again.
- **A crash can lose an attempt uncounted.** An attempt whose call was made
  before its identity became durable, followed by a crash, is neither reported
  nor counted: nothing durable records it.
- **A retired key still verifies.** A party that obtains a retired report key
  that is not revoked can sign records a receiver verifies, and with a high
  `attempt_seq` can make its own attempt the latest of a notice. A key
  suspected of exposure is revoked, never only retired.
- **An undetected restore lowers counters.** A runtime that cannot tell its
  store was restored keeps signing under the same key over lowered
  `attempt_seq`, tally counts and, where its minting allows, reissued
  `alert_id` values. A reused `attempt_seq` is held as `conflict`,
  and both notices are presented as unsettled; a restored `attempt_seq` below
  every held one can order a new attempt below an older one, so a reader can
  misjudge which is latest. A reset the runtime can tell makes a new key, under
  [Key changes](#key-changes), and has neither effect.

## Representable and enforced

Nothing here is enforced by any production consumer. The runtime is the
enforcing repository for minting, recording, signing and publishing reports
(ori-runtime#528); ori-gateway for custody and forwarding; and the product's
report receiver for enrolment, verification, storage and presentation. The
forwarding hop is #405's.

**Design targets with no runtime yet.** No runtime rotates its evidence device
key: `ori.evidence.rotation.v2` is unimplemented, so the rotation rules of
*Every record has one key* and *Key changes*, signing under the outgoing key
included, are design targets. ori-runtime today refuses to make a key again
when its key cannot be unsealed, and evidence becomes unavailable instead; the
rule for a key made again binds only a runtime that does.

**Health this contract names but does not define.** The runtime's counts of
unreported attempts, observations and withholdings, among them those a
rotation, a reset or a move leaves, dropped observations by notice kind, class
overflow and terminal refusals by reason, and its report that reports are
unavailable, have no member in runtime-health/v4, so no consumer can read them
yet. A later runtime-health version owns them. runtime-health/v4 *`alert_outbox`
object* also says "delivery is unconfirmed" of an alert no provider has
accepted; that is not this contract's `unconfirmed`, and a reader never takes one
for the other.

**Rollout.** Consumers come before producers: a gateway, and then a receiver,
take a version before any runtime publishes it. A record of a version a gateway
does not take is `unsupported_version`, which the runtime retries rather than
drops. The runtime-health members that count unreported attempts, observations
and withholdings and dropped records are adopted by a health version before any
runtime publishes this one, so the losses this contract names are visible when
it ships.

## Vectors

[vectors/alert-delivery-v1.json](vectors/alert-delivery-v1.json) holds:

- **`test_keys`**: Ed25519 test keys, each seeded but the negated one by the SHA-256 of the ASCII label
  `ori alert-delivery/v1 <name> test key` as its 32-byte seed, with its public
  key and `key_identity`. They are test keys only.
- **`records`**: records as exact bytes, each with the verdict a gateway gives
  it at checks 1 and 3 to 6 of [Carriage and custody](#carriage-and-custody), for the
  topic device and configured devices the case names, and the verdict a
  receiver gives it at checks 1 to 5 of [Verifying](#verifying), for the
  enrolments and forwarding permissions the case names. Every refusal reason of
  both lists, other than those of the Payload Member Rule and Payload Volume,
  which gateway-api/v2's corpora hold, has a case refused for that reason
  alone; every outcome, every row of the
  observation table, every detail code and both record kinds have an accepted
  case; and `delivered` is `malformed`. Accepted cases hold the longest record
  of each kind the rules permit together, each string at the longest and each
  integer at the largest its rules allow alongside the others, and the longest
  submission whose `notice` is mandatory. Each is under the 1024 bytes
  gateway-api/v2.md *Payload Size* claims for the record topic.
- **`receiver_sequences`**: records in arrival order, each with the verdict the
  receiver gives it at check 6, and after the last, the reading of
  [Reading a notice](#reading-a-notice) and the tallies held. They cover a
  duplicate, a conflict under one identity, a breach of each rule of
  [Consistency across records](#consistency-across-records), every impossible
  history of one attempt's observations in every subset and arrival order, a
  lower count, a
  later failure of an accepted attempt, a failed retry after an accepted
  attempt, failover to the other channel, and tallies of two epochs kept apart.
- **`carriage_sequences`**: messages in arrival order with the gateway's
  custody verdict: `queued`, `replayed`, both records of a pair with one
  identity and different bytes queued, and `queue_full` at
  `max_records_per_device`.
- **`enrolment`**: enrolment proofs, each with its challenge's canonical
  bytes, its signing input and its signature, and the receiver's verdict, with
  a case for each refusal reason of *The enrolment proof* that fails that check
  alone wherever the order allows one; and enrolment sequences, proofs judged in
  order against what earlier ones left held, so that a proof refused at any
  check holds nothing and the same key's later valid proof passes.
- **`config`**: gateway-config/v2 `alert_delivery` load-rule cases, one for
  each rule and accepted cases.

It is reproduced byte for byte by `scripts/generate-alert-delivery-vectors-v1`.
`scripts/check-alert-delivery-vectors-v1`, which shares no code with it, holds
the corpus to this text, and with `--mutations` shows that each of its checks
fails on a corpus or text altered to break that check.

These rules have no corpus case and are exercised by no vector: the runtime's
report queue, its drop order, its reserved tally places and its pacing; when an
attempt is unreported, and the delay guarantee; what a reset or a move drops and
the observations a rotation leaves unreported; a same-key resend after `unconfirmed`; tallies signed at a
rotation; tally coalescing and month boundaries; the gateway's
custody store and its acknowledgement's signing time; key retirement,
revocation and stale trust; and every presentation rule.
